# 업데이트 검증 폼 — 개발 전달 명세

작성일: 2026-10-24 · 공통 기록 의미 대조: 2026-10-27. 필드 키·화면 구성·저장/API는 개발팀 설계 대상이다. 공통 규칙은 03·05와 [최소 명세](결과기록_최소명세_초안.md), 구현 인계는 [개발팀 인계 명세](개발팀_인계명세.md)를 따른다.

이 문서는 프레임워크의 적용·판정 규칙을 화면으로 구현하기 위한 별도 명세다. 공통 기준은 [02 환경 적용](../02_환경별_적용기준.md), [03 CHK](../03_체크리스트와_보완가이드.md), [05 공통 적용·결과 기록](../05_평가와_증거관리.md)을 따른다. 기존 CHK·분기·판정 조건을 사용한다. 아래 서비스 등록·수집·선정·실행·연동 동작은 구현 목표이며 실제 지원 범위는 화면에 표시한다.

## 1. 이용 단위와 입력 원칙

- 업데이트 평가 한 건은 현재 환경·후보 환경, 정책·체크리스트 판본, 선정 목록과 개별 시험 결과를 묶는다. 현재/후보 결과는 각 환경으로 구분하고 하나의 판정 필드에 덮어쓰지 않는다.
- 정책 결정·환경 자료 제공·시험 수행·검토·승인 역할을 조직 계정에 배정한다. 팀 이름을 고정하지 않고 기존 권한·겸임 규칙을 적용한다. 권한 없는 사용자는 해당 역할에 확인·승인을 요청할 수 있다.
- 기존 서비스 자료·승인 정책·평가 기록을 먼저 불러온다. 출처와 현재 대상의 일치 여부를 확인하고 변경·미정·만료·확보 실패한 부분만 질문한다. 최초 등록이면 환경·정책 확인을 별도 준비 작업으로 안내한다.
- 입력·저장은 초안부터 가능하다. 실제 시험은 실행 권한·안전 조건·시험 준비를 확인한 범위에서 수행한다. 미정 정책에 의존하는 충족 판정은 보류하고 이미 확인한 위반은 유지한다.
- 입력 개수는 자료 확보 수준과 실제 변경에 따라 달라진다. ‘77개 CHK × 모든 결과 필드’를 기업 담당자의 수기 입력으로 제시하지 않는다.

## 2. 화면 1 — 평가 대상 지정

키는 이 폼의 권고 이름이다. 결과 JSON 필드와 별도로 평가 묶음에 저장하고, 다음 화면에서 환경·정책 기록에 연결한다.

| 항목·권고 키 | 필수 시점 | 기본 확보·입력 | 값이 없을 때 |
| --- | --- | --- | --- |
| 서비스 `service_ref` | 평가 대상 지정 | 등록 서비스 선택. 최초 이용이면 이름과 관리 대상 지정 | 서비스 등록·환경 자료 확보로 안내 |
| 현재 환경 `current_environment_ref` | 비교·실행 준비 | 서비스의 현재 배포 기록을 불러와 출처·확인 시점 표시. 플랫폼 역할이 실제 상태 확인·수정 | 기존 환경 자료 연결·내보낸 파일 업로드·수동 확인 요청 |
| 후보 자료 `candidate_source_ref` | 업데이트 대상 지정 | 후보 배포 기록 선택, 불변 이미지 참조 또는 배포 자료 업로드 | 버전명만 있으면 후보 구성 미확정 표시. 추출 못 한 필수값만 요청 |
| 시험 환경 `test_environment_ref` | 실행 준비 | 준비된 시험 환경 선택. 접근·자원·실제 실행 대상 확인 | 준비 담당자 지정·요청. 초안 저장 가능 |
| 이전 평가 `prior_assessment_ref` | 재사용 검토 시 | 같은 서비스의 이전 기록 제안, 사용자가 대상 일치 확인 | 최초 평가로 진행. 기존 통과를 생성하지 않음 |
| 확인·승인 역할 `role_assignments` | 역할에 해당하는 검토·결정 시 | 서비스의 기존 역할 배정을 재사용 | 조직 권한에 맞춰 배정·확인 요청 |

비밀키·토큰 원문을 입력받지 않고 비밀 저장소·접근 권한의 참조를 사용한다. 이미지·설정 등 추출값은 출처·시각·수집 성공 여부와 함께 보여주며, 수동 정정 시 이유와 근거를 기록한다. 시험 환경에서 운영 환경으로 결과를 적용할 범위와 실제 구성 차이도 기록한다.

## 3. 화면 2 — 변경·정책·시험 계획 확인

| 확인 묶음 | 미리 보여줄 내용 | 사용자 행동·조건부 입력 | 확인 역할 |
| --- | --- | --- | --- |
| 변경 범위 | 현재/후보 엔진·이미지·모델·Gateway·권한·기능·의존성 차이와 미확인 | 맞음 / 수정 필요 / 확인 필요. 수정 시 해당 값·출처만 보완 | 환경 자료 제공·검토 |
| 위협·영향 판단 | 변경 근거와 실제 경로·자산·경계·보호 조건의 영향, 관련 요구·CHK·분기와 선정 이유 | 기존 변경 기록 참조 또는 판단 보완, 대응 공백·남은 확인·담당 지정 | 평가 검토, 개발·운영의 근거 제공 |
| 정책 | 기존 승인 판본·적용 범위·유효기간과 이번 변경에 관련된 값 | 유지 / 변경 / 확인 필요. 변경·미정인 값만 단위·적용 범위·근거·승인 상태와 입력 | 정책 소유·승인 |
| 평가 선정 | 77개 CHK의 적용·비적용·미정 및 이유, 필요한 실제 분기·케이스, 기존 증거 재사용 범위 | 누락·제외·대표 범위 검토, 남은 쟁점 기록. 미정은 자동 제외하지 않음 | 평가 검토 |
| 시험 준비 | 입력 자료·계측 지원 여부·정상 대조·자원·예상 점유 시간·운영 영향·중단·복구·정리 계획 | 검토 완료 / 수정 요청 / 확인 요청. 미정 시간·예산 등을 임의 숫자로 채우지 않음 | 시험 수행·운영 영향 승인 역할 |

화면은 위 묶음으로 제시하되 ‘한 번 확인’으로 모든 항목이 충족·승인되는 기능을 만들지 않는다. 상세 값과 근거는 펼쳐 확인한다. 선정·비적용 검토, 시험 준비 확인, 조직의 승인 권한은 각각 처리한다. 실제 지원하는 Q selector의 출력을 77개 CHK·분기의 자동 선정 결과로 표시하지 않는다.

정책을 유지해도 실제 설정·통제 효과의 증거는 별도 확인한다. 변경·만료·접근 권한 부족 등이 없는 값은 재작성 대신 기존 기록 참조를 저장한다. 자동 추출·판정이 지원되지 않는 경로는 수동 검토 대상으로 명시한다.

## 4. 추가 질문을 만드는 규칙

| 질문 유형 | 질문을 표시할 조건 | 받아야 할 답변 | 답변 후 처리 |
| --- | --- | --- | --- |
| 환경 사실 | 적용·분기·판정을 바꿀 실제 구성 정보가 미정·충돌·오래된 상태 | 현재 대상의 값과 근거 또는 확인 필요 | 영향받는 선정·재사용 범위 재검토 |
| 정책 값 | 필요한 허용표·수치·기한의 승인 기준이 없거나 적용 범위·유효성이 불명확 | 승인된 기존 기준 참조, 변경 제안 또는 확인 요청 | 승인 상태를 구분. 기준 확정 후 의존 판정 재검토 |
| 실행 증거 | 해당 CHK의 필수 경로·정상 대조·관측이 부족 | 기존 증거 참조, 추가 시험 계획 또는 확보 불가 사유 | 재사용 가능 범위 검토 또는 추가 실행. 남은 범위 미확인 |
| 시험 미지원 | 실행기·입력 자료·계측·환경이 준비되지 않음 | 준비 담당·후속 처리 또는 미지원 유지 | 구현·준비 과제로 남기고 해당 실행을 완료 처리하지 않음 |

같은 사실·정책을 쓰는 질문은 적용 범위·판본이 같은 경우 묶는다. 사용자에게 질문 내용, 필요한 이유, 관련 CHK 목록, 사용할 기존 자료, 확인 역할을 보여준다. ‘모름·확인 요청’을 선택할 수 있게 하고 `null`을 `false`·해당 없음으로 바꾸지 않는다. 여러 항목이 같은 자료를 참조해도 각 판정은 유지한다.

추가 요청 저장에는 `질문 유형 / 확인할 사실·값 / 대상·적용 범위 / 관련 CHK·분기 / 기존 근거 / 부족한 이유 / 다음 행동·담당 / 답변·출처·확인 시점`을 둔다. 이 목록은 개발용 저장 권고이며 새로운 CHK 필수 증거를 추가하는 기준이 아니다. 승인·보완 기한은 조직 규칙에 따라 기록한다.

## 5. 화면 3 — 검증 진행과 결과

시험 케이스별 준비·실행·수집 상태를 구분하고, 보안·정상 기능·성능 판정을 각각 표시한다. 필요한 케이스 목록·실행한 케이스·남은 미확인을 함께 보여준다. 자동화 미지원 시 수동 시험 증거를 연결할 수 있게 하되 검토와 판정 근거를 남긴다.

결과 첫 화면에는 다음을 표시한다.

- 비교 대상·실제 시험 환경과 정책·체크리스트 판본, 평가 범위·비교 불가 조건.
- 미충족의 위반 사실·증거·보완, 미확인의 부족한 내용·추가 확인, 재사용한 근거의 범위.
- CHK별 적용 분기·케이스·필수 증거·보안/기능/성능 결과의 상세 보기.
- 보완·재시험 요청, 보류, 권한자의 배포·재개 결정 및 조건. 권한 없는 이용자는 검토·승인 요청.

완료율·통과율을 제공하면 필요한 시험 목록의 완결 여부와 미실행·미확인·비적용을 함께 표시한다. 실행된 시험만을 분모로 삼아 전체 검증 성공으로 요약하지 않는다. 기존 집계 규칙은 [05](../05_평가와_증거관리.md#결과-기록과-집계)를 따른다. 폼의 승인 동작과 실제 배포 실행은 별도 권한·연동 작업으로 둔다.

## 6. 결과 JSON과의 대응

[data/result_template.json](../data/result_template.json)은 개별 시험 결과의 빈 양식이다. 평가 묶음·업로드 파일·역할 배정 전체를 한 결과 JSON에 중복 저장하지 않는다.

| 폼·시험 정보 | 결과 기록 |
| --- | --- |
| 결과 기록 식별 | `record_id`를 도구가 생성 |
| 대상 CHK·주 보호 요구 | `assessment_id`·`protection_requirement_id`를 기준 판본에서 선택 |
| 기준·선정 분기 | `checklist_revision`·`test_branch_ref`. CHK·판본·기존 분기명/SC/`apply_when` 원문으로 유일하게 참조 |
| 실제 케이스·범위 | `test_case_id`·`test_case_parameters`·`procedure_version` |
| 환경·정책 | `environment_id`·`environment_revision`·`policy_revision`·`policy_values`, 출처·확인 필드 |
| 도출 근거·공유 시험 초점 | 기존 `question_id`·`shared_question_ids`·`scenario_ids`·`subtest_id` 유지 |
| 실행·수집·증거 | `execution_id`·실행/수집 상태·시각·`evidence`·`facts`·`limitations` |
| 판정·후속 처리 | 보안/기능/성능 판정·`normal_control_result`·보완 담당/기한·`retest_conditions`·`approval` |

같은 실행이 여러 CHK를 평가하면 실행·증거 참조를 공유하고 결과 기록은 나눈다. 분기 아래 실제 경로·상태 조합이 여러 개면 케이스를 나눈다. 미실행 기록에는 실제 실행 ID·시각·측정값을 만들지 않는다. 완료한 수동 검토는 EVD·검토자·시각·절차 Ref로 식별하고 출처 상한을 유지한다. 화면에서는 검토 완료와 필요한 엔진 시험 미실행을 함께 표시한다. 공통 확인·116분기·9필수 결과와 주/보조 요구의 실제 기여 범위를 각각 보존한다. 결과 양식의 필드는 사용자에게 전부 입력받는 화면 항목 수가 아니다.

과거 기록에는 새 필드를 검토 후 연결한다. 실제 시험 범위를 확인하지 못한 Q 중심 기록을 다대다 연결로 모든 CHK에 통과 복사하지 않는다. 새 필드를 무시하거나 거부하는 기존 가져오기·저장·내보내기 코드가 있는지 개발팀이 확인하고 갱신한다.

## 7. 입력 부담 예시와 구현 확인

기존 서비스·정책·시험 환경이 준비된 경우 첫 화면은 서비스·후보 자료·시험 환경의 3개 지정 항목을 중심으로 구성할 수 있다. 현재 환경·이전 기록·역할은 재사용한다. 다음 화면에서 변경·정책·선정·시험 준비를 확인하고 마지막에 처리 결정을 남긴다. 실제 질문 수는 변경·누락·미지원에 따라 달라지며 최초 등록·미정 정책에 대한 고정 최소 입력 수는 정하지 않는다.

개발팀은 다음 경우로 폼 흐름을 확인한다.

1. 엔진만 변경하고 정책은 유효함: 정책을 다시 입력받지 않고 영향 시험·남은 미확인을 표시한다.
2. 응답 허용 기준이 없음: 관련 CHK를 연결한 정책 질문을 한 번 제시하고 해당 기준에 의존하는 충족 판정을 보류한다.
3. 자료 수집 실패·미지원: 확인 요청·수동 자료 제공 경로를 표시하고 해당 없음으로 제외하지 않는다.
4. 일반 응답만 시험함: 남은 필수 옵션·오류 경로를 미확인으로 남긴다.
5. 같은 실행이 여러 CHK의 증거를 제공함: 실행 참조는 공유하고 CHK별 판정·범위는 분리한다.
6. 과거 결과의 CHK·분기 연결이 불명확함: 원본을 보존하고 연결 검토 대상으로 표시한다.
7. 승인 권한이 없는 이용자 또는 만료된 정책: 해당 역할 확인을 요청하고 임의 승인하지 않는다.

엔진별 실제 시험·수집·조건식·지원 기능은 개발팀이 구현한다. 정책값·허용 관계·위험 수용·승인 권한은 적용 조직이 결정한다. 질문을 구성하다 기존 공통 규칙으로 결정할 수 없는 요구가 발견되면 근거와 함께 프레임워크 검토로 넘긴다.

## 8. 시험 전 기준 보완의 구현 인계 — 2026-10-25

프레임워크 공통 기준은 [05 업데이트 영향평가 인계](../05_평가와_증거관리.md#update-impact-handoff)와 [분기 참조 규칙](../05_평가와_증거관리.md#result-record-template)을 따른다.

- 변경 자료의 입력·추출과 영향 검토 기록을 실제 업데이트 흐름의 선정·실행으로 연결한다. 자동 추천과 사람이 확인한 판단을 구분한다. 저장 구조·수집기·화면은 개발팀이 정한다.
- 기준 판본에서 `test_branch_ref.apply_when`을 채우고 저장·가져오기·내보내기 시 보존한다. 사용자가 원문을 매번 입력할 필요는 없다. 기존 CHK ID를 보존하며 이름·SC가 같아도 적용 조건이 다른 분기의 결과를 합치지 않는다.
- CHK-SUP-008, CHK-REQ-018, CHK-REQ-020, CHK-PLT-008의 중복 이름 분기를 각각 저장·복원해 해당 판본의 한 분기로 대응되는지 확인한다. 실제 시험 조건은 `test_case_parameters`에 별도로 유지한다.
- 과거 자료에서 분기 연결이 불명확하면 원본·판정을 보존하고 검토 대상으로 표시한다. 조건이 다른 분기나 다른 환경에 기존 합격을 복사하지 않는다.

프레임워크 담당자는 요구·범위 공백과 판단 규칙 충돌을 검토한다. 개발·시험 담당자는 수집·실행 지원과 실제 증거를 제공한다. 적용 조직은 정책값·역할·위험 수용·배포 승인을 정한다. 이 절은 구현 요청이며 구현 완료를 나타내지 않는다.
