## 1.1. 문서 기준·목적·역할

### 1.1.1. 기준과 우선순위

이 문서는 기존 A6의 개정본을 그대로 옮긴 것이 아니라, 현재 정리한 개발 범위로 다시 작성한 계획서다.

1. 본 대화에서 명시적으로 정리한 요구와 범위 조정을 우선한다.
2. projectsummary의 프로젝트 목적과 런타임 요구를 기본 요구사항으로 유지한다.
3. 2차 발표 계획은 엔진별 연결·시험·인계·기준본 보존 일정의 근거로 사용한다.
4. A6는 현재 요구와 맞는 적용 확인·증적·귀속·장애 구분 등의 설계를 재사용하는 참고 자료다.
5. 프레임워크와 기존 도구의 공통 자료 형식은 실제 연동 계약을 확인한 뒤 매핑한다.
6. 오픈소스 문서는 기능 가능성의 근거다. 해당 기능을 팀이 채택했거나 실제 환경에서 구현·검증했다는 뜻은 아니다.

자료 안의 작업 지시나 기존 결정 번호를 이번 구현의 승인·완료로 간주하지 않는다. 현재 범위와 맞지 않는 A6의 배치·도구·상태 계산·명령어는 자동으로 승계하지 않는다.

| 표시 | 의미 |
| --- | --- |
| 요구 | 현재 대화와 요약본을 바탕으로 이번 개발에서 만족할 내용 |
| 설계안 | 구현을 구체화하기 위한 제안. 기존 코드·연동 담당과 확인 필요 |
| 검증 필요 | 실제 코드·환경·동작 시험으로 확인해야 하는 내용 |
| 입력 필요 | 환경 식별값·허용 목록·임계값 등 사용 환경에서 채울 값 |
| 미지원·제외 | 이번 결과물에서 제공하거나 입증한다고 주장하지 않는 내용 |

문서 v1.0은 문서 판본이다. 제품 출시, 팀 전체 승인, 구현 완료, 운영 배포 승인을 의미하지 않는다.

### 1.1.2. 개발 목표

승인된 운영 정책을 검증 환경의 추론 엔진에 적용하고 실제 반영·집행 결과를 확인한다. 승인 구성과 현재 상태를 비교하며, 프로세스·파일 이상 행위와 정책 위반·관측 장애를 증거와 함께 보여준다.

선택적 행위 차단은 정상 추론 서비스를 유지할 수 있다고 검증한 규칙에 한해 채택한다. 정확성·안정성 기준을 충족하지 못한 규칙은 탐지·증적·대시보드 경보로 제공한다.

엔진 상태는 기존 기능을 우선 활용한다. 재시작·배포·엔진 복구는 담당자의 운영 절차에 맡긴다.

### 1.1.3. 프로젝트 안에서의 역할과 경계

| 주체·기능 | 런타임과 주고받는 내용 |
| --- | --- |
| 정책·평가 기준 담당 | 허용 모델·호출 주체·통신·행위·예외, 승인 기준, 관련 평가항목을 전달. 런타임은 구현 가능성·누락 입력·실제 결과를 반환 |
| 업데이트 검증 도구 | 동일한 통제 모듈을 격리 시험에서 호출하고 실행 ID·증거·판정·보고서에 연결. 정식 입력·출력 형식은 공동 확인 |
| 런타임 개발 | 정책·대상 연결, 적용 확인, 구성 비교, 관측 정규화, 증적 저장, 경보·조회, 최소 재검증 요청 기록 |
| 운영 담당 | 정책·예외 승인, 실제 적용 검토, 재검증 수행 결정, 재시작·배포·복구와 필요한 수동 대응 |
| 추론 엔진 | 일반·스트리밍 요청 처리, 지원되는 상태·로그·지표 제공. 엔진 내부의 모든 보안 요구를 런타임 도구 하나로 입증하지 않음 |

격리 시험은 통제를 검증하는 절차이고, 런타임 통제는 적용·관측 기능이다. 동일 모듈을 두 단계에서 재사용하되 시험 실행과 시험 밖 관측 기록은 구분한다.

## 1.2. 개발 범위와 제외 범위

### 1.2.1. 필수 개발 범위

| 번호 | 범위 | 이번 산출물 |
| --- | --- | --- |
| F1 | 적용 환경·대상 | 전용 시험 환경과 엔진·모델·워크로드 식별, 지원 범위 기록 |

| F3 | 송신·내부 통신 통제 | 허용 목적지·포트·프로토콜 적용, 실제 허용·거부와 필수 정상 통신 확인 |

F1~F8은 이 문서 안에서 사용하는 기능 번호다. 기존 프레임워크의 R 번호나 공통 객체 ID를 대체하지 않는다.

### 1.2.2. 행위 대응의 지원 수준

| 수준 | 결과물의 의미 | 채택 조건 |
| --- | --- | --- |
| 관측·경보 | 지정 행위를 식별하고 대상·규칙·증거를 표시 | 정상 대조·양성 대조, 귀속·수집 상태 확인 |
| 개별 동작 차단 | 특정 실행·파일 접근 등을 실제 거부한 결과를 입증 | 지원 지점·규칙·커널 조합 확인, 정상 기능·오탐·성능 기준 충족 |
| 특정 프로세스 종료 | 서비스와 독립성이 확인된 제한된 대상의 종료 | 기본 필수 범위가 아닌 조건부 확장. 종료 대상·영향·결과를 별도 검증 |

1차는 보호 경로의 쓰기 거부처럼 좁은 동작 하나부터 차단을 검증하는 설계안이다. 실행 거부와 민감 파일 접근 거부는 각각 별도 지원 항목으로 관리한다.

차단 검증에 실패했을 때 관측·경보를 제공하는 것은 허용된 축소 결과다. 다만 실패 원인·서비스 영향·남은 한계를 기록하고 해당 규칙을 차단 지원으로 표시하지 않는다. 관측 기능 자체의 신뢰성이 확인되지 않으면 경보 단계도 완료로 처리하지 않는다.

### 1.2.3. 제외·후속 확장

- 추론 서버·필수 worker 자동 종료, Pod 자동 삭제·퇴출·격리
- 엔진 자동 재시작·재배포·업데이트·롤백, 자동 재검증 실행
- 재검증 실행 큐·담당자 배정·승인 결재 등 별도 업무처리 시스템
- 기업 클러스터 전체, 임의 커널·CNI·다중 노드·RDMA 경로에 대한 포괄 지원
- 1차 필수 시험을 넘는 FQDN·URL 경로 기반 송신 통제
- 별도 종합 서버·GPU 관측 제품 구축과 장기 시계열 분석 플랫폼
- 임의 Python 함수·모든 악성 코드 실행의 완전 탐지, 모든 파일 변경의 완전 탐지
- 집계 지표만으로 요청별 GPU 사용·작업 취소 후 자원 회수·실제 모델 소비를 입증하는 기능
- 경보를 분석해 정책·허용 목록을 자동 생성·완화하는 기능
- 무손실 중앙 전송·무제한 버퍼·자동 재전송 체계

담당자의 기본 복원 절차와 복원 후 정책·관측 재확인은 시험·운영 자료에 포함한다. 자동 복구 제품의 구현과 구분한다.

## 1.3. 대상 환경·배치 구조

### 1.3.1. 환경 기준

- Linux Kubernetes 전용 시험 노드의 등록된 엔진 워크로드를 대상으로 한다.
- 운영 워크로드와 섞인 노드에 특권 센서를 임의 설치하지 않는다.
- vLLM부터 구현·검증하고 SGLang에 공통 계약을 적용한다.
- vLLM 소스 검토 버전과 실제 설치 이미지·의존성 조합을 구분한다. 참조 문서의 v0.31.0은 실제 설치 완료의 근거가 아니다.
- 도구·커널·CNI 버전은 실제 준비 후 고정한다. 최신 문서의 버전을 설치 버전으로 복사하지 않는다.

| 환경 항목 | 기록할 값 | 현재 상태 |
| --- | --- | --- |
| 노드·격리 | cluster ID, node UID, OS·kernel, 전용 여부 | 입력·검증 필요 |
| Kubernetes·네트워크 | Kubernetes·CNI 버전·모드, 정책 집행·관측 기능 | 입력·검증 필요 |

### 1.3.2. 도입 도구를 최소화하는 구성안

추론 엔진과 기존 Gateway를 재사용한다는 전제에서, 추가 상시 구성요소는 Cilium·Tetragon 중심으로 검토하고 Hubble이 필요한 경우 세 번째 후보로 포함한다.

| 후보 | 맡길 역할 | 채택 전 확인 |
| --- | --- | --- |
| Cilium | 워크로드 ingress·egress 정책 집행 | 실제 CNI 구성·권한·기존 정책과의 관계·허용/거부 결과 |
| Tetragon | 프로세스·파일 행위 관측, 지원 지점의 선택적 집행 | 커널·버전·규칙·모드 전환·필터·손실·서비스 영향 |
| Hubble | 통신 흐름·정책 판정 증거 | 필요한 필드·정책 원인·대상 귀속·손실을 기존 출력으로 확보 가능한지 |

도구 2~3개는 추가 도입 목표이며 모든 하위 프로세스·라이브러리 수를 뜻하지 않는다. Cilium이 이미 설치돼 있다면 재사용 여부부터 확인한다. 호환되지 않는 기존 CNI를 이 문서만으로 교체하지 않는다.

기존 Gateway 구현이 요구사항을 충족하지 못하면 재사용·보완·대체에 따른 개발량과 도구 수를 다시 기록한다. 기존 설계가 있다는 이유만으로 재사용 가능하다고 확정하지 않는다. Falco·KubeArmor 등 같은 역할의 센서를 기본 구성에 중복 도입하지 않는다.

기능 근거: [Cilium 정책](https://docs.cilium.io/en/stable/security/policy/), [Hubble 관측](https://docs.cilium.io/en/stable/observability/hubble/).

### 1.3.4. 신뢰·권한 경계

- 정책 적용 자격과 증거 조회 자격을 분리하고 엔진 Pod에 관리 자격을 넣지 않는다.
- 승인 정책은 기존 승인 근거·판본·대상·유효성을 확인한다. 새 승인 서비스를 만들지 않는다.
- 센서·수집 경로의 발신자와 대상을 확인하고, 엔진이 자기 사건을 임의 주입·수정할 수 없게 한다.
- 센서 수신부는 관리 경로로 제한한다. 같은 namespace·ClusterIP만으로 발신자 인증을 대체하지 않는다.
- 조회 화면은 관리 경로와 조회 권한을 적용한다. 요청 주체가 보내는 본문·헤더를 신원이나 정책 승인으로 신뢰하지 않는다.
- 구체 인증·전달 방식은 기존 환경과 함께 D-03에서 확정한다.

## 1.4. 기능별 상세 설계

### 1.4.1. F1 — 대상 등록·현재 환경 확인

**입력:** 승인 환경·엔진·모델 식별값, cluster·namespace·workload selector, 기준 구성 참조.

**처리:**

1. 접근 가능한 실제 cluster·node·workload·Pod·container를 조회한다.
2. 승인 대상과 실제 대상의 일치 여부와 지원 기능을 확인한다.
3. 대상 식별값과 조회 시각을 저장한다.
4. Pod 교체·컨테이너 재시작을 새 관측 대상으로 구분한다.

**출력:** 대상 스냅샷, 지원·미지원·미확인 목록, 기준 구성 연결.

**오류:** 권한 부족·메타데이터 누락·다중 대상 충돌은 자동 추정하지 않는다. 누락 값·원인을 표시하고 해당 적용·판정을 보류한다.

**완료 기준:** 시험·적용·관측이 같은 대상을 가리키고, 이전 Pod의 증거가 새 Pod의 적용 근거로 사용되지 않는다.

### 1.4.2. F2 — API 접근 통제

**입력:** 실제 활성 API 목록, 경로·메서드·모델 허용 목록, 인증 방식·주체·역할, 일반·관리·진단 API 구분, 직통 허용 운영 주체.

**처리:**

1. 기존 Gateway 코드와 경로 정규화·인증·인가·스트리밍 처리를 점검한다.
2. 신뢰할 수 있는 인증 결과로 요청 주체를 확인한다.
3. 허용된 경로·메서드·모델인지 평가하고 엔진 호출 전 허용·거부한다.
4. 일반 호출자의 엔진 직통 경로를 네트워크 구성과 함께 제한한다.
5. 일반·관리·진단 API와 실제 노출 경로를 함께 시험한다. /v1 경로만으로 전체를 대표하지 않는다.

**출력:** 주체·대상·정책·허용/거부·사유·시각, 확인 가능한 요청 ID, Gateway 자체 오류와 엔진 오류 구분.

**정상 기능:** 청크 단위 스트리밍을 유지하고, 취소·타임아웃·업스트림 오류 처리를 검증한다. HTTP 연결 종료만으로 엔진 작업 정리를 입증하지 않는다.

**오류:** 인증 실패에 따른 거부, 정책 평가 오류, 엔진 연결 실패를 다른 원인으로 기록한다. 평가 오류를 정상 차단 성공으로 집계하지 않는다. 정책 부재·평가 오류 시 요청 처리 제안은 §7.3과 D-05에 둔다.

**완료 기준:** 허용 일반·스트리밍 요청 성공, 금지 주체·API·모델 거부, 직통 제한 확인, 정상 요청 오차단·추가 지연 측정.

### 1.4.3. F3 — 송신·내부 통신 통제

**입력:** 대상, 승인 목적지 IP/CIDR·포트·프로토콜, 필요한 DNS·관측·모델 취득·내부 통신, 기존 유효 정책 집합.

**1차 필수 범위:**

- IP/CIDR·TCP 단일 포트 조건의 허용·거부 시험부터 시작한다.
- 인터넷과 사내 서비스 목적지를 모두 정책 대상으로 취급한다.
- 필수 정상 통신은 실제 목적지·포트·프로토콜을 명시해 허용한다. TCP 결과로 DNS UDP 등 다른 경로의 통제를 입증하지 않는다.
- IPv4·IPv6, UDP, FQDN은 실제 선정·검증 범위를 별도 표시한다. 미검증 주소 계열·프로토콜은 지원이라고 표시하지 않는다.

**처리:**

1. 목적지·프로토콜·포트와 정책 결합 의미를 검증한다.
2. 기존 정책과 중첩된 최종 허용 범위를 확인한다. 여러 허용 목록을 임의 합집합으로 만들지 않는다.
3. 정책을 적용하고 현재 설정·대상·집행 상태를 다시 확인한다.
4. 팀 소유 확인 목적지로 허용·금지 시도를 수행한다.
5. 시도 결과·정책 판정·수신 관측·수집 상태를 같은 구간과 대상에 연결한다.

**출력:** 원본 정책 참조, 적용 설정·대상, 시도 ID·연결 정보, 실제 결과, 정책 원인과 증거 위치.

**오류·한계:** timeout·404·수신 없음만으로 통제 성공을 추정하지 않는다. 목적지 미기동·센서 중단·정책 원인 미확인은 별도 사유로 표시한다. 네트워크 제어 밖의 로컬 IPC·RDMA를 자동 포함하지 않는다.

**완료 기준:** 금지 통신의 제한과 허용 통신·모델 로딩·추론·필수 내부 통신의 유지를 함께 확인한다.

### 1.4.4. F4 — 승인 구성 비교

**입력:** 승인 기준 스냅샷, 실제 구성 조회값, 의미 비교할 필드 목록.

| 비교 항목 | 조회·비교 수준 |
| --- | --- |
| 엔진·이미지 | 실제 엔진 버전, 이미지 digest |
| 실행 설정 | 비밀을 제외한 실행 옵션과 선정 환경 설정 |
| 모델 | 모델 ID·고정 revision·승인 파일 식별 정보 |
| 실행 기반 | 계정·권한·마운트·모델 경로 읽기 전용 등 선정 항목 |
| 정책 | 기대 정책과 실제 적용 판본·의미 내용 |

**처리:** 동일한 대상·필드에서 승인값과 현재값을 정규화해 비교하고, 일치·불일치·조회 불가를 구분한다. Pod UID·IP 같은 자동 변동 메타데이터를 의미 구성과 구분하되 사건 귀속에는 보존한다.

**출력:** 승인값·현재값·차이·확인 시각·대상, 관련 정책·평가항목·재검증 요청 기록.

**오류·한계:** 읽기 실패를 불일치로 단정하지 않는다. 파일 metadata·해시 일치와 실제 로딩·소비 확인은 다른 수준으로 표시한다. 모델 전체 파일 검증이 필요한 시험을 metadata로 대체하지 않는다.

**완료 기준:** 통제된 구성 변경을 식별하고, 조회 실패·자동 메타데이터 변화와 구별한다.

### 1.4.5. F5 — 프로세스·파일 행위 관측과 선택적 차단

**입력:** 대상, 실행 단계, 행위 규칙·판본, 정상 예외, 보호·민감 경로, 센서·커널 기능, 규칙별 관측/차단 모드.

| 선정 행위 | 관측할 내용 | 정상 예외의 범위 |
| --- | --- | --- |
| 승인되지 않은 프로세스 실행 | 셸·다운로더·지정 실행 파일과 부모·대상 식별 | 기동 스크립트·승인된 컴파일 도구·유지보수 |
| 보호 경로 변경 시도 | 모델·설정 경로의 쓰기·변경 시도와 결과 | 승인된 재배포·모델 교체·캐시·로그 경로 |
| 지정 민감 파일 접근 | 워크로드에 불필요한 자격증명·호스트 파일 접근 | 실제 정상 동작에 필요한 파일 목록 |

**처리:**

1. 대상 필터·규칙 적재·센서 상태를 확인한다.
2. 정상 기동·로딩·추론·컴파일·유지보수와 무해한 양성 대조를 관측한다.
3. 예외를 조정하고 탐지 대상이 여전히 식별되는지 재시험한다.
4. 좁은 동작 하나부터 지원되는 지점의 거부를 구현·시험한다.
5. 실제 거부 결과와 정상 서비스 영향 기준을 확인한다.
6. 기준을 충족한 규칙만 차단 지원 목록에 등록한다. 나머지는 관측·경보 또는 미지원으로 기록한다.

Tetragon은 지원되는 지점에서 호출 반환값을 바꾸는 동작 거부와 프로세스 종료 신호를 제공한다. 종료 신호만으로 이미 진행된 동작을 되돌리거나 반드시 막는다고 볼 수 없다. 임의 함수에서 모든 행위를 거부할 수 있다고 가정하지 않는다. [공식 집행 설명](https://tetragon.io/docs/concepts/enforcement/)

**출력:** 규칙·판본·모드·대상·실행 파일·부모·대상 경로·단계·시각·귀속·관측/집행 결과·증거·손실 정보.

**필수 제약:**

- 추론 서버·필수 worker·그 스레드를 자동 종료하지 않는다.
- 자식 프로세스라는 사실만으로 서비스와 독립적이라고 판단하지 않는다.
- 접근 거부도 엔진 오류·중단을 일으킬 수 있으므로 정상 기능 시험을 생략하지 않는다.
- write 관련 사건을 관측했다는 사실과 실제 파일 내용 변경을 구분한다.
- 요청·사용자 귀속은 별도 신뢰 가능한 연결이 있을 때만 기록한다.
- 센서가 사건을 내보내지 않았다는 사실만으로 안전·차단 성공으로 판정하지 않는다.
- Python 내부의 모든 함수·import·악성 코드 실행을 포괄 탐지한다고 주장하지 않는다.

**완료 기준:** §7의 관측→차단 검증과 정상 서비스 기준 충족. 차단이 어려우면 탐지·증적·경보를 제공하고 제한을 명시한다.

### 1.4.6. F6 — 엔진 기본 상태 조회

**입력:** 관리 경로의 엔진 상태·로그·지표, 실제 지원 지표 목록·단위, 수집 주기·최신성 기준.

**처리:** vLLM 내장 기능을 먼저 사용하고 요청 실행·대기·지연·처리량·KV 캐시·선정 오류 상태를 수집한다. SGLang은 자체 제공 항목을 공통 의미에 매핑하고 미제공 항목을 표시한다.

**출력:** 지표명·단위·대상·기간·수집 시각·판본·최신성·임계값 초과 여부. 누적 계수와 기간별 비율을 구분하고 재시작에 따른 계수 초기화를 기록한다.

**오류·한계:** 지표 누락·수집 실패를 0으로 표시하지 않는다. 엔진 지표를 서버 전체 GPU·CPU 관측으로 확대 해석하지 않는다. 지연·처리량 비교는 같은 워크로드·조건에서 수행한다.

**완료 기준:** 실제 제공되는 선정 항목 조회·표시와 수집 중단·오래된 값 구분. 임계값은 정상 부하 측정 후 고정한다.

vLLM의 /metrics는 엔진 지표를 제공한다. 현재 문서와 실제 채택 버전의 지표 이름·의미를 다시 대조한다. [vLLM 공식 지표](https://docs.vllm.ai/en/latest/usage/metrics/)

### 1.4.7. F7 — 정책 적용·변경 이력

**입력:** 승인 정책 참조·판본·대상·유효 기간·승인 근거, 기존 적용 상태, 후보 설정.

**처리:**

1. 정책 출처·대상·유효성·지원 범위를 확인한다.
2. 적용할 설정으로 변환하되 허용 목록·예외를 조용히 추가·삭제하지 않는다.
3. 기대 정책과 실제 설치된 정책을 구분해 저장한다.
4. 설정 재조회와 선정 허용·거부 시험으로 실제 상태를 확인한다.
5. 적용·변경·철회와 실패·확인 시각을 이력에 남긴다.

**출력:** 기대/적용 정책, 설정 반영·동작 확인 결과, 실패 사유, 변경 이력.

**오류:** 새 후보의 실패와 기존 정책의 실패를 구분한다. 읽기 실패로 적용 성공을 추정하지 않는다. 확인되지 않은 후보를 현재 유효 정책으로 교체하지 않는다.

**완료 기준:** 승인 입력→설정 반영→동작 확인→조회·증적 연결이 일관되고, 정책 변경 후 판본과 관측 구간이 섞이지 않는다.

### 1.4.8. F8 — 관측 장애·정책 유효성·증적 기록

**입력:** 각 수집부의 상태·시각·손실, 현재 정책·유효성 확인 근거, 위반·구성 차이·적용 실패 기록.

**처리:**

1. 수집 정상·중단·지연·손실·확인 불가를 구분한다.
2. 정책의 적용 여부와 승인 유효성을 별도 확인한다.
3. 중앙 연결 실패·정책 만료·철회·초기 부재·확인 실패를 기록한다.
4. 사건·현재 상태·경보·증거·최소 재검증 요청 기록을 저장·표시한다.
5. 연결 단절 중 기존 제한이 유지되는지 실제 시험하고 결과를 기록한다.

**출력:** 상태 스냅샷, 관측 구간·누락 사유, 정책 유효성 결과, 사건·증거 링크.

**제약:** 센서·중앙 연결 장애만으로 정책을 자동 해제·완화하거나 서버를 종료하지 않는다. 유효성을 확인하지 못한 정책을 유효하다고 표시하지 않는다. 자동 복구·재배포·시험 실행 큐는 만들지 않는다.

관측 경로의 장애와 실제 집행 경로의 장애는 별도로 확인한다. 사건 수신이 중단됐다는 사실만으로 설치된 커널·네트워크 규칙의 집행 중단이나 정상 집행을 추정하지 않는다.

**완료 기준:** 오래된 정상 화면과 현재 정상 상태를 구분하고, 확인된 위반이 수집 장애 때문에 지워지지 않는다. 관측 불가를 안전·준수로 바꾸지 않는다.

## 1.5. 정책·대상·기준 구성 관리

### 1.5.1. 승인 입력과 최소 연동 계약

기존 승인 체계에서 확인 가능한 정책 참조·판본·대상·기간·승인 근거를 입력받는다. 별도 승인 키·결재 서비스를 새로 만들지 않는다. 기존 검증기·서명·번들 검증이 필요한 경우 해당 인터페이스를 재사용하고 확인한 범위만 문서화한다.

| 교환 항목 | 최소 내용 | 연동 책임 |
| --- | --- | --- |
| 정책 입력 | 정책·판본·대상·허용/금지·예외·기간·승인 근거 | 정책 담당과 런타임 담당 |
| 기준 구성 | 엔진·이미지·모델·선정 옵션·권한·마운트 | 환경·배포 담당과 런타임 담당 |
| 적용 결과 | 기대/적용 설정·대상·조회·동작·실패 사유 | 런타임 담당 |
| 관측·증적 | 사건·상태·관측 구간·수집 상태·위치·무결성 정보 | 런타임·검증 도구 담당 |
| 재검증 요청 기록 | 발생 사유·관련 항목·대상·정책·증거 | 런타임 생성, 기존 절차에서 담당자 처리 |

최소 교환은 버전이 명시된 JSON과 증거 참조로 정의하는 설계안이다. 파일 전달 또는 기존 API 중 실제 접점을 D-03에서 확정한다. 가상의 공통 API·객체 ID를 이미 존재하는 것처럼 사용하지 않는다.

### 1.5.2. 정책별 독립성과 변경

- API·통신·행위 규칙의 적용 상태를 구분한다. 한 영역의 성공으로 다른 영역까지 정상이라고 표시하지 않는다.
- 변경 전후 정책·대상·규칙·모드와 시행 시각을 기록한다.
- 승인 정책이 바뀌면 관련 설정·정상 예외·지원 기능을 재확인한다.
- 철회된 정책을 신규 적용 근거로 사용하지 않는다. 현재 남아 있는 설치 규칙과 승인 상태는 별도로 기록한다.
- 적용 실패 때의 원래 규칙 보존·부분 적용 여부를 확인한다. 자동 복구를 구현했다고 주장하지 않는다.

### 1.5.3. 기준 구성의 깊이

1차는 선정한 배포·실행 구성과 조회 가능한 모델 식별 정보의 비교다. 모델 파일 전체 해시, 실제 프로세스가 읽은 파일, 실제 추론에 소비한 모델을 각각 다른 확인 수준으로 둔다.

새 기준 구성의 승인은 기존 담당자 절차를 사용한다. 런타임이 발견한 현재값을 자동으로 새 승인값으로 삼지 않는다.

## 1.6. 이벤트·상태·증적 형식

### 1.6.1. 자료 단위

| 단위 | 의미 |
| --- | --- |
| 대상 스냅샷 | 특정 시각에 확인한 실제 환경·워크로드·컨테이너 |
| 정책 적용 기록 | 기대 정책과 실제 설정·적용·동작 확인 |
| 사건 기록 | 특정 동작·변경·오류가 발생한 사실 |
| 상태 스냅샷 | 특정 대상·구간의 정책·구성·관측 상태 |
| 증거 항목 | 파일·로그·측정·조회 결과와 출처·크기·해시 |
| 재검증 요청 기록 | 기존 검증 절차에서 사람이 처리할 최소 요청 정보 |

이 단위들은 내부 설계안이다. 기존 A1/A5의 RuntimePolicy·RuntimeEvent·EnforcementStatus·OBS/EVD/RES로 발행할 때는 실제 공통 계약에 맞는 변환·누락 사유를 확정한다. 네트워크 전용 결과 필드에 파일 경로나 프로세스 차단 결과를 억지로 넣지 않는다.

### 1.6.2. 공통 필드

| 분류 | 최소 필드·의미 |
| --- | --- |
| 식별 | 내부 기록 ID, schema version, 사건 종류·출처 |
| 시각 | 발생·수집 시각, 관측 시작·종료, 마지막 정상 수집 시각 |
| 대상 | cluster·node·namespace·workload·Pod UID·container ID, image digest |
| 정책 | 승인 정책 참조·판본, 규칙 판본/해시, 기대·적용 상태, 관측/차단 모드 |
| 행위 | 필요한 API·목적지·프로토콜·포트·실행 파일·부모·대상 경로·단계 |
| 대응 | 요청한 조치, 실제 수행 조치, 수행 결과·근거·미확인 사유 |
| 신뢰성 | 귀속 확인, 관측 상태, 손실·지연·누락·센서 재시작 |
| 연결 | 실제 시험의 실행 ID 또는 시험 밖 관측 세션 ID, 관련 평가항목, 증거 참조 |
| 자료 출처 | 실제 측정·예시·수동 확인 구분, 수집기·parser·규칙 버전 |

적용되지 않는 필드는 값과 사유를 구분한다. 누락·미확인 값을 임의 ID·0·빈 문자열로 채워 근거가 있는 것처럼 만들지 않는다.

실제 시험에서는 기존 실행 ID를 연결한다. 시험 밖 사건 때문에 가짜 시험 실행을 만들지 않는다. 요청 ID는 신뢰 가능한 연동이 있을 때만 추가한다.

### 1.6.3. 탐지·조치·효과의 구분

| 기록 | 의미 | 추가 확인 없이 주장할 수 없는 것 |
| --- | --- | --- |
| 탐지 | 규칙에 맞는 사건을 관측함 | 공격 성공·행위 차단 |
| 집행 시도 | 거부·종료 동작이 실행됐거나 요청됨 | 해당 행위가 실제로 중단됨 |
| 거부 확인 | 오류 반환·보호 대상 결과 등으로 해당 동작 거부를 확인함 | 모든 우회 차단·정상 서비스 유지 |
| 종료 확인 | 지정 프로세스 종료를 확인함 | 이미 발생한 쓰기의 취소·서비스 무영향 |
| 정상 대조 확인 | 선정 정상 작업이 정한 조건에서 성공함 | 임의 워크로드·다른 환경의 무중단 보장 |

API·통신·프로세스·파일 결과를 같은 차단 건수로 합산하려면 집계 기준을 별도 정의한다. 1차 화면에서는 영역·규칙·지원 수준별로 구분한다.

### 1.6.4. 상태를 독립적으로 표현

| 상태 축 | 표시할 내용 |
| --- | --- |
| 정책 유효성 | 확인된 유효·만료·철회·없음·확인 불가, 마지막 확인 시각 |
| 적용·동작 | 미적용·반영 확인·동작 확인·실패·확인 불가 |
| 구성 비교 | 일치·불일치·일부 확인·조회 불가 |
| 관측 | 정상·지연·부분 손실·중단·확인 불가 |
| 행위 결과 | 탐지·집행 시도·거부 확인·종료 확인·결과 미확인 |

위 표현은 공통 교환 enum을 새로 확정한 것이 아니다. 내부 저장값과 공통 형식의 매핑은 D-03에서 정한다.

같은 대상·구간에서 유효한 위반 근거와 센서 장애가 함께 있으면 둘 다 보존한다. 사건의 귀속·무결성 자체가 깨진 경우는 근거 제외 사유를 남긴다. 관측 결손과 확인된 위반을 하나의 정상/비정상 색으로 덮지 않는다.

### 1.6.5. 저장·보존·민감정보

- 초기 설계안은 기존 저장 기능 우선 재사용, 없으면 소규모 JSON/JSONL·증거 파일과 색인으로 시작한다. 별도 중앙 로그 플랫폼을 필수로 추가하지 않는다.
- 동시 기록·쓰기 실패·용량 한도·보존·삭제·재시작 때 누락 구간을 처리하고 표시한다.
- 원본과 정규화 결과의 관계를 남기고, 변경·재분석 때 기존 증거를 덮어쓰지 않는다.
- 파일 증거는 실제 bytes의 크기·해시를 계산한다. 수집 실패·파일 없음은 별도 사유로 기록한다.
- 해시는 내용 일치 확인 수단이다. 저장 관리자까지 포함한 변조 방지를 해시 하나로 보장하지 않는다.
- 엔진에는 감사 기록 수정 권한을 주지 않는다. 조회·기록·삭제 권한을 분리한다.
- 프롬프트·응답·API 키·인증 헤더·환경변수·파일 내용·프로세스 인자 원문은 기본 수집에서 제외한다.
- 비신뢰 문자열의 길이·제어문자·화면 출력을 제한·이스케이프한다.
- 로컬 보관 한도·보존 기간·허용 필드 목록은 D-08에서 확정한다.

## 1.7. 정상 서비스 유지·장애 처리

### 1.7.1. 정상 서비스 유지의 의미

정상 서비스 유지는 검증할 요구사항이다. 제품이 모든 상황에서 무중단이라는 보장은 아니다.

- 추론 서버·필수 worker의 자동 종료·Pod 삭제·자동 재시작을 대응 기능으로 사용하지 않는다.
- 금지 요청·행위가 거부되는 것과 정상 사용자 작업이 실패하는 것을 구분한다.
- 정상 요청·스트리밍 완료, 준비 상태, 필수 프로세스·연결 유지와 오류율·지연·처리량을 확인한다.
- 프로세스가 살아 있다는 사실만으로 서비스가 정상이라고 판단하지 않는다.
- 센서 CPU·메모리·이벤트 부하를 측정한다. 상시 종합 관측 제품을 도입하지 않더라도 시험 중 영향 측정은 수행한다.
- 기준·워크로드·반복 조건을 측정 전에 고정한다. 허용 수치는 D-04에서 측정 근거와 함께 확정한다.

### 1.7.2. 관측에서 차단으로 전환하는 조건

1. 엔진·모델·이미지·워크로드·규칙·예외·관측 구간을 고정한다.
2. 기동·로딩·일반·스트리밍·취소·컴파일·유지보수 정상 대조를 수행한다.
3. 무해한 양성 대조로 규칙·귀속·수집 경로가 작동하는지 확인한다.
4. 예외를 좁게 조정하고 양성 대조를 다시 수행한다.
5. 선정한 동작의 거부와 정상 작업을 같은 조건에서 확인한다.
6. 오탐·서비스 영향·성능·수집 손실 기준을 만족한 규칙만 집행 대상으로 기록한다.
7. 미충족 규칙은 해당 규칙의 집행을 해제·관측으로 전환한 후 적용 상태를 다시 확인한다. 다른 통제까지 일괄 해제하지 않는다.
8. 변경 전후 규칙·모드·시각·이유·확인 결과를 보존한다.

정책 모드 지원은 실제 버전에서 확인한다. [Tetragon 정책 모드](https://tetragon.io/docs/concepts/tracing-policy/mode/)

### 1.7.3. 오류 상황별 처리

| 상황 | 처리 기준 | 상태 |
| --- | --- | --- |
| 잘못된 새 정책·승인 근거·대상 | 후보 적용을 보류하고 기존 적용 상태 확인, 실패·사유 기록 | 요구 |
| 새 정책 적용 중 부분 실패 | 대상별 실제 상태 기록. 기존 규칙 유지 여부 확인 후 담당자 절차로 처리 | 요구 |
| 센서·수집기 중단·손실 | 관측 불가/부분 상태와 구간 기록. 이것만으로 서버 종료·정책 완화하지 않음 | 요구 |
| 중앙 연결 단절 | 기존 승인 정책의 집행 유지 시험, 새 승인·변경 사용 보류, 로컬 한도 내 기록 | 요구 |
| 로컬 저장 용량 초과 | 손실량·구간·저장 실패 경보. 빈 증거를 정상 기록으로 대체하지 않음 | 요구 |
| 유효 정책 없는 초기 준비 | 사전 확인 실패로 기록하고 보호 경로 개시를 보류하는 안. 기존 서빙 대상 임의 종료 없음 | 설계안, D-05 |
| Gateway 인증·인가 실패 | 해당 요청을 거부하고 사유 기록 | 요구 |
| Gateway 정책 평가 내부 오류 | 엔진 직접 우회는 만들지 않고 해당 요청에 오류를 반환하는 안. 정상 정책 차단과 구분하고 서비스 영향 시험 | 설계안, D-05 |
| 정책 만료·철회·유효성 확인 불가 | 상태·확인 시각·경보 기록, 신규 적용 근거로 사용하지 않음. 기존 제한을 임의 해제·확장하지 않음 | 요구, 운영 요청 처리 기준은 D-05 |
| 정상 요청 오차단·영향 기준 초과 | 해당 행위 규칙의 관측 전환·이전 검증 설정 복귀를 담당자가 수행하고 확인 | 요구 |
| 구성 변경 | 차이·증거·경보와 최소 재검증 요청 기록 | 요구 |

특히 유효 정책 부재·평가 오류·만료 시의 요청 처리 방식은 서비스 연속성과 권한 요구를 함께 결정해야 한다. A6의 fail-closed를 확인 없이 모든 통제에 복사하지 않는다. D-05가 닫히기 전에는 해당 장애 동작을 운영 지원 완료로 주장하지 않는다.

중앙이 끊긴 뒤 정책 만료까지 진행되는 경우도 따로 시험한다. 설치된 제한이 남아 있다는 사실을 승인 유효성이 유지된 것으로 표시하지 않는다.

### 1.7.4. 실행 단계·정상 예외

| 단계 | 구분 근거 | 예외 원칙 |
| --- | --- | --- |
| init | 컨테이너 기동·정상 준비 전 단계 | 승인된 모델 로딩·컴파일에 필요한 행위 |
| serve | 서비스 준비 후 | 좁게 선정한 정상 실행·접근 |
| maintenance | 담당자·사유·대상·시작/종료 시각이 있는 승인된 작업 | 작업에 필요한 제한된 예외, 관측 지속 |

단계·예외는 신뢰할 수 있는 관리 경로에서 입력한다. Pod 주석·사건 문자열만으로 예외 권한을 생성하지 않는다. 기한 없는 유지보수 예외를 만들지 않는다.

단계가 불명확하면 근거를 기록하고 새 차단 채택을 보류한다. 기존 API·통신 통제를 임의 완화하지 않는다. 예외 만료 후 차단을 재개할 때도 실제 규칙·단계·정상 기능을 확인한다.

엔진·모델·이미지·규칙·예외 변경 시 관련 시험을 다시 수행한다.

### 1.7.5. 담당자 복원 절차

자동 엔진 복구를 만들지 않는다. 담당자용 절차에는 영향 규칙 식별, 이전 유효 설정 확인, 승인된 변경 경로로 관측 전환·설정 복귀, 실제 적용 재조회, 정상 요청·통신·수집 재확인, 결과 기록을 포함한다.

만료·철회된 승인으로 복원했다고 정상 처리하지 않는다. 엔진 버전 복구와 통제 규칙 복귀를 별도 절차로 기록한다.

## 1.8. 대시보드·기존 도구 연동

### 1.8.1. 필수 화면

| 화면 | 최소 표시 |
| --- | --- |
| 대상·정책 상태 | 엔진·모델·대상, 기대/적용 정책 판본, 적용·유효성 확인 시각 |
| 관측 상태 | 센서·수집부 상태, 관측 구간, 최신성·손실·누락 |
| 구성 비교 | 승인값·현재값·차이·미확인 사유 |
| 경보 목록·상세 | 위반·변경·장애, 행위·주체/대상·규칙·모드·실제 대응·결과·증거 |
| 엔진 상태 | 선정 지표·단위·시각·범위·미제공·임계값 초과 |
| 재검증 요청 기록 | 발생 사유·관련 항목·대상·정책·증거, 내보내기 |

1차 화면은 읽기 전용으로 한다. 관리 인증·조회 권한을 적용하고, 화면 버튼으로 규칙 변경·프로세스 종료·Pod 삭제를 제공하지 않는다. 정책 적용은 기존 승인된 관리 경로를 사용한다.

연결 단절 시 마지막 성공값과 마지막 시각·현재 오프라인 상태를 함께 표시한다. 새로 조회하지 못한 데이터를 현재 정상처럼 보이지 않게 한다. 화면과 보고서가 각자 다른 상태 계산을 하지 않게 같은 원본 결과를 사용한다.

### 1.8.2. 최소 재검증 요청

projectsummary의 재검증 요청 요구는 다음 기록 생성·조회·내보내기로 구현한다.

- 발생 시각·사유: 위반·구성 변경·관측 결손·정책 유효성 등
- 대상·기준 구성·정책·변경 필드
- 연결 가능한 관련 평가항목과 미확인 사유
- 증거 참조·관측 구간
- 요청 기록 식별자·전달 가능한 요약

자동 시험 스케줄링·요청 큐·담당자 배정·처리 상태 업무 흐름은 구현하지 않는다. 담당자가 기존 검증 도구에서 시험 범위를 정하고 수행한다. 기존 API가 있으면 그 계약에 맞춰 기록을 전달한다.

### 1.8.3. 외부 알림·보고서

필수 알림은 대시보드 경보다. Slack·메일·메신저 전송은 별도 합의가 없는 한 제외한다.

기존 검증 도구·보고서에는 사건·정책·대상·시험/세션·증거와 확인 범위를 전달한다. 실제 측정과 예시, 탐지와 차단을 구분해 표현한다.

## 1.9. 시험·완료 기준

### 1.9.1. 공통 실행 조건

- 팀이 소유한 전용 시험 노드·목적지·무해한 파일·규칙을 사용한다.
- 엔진·모델·정책·규칙·시험 절차·워크로드·시간·대상을 고정해 기록한다.
- 정상 대조, 시험 대상 동작, 수집 경로의 양성 대조를 구분한다.
- Gateway 경유와 엔진 직접 호출을 구분해 엔진 자체 효과와 앞단 통제 효과를 혼동하지 않는다.
- 실제 실행 ID가 있는 시험과 시험 밖 관측 세션을 구분한다.
- 정상·위반·미확인·미실행·비적용 사유를 각각 남긴다. 증거 부족을 통과로 처리하지 않는다.
- 아래 RT-*는 본 문서의 시험 식별자다. 기존 TEST/Q/SC ID와의 대응은 연동 때 확인한다.

### 1.9.5. 지원 수준·완료 보고

기능별로 구현 상태, 실제 측정 여부, 시험 환경, 증거 위치, 미실행·미지원 사유를 기록한다.

- 탐지 완료와 차단 완료를 별도 표시한다.
- 경보 제공으로 축소한 행위는 축소 사유와 정상 서비스 영향 결과를 적는다.
- 합성 자료·예시 화면은 실제 실행 결과와 구분한다.
- 필수 항목의 증거가 없으면 전체 완료로 표시하지 않는다.
- 팀 운영 적용 승인은 별도다. 시험 성공이 자동 배포로 이어지지 않는다.
