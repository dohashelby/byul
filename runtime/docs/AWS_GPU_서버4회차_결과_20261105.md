### 1. `bundle build`·`apply`

- 노트북에서 플랫폼 승인 원본으로 묶음 4개를 만들었다. 엔진마다 base 1개와 probe-enforce 1개다. base의 Gateway 정책 바이트(SHA-256 `472a7cca…`)와 intent는 3회차 묶음과 같다. 서버에서 다시 `bundle verify`해 통과했다.
- 실제 apply는 4번 했다. vLLM base, SGLang base, SGLang probe-enforce까지 3번은 `bundle apply`로 했다. 나머지는 아래 문제 2 때문에 수동으로 링크를 교체했다. 매번 이전 `current`를 기록했고, root:10000·0750 복사, 서버 재검증, 상대 링크 교체, Gateway 재시작까지 성공했다.
- **문제 1(도구 결함):** rollout 직후 상태 확인이 매번 30초 동안 `URLError`를 냈다. 도구는 설계대로 "새 링크 유지·수동 확인 필요"로 끝났고, 잘못 되돌리지 않았다. 별도로 새 port-forward를 열어 수동으로 조회하니 `bundle_id` 일치, `gateway_active=true`, 승인 `verified`였다. 원인은 코드 확인 결과 재시도가 같은 port-forward만 쓰는 것이다. 종료 중인 이전 Pod에 붙은 연결을 계속 쓴다(`bundle_tools.py` `_checked_status`).
- **문제 2:** 이미 루트에 있는 묶음 ID로는 apply가 거부된다. 그래서 base 묶음 복귀와 vLLM 복귀는 수동 상대 링크 교체와 재시작으로 했다.
- **문제 3:** `--dry-run`도 묶음 루트(root:10000 0750) 읽기 권한이 필요해 일반 사용자로는 `Permission denied`가 났다. sudo로 다시 실행해 "적용 계획 성공"을 확인했다.

### 4. Tetragon 보호 파일 읽기 차단(AWS-20)

- 차단 시험용 intent에는 가짜 파일 `/run/byul-probe/secret.txt` 한 경로만 넣었다. 실제 서비스 계정 폴더는 차단 대상에서 뺐다.
- 02:03:05Z에 enforce 규칙(Equal + Post + Override argError -1)을 적용했다. Tetragon 상태는 `load_error`였고, 오류는 다음과 같다.
  `override validation failed: can't override 'security_file_permission' function with kprobe_multi, use --disable-kprobe-multi option`
- 커널 확인 결과:
  - `CONFIG_BPF_KPROBE_OVERRIDE=y`, `CONFIG_FUNCTION_ERROR_INJECTION=y`, `CONFIG_BPF_LSM=y`이고 Tetragon `override_return: true`다.
  - 그러나 `/sys/kernel/debug/error_injection/list`(1013개 함수)에 `security_` 함수가 **하나도 없고**, Tetragon의 `lsm: false`다.
  - 따라서 `--disable-kprobe-multi`를 켜도 이 함수에 Override가 될지는 **미확인**이며, 될 가능성은 낮다고 본다(추정).
- 노트북 kind(WSL 커널)의 L-05b에서는 같은 형태의 규칙으로 EPERM 차단이 됐다. **커널에 따라 차단 가능 여부가 다르다**는 것을 실제로 확인했다.
- AWS-20 판정은 `unknown`("적용된 enforce 규칙 또는 monitor 복원 대상 불일치")이다. 차단 효과를 판정하지 않았으며, 차단 실패로도 차단 성공으로도 세지 않는다.
- **감시 공백:** enforce 규칙을 불러오지 못한 동안에는 TG-SECRET-01 감시도 꺼져 있었다. 02:03:05Z에 기존 규칙을 삭제했고 02:03:50Z 무렵 원래 monitor 규칙(두 경로, Post)을 다시 적용해 `enabled`·`monitor_only`를 확인했다. **약 45초 동안 보호 파일 감시가 없었다.** 이 구간의 보호 파일 접근은 관측 불가다.

## 남은 것

1. `bundle apply` 결함 3건 수정과 실서버 재확인: port-forward 재연결, 이미 배치된 묶음으로의 전환, dry-run 권한 안내.
2. Tetragon 차단 방향 재설계. 보호 파일은 설정 예방(서비스 계정 토큰 자동 마운트 끄기, 비밀 미배치, 읽기 전용·권한)을 1차로 둔다. 커널 능력을 판별해 BPF LSM이 있으면 LSM, 없으면 시스템 호출 Override를 보조로 쓰고(우회 한계 표시), 둘 다 없으면 탐지만 한다. 이 환경(BPF LSM 비활성, `security_` 함수 오류 주입 불가)은 "커널 차단 불가, 탐지만"에 해당한다.
3. enforce 규칙을 불러오지 못하면 monitor 감시까지 꺼지는 문제. 앞으로는 규칙을 바꾸기 전에 새 규칙이 로드되는지 먼저 확인하거나, monitor 규칙을 남긴 채 별도 이름으로 enforce 규칙을 추가하는 방식을 검토한다.
4. 실제 자료로 화면 확인(사람).
5. 1회 관찰이며 정식(reference) 환경 평가가 아니다.
