# AWS GPU dev 서버 5회차 확인순서 초안

상태: **실행 전 초안**. 이번 변경에서 AWS를 시작하거나 정책을 적용하지 않았다. 4회차의 `security_file_permission` load 실패와 규칙 삭제 뒤 약 45초 감시 공백을 재발시키지 않는 것이 핵심이다. 4회차 결과는 [결과 문서](../../docs/AWS_GPU_서버4회차_결과_20261105.md), 적용 명령·복구 조건은 [정책 수동적용 절차](정책_수동적용_절차.md)를 따른다. 기록에는 역할·판본·해시·Pod UID·시각·판정만 남기고 비밀 값과 원시 내용은 반출하지 않는다.

## A. 서버 전 준비

1. 플랫폼에서 CONFIRMED 정책 판본과 환경 판본을 골라 **정책 묶음 내보내기**를 수행한다. 받은 `.tar.gz`를 별도 디렉터리에 풀고 `cd runtime && .venv/bin/python -B -m serving_runtime bundle verify --bundle-dir <받은-묶음-폴더>`를 실행한다. `bundle_id`, `bundle.json` 해시, 정책 정규 해시와 네 역할 파일 해시·크기를 응답 기록과 대조한다. 누락 필드나 사람 입력 덮어쓰기가 있으면 출처를 명시하고 승인 판본과 별도 대조한다.
2. 현재 서버의 `current` 상대 링크와 복귀할 기존 묶음 ID, Tetragon 기준 감시 정책의 ID·STATE·MODE, 정상 요청 200과 가짜 파일 monitor 읽기 결과를 기록한다. 실제 비밀 경로를 시험 정책에 넣지 않는다.
3. 방식별 정책은 `protected_paths.enforce_exact_files`의 **가짜 파일**만 선택한다. `override_lsm`, `override_syscall`, `sigkill_fd_install` 중 사전 점검으로 후보를 고른다. 신규 후보는 `spec.options.policy-mode=monitor`여야 한다. 같은 이름을 delete 후 apply하지 않는다. 내용 변경은 `tools/tetragon_mode.py`의 새 이름 적용→enabled 확인→기존 정책 제거 순서만 사용한다.

## B. 서버에서 순서대로 확인

| 순서 | 실행·증거 | 멈춤·복귀 조건 |
| --- | --- | --- |
| 1. 묶음 적용 | [수동적용 절차](정책_수동적용_절차.md)의 `bundle apply --dry-run` 뒤 실제 apply. 재연결된 상태 조회에서 `bundle_id`, `gateway_active=true`, 승인 `verified`, 정상 요청을 대조한다. 이어 `--existing <기존-ID> --dry-run`과 실제 복귀를 확인한다. | 상태 조회 불가·불일치·정상 요청 실패면 성공으로 세지 않고 이전 링크·Pod 상태를 확인한다. |
| 2. 차단 능력 | `cd runtime && .venv/bin/python -B tools/aws_lab_preflight.py --engine <vllm 또는 sglang> --override-check`의 방식별 결과를 기록한다. 커널 버전, `CONFIG_BPF_KPROBE_OVERRIDE`·`CONFIG_BPF_LSM`, `/sys/kernel/security/lsm`의 AppArmor·bpf, 오류 주입 목록의 `security_file_permission`·openat 심볼, Tetragon `tetra probe`를 대조한다. | 근거가 없으면 `unknown`; load 가능이나 차단 효과를 추정하지 않는다. 4회차처럼 security 훅이 목록에 없으면 `override_lsm` 후보를 건너뛴다. |
| 3. 시험용 Pod | 가짜 파일이 마운트된 별도 Pod와 그 Pod만 선택하는 신규 monitor 정책을 준비한다. 먼저 monitor 이벤트를 확인하고 `sigkill_fd_install`과 `override_syscall`을 각각 분리해 MODE 전환한다. 정책 ID 유지·STATE enabled·MODE enforce, 원시 이벤트와 파일 결과, monitor 복귀 뒤 읽기 성공을 확인한다. `sigkill_fd_install`은 종료 코드와 Sigkill 이벤트를 함께 본다. | load 실패·이벤트/파일 결과 불일치·복귀 미확인이면 `unknown` 또는 `failed`를 기록하고 엔진 대상으로 진행하지 않는다. 모드 전환 실패 시 도구의 rollback 결과와 실제 MODE를 재확인한다. |
| 4. 감시 공백 | 전환 전·중·후 정책 ID, MODE, TG-SECRET-01의 monitor/차단 원시 이벤트와 수집 gap을 같은 UTC 시간선에 둔다. 신규 이름 교체는 새 정책 enabled 뒤 기존 정책 제거를 확인한다. | 정책 ID가 예상 없이 바뀌거나 기준 감시가 사라지면 즉시 중단한다. 사건 부재만으로 감시 연속을 증명하지 않는다. |
| 5. AWS-20 | 검토한 monitor manifest와 현재 spec을 먼저 대조한다. `aws_lab_acceptance.py --engine <엔진> --cases AWS-20 --allow-rule-switch --aws20-monitor-manifest <manifest> --aws20-probe-pod <시험용-Pod>`를 시험용 Pod에 우선 적용한다. 방식별 errno 또는 종료·같은 Pod UID 원시 이벤트·같은 구간 정상 요청 200·monitor 복귀를 대조한다. | 근거 부족은 `unknown`. 엔진 대상 Sigkill 계열은 `--allow-engine-sigkill` 별도 opt-in이 필요하다. 현재 `kubectl exec` 읽기 probe는 엔진 주 프로세스를 종료하지 않으므로 그 결과로 503·재시작을 통과 처리하지 않는다. 엔진 주 프로세스에 대한 별도 안전한 시험 절차가 준비된 경우에만 Gateway 503(엔진 미전달)→Kubernetes 재시작→200 복구를 별도 기록한다. |
| 6. 화면 | 실제 Gateway·Tetragon 수집 연결을 확인한 뒤 차단 내역의 Override/Sigkill 원시 action, Pod UID, 시각을 대조한다. Sigkill은 “프로세스 종료”, 양쪽 모두 “차단 시도” 표지로 확인한다. | 합성 자료·수집 gap·시간 불일치면 실제 차단 표시 확인으로 세지 않는다. |

## C. 종료

모든 시험 정책을 monitor로 되돌리고 같은 ID·STATE·MODE를 다시 읽는다. 시험용 정책·Pod만 정리하고 기준 감시 규칙을 유지한다. Gateway는 승인된 기존 묶음으로 복귀해 `current`·`bundle_id`·`verified`·정상 요청을 대조한다. 결과에는 각 단계의 `passed`/`failed`/`unknown`, 복귀 결과와 남은 미확인을 적는다. 복구·증거 정리 뒤 서버 중지를 사용자·Claude 절차에 따라 확인한다.
