# 11/4 AWS GPU dev 서버 1회차 실행순서표

GPU 1장, vLLM → SGLang v0.5.22 → vLLM 순차 실행. 작업 위치는 서버의 `~/byul/runtime`이다. 명령의 `<...>`는 서버 전용 값이며 명령·증거에 주소, 토큰, 실명을 남기지 않는다. 각 인수 명령은 새 `evidence/aws-acceptance-*` 폴더를 만든다. 시간은 계획치이며 실제 시각을 기록한다. 서버 Stop은 증거 반출과 복귀 검증 뒤에만 한다. 단계 실패 시 **즉시 다음 시험을 중단하고**, 오류 코드·시각·기존 증거를 보존하고 해당 단계의 복구 절차를 수행한다. 복구 실패나 증거 미반출이면 서버를 끄지 않고 담당자에게 상태를 전달한다.

공통 인수 명령 접두: `.venv/bin/python -B tools/aws_lab_acceptance.py --kube-context byul-aws-lab --namespace serving-lab --engine <vllm|sglang> --gateway-url http://127.0.0.1:18080 --token-env-file <비공개-토큰-파일> --evidence-dir <증거-부모-폴더>`. 아래 `ACC`는 이 접두를 담은 셸 배열이다. 변경 사례는 표의 `--allow-*`가 있어야 실행된다. Gateway 포워드는 별도 터미널에서 `kubectl --context byul-aws-lab -n serving-lab port-forward deploy/serving-gateway 18080:8080`으로 연다. Gateway 재시작 뒤 별도 실행에 앞서 포워드를 새로 연다.

```bash
cd ~/byul/runtime
ACC=(.venv/bin/python -B tools/aws_lab_acceptance.py --kube-context byul-aws-lab --namespace serving-lab --engine vllm --gateway-url http://127.0.0.1:18080 --token-env-file <비공개-토큰-파일> --evidence-dir <증거-부모-폴더>)
```

2a단계에서 이미지 저장소 디스크 여유를 첫 preflight의 `image_store_disk` 항목으로 확인한다. 다른 경로라면 `--image-store <containerd-저장소-경로> --min-image-free-gib 60`으로 확인한다. 서버를 켜자마자 다음 pull을 백그라운드로 시작하고, 12단계 전에 완료·digest를 확인한다. 공개 index digest는 `sha256:e3a4f06001a29542fc4a8638536d9ffc5eb9c9942b08603c09b19a56eae4a1ae`이며 amd64 manifest digest는 `sha256:5fc09edb6a0bb1d5b6992b543723c66d08f86d7a507e951e87e0d05db4ac766e`다.

```bash
sudo ctr -n k8s.io images pull docker.io/lmsysorg/sglang:v0.5.22@sha256:e3a4f06001a29542fc4a8638536d9ffc5eb9c9942b08603c09b19a56eae4a1ae > <증거-부모-폴더>/sglang-image-pull.log 2>&1 &
# 받은 뒤 kubelet이 찾는 digest 전용 이름으로도 등록한다(없으면 ErrImageNeverPull, 11/3 확인)
sudo ctr -n k8s.io images pull docker.io/lmsysorg/sglang@sha256:e3a4f06001a29542fc4a8638536d9ffc5eb9c9942b08603c09b19a56eae4a1ae
```

12단계 직전에 완료 여부와 이미지·digest를 확인한다.

```bash
sudo ctr -n k8s.io images ls | rg 'docker.io/lmsysorg/sglang:v0.5.22@sha256:e3a4f06001a29542fc4a8638536d9ffc5eb9c9942b08603c09b19a56eae4a1ae'
```

pull은 호스트 프로세스이므로 엔진 Pod용 Tetragon 정책 대상이 아니며, vLLM 시험 기록에 섞이지 않았는지 한 줄로 남긴다.

3단계의 정책 적용은 플랫폼 `aws-lab-policy-001` 승인 판본 `aws-lab-policy-001-v2`(시험용 자기 신고 승인)의 **원본 정규 해시**를 먼저 대조한다. Gateway 파일과 승인 목록·target·intent를 서버용으로 만든 뒤 로컬 `bundle verify`, 서버 복사 뒤 서버 `bundle verify`를 각각 실행한다. `current`는 `ln -s <bundle_id> current.next && mv -Tf current.next current` 방식의 **상대 링크**로만 바꾸고 이전 ID를 기록한다. `kubectl --context byul-aws-lab -n serving-lab rollout restart deployment/serving-gateway` 뒤 `/api/status`의 승인 `verified`를 확인한다. 규칙은 `.venv/bin/python -B -m serving_runtime enforce render --intent deploy/gpu-lab/intent.aws-lab.json --out <규칙-출력-폴더>`로 후보를 만들고 검토 후 적용한다. 적용할 규칙 목록과 원래 AWS 정책 이름을 먼저 기록한다. `runtime-receiver-fixture-ingress`와 불필요한 `runtime-acquire-egress`는 이번 AWS-05 구간에 넣지 않는다. **반입한 이미지와 정책 적용 완료 뒤 preflight를 다시 실행**한다.

Gateway 기대값은 **태그로 비교**한다. 노트북 `docker inspect Id`는 config ID이고 클러스터 Pod `imageID`와 형식이 달라 직접 같은 값으로 판정하지 않는다(kind 리허설에서도 config ID `ef29b1eb…`와 Pod `imageID` `6a817b09…`가 달랐다). 서버에 반입할 tar는 `~/.local/state/serving-runtime/aws-lab/serving-gateway-rt-<sha>.tar`이며 `.build.txt`와 `.tar.sha256`을 동봉한다. 최종 태그는 PR 머지 뒤 빌드에서 정한다.

6단계에서는 AWS 묶음의 원본 `engine-isolation.yaml`에서 **실제 NetworkPolicy 두 이름**을 확인하고 복원 파일의 경로·내용을 먼저 검증한다. 다음 명령 사이의 임시 회수 시간을 기록한다. 회수/복원 오류가 나면 04·05 결과를 합격으로 쓰지 않는다.

```bash
kubectl --context byul-aws-lab -n serving-lab get networkpolicy <기본-정책-1> <기본-정책-2> -o yaml > <증거-부모-폴더>/base-networkpolicy-before.yaml
kubectl --context byul-aws-lab -n serving-lab delete networkpolicy <기본-정책-1> <기본-정책-2>
"${ACC[@]}" --cases AWS-04,AWS-05
kubectl --context byul-aws-lab -n serving-lab apply -f <AWS-묶음>/engine-isolation.yaml
kubectl --context byul-aws-lab -n serving-lab get networkpolicy <기본-정책-1> <기본-정책-2> -o yaml
```

실행 전후 spec·labels를 대조한다. 인수 명령이 실패해도 **복원 명령은 반드시 실행**한다. SGLang 재실행도 같은 복원 절차를 따른다.

```bash
# 서버에서 작업; 검증 전에는 current를 교체하지 않는다.
sudo ctr -n k8s.io images import <gateway-이미지.tar>
.venv/bin/python -B -m serving_runtime bundle verify --bundle-dir /srv/serving/bundles/<bundle_id>
cd /srv/serving/bundles && ln -s <bundle_id> current.next && mv -Tf current.next current
cd ~/byul/runtime
kubectl --context byul-aws-lab -n serving-lab rollout restart deployment/serving-gateway
kubectl --context byul-aws-lab -n serving-lab rollout status deployment/serving-gateway
python3 -B tools/aws_lab_preflight.py --engine vllm --expect-gateway-tag <tag> --expect-engine-digest sha256:<엔진-이미지-digest> --env-file <비공개-토큰-파일> --evidence-dir <증거-부모-폴더>
python3 -B tools/aws_lab_preflight.py --engine sglang --expect-gateway-tag <tag> --expect-engine-digest sha256:<digest> --env-file <비공개-토큰-파일> --evidence-dir <증거-부모-폴더>
```

마지막 SGLang preflight 명령은 **12단계 전환 뒤**에만 실행한다. 두 엔진의 기대 digest는 선언 이미지의 레지스트리 digest 또는 Pod imageID digest이며, 값이 다른 형식이면 각각의 근거를 따로 보존한다.

12단계의 SGLang 관리 키는 [전환 절차](SGLANG_전환절차.md)처럼 비공개 `config.yaml`에만 넣고 `create secret ... --from-file=config.yaml=<비공개-config.yaml> --dry-run=client -o yaml | kubectl ... apply -f -`로 갱신한다. 기존 Secret의 `admin-api-key` 데이터 키가 남으면 전환 절차의 JSON patch로 제거하고 키 이름 조회에서 `config.yaml`만 확인한다. 엔진의 공개 옵션은 `engine.yaml`의 `args`에서 검토한다.

```bash
SACC=(.venv/bin/python -B tools/aws_lab_acceptance.py --kube-context byul-aws-lab --namespace serving-lab --engine sglang --gateway-url http://127.0.0.1:18080 --token-env-file <비공개-토큰-파일> --evidence-dir <증거-부모-폴더>)
"${SACC[@]}" --cases AWS-01,AWS-02,AWS-03,AWS-04,AWS-05,AWS-06,AWS-12,AWS-18,AWS-19 --allow-compare-policy
"${SACC[@]}" --cases AWS-07,AWS-08 --allow-collector-stop --allow-engine-restart
"${SACC[@]}" --cases AWS-04,AWS-05
"${SACC[@]}" --cases AWS-13,AWS-14,AWS-15,AWS-16,AWS-17 --allow-bundle-switch --allow-gateway-restart --allow-collector-stop --allow-engine-restart
"${SACC[@]}" --cases AWS-09,AWS-10,AWS-11
```

SGLang의 04·05 재실행도 위 6단계와 같은 **기본 정책 임시 회수·복원** 뒤에만 수행한다. `--cases AWS-09,AWS-10,AWS-11`에서 11은 현재 SGLang Pod UID의 신선한 단계 시간표와 경고를 대조한다. 16·17도 같은 단계 근거로 판정하며, 근거가 없을 때만 `unknown`이다. 실제 실패를 unknown으로 바꾸지 않는다.

## SGLang 첫 기동 확인 목록

모든 조회는 `kubectl --context byul-aws-lab -n serving-lab exec deploy/serving-engine -c engine -- <명령>` 접두를 사용한다. 원시 설정·키·프롬프트는 저장하지 않고 **성공 여부, 버전, 필드 이름, 오류 종류, 시각**만 기록한다.

| 확인·읽기 명령 | 기대·실패 시 대체 수와 기록 |
| --- | --- |
| `python3 -m sglang.launch_server --help`에서 `--context-length`, `--log-requests`, `--log-requests-level`, `--log-requests-format`, `--enable-metrics`, `--config`와 YAML 설정 지원 확인 | 하나라도 없으면 이미지/버전 불일치로 중단. help 전문 대신 누락 옵션 이름만 기록. 다른 옵션으로 임의 치환 금지 |
| 고정 정상 요청 1건 뒤 `kubectl ... logs deploy/serving-engine -c engine --since=2m`의 JSON 한 줄에서 `headers.x-request-id`와 프롬프트 관련 칸 부재 확인 | 요청 ID가 없으면 AWS-01 로그 대조는 unknown, 요청 로그 설정과 실제 버전을 기록. `text`, `input_ids`, `prompt` 등 칸이 있으면 원문 반출 중단하고 **필드 이름만** 기록 |
| `id -u`와 `id -g` | UID 2000·GID 0 기대. UID 2000 부팅 실패는 오류 종류·마운트 권한 기록 후 중단. root 전환은 **사용자 승인 후에만** 검토 |
| `ss -ltn`으로 내부 8000 리슨 확인 | `ss` 부재면 `netstat -ltn`, 둘 다 없으면 `/proc/net/tcp`의 8000(hex `1F40`) LISTEN 확인. 포트가 없으면 startup 로그의 오류 종류만 기록하고 중단 |
| `python3 -c 'import urllib.request; print(urllib.request.urlopen("http://127.0.0.1:8000/ready").status)'` 및 같은 방식의 `/v1/models` | 200과 모델 ID `test-model` 기대. 실패 시 포트·Pod Ready·HTTP 상태만 기록하고 중단. 응답 전문은 저장하지 않음 |
| `kubectl ... exec ... -- python3 -c 'import pathlib; print(any(b"--admin-api-key" in p.read_bytes() for p in pathlib.Path("/proc").glob("[0-9]*/cmdline") if p.is_file()))'` | 새 manifest의 `--config` 시작에서는 `/proc/*/cmdline`에 `--admin-api-key`가 없어야 한다. 값은 보거나 저장하지 않고 boolean 결과와 접근 가능 범위만 기록한다. `true`이면 이전 셸 시작이 남았는지 확인하고 중단한다. 시작 로그와 `/server_info`의 값 노출은 별도 점검한다. 접근 오류면 검사 불가로 기록한다 |
| `kubectl --context byul-aws-lab -n serving-lab get pod -l app=serving-engine -o jsonpath='{range .items[*].status.containerStatuses[*]}{.name}{"\t"}{.lastState.terminated.reason}{"\t"}{.restartCount}{"\n"}{end}'`; 서버에서 `nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader,nounits` | 엔진 메모리 상한 dev 16 GiB에서 `OOMKilled`·재시작 횟수와 GPU 메모리 사용량을 기록. OOM이면 오류를 기록하고 요청을 중단한다. 상한 상향은 호스트 32 GB 범위에서 사용자 승인 후에만 검토 |
| `python3 -c 'import json,urllib.request; print(json.load(urllib.request.urlopen("http://127.0.0.1:8000/server_info")).get("version"))'` 1회 | 버전만 기록. 실패 시 HTTP 상태·원인만 기록하고 이미지 레이블/패키지 버전과 대조; 원문 저장 금지 |

## 시간이 부족할 때

먼저 **AWS-12·13**을 다음 회차로 미루고, 다음으로 **AWS-07·08**을 줄인다. 07·08을 생략하면 수집 중단·Pod 교체 복구를 입증하지 못했다고 표시한다. 13~17 중 복구가 필요한 시험을 시작했다면 시간 부족을 이유로 정리·복구를 생략하지 않는다. 필수 복귀 확인·증거 반출·Stop 순서는 유지한다.


## 11/3 서버 1회차에서 확인한 운영 주의

| 상황 | 해야 할 일 |
| --- | --- |
| 정책 묶음 폴더 권한 | `/srv/serving/bundles`는 `root:10000 0750`이라 운영 계정이 목록을 볼 수 없다. 묶음 파일 권한 변경은 `sudo sh -c "chmod 0640 <묶음>/*"`처럼 셸 전체를 sudo로 실행한다(사용자 셸의 `*` 확장은 실패). preflight의 `bundle`은 `unknown`이 정상이며, `sudo .venv/bin/serving-runtime bundle verify`로 따로 확인한다 |
| AWS-13 실행 | 묶음 폴더 쓰기가 필요하므로 `sudo -E env KUBECONFIG=$HOME/.kube/config PATH=$PATH .venv/bin/python -B tools/aws_lab_acceptance.py ... --cases AWS-13 --allow-bundle-switch --bundle-root /srv/serving/bundles`로 실행하고, 끝나면 `sudo chown -R ubuntu:ubuntu <증거-부모-폴더>` |
| Gateway 재시작 뒤 | AWS-13·14·15와 엔진 전환 뒤에는 사용자 포트포워드가 끊긴다. 다음 실행 전에 기존 포워드를 끄고 `nohup kubectl ... port-forward deploy/serving-gateway 18080:8080 &`으로 다시 연다 |
| 재부팅 직후 | 이전 엔진 Pod가 `Unknown`·`UnexpectedAdmissionError`로 남을 수 있다. 목록을 증거에 저장한 뒤 그 Pod만 삭제한다 |
| SGLang 캐시 | 새 캐시 경로에는 하위 폴더(`tmp`, `home`, `config`, `xdg`, `hf`, `inductor`, `triton`, `cuda`, `pycache`)를 UID 2000으로 먼저 만든다 |
| SGLang 증거 반출 | SGLang 시작 로그(`server_args`)와 `/server_info` 응답에 관리 키 값이 들어 있다. 반출 전 토큰·관리 키 값으로 증거 폴더를 검사하고, 나오면 해당 값만 가린다 |
| 엔진 한도 | SGLang은 `--context-length N`에서 입력 N-7, 합계 N-2까지만 처리한다. 배포 값은 2112(정책 2048 + 여유 64)이며, 전환 뒤 `preflight --boundary-probe`로 실측한다 |
