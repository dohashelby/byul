# 내부 기록 형식과 계획서 §6 변환표

기준일: 2026-10-25 · 개발계획서 v1.4 §6·§9.8, Git 기준점 HEAD `ce2edd5`에서 시작한 현재 코드. 이 문서는 현재 구현을 설명하며 새 공통 계약을 만들지 않는다.

## 1. 공통 원칙과 경로 표기

- `<data-dir>`은 Gateway의 `--data-dir`이다. 기본값은 `$XDG_STATE_HOME/serving-runtime/mvp` 또는 `~/.local/state/serving-runtime/mvp`다.
- JSONL은 한 줄에 JSON 객체 하나를 UTF-8로 추가한다. `JsonlStore`는 쓰기 뒤 `fsync`하며, 읽을 때 객체가 아닌 줄·UTF-8/JSON 손상 줄은 정상 기록과 섞지 않고 줄 번호와 사유로 돌려준다. 프로세스 안에서는 같은 경로의 append와 보존 rewrite가 같은 잠금을 쓴다. 프로세스 사이 동시 쓰기는 보호하지 않는다.
- 시각은 별도 설명이 없으면 시간대가 있는 ISO 8601 문자열이다. 값이 없거나 확인되지 않았을 때는 근거 없이 `0`이나 빈 문자열을 만들지 않고 JSON `null`, 필드 생략, 빈 배열, 또는 `not_configured`·`not_available`·`unknown` 같은 명시 상태를 쓴다. 형식마다 실제 표현은 아래에 적는다.
- 프롬프트·응답 원문, API 키·Authorization, 환경변수 값, 파일 내용, 전체 프로세스 인자는 내부 정규화 기록의 기본 저장 대상이 아니다. 필요한 입력은 이름·판정·개수·SHA-256처럼 원문을 복원하지 않는 값으로 남긴다. 외부 명령이 만든 raw feed는 이 원칙으로 정규화되기 전 자료이므로 별도 접근 통제가 필요하다.
- 해시는 내용 일치 확인용이다. 저장 관리자까지 포함한 변조 방지나 엔진이 실제로 메모리에 올린 바이트를 증명하지 않는다.
- **외부 형식 매핑은 D-03 이후**에 정한다. 특히 `runtime-revalidation-export/0.1`은 연동 초안일 뿐 RuntimeEvent·OBS/EVD/RES 등 팀 공통 형식이 아니다.

추론 요청 판정은 정책 유효성 → 인증 → 대상 등록 → 본문 순서다. 따라서 인증 실패 기록에는 대상 보류 결과가 노출되지 않고, 인증에 성공한 대상 보류 기록에는 `auth.principal_id`와 역할이 남는다.

## 7. §6.3 탐지·집행 시도·거부 확인의 표현

| 구분 | 현재 표현 | 판정 한계 |
| --- | --- | --- |
| 탐지 | Tetragon `action_mode: monitor`/`action_raw: observed|KPROBE_ACTION_POST`, process/file observation; Hubble flow와 raw verdict | 탐지만으로 공격 성공·행위 차단을 말하지 않는다. Hubble `dropped`도 source/destination·정책 귀속과 receiver 대조 전에는 프로젝트 거부 확인이 아니다. |
| 집행 시도 | Tetragon `action_mode: enforce`와 raw Override action; Gateway의 DENIED/INVALID 결정과 응답 시도; 엔진 일반 4xx·429는 별도 `ENGINE_REJECTED`, 엔진 401/403은 `ERROR` | Tetragon action만으로 syscall/파일 결과를 확정하지 않는다. Gateway 내부 오류와 엔진 거부·upstream 인증 설정 오류는 Gateway 정책 거부로 바꾸지 않는다. |
| 거부 확인 | Gateway `decision.result: DENIED` + 정한 HTTP 상태 + `delivery.attempted: false`; lab의 EPERM/연결 실패·receiver 미수신 등 실제 대조 | 한 요청·probe의 거부만 확인한다. 모든 우회 차단이나 정상 서비스 유지는 별도다. 외부 backend의 미수신은 backend 증거가 없으면 `gateway_only`다. |
| 종료 확인 | 해당 없음 | 프로세스 kill/Pod 삭제를 대응 기능으로 만들지 않았고 종료 확인 공통 기록도 미구현이다. |
| 정상 대조 확인 | 수용/lab/S3B/perf의 정상 일반·stream 사례와 case 결과 | 선정 환경·입력에 한정한다. mock, CPU, local kind를 정식 GPU 결과로 확대하지 않는다. |

## 8. §6.4 독립 상태 축의 현재 위치

| 상태 축 | 현재 위치와 값 | 주의 |
| --- | --- | --- |
| 정책 유효성 | `/api/policy`의 `loaded`, `gateway_active`, validity period/revocation/approval item; policy history의 load event | approval 미설정은 `not_configured`, LAB 검증기는 `verified`/`unverified`/`rejected`/`error`, external enforcement는 `not_connected`; 실제 승인 검증기의 공통 교환 enum은 아니다. |
| 적용·동작 | 후보 manifest annotation, Cilium collector의 object/condition/node 상태, lab case `status`, Gateway delivery | candidate/unapplied, 객체 존재, 실제 probe 결과를 각각 유지한다. 하나를 다른 단계의 성공으로 승격하지 않는다. |

| 관측 | collector `disconnected`/`never`/`ok`/`stale`/`error`, heartbeat, 손상·중복·실행 전·checkpoint reset 수 | 이미 저장된 유효 위반은 현재 collector 장애 때문에 지우지 않는다. |
| 행위 결과 | Gateway decision/final outcome/delivery, observation verdict/action mode, lab case의 실제 probe 결과 | 공통 단일 enum은 미구현이다. 탐지·집행 시도·거부 확인을 영역별 근거와 함께 읽는다. |

## 9. 기록 간 연결 키

| 키 | 생성·등장 위치 | 연결 범위와 한계 |
| --- | --- | --- |
| `request_id` | Gateway가 생성; gateway record, mock receipt, request detail/evidence, 수용·CPU/perf raw 보고서 | 한 추론 요청의 Gateway 단계와 가능한 backend 증거를 묶는다. Hubble/Tetragon 사건에는 신뢰 가능한 전달이 없어 넣지 않는다. |
| `observation_session_id` | Gateway 시작 때 생성; gateway record, policy history, revalidation | 한 Gateway 프로세스 관측 세션을 구분한다. 이전 세션의 모의 live lookup으로 미수신을 단정하지 않는다. |
| `environment` + `run_id` | Gateway/관측 CLI 옵션; gateway record와 normalized observation | 사람이 같은 시험 범위를 지정할 때 교차 조회한다. 이름이 같다는 것만으로 인과를 증명하지 않는다. Gateway scope와 observation scope는 별도 옵션이다. |
| `event_key` | 연속 observation feed가 raw line과 scope를 hash | 회전·재연결 중복 방지용. 직접 ingest 관측에는 없고 request ID가 아니다. |
| policy `policy_id` + `policy_version` + `sha256` | 정책 load/history, gateway record, revalidation, revocation | 같은 논리 판본과 실제 bytes를 함께 식별한다. ID/version만 같고 hash가 바뀌면 별도 재검증 근거다. |
| `target_id` | runtime policy, gateway record, revalidation | 정책이 가리키는 논리 대상. cluster/Pod UID snapshot은 아니므로 실제 workload 교체를 식별하지 못한다. |
| `revalidation_id` + `fingerprint` | revalidation event/summary/export | 같은 근거의 lifecycle과 중복 방지. 같은 scope에서 근거가 바뀌면 기존 event의 `superseded_by`로 새 ID를 잇는다. |
| asset `manifest_sha256` | asset load/check/revalidation evidence | 승인 목록 파일 bytes를 연결한다. 실제 file bytes는 각 항목 `sha256`으로 비교한다. |
| feed path + device/inode + offset | observation checkpoint/heartbeat | 어느 append stream을 어디까지 읽었는지 연결한다. 사건의 의미 ID가 아니다. |
| report `run_id`·case ID·`evidence_request_ids` | lab/perf/수용/CPU 보고서 | 보고서 내부 반복과 요청 증거를 연결한다. 서로 다른 도구의 `run_id` 문자열은 자동으로 같은 실행이 아니다. |
| `rule_id`/policy name | normalized Tetragon observation, candidate manifest, lab 사례 | 규칙 후보와 관측을 보조 연결한다. 실제 적용 판본·Pod 귀속이 없으면 rule ID 하나로 적용/효과를 확정하지 않는다. |

시간 근접만으로 서로 다른 기록의 인과를 확정하지 않는다. 연결 키가 없으면 대상·구간·관리 snapshot과 한계를 남기고 요청별 ID를 만들어 채우지 않는다.

## 10. D-03 경계와 회귀 검사

현재 내부 schema 이름과 필드는 저장소 구현을 위한 값이다. `runtime-revalidation-export/0.1`의 `format_status`가 밝히듯 검증 도구의 RuntimePolicy·RuntimeEvent·EnforcementStatus·OBS/EVD/RES 계약은 합의되지 않았다. 따라서 **외부 형식 매핑은 D-03 이후** 실제 공통 계약, 인증 주체, ID, 누락 사유, round-trip을 확인해 작성한다. 네트워크 전용 필드에 파일·프로세스 결과를 억지로 넣지 않는다.

`tests/test_internal_record_formats.py`는 `src/**/*.py`를 AST로 읽어 문자열 상수 중 `runtime-*` 또는 `serving-runtime-*` 접두와 `/숫자.숫자`(내부 mock pseudo schema는 `/mock`) 패턴에 전체 일치하는 값을 모두 모아 이 문서에 있는지 검사한다. Python 소스 밖의 README/예시/시험 fixture, URL, 필드 이름만 있는 문자열, 그리고 `tools/`의 독립 실행 도구 schema는 이 검사의 대상이 아니다. 독립 도구 형식도 위 §4에는 사람이 확인할 수 있게 별도로 기록했다.
