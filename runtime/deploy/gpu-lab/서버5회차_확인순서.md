# AWS GPU dev 서버 5회차 확인순서

- 작성: 2026-11-06, Claude.
- 기준: main `e5a8ba7`(PR #227 머지) + 모니터 기록 생성기(개발 중, 머지 후 그 커밋으로 교체).
- 목적: 노트북 kind에서 확인한 **대시보드 운영 요청 → 서버 적용 에이전트 → 정책 묶음 적용 / Tetragon 탐지·차단 전환**을 실제 AWS GPU 서버에서 확인한다.
- 근거 문서: [설계](../../docs/설계_원격적용_모드전환.md), [사용과 검증](../../docs/원격운영_사용과검증.md), [4회차 결과](../../docs/AWS_GPU_서버4회차_결과_20261105.md).
- 승인: runtime 담당 자기 승인(LAB). 비용은 약 USD 1.2/시간이다.

## A. 켜기 전 (노트북)

| 순서 | 할 일 | 멈출 조건 |
| --- | --- | --- |
| 1 | 승인 기록(범위: 에이전트 설치, 묶음 원격 적용, TG-SECRET-01 시험용 Pod 차단 전환, 선택적으로 엔진 대상 차단 1회) | 기록 없음 |
| 2 | 같은 커밋으로 Gateway 이미지 빌드(tar·해시·빌드 기록), 서버 반입용 git 묶음 또는 main fetch 확인 | 빌드 실패 |
| 3 | 운영 토큰 4종(operator·approver·agent·viewer)을 비공개 파일에 만들고 해시를 `BYUL_OPERATION_TOKENS`에 넣는다. 노트북 platform(별도 포트)을 띄운다. LAB 자기 승인은 끈다 | 토큰 값이 화면·로그에 나옴 |
| 4 | 플랫폼 승인 원본 `aws-lab-policy-001` r2로 vLLM 묶음 2개를 만든다: `…-op-a`(기본)와 `…-op-c`(intent에 `tetragon_allowed_modes` TG-SECRET-01 monitor·enforce, `tetragon_enforce_method: sigkill_fd_install`, `enforce_exact_files` 가짜 경로). `bundle build` 사용 | verify 실패 |
| 5 | 시험용 Pod(`app=byul-tetragon-proof`, 가짜 파일 `/run/byul-probe/secret.txt`)와 그 Pod를 고르는 `runtime-tg-secret-01`(sigkill_fd_install, **policy-mode monitor**) manifest를 준비한다. B-7 서버 시험과 **같은 spec**이어야 실측 근거가 맞는다. kind 근거는 node·kernel이 달라 AWS에서 재사용할 수 없다 | — |
| 6 | 전체 시험(runtime·web·api) 통과 | 실패 |

## B. 서버 가동 중

| # | 확인 | 방법 | 통과 기준 |
| --- | --- | --- | --- |
| 1 | 켜기·코드·이미지 | 4회차 1번과 같다(새 이미지 import, 묶음 배치는 `bundle apply`) | preflight fail 0, 승인 `verified` |
| 2 | 차단 능력 판별 | `aws_lab_preflight.py --override-check` + sudo로 `/sys/kernel/security/lsm`·오류 주입 목록·`tetra probe` | 결과 기록. 4회차와 같다면 `override_lsm` unavailable, `sigkill_fd_install` unknown |
| 3 | **에이전트 실제 설치** | `/opt/byul/runtime`(root 소유) 복사·venv, `runtime-agent` 계정, `/etc/serving-runtime/{agent.token(0600 root 또는 agent 소유), agent.env, kubeconfig, viewer.env}`, `deploy/agent/sudoers.example`을 서버 값으로 바꿔 `visudo -cf` 확인 후 설치, systemd 단위 설치·시작(**처음엔 dry-run**) | `systemctl status` active, `visudo` OK, `sudo -l -U runtime-agent`가 `bundle apply` 한 형태만 |
| 4 | 플랫폼 연결 | 노트북에서 `ssh -R 127.0.0.1:<서버포트>:127.0.0.1:<노트북 platform 포트>`로 역방향 터널. 에이전트 `--platform-url http://127.0.0.1:<서버포트>` | 에이전트 agent-state가 플랫폼에 보임 |
| 5 | **묶음 원격 적용** | 대시보드: op-a → op-c 적용 요청(다른 사람 승인) → 에이전트 dry-run(`checked`) → `--execute`로 전환 → Gateway 재시작·`verified` | steps 모두 passed, 독립 조회 일치, 감사 기록 |
| 6 | 되돌리기·상태 경쟁 | op-c → op-a 되돌리기(즉시), 오래된 expected 요청 → `STATE_CHANGED` 무실행 | 기대대로 |
| 7 | 시험용 Pod 실측 근거 | 서버 자신이 단일 Kubernetes 노드인 호스트에서 `sudo -n`으로 crictl·uname·procfs 조회가 가능한 사용자로 runtime 디렉터리에서 실행: `.venv/bin/python -B -m tools.tetragon_trial --node-access local-sudo --context byul-aws-lab --image serving-gateway:rt-<sha> --methods sigkill_fd_install --allow-isolated-trials --output <evidence-dir>`. Python 포함 시험 이미지가 노드에 import돼 있어야 한다(기본 imagePullPolicy `IfNotPresent`, 외부 pull 없이 실행하려면 `--image-pull-policy Never`). 호스트 `sudo -n uname -n`과 시험 Pod nodeName이 다르면 거부한다. 이어 `.venv/bin/python -B -m tools.tetragon_status --context byul-aws-lab --evidence-dir <evidence-dir> --output <state.json>`으로 연결(운영 감시는 기존 복구 인자와 `--watch`도 유지). 생성기는 격리 namespace·임시 정책을 만들고 정리하며 임의 spec을 받지는 않는다 | `*.verification.json`의 real·combined·passed, AWS node·kernel·context·policy_spec_sha256·task identity 기록. 같은 context만 수집하고 원본 보고서 해시를 붙인다. 대상 정책과 spec·node·kernel이 다르면 안전 조건 거부 |
| 8 | **모니터 기록 생성기** | 생성기를 `sudo -u runtime-agent`로 `--watch` 실행(시험용 정책, 모니터 시간 설정은 LAB 값으로 짧게), 에이전트 `--review-file`로 연결. 에이전트는 root 또는 runtime-agent 소유·0600 파일만 읽으므로 ubuntu로 실행하면 기록이 무시돼 모니터 기간이 미충족으로 남는다. 출력 위치는 runtime-agent가 쓸 수 있는 곳(예: `/var/lib/serving-runtime/`)으로 한다 | 안전 조건 6개 모두 통과(capability_basis live_trial) |
| 9 | **AWS 커널 Sigkill 차단 전환** | 대시보드 차단 전환 요청(ENGINE_RESTART 확인) → 다른 사람 승인 → 에이전트 실행 → `tetra tp list` MODE enforce → 시험용 Pod에서 가짜 파일 읽기 | exit 137, Tetragon 이벤트 귀속 확인 → 탐지 복귀 요청(즉시) → monitor·읽기 정상 |
| 10 | (선택) **실제 GPU 엔진 대상** | 엔진 Pod에 같은 차단 정책(엔진 selector, 가짜 파일)을 monitor로 → 근거·모니터 → 차단 전환 → 엔진 안에서 가짜 파일 읽기 1회 | 엔진 프로세스 종료 → Gateway 503(엔진 미전달) → Pod 재시작 → 200 복구 시간 기록 → 탐지 복귀 |
| 11 | 실제 자료로 화면 | 노트북 대시보드를 서버 Gateway·플랫폼에 연결해 운영 요청·차단 내역·Tetragon 정책 화면 스크린샷 | 화면 상태가 API·서버와 일치 |

**의도한 엔진 실행 기록:** 시험용 Pod·엔진 안의 가짜 파일 읽기는 시각·목적을 기록해, AWS-11 오탐으로 세지 않는다.

## C. 복구·증거·Stop

1. 차단 정책을 모두 monitor로 되돌리고, 시험 정책·Pod를 삭제하고, 원래 묶음으로 복귀한다.
2. 에이전트 서비스를 중지·비활성화할지 결정해 기록한다. sudoers 설치본은 유지 여부를 결정한다.
3. 역방향 터널을 종료한다.
4. 증거를 비밀값 검사 → 압축·해시 → 노트북으로 반출한다.
5. Stop.
