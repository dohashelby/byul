## 사용하는 순서

1. 아래 참조 구성과 12개 환경 조건을 대조해 실제 환경을 기록한다.
2. 앱·Gateway·엔진의 호출 경로와 신원·공유 관계를 확인한다.
3. 채택한 정책 중 재사용할 기준과 조직에서 채울 값을 정한다.
4. 조건에 맞는 점검을 선택하고 제외·미정의 이유를 남긴다.
5. 엔진·버전 차이는 [04](04_엔진과_버전별_차이.md), 구체 점검은 [03](03_체크리스트와_보완가이드.md), 시험·판정은 [05](05_평가와_증거관리.md)를 사용한다.

## 팀 참조 구성과 12개 환경 조건

팀 참조 구성은 Gateway → vLLM v0.31.0 → 단일 노드 다중 GPU·TP 그룹 1개다. 텍스트 모델 1개와 일반/스트리밍·prefix cache를 사용하며, 이미지·모델·설정 변경은 중단 후 재배포로 처리한다. 실제 모델·GPU·executor·정책값은 아직 입력해야 한다.

환경표의 R10·R14는 확장을 위해 남겨둔 연결이다. 이번 28개 체크리스트에서는 두 경로의 평가를 완료하거나 지원한다고 표시하지 않는다.

## 12개 환경 조건과 현재 JSON 입력 키

현재 `environment_template.json`에는 환경을 모두 표현하는 필드가 갖춰져 있지 않다. 아래는 **이미 있는 키**와 사람이 보완할 내용을 연결한 표다. 전용 키가 없는 자료는 `runtime_evidence`에 근거 위치를, 조직의 기준은 `policy_values`에 기록할 수 있지만, selector가 그 내부 내용을 해석하는 기능은 아직 없다. 값을 추가로 적었다고 자동 선택·검증이 되는 것은 아니다.

| 환경 조건 | 현재 사용할 키 | 사람이 보완할 부분·관련 점검 |
| --- | --- | --- |
| 1. 엔진·버전·의존성 | `engine`, `version`, `source_commit`, `image_digest`, `dependencies` | 실제 배포 식별과 코드·의존성 근거. 다른 버전은 04에서 구현 연결 확인 |
| 2. 진입·인증·인가 | `gateway`, `runtime_evidence` | route·listener·앱 신원·직통 ACL 전용 키는 없음. Q-C01·Q-C07 |
| 3. 사용자·역할·공유 | `prefix_cache`, `prefix_cache_or_shared_cache`, `policy_values` | 사용자/서비스 계정·공유 집단은 별도 정책 입력. Q-C02·Q-C03 |
| 4. 공급물·로딩 | `model`, `request_code_revision_selection`, `dynamic_import`, `alternate_sources_or_formats_or_derived_cache` | 실제 파일·reader·승인 목록은 근거 연결. Q-R05 계열 |
| 5. 요청·활성 기능 | 위 코드 선택 키, `r10_features`, `runtime_evidence` | endpoint·옵션·선택 기능은 근거로 보완. 기본값을 비사용으로 추정하지 않음 |
| 6. 실행 배치·내부 통신 | `nodes`, `tp_groups`, `gpu_count`, `runtime_evidence` | 실제 TP 크기·runner·executor·IPC 전용 키는 없음. GPU 수와 TP 크기를 동일시하지 않음 |
| 7. 호스트·자격·외부 접근 | `remote_acquisition_or_retry`, `policy_values`, `runtime_evidence` | UID·mount·자격 참조·TLS·송신 목록은 보완. Q-C07·Q-C10 |
| 8. 가중치 제공·공유 | `shared_or_remote_weights`, `feature_absence_evidence` | daemon·consumer·fallback의 실제 설정과 근거. Q-C13 |
| 9. 배포·변경·복귀 | `policy_revision`, `policy_values`, `runtime_evidence` | 전환 방식·복원 대상·재개 기준은 보완. Q-C09·Q-C12 |
| 10. 부하·자원·수용 | `policy_values`, `runtime_evidence` | 입력/출력·동시성·자원·지연·종결 기한. Q-C05·Q-C08 |
| 11. 관측·보존·폐기 | `policy_values`, `runtime_evidence` | 필수/금지 필드·독자·수집 장애·사본·기간. Q-C11·Q-C12 |
| 12. 책임·관리형 | `managed_or_external_fallback`, `policy_values` | 조직·사업자 책임과 접근 가능한 증거. R14는 평가 대기 |

`id`는 환경 프로필 식별자, `profile_status`는 계획값/실제 확인값의 구분이다. 사용 여부를 모르면 `null`로 두고, 비사용 후보의 구조화 근거는 `feature_absence_evidence`에 기록한다. selector는 현재 기존 Q 단위만 분류한다. 77개 점검과 시나리오별 선택은 평가자가 적용 조건을 보고 정한다.


## 앱·백엔드를 거치는 호출과 사용자 신원

직원용·고객용이라는 이름만으로 점검 항목을 선택하지 않는다. 사용자 단말의 망과 추론 서버의 망을 따로 기록한다. 내부 직원용도 사무용 PC 망에 엔진을 둔다고 가정하지 않으며, 서버망·사설망이라는 이유만으로 접근 제한을 충족 처리하지 않는다.

기존 팀 참조 구성은 유지한다. 앱을 거치는 환경의 예는 `사용자 → 업무 앱/서비스 백엔드 → Gateway → vLLM`이다. Gateway가 앱 앞에 있거나 앱이 여러 프록시를 거치는 경우에는 실제 순서대로 기록한다. 앱이 없는 직접 API 이용도 지원할 환경 조건으로 남긴다. 업무 앱 전체를 감사하는 대신 엔진 호출·신원 전달·결과 귀속에 연결된 접점을 확인한다.

<a id="필터와-미정-값"></a>
## 적용·제외·미정 판단

공통 보호 요구와 엔진별 구현 연결을 분리한다. 엔진이 다르면 질문을 삭제하는 대신 route·옵션·consumer·증거 위치를 새 엔진에 연결한다. 같은 버전 문자열이어도 이미지·패치·의존성·모델·GPU가 다르면 같은 검증 결과를 재사용하지 않는다.

- 명시된 기능 비활성과 비노출 근거가 함께 있을 때 해당 하위 시험을 제외한다.
- 미정 값은 `null`로 기록한다. false로 대신 채우지 않는다.
- 판본 미고정, 검사기 미설치, 접근 통제 부재는 적용 제외 사유가 아니다. 보호 요구를 만족하는지 확인할 대상이다.
- 사용자·부하·모델·네트워크 조건의 조합을 기록한다. 모든 조합을 실행한 것으로 표시하지 않는다. 중요한 경계·실패 조합을 선정하고 나머지 미실행 범위를 남긴다.

`select_checklist.py`는 큰 질문의 선택을 돕는다. 세부 기능별 테스트 생성이나 보안 판정은 하지 않는다. 예제 JSON은 계획값이며 실제 설치 증거가 아니다.

### 현재 selector가 판단하는 범위

현재 선택 단위는 기존 Q이며 77행·시나리오별 자동 선택은 미구현이다. Q-R05-11은 기본 loader 파일 선택도 포함하므로 항상 유지한다. prefix_cache=true와 cache 집계값=false가 충돌하면 미정으로 둔다. 기능 비사용의 단순 문자열은 제외 근거로 받지 않는다.

비사용 기록에는 feature, status=reviewed, reviewer, reviewed_at, disabled=true, nonexposed=true, references와 target(engine/version/source_commit/image_digest)을 둔다. 현재 대상과 일치하고 검토된 판본인 경우에도 출력은 **비적용 후보**이며 담당자가 근거의 진위·제외 범위를 확인한다. 계획 환경·대상 불일치·미확인 판본은 미정이다. 노드 수·TP 그룹·Gateway 값은 추가 확인 안내에 사용하며 세부 시험을 자동 선택했다고 표시하지 않는다. R10·R14의 평가 범위 제한은 비사용 문자열로 숨기지 않는다.

## 부록 — 입력을 줄이기 위한 자동 수집 계획

기업이 12개 환경표나 평가항목별 근거를 모두 직접 작성하지 않도록 한다. 사용자는 평가할 서비스와 접근 가능한 자료를 지정하고, 도구는 읽기 전용 연결 또는 업로드한 배포·설정 자료에서 환경 정보를 채운다. 기존 기업 정책도 구조화된 값으로 가져올 수 있으면 재사용하고 담당자가 적용 범위를 확인한다. 정책 문서 전체의 자동 해석은 전제하지 않는다.

**현재 상태:** 아래 수집·대조·입력 최소화 기능은 구현 계획이다. 현재 `select_checklist.py`는 제공된 환경값으로 Q 기록을 선택하는 보조 기능이며, 실제 환경 수집이나 세부 시험 자동 선택은 구현하지 않았다.

| 5. 요청·활성 기능 | 등록 API·실행 옵션·활성 기능과 확인 가능한 소비 경로 | 실제 공개할 기능, 수집 결과와 운영 의도가 다른 부분 |
| 6. 실행 배치·내부 통신 | 노드·GPU·TP·worker·executor·IPC·통신 설정 | 허용 운영·접근 주체. 배치 구조는 수집값을 재사용 |
| 7. 호스트·자격·외부 접근 | 계정·mount·권한·자격 참조·송신 규칙·TLS 설정 | 필요한 접근 범위와 허용 목적지. 비밀값 자체는 수집하지 않음 |
| 8. 가중치 제공·공유 | loader·daemon·배포 설정의 공급·공유·fallback 경로 | 허용 consumer·공유 관계와 대체 공급원 승인 |

| 11. 관측·보존·폐기 | 수집 필드·목적지·접근 권한·보존·삭제 설정 | 금지·필수 기록, 독자·재실행 권한·보존 기간 |

<a id="기업이-사용하는-순서"></a>
### 자동 수집 기능이 구현됐을 때의 이용 순서

1. 서비스와 자료 연결: 연결 범위·읽기 권한을 지정하거나 배포·설정 파일을 제공한다. 현재 환경 평가만 할 때는 후보 환경을 요구하지 않는다.
2. 환경 요약 확인: 수집한 구성과 관련 항목을 제안한다. 사용자는 잘못된 값과 수집하지 못한 값만 보완한다.
3. 정책 확인: 기존 승인 정책을 재사용하고, 공유·공급물·접근/송신·서비스 기준·보존·책임 중 새로 정할 값만 묻는다.
4. 평가 항목 확인: 선정·제외·미정의 이유와 사용한 근거를 보여준다. 여러 항목이 같은 환경값을 쓰면 한 번 확인한 정보를 함께 사용한다.
5. 다음 평가: 이전 승인 정책과 환경 정보를 가져오고, 변경·만료·수집 실패한 부분만 다시 확인한다.

<a id="자동-판단에-필요한-규칙"></a>
### 수집값을 사용할 때 지킬 규칙

- 현재 설정과 승인 기준은 별도 값으로 보관한다. 현재 보존 설정이 30일이라고 기업 승인 기준도 30일로 정하지 않는다.
- 수집값에는 대상·엔진/판본·출처·수집 시각·수집 성공 여부를 남긴다. 사람이 고친 값도 수정 이유와 출처를 보존한다. 이전 자료와 충돌하거나 오래된 값은 그대로 확정하지 않는다.
- 수집 실패·접근 권한 부족·알 수 없는 버전은 ‘미정’으로 둔다. 사용자에게 모든 항목의 근거를 요구하지 말고 판정을 바꾸는 미정 값만 묶어 질문한다.
- 기능 비사용 판단은 엔진·판본별 규칙으로 한다. 실행 옵션에 없거나 일정 시간 이벤트가 없었다는 이유만으로 제외하지 않는다. 등록·설정·plugin·다른 진입 경로 중 필요한 확인 범위를 규칙에 명시한다.
- 같은 환경 근거는 관련 하위 시험에서 재사용한다. 지원되지 않는 기능이나 미선정 backend의 세부 시험은 이유와 재검토 조건을 남긴다. R10 사용 시 미디어 일부 정적 근거는 재사용하되 미확인 분기와 실제 시험은 대기로 표시한다. R14는 검토 대기로 표시한다.
- 설정 수집은 통제 효과 시험을 대신하지 않는다. 직통 차단·인가·송신 제한의 실제 효과는 별도 허용 시험과 증거로 판정한다.
- 도구는 정책 적용을 제안하고 근거를 보여준다. 공유 허용·예외·승인·최종 적용 결정은 담당자에게 남긴다.

## 버전 정보와 환경 수집의 연결 — 계획

[04의 버전별 관리·자동 수집 계획](04_엔진과_버전별_차이.md#version-management-plan)을 따른다. 기업이 직접 적을 값은 허용 역할·공유·통신·성능/종결 기준 등 정책과 자동 수집이 불가능한 정보로 줄인다. 정책 의도를 현재 설정값에서 자동 추정하지 않는다. 실제 대상·기능·유효 설정은 수집 후보이며 수집 기능은 아직 미구현이다. 최초 판본·포크·backport는 검토 필요로 두고, 미수집값은 미정으로 유지한다. 기본 참조 구성의 계획값을 실제 설치 확인값으로 대체하지 않는다.

### 기능별 적용 범위

기본 chat template·TP는 기본 흐름에서 확인한다. R10 미디어 입력·사용자 UUID·processor cache·raw disk cache·오디오 backend는 실제 활성·도달 조건을 확인해 03의 조건부 보완을 선택한다. 로컬 반입·원격 취득, 공유 daemon/원격 공급, 재배포/live 변경의 기존 구성 분기는 유지한다. R10 전체 검토 완료나 기본 텍스트 범위 확장을 뜻하지 않는다. 자동 선택·수집은 계속 구현 계획이다.
