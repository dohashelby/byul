# Tetragon 운영 이벤트 대상 확인·중단 복구

기준 `byul_runtime`의 `82804c1` 이후 작업. 이번 변경은 사용자 요청으로 로컬 커밋하며 AWS를 켜거나 실제 GPU 엔진에 적용하지 않았다. 화면의 서버 자동 적용·모드 변경 실행은 후속 범위로 둔다.

## 개발한 것

1. intent 1.1의 선택 필드 `tetragon_kernel_identity: true`로 일반 파일 관측 정책에도 커널 current_task의 tgid·group_leader.start_boottime·PID namespace 데이터를 추가한다. 스레드에서 읽어도 프로세스 시작 시각과 대조하도록 group_leader를 사용한다. 필드가 없거나 false면 기존 렌더를 유지한다. 파일 조건·집행 action·Gateway 요청 정책은 바꾸지 않는다.
2. `tools.tetragon_identities`가 명시한 context·namespace·Pod selector에서 Kubernetes의 Pod UID·CRI 컨테이너 ID와 해당 노드 Tetragon 컨테이너의 `/procRoot`를 대조한다. cgroup의 정확한 컨테이너 ID로 범위를 좁히고, 시작 tick·exe·cgroup을 다시 읽어 exit/exec 경합을 거부한다. 인자·환경 변수·파일 내용은 수집하지 않는다.
3. Gateway의 `--tetragon-identities` 경로를 읽어 일반 `ObservationFeed`에서 대상을 확인한다. 같은 노드·namespace inode·프로세스 시작 tick 구간·적용 정책 선언·selector가 유일하게 일치해야 한다. native exec는 원래 PID·exec_id·binary를 유지하고 정확한 컨테이너 ID가 하나일 때만 Pod를 보완한다. 노드 PID와 커널 전역 PID를 같은 값으로 추정하지 않는다.
4. `tools.tetragon_stream`은 명시 정책의 노드별 gRPC 스트림을 감독한다. 에이전트 UID/restartCount·준비 상태가 바뀌면 살아 있는 follow도 다시 연결하고 공백을 기록한다. 다른 namespace에 같은 정책 이름이 있으면 모호한 구독을 거부한다. gRPC 과거 재조회는 지원하지 않으므로 누락 구간은 복원 완료로 표시하지 않는다.
5. `tools.tetragon_status`는 사전에 저장한 정책 spec/모드와 실제 상태를 대조하고, writer heartbeat·식별 자료·30초 내 확인된 실제 이벤트를 함께 요구한다. 에이전트/확인 수집기 재시작, 정책 불일치, 자료 만료, 살아 있지만 전달이 멈춘 상태는 복구 확인 중으로 표시한다. 설정·source가 돌아온 뒤 발생한 새 관측으로만 복구를 닫는다. 기대 정책 파일이 없으면 자동으로 현재 상태를 승인하지 않는다.
6. 화면에 운영 복구 조건·공백 이력·실측 결과와 일반 파일 이벤트의 Pod UID·컨테이너·PID를 표시한다. 대상 충돌/중복/자료 만료는 미확인으로 남긴다. 양성 귀속으로 기존 엔진 범위의 exec 분류가 가능해지지만 허용 목록·단계 판정 규칙 자체는 유지한다. 충돌한 native Pod 정보는 엔진 허용 판단에 쓰지 않는다.

## 로컬 실측

`tools.tetragon_operations_check --allow-isolated-kind-check --restart-agent`로 별도 namespace와 가짜 파일만 사용했다. 시험 ID `byul-proof-4296fa7ca9`.

- 서로 다른 두 Pod를 구분하고 주 프로세스와 자식 프로세스를 확인했다. 시험 전용 PID 1 결합이 아닌 일반 운영 식별 경로를 사용했다.
- Tetragon 에이전트를 한 번 교체했다. follow 재연결만으로 성공 처리하지 않고 기대 정책·writer·새 epoch의 식별 자료·새 실제 이벤트를 확인한 뒤 복구했다.
- 원시 스트림 gap과 복구 확인 이력이 남았다. 원래 정책 spec은 유지됐고 시험 namespace를 삭제했다.
- 원본 보고서·정규화 이벤트·정책·상태와 해시는 `/tmp/byul-operating-check/`, 영구 사본은 `~/.local/state/serving-runtime/tetragon-evidence/operations-artifacts/`에 있다. 기존 보고서는 gRPC의 과거 요청을 실제로 수행한 증거로 사용하지 않는다.
- 추가로 개발 서비스가 소유한 gRPC kubectl 프로세스만 잠시 정지했다. writer heartbeat와 에이전트가 정상이어도 확인 이벤트가 30초 넘게 멎으면 복구 확인 중으로 바뀌었고, 프로세스를 재개해 새 관측을 받은 뒤 정상으로 돌아왔다. 정지 대상은 finally에서 재개했다. 기록 `/tmp/byul-tetragon-silent-stall-check.json`.
- 개발 서비스 전체의 실제 연결에서도 에이전트를 한 번 더 교체해 공백 감지·새 epoch·8개 정책/모드·자가점검 새 이벤트 복구를 확인했다. 정책 spec은 모두 유지됐다. 기록 `/tmp/byul-tetragon-live-agent-recovery.json`.
- 서비스 재시작 검수에서 원격 읽기 세션 정리 지연을 발견해 자기 UUID wrapper와 그 자식만 정리하도록 보완했다. 출력 폴더 단일 writer lock·이전 자기 세션 회수·RPC 제한 시간을 적용했다. 중복 종료 신호 처리 중 Event lock 재진입도 제거했다. 최신 코드의 서비스 정상 재시작은 1.63초였으며 외부 프로세스나 정책을 종료하지 않았다.

- 스레드 접근 회귀 실측 `byul-proof-265c9552ed`도 통과했다. 두 Pod의 주 프로세스와 별도 자식 프로세스 안의 스레드가 읽는 파일을 group_leader 시작 시각으로 연결했다. 이 실행은 에이전트 재시작 시험을 하지 않았으며 앞선 재시작 실측과 구분한다. 보고서·artifact 영구 사본도 같은 evidence 폴더에 보존했다.

## 실행·연결

```bash
cd runtime
# intent 1.1에서 tetragon_kernel_identity=true로 준비하고 렌더·검토한다.
.venv/bin/python -B -m serving_runtime enforce render --intent '<검토한-intent>' --out '<후보-폴더>'
# 기존 정책 삭제 없이 새 이름으로 선로드·검증하는 절차를 따른다.
.venv/bin/python -B -m tools.tetragon_identities --context '<ctx>' --namespace '<ns>' \
  --selector 'app=engine' --output '<identities.json>' --watch
.venv/bin/python -B -m tools.tetragon_stream --context '<ctx>' --namespace '<ns>' \
  --policy '<정확한-정책-이름>' --output '<feed-폴더>'
# 정상임을 확인한 상태를 기대값으로 명시 저장한다. 장애 후 자동 갱신하지 않는다.
.venv/bin/python -B -m tools.tetragon_status --context '<ctx>' --output '<상태.json>' \
  --evidence-dir '<시험-근거>' --capture-baseline '<baseline.json>'
.venv/bin/python -B -m tools.tetragon_status --context '<ctx>' --output '<상태.json>' \
  --evidence-dir '<시험-근거>' --expected-policies '<baseline.json>' --identities '<identities.json>' \
  --feed-heartbeat '<feed-폴더>/tetragon.heartbeat.json' --observations '<Gateway-data-dir>/observations.jsonl' --watch
```

Gateway에는 `--tetragon-identities`, `--observation-feed tetragon=<feed-폴더>/tetragon.jsonl`, `--observation-heartbeat tetragon=<feed-폴더>/tetragon.heartbeat.json`, 같은 `--kube-context`를 준다. platform 개발 스크립트는 `RUNTIME_TETRAGON_IDENTITY_SELECTOR`, `RUNTIME_TETRAGON_NAMESPACE`, `RUNTIME_TETRAGON_STREAM_POLICIES`, `RUNTIME_TETRAGON_BASELINE`으로 같은 생산자들을 연결한다.

## 현재 개발 서비스

로컬 kind의 기존 네 정책을 유지하고 Post만 하는 identity 관측 정책 세 개를 새 이름(`-identity-v2`)으로 추가했다. `deploy/lab/tetragon-sentinel.json`의 별도 비특권 DaemonSet과 `runtime-tg-health-01-sentinel-v2`이 5초마다 가짜 파일을 읽는다. 기존 엔진 Pod를 재시작하거나 차단 모드를 바꾸지 않았다.

v1 추가 관측 정책은 v2의 실제 이벤트 확인 뒤 제거했으며 원래 네 정책은 유지했다. 정책 후보와 기대값은 `~/.local/state/serving-runtime/tetragon-monitoring/`에 있고 개인 서비스 설정은 `byul-dev.service.d/30-tetragon-monitoring.conf`다. 개발 스크립트에 연결해 실제 정책 8개·writer·대상 식별·자가점검 이벤트를 확인했다. 자가점검은 노드당 최신 receipt만 별도 파일에 저장하므로 일반 보안 사건 수를 늘리지 않는다. 운영 배포에는 검토한 image digest와 해당 환경의 범위·정책을 별도로 준비해야 한다.

중지하려면 개인 서비스의 30번 drop-in을 제거하고 daemon-reload/restart한 뒤, 이 작업이 추가한 `byul-tetragon-sentinel` DaemonSet과 `runtime-tg-health-01-sentinel-v2`, `runtime-tg-{asset,cache,secret}-01-identity-v2` 정책만 삭제한다. 기존 네 정책을 삭제하지 않는다.

## 남은 한계

- 원래 Tetragon process-cache 귀속 버그나 정책 조회 내부 버그를 수정한 것은 아니다. 독립 메타데이터 경로와 오류 탐지·재확인으로 대응한다. 정책/에이전트 변경 직후에는 조회 안정화 대기를 둔다.
- 같은 namespace에서 같은 tick에 시작한 후보가 여러 개이거나 너무 빨리 종료돼 procfs에서 확인하지 못한 프로세스는 미확인이다. 모호한 후보를 강제로 하나에 연결하지 않는다.
- 복구는 조회·수집 재연결과 사전에 정한 정책 상태·새 이벤트를 확인하는 것이다. 누락된 보안 정책의 무조건 재적용이나 자동 enforce는 하지 않는다. 노드/정책이 바뀌면 기대값을 검토해야 한다.
- 감지에는 polling/freshness 허용 시간이 있다. 실제 공백 시작 시각·구간 전체 이벤트·앞으로의 무공백을 보장하지 않는다. quiet 환경은 자가점검 같은 무해한 관측원이 있어야 새 이벤트 검증을 계속할 수 있다.
- 이번 실증은 로컬 단일 kind 노드다. 실제 GPU 엔진 503·복구, AWS 적용 및 다중 노드 장애 실증은 별도다.

## 마무리 검증

- runtime 전체 768건(skip 0), API 197건, web 93건 및 타입 검사 통과. 계약 스키마 13개·예시 11개 오류 0, 셸 구문·diff 검사 통과. runtime 중간 실행의 기존 만료 시각 경합 1회는 시간 한도를 바꾸지 않고 개별/최종 전체 재시험에서 통과했다.
- 최종 개발 상태는 실제 `ok/healthy`, 정책 8개, 운영 실측 보고서 2개이며 시험 namespace는 남기지 않았다. 로그는 `/tmp/byul-ops-runtime-final-verified.log`, `/tmp/byul-ops-web-verified.log`, `/tmp/byul-ops-api-full.log`.
- 사용자 요청으로 작업을 마무리하고 로컬 커밋한다. 푸시·PR은 하지 않는다. Claude 대화형 독립 검수와 최신 화면의 브라우저 시각 검수는 별도다.
