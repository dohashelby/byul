# 런타임 인계 안내 최소판

기준일: 2026-10-25

대상: 런타임 담당 → 인수 담당(공동 개발 담당)

일정: 10/29까지 실행 방법·남은 작업을 공유하고 기능별 담당을 확정한다. 11/2~3에는 인수 담당이 아래 절차를 직접 실행해 확인한다.

이 문서는 개발계획서 v1.4 §10.3~10.4의 최소 실행 안내다. **문서 전달만으로 인계를 완료하지 않는다.** 현재 구현된 CLI와 기록 경로만 적었으며, 계획상의 모듈명을 CLI/API처럼 제시하지 않는다.

## 1. 이 문서로 할 수 있는 것

- 단위시험과 39개 수용 사례를 실행하고 보고서를 찾는다.
- 모의 엔진 Gateway에서 허용 200과 정책 거부·엔진 미전달을 확인하고 대시보드에서 증거를 조회한다.
- LAB 인증·조회 보호, 대상 등록, 정책 승인 목록을 선택적으로 켠다.
- 준비된 CPU vLLM 또는 로컬 kind 환경이 있을 때 연결·관측·경보·기본 복원을 재현한다.
- 기능별 구현 상태와 실제 확인 수준, 미확인·남은 결정을 구분한다.

확인 수준 표기는 `docs/지원_미지원_목록.md`와 같다.

| 표시 | 이 문서에서의 뜻 |
| --- | --- |
| **정식** | 계획서 §3.5의 승인 GPU·Kubernetes 1.36.5 환경에서 확인. **현재 해당 항목 없음** |
| **CPU vLLM** | 이 PC의 vLLM CPU v0.29.0·Qwen2.5-0.5B-Instruct 사전 점검. 정식 S3B 아님 |
| **로컬 kind** | WSL2 kind(node v1.37.0)의 실제 Cilium·Hubble·Tetragon과 시험용 가짜 엔진으로 확인 |
| **모의·가짜** | 저장소의 모의 엔진·가짜 vLLM/SGLang으로만 확인 |
| **합성** | 공식 출력 모양을 흉내 낸 fixture로만 확인. 실제 수집 자료 아님 |
| **미구현·범위 밖** | 코드가 없거나 개발계획서 §2.3 제외/별도 승인 대상 |

`구현됨`은 코드가 있다는 뜻이고 `확인됨`은 표시한 환경에서 실행했다는 뜻이다. 이 둘을 합치지 않으며, 정식 환경 확인은 아직 없다.

## 3. 인수 담당 직접 실행 순서

각 단계에서 명령, 기대 결과, 증거 위치, 실패 시 확인을 함께 기록한다. 비밀값은 결과 화면이나 인계 기록에 붙이지 않는다.

### 3.1 단위시험

```bash
.venv/bin/python -B -m unittest discover -s tests
```

- 기대: 실패 0. 로컬 소켓 생성이 제한된 환경에서는 HTTP 시험이 `skip`으로 집계될 수 있다. `skip`은 해당 HTTP 동작을 확인했다는 뜻이 아니다.
- 증거: 터미널의 전체 시험 수·통과·skip·실패 요약. 별도 보고서 파일은 만들지 않는다.
- 실패 시: 첫 traceback의 실제 실패를 확인한다. 임시 디렉터리 권한 오류라면 `/dev/shm`이 쓰기 가능한 환경에서만 `TMPDIR=/dev/shm`으로 재시도한다. 소켓 제한 skip은 소켓 허용 환경에서 다시 확인한다.

### 3.2 수용 시험 39개

```bash
.venv/bin/python -B -m serving_runtime mvp-acceptance
```

- 기대: MVP-01~11, S1-01~06, S2-01~06, S3A-01~08, SGL-01~02, S4-01~06의 **39개**가 통과한다. S3A·SGL·S4-06 일부는 모의·가짜 확인이며 실제 엔진 확인이 아니다.
- 증거: 기본 `~/.local/state/serving-runtime/mvp/acceptance/<UTC시각>.json`과 `.md`. 다른 위치는 `--report-dir PATH`를 쓴다.
- 실패 시: 소켓 생성 제한이면 실행 자체가 시작되지 않을 수 있다. 보고서가 만들어졌다면 실패 case의 기대/실제와 증거 요청 ID를 확인하고, 하나라도 실패한 종료 코드 1을 통과로 바꾸지 않는다.

### 3.3 모의 엔진 Gateway·대시보드

첫 터미널:

```bash
.venv/bin/python -m serving_runtime mvp \
  --data-dir ~/.local/state/serving-runtime/handoff-mock
```

둘째 터미널:

```bash
# 허용: 200
curl -i -H 'Content-Type: application/json' \
  -d '{"model":"test-model","messages":[{"role":"user","content":"hi"}],"max_tokens":64}' \
  http://127.0.0.1:8080/v1/chat/completions

# 금지: 출력 상한 초과 403, 엔진 미전달
curl -i -H 'Content-Type: application/json' \
  -d '{"model":"test-model","messages":[{"role":"user","content":"hi"}],"max_tokens":129}' \
  http://127.0.0.1:8080/v1/chat/completions
```

- 기대: 허용 요청은 200, 금지 요청은 403이다. 각 응답의 `X-Request-ID`를 기록한다.
- 증거: `~/.local/state/serving-runtime/handoff-mock/gateway_records.jsonl`, `engine_receipts.jsonl`, `policy_history.jsonl`. `http://127.0.0.1:8080/`에서 요청 행 → 상세 → 전달 여부 → 증거 JSON 내려받기를 확인한다. 금지 요청은 같은 실행의 모의 엔진 수신 기록과 대조돼야 “Gateway 미전달, 엔진 미수신 확인”이다.
- 실패 시: 저장소 루트에서 실행했는지, 포트 8080/8088 충돌, 정책 카드 오류, 기록 저장 권한을 확인한다. 이전 실행이나 엔진 조회 실패는 엔진 미수신을 확정할 수 없어 `확인 불가`다.

### 3.4 인증·조회 보호, 대상 등록, 정책 승인 목록

`examples/mvp/auth.example.json`, `target.example.json`, `policy-approvals.example.json`의 값은 모두 **예시 전용**이다. 운영 비밀·승인값으로 쓰지 않는다. 인증 파일을 저장소 밖 권한 600 경로에 복사하고, 새 토큰의 해시만 넣는다.

```bash
printf '%s' "$LAB_TOKEN" | .venv/bin/python -m serving_runtime auth hash-token
```

조회 보호를 켜려면 인증 설정의 `route_roles`에 `"GET /api/*": ["viewer"]`를 추가한다. 토큰 원문은 설정에 넣지 않고 위 명령의 SHA-256 출력만 `token_sha256`에 넣는다. 다음 조합은 모의 엔진용 LAB 예시다.

```bash
.venv/bin/python -m serving_runtime mvp \
  --policy examples/mvp/policy-v1.1.json \
  --policy-approvals examples/mvp/policy-approvals.example.json \
  --auth-config /보호된/경로/auth.json \
  --target examples/mvp/target.example.json \
  --data-dir ~/.local/state/serving-runtime/handoff-protected
```

- 기대: 추론 경로는 토큰 없음/불일치 401, 역할·모델 불허 403, 올바른 inference 주체는 요청 판정으로 진행한다. `GET /api/*` 보호를 설정했다면 viewer 권한 없는 조회는 401/403이다. 정책 ID·판본·`approval_ref`·정책 파일 SHA-256이 승인 목록과 맞아야 하며, 대상 ID가 정책과 맞아야 한다.
- 증거: 대시보드의 API 인증·대상 등록·정책 승인 상태와 `<data-dir>/gateway_records.jsonl`, `policy_history.jsonl`, `target_snapshots.jsonl`(Pod 조회를 쓴 경우).
- 실패 시: 인증/승인/대상 파일 읽기 권한과 schema를 확인한다. 인증 설정 오류, 승인 항목 없음·불일치·만료·손상, 대상 불일치는 503이며 보안 차단 성공으로 세지 않는다. 토큰 또는 해시를 인계 기록에 복사하지 않는다.

### 3.5 CPU vLLM 연결(이미지·모델이 준비된 경우만)

정식 GPU S3B가 아닌 **CPU vLLM** 확인이다. `examples/mvp/backend-vllm.example.json`을 저장소 밖에 복사해 `base_url`, `model_map`, 권한 600의 `credential.file`, 실제 metrics 이름을 채운다. 자격정보 원문은 넣지 않는다.

```bash
RUNTIME_CPU_DIR=/보호된/절대/경로/s3b-cpu
.venv/bin/python -m serving_runtime mvp \
  --policy examples/mvp/policy-v1.2-zeroday-lab.json \
  --backend vllm --backend-config "$RUNTIME_CPU_DIR/backend.json" \
  --gateway-port 18080 --data-dir "$RUNTIME_CPU_DIR/data" \
  --environment docker-cpu --run-id handoff-cpu
```

- 기대: `http://127.0.0.1:18080/`에서 “외부 vLLM 모드”와 health 상태가 보이고, 기본 요청은 실제 CPU 엔진 응답과 `backend_kind: vllm` 기록을 남긴다. 정책 1.2 `zeroday-lab`은 시험 전용 추가 필드 프로필이며 D-09 기본 정책을 대체하는 운영 승인값이 아니다.
- 증거: `$RUNTIME_CPU_DIR/data/gateway_records.jsonl`, Gateway 로그, vLLM 요청 로그, 기존 사전 점검 보고서 `~/.local/state/serving-runtime/s3b-cpu/reports/`.
- 실패 시: `/health`, backend 고정 주소·모델 별칭·credential 파일 권한, relay timeout, 컨테이너 로그와 메모리를 확인한다. 7GB 환경에서는 kind를 함께 실행하지 않는다. CPU `logprobs`는 완료 확인이 없으므로 인수 통과 항목으로 세지 않는다.

### 3.6 로컬 kind lab·실시간 수집·대시보드 연결

준비된 클러스터에서만 실행한다. 이 명령은 클러스터에 시험 정책·Pod를 만들고 지우므로 현재 context와 권한을 먼저 확인한다.

```bash
.venv/bin/python -B tools/k8s_lab_check.py \
  --context kind-runtime-lab --namespace serving-lab \
  --state-dir ~/.local/state/serving-runtime/k8s-lab --task-checks
```

도구는 안전 context 확인 뒤 L-01 전에 자신이 관리하는 잔여 Cilium/Tetragon 정책을 삭제 완료까지 기다린다. 관리 대상 밖 정책은 지우지 않고 “실행 전 정리” 경고로 남긴다. `--task-checks`의 시험 Pod·정책은 매번 정리한다.

| 사례 | 확인 의미 |
| --- | --- |
| L-01 | 정책 적용 전 기준선 |
| L-02 | Cilium 통신 정책의 허용·거부 |
| L-03 | 실제 Hubble `DROPPED` 증거 |
| L-04 | Tetragon 파일·실행 관측 |
| L-05 | Tetragon 시험 probe 쓰기 차단(EPERM) |
| L-06 | 이번 실행이 적용한 정책 정리(`--cleanup` 지정 시) |
| L-07 | SP4 acquire/receiver 작업 통신 허용과 engine/기타 client 거부 |
| L-08 | SP1 공급물 읽기 전용 mount·비root 계정·캐시 세대 쓰기 |

- 기대: 환경에 맞는 case가 `passed`; 의도적으로 실행하지 않은 L-06 등은 `not_run`일 수 있다. `overall: partial`을 전체 통과로 바꾸지 않는다.
- 증거: `~/.local/state/serving-runtime/k8s-lab/reports/<run_id>.json`과 `.md`, 보고서가 가리키는 raw evidence.
- 실패 시: “실행 전 정리”, L-01 기준선, 현재/지정 context, namespace, Pod 준비 상태, Cilium/Hubble/Tetragon 상태를 순서대로 확인한다. 과거 L-01 실패 원인은 잔여 정책이었고 현재는 관리 대상만 실행 전에 자동 정리한다.

실시간 수집은 별도 터미널에서 실행한다.

```bash
.venv/bin/python -B tools/k8s_observation_feed.py \
  --context kind-runtime-lab \
  --output-dir ~/.local/state/serving-runtime/k8s-lab/live
```

Gateway 연결 예시는 다음과 같다.

```bash
.venv/bin/python -m serving_runtime mvp \
  --data-dir ~/.local/state/serving-runtime/handoff-kind \
  --environment kind-lab-wsl --run-id handoff-kind \
  --observation-feed hubble=~/.local/state/serving-runtime/k8s-lab/live/hubble.jsonl \

  --observation-heartbeat tetragon=~/.local/state/serving-runtime/k8s-lab/live/tetragon.heartbeat.json \
  --observation-origin real \
  --observation-environment kind-lab-wsl --observation-run-id handoff-kind \
  --observation-intent deploy/lab/intent.lab.json \
  --lab-report ~/.local/state/serving-runtime/k8s-lab/reports \
  --cilium-policy-status
```

- 기대: heartbeat가 갱신되고 대시보드에 실제 수집/새 이벤트 없음 또는 실제 관측이 표시된다.
- 증거: `live/{hubble,tetragon}.jsonl`, `.heartbeat.json`, `.gaps.jsonl`; Gateway `<data-dir>/observations.jsonl`; lab 보고서와 대시보드.
- 실패 시: heartbeat의 `state`, 자식 return code, gap의 원인과 backfill 상태, context를 확인한다. 재연결은 복구를 요청할 뿐 완전 복구를 증명하지 않는다.

### 3.7 단계 신호·관리 listener·캐시 점검

단계 신호 배치:

```bash
.venv/bin/python -m serving_runtime enforce phase-signals \
  --engine vllm --log engine.log --year 2026 --tz +00:00 \
  --out /tmp/runtime-phase-timeline.json
```

파일 follow와 health:

```bash
.venv/bin/python -m serving_runtime enforce phase-signals \
  --engine vllm --log engine.log --year 2026 --tz +00:00 \
  --out /tmp/runtime-phase-timeline.json --follow \
  --health-url http://127.0.0.1:8000/health --overwrite
```

- 기대: 확인된 vLLM CPU v0.29.0 표지만 loading/compiling 시간표로 변환된다. follow+health는 init/compile 뒤의 첫 200이 로그 경계보다 뒤일 때만 inferring을 연다.
- 증거: 지정한 timeline JSON의 `entries`(단계 구간)와 `extraction`(처리 위치·상태·heartbeat·시계 출처).
- 실패 시: 로그의 연도/UTC offset, 기존 출력 파일(`--overwrite` 또는 `--resume` 필요), health URL을 확인한다. GPU 표지와 SGLang 패턴은 미확인/미지원이다.

읽기 전용 관리 listener:

```bash
.venv/bin/python -m serving_runtime management-listener \
  --listen-host 127.0.0.1 --listen-port 18081 \
  --engine-url http://127.0.0.1:8000 \
  --record-file /tmp/runtime-management-access.jsonl
```

- 기대: 기본 `/metrics`, `/health`, `/v1/models`, `/version`의 정확한 GET/HEAD만 중계하고 다른 메서드·경로 변형·query·본문은 거부한다.
- 증거: stdout과 `--record-file`의 최소 접근 JSONL. 요청·응답 본문과 헤더는 기록하지 않는다.
- 실패 시: 18081 충돌, engine URL, 선택 credential 파일 권한, timeout·응답 크기 상한을 확인한다. 실제 kind sidecar 배치는 아직 확인하지 않았다.

캐시 읽기 전용 점검:

```bash
.venv/bin/python -m serving_runtime enforce cache-check \
  --intent examples/enforcement/intent-v1.1.example.json \
  --root /점검할/cache-copy
```

- 기대: 세대 디렉터리의 소유자·권한·다른 세대를 보고하고 아무것도 삭제하지 않는다.
- 증거: stdout JSON. 필요하면 비밀이 없는 인계 폴더에 별도 저장한다.
- 실패 시: intent의 `cache_root`/세대 경로와 `--root` 사본 경로, 링크·권한을 확인한다. 실제 vLLM/SGLang resolved cache 경로는 미확인이다.

## 4. 오류 확인과 알려진 오류

| 표시·현상 | 의미와 확인 |
| --- | --- |
| 관측 `stale` | 마지막 성공 뒤 신선도 기준을 넘었거나 heartbeat 없는 feed에서 새 이벤트가 없다. 현재 상태를 정상으로 단정하지 않는다. |
| 관측 `error` | feed/heartbeat 읽기, 변환 또는 수집원이 실패했다. 마지막 성공값이 남아 있어도 현재 관측 가능을 뜻하지 않는다. |
| heartbeat `reconnecting` | helper 자식이 끝나 재연결 중인 **관측 불가** 구간이다. `{kind}.gaps.jsonl`의 열린 gap과 원인을 확인한다. |
| helper 재연결 | 1~30초 backoff와 마지막 정상 확인 1초 전부터 backfill을 요청한다. gap은 유지되며 닫혀도 `requested_unverified`; 로그 회전·Pod 재시작의 완전 복구는 미확인이다. |
| lab L-01 실패 | 과거 잔여 관리 정책 때문에 기준선이 실패했다. 지금은 안전 context 확인 뒤 관리 대상 정책만 실행 전에 자동 정리하고 결과를 보고서 “실행 전 정리”에 남긴다. |
| CPU vLLM `logprobs` | 3회가 엔진 정지/timeout 또는 무응답으로 미완료다. CPU 결함과 메모리 부족 중 원인은 미확정이며 컨테이너 재시작이 필요했던 사례가 있다. |
| 504·엔진 정지 | RAM 약 7GB에서 CPU vLLM+kind 동시 실행 시 메모리·swap 부족으로 기본 요청도 120초 504가 났다. 메모리와 컨테이너 상태를 먼저 확인한다. |
| Tetragon kprobe 귀속 | 로컬 WSL+kind에서 kprobe 이벤트의 Pod·process 귀속이 비어 정책명·경로·접근·시각으로 판정했다. 정식 환경 귀속 증거가 아니다. |
| WSL Override | syscall 대상 Override capability는 제한됐지만 현재 `security_file_permission` fmod_ret 경로의 EPERM은 Tetragon 재시작 뒤 확인했다. helm upgrade 직후 초기 불일치 원인은 미확정이다. |
| `docker logs -f` 입력 | 컨테이너가 재시작되면 기존 follow가 끝날 수 있다. `phase-signals --log - --follow`도 입력 EOF 뒤 스스로 새 컨테이너 로그에 붙지 않으므로 파이프를 다시 시작하거나 파일 follow를 사용한다. |

## 5. 기본 복원

자동 엔진 재시작·재배포·Pod 삭제·자동 재검증 같은 **운영 자동 복구는 개발계획서 §2.3 범위 밖**이다. 아래는 인수 담당이 직접 수행하고 복원 뒤 정책·관측을 다시 확인하는 기본 절차다.

1. **Gateway:** 전경 프로세스를 `Ctrl+C`로 끝내고, 같은 정책·설정·`--data-dir` 명령으로 다시 실행한다. `/api/status`, 허용 200, 거부 403, 이전 기록 표시를 재확인한다.
2. **관측 helper:** `Ctrl+C` 후 3.6의 `k8s_observation_feed.py` 명령을 같은 `--output-dir`로 다시 실행한다. 기존 `{kind}.gaps.jsonl`을 지우지 말고 새 heartbeat와 재연결 횟수를 확인한다.
3. **lab 정책:** 명시적으로 정리할 때 3.6의 점검 명령에 `--cleanup`을 붙인다. 다음 실행도 L-01 전에 관리 대상 잔여 정책을 자동 정리한다. 관리 대상 밖 정책은 수동 판단 없이 삭제하지 않는다.
4. **CPU vLLM:** 컨테이너가 준비된 환경에서 `docker stop s3b-vllm-cpu` 후 `docker start s3b-vllm-cpu`를 실행하고 `/health` 200 뒤 Gateway를 다시 확인한다. 비밀값을 로그·명령 인자에 붙이지 않는다.
5. **kind 일시정지 해제:** `kind get nodes --name runtime-lab`로 실제 node 이름을 확인하고, 기록된 기본 이름이면 `docker unpause runtime-lab-control-plane`을 실행한다. Pod·Tetragon 재시작과 관측 heartbeat를 다시 확인한다.

## 7. 남은 작업과 결정

- **D-02:** LAB 정적 bearer 토큰 프레임은 구현했지만 운영 인증 연동 방식은 미결이다. 기존 인증 체계를 확인해 선택하고 별도 인증 제품은 만들지 않는다.
- **D-03:** 기존 검증 도구 ID·OBS/EVD/RES 매핑, 인증 주체, 계정·역할·권한과 실제 실행 1개 round-trip을 검증 도구/런타임/정책 담당이 합의해야 한다.
- **D-08:** LAB 5초 점검·15초 stale, 7일 또는 5GiB의 먼저 도달한 한도는 구현/단위시험했지만 운영 보존 기간과 조회·삭제 권한은 인계 때 확정해야 한다. 시험 증거는 정리 전에 별도 보존한다.
- **앞 단계 입력:** 실제 정책값·승인 구성, 허용 통신 목적지, 보호 경로·정상 실행 목록, 대상/모델/image 식별값, 공통 결과·증거 형식을 받아야 한다. 모르는 값은 만들지 않는다.
- **정식 환경:** 승인 GPU 서버, vLLM v0.31.0/선정 모델, Kubernetes 1.36.5·containerd 2.3.7에서 vLLM·SGLang과 Cilium/Hubble/Tetragon을 다시 확인해야 한다. 현재 CPU vLLM·로컬 kind·모의·합성 결과를 정식 확인으로 승격하지 않는다.
