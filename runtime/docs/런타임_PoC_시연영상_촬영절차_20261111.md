# 런타임 PoC 시연영상 촬영 절차

- 작성일: 2026-11-11
- 목적: 개발한 런타임 솔루션의 요청 통제·네트워크 차단·행동 탐지·플랫폼 기록 연결을 영상으로 보여 준다.
- 환경: Windows + WSL Ubuntu, 기존 AWS GPU lab의 vLLM 배포.
- 근거: [PR #245](https://github.com/dohashelby/byul/pull/245), [AWS 16회차 결과](AWS_GPU_서버16회차_결과_20261111.md).
- 이 문서는 촬영 안내다. 문서 작성 중 서버 기동·접속·배포·정책 변경·녹화를 실행하지 않았다. 재기동 뒤 상태는 아래 순서로 확인한다.

## 1. 이번에 찍을 영상

완성 영상은 약 4~5분으로 잡는다. 서버를 켜고 연결하는 준비 과정은 녹화하지 않는다.

| 순서 | 영상에서 할 일 | 보여 줄 결과 |
| --- | --- | --- |
| 1 | 플랫폼 현황 확인, 정상 요청 전송 | 실제 vLLM 연결, 정상 응답 200 |
| 2 | 코드 선택 필드가 든 요청 전송 | 400, 전용 거부 사유, 엔진 미전달 |
| 3 | 별도 시험 Pod에서 엔진에 직접 접근 | 연결 실패와 해당 Hubble DROPPED 기록 |
| 4 | 엔진 컨테이너에서 무해한 코드 파일 불러오기 | TG-CODE-01 탐지와 관련 파일·시각 |
| 5 | SUP-008 관련 사건 확인, 정상 요청 재전송 | 체크리스트 연결, 서비스 정상 유지 |

이번 영상에는 업데이트 전후 비교, 승인 밖 이미지 교체, 보호 파일 차단 모드 전환을 넣지 않는다. Gateway `/tokenize` 404도 필수 촬영 장면에서 뺀다.

### 설명할 때 지킬 구분

- 위험 요청 거부는 실제 요청으로 확인한다. 실제 RCE 성공·차단을 재현하는 영상이라고 말하지 않는다.
- 행동 탐지는 엔진 컨테이너 안의 별도 시험 프로세스로 재현한다.
- TG-CODE-01은 감시 대상 코드 파일 열기 탐지다. 모든 import나 승인되지 않은 코드 전체를 식별·차단하는 기능이라고 설명하지 않는다.
- 연결 실패만 보고 네트워크 정책 차단이라고 단정하지 않는다. 해당 연결의 Hubble DROPPED 기록과 정상 요청 성공을 함께 확인한다.

## 2. 먼저 알아 둘 창과 주소

터미널 창 또는 탭을 네 개 사용한다. 아래에서 창 번호를 계속 같은 의미로 쓴다.

| 창 | 실행 위치 | 용도 | 계속 켜 둘 것 |
| --- | --- | --- | --- |
| ① 서버 연결 | 노트북 WSL → SSH로 AWS 접속 | SSH 터널과 Gateway port-forward | 예 |
| ② 플랫폼 | 노트북 WSL | AWS Gateway를 읽는 플랫폼 실행 | 예 |
| ③ 사용자 요청 | 노트북 WSL | 정상·위험 요청 전송 | 예 |
| ④ 서버 작업 | 노트북 WSL → 별도 SSH 접속 | 시험 Pod와 엔진 컨테이너에서 행동 재현 | 예 |

| 주소 | 의미 |
| --- | --- |
| 노트북 `http://127.0.0.1:18700` | 이번 촬영용 플랫폼 |
| 노트북 `http://127.0.0.1:18081` | SSH 터널로 연결한 AWS Gateway |
| 서버 `http://127.0.0.1:18080` | 서버에서 port-forward한 Gateway |
| 클러스터 `serving-engine:8000` | 엔진 서비스. 직통 접근 차단 시험 대상 |

전체 연결은 다음과 같다.

```text
브라우저 → 노트북 플랫폼 :18700
                    ↓ 기록 조회
노트북 :18081 → SSH 터널 → 서버 :18080 → Gateway :8080 → 엔진 :8000

별도 시험 Pod ───────────→ 엔진 :8000
                    Cilium 차단 확인
```

기본 `byul-dev`는 로컬 모의 엔진도 띄운다. 이번 절차는 그것과 구분하기 위해 플랫폼을 18700에서 별도로 실행한다. 기존 개발 서버를 종료할 필요는 없다.

## 3. Windows에서 터미널 열기

1. Windows 키를 누른다.
2. `터미널` 또는 `Windows Terminal`을 검색해 실행한다.
3. 위쪽 탭 옆의 아래쪽 화살표를 누른다.
4. 현재 개발에 사용하는 WSL Ubuntu 프로필을 선택한다.
5. PowerShell이 아니라 Ubuntu 셸이 열린 것을 확인한다.
6. 다음 명령을 입력한다.

```bash
cd /home/bobgy/bobproject/byul
pwd
```

출력이 다음과 같아야 한다.

```text
/home/bobgy/bobproject/byul
```

이 창을 ① 서버 연결로 사용한다. 나머지 창도 같은 방법으로 Ubuntu를 연다. Windows Terminal의 탭을 오른쪽 클릭하면 이름을 바꿀 수 있으므로, 표의 이름으로 붙여 두면 구분하기 쉽다.

명령 블록은 하나씩 붙여 넣고 결과를 확인한 뒤 다음 블록으로 넘어간다. 여러 줄 블록을 붙였을 때 마지막 줄 뒤에서 Enter가 필요할 수 있다.

## 4. AWS 서버 켜기 — 아직 녹화하지 않는다

1. 브라우저에서 AWS 콘솔에 로그인한다.
2. 리전을 서울 `ap-northeast-2`로 맞춘다.
3. EC2 → 인스턴스로 이동한다.
4. 16회차 시험에 사용한 기존 GPU lab 인스턴스를 선택한다.
5. 상태가 `stopped`이면 시작한다. 이미 `running`이면 다시 시작하지 않는다.
6. 실행 상태와 상태 검사가 정상인지 확인한다.
7. 인스턴스 상세에서 현재 퍼블릭 IPv4 주소를 복사한다. 중지 후 재기동하면 주소가 바뀔 수 있다.

이 단계에서 인스턴스 유형 변경, 새 인스턴스 생성, 엔진 이미지 교체는 하지 않는다. 기존 16회차 배포를 다시 사용하는 절차다.

## 5. 창 ①에서 서버 접속과 터널 열기

### 5-1. 노트북 WSL에서 실행

키 파일 존재를 확인한다. 키 내용은 출력하지 않는다.

```bash
test -f "$HOME/.ssh/byul-aws-lab.pem" && echo "SSH 키 파일 있음"
```

아래를 실행한 뒤 입력을 기다리면, 방금 복사한 서버 IP를 붙여 넣고 Enter를 누른다.

```bash
read -r -p '현재 EC2 공인 IP: ' BYUL_POC_HOST
```

이어서 접속한다.

```bash
ssh -i "$HOME/.ssh/byul-aws-lab.pem" \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -L 18081:127.0.0.1:18080 \
  "ubuntu@$BYUL_POC_HOST"
```

처음 보는 호스트 키 확인이 나오면 접속하려는 기존 서버가 맞는지 확인한 뒤 진행한다. `REMOTE HOST IDENTIFICATION HAS CHANGED`가 나오면 known_hosts를 무조건 지우지 말고 먼저 접속 대상과 호스트 키를 확인한다.

### 5-2. 접속한 서버에서 실행

프롬프트가 바뀌면 이제 이 창의 명령은 AWS 서버에서 실행된다.

```bash
cd ~/byul/runtime
export PS1='[서버 연결] $ '
kubectl --context byul-aws-lab -n serving-lab get deploy,pod
```

확인할 것:

- `serving-gateway` Deployment가 준비돼 있다.
- `serving-engine` Deployment의 현재 엔진 Pod가 Ready다.
- `other-client` Pod가 실행 중이다.
- 오래된 실패 Pod가 아니라 현재 Deployment가 사용하는 Pod를 확인한다.

엔진 준비가 진행 중이면 아래로 기다린다.

```bash
kubectl --context byul-aws-lab -n serving-lab \
  rollout status deployment/serving-engine --timeout=300s
```

준비가 안 되면 촬영을 시작하지 않는다. 특히 EC2 재기동 직후에는 GPU 플러그인 복구가 늦어질 수 있다. 엔진 Pod 실패 상태를 확인하고 해결한 뒤 재개한다. 반복 재시작으로 상태를 덮지 않는다.

다음으로 Gateway를 포워딩한다.

```bash
kubectl --context byul-aws-lab -n serving-lab \
  port-forward deployment/serving-gateway 18080:8080
```

`Forwarding from 127.0.0.1:18080`이 보이면 연결 대기 상태다. 명령이 끝나지 않는 것이 정상이다.

**이 창은 그대로 둔다. Ctrl+C를 누르거나 닫으면 Gateway 연결이 끊어진다.** 이후 서버 작업은 창 ④에서 한다.

## 6. 창 ③에서 Gateway 연결 확인과 요청 준비

### 6-1. 새 Ubuntu 창을 연다

Windows Terminal에서 새 Ubuntu 탭을 만들거나 별도 창을 연다. 이 창은 계속 노트북 WSL에서 사용한다. SSH로 접속하지 않는다.

```bash
cd /home/bobgy/bobproject/byul
export PS1='[사용자 요청] $ '
set +x
```

### 6-2. 기존 시험 토큰을 불러온다

16회차에 사용한 노트북 토큰 파일은 아래 위치에 있다. 문서 작성 시 파일 존재, 권한 0600, 필요한 두 변수 이름을 확인했다. 토큰 유효성은 지금 Gateway 요청으로 확인한다.

```bash
set -a
source "$HOME/.local/state/serving-runtime/aws-lab/runtime-acceptance.env"
set +a
```

토큰을 출력하지 않고 값이 들어왔는지만 확인한다.

```bash
test -n "$RUNTIME_INFERENCE_TOKEN" && echo "추론 토큰 준비됨"
test -n "$RUNTIME_VIEWER_TOKEN" && echo "조회 토큰 준비됨"
```

`cat`으로 토큰 파일을 열거나 `echo`로 토큰 자체를 출력하지 않는다. 촬영 중 `curl -v`도 사용하지 않는다.

### 6-3. Gateway 조회가 되는지 확인한다

```bash
export BYUL_POC_GATEWAY='http://127.0.0.1:18081'
curl --silent --show-error --max-time 20 \
  --output /dev/null --write-out 'Gateway 조회 HTTP %{http_code}\n' \
  --header "Authorization: Bearer $RUNTIME_VIEWER_TOKEN" \
  "$BYUL_POC_GATEWAY/api/status"
```

`Gateway 조회 HTTP 200`이어야 한다. `000`이면 터널·포워딩부터, `401` 또는 `403`이면 토큰부터 확인한다.

### 6-4. 이번 촬영만의 임시 작업 폴더를 만든다

```bash
BYUL_POC_DIR=$(mktemp -d /tmp/byul-poc.XXXXXX)
cd "$BYUL_POC_DIR"
```

새 폴더라 기존 시험 기록을 건드리지 않는다. 이후 창 ③에서는 이 위치를 유지한다.

### 6-5. 정상 요청 파일을 만든다

아래 블록 전체를 붙여 넣는다. 마지막 `JSON`도 포함한다.

```bash
cat > normal.json <<'JSON'
{
  "model": "test-model",
  "messages": [
    {"role": "user", "content": "Say hello in one short sentence."}
  ],
  "max_tokens": 32
}
JSON
```

`test-model`은 이 lab의 서비스 모델 이름이다.

### 6-6. 위험 필드를 넣은 요청 파일을 만든다

```bash
cat > attack-chat.json <<'JSON'
{
  "model": "test-model",
  "messages": [
    {"role": "user", "content": "Say hello in one short sentence."}
  ],
  "max_tokens": 32,
  "mm_processor_kwargs": {
    "code_revision": "BYUL_POC_UNAPPROVED_REVISION"
  }
}
JSON
```

판본 값은 실제 공격자 코드 위치가 아니라 시험용 표식이다. 이번 Gateway 시험은 필드 자체를 거부하는지 확인한다.

### 6-7. 촬영 중 사용할 요청 함수를 준비한다

아래 블록 전체를 한 번 실행한다. 함수를 정의하는 단계라 아직 요청을 보내지 않는다.

```bash
poc_request() {
  if ! curl --silent --show-error --max-time 90 \
    --dump-header response.headers \
    --output response.json \
    --write-out '\nHTTP %{http_code}\n' \
    --header "Authorization: Bearer $RUNTIME_INFERENCE_TOKEN" \
    --header 'Content-Type: application/json' \
    --data-binary "@$1" \
    "$BYUL_POC_GATEWAY/v1/chat/completions"; then
    echo '통신 실패: 연결 상태부터 확인'
    return 1
  fi
  python3 -m json.tool response.json
}
```

이제 `poc_request normal.json` 또는 `poc_request attack-chat.json`만 입력하면 된다. 응답 헤더·본문은 이 임시 폴더에 저장된다.

### 6-8. 정상 요청을 미리 한 번 보낸다

```bash
poc_request normal.json
```

`HTTP 200`과 모델 응답이 보여야 한다. 503이면 대상·정책·관측 상태를 확인한다. 응답 본문의 사유를 해결하기 전에는 다음 촬영 단계로 넘어가지 않는다.

## 7. 창 ②에서 촬영용 플랫폼 실행

### 7-1. 새 Ubuntu 창을 열고 화면을 빌드한다

이 창도 노트북 WSL이다.

```bash
cd /home/bobgy/bobproject/byul/platform/web
npm run build
```

빌드가 정상 종료돼야 한다. 기존 설치 환경을 사용하는 명령이다. 의존성 부재로 실패하면 원인을 해결한 뒤 다시 빌드한다.

### 7-2. 토큰과 플랫폼 실행 설정을 불러온다

```bash
cd /home/bobgy/bobproject/byul/platform/api
set +x
set -a
source "$HOME/.local/state/serving-runtime/aws-lab/runtime-acceptance.env"
set +a

export RUNTIME_BASE_URL='http://127.0.0.1:18081'
export BYUL_PLATFORM_HOST='127.0.0.1'
export BYUL_PLATFORM_PORT='18700'
export PLATFORM_DATA_DIR='/tmp/byul-poc-platform-data'
```

`RUNTIME_VIEWER_TOKEN`은 방금 파일에서 export됐으므로 플랫폼이 서버 쪽 조회 인증에 사용한다. 화면 입력칸에 붙여 넣지 않는다.

### 7-3. 플랫폼을 실행한다

```bash
uv run --frozen \
  --with-editable ../../runtime \
  --with-editable ../../update \
  byul-platform
```

`127.0.0.1:18700`에서 실행 중이라는 로그가 보이면 그대로 둔다. 이 창도 닫거나 Ctrl+C를 누르지 않는다.

18700이 이미 사용 중이면 기존 촬영용 플랫폼이 켜져 있는지 확인한다. 확인하지 않은 프로세스를 강제로 종료하지 않는다.

### 7-4. 브라우저로 접속한다

주소창에 다음을 입력한다.

```text
http://127.0.0.1:18700/runtime/overview
```

로그인 화면이 나오면 로그인한다. 위 임시 데이터 폴더를 처음 사용하는 기본 설정에서는 초기 계정이 `admin` / `admin`이다. 같은 폴더에서 이미 비밀번호를 바꿨다면 변경한 비밀번호를 사용한다. 로그인과 비밀번호 입력은 녹화 전에 끝낸다.

### 7-5. 실제 AWS 연결인지 확인한다

다음 항목을 확인한다.

- 사이드바 runtime 연결이 `연결 정상`이다.
- 현황의 백엔드가 외부 vLLM이며 `모의 엔진`이 아니다.
- 창 ③에서 방금 보낸 정상 요청이 `요청` 화면에 나타난다.
- `수집 상태`에서 Hubble·Tetragon의 최근 수집이 정상이다.
- `엔진 실행 단계`에서 현재 엔진의 추론 단계 근거가 있다.

상단에 다른 출처의 예시 자료 안내가 남을 수 있다. 촬영에서 사용하는 runtime 출처가 실제 연결인지 구분한다. runtime 자체가 예시 데이터라면 촬영을 진행하지 않는다.

## 8. 창 ④에서 서버 시험 준비

### 8-1. 별도 SSH 연결을 연다

새 Ubuntu 창을 열고 아래를 실행한다. 이 연결에는 `-L`을 붙이지 않는다. 터널은 창 ①이 이미 담당한다.


### 8-2. 에이전트와 정책 상태를 확인한다

```bash
systemctl is-enabled serving-runtime-agent.service
systemctl is-active serving-runtime-agent.service
```

16회차 종료 상태의 기대값은 각각 `disabled`, `inactive`다. 이 두 조회는 해당 상태에서 종료 코드가 0이 아닐 수 있다. 출력으로 확인한다. 이번 촬영에서는 에이전트를 시작하거나 정책 전환을 요청하지 않는다.

```bash
kubectl --context byul-aws-lab -n serving-lab \
  get pod other-client

kubectl --context byul-aws-lab -n serving-lab \
  get tracingpolicynamespaced runtime-tg-code-01

kubectl --context byul-aws-lab -n serving-lab \
  get tracingpolicynamespaced runtime-tg-code-01 \
  -o go-template='{{index .metadata.annotations "serving-runtime.local/kernel-identity"}}{{"\n"}}'
```

コード 감시 정책은 16회차에 남겨 둔 monitor 정책을 사용한다. kernel identity 표시는 `v2`여야 한다. 플랫폼의 `파일·프로세스 정책 (Tetragon)`에서도 실제 적재·상태를 확인한다. 객체 존재만으로 적재 성공을 판단하지 않는다.

정책이 없거나 신원·단계가 미확인이면 코드 탐지 장면을 먼저 해결하고 리허설한다. 기본 intent로 전체 정책을 다시 렌더·적용하는 명령을 임의로 실행하지 않는다. 16회차에는 코드 감시 정책만 kernel identity를 켜 보정한 이력이 있다.

### 8-3. 직통 접근 시험 스크립트를 만든다

아래 파일은 서버의 `/tmp`에 만든다. 나중에 이 내용을 `other-client` 컨테이너의 Python으로 실행한다.

```bash
cat > /tmp/byul-poc-direct-tokenize.py <<'PY'
import errno
import json
import socket
import sys

body = json.dumps({
    "model": "test-model",
    "messages": [{"role": "user", "content": "Say hello."}],
    "mm_processor_kwargs": {
        "code_revision": "BYUL_POC_UNAPPROVED_REVISION"
    },
}).encode()

sock = socket.socket()
sock.settimeout(3)
try:
    result = sock.connect_ex(("serving-engine", 8000))
except OSError as error:
    sock.close()
    print("PROBE_ERROR", type(error).__name__)
    sys.exit(2)

if result:
    sock.close()
    print("CONNECT_FAILED errno=%d name=%s" % (
        result, errno.errorcode.get(result, "UNKNOWN")))
    print("TCP 연결 실패: HTTP 본문은 전송되지 않았습니다.")
    expected = {errno.EAGAIN, errno.EWOULDBLOCK, errno.ETIMEDOUT}
    sys.exit(0 if result in expected else 2)

print("CONNECTED: 직통 접근 차단을 확인하지 못했습니다.", flush=True)
try:
    headers = (
        "POST /tokenize HTTP/1.1\r\n"
        "Host: serving-engine:8000\r\n"
        "Content-Type: application/json\r\n"
        "Connection: close\r\n"
        "Content-Length: %d\r\n\r\n" % len(body)
    ).encode()
    sock.sendall(headers + body)
finally:
    sock.close()
sys.exit(1)
PY
```

이 스크립트는 연결 단계가 막히면 JSON을 보내지 못했다고 출력한다. 이것을 엔진의 필드 검사 결과로 설명하면 안 된다.

### 8-4. 무해한 코드 불러오기 스크립트를 만든다

```bash
cat > /tmp/byul-poc-code-load.py <<'PY'
import importlib.util
import json
import os
import tempfile
import time
from datetime import datetime, timezone
from pathlib import Path

modules = Path(
    os.environ.get("HF_MODULES_CACHE")
    or str(Path(os.environ.get("HF_HOME")
                or str(Path.home() / ".cache/huggingface")) / "modules")
)
modules.mkdir(parents=True, exist_ok=True)

# 16회차 재현과 같이 수집·신원 대조를 위한 시간을 둡니다.
time.sleep(15)
with tempfile.TemporaryDirectory(prefix="byul-poc-", dir=modules) as directory:
    path = Path(directory) / "harmless.py"
    path.write_text("VALUE = 42\n", encoding="utf-8")
    started = datetime.now(timezone.utc).isoformat()
    spec = importlib.util.spec_from_file_location("byul_poc_probe", path)
    module = importlib.util.module_from_spec(spec)
    spec.loader.exec_module(module)
    ended = datetime.now(timezone.utc).isoformat()
    time.sleep(8)
    print(json.dumps({
        "path": str(path),
        "pid": os.getpid(),
        "import_from": started,
        "import_until": ended,
        "value_ok": module.VALUE == 42,
    }, indent=2))
PY
```

이 코드는 임시 디렉터리에 무해한 파일을 만들고 불러온 뒤 정리한다. 기존 모델 파일이나 기존 캐시 파일을 수정하지 않는다. 정상 실행도 약 23초 이상 걸리므로 잠시 출력이 없어도 바로 중단하지 않는다.

파일 생성과 import 둘 다 파일 열기를 발생시킬 수 있다. import 구간까지 구분하려면 출력의 시각·경로·프로세스와 이벤트를 대조한다. 단순 open 이벤트만으로 import 실행을 입증했다고 말하지 않는다.

## 9. 브라우저 탭을 미리 준비한다

아래 주소를 각각 열어 둔다. 로그인 후 사용하는 주소다.

| 탭 | 주소 |
| --- | --- |
| 현황 | `http://127.0.0.1:18700/runtime/overview` |
| 요청 | `http://127.0.0.1:18700/runtime/requests` |
| Hubble | `http://127.0.0.1:18700/runtime/observe/hubble` |
| 코드 탐지 사건 | `http://127.0.0.1:18700/runtime/events?source=tetragon&rule=TG-CODE-01` |
| SUP-008 | `http://127.0.0.1:18700/runtime/observe/checks?check=CHK-SUP-008` |

기간은 지금 발생시키는 사건이 포함되는 범위로 맞춘다. 환경 필터가 다른 환경으로 고정돼 있다면 해제하거나 실제 AWS 대상에 맞춘다.

코드 탐지는 Tetragon 전용 표보다 `사건 로그`의 해당 규칙 필터에서 결과와 원본을 확인하기 쉽다. 상세에서 `code_load_verdict`, `phase`, `path`를 대조한다.

화면 크기가 작아 상세를 보기 어려우면 확인 장면에서 브라우저를 잠시 크게 띄운다. 글자를 지나치게 작게 줄여 두 화면을 억지로 넣지 않는다.

## 12. 본 촬영 — 화면과 명령 순서

### 장면 1. 정상 서비스 — 약 40초

1. 브라우저 `현황`을 보여 준다.
2. 외부 vLLM 연결과 Gateway 상태를 확인한다.
3. 창 ③에서 실행한다.

```bash
poc_request normal.json
```

4. `HTTP 200`과 모델 응답을 잠시 보여 준다.
5. 브라우저 `요청` 탭에서 방금 요청을 확인한다.

설명할 내용: 사용자 요청이 우리 Gateway를 통해 실제 엔진으로 전달되고 정상 처리된다.

### 장면 2. 위험 필드 거부 — 약 50초

1. 창 ③에서 요청 파일을 보여 준다.

```bash
cat attack-chat.json
```

2. `mm_processor_kwargs.code_revision`이 있는 부분을 보여 준 뒤 실행한다.

```bash
poc_request attack-chat.json
```

3. `HTTP 400`과 실제 응답 사유를 보여 준다.
4. 브라우저 `요청` 탭의 새 거부 행을 클릭한다.
5. 상세에서 다음을 순서대로 보여 준다.

| 항목 | 확인할 내용 |
| --- | --- |
| HTTP | 400 |
| 원본 코드 | 16회차 결과는 `CODE_SELECTION_FIELD`. 지금 결과도 실제 값으로 확인 |
| 적용 규칙 | `request_code_selection` |
| 설명 | 코드 선택 필드 경로 |
| 전달 시도 | `아니요 (엔진 미호출)` |

설명할 내용: Gateway가 코드 선택 필드를 엔진 전달 전에 거부하며, 일반 오류와 구분해 기록한다. 공격 필드 값은 기록하지 않는다.

### 장면 3. Gateway 우회 접근 차단 — 약 50초

1. 창 ④를 앞으로 가져온다.
2. 브라우저는 `Hubble` 탭을 연다.
3. 창 ④에서 실행한다.

```bash
kubectl --context byul-aws-lab -n serving-lab \
  exec -i pod/other-client -c client -- python3 - \
  < /tmp/byul-poc-direct-tokenize.py
```

4. `CONNECT_FAILED`와 시간 초과 계열 결과를 보여 준다. 16회차에는 `EAGAIN`이었다.
5. 브라우저에서 같은 시각의 `other-client` → `serving-engine`, 목적지 8000의 `DROPPED` 기록을 보여 준다.

설명할 내용: 별도 Pod에서 Gateway를 건너뛰고 엔진에 직접 접근해도 네트워크에서 차단된다. TCP 연결이 막혔으므로 공격 JSON 본문은 엔진에 전달되지 않았다.

`ECONNREFUSED`나 DNS 실패만 나온다면 정책 차단 성공으로 설명하지 않는다. 잘못된 목적지나 서비스 장애일 수 있다. `CONNECTED`가 나오면 촬영을 멈추고 통제 상태를 확인한다.

### 장면 4. 코드 파일 열기 행동 탐지 — 약 60초

1. 브라우저를 미리 `코드 탐지 사건` 탭으로 바꾼다.
2. 엔진 컨테이너의 별도 시험 프로세스로 행동을 재현한다고 밝힌다.
3. 창 ④에서 실행한다.

```bash
kubectl --context byul-aws-lab -n serving-lab \
  exec -i deployment/serving-engine -c engine -- python3 - \
  < /tmp/byul-poc-code-load.py
```

4. 약 23초 이상 기다린다. 대기 중 플랫폼을 확인해도 된다.
5. 출력의 `value_ok: true`, 파일 경로와 실행 시각을 확인한다.
6. 브라우저에서 새 사건을 클릭한다.
7. 개요·원본에서 다음을 확인한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 출처 | Tetragon |
| 규칙 | `TG-CODE-01` |
| 결과 | 탐지 (`detected`) |
| 단계 | 추론 (`inferring`) |
| 파일 경로 | 방금 출력된 `harmless.py` 또는 그에 대응하는 코드 파일 |
| 모드 | monitor |

설명할 내용: 요청 필드 검사와 별개로, 서비스 중 감시 대상 경로의 코드 파일을 여는 행동을 탐지해 기록한다. 이 규칙은 차단 기능이 아니다.

결과가 `unknown`이면 탐지 성공으로 설명하지 않는다. 현재 수집 상태·단계 근거·커널 신원·Pod 귀속을 확인한다. 파일 생성과 import의 이벤트를 따로 설명하려면 출력 시각과 동일 프로세스 근거를 추가 대조한다.

### 장면 5. 체크리스트 연결과 정상 서비스 유지 — 약 40초

1. 브라우저 `SUP-008` 탭을 연다.
2. 연결 규칙의 `request_code_selection`, `TG-CODE-01`과 관련 사건 수를 보여 준다.
3. `관련 사건` 링크를 눌러 어떤 기록이 연결되는지 확인한다.
4. 창 ③으로 돌아와 실행한다.

```bash
poc_request normal.json
```

5. 마지막 `HTTP 200`을 보여 준 뒤 녹화를 끝낸다.

설명할 내용: 요청 거부와 행동 탐지 기록이 체크리스트의 운영 근거로 연결되고, 정상 서비스는 계속 동작한다. 관련 사건 집계 자체를 체크리스트 전체의 보안 통과 판정이라고 말하지 않는다.

말을 동시에 녹음하는 것이 부담되면 화면을 먼저 찍고 자막을 붙여도 된다. 각 장면의 설명은 위 `설명할 내용`을 사용한다.

## 14. 촬영이 안 될 때 확인 순서

| 증상 | 먼저 확인할 것 |
| --- | --- |
| SSH 연결 실패 | 현재 공인 IP, 서버 상태, SSH 키, 기존 접속 허용 설정 |
| Gateway 조회 HTTP 000 | 창 ①의 SSH 터널과 port-forward가 살아 있는지 |
| Gateway 401·403 | 토큰 파일, 추론/조회 역할 구분. 토큰을 출력해 확인하지 않음 |
| 정상 요청 503 | 응답 사유, Gateway 활성·승인·대상 일치·수집 상태 |
| 플랫폼 접속 실패 | 창 ② 실행 로그, 18700 포트, 노트북 localhost 접근 |
| 플랫폼이 모의 엔진을 표시 | 18700 촬영용 플랫폼인지, `RUNTIME_BASE_URL`이 18081인지 |
| 요청 화면이 비어 있음 | 기간·환경·검색 필터, 요청 시각, 연결 상태 |
| 코드 탐지가 unknown | kernel identity v2, 현재 Pod 귀속, 추론 단계, 수집 정상 여부 |
| 코드 탐지가 금방 사라짐 | 최근 Tetragon 조회 창 한계. 재현 직후 촬영하고 기록 보존 |
| 직통 연결이 성공함 | 우회 차단 미확인. 정책·엔진 대상·시험 Pod 상태부터 점검 |
| Hubble 기록만 없고 연결 실패 | 수집·필터·해당 흐름을 확인. 기록 없이 정책 차단을 단정하지 않음 |

상태가 달라졌을 때 전체 배포 재적용이나 모든 정책 교체부터 하지 않는다. 이번 안내는 기존 16회차 환경을 이용한 촬영 순서이며, 설치·마이그레이션·정책 복구 절차 전체를 대체하지 않는다.

## 15. 촬영 후 종료 — 영상 저장을 확인한 뒤

1. 창 ③에서 마지막 정상 요청 200을 확인한다.
2. 영상 파일이 실제 저장됐고 재생되는지 확인한다.
3. 창 ④에서 `exit`로 서버 접속을 종료한다.
4. 창 ②에서 Ctrl+C를 눌러 촬영용 플랫폼을 종료한다.
5. 창 ①에서 Ctrl+C를 눌러 port-forward를 종료한다.
6. 이어서 창 ①에서 `exit`로 SSH를 종료한다. SSH 터널도 함께 닫힌다.
7. AWS 콘솔에서 해당 인스턴스를 선택한다.
8. 인스턴스 상태 → 인스턴스 중지를 선택한다. 종료/삭제를 선택하지 않는다.
9. 최종 상태가 `stopped`인지 확인한다.

터미널이나 브라우저만 닫아도 EC2가 중지되는 것은 아니다. 콘솔의 stopped까지 확인한다.

이번 순서에서는 정책 모드를 바꾸지 않았으므로, 원래 정책을 복구하는 추가 작업은 없다. 코드 시험의 임시 디렉터리는 스크립트가 정상 종료되면 정리된다. 정상 종료 전에 강제로 끊었다면 해당 시험의 임시 파일 잔존 여부를 별도로 확인한다.

## 16. 촬영 직전 한 장 확인표

- [ ] 서버가 실행 중이고 현재 엔진·Gateway가 Ready다.
- [ ] 창 ① SSH 터널과 Gateway port-forward가 켜져 있다.
- [ ] 창 ② 촬영용 플랫폼이 18700에서 실행 중이다.
- [ ] runtime 출처가 실제 AWS 연결이며 모의 엔진이 아니다.
- [ ] 정상 요청이 200이다.
- [ ] 위험 필드 요청이 400이고 엔진 미전달이 확인된다.
- [ ] 직통 접근 실패와 해당 Hubble DROPPED를 리허설했다.
- [ ] TG-CODE-01의 kernel identity·수집·단계가 준비돼 있고 탐지를 리허설했다.
- [ ] SUP-008 관련 사건이 화면에 보인다.
- [ ] 로그인·토큰·공인 IP 준비 화면이 녹화 영역에 없다.
- [ ] 촬영 후 저장할 폴더를 정했다.
- [ ] 촬영 후 EC2 stopped까지 확인한다.
