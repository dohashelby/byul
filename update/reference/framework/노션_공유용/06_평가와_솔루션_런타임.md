## 전체 체계에서 평가와 솔루션의 역할

거버넌스는 정책·책임·승인 조건을 정하고, 위험 관리는 보완·수용·대응 우선순위를 정한다. 평가는 실제 환경에서 보호 요구를 확인해 그 결정에 필요한 증거를 제공한다. 업데이트 검증과 런타임 도구는 일부 점검과 통제·관측을 구현한다. 도입·변경·운영·복구·폐기에서 필요한 평가 시점을 정하고, 같은 CHK의 실행 조건과 결과를 구분해 남긴다.

<a id="61-사용자가-넣는-정보와-받는-결과"></a>
## 5.1 사용자가 넣는 정보와 받는 결과

| 단계 | 사용자가 제공·확인할 것 | 도구가 지원할 결과 |
| --- | --- | --- |
| 환경 등록 | 실제 배포에 대한 읽기·시험 권한, 수집된 환경 정보 확인 | 엔진·모델·설정·GPU·호출 경로·활성 기능 요약과 확인하지 못한 내용 |
| 정책·점검 선택 | 허용 사용자·모델·통신·공유·자원·성능 기준과 예외 | 적용 CHK·분기, 선정·제외 이유, 필요한 준비·수동 확인 |
| 현재 환경 평가 | 선택한 시험과 격리 환경·시험 자료 확인 | 보안·정상 기능·성능 결과와 증거·보완 사항 |
| 업데이트 비교 | 기준·후보 환경, 변경 내용과 비교 조건 | 버전별 결과·개선·회귀·기존 위반·비교 불가 |
| 승인 검토 | 미충족·미확인·보완 효과와 운영 조건 검토 | 검토 보고서·승인 조건·재시험 목록 |
| 운영 확인 | 통제 대상·승인 정책·알림·장애 대응 기준 | 정책 적용·허용/거부·구성 변경·관측 상태·재평가 요청 |

위 표는 **제공할 기능**을 설명한다. 현재 구현 상태는 5.8에 적었다. 자동수집으로 알 수 없는 허용 관계·정책·예외는 사람이 정하고, 실제 변경·운영 적용도 담당자가 승인한다.

## 5.2 평가 흐름

![업데이트 영향평가의 전체 흐름](assets/evaluation-flow.png)

그림의 ②는 항목·정책·자료·판정 계획을 정하는 단계이고 ③은 실제 격리 환경을 준비하는 단계다. 기준 버전과 후보 버전은 같은 조건에서 차례로 실행할 수 있다. GPU를 공유하면 이전 실행에서 남은 상태·캐시·자원을 확인한 뒤 다음 시험을 시작한다.

| 순서 | 할 일 | 다음 단계로 넘길 내용 |
| --- | --- | --- |
| 1. 대상 확인 | 실제 엔진·이미지·의존성·모델·유효 설정과 호출 경로 확인 | 환경 식별·버전·수집 근거·미확인 |
| 2. 위협·영향평가와 계획 | 변경 근거를 실제 사용 경로·자산·경계·보호 조건에 대조하고 관련 CHK·분기와 시험·증거 선택 | 영향 판단·선정 이유·재사용 범위, 실행 명세와 남은 확인·담당 |
| 3. 격리 준비 | 권한·망·GPU·모델 기동·수집·정리 범위 확인 | 준비 확인 결과와 중단·복구 절차 |
| 4. 기준 시험 | 정상·보안·성능 시험과 증거 수집 | 기준 환경의 항목별 결과 |
| 5. 후보 시험 | 같은 의미의 설정·입력·부하에서 시험 | 후보 환경의 항목별 결과와 조건 차이 |
| 6. 비교·보고 | 버전별 판정 후 차이·미확인·보완 정리 | 검토 보고서와 재시험·승인 조건 |
| 7. 검토·적용 | 담당자가 보완·재시험·적용·보류 판단 | 승인한 배포·정책·예외·운영 조건 |

변경 영향·알려진 패치 회귀 시험뿐 아니라 해당 환경의 공통 보호 요구가 유지되는지와 정상 기능·성능을 확인하는 시험도 계획에 포함한다. 이전 버전의 통과 결과를 그대로 승계하지 않고, 기존 시험을 재사용할 때도 준비 조건·입출력·증거가 새 환경에서 같은 내용을 확인하는지 살펴본다.

업데이트 건별 인계는 [05의 공통 규칙](../05_평가와_증거관리.md#update-impact-handoff)을 따른다. 변경 근거 → 실제 보호 조건의 영향 → 관련 요구·CHK·분기 → 시험·증거 재사용 범위 → 남은 확인·담당을 기존 기록에 연결한다. 대응되지 않는 변경은 범위 공백 검토로, 근거 부족은 추가 확인으로 넘긴다. 필요한 시험 목록을 바꾸는 미결 사항은 목록 완결 여부에 반영한다.

변경 대상이 없으면 현재 환경의 보호 요구 충족 여부를 평가한다. 업데이트 비교는 현재·후보 환경을 추가해 같은 기준의 결과를 비교하는 사용 방식이다.

### 시험 명세에 필요한 내용

정상 대조는 허용된 입력·작업을 같은 조건에서 실행해 정상 동작을 확인하는 비교 시험이다.

**CHK·분기·SC → 실제 환경·정책 → 입력·준비 → 정상 대조·시험 순서 → 필수 증거 → 충족·미충족·미확인 → 정리·복구**

Q·SC의 시험 초점에 맞춰 실행 절차를 작성한다. 실제 시험 실행기와 입력 자료, 도달해야 할 처리 함수(handler), 관측 위치, 정리할 대상과 시점을 정한다. 각 CHK가 허용하는 검토·시험 방법을 적용한다. 자동 시험이 어려우면 허용된 문서·설정 검토나 수동 시험의 절차와 증거를 정하고, 필요한 실행 증거를 확보하지 못한 범위는 미확인으로 남긴다.

<a id="기존-자료로-점검을-준비하는-순서"></a>
### 기존 자료로 점검을 준비하는 순서

기존 정책·배포 자료·평가 기록을 먼저 모아, 선택한 CHK의 적용 조건·필요한 증거·정상 대조와 맞춘다. 보호 요구의 ‘환경에 맞춰 채울 값’은 관련 점검을 묶은 안내이므로, 이번 CHK·분기에 필요한 값만 확인한다. 여러 항목에 쓰는 같은 허용표·설정·실행 증거는 한 번 확보하고 해당 기록을 참조한다.

| 가져온 자료 | 재사용 여부를 확인할 내용 | 부족할 때 다음 행동 |
| --- | --- | --- |
| 승인 정책·허용표·서비스 기준 | 이번 서비스·대상·작업에 적용되는 승인 판본과 유효기간을 확인한다. 유효한 기준은 참조하고 변경·미정인 값만 결정한다. | 정책 소유자가 필요한 기준을 마련하고 권한자가 확정한다. 현재 설정값과 승인 기준은 구분한다. |
| 배포 기록·설정·환경 자료 | 이번 실제 대상과 유효 상태를 뒷받침하는지 확인한다. 기존 자료에 변경 내역·현재 상태 확인 근거를 더할 수 있다. | 환경·운영 자료 제공 역할이 빠진 경로·구성·설정을 확인한다. 계획값이나 오래된 자료만 있으면 실제 상태 확인을 요청한다. |
| 과거 시험 결과·원본 증거 | 기존 재사용 조건에 따라 이번 결론을 뒷받침하는 범위를 정한다. 변경된 집행 경로·입력 처리·공유·의존성·측정 조건이 결과에 영향을 주는지 검토한다. | 평가자가 재사용할 범위와 다시 확인할 범위를 구분하고, 시험 담당자가 필요한 경로·분기의 증거를 확보한다. |

문서·설정 검토로 판정하는 내용과 실행 결과가 필요한 내용은 각 CHK의 기존 기준을 따른다. 자료 확보는 연결 조회·내보낸 파일·기존 문서나 시험 보고서 등 기업이 제공 가능한 방법을 사용하되, 대상·출처·시점·확인 범위가 해당 결론을 뒷받침해야 한다. 담당자 설명은 운영 의도나 증거 위치를 확인할 때 활용한다.

부족한 내용은 기존 평가 기록에 **CHK·분기 → 확보한 근거 → 남은 확인 → 다음 행동·담당 역할** 순서로 정리한다. 일반 응답만 시험했으면 남은 필수 옵션·오류 경로를, 취소 응답만 있으면 해당 CHK가 요구하는 내부 종결 증거를 추가 대상으로 적는다. 계측·시험기가 필요한 경우 개발·시험 담당자의 준비 과제로, 허용값이 필요한 경우 정책 결정 과제로 나눈다. 실제 역할은 기업의 업무·권한에 맞춰 지정한다.

재사용 여부는 자료별·확인 범위별로 기록한다. 예를 들어 응답 허용 정책이 그대로여도 반환·오류 처리 경로가 바뀌면 정책은 참조하고 관련 실행 결과는 다시 확보한다. 판정·집계와 증거 충분성은 [원문 05의 기존 규칙](../05_평가와_증거관리.md#증거-충분성과-채택-검토)을 적용하고, 확인된 위반·미확인 범위와 관리자의 처리 결정은 각각 유지한다. 기존 보고서·티켓·평가 기록을 참조하며 같은 내용을 항목마다 새 문서로 작성할 필요는 없다.

### 시험 자원과 운영 영향

시험 준비와 결과에는 다음 자원 정보를 함께 기록한다. 대상 구성과 중단·복구·정리 절차는 기존 기록을 참조한다.

- **시험 자원:** 필요한 CPU·메모리와 GPU 사용 시 GPU 수·GPU 메모리·TP 구성, 전용·공유 여부.
- **시간:** 예상 자원 점유 시간과 산정 근거, 실행 후 실제 점유 시간과 측정 근거. 전체 실행 시간은 기존 시작·종료 시각을 재사용하고 자원 점유 시간과 구분한다.
- **운영 영향:** 운영 서비스와 자원을 공유하면 영향받는 서비스, 허용 영향·시험 시간대와 기존 중단 기준의 적용 범위.
- **자원 반환:** 시험 종료 후 임시 실행 환경과 할당·예약이 정리되고 시험용 자원이 반환됐는지 확인할 기록·시각·관측 근거.

개발·시험 담당자가 추정·측정값과 근거를 제공한다. 확인 전 값은 미정·미확인으로 남긴다.

### 증거 충분성과 채택 검토

검토자는 [04 체크리스트](04_환경별_적용과_체크리스트.md)의 필요한 증거와 충족·미충족·미확인 기준을 적용할 때 다음 내용을 확인한다. 시험 담당자는 실행 전에 증거와 판정 조건의 대응을 제시하고, 검토자는 수집 방법이 해당 결론을 뒷받침하는지 검토한다. 실행 후에는 실제 확보한 증거로 다시 확인한다. 항목의 성격에 맞춰 기존 문서·설정·실행 기록과 검토 결과를 재사용한다. 문서·설정 검토는 기준과 유효 상태를 대조하고, 실행·메모리·시간·통계 증거는 해당 CHK의 기존 판정에 필요한 범위에서 확인한다.

- **판정 대상까지의 연결:** 문서·설정 검토는 승인 대상과 유효 설정을, 실행 시험은 실제 집행·소비·거부 지점에 도달한 결과를 뒷받침해야 한다. 관측 지점의 신뢰 근거·관측 범위와 누락 구간을 적는다. 설정값과 자기 보고만 확보했다면 실제 집행에 대한 결론의 범위를 제한한다.
- **위반을 구별하는 방법:** 실행 시험은 해당 CHK에서 정한 정상·비허용 대조가 보호 조건의 충족과 위반을 구별하는지 확인한다. 통계적 추론을 사용하는 시험은 표본·오차·대조 설계의 근거를 검토한다. 결과를 보고 판정 방법을 조정한 경우 변경 이유와 판본을 남기고 조정한 방법의 결론을 별도 자료·실행에서 확인한다. 이미 확인한 요구 위반은 유지한다.
- **충돌과 적용 한계:** 서로 다른 증거가 같은 대상·시각·조건을 가리키는지 대조하고 불일치 원인을 확인한다. 관측하지 못한 경로·rank·조건과 증거 재사용 범위를 남긴다. 필수 증거 부족은 미확인, 확인된 요구 위반은 미충족으로 유지하며 항목별 판정과 집계는 [5.4 판정과 버전 비교](#64-판정과-버전-비교)를 따른다.

다음 두 항목은 기존 증거 목록에 더해 **증거 사이의 대응과 방법의 한계**를 검토한다.

| 점검 | 증거를 채택할 때 추가로 확인할 내용 |
| --- | --- |
| [CHK-SUP-006](04_환경별_적용과_체크리스트.md#CHK-SUP-006) — 승인 모델의 실제 적재 | 승인 파일·rank별 배정·필수 tensor에서 mapper·양자화·후처리를 거쳐 실제 적재 내용으로 이어지는 대응을 확인한다. 기대값은 승인 원본과 승인된 변환 절차에서 정하고, 의도된 생성값과 누락을 구분한다. 바이트가 달라지는 변환은 비교할 표현을 정하고, 수치 오차가 있는 비교를 사용할 때 그 허용 근거를 남긴다. 각 필수 rank·부분의 실제 소비를 뒷받침하는 계측·비교 범위를 명시하고, 누락·교체 자료를 구별하는지 확인한다. 직접 계측과 검토된 대체 증거를 조합해 필수 대응을 확인한다. 파일 hash·header·경로명·canary 결과만으로 남는 적재 증거의 공백을 해소하지 못하면 해당 범위는 미확인으로 남긴다. |
| [CHK-REQ-017](04_환경별_적용과_체크리스트.md#CHK-REQ-017) — 캐시 신호에 의한 추론 | 공격자가 읽을 수 있는 시간·응답 필드·지표별로 prefix 존재·부재의 실제 상태와 추론 결과를 대조한다. 지연 등으로 통계적 추론을 하는 분기에서는 표본·오차, cache 상태·요청 순서·동시부하 등 주요 조건의 통제와 정상 대조를 확인한다. 존재·부재 구성비와 우연 수준을 고려해 추론 성능의 불확실성 범위가 채택 기준에 대한 결론을 지지하는지 본다. 추론 방법을 자료에 맞춰 조정하면 조정 자료와 최종 판정 자료를 구분한다. 직접 반환된 hit 정보는 그 독자·집단·보호 정책과 대조한다. 기준을 넘는 추론과 관측 능력 부족을 구별할 근거가 부족하면 미확인으로 남긴다. |

개발·시험 담당자가 fixture·계측·변환 비교·통계 계산을 구현하고 측정값과 원자료를 제공한다. 보안·플랫폼 검토자는 관측 범위와 방법의 충분성을 검토하고 정책 승인자는 조직별 허용값을 확정한다. 표본 수·오차·기한·예산 등 실제 수치는 대상과 방법의 근거가 확보된 뒤 기록한다.

<a id="기한-판정의-증거"></a>
### 기한 판정의 증거

기한을 판정하는 시험에서는 채택한 시작·완료 사건의 의미와 각 시각을 같은 실행에 연결한다. 같은 시계의 기록을 사용하거나 서로 다른 시계의 차이·오차를 확인할 근거를 남긴다. 오차 때문에 기한 준수 여부를 가를 수 없으면 해당 결과는 미확인으로, 기한 초과가 확인되면 미충족으로 기록한다. 기존 시각·동기화·수집 기록을 재사용하고 기한값과 실제 측정값은 담당 조직·시험 담당자가 제공한다.

<a id="63-솔루션은-어디에서-동작하는가"></a>
## 5.3 솔루션은 어디에서 동작하는가

![ServeGuard 런타임 통제·관측 전체 구성 — v1.3 설계](assets/solution-architecture.png)

그림은 팀원의 **v1.3 런타임 설계**다. 승인된 정책·구성을 Gateway·통신·파일 권한에 적용하고, 엔진·통제 도구의 기록을 런타임 관리부에서 수집해 담당자가 상태와 증거를 확인한다. Cilium·Hubble·Tetragon은 설계에서 선택한 도구이며, 기존 Gateway·구성 비교 코드와의 통합 및 vLLM·SGLang 실환경 검증은 남아 있다. 업데이트 전 격리 시험은 6.2의 절차를 따른다.

코드·실행 시험의 기본 참조 구성은 vLLM 0.31.0 다중 GPU·TP다. 내부 통신과 rank 장애는 해당 TP 구성에서 시험하고, 단일 GPU 시험과 각각의 확인 범위를 환경 명세·결과에 남긴다.

| 격리 시험 실행부 | 자원을 준비하고 두 환경을 시험하며 증거를 수집·정리 | 실행 ID·실제 구성·입력·결과·중단/정리 |

<a id="64-판정과-버전-비교"></a>
## 5.4 판정과 버전 비교

03의 체크칸은 안내서에서 사용하는 빈 점검 양식이다. 실제 평가에서는 읽기 번호와 CHK ID, 대상 환경·정책·증거를 함께 기록하고 결과를 선택한다. 미확인과 해당 없음의 사유도 남긴다.

| 항목 판정 | 필요한 근거 |
| --- | --- |
| 충족 | 필요한 적용 분기와 정상 대조를 실행하고 필수 증거를 확보했으며, 채택한 기준을 만족함 |
| 미충족 | 해당 보호 요구의 위반을 확인 |
| 미확인 | 시험하지 않았거나 필요한 경로에 도달하지 못했음. 정책·수치가 미정이거나 필수 증거가 부족한 경우도 포함 |
| 해당 없음 | 해당 기능·경로를 사용하지 않는 근거와 그 근거가 유효한 대상 범위를 확인함 |

**현재 평가 단위는 CHK다.** 적용 분기와 정책·환경값을 기준으로 결과를 모은다. Q의 정책·시험·사례 기록은 근거로 사용한다. 서로 다른 기준이 충돌하면 확인·정정 전에는 충족으로 처리하지 않는다.

- 적용 분기와 필수 세부 결과를 각각 판정한다. 확인된 미충족이 하나라도 있으면 해당 CHK는 미충족이다.
- 미충족 없이 필수 미확인이 남으면 CHK는 미확인이다.
- 필수 분기·세부 결과 목록과 실행 증거가 갖춰지고 모두 만족해야 충족이다.
- 보호 요구도 그 요구에 실제 기여하는 공통·세부 범위 결과와 증거로 집계한다. CHK 전체 판정을 보조 요구에 복사하지 않는다. 관련 링크만으로 충족 처리하지 않는다.

발생이 확인된 필수 사건의 기록이 채택한 수집·보존 조건이나 기한을 위반하면 기록 확보 요구는 미충족이다. 기록 확보 여부를 판단할 필수 증거가 부족하면 미확인으로 남긴다. 누락된 기록을 대신할 다른 필수 증거로도 판단할 수 없는 의존 시험은 미확인으로 두고, 이미 확인한 요구 위반은 미충족으로 유지한다.

기준·후보 버전은 각각 판정한 뒤 **유지·개선·회귀·기존 위반·비교 불가**를 검토한다. 모델·의존성·GPU·부하 조건이 달라 비교할 수 없으면 사유를 남긴다. 기준 버전의 동작을 무조건 정상 답으로 삼지 않는다.

충족은 각 점검의 적용 분기·정상 대조·필수 증거·정책 조건을 기준으로 판정한다. 문서·설정 검토 항목은 해당 단계의 검토 증거를, 실행 시험 항목은 해당 집행 위치의 결과를 확인한다.

### 기록 확보와 수집 장애 탐지의 판정 예시

사건별 수집·보존 조건과 기한을 먼저 확인한다. 일시 중단 뒤 기록이 정한 기한 안에 복구되고 필수 필드를 대조할 수 있으면 기록 확보의 충족 근거가 된다.

| 확인한 상황 | 기록 확보 — CHK-OBS-001 | 장애 탐지 — CHK-OBS-011 | 해당 기록이 필요한 시험 |
| --- | --- | --- | --- |
| 필수 기록이 수집 기한을 넘겨 누락됐고 장애를 정한 범위·기한에 정확히 탐지·처리함 | 미충족 | 해당 장애 시험 분기의 충족 근거 | 다른 필수 증거로 판단할 수 없으면 미확인 |
| 필수 기록 누락과 필수 탐지의 기한 초과를 각각 확인함 | 미충족 | 미충족 | 다른 필수 증거로 판단할 수 없으면 미확인 |

각 CHK의 전체 판정은 필요한 다른 적용 분기까지 모아 정한다. 탐지 성공과 기록 확보 실패는 각각 남긴다. 이미 확인한 요구 위반은 미충족으로 유지한다.

필수 검사 원결과가 미확인이어도 보류가 요구되는 경로에서 운영 사용을 정확히 막았다면 SUP-014의 해당 보류 분기는 충족 근거가 된다. CHK 전체 판정에는 정상 성공 시 허용되는지 등 필요한 적용 분기를 함께 확인한다.

<a id="평가-방법의-적용-사례"></a>
### 평가 방법의 적용 사례

보호 조건을 확인하는 시험은 실제 처리 경로를 거치고, 위반을 드러낼 입력과 정상 대조를 갖춰야 한다. 팀의 「vLLM 보안 수정에서 보안 함수 호출 누락에 대한 회귀 시험의 검출 한계 연구」는 이 평가 방법을 검토할 사례를 제공한다.

| 구분 | 시험 범위와 확인 내용 |
| --- | --- |
| 시험 대상 | 2026년 상반기 vLLM 보안 수정 17건에서 만든 변이 78개 중 보안 위반이 확인된 22개를 비교했다. |
| 관찰 결과 | 선정 CPU 시험은 호출형 18개 중 14개를 검출하지 못했다. 미검출 14개 중 13개는 계측한 시험 프로세스에서 호출 실행이 관찰되지 않았고, 1개는 차이를 드러낼 입력이 부족했다. |
| 보완 시험 | 미검출을 확인한 뒤 작성한 사용 지점 시험은 수정본에서 통과하고 해당 변이 14개를 검출했다. |

**평가 방법에 반영할 내용:** 보안 함수의 동작 확인과 함께 실제 처리 코드의 호출·설정 전달을 확인한다. 위반을 구별할 입력으로 최종 보안 결과를 검사하고, 허용한 정상 동작도 유지되는지 대조한다. 실행 관찰은 해당 경로를 거쳤는지 판단하는 보조 증거로 사용한다.

**현재 확인 범위와 후속 검증:** 위 결과는 선정한 수정·변이와 시험·계측 범위의 결과다. 사용 지점 시험은 미검출 확인 뒤 작성됐으며, 별도 서버·자식 프로세스는 원 CPU 계측 범위 밖이었다. 현재 CHK에 활용할 때는 논문의 사례·환경·시험을 해당 점검과 분기에 대응시켜 다시 실행하고, 보안·정상 동작의 증거와 판정을 기록한다.

**관련 점검:** [오류 응답 정보 제한](04_환경별_적용과_체크리스트.md#CHK-REQ-013), [외부 송신 제한](04_환경별_적용과_체크리스트.md#CHK-PLT-007), [추가 코드 실행 허용](04_환경별_적용과_체크리스트.md#CHK-SUP-009), [실행 방식별 외부 모듈 제한](04_환경별_적용과_체크리스트.md#CHK-SUP-011).

**연구 원문:** [팀 보관 PDF](assets/ACK2026_paper.pdf), 본문 2–3쪽의 방법·결과·한계.

## 5.5 증거와 보고서

### 기존 gua 실행 자료를 적용한 REQ013 평가 기록

금지된 입력 사본의 추가 반환과 합성 system 표식 반환을 기존 CHK-REQ-013에 대응했다. 합성 표식의 반환과 실제 운영 비밀의 유출은 확인 범위를 구분해 기록했다. 정상 기능 결과는 시험 전후 네 표본에 한한다.

`CHK-REQ-013`에 gua CPU chat 한 실행(`case1-budget127`)의 공개 선별 증거를 적용했다. **보안 미충족·선정 정상 기능 충족·성능 미확인**으로 기록했다. 금지 추가 반환 옵션의 효과와 engine·gateway의 합성 system 표식 반환을 근거로 삼았다. 정상 기능은 시험 전후 네 표본에 한한다.

정상 chat 필드의 허용 목록 적합성은 금지 입력 사본 반환과 구분해 검토한다. 원 보고의 `official=false`·정책 `DRAFT`를 유지하며, 원본 증거의 독립 검증·실제 정책 승인·보완 이행·새 재시험은 미확인이다. 프레임워크 담당은 적용 범위·정책 적합성·재확인 충분성을 검토하고 개발·시험 담당은 실제 통제 보완·재시험 증거를 제공한다.

| 추가 필드 | 기록 규칙 |
| --- | --- |
| `record_id` | 결과 기록 자체의 고유 식별자. 기록 생성 도구가 발급하며 빈 양식에서는 `null`로 둔다. |
| `assessment_id` | 기존 CHK 고정 ID. 한 기록에 한 CHK를 지정한다. |
| `protection_requirement_id` | 해당 판본 CHK의 `purpose_ref.id`. 함께 확인하는 요구는 기존 연결로 추적하고 각 요구의 세부 결과를 보존한다. |
| `checklist_revision` | 기준으로 사용한 `data/checklist.json`의 판본. 예시는 원본 bytes의 SHA-256을 기록하며 해당 원본을 함께 보존한다. 새 판본으로 시험할 때 실제 기준 판본으로 갱신한다. |
| `test_branch_ref` | 해당 CHK의 `test_branch_conditions`에서 `name`, `scenario_ids`, `apply_when`을 원문 그대로 복사한다. CHK·체크리스트 판본과 세 값을 함께 대조해 정확히 한 분기를 참조한다. CHK ID와 기존 112개 분기의 이름·조건은 유지한다. |
| `test_case_id` | 해당 분기를 실제 경로·대상·조건으로 구체화한 시험 케이스의 식별자. 시험 담당자가 케이스 명세에 부여하고 개정된 내용은 `procedure_version`으로 구분한다. 준비 전에는 `null`이다. |
| `test_case_parameters` | 이번 케이스의 경로·작업·신원 역할·rank·상태 등 판정 범위를 구분하는 조건. 필요한 값만 기록하며 비밀값은 참조로 남긴다. |

`subtest_id`는 기존 Q/SC의 공유 시험 초점이고 `test_case_id`·`execution_id`는 각각 구체적인 케이스와 실제 실행이다. 같은 실행·증거가 여러 CHK에 쓰이면 `execution_id`와 증거 참조를 공유하되 결과 기록은 CHK별로 나눈다. 같은 분기에서도 실제 경로·조건에 따라 케이스를 나누고, 현재/후보 환경 및 재시험 실행의 결과는 각각 남긴다. 기록 고유 ID나 시험 케이스 ID를 새 CHK·분기 ID로 사용하지 않는다.


`test_branch_ref.apply_when`은 기준 판본의 분기 적용 조건이고, `test_case_parameters`는 실제 시험 조건이다. 적용 조건을 복사하는 작업은 기준 선택으로 자동 채울 수 있다. 참조가 0개 또는 여러 분기에 대응하면 연결을 확정하지 않고 검토 대상으로 남긴다. 과거 기록은 원본과 판정을 보존하며, 당시 판본·실제 시험 조건·증거로 분기를 유일하게 확인한 경우에만 정정·연결 기록을 추가한다. 모호한 연결을 CHK 충족 집계에 자동 반영하지 않는다.

양식은 미실행·미확인 상태를 유지한다. 실행 결과를 등록할 때 CHK·분기·Q/SC·주 보호 요구가 기준 판본과 일치하는지 확인하며, 근거를 확보하지 못한 값은 미정으로 남긴다. `subtest_inventory_complete`와 CHK 집계는 [상세 원문 02의 선정 목록 완결성](../02_환경별_적용기준.md#선정-목록의-완결성-검토) 및 이 문서의 기존 집계 규칙을 따른다.

기존 Q 중심 기록은 원본·판정·식별자를 보존한다. Q/SC만으로 CHK를 자동 확정하지 않고, 실제 시험 범위와 증거를 검토한 연결만 추가한다. 미해결 연결은 검토 대상으로 남기고 CHK 충족 집계에 자동 반영하지 않는다. `facts`에 남긴 과거 설명도 보존한다. 새 필드의 저장·가져오기·검증·기존 기록 연결은 개발팀 구현 과제다.

| Gateway·엔진 진입 | 일반·관리 API의 인증·인가·모델·지원 입력 제한과 직통 접근 | 허용·거부 결과와 엔진 전달 여부. 내부 통신은 해당 통신 경로의 접근 통제로 확인 |
| 서빙 호스트·컨테이너 송신 | 목적지 주소·포트·프로토콜·작업 단계 | 실제 정책 적용, 허용·차단, 실패. 인터넷·사내 목적지를 모두 확인 |
| 배포 설정·프로세스 | 이미지·모델 식별·유효 옵션·권한 참조 | 승인 구성과의 차이·변경 시각·확인 범위 |
| 엔진·서버·GPU | 지원되는 오류·서비스·자원 상태 | 수집한 지표와 한계. GPU 집계 지표와 요청별 자원 회수의 계측 결과를 각각 기록 |
| 시스템 센서 | 계획에서 선정한 프로세스·파일·연결 행위 | 행위를 수행한 워크로드·프로세스, 시각·결과. 어느 요청의 행위인지 확인할 때는 프로세스·작업 식별정보도 확인 |
| 정책 적용부·수집부 | 정책 검증·대상·적용 실패·중단·오래된 관측 | 마지막 확인 시각·수집 손실·현재 확인 불가 상태 |

외부 송신 제한을 우선 구현하고 API 통제·시스템 관측은 지원할 대상·수단·증거를 정해 구현한다. 이벤트를 관측한 뒤 대응한 결과와 실행 전에 실제 거부한 결과를 구분해 표시한다. 지원하는 통제 수단별로 차단·관측할 행위와 적용 범위를 정한다.

### 장애가 났을 때

- 중앙 연결이 끊겨도 **유효한 마지막 승인 정책**을 유지하는 방향으로 설계한다. 신규 정책·승인 처리와 정책 만료 후 동작은 별도 기준이 필요하다.
- 수집이 끊기거나 상태가 만료되면 수집 중단·관측 만료 상태로 표시한다.
- 새 정책 적용 실패 시 대상·원인·이전 유효 정책의 유지 여부를 남긴다.
- 기존 서비스를 계속 제공할지 제한할지는 사건 중요도·업무 요구에 따라 미리 정한다. 기준이 미정이면 정책 결정이 필요한 항목으로 남긴다.
- 정책 복원과 엔진 이미지·모델·설정 복구는 대상과 확인 항목을 나눠 준비한다.

<a id="67-보완재평가"></a>
## 5.7 보완·재평가

운영 중 이미지·모델·설정·권한·활성 기능·정책이 바뀌거나 위반·관측 장애가 발생하면 관련 CHK와 필요한 시험을 다시 선택한다. 재현시험은 격리 환경에서 수행한다.

| 평가·운영 구분 | 사용할 기준 | 결과의 활용 |
| --- | --- | --- |
| 업데이트 검증 | CHK·시험 분기·시나리오, 환경 조건, 정책·증거·판정, 변경·재시험 조건 | 현재·후보 환경의 결과를 비교하고 미충족·미확인과 보완 사항을 보고 |
| 런타임 통제·관측 | 허용한 접근·통신, 필요한 사건·상태·기한, 운영 장애와 재평가 조건 | 실제 정책 적용·관측 상태와 위반을 확인하고 알림·보완·관련 항목을 다시 평가 |
| 기준·결과 관리 | 공통 보호 요구·정책·CHK의 관계와 미확인 목록 | 기준 충돌을 조정하고 평가 결과와 운영 조건을 함께 검토 |

### 시험을 준비하는 순서

| 순서 | 먼저 준비할 것 | 필요한 이유 |
| --- | --- | --- |
| 1 | 진입·통신과 기본 증거 | 허용 경로·실제 handler·수집 상태를 확인해야 다음 시험 결과를 해석할 수 있다. |
| 2 | 승인 공급물·정상 기동 | 시험하는 모델·코드와 필수 worker 준비를 확인한다. |
| 3 | 요청·결과·cache | 기본 일반·스트리밍·공유 상태에서 입력·귀속·공유 제한을 대조한다. |
| 4 | 자원·종결·장애·복원 | 정상 경로와 수집을 준비한 뒤 경계 부하·취소·실패를 제한적으로 시험한다. |

선택 기능은 실제 도입할 때 관련 점검을 함께 추가한다. 이 순서는 준비 안내이며, 환경의 노출·영향·준비 상황에 따라 조정한다. 상세 명세는 [원문 05의 공동 시험 준비](../05_평가와_증거관리.md#먼저-준비할-공동-시험-묶음)를 따른다.

정상 동작·보호 요구 위반·증거 누락의 사례를 각각 넣어 판정 결과가 맞는지 확인한다. 같은 시험 자료·판정 기준으로 사람이 수행한 결과와 자동화 결과를 비교해 선택에서 빠진 항목, 잘못된 판정, 재현 여부와 소요 시간을 확인한다. 절감 효과·지원 범위는 실제 측정 후 보고한다.

### 위반 발견 후 조치와 재개

환경별 보완 순서는 노출 경로, 필요한 공격 권한, 영향받는 자산·서비스, 실제 통제와 남은 위험을 보고 정한다. 위협 후보의 적용 여부와 미확인을 함께 적고 검토자가 우선순위와 이유를 기록한다. 기업이 쓰는 위험평가 방식이 있으면 그 기준을 따른다.

보안 위반을 발견하면 영향 모델·요청·계정을 확인하고 기업의 사고 대응 담당에게 보고한다. 사건의 영향과 정한 권한에 따라 필요한 요청·통신·자격을 제한하고 원본 증거를 보존한다. 보완 후 관련 항목을 다시 시험하며 재개 승인자가 서비스 재개를 결정한다. 보고 담당·채널·기한, 초기 제한 권한, 보존 대상과 재개 승인자는 기업이 정한다. 실제 통제 연동과 대응 시험은 남아 있다.

### 생명주기별 평가 기록

[시점별 담당·점검·증거·결정 조건](02_보안_프레임워크.md#생명주기별-보안-활동)을 기준으로 평가를 준비한다.

생명주기별 기록은 시점과 발생 사건을 먼저 적고, 해당 환경에서 선택한 CHK·시험 분기와 근거를 남긴다. 도입과 설계에서는 계획과 정책 결정 근거를 기록하고, 실행한 시험에는 실행 ID와 결과를 남긴다.

| 기록 | 작성할 내용 |
| --- | --- |
| 대상과 계기 | 일곱 시점 중 해당 시점, 발생 사건, 엔진·모델·설정·정책 버전 |
| 책임 | 실제 수행자·검토자, 승인이 필요한 경우 승인자와 권한 |
| 선정 | 적용 CHK·시험 분기, 비적용 근거·미정 조건, 변경·복구의 영향 범위 |
| 증거와 판정 | 출처·수집 시각·실행 ID·수집 상태, CHK별 결과·한계 |
| 처리 결정 | 적용·보류·예외·재개 등의 결정과 이유, 승인 시각·조건 |
| 후속 확인 | 보완 담당자·기한, 재시험 대상, 예외 만료·재검토 계기 |

기존 증거를 쓰는 경우 대상·구성·정책·시험 절차와 수집 상태가 여전히 유효한지 확인하고 재사용 이유를 적는다. 수치 기준이나 증거가 부족한 점검은 미정·미확인 상태를 유지한다. 담당자의 예외·사용 승인은 CHK의 충족 여부와 함께 각각 남긴다.

## 5.8 현재 상태와 완료 기준

현행 EVD는 한 CHK·side의 증거를 담는다. 여러 세부 결과를 독립 EVD revision으로 덮어쓰는 방식은 마지막 revision만 소비하는 현재 경로에서 정보가 사라질 수 있다. 후속 확장은 한 EVD 안의 범위별 관측/사례와 그 RES의 범위별 판정을 유지하는 방향으로 정한다. 큰 증거는 기존 artifacts/CAS를 참조한다.

## 판본과 정확한 참조

- 내용 근거는 저장소·정확 commit 또는 미게시 로컬 commit, checklist 파일 bytes SHA256, CHK ID로 식별한다. 형식 schema_version은 파서 구조, date/record_date는 원 작성/기록일, 개별 revision은 해당 객체 내용 판본이다. 서로 대신하지 않는다.
- commit·파일 bytes hash·JSON canonical hash는 이름과 범위를 명시한다. 과거 날짜/해시를 최신값으로 일괄 바꾸지 않는다. 내용 판본을 알 수 없으면 null과 미확인 사유를 남긴다.
- 기존 내부 check_id와 framework CHK ID는 id_map의 고정 대응을 사용한다. 이름·정렬·문장 수정으로 재번호하지 않는다.
- 기존 full branch ref는 `{assessment_id, checklist_ref, name, scenario_ids, apply_when}`다. checklist_ref에는 내용 판본과 SHA를 포함한다. `apply_when` 원문은 공백·구두점을 포함해 보존한다. 배열 index는 해당 판본 안의 조회 보조이고 영구 ID를 대신하지 않는다.
- 분기 이름과 SC만으로 병합하지 않는다. 같은 이름/SC를 쓰는 SUP-008·REQ-018·REQ-020·PLT-008의 서로 다른 apply_when을 별개 참조로 저장한다. 새 내부 범위 ID는 선택 설계이며 기존 full ref와 명시적 대응 없이 대체하지 않는다.
- 문구 수정은 구/신 full ref의 관계를 기록한다. 원문이 바뀌었는데 새 ref의 apply_when만 옛 결과에 삽입하지 않는다.

## 공통 확인과 분기와 필수 결과

공통 확인은 CHK가 기본적으로 요구하는 보호·정상 대조다.112개 분기는 조건별 시험 초점이며 모든 실행 목록을 열거한 것이 아니다. 필수 세부 결과9개는 각각 판정할 보호 범위다. 하나의 실행이 여러 분기·세부 결과에 증거를 제공할 수 있고, 하나의 세부 결과가 여러 실행·문서 검토를 필요로 할 수 있다. 이 관계는 일대일이 아니다.

선정 snapshot에는 기대하는 공통 확인·분기·필수 결과, 각각의 적용 근거와 지원·선정 상태를 남긴다. 실행을 위해 자연어 apply_when을 임의 조건식으로 바꾸지 않는다. 검토된 fact/정책 매핑 또는 사람의 적용 검토를 별도로 기록한다. API 보호처럼 기존 SC 분기만으로 충분히 표현되지 않는 기본 결과를 누락하지 않는다.

## 적용부터 판정까지의 필드 의미

|---|---|---|

선정 목록 완결성은 **특정 팩/정책/환경/시점의 기대 범위를 빠짐없이 적용 판단했는지**다. 현재 `inventory_complete`의 의미와 REVIEWED 팩 조건을 유지한다. 새 수행 범위 완결성은 **선정된 적용 범위의 필수 절차·정상 대조·관측·필수 결과가 충분한지**다. `coverage_complete`는 제안 필드이며 inventory_complete를 덮어쓰지 않는다. 기존 case 안의 subtest_inventory_complete는 구판 입력값으로 보존하고 새 PLAN snapshot과 상충하면 충돌로 표시한다. case boolean 하나를 전체 목록 권위로 삼지 않는다.

CHK 집계는 적용 범위의 FAIL 우선, 필요한 공통/필수 결과가 UNKNOWN이면 전체 UNKNOWN, 모든 적용 필수 범위가 PASS이고 해당 완결성 관문을 만족할 때 PASS다. CHK 전체의 비적용은 대상에 연결된 근거가 필요하다. 조건부 결과의 NOT_APPLICABLE은 근거를 보존하며 나머지 적용 결과를 가리지 않는다. 세 축의 정상 기능·성능 미확인은 보안 근거와 각각 기록한다.

## 보호 요구별 판정과 증거 기여

주 요구는 purpose_ref, 보조 요구는 security_requirement_contributions에 있는 관계만 사용한다. 각 요구 기여는 `{requirement_id, source_unit_refs, evidence_refs, verdict, reasons, missing_evidence}`로 제안한다. CHK 전체 판정을 보조 요구에 그대로 복사하지 않는다. 해당 요구가 필요한 단위와 증거의 범위를 검토해 기여한다.

- OBS-006에서 조회·반출 권한 PASS와 암호화 UNKNOWN을 함께 보존한다. 저장 자료 보호(requirement-5-4)는 UNKNOWN, 작업·대상 인가(requirement-1-2)의 확인한 조회권한 기여는 PASS로 남길 수 있다. 후자는 해당 요구 전체의 다른 CHK까지 통과했다는 뜻이 아니다.
- PLT-008에서 내부 통신 PASS와 API 증거 부족 UNKNOWN을 보존한다. 통신 상대·전송 보호(requirement-5-5)는 UNKNOWN이다. 내부 peer 근거가 인증/인가 요구에 기여할 범위만 별도로 가리키며 API 인증/인가 전체에 확대하지 않는다.
- LIF-013의 release 권한 PASS, 후속 취득의 비승인 공급 FAIL, 참조 수명 UNKNOWN은 각각 보존하고 CHK는 FAIL이다. 실제 사용 무결성 등 해당 보조 요구의 위반도 근거별로 기록한다.

## 채운 자료형과 null과 빈 값

전체 필드 사전은 `결과기록_필드사전_초안.json`에 있다. 현행 result_template의 모든 최상위 필드를 기존 객체와 대응하고 추가 계약을 구분한다.

- `evidence`는 설명 문자열 나열이 아니라 case별 descriptor 배열을 제안한다. 각 항목은 대상/관측, 기존 EVD·artifact 또는 문서 bytes Ref, 출처·수집/검토 시각·자료 등급·필수 여부·채택 근거를 담는다. 본문/Secret을 공통 계약에 추가하지 않는다.
- `/`·`·`로 이어 쓴 required_observations 문구는 설명이다. OR 또는 전역 AND로 자동 파싱하지 않는다. 각 판정에 필요한 실제 증거와 대체 증거 동등성의 승인 근거를 따로 정한다. 근거 부족을 이름이 비슷한 다른 관측으로 채우지 않는다.
- `normal_control_result`는 기존 `{attempted:boolean,succeeded:boolean|null,detail:string}`와 관련 증거 Ref를 사용한다. null은 미제공/미확인, false는 실제 실패, `attempted:false`에서 succeeded=true는 허용하지 않는다.
- `approval`은 기존 RPT의 ACCEPT/REJECT 자기신고 관리 결정과 가능한 근거 Ref로 대응한다. `null`은 결정 미제공, 빈 객체는 채운 승인으로 허용하지 않는다. CHK 판정과 승인/예외·보류를 분리한다. 미정 정책의 보류 사유를 PASS로 바꾸지 않는다.
- `environment_evidence_source`, adapter/procedure/fixture 참조는 이름·판본·내용 hash와 EVD/입력/문서의 명시 Ref로 대응한다. 외부 링크 문자열만으로 자료 진위나 지금 유효성을 확인했다고 하지 않는다.
- 빈 배열은 기록된 항목0개, null은 미제공/미확인이다. 비적용은 별도 applicability/verdict와 근거로 표현한다. `policy_values:{}`는 필요한 정책이 없는 범위에만 완결될 수 있고 필수값 누락을 대체하지 않는다.

## 수동 문서와 설정 검토

수행 방식은 ENGINE_TEST / CONFIG_REVIEW / DOCUMENT_REVIEW를 제안한다. 엔진 수행과 문서 검토의 완료 의미를 구분한다. 수동 자료의 원 출처는 DECLARED 상한이고 합성 예시는 EXAMPLE이다. 기존 `EVD.execution.operator {by,at}`와 manual-entry executor·절차 판본/증거 Ref를 재사용한다.

문서 검토가 완료되면 그 절차의 execution_status=COMPLETED와 실제 검토 시각·검토자·procedure Ref를 남길 수 있다. EVD ID와 operator/procedure 조합이 수행 신원이며 엔진 request ID를 만들어 넣지 않는다. 실제 엔진의 정상 대조/위반 시도가 필수인 CHK에서 문서 검토만 끝났다면 normal_control.attempted=false, 실제 challenge 미시도, 판정 UNKNOWN을 유지한다. 수동 판정기의 기존 허용 관측/상한을 확대하지 않는다. 새 typed 수행 방식 필드는 후속 객체 판본 확장 전까지 제안이다.

## Q와 공유 시험 초점과 SC의 허용 관계

- canonical focus는 `items[].subtests[].id`의 고유 ID이며 primary_question과 scenario_id를 원문에서 확인한다. 동일 focus가 여러 Q 아래에 나타나는 것은 같은 실행의 별도 보호 요구 연결이다.
- `subtest_id`가 있을 때 question_id는 canonical primary Q, shared_question_ids는 같은 focus를 참조하는 다른 Q 목록이다. 임의 Q/SC 문자열을 이어 새 focus를 만들지 않는다. canonical 목록·CHK.subtest_ids·Q membership의 관계를 검증한다.
- case의 scenario_ids는 실제 확인한 focus/CHK의 허용 SC이고, branch_ref.scenario_ids는 원 분기의 전체 정의를 정확히 보존한다. 두 배열을 무조건 동일하게 만들지 않는다. 단일 focus case의 실제 SC는 canonical focus의 SC와 일치한다.
- 공통 확인이나 필수 결과가 기존 focus 하나로 표현되지 않으면 subtest_id/question_id=null, shared_question_ids=[]와 이유를 남긴다. 예를 들어 PLT-008의 API 보호 기본 결과에 내부 IPC SC를 억지로 붙이지 않는다. 연결 가능한 실제 branch/focus만 선택적으로 참조한다.

## 원 실행과 새 재사용 판단

원 EVD/RES Ref, 원 PLAN·환경·정책·팩/프로파일·실행/수집 시각은 바꾸지 않는다. 새 판단은 새 PLAN/대상 환경·정책·범위, 재사용 검토자/시각/유효성 근거, 채택/보류와 이유를 따로 기록한다. 원 자료의 data_origin은 재사용 때문에 승격하지 않는다. 이월은 새 실측으로 세지 않는다.

CHK·관측/절차/판정기·정책·모델/실행 조건·범위가 동등한 부분만 재사용한다. 새 필수 결과가 생기면 그 부분은 UNKNOWN/재시험이다. 원환경/정확Ref가 미해소면 재사용을 보류한다. 허용되는 재사용과 비교 가능성은 다른 판단이며 `FAIL→UNKNOWN`은 FIXED가 아닌 UNKNOWN이라는 기존 compare 규칙을 유지한다.

## 과거 형식의 읽기와 반출과 재판정

`record_kind:framework_assessment_review`는 과거 CPU 실행 자료의 검토 dossier이며 현행 result_template case·guard RPT와 별도로 라우팅한다. 원 JSON bytes/해시·원 case/RES Ref·당시 환경/팩을 보존한다. dossier의 execution_id=null을 새 엔진 실행으로 채우지 않는다. 명시된 실행/관측/주장만 새 구조의 대응 후보로 연결하고 독립 원 객체를 확인하지 못한 상태도 보존한다.

현행 guard importer는 이 dossier를 자동 RPT/EVD로 받아들이는 기능이 없다. 읽기·복원 성공, 새 기준에 따른 재판정, 실제 운영 적용 승인은 각각의 수행·결정 기록으로 남긴다. 원판정의 보안 충족이 새 배포의 승인 권한을 대신하지 않는다. 후속 reader를 구현하기 전에는 검토용 자료로 읽고 변환 완료로 표시하지 않는다. 과거 PACK18 실측은 현재 PACK29의 실측이 아니다.

구판 읽기·복원은 원문 우선으로 유지한다. 새 필드를 기본값으로 채워 과거 객체를 다시 봉인하지 않는다. 새 범위 해석은 새 PLAN/EVD 참조/RES/RPT 이력으로 남긴다. 현재 pack snapshot은 정의를 보존하므로 당시 재판정 재현에는 당시 judge/parser/canonicalizer 코드·wheel/lock·Python 또는 검증된 구판 호환 회귀가 더 필요하다. 확보하지 못하면 원판정 읽기·복원과 현행 새 평가를 구분한다.

반출은 기존 bundle의 DB·CAS·팩/범위 정의·참조 폐쇄를 검증한다. 새 품질/재사용 판단 artifact도 참조에 포함한다. 단위 결과·full branch 원문·관측·관리 결정을 저장/내보내기/복원해 동일한 의미를 유지해야 한다. 예시 validator의 JSON roundtrip은 이 설계 관계의 검사이며 제품 store 전체 구현 완료를 뜻하지 않는다.

## 구조 필드와 합성 표시문

편집 원천은 base_method_and_evidence의 일반 방법/엔진별 고유 메모와 normal_control·challenge_steps·required_observations·fail_criteria·unknown_criteria·remaining_setup 등 구조 필드로 정한다. method_and_evidence는 그 순서/강조/줄바꿈을 적용한 표시문으로 생성 또는 동등성을 검사한다. 앞부분32개 문장 차이를 모두 오류로 단정하지 않는다. HTML escape·고유 F 조건·인용·엔진 활성 조건을 보존한다.

현재 표현에서 분리할 수 없는 고유 설명은 원문 메모와 근거에 남기고 사람이 검토한 대응을 기록한다. 한쪽만 변경한 반례를 검출하는 도구를 후속 생성기의 인수 기준으로 삼는다. 이 명세는 자동 prose parser를 새로 만드는 요구가 아니다.

## 합성 예시와 후속 구현의 인수 조건

`examples/결과기록_합성예시_초안.json`은 네 CHK의9필수 결과, 수동 검토, 원 실행/새 판단, 같은 이름의 full branch 참조와 과거 dossier 대응을 채운 EXAMPLE 자료다. 실제 지원 판본의 사용법으로 게시하기 전에 기존 객체 확장/reader/validator/생성팩·정책/계약/API/OpenAPI·TS/화면 변경을 함께 검토한다.

인수 조건은 전체 PASS 관문·독립 FAIL·요구별 기여, 잘못된 Q/SC/Ref/모호한 분기·만료/상충 inventory, 구판 dossier 라우팅·원본 해시, 재사용 원환경 보존·비교·반출복원이다. 명세·합성 사례 검증은 자료 관계와 반례를 확인한다. 개발팀 구현의 입력·출력·기존 모듈 대응·완료 조건은 [개발팀 인계 명세](../개발전달/개발팀_인계명세.md)를 따른다. 제품 저장·반출복원·실제 엔진 시험의 완료 근거는 개발팀이 별도로 제공한다.
