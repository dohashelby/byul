<a id="선택-진입경로-적용범위"></a>
## 선택 frontend·protocol·listener의 적용 범위

엔진 이름·버전과 함께 **실제 frontend, protocol, bind 주소/port, listener, 서비스·작업 목록**을 확인한다. 기동 명령·해석한 설정·설치 패키지/추가 의존성·Gateway 경유/직접 도달 경로를 근거로 남기고, 지원하는 시험 범위를 표시한다. HTTP·gRPC 또는 여러 listener가 함께 있으면 각 범위의 적용·지원·실행·판정을 구분한다.

고정 vLLM v0.31.0의 `serve`는 `args.grpc`이면 별도 gRPC launcher를 선택한다. 그 뒤 Rust frontend·단일/다중 API server·headless 등의 분기가 있다. gRPC launcher에는 외부 `VllmEngine` 서비스·표준 health·reflection 등록과 `add_insecure_port` 선언이 있다. [고정 소스·분기·해시와 인계표](../엔진별_적용검토/vLLM_v0.31.0_진입경로.md)에 함수·줄·조건을 기록했다. 실제 설치의 추가 패키지 판본·활성 RPC method·내부 인증·노출·전송 보호는 미확인이다.

| 기존 CHK | 선정 범위와 정상 대조 | 남길 증거 |
| --- | --- | --- |
| CHK-REQ-001 | 각 frontend/protocol의 허용 추론 호출과 자격 누락·오류 비교 | 실제 서비스/method·listener·신원·집행점·handler 도달 |
| CHK-REQ-003 | 실제 관리 작업의 허용 역할 정상 처리와 비허용 역할 거부 | 역할–작업 허용표·다른 protocol의 대응 작업·실제 상태 변경 |
| CHK-PLT-008 | API 각 구간과 내부 IPC/TP 구간의 허용 peer·정상 호출/작업 | 구간별 상대 인증·암호화·OS 통제·거부 증거와 두 필수 결과 |

HTTP 결과는 시험한 HTTP 범위에 귀속한다. 다른 frontend/protocol의 지원·증거가 부족하면 해당 범위는 미확인으로 남긴다. 비사용은 실제 기동·listener 조사 근거와 연결한다. 개발·시험 담당은 선정한 범위의 inventory·계측·정상/실패 증거를 준비하며, 이번 설명 보완으로 모든 엔진 실행기의 구현을 필수로 추가하지 않는다.

## SGLang v0.5.22 적용성 검토 — 2026-10-24

공식 release의 commit `baa9befa381511cd4d56f83980951e5a45fffc6d`를 고정해 77개 CHK와 일곱 구성요소를 대조했다. [항목별 적용표·보완 후보](../엔진별_적용검토/SGLang_v0.5.22.md)와 [JSON](../엔진별_적용검토/SGLang_v0.5.22.json)에 원 기준 참조·소스·남은 실제 증거를 기록했다. [현행 HTTP 정적 후보 v2](../엔진별_적용검토/SGLang_v0.5.22_HTTP_정적후보_v2.json)와 [조건·계수·재생성 안내](../엔진별_적용검토/SGLang_v0.5.22_HTTP_목록안내.md)를 함께 읽는다. [기존 80행 목록](../엔진별_적용검토/SGLang_v0.5.22_HTTP_route목록.json)은 당시 상위 수준 함수만 추출한 제한 목록으로 보존했다.

77개 적용표의 기준은 당시 checklist SHA256 `7f857208…`이며, 현행 `cf4903ef…`와의 [기준 차이·적용 안내](../엔진별_적용검토/SGLang_v0.5.22.md#sglang-criteria-basis-20261027)를 따로 기록했다. 77개 ID는 유지되고 CHK 기록 39개에 필드 변경이 있다. 기존 profile의 5필드 기준 hash는 7개에서 달라졌고, 분기 조건 변경은 LIF-004·LIF-012다. 당시 적용표는 보존하며 선정 환경에서 현행 문구와 필요한 증거를 대조한다.

2026-10-27 정적 목록 보완에서 같은 파일의 조건부 dumper/root 3함수와 포함 router 2모듈의 3함수를 추가 확인했다. v2는 고유 함수 후보 86개·decorator 등록 선언 91개를 기록한다. 두 root 함수의 상호 배타 조건·동적 경로·include 위치를 유지하며 실제 API 수·동시 활성 수는 미확인이다. 실제 등록·역할별 접근은 선정 환경에서 대조한다.

대응 조사 분류는 엔진 경로 35개·외부 집행 28개·선택 기능 10개·동일 기능 매핑 보류 3개·부분 대응 1개다. 실제 설치 환경은 미선정이며 77개 모두 미실행·미확인이다. 후보 구성은 단일 노드 NVIDIA GPU·텍스트 모델·TP·일반/스트리밍·Radix cache이고, 실제 모델·이미지·GPU·TP 크기·정책값은 미정이다.

프레임워크 담당자가 검토할 보완 후보는 **native session의 이어쓰기·종료 권한을 기존 검사에 연결할 분기**와 **지속 KV 사본의 저장 보호·보존 범위**다. 기존 1.2/4.1/1.7/6.4와 4.2/4.3을 우선 재사용하되, 저장 응답 객체 기준과 로그·진단 저장 기준만으로 각각 충분하다고 처리하지 않는다. 요구 개정 여부는 미결이며 이번 검토에서 CHK ID·확정 판정 기준은 변경하지 않았다.

SGLang의 `input_ids`·`cache_salt`·선택 custom callable·Responses 저장·관리 키 등급·weights daemon은 실제 소비 경로에 대응했다. SUP-008의 요청별 코드 판본과 OBS-004/005의 제품 usage reporter는 동일 기능 매핑을 보류했다. LIF-013은 daemon이 존재하지만 조사한 메시지에는 release 요청이 없어 종료·fallback·기존 참조 수명과 release 호출 부분을 나눴다. 부재·미도달은 실제 설치/확장 조사 후 확정한다.

실제 설정·권한·reader·GPU 상태 수명 조사, adapter/계측·시험·측정은 개발·운영·시험 담당 업무다. 프레임워크 담당은 보완 범위·분기·증거 충분성과 판정을 검토하고, 조직 정책 담당은 실제 허용·공유·예산·기한·승인 결정을 확정한다.

## 4.5 기존 판정 기준에 맞는 증거를 준비한다

정책·허용표·정상 대조를 먼저 준비하고, 실제 거부·소비·출력·상태 변화를 연결해 수집한다. 아래 예시는 기존 CHK를 SGLang에 연결할 때 필요한 관측 지점이다.

| 확인할 동작 | 함께 받을 증거 | 관련 CHK |
| --- | --- | --- |

## 4.6 결과와 남은 범위를 기록한다

### 적용 전에 범위를 더 정해야 하는 기능

| 기능 | 현재 기준에서 사용할 부분 | 추가로 정리할 평가 범위 |
| --- | --- | --- |
| native session | 작업·대상 인가, 요청·결과 귀속, 권한 철회, 종결·회수 | session 생성·이어쓰기·종료의 사용자/공유 집단별 허용 행위와 기존 검사 분기의 연결. REQ-006은 현재 저장 Responses/결과 객체를 대상으로 한다. |

### 현재 소스 대응에서 남은 확인

- **SUP-008:** 요청별 코드 판본 선택과 동일한 필드→코드 소비 경로의 대응이 남아 있다. 설치 확장과 활성 API를 조사한다.
- **OBS-004/005:** 제품 사용 통계 reporter의 대응이 남아 있다. 응답 token usage·OTel 추적은 각각의 기능으로 구분해 조사한다.
- **LIF-013:** weights daemon은 있으나 조사한 socket 메시지는 `query_config/fetch_state/ping`이다. 전체 release 호출의 도달성, daemon 종료·재취득/fallback·기존 참조 수명을 분기별로 기록한다.

## 4.9 엔진·버전 비교와 근거 관리

다음은 원문 04의 공통 버전 비교·근거 관리 안내다. 앞 절의 SGLang 적용 내용과 함께 사용한다.

### 사용하는 순서

실제 설치 버전과 기능을 확인한 뒤 아래 비교 절차에 따라 적용 항목을 고른다. 다른 엔진의 검증 상태는 해당 환경의 실행 기록에서 확인한다. 처음 보는 버전의 처리와 자동 수집 계획은 뒤에서 설명한다.

### 버전 비교의 실행 순서

1. 비교 환경 A/B 각각 서버·backend·엔진 commit, 이미지 digest, 설치 의존성, 모델 묶음, GPU/driver, 유효 설정을 고정한다. v0.11.0은 기존 분석 근거이지 반드시 업데이트 시험의 직전 버전일 필요는 없다.
2. 공통 평가 질문은 유지하고, 인증 route·loader·cache key·IPC·관리 작업·진단 경로의 변경을 해당 질문에 연결한다. 이름만 바뀐 경우와 집행 의미가 바뀐 경우를 나눈다.
3. 공식 advisory/patch/test와 코드 변경을 함께 읽는다. 버전 문자열만으로 취약·해결을 자동 확정하지 않는다. 적용 경로 미사용이면 제외 근거와 재검토 조건을 남긴다.
4. A/B 모두 정상 기능을 먼저 확인하고 동일 정책·workload·관측 기준으로 시험한다. 패치 전후의 기대 결과가 다른 시험과 기존 보호 유지 시험은 판정 기준을 각각 쓴다.
5. 결과는 `(평가항목, 엔진·서버·backend 판본, 기능·환경, 정책 버전, 시험 버전)`에 귀속한다. 미실행 엔진·판본은 적용 설계 또는 미확인으로 표시한다.

### 다른 환경에 적용할 때 남는 확인

다른 엔진·버전에서도 CHK ID와 공통 보호 의미를 유지한다. 각 CHK의 환경·분기 조건에 실제 endpoint·loader·runner·기본값·의존성을 대응시키고, 확인한 범위·근거·미확인을 기록한다. 이름이 같은 옵션이나 과거 Q·SC 연결만으로 지원·비사용을 판정하지 않는다. 구현 매핑 미확인과 기능 부재 확인은 별도 상태다. 이 연결 기준을 선택기로 구현하는 방식은 개발팀이 정한다.

- SGLang·TensorRT-LLM·Triton 특정 설치판의 전체 route 인가, 실제 종료/회수, tenant 격리, 모든 선택 backend.
- 인터넷 문서의 최신 기능이 설치할 release에 포함되는지 여부.
- 운영 환경의 네트워크 허용 범위·credential·logger/collector·공급물 승인 정책.
- 모든 기업·엔진·버전에 대한 완전성. 현재는 주요 차이 축과 기능별 연결 방법을 제공하며, 환경 입력에서 새 접점이 나오면 해당 질문의 적용 분기를 보완한다.

### 부록 — 버전별 근거 관리와 자동 수집 계획

모든 엔진·버전을 미리 조사한 DB를 만들지 않는다. 공통 기준과 엔진·판본별 구현 근거를 관리하고, 현재·후보 환경과 공식 변경 자료를 수집해 영향 항목을 선정한다. 아래 기능은 구현 계획이며, 현재 selector는 입력 JSON에 따른 기존 Q 선택만 수행한다. 자동 환경 조사·공지 수집·코드 의미 분석·시험 실행은 구현 완료로 표시하지 않는다.

| 미리 관리할 자료 | 저장할 내용 | 갱신 시점 |
| --- | --- | --- |
| 공통 보호 기준 | 영역·목적·Q/SC·적용 조건·정책 입력·판정 기준 | 보호 요구나 범위가 바뀔 때 |
| 엔진·판본별 구현 근거 | 엔진/서버/backend commit·의존성·활성 기능, 실제 route/loader/runner/executor, 근거 위치·확인자·확인 시각·한계 | 새 구현·기능·수정 경로를 검토한 뒤 |
| 시험 명세와 adapter | 시험 입력 자료·계측·정상 대조·판정식·지원 조건·절차 판본 | 실제 작성·검증한 뒤 |
| 알려진 취약점·패치 | 공식 공지·수정 commit·영향 조건·원문 범위와 확인한 해석·Q/SC 연결 | 출처 확인·정정·패치 변경 시 |
| 실제 평가 기록 | 환경·정책·시험 버전·실행 ID·증거·결과·한계 | 실행 완료/중단/오류 때마다 |

| 실행 시 자동 수집할 후보 | 수집할 정보 | 사람의 확인이 필요한 부분 |
| --- | --- | --- |
| 현재·후보 실물 | 이미지 digest·엔진/backend commit·패키지·GPU/driver·모델 식별·설정 | 수집 접근 범위·부족한 자료·실물 일치 |
| 실제 활성 경로 | route·runner/executor 유효값·로딩 형식·통신·관측 구성 | 수집하지 못한 내부 동작·새 분기 의미 |
| 공식 변경 자료 | 릴리스·advisory·패치·회귀시험·버전 간 diff | 영향 범위·backport·포크 수정·해석 오류 |
| 이번 실행 | 시험·관측·정상 기능·성능·오류·미수집 상태 | 기준값·증거 충분성·예외·위험 수용 |

수집 자료에는 원 URL/로컬 출처·고정 commit 또는 자료 hash·수집 시각·도구 판본·확인 범위를 남긴다. 변경 공지와 코드 diff는 항목 선정의 근거 후보이며 곧바로 안전·취약 판정이 아니다. 보안 공지의 판본 범위가 모호하거나 실제 이미지에 backport가 있으면 사람이 확인한다. 서버 버전만으로 포함된 라이브러리의 수정 여부를 추정하지 않는다. 수집 실패·권한 부족·접근 불가는 기능 없음으로 처리하지 않는다. 비밀값과 사용자 본문은 자동 수집 대상에서 제외하거나 합성/식별 참조로 대체한다.

#### 처음 보는 버전의 처리

1. 현재·후보 환경의 실제 대상과 기능을 식별한다. 버전 이름이 같아도 이미지·패치·의존성·설정이 다르면 별도 환경으로 기록한다.
2. 공통 보호 요구는 유지한다. 구현별 확인 근거와 시험 adapter의 상태는 `검토 필요`로 둔다. 이전 판본의 통과 결과를 승계하지 않는다.
3. 기존에 지원하는 외부 API 시험이라도 준비·입출력·증거 의미가 같은지 사전 확인한다. 적합한 시험만 격리 환경에서 실행하고, 불일치·미지원은 미확인으로 남긴다.
4. 변경 영향 시험과 알려진 패치 회귀 시험에 더해, 해당 환경의 공통 보호 유지·정상 기능·성능 시험을 선정한다. diff에 없는 경로를 자동으로 생략하지 않는다.
5. 새 runner/loader/통신·증거 경로가 나오면 해당 부분의 구현 조사·adapter 보완·검토를 수행한다. 변경 의미를 파악하지 못하면 항목 선정 범위를 잠정으로 표시한다.
6. 결과는 실제 시험한 구성과 판본에 한정해 기록한다. 증거가 부족한 항목은 보고서에 미확인으로 남기며, 적용·보류·보완 후 재시험은 담당자가 판단한다.

이미 아는 버전도 정책·모델·기능·의존성이 바뀌면 재평가한다. 기준 저장소와 실행 결과는 처음에는 기존 JSON·근거 파일로 관리하고, 검색·동시 사용 수요가 생기면 DB로 옮길 수 있다. DB 도입 자체가 구현 근거를 자동으로 채워주지는 않는다.

### 보안 공지와 비교 근거의 확인 상태

- GHSA-3c86-2m5g-59q7과 GHSA-5fj9-pfhr-6j48의 현재 공식 공지에는 각각 CVE-2026-90553, CVE-2026-105759가 있다. 보고서의 “공지에 없는 CVE” 지적만으로 삭제하지 않는다. 후자는 Rust frontend 조건을 Python 기본 경로로 일반화하지 않는다.
- GHSA-7972-pg2x-xr59는 공지 영향 범위에 상한이 없고 수정 판본은 0.18.0으로 제시한다. 영향 범위에 임의의 상한을 채워 자동 판정하지 않는다. 영향·수정 경계 중복이나 중간 판본 공백도 원문과 정규화한 범위를 분리하고 확인 전에는 자동 판정에 사용하지 않는다.
- SGLang은 api-key와 admin-api-key를 별도로 확인한다. 공식 저장소 issue #43706의 ADMIN_OPTIONAL fallback 설명은 v0.5.19/지정 main의 보고이며, 설치판 검증 완료를 뜻하지 않는다. 단일 키의 관리 권한 범위를 확인해야 한다.
- Triton 현행 배포 문서의 metrics·HTTP/GRPC 활성 및 GRPC TLS 기본값은 설치판을 선정할 때 다시 대조한다. 이 문서를 vLLM 0.31.0이나 미선정 Triton 판본의 실행 증거로 사용하지 않는다.

실행 역할의 실제 대응은 [02 역할 대응표](04_환경별_적용과_체크리스트.md#다른-엔진의-실행-역할-대응)를 따른다. 새로운 접점은 기존 보호 요구·CHK로 확인할 수 있는지 먼저 검토하고, 충분히 다루지 못하는 위험은 범위의 공백으로 남겨 요구 개정 필요성을 검토한다. 현재 검토에서는 CHK를 신설하거나 확정 판정 기준을 변경하지 않았다.

#### 공통 증거와 참조 절차를 보완한 항목

77개에서 질문·적용 조건·세 판정·증거·정상 대조·절차를 대조했다. 아래 10개는 판정 문장보다 증거·정상 대조의 참조 기술 의존이 문제여서 공통 표현을 보완하고 기존 구체 절차를 참조 예시로 분리했다. 나머지 67개는 vLLM 이름을 제외해도 기존 동작·증거·판정 관계가 남아 변경하지 않았다. 이 수는 명세 대조 결과이며 실행·범용성 검증 결과와 구분한다.

| CHK | 기존에 모호했던 부분 |

#### Llama 모델과 llama.cpp에 적용하는 방법

[Meta의 Llama](https://github.com/meta-llama/llama-models/blob/main/README.md)는 모델 계열이다. 지원되는 Llama 모델을 현재 엔진에 배포하면 모델·tokenizer·template·유효 입력 범위·파일/코드·의존성과 관련된 기존 CHK를 재평가한다. 모델 이름만으로 실행·공유 구조까지 바뀐다고 가정하지 않는다.

[llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/README.md)는 C/C++ 추론 구현이며 [llama-server 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)는 CPU/GPU 실행, chat API, GGUF 모델과 slot·진단 접점을 설명한다. 다음은 2026-10-24 확인한 master 문서에 따른 적용 검토 예시다. 설치할 commit·빌드·기능·집행 효과는 별도 확인한다.

| 대상 | 연결할 기존 요구·CHK | 확인 범위 |
| --- | --- | --- |
| GGUF 모델과 tokenizer/template 등 실제 공급물 | SUP-003·004·005·006·012·015·016 | 실제 읽는 파일·내장/별도 자료·변환/양자화 산출물·reader를 승인 범위와 대조하고 정책 담당자가 적용 판본을 확정한다. 정상 대조에는 실제 승인된 형식을 사용한다. |
| 추론 API와 slot·관리/관측 접점 | REQ-001·002·003·005·013, OBS-003·006 | 등록·노출·역할·반환 정보와 일반 호출자의 실제 작업을 확인한다. API key 설정만으로 모든 작업 인가를 충족 처리하지 않는다. |
| 요청별 slot·cache 재사용과 입력 처리 | REQ-007·008·009·011·012·015·016·018, LIF-010 | 실제 사용하는 token 입력·template·재사용 단위·공유 범위와 결과·종결을 연결한다. 문서상 slot과 vLLM 내부 상태 배열의 동등성은 별도 확인한다. |
| CPU/GPU·단일/복수 실행 단위 | PLT-001·002·006·008, REQ-014·019·020·021, LIF-007·008·009·011 | 공통 권한·입력·준비·정리는 실제 실행 단위로 확인한다. GPU·CUDA Graph·TP·IPC 분기는 활성/부재 근거로 선정한다. CPU-only에서는 GPU 점검을 비적용으로 둘 수 있으나 CPU native 연산 메모리 안전성은 현재 범위의 공백으로 남는다. |
| slot 상태 저장·복원 기능을 사용하는 경우 | SUP-005·012, REQ-003·015·016, LIF-015·016, OBS-006·012 | 관리 작업 권한과 상태의 주체·출처·무결성·재사용 문맥·읽기/쓰기·사본 수명을 확인한다. slot cache는 저장 응답 객체나 전체 프로세스 snapshot과 구분한다. |

프레임워크 담당자는 기존 요구의 대응·공백·비적용 근거와 최소 증거를 검토한다. 실제 설치·API/reader/state 경로 확인, 실행기·계측·시험은 개발·시험 담당이 맡는다. 조직의 정책 담당자는 독자·공유·예산·예외·사용 결정을 확정한다. llama.cpp나 모든 Llama 모델에 대한 gua 자동 실행 지원은 이 검토로 확인되지 않는다.
