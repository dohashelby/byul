우리가 만들 산출물은 여섯 가지이다. 서빙엔진의 보안 점검 기준을 정리하고, 그 기준으로 업데이트 전후를 시험한 뒤, 운영 중에도 승인한 정책과 구성이 유지되는지 확인한다.

| 산출물 | 사용하는 목적 |
| --- | --- |
| **① 서빙엔진 보안 프레임워크** | 무엇을 보호하고 어떤 위험을 점검해야 하는지 파악한다. |
| **② 체크리스트·가이드라인·시험 기준** | 환경에 맞는 확인 항목을 고르고, 점검·보완·판정 방법을 확인한다. |
| **③ 업데이트 검증 자동화 도구** | 현재·후보 환경에서 시험을 실행하고 결과와 증거를 비교한다. |
| **④ 업데이트 검토 보고서** | 평가 결과와 남은 문제를 보고 업데이트 적용 여부를 결정한다. |
| **⑤ 런타임 통제·관측 기능** | 운영 정책을 적용하고, 위반·구성 변경·관측 장애를 확인한다. |
| **⑥ 재현·운영 자료** | 도구를 설치하고 시험을 재현하며 운영 중 문제에 대응한다. |

# **1. 서빙엔진 보안 프레임워크**

서빙엔진을 도입·운영·변경할 때 무엇을 보호해야 하는지, 어떤 위험이 있는지, 어떤 대책과 점검이 필요한지 정리한다. 전체 구조도와 영역별 설명, 기업 환경에 맞춰 적용하는 절차를 제공한다.

보안 내용은 다섯 영역으로 구성한다.

| 영역 | 주요 내용 |
| --- | --- |
| **모델·코드·실행 공급물** | 모델 파일·토크나이저·추가 코드·패키지·이미지의 출처와 무결성을 확인한다. 승인한 파일·코드·버전이 실제로 사용되는지, 허용하지 않은 코드가 실행될 여지가 있는지 살펴본다. |
| **추론 요청·자료·공유 상태** | 호출자가 사용할 수 있는 모델·작업·결과의 범위를 확인한다. 입력 처리, 결과 반환·조회, KV·캐시·버퍼 공유 과정에서 다른 사용자의 정보나 작업에 영향을 줄 수 있는지 살펴본다. |
| **실행 기반·자격·통신** | 엔진이 사용하는 호스트·컨테이너·장치·파일시스템 권한과 자격을 확인한다. 외부 저장소 접근과 내부 통신에서 허용한 대상에만 접근하는지 살펴본다. |
| **배포·변경 상태와 실행 자원** | 모델·설정 변경이나 작업 취소·중단·복원 시 진행 중인 요청과 자원이 어떻게 처리되는지 확인한다. 변경 적용, 작업 종료, 서비스 재개를 판단할 조건도 포함한다. |
| **관측·진단·감사 자료** | 로그·지표·추적 기록·덤프에 남길 정보와 이용 권한을 확인한다. 민감정보 수집, 조회·재실행, 보존·삭제, 기록의 변조 가능성을 살펴본다. |

각 영역에는 다음 세 관점을 공통으로 적용한다.

- **주체·권한·책임:** 누가 무엇을 입력·변경·조회할 수 있고, 검사와 운영은 누가 맡는가?
- **상태·생명주기:** 취득·로딩·실행·변경·실패·종료 과정에서 무엇이 달라지고, 언제 완료됐다고 판단하는가?
- **구성·배포 조건:** 엔진·버전·활성 기능, 게이트웨이 경유 여부, 공유·분산 구성에 따라 확인할 내용이 어떻게 달라지는가?

보호 기준과 예외를 승인할 담당자, 남은 위험을 검토할 담당자, 재평가가 필요한 변경 조건도 정리한다. 기업은 자신의 허용 모델·역할·통신 대상·성능 기준을 입력하고, 그 조건에 맞는 점검 항목을 적용한다.

**현재 준비된 내용**

통합본에 R별 정상 흐름, 보호 자산과 요구, 권한, 공격표면, 신뢰 경계, 기존 통제와 남은 질문을 정리했다. 팀원이 제출한 검토안 중 타당한 보완을 반영했으며, 다섯 보안 영역과 세 관점을 기준으로 평가 질문을 배치했다.

위협 분석은 **24개 묶음·83개 세부 시나리오**로 정리하고 관련 보호 요구·통제·평가 질문을 연결했다. 기업 환경에 따라 달라지는 **12개 조건**과 엔진·버전별 확인 범위도 정리했다. 환경 정보는 도구가 수집하고 정책·예외는 사람이 결정하는 사용 방식을 계획했으며, 자동 수집 기능은 아직 구현 전이다.

**남은 작업**

실제 코드와 실행 흐름을 독립적으로 검토해 빠진 경로와 잘못된 설명을 보완한다. **R10·R14는 검토 대기**이며, 다른 엔진·버전의 상세 적용도 추가 확인이 필요하다.

참조 정책의 채택 여부를 정하고, 실제 환경에 적용해 필요한 평가항목을 선택할 수 있는지 확인한다. 이후 SGLang 등에서도 공통 보호 요구를 재사용할 수 있는지 검증한다.

# **2. 체크리스트·가이드라인·시험 기준**

평가자가 항목을 읽고 **무엇을 왜 확인해야 하는지, 어디를 어떻게 점검할지, 문제가 있으면 무엇을 고칠지** 알 수 있도록 작성한다.

| 구성 | 제공할 내용 |
| --- | --- |
| **체크리스트** | 확인 질문과 적용 조건을 제시한다. 관련 보호 요구·위협·취약점 사례를 함께 적어 점검 이유를 설명한다. |
| **가이드라인** | 필요한 설정, 접근 제한, 운영 절차를 설명한다. 기존 통제가 보호하는 범위와 부족한 부분을 적고 보완 방법을 제시한다. |
| **시험·확인 절차** | 준비 조건, 입력, 실행 순서, 정상 동작과의 비교 방법, 수집할 기록을 정한다. 자동 시험이 가능한 항목과 설정·문서·담당자 확인이 필요한 항목을 표시한다. |
| **판정 기준** | 요구를 충족했다고 판단할 증거와 예상 결과를 정한다. 위반, 증거 부족, 미실행, 해당 없음의 사유도 기록할 수 있게 한다. |

예를 들어 “승인한 공급물과 실제 로딩 대상이 일치하는가?”에는 승인 대상을 식별하는 방법, 실제 소비 파일을 확인하는 방법, 불일치 시 처리, 필요한 기록까지 포함한다.

한 R에서 여러 평가항목이 나올 수 있다. 같은 보호 요구가 여러 R에서 반복되면 공통 질문으로 묶고, 검사 위치나 소비 경로에 따라 세부 절차를 작성한다. 여러 취약점 사례가 같은 질문을 뒷받침할 수도 있다.

**현재 준비된 내용**

기존 R05 초안을 확장해 **28개 평가 질문**을 작성하고 다섯 보안 영역으로 정리했다. 각 질문에 적용 조건, 관련 위협·근거, 기존 통제와 한계, 설정·운영·보완 방법, 요구 증거와 판정 기준을 채웠다.

**83개 시나리오에 하위 시험 설계**를 연결했다. 공통 보호 질문과 vLLM v0.31.0의 구체적인 구현·시험 설명을 나누고, 공통 참조 구성에서 우선 확인할 항목과 선택 기능에 해당하는 항목을 표시했다.

**남은 작업**

독립 검토 결과에 따라 질문의 중복·누락과 시험 조건을 보완한다. 기업이 정할 허용 대상·공유 범위·승인 역할·자원 한도 등의 정책값을 확정하고, 실제 시험에 필요한 입력 자료·계측·실행 코드를 준비한다.

공통 참조 구성의 우선 항목부터 시험해 증거를 확보하고, 충족·미충족·미확인을 일관되게 판단할 수 있는지 확인한다. **현재 83개는 시험 설계이며, 실행 가능한 자동 시험 83개가 완성된 상태는 아니다.**

# **3. 업데이트 검증 자동화 도구**

현재 환경과 업데이트 후보를 입력하면 관련 체크리스트를 고르고, 등록된 시험을 실행해 결과를 비교한다. 사람이 확인해야 하는 항목은 검토 결과와 근거를 입력할 수 있게 한다.

| 기능 | 실제로 할 일 |
| --- | --- |
| **환경과 변경사항 확인** | 현재·후보 환경의 엔진·의존성 버전, 모델, GPU, 실행 옵션, 활성 기능, 게이트웨이 정책을 기록하고 차이를 보여준다. |
| **평가항목 선정** | 환경과 변경사항을 체크리스트의 적용 조건에 대조한다. 필요한 항목과 선정 이유, 제외 이유, 추가로 확인할 조건을 보여준다. |
| **시험 실행** | 등록된 보안 수정 사례와 접근통제·입력 오류·취소·정상 기능·성능 시험을 두 환경에서 실행한다. 비교 조건을 맞추고 달라진 조건은 기록한다. |
| **증거 수집** | 실행 ID에 대상 환경, 정책, 시험 절차의 버전, 로그·관측값·측정 결과를 연결한다. 시험과 수집 과정의 오류도 남긴다. |
| **결과 비교·판정** | 보안 수정 여부와 기존 기능·보호 조건·성능의 변화를 비교한다. 증거 부족이나 환경 차이로 판단하기 어려운 항목은 사유를 표시한다. |
| **보고서 작성** | 항목별 결과와 근거를 모아 보고서를 만든다. 수동 확인 결과와 담당자의 검토·승인 기록도 함께 관리한다. |

보안 사례와 시험은 사람이 검토해 등록하고, 도구는 등록된 조건에 따라 선정·실행·비교한다. 시험 결과에는 엔진 직접 호출인지 게이트웨이 경유 호출인지 기록한다. 그래야 엔진의 보안 수정 효과와 앞단의 차단 효과를 각각 확인할 수 있다.

**현재 준비된 내용**

기존 `vllm-guard` 작업본에 정책·환경 입력, 변경 분석, 시험 계획, 실행 기록, 증거 검사, 판정·보고서 관련 코드와 일부 화면/API가 있다. 별도의 연구용 비교 시험 스크립트와 실행 결과도 있다. 일부 기능은 합성 자료로 동작을 확인한 상태다.

**남은 작업**

체크리스트의 적용 조건과 시험·판정 기준을 기존 코드에 반영한다. 실제 실행기와 수집기를 연결하고, 정한 vLLM 환경에서 입력부터 보고서 작성까지 실행한다. 연구용 시험은 적용 조건과 실행 범위를 확인한 뒤 재사용한다.

실제 두 환경에서 반복 시험이 가능하고, 보고서의 결과를 원본 증거까지 따라가 확인할 수 있어야 한다. 최종 운영 적용은 담당자가 검토한 뒤 결정한다.

# **4. 업데이트 검토 보고서**

자동 시험과 수동 검토 결과를 모아, 담당자가 업데이트를 적용할지 판단할 수 있도록 작성한다.

| 보고 항목 | 담을 내용 |
| --- | --- |
| **평가 대상과 변경사항** | 현재·후보 버전, 모델·설정·의존성·하드웨어 조건, 비교 중 달라진 부분 |
| **평가항목과 선정 이유** | 적용한 체크리스트와 보안 사례, 선정 이유, 제외하거나 실행하지 못한 항목과 사유 |
| **보안 결과** | 선정한 보안 수정의 효과, 기존 접근 제한과 보호 조건의 유지 여부, 발견한 위반과 미확인 |
| **정상 기능·품질·성능 결과** | 응답 형식과 사용 기능, 정해진 평가 데이터의 품질 기준, 지연시간·처리량·오류율·자원 사용량의 변화 |
| **증거와 평가 범위** | 로그·측정값·실행 기록, 증거가 부족한 부분, 시험하지 못한 기능, 환경 차이와 비교 불가 사유 |
| **보완과 최종 검토** | 수정할 설정·통제, 다시 실행할 시험, 남은 제한 사항, 적용·보완 후 재시험·보류 결정과 예외 승인 |

품질 평가는 해당 서비스에서 정한 데이터와 기준을 사용한다. 운영 적용 전에는 실제 배포할 구성이 시험한 조건과 일치하는지도 확인한다.

**현재 준비된 내용**

보고서 양식과 생성 코드, 버전 비교·증거 연결 형식이 있다. 개별 보안 시험의 실제 결과와 한계를 정리한 자료도 있다.

**남은 작업**

정한 두 버전의 보안·정상 기능·성능 결과로 보고서를 채운다. 각 결과에는 함수 단위 시험인지, 일부 구성요소를 대체한 시험인지, 전체 서빙 환경에서 실행한 시험인지 적는다. 담당자의 최종 결정과 그 근거까지 기록해야 보고서가 완성된다.

# **5. 런타임 통제·관측 기능**

운영 정책을 실제로 적용하고, 승인한 구성과 현재 상태를 비교한다. 정책 위반이나 구성 변경, 관측 장애가 발생하면 증거와 함께 알리고 필요한 재검증을 요청한다.

| 위치 | 확인하거나 통제할 내용 |
| --- | --- |
| **게이트웨이** | 일반·관리 API의 허용·거부 정책을 적용하고 호출 결과를 확인한다. 게이트웨이를 거치지 않는 엔진 직접 접근도 점검한다. |
| **서빙 호스트·컨테이너의 송신 경로** | 목적지 주소·포트·프로토콜에 따라 통신을 제한하고 적용 상태와 허용·거부 결과를 기록한다. 인터넷과 사내 서비스로 향하는 통신을 모두 포함한다. |
| **배포 설정·실행 프로세스** | 엔진 버전·이미지·실행 옵션·모델 식별정보를 승인된 구성과 비교한다. 관련 변경이 있으면 알림과 재검증 요청을 남긴다. |
| **엔진 로그·서버 및 GPU 지표** | 지원되는 오류·서비스 상태·자원 사용량을 수집하고 정한 기준을 벗어났는지 확인한다. 취소 후 작업 정리는 별도 시험에서 확인하고, 운영 화면에는 현재 수집 가능한 상태를 보여준다. |
| **정책 적용부·수집부** | 정책 적용 실패, 오래된 관측값, 수집 중단을 확인한다. 수집이 끊기면 관측 불가 상태를 표시한다. |

기존 게이트웨이, 네트워크 통제, 지표 수집 기능을 활용한다. 우리가 개발할 부분은 정책과 적용 대상 관리, 실제 적용 상태 확인, 승인 구성과의 비교, 알림, 관련 기록 조회다.

운영 기록에는 대상 워크로드·환경·정책·시각을 남기고, 가능한 경우 요청 식별자도 함께 기록한다. 중앙 관리부와 연결이 끊겨도 마지막 승인 정책이 유지되도록 한다. 재시작·배포·복구는 담당자의 운영 절차에 맡긴다.

**현재 준비된 내용**

송신 통신 제한과 게이트웨이 연동 설계, 정책·이벤트·적용 상태의 자료 형식과 예시가 있다. 승인 구성 변경 감지, 알림, 증거 조회도 기능 계획에 포함돼 있다.

**남은 작업**

정책 적용, 상태 확인, 기록 수집, 구성 비교, 알림·조회 기능을 구현하고 실제 환경에서 시험한다. 정상 상황과 함께 적용 실패·수집 중단·중앙 연결 단절도 확인해야 한다.

차단 효과는 적용된 정책과 연결 결과·관측 기록을 함께 보고 판단한다. 특정 요청의 자원 회수를 확인하려면 요청별 종료·정리 기록이 필요하고, 실제 로딩 대상을 확인하려면 승인 파일 정보와 소비 기록이 필요하다. 집계 자원 지표와 파일 해시로 확인할 수 있는 범위도 문서에 적는다.

# **6. 재현·운영 자료**

다른 담당자가 도구를 설치하고 같은 시험을 실행하며, 결과를 해석하고 운영 중 문제에 대응할 수 있도록 작성한다.

| 자료 | 담을 내용 |
| --- | --- |
| **설치·시험 환경 안내** | 엔진·의존성·모델·GPU·드라이버·실행 설정, 필요한 권한, 설치와 준비 확인 방법 |
| **검증 실행 안내** | 현재·후보 환경 등록, 정책 입력, 평가항목 확인, 시험 실행, 수동 검토, 보고서 확인 순서 |
| **재현 자료** | 시험 입력과 스크립트, 실행 환경 기록, 증거 위치, 예상 결과와 알려진 차이 |
| **운영 안내** | 정책 적용·변경, 승인 구성 등록, 알림 확인, 재검증 요청, 담당자가 확인할 사항 |
| **장애 대응·지원 범위** | 시험·수집·정책 적용 실패와 중앙 연결 단절 시 확인 순서, 시험한 버전·기능, 수동 작업과 미지원 범위 |

**현재 준비된 내용**

설치 안내, 의존성 고정 파일, 실행 스크립트, 환경·시험 명세, 증거 묶음과 실험 기록이 있다. 자료마다 작성 시점과 대상 환경이 달라 현재 기능에 맞춰 정리해야 한다.

**남은 작업**

완성한 도구의 사용 순서에 맞춰 문서를 통합한다. 예시 설정에는 사용자가 바꿔야 할 값을 표시하고, 실제 시험한 환경과 결과를 함께 제공한다. 다른 팀원이 문서만 보고 설치·시험·결과 확인을 수행하게 한 뒤, 막히거나 설명이 부족한 부분을 수정한다.
