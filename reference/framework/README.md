# 서빙엔진 보안 프레임워크

서빙엔진을 도입·운영·변경할 때 필요한 보안 점검을 고르고, 어떤 증거로 충족 여부를 판단할지 안내한다. **플랫폼·ML 운영자, 보안 검토자, 개발·시험 담당자**가 같은 기준으로 점검을 준비하고 결과를 검토하는 데 사용한다.

처음에는 [01 전체 체계](01_프레임워크와_위협통제연결.md)를 읽는다. 실제 사용은 **① [환경 확인](02_환경별_적용기준.md) → ② [점검 선택·기준 확인](03_체크리스트와_보완가이드.md) → ③ [시험·판정·보고](05_평가와_증거관리.md)** 순서다. 엔진·버전이 달라지면 [04 비교 근거](04_엔진과_버전별_차이.md)를 함께 본다.

## 현재 상태 — 2026-10-19

| 항목 | 현재 상태 |
| --- | --- |
| 구성 | 5개 영역·보호 목적 28개·세부 점검 77개·Q 평가 기록 28개 |
| 위협 분석 | 24개 묶음·시나리오 83개·Q–SC 연결 136개 |
| 정책 | 다섯 영역의 팀 참조 기준 채택. 실제 계정·대상·수치·기한과 조직별 값은 입력 필요 |
| 실행·도구 | 엔진/GPU 시험 미실행. selector는 입력한 환경으로 Q 적용 여부만 분류 |
| 확장 범위 | R10 미디어 일부 정적 검토만 반영, R10 전체와 R14는 평가 대기 |

**상태 표시:** ‘팀 기준 채택’은 평가 기준을 정했다는 뜻이다. ‘구현 계획’은 기능을 만들 예정이라는 뜻이고, ‘미실행’은 시험 전, ‘미확인’은 판정할 증거가 부족한 상태다. 기능을 쓰는지 모르면 적용 상태는 ‘미정’으로 둔다.

## 용어와 숫자를 읽는 법

| 용어 | 뜻과 쓰임 |
| --- | --- |
| 보호 자산(AS) | 모델·요청 자료·실행 상태·자격·기록 등 보호할 대상 |
| 보호 요구(POL) | 허용한 접근·실행·공유·종결 등 지켜야 하는 조건. 기존 통합본의 POL을 참조한다. |
| 보호 목적 28개 | 다섯 영역에서 무엇을 확인할지 찾는 공통 분류. 각 목적에 공통 확인 질문을 둔다. |
| 세부 점검 77개 | 적용 조건·정책·방법·증거·판정 기준을 갖춘 체크리스트 항목 |
| Q 평가 기록 28개 | 기존 정책·판정·구현·사례·시험 연결을 보존한 기록. 세부 점검의 관련 근거와 판정을 추적한다. |
| 시나리오(SC) 83개 | 공격자·접점·적용 조건과 보호 요구 위반 또는 실패 상황. 위협 후보 74개·실패/오설정 9개다. |
| 시험 초점 83개 | 시나리오마다 무엇을 확인할지 적은 설계 초점. 구현된 시험 수나 실행 횟수가 아니다. |
| 실행 시험 | 실제 환경·입력·절차·계측을 갖춰 실행하는 단위. 한 시나리오가 여러 시험으로 나뉠 수 있다. |
| R / TB / B-SURF | 동작 경로 / 신뢰가 달라지는 경계 / 구체적인 공격표면. B-SURF는 기존 통합본의 접점 ID다. |
| F / P0 | F는 기존 코드 검토 지적 번호. P0는 먼저 준비할 공동 시험을 가리키던 표기로, 취약점 심각도 등급은 아니다. |

보호 목적·세부 점검·Q·SC는 **여러 개씩 연결된다.** Q–SC 136개는 연결 수이며 실행 시험 136개를 뜻하지 않는다. 동일 실행의 증거를 재사용하더라도 각 점검·요구의 판정은 따로 남긴다.

## 자료의 역할

[최신 통합본](참고자료/통합본/통합본.md)은 정상 흐름과 소스 근거의 기준이고, 기존 취합용（출처: `서빙엔진_통합검토_초안_v0.2.1.md`）은 팀원 의견·위협 도출의 작업 이력이다. 이 폴더는 그 내용을 평가자가 사용할 수 있게 정리한 프레임워크·체크리스트다. 근거 수정 시 원본을 고친 뒤 여기의 같은 Q ID를 갱신한다. 원본 파일의 기준 해시는 `data/source_manifest.json`에 기록했다.

R01~R09·R11~R13을 다룬다. **R10은 미디어 일부 정적 검토 반영·전체 평가 대기, R14는 검토 대기**이며 관련 환경 차이는 빠뜨리지 않도록 남겨두었다. 그 기능을 쓰는 환경의 전체 보안을 이번 체크리스트만으로 평가 완료할 수 없다.

현재 엔진 구현 근거의 중심은 프로젝트 고정 vLLM v0.31.0이다. 다른 엔진은 공식 문서에서 확인한 기능 차이와 적용 방법을 제공한다. 특정 설치판의 지원·통제 효과는 선정 판본의 소스와 실제 시험으로 확인해야 한다. 모든 기업·엔진·버전의 조합을 검증한 목록은 아니다.


## 공유 폴더 구성과 원본 자료

이 폴더 전체를 공유하면 프레임워크·통합본·검토 근거·vLLM 소스를 함께 확인할 수 있다. 문서를 읽을 때는 아래 순서로 사용한다.

```text
serving-security-framework-20261018/
├── README.md                         사용 안내·현재 상태
├── 01~05 문서                        프레임워크·환경·점검·버전·평가
├── data/                             체크리스트·입력/결과 양식·출처·검수
├── select_checklist.py               Q 적용 분류·회귀 검사
├── 참고자료/
│   ├── 통합본/                       최신 통합본 원문·그림·원본 drawio·참고 근거
│   ├── 취합용/                       팀원 의견·위협/평가항목 도출 이력
│   └── 실행흐름검토/                 검토 결과·상세 코드 근거·분석 기록
└── 소스/
    ├── vllm-0.31.0/                 현재 구현 근거의 전체 소스
    ├── vllm-0.11.0/                 구판 비교용 전체 소스
    └── 출처확인/                     고정 commit·파일 확인 기록
```

- **현재 기준:** 이 폴더의01~05와 [최신 통합본](참고자료/통합본/통합본.md)을 사용한다. 복사한 최신 통합본은 원본과 바이트 단위로 같다.
- **작성 이력:** [취합용](참고자료/취합용/서빙엔진_통합검토_초안_v0.2.1.md)과 통합본 폴더의 수정전 원문은 과거 판단을 추적하는 자료다. 현재 프레임워크의 정책·판정·지원 상태를 과거 문구로 되돌리지 않는다.
- **실행흐름:** [검토 결과](참고자료/실행흐름검토/검토결과와_수정제안.md)와 [상세 코드 근거](참고자료/실행흐름검토/상세_코드근거.md)를 함께 본다. 검토 대상 구성·미실행 범위는 각 문서의 조건을 따른다.
- **코드:** [vLLM v0.31.0 소스](소스/vllm-0.31.0/README.md) · [v0.11.0 비교 소스](소스/vllm-0.11.0/README.md). vLLM v0.31.0은 고정 commit `db9527a46873454610df6dbedf79a36d6bf1a7f6` 기준이다. v0.11.0은 과거 비교 근거이며 업데이트 비교 버전으로 확정한 뜻이 아니다. 소스는 검토 자료이고 설치된 실행 환경이 아니다. PyTorch·CUDA·Transformers 등 외부 의존성 전체를 별도로 포함하지는 않았다.
- **취약점 조사:** [R별 색인](참고자료/통합본/references/vllm031-review-inputs/serving-vulnerability-r-index-20261016/취약점_사례_R별_참고색인.md) · [유형별 분류](참고자료/통합본/references/vllm031-review-inputs/serving-vulnerability-types-20261016/취약점_유형별_분류와_체크리스트_시험_연결_초안.md) · [기존 사례 원장](참고자료/통합본/references/vllm031-review-inputs/serving-vulnerability-catalogue-20261016/서빙엔진_취약점_사례목록_20261016.md). 이후 정정은04의 공지 확인 기록과 `data/checklist.json`의 정정값을 우선한다.

공유 사본의 일부 근거 문서는 개인 경로만 폴더 안 상대 링크로 바꿨다. 바뀐 파일과 원본/공유 사본 해시는 `data/source_manifest.json`에 기록했다. 예전 제출자의 컴퓨터에만 있던 자료는 임의로 채우지 않고 ‘해당 과거 자료 미포함’으로 표시했다. 현재 통합본·필수 점검·포함한 소스의 확인에는 그 경로를 사용하지 않는다.

## 개발에 사용할 자료

- `data/checklist.json`: 기존 Q 28개 평가 기록과 새 상위 질문 대응, 다섯 영역 세부 점검 초안과 버전 관리 계획. selector는 기존 Q만 사용하며 새 구조의 세부 선택·실행은 미구현.
- `data/environment_template.json`: 팀 참조 구성의 **계획값**. 실제 설치값·정책값은 null.
- `data/result_template.json`: 하위 시험 결과 기록 양식. 실행 결과를 꾸며 넣지 않았다.
- `select_checklist.py`: 환경값으로 큰 질문을 적용/비적용 후보/미정으로 고르는 보조 기능. 엔진에 접속하거나 시험하지 않는다.

```sh
python3 -B select_checklist.py data/environment_template.json
```

기능을 false로 지정하더라도 `feature_absence_evidence`에 비사용·비노출 근거가 없으면 미정으로 남는다. 다른 엔진·판본은 공통 질문을 유지하고 구현 매핑 필요 상태로 표시한다. 출력은 선택 결과이며 통과 판정이 아니다.

조건부 입력 키는 `request_code_revision_selection`, `dynamic_import`, `alternate_sources_or_formats_or_derived_cache`, `remote_acquisition_or_retry`, `prefix_cache_or_shared_cache`, `shared_or_remote_weights`이다. 여러 조건을 OR로 묶은 키는 관련 기능이 모두 비활성이고 비노출 근거가 있을 때만 false로 둔다. `r10_features`와 `managed_or_external_fallback`은 이번 범위 밖의 검토 필요성을 표시한다.


## 다음에 채울 내용

1. 실제 모델·이미지·GPU·의존성·실행기와 접근·송신·수집 설정을 확인한다.
2. 팀 기준을 적용할 계정·허용표·수치·기한과 승인자를 정한다.
3. 우선 점검의 시험 입력·계측·중단·복구 절차를 구현한다.
4. 시험 증거와 보안·정상 기능·성능 결과를 기록하고 보완·적용 여부를 판단한다.

원본 통합본·취합용·실행흐름 검토 자료는 위 참고자료 폴더에서 연다. 현재 문서의 링크는 폴더 안 상대 경로를 사용하며, 원본 위치·해시는 `data/source_manifest.json`에서 관리한다. 상세 수정 이력은 [검수기록](검수기록.md)에 있다.

selector의 12개 회귀 검사는 `python3 -B select_checklist.py --self-test`로 재현한다. 이 검사는 적용 분류 로직만 확인하며 엔진·보안 통제 시험을 실행하지 않는다.
