## 판정 방법과 우선순위

- **시험 통과**: 정상 요청의 유지, 선정한 위반의 거부 또는 탐지, 엔진 미도달·실제 차단 같은 독립 증거, 장애 시 `unknown` 처리를 함께 확인한다. 정책 객체가 있거나 코드가 있다는 것만으로 통과시키지 않는다.
- **기존 증거**: `A2`는 [AWS GPU 2회차](AWS_GPU_서버2회차_결과_20261104.md), `A3`는 [3회차](AWS_GPU_서버3회차_결과_20261104.md), `A4`는 [4회차](AWS_GPU_서버4회차_결과_20261105.md), `CPU`는 [STATUS의 CPU 점검](../project-context/STATUS.md), `U`는 `runtime/tests/`의 로컬 단위·가짜 환경 시험이다. A2에서 양 엔진 AWS-01~19가 최종 통과했고 A3·A4는 표에 적은 사례만 재확인했다. 이는 **해당 사례의 판정**이지 37개 요구 전체의 합격이 아니다. A4의 AWS-20은 규칙 `load_error`로 `unknown`; vLLM은 미실행이다.
- **구현 상태**: `구현`은 좁게 적힌 동작의 코드가 있다는 뜻, `부분`은 핵심 연결/경계가 빠진 상태, `안전 거부`는 해당 고급 입력을 지원하지 않고 입구에서 거부하는 상태다. 운영 전체의 충족 여부는 별도다.
- **P0**: 현재 지원 경로의 우회·누출·오귀속·fail-open 또는 배포/복귀 오류를 막기 위해 먼저 시험한다. **P1**: 현재 구현의 실제 경계·장애·보존을 검증하고 부족한 연결을 개발한다. **P2**: 명시적으로 미지원인 입력이나 엔진 내부 계측이 필요한 확장이다. P2 확장 개발은 뒤로 두되, 현재의 안전 거부는 입력 회귀 시험과 함께 먼저 확인할 수 있다.
- 각 표의 **합격 기준**은 그 항목의 다음 시험에서 확인할 최소선이다. 엔진 내부까지 요구하는 원문의 전체 충족 여부와 혼동하지 않는다. `미확인`은 실패나 통과로 바꾸지 않는다.

## 로컬 시험과 GPU 실증의 관계

- **로컬 통과는 사전검증이다.** 실제 vLLM·SGLang을 대상으로 현재 지원한다고 주장할 동작은 최종적으로 배포된 Gateway·정책 묶음·엔진·Cilium/Tetragon·수집기 조합에서 정상/위반/장애를 대조해야 한다. 기존 A2~A4 통과는 해당 시험 조건의 유효한 실증 이력으로 유지한다. 현재 변경이 해당 통제 경계에 영향을 주는지 확인하고, 영향이 있는 사례만 회귀 시험한다. 저장소의 다른 코드나 무관한 필드가 바뀌었다는 이유만으로 전체를 다시 실행하지 않는다. 로컬 통과만으로 실제 엔진 항목을 `실증 완료`로 표시하지 않는다.
- **GPU가 동작 자체에 필요한 항목**은 실제 모델/파일 선택·캐시 생성/소비(SUP-003/005/007/015), template/tokenization·응답 귀속/취소·캐시 분리(REQ-007/011/012/015), GPU Pod 권한·비밀(PLT-001/004), 부하·준비·worker 장애·취소(LIF-003/004/007~010), 실제 엔진 로그/단계(OBS-002/003) 등이다. 이들은 엔진별로 대표 정상·위반·장애 사례와 원시 증거를 남긴다. LIF-008/009 같은 다중 worker 판정은 현재 단일 L4 서버로 충분하지 않을 수 있어 별도 다중 worker 구성이 필요하다.
- **GPU 하드웨어가 판정의 원인은 아닌 항목**도 실제 배포 조합의 통합 확인은 필요하다. 인증·route/옵션 거부(REQ-001~005/008~010/013), 정책 적용·복귀(SUP-014, LIF-015), 송신/관측(PLT-007, OBS-011), 기록 접근·보존(OBS-006/009/012) 등이 이에 해당한다. 모든 잘못된 입력 조합을 GPU에서 다시 반복할 필요는 없지만, 로컬에서 자세히 시험한 규칙이 실제 배포에서도 같은 결정을 내리고 거부 요청이 엔진에 도달하지 않는지 대표 사례를 확인한다. 저장소 ACL·암호화·백업 보존처럼 GPU와 무관한 운영 경계는 실제 운영 저장소에서 별도 인수한다.
- **지원하지 않는 기능은 안전 거부를 실증**한다. 예를 들어 REQ-008의 토큰 ID 입력은 현재 GPU에서 안전하게 처리됨을 입증할 대상이 아니라, 실제 Gateway에서 거부·엔진 미도달을 확인할 대상이다. 엔진 내부 계측이나 다중 worker 환경이 없으면 해당 전체 요구를 `미확인`으로 둔다.
- **AWS GPU dev와 정식 평가는 다르다.** A2~A4는 AWS dev의 특정 이미지·정책·시험 구간 결과다. 개발계획서 v1.4의 reference 환경 완료 주장은 해당 환경에서 재실행한 뒤에만 한다. 37개 각각을 독립 AWS 시험 번호로 만들 필요는 없지만, 지원 범위의 각 항목을 실제 엔진 결과에 연결하는 증거표는 필요하다.

## 실행 규칙

- 위 표의 01번부터 착수하되, AWS 가동은 로컬 선행 시험과 배포 입력을 준비한 뒤 가능한 행을 한 번에 묶어 실행한다. 개발 선행 행은 코드·계약·배포 변경을 먼저 만들고 로컬 회귀를 통과시킨 뒤 GPU에서 확인한다.
- 기존 A2~A4의 통과 범위는 증거로 인정한다. 해당 동작에 영향을 주는 변경, 새 환경의 인수, 원래 확인하지 않은 경계에 한해 추가 실증한다. 다중 worker 행은 단일 L4 서버의 통과로 간주하지 않는다.
- 각 행을 실행한 뒤 결과·증거 위치·남은 결함을 그 행에 연결하고, 미실행 항목은 계획으로 유지한다.
