## 2. LAB 범위에서 쓰는 방식 (현재 구현)

**정적 bearer 토큰 프레임 (`runtime-auth/1.0`, `--auth-config`)**

- 주체별 토큰 SHA-256·역할·허용 모델을 관리 경로의 설정 파일에 둔다. 토큰 원문은 파일·기록·상태에 남기지 않는다.
- 추론 경로 `POST /v1/chat/completions`와 조회 경로 `GET /api/*`를 역할로 보호할 수 있다(조회 경로 보호는 `route_roles`에 넣었을 때만).
- 인증 없음·실패 401, 역할·모델 불허 403, 설정 오류 503(오류로 기록, 차단 성공 아님). 모두 엔진에 전달하지 않는다.
- 인증 부분은 `AuthState.authenticate()` 한 곳으로 모여 있어 다른 방식으로 바꿔 끼울 수 있다.

**이 방식을 LAB에 쓰는 이유**

1. 외부 인증 서버·인증서 체계가 LAB에 없고, 계획서가 별도 인증 제품 구축을 금지한다.
2. 표준 라이브러리만으로 구현·시험할 수 있어 2차 발표 일정(11/8 연결 완료) 안에 401/403·미전달 증거를 만들 수 있다.
3. 주체·역할·거부 사유를 요청 기록에 남기는 흐름(§4.2 출력)을 실제 연동 방식과 무관하게 먼저 검증할 수 있다.

**LAB 방식의 한계 (운영 사용 금지 사유)**

- 토큰 회전·만료·폐기 이력이 없다. 파일을 바꾸면 Gateway를 다시 시작해야 한다.
- 토큰 발급·전달 경로를 다루지 않는다. 예시 파일의 토큰은 공개값이다.
- (2026-10-25 변경) Gateway 자체 대시보드는 제거됐다. 화면은 byul platform이며, 조회 토큰은 platform 서버가 환경변수 `RUNTIME_VIEWER_TOKEN`으로 받아 서버 쪽에서만 보낸다. 로그인·세션 만료는 여전히 없다.

## 3. 운영 연동 후보 (미결, 대상 기업 환경에 따라 선택)

| 후보 | 맞는 경우 | 추가 작업 | 확인할 것 |
| --- | --- | --- | --- |
| Kubernetes ServiceAccount 토큰 + TokenReview | 호출자가 같은 클러스터의 워크로드 | Gateway에 TokenReview 호출 권한, audience 고정 | API server 접근 권한(D-03), 토큰 audience·만료 |
| mTLS 클라이언트 인증서 | 서비스 간 호출, 사내 PKI 존재 | 인증서 발급·회전 체계, 주체 매핑 | CA·회전 주기·폐기 방식 |
| OIDC/JWT | 사내 로그인 서버(IdP) 존재, 사람·서비스 혼합 | 서명 검증 라이브러리 선정(출처·라이선스·판본, §부록 C 기준) | issuer·audience·키 회전, 역할 claim 매핑 |
| 기존 API Gateway/프록시 위임 | 대상 기업이 이미 앞단 Gateway를 운영 | 신뢰 헤더·mTLS로 전달받은 주체만 신뢰 | 앞단과 이 Gateway 사이 위조 방지 |

선택 기준: 대상 기업의 기존 인증 체계 재사용(§5.1), 주체·역할을 요청 기록에 남길 수 있는지, 엔진 직통 우회가 없는지(§4.2 처리 4), 표준 라이브러리 밖 의존성이 필요하면 출처·라이선스·판본 기록.
