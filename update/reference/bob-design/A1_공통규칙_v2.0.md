## 1. 단계와 책임

객체를 만드는 쪽이 상세 스키마를 정한다. 받는 쪽은 정의되지 않은 필드를 추가하거나 의미를 바꾸지 않는다. 필요한 변경은 소유자에게 요청하고, 소유자가 새 버전을 전달한다.

| 단계 | 역할 | 소유 / 문서 | 산출 객체 |
| --- | --- | --- | --- |
| S1 | 정책·환경 입력, 정책 확정 | T1 / A11 | ConfirmedPolicy, EnvironmentProfile |
| S2 | 변경 분석 | T2 / A4 | ChangeFact |
| S3 | 변경 영향평가 | T2 / A4 | ImpactAssessment |
| S4 | 시험 선정 | T2 / A4 | TestPlan |
| S5 | 격리 실행 | T2 / A5·A15 | RunManifest, Observation, Evidence, TestResult |
| S6 | 비교·권고 | T2 / A4·A5 | Comparison, Recommendation |
| S7 | 런타임 통제·상태 확인 | T3 / A6 | RuntimePolicy, RuntimeEvent, EnforcementStatus |
| S8 | 보고서·승인 기록 | T3 / A12 | Report, Approval |

- 최종 단계 번호는 A3가 정한다. 번호가 바뀌어도 객체와 판정의 의미는 바뀌지 않는다. (D01)
- 표는 책임의 흐름이다. S5 실행에 필요한 격리·통제 준비는 S7보다 먼저, 실행의 선행 조건으로 확인한다.
- 영향평가 보고서는 S4 이후·S5 이전에, 검증 결과 보고서는 S6·S7 이후에 만든다. 시험 전 보고서에 결과를 미리 채우지 않는다.
- 정책·예외 승인은 S1에서, 릴리스 승인은 검증 결과 검토 뒤에 한다. Approval 객체의 소유가 S8이라는 이유로 모든 승인을 마지막에 몰지 않는다.
- **S6 권고 범위 (D06):** S6 권고는 선정된 격리 검증 범위만 다룬다. S7 준수 상태는 별도로 유지하고, 릴리스 승인에서 둘을 함께 검토한다.
- **릴리스 승인 직전 재확인 (D13, D21로 보완):** 승인자는 근거로 쓴 ConfirmedPolicy·예외·EnvironmentProfile이 판정 시점 그대로 유효한지 재확인한다. 변경이 있으면 재평가한다 — 기존 증거로 재판정 가능하면 재시험 없이 그 근거로 판정하고, 기존 증거가 바뀐 조건을 다루지 못하면 재시험한다(불변식 13).
- **Approval 생성 시점 (D20, 신규):** Approval의 스키마 소유는 T3(A12)지만, 실제 Approval 객체는 두 시점에 각각 생성된다 — 정책·예외 승인은 S1에서, 릴리스 승인은 검증 결과 검토 뒤에. 산출 객체 표의 "S8" 표기는 스키마 소유만 뜻한다. S1에서 A11은 Approval을 직접 만들지 않고 이미 존재하는 승인을 참조만 한다.

## 2. 식별·참조 규칙

### 2.1 ID

형식은 `접두어-범위-일련번호`다. 예: `POL-POC-001`, `RUN-POC-001`. 범위 토큰은 생성 시 고정하고, ID에 판정값을 넣지 않는다.

| 접두어 | 의미 | 접두어 | 의미 |
| --- | --- | --- | --- |
| CTRL | 공통 정책 정의 | POL | 정책 (확정 과정의 정책 객체) |
| EXC | 예외 | APPR | 승인 |
| ENV | 환경 프로필 | CHG | 변경 사실 |
| ADV | 보안 권고 기록 | IA | 영향평가 |
| TEST | 시험 정의 | PLAN | 시험 계획 |
| RUN | 실행 명세 | OBS | 관측 |
| EVD | 증적 | RES | 시험 결과 |
| CMP | 비교 | REC | 권고 |
| RTP | 런타임 정책 | RTE | 런타임 이벤트 |
| ENS | 준수 상태 스냅샷 | RPT | 보고서 |
| ASG | 기업 Assignment (D21, 신규) | SUG | 판단 보조 제안 (D34, A23) |
| PACK | 콘텐츠 팩 (D34, A17 — 카탈로그 입력, 교환 객체 아님) | — | — |

- 시험 정식 ID는 `TEST-MODEL-007`, `TEST-FUNC-003`, `TEST-NET-004`다. `MODEL-007` 등은 화면 표시용 코드다.
- CVE·GHSA 번호는 외부 식별자다. 내부 ADV ID와 따로 저장한다.
- ID 재사용과 덮어쓰기를 금지한다. 재실행은 새 RUN, 재판정은 새 RES를 만들고 이전 것을 참조한다.
- A11 등에서 새 객체가 필요하면 소유자가 접두어를 제안하고 A1에 등록한다. 받는 쪽이 임의로 만들지 않는다.
- **내부 모델과 내부 축 (D24, 신규):** 소유 문서는 구현용 내부 클래스·내부 enum(예: RuntimeHealth, EvidenceKind, EffectSource)을 둘 수 있다. 단 문서 사이를 오가는 객체는 3절의 이름·핵심 필드를, 판정·비교·권고·준수 상태는 4절 값을 쓰고, 내부 값은 경계에서 A1 값으로 변환한다. 내부 축을 정의할 때 "A1 교환 enum이 아님"을 함께 적는다.

### 2.2 공통 필드와 참조

- 모든 교환 객체는 `id`, `schema_version`, `revision`, `created_at`을 가진다. `schema_version`은 구조 버전, `revision`은 같은 ID의 내용 개정 번호다.
- 같은 ID·revision의 내용은 바뀌지 않는다. 상태가 바뀌면 새 revision이나 새 객체로 기록한다.
- 참조는 `{id, revision}`으로 고정한다. 최신본을 가리키는 참조로 과거 보고서의 근거가 바뀌게 하지 않는다.
- 시각은 시간대를 포함한 RFC 3339로 저장하고, 화면에는 한국 시각으로 표시한다.
- `null`, 필드 누락, 빈 배열, `UNKNOWN`은 서로 다르다. 미확인을 `false`, `0`, 빈 문자열로 대체하지 않는다. null 허용 여부는 소유 스키마에 명시한다.
- 정의되지 않은 enum, 필수 필드 누락, 지원하지 않는 스키마, 해결되지 않는 참조는 검증 오류다. 받는 쪽은 값을 보정해 판정을 계속하지 않고, 오류 위치와 이유를 돌려준다.
  - **예외 (D33):** 기업이 제출하는 정책 입력(Assignment·Exception·승인 참조)이 파싱은 되지만 스키마를 어기면, A11 Resolver는 오류 위치·이유를 담은 `DRAFT` ConfirmedPolicy를 만든다(A11 §3 1단계). 이 DRAFT는 진단·확인 질문용이며 공식 평가 기준으로 다른 단계에 전달하지 않는다. 그 밖의 교환 객체와 카탈로그(CTRL·TEST)·환경 입력·EnvironmentProfile에는 이 예외가 없다.

### 2.3 v2.0 구조 기준선

새 구현의 교환 객체 버전은 아래 객체별 표를 따른다. D43 이전의 일괄 `2.0` 신규 생성 규칙은 아래 표로 대체한다. 문서 버전과 객체 revision은 별개다. v1.x 예시·저장 객체를 필드 이름만 바꿔 자동 승격하지 않는다. 이전 bytes·해시·서명은 보존하며, 필요한 이전 자료는 별도 명시 변환 및 검증 후 새 객체/새 revision으로 등록한다. 닫힌 스키마의 추가 필드는 소유 문서 표와 아래 지원 버전에 함께 등록된 것만 허용한다. 서로 다른 구조를 같은 schema_version으로 새로 저장하지 않는다.

PROFILE·PDAT는 팩 안 부하 프로필·정책 목록/표식 자료의 내부 카탈로그 ID이며 교환 객체가 아니다. exact Ref 형태와 bytes SHA로 팩 잠금에 연결한다(A17 §2·§4.4). TEST-SYS-001·002·PERF-001도 A7 정식 ID다. 선언형 규칙·센서·보조 제안이 새 enum을 만들지 않는다.

보고서의 판단 근거 그래프와 SUG 표시 참조 그래프는 분리하지만 둘 다 무결성 검증한다. 기능 비활성은 정책 면제가 아니며, 모든 필수 SYS/PERF 미검증은 권고·승인 gap에 포함한다.

### 2.4 D43 객체별 버전과 수치·바이트 규약

D43은 개발 착수 전 계약 수정본이다. 대상 저장소에는 제품 코드·저장 객체·실서명이 없고 저장소 밖 자료는 미확인이다. 문서 파일명은 참조 유지를 위해 v2.0을 유지한다. 소유자 확인·실측 완료를 뜻하지 않는다.

| 교환 객체 | 신규 생성 버전 | 변경 이유·소유 정본 |
| --- | --- | --- |
| POL | 2.1 | 상태별 DRAFT·preview 추적, A11 §4.4 |
| IA, PLAN | 2.1 | 기대값 타입·복수 IA·RequirementRef, A4 §11 |
| RUN, OBS | 2.1 | 요구 참조·시작 전 실패·APIGW health subject, A5 §3.3·§8.8 |
| RTP, RTE | 2.1 | 컴파일된 입력 스키마·실제 시험 RUN 귀속, A6 §15 |
| RPT | 2.1 | 요구 참조·운영 진단 표시, A12 §2 |
| CTRL, ASG, EXC, ENV, CHG, TEST, EVD, RES, CMP, REC, ENS, APPR, SUG | 2.0 | 필드 구조 유지. 승인 domain/v1 유지 |

생산자는 이 표와 소유 스키마가 일치하는 버전만 생성한다. 새 공식 평가 흐름은 위 버전 조합만 받는다. 교환 스키마·객체 revision·팩 revision·문서 버전·서명 domain은 별개다. 2.0 POL/IA/PLAN/RUN/OBS/RTP/RTE/RPT는 역사 조회·검증용이며 새 흐름에서 자동 승격하지 않는다. 기존 실제 구현·저장 자료가 확인되면 해당 serializer와 저장 바이트를 대조하고 명시 변환·새 승인 범위를 먼저 정한다. 역사 decoder가 없으면 UNSUPPORTED_HISTORICAL_PROFILE로 표시하고 효력을 인정하지 않는다.

**새 비밀 제외 JSON의 의미 해시 프로필 `guard-json-decimal/1`:** UTF-8, NFC 입력 검증(몰래 정규화하지 않음), 문자열 key의 Unicode 코드포인트 오름차순, 공백 없는 JSON, ensure_ascii=False, trailing LF 없음, 배열 순서 보존. boolean과 integer를 구분하고 중복 키·비유한 수·잘못된 Unicode를 거부한다. 수치는 입력의 십진 토큰을 Decimal로 파싱하고 이진 float로 변환하거나 반올림하지 않는다. 유한 수의 값만 허용하며 -0은 0, 불필요한 소수 끝 0과 exponent를 제거한 십진 표기를 사용한다(1/1.0/1e0→1, 0.0100→0.01). 객체 크기 제한은 A13 입력 상한을 따른다. exponent 전개가 해당 상한을 넘으면 거부한다. PERF 단위·범위·측정 집계의 허용오차는 A7·A5의 값 그대로이며 임계값을 임의 문자열로 바꾸지 않는다. 공용 serializer 하나를 preview·설정/정책 해시·compiler·readback에서 사용한다. RFC 8785/JCS 준수를 주장하지 않는다.

이 프로필은 수치를 포함할 수 있는 **새 객체/설정/목록의 의미 해시**를 닫는 규약이다. 승인 payload는 A12 §4.1의 기존 정수 전용 domain/v1 규약을 유지한다. 승인에는 subject의 exact Ref와 의미 해시를 넣으며 subject 본문을 payload에 끼워 넣지 않는다. 서명 payload에 허용되지 않는 소수가 직접 들어오면 오류다. 파일(EVD·팩·manifest·생성 Markdown)은 보존한 실제 bytes의 SHA-256이다. 비밀 포함 원문 및 그 해시를 남기지 않는다.

store의 내부 무결성 metadata에 각 의미 해시의 profile과 최초 등록 bytes 해시를 고정한다(교환 객체 필드가 아님). 과거 profile이 확인되지 않으면 현행 profile로 재계산해 기존 서명을 검증하지 않는다. 과거 서명 bytes·해시·유효성은 별도로 보존한다. 기존 승인에 새 scope·효력을 부여하지 않는다.

## 3. 교환 객체 목록

객체별 **핵심 필드**만 정한다. 필드명·타입·조건부 필수 여부는 소유 문서가 확정한다. 소유자 참고용 상세 제안은 별도 부록(T2용, T3용)으로 전달한다. **참조 필드는 모두 §2.2의 `{id, revision}` 형식이다.**

| Approval | T3 (A12) | 검토자 | `approval_type`, `subject_ref`, `status` |
| AssistSuggestion | T1 (A23) | 검토자, T3(A12 보고) | `feature`, `subject_refs`, `content`(인용 포함), `validation`, `status`, `data_classes_sent` |

- **AssistSuggestion은 어느 단계의 산출물도 아니다 (D34).** 판단 보조 기능(A23)이 켜져 있을 때만 생기며, S1~S8의 어떤 판정 함수에도 입력되지 않는다(불변식 16).
- `ConfirmedPolicy`는 `status=DRAFT`도 담는다. 이름이 아니라 `status`만으로 확정 여부를 판단한다.
- `expected_behaviors.evidence`는 필요한 증적의 **명세**다. 실제 EVD 목록이 아니다.
- Evidence 스키마는 T2가 관리한다. T3가 런타임 증적을 만들 때도 같은 계약을 따른다.
- `Comparison`·`Recommendation`처럼 여러 TestResult를 근거로 삼는 객체가 `verification_level`·`data_origin`을 어떻게 표시하는지는 4절의 집계 규칙을 따른다.
- **Recommendation.direction·대상 버전 일관성 (D16):** `Recommendation`의 `direction`과 대상 버전은 `basis_refs`가 참조하는 모든 `Comparison`의 `direction`·버전과 일치해야 한다. 하나라도 불일치하면 §2.2의 검증 오류로 처리하고, 근거를 나눠 별도 Recommendation을 만든다. 업데이트 권고와 롤백 권고가 한 객체에 섞이지 않게 하는 조건이다.
- **Report와 Approval은 서로 다른 객체다 (D20, 신규).** 이전까지 한 행에 합쳐 `report_type`·`approval_type` 등 필드 소속이 모호했다. RuntimePolicy/RuntimeEvent/EnforcementStatus를 세 객체로 나눈 것(D15)과 같은 이유로 분리한다.
- **정책 적용 범위와 요구 동작별 예외는 다른 층위다 (D21, 신규):** `scope`는 정책 자체가 이 환경·대상에 포함되는지(`APPLICABLE`/`NOT_APPLICABLE`/`UNKNOWN`)만 판정한다. `EXEMPTED`는 정책 전체가 아니라 `expected_behaviors`의 개별 항목(`applicability`)에 표시한다. 정책이 `APPLICABLE`이어도 예외 승인을 받은 요구 동작만 그 항목이 `EXEMPTED`이고, 승인받지 못한 나머지 요구 동작은 `APPLICABLE`로 남아 시험이 유지된다. 정책 하나의 `scope`가 `EXEMPTED`라는 값을 갖는 일은 없다.
- **RunManifest 상태와 TestResult UNKNOWN의 연결 (D20, D21로 보완):** `RunManifest.execution_status`가 `ABORTED` 또는 `NOT_STARTED`이고 **판정 가능한 증거가 확보되지 않았다면** 해당 시험의 `TestResult`는 `UNKNOWN`이며, `reason`에 RunManifest 상태를 근거로 남긴다. 중단 전에 위반 등 판정 가능한 증거가 이미 확보됐다면 그 증거로 판정하고 중단을 이유로 `UNKNOWN`으로 덮어쓰지 않는다(불변식 10·12와 연결).

## 4. 공통 enum

UPPER_SNAKE_CASE를 쓰고, 목록 밖 값은 금지한다. 같은 문자열이라도 다른 축의 값과 섞지 않는다.

| 구분 | 허용값 | 의미 |
| --- | --- | --- |
| 정책 확정 | `DRAFT`, `CONFIRMED` | 공식 평가 기준으로 쓸 수 있는가 |
| 정책 적용 범위 | `APPLICABLE`, `NOT_APPLICABLE`, `EXEMPTED`, `UNKNOWN` | 이 환경·대상에 정책이 적용되는가 |
| 변경 영향 | `APPLICABLE`, `NOT_APPLICABLE`, `UNKNOWN` | 변경이 평가 대상 동작에 영향을 주는가 |
| 시험 판정 | `PASS`, `FAIL`, `UNKNOWN` | 시험의 기대 동작을 충족하는가 |
| 비교 | `NO_CHANGE`, `REGRESSION`, `FIXED`, `EXISTING_FAILURE`, `BEHAVIOR_CHANGED`, `INCONCLUSIVE` | 출발 → 도착 방향의 비교 결과 |
| 권고 | `ELIGIBLE`, `MANUAL_REVIEW`, `BLOCKED` | 명시한 범위에서 도착 버전으로의 변경 권고 |
| 준수 상태 | `COMPLIANT`, `DRIFTED`, `PARTIAL`, `UNKNOWN` | 관측 범위·시점에서 런타임 통제 상태 |
| 승인 상태 | `PENDING`, `APPROVED`, `REJECTED` | 권한 있는 사람의 결정 |
| 승인 종류 | `POLICY`, `EXCEPTION`, `RELEASE` | 무엇에 대한 승인인가 |
| 보고서 종류 | `IMPACT_ASSESSMENT`, `VALIDATION_RESULT` | 시험 전 / 시험 후 |
| 기대 동작 단계 | `ISOLATED`, `RUNTIME`, `DEFERRED` | 격리 시험 / 운영 통제 / 이후 범위 |
| 방향 | `UPDATE`, `ROLLBACK` | 출발·도착 버전과 함께 기록 |
| 실행 상태 | `NOT_STARTED`, `RUNNING`, `COMPLETED`, `ABORTED` | 미시작·중단을 판정과 섞지 않음 |
| 증적 수집 상태 | `COMPLETE`, `PARTIAL`, `FAILED` | 수집 완결성. 진위나 시험 성공을 뜻하지 않음 |
| 런타임 통제 모드 | `OBSERVE`, `BLOCK` | 입력값은 A11 경계에서 변환 |
| 검증 수준 | `ENGINE`, `PARTIAL_PATH`, `STATIC` | 실제 엔진 경로 / 일부 경로 / 정적 근거 |
| 데이터 출처 | `EXAMPLE`, `MEASURED` | 예시 자료로 만든 결과 / 실제 실행·관측으로 만든 결과 (신뢰도 서열이 아니라 **출처 구분**) |
| 분석 확실성 | `CONFIRMED`, `PARTIAL`, `UNKNOWN` | 분석 주장의 근거 충분성 |

- **변경 영향 판정 순서 (D24, 신규):** `ImpactAssessment.applicability`는 전제조건을 환경 사실에 대입해 정한다. 하나라도 거짓이면 `NOT_APPLICABLE`(이유 기록), 모두 참이면 `APPLICABLE`, 거짓이 없고 미확인·충돌이 있으면 `UNKNOWN`(추가로 필요한 사실 목록 출력). **거짓이 미확인보다 우선한다.**
- **ImpactAssessment 요구 두 갈래 (D24, 신규):** `validation_requirements`는 격리 시험(S5) 요구, `runtime_requirements`는 런타임 통제(S7) 요구다. 런타임 요구의 조치는 `enforcement_mode`(OBSERVE/BLOCK)로 표현한다.
- **정책 적용 범위 enum의 적용 대상 (D21, 신규):** 이 enum은 `ConfirmedPolicy.scope`와 `expected_behaviors[].applicability` 두 필드에서 함께 쓰이지만 값의 범위가 다르다. `scope`는 `APPLICABLE`/`NOT_APPLICABLE`/`UNKNOWN` 중 하나만 가지며 `EXEMPTED`를 쓰지 않는다. `EXEMPTED`는 `expected_behaviors[].applicability`에서만 쓴다(3절 참고).
- `ENGINE`은 해당 시험의 실제 엔진 경로를 확인했다는 뜻이다. 전체 보안성을 뜻하지 않는다.
- 실행하지 못해 검증 근거가 없으면 `verification_level`, `data_origin`은 null로 두고 사유를 남긴다. 실행하지 않은 항목에 `MEASURED`나 `STATIC`을 억지로 붙이지 않는다.
- 준수 상태: 확인된 불일치가 있으면 `DRIFTED`, 불일치 없이 일부만 확인하면 `PARTIAL`, 판단할 관측이 없거나 센서를 믿을 수 없으면 `UNKNOWN`, 필요한 범위를 확인했고 불일치가 없을 때만 `COMPLIANT`.
- **집계 규칙 (D12, D14로 보완):** `Comparison`·`Recommendation`처럼 여러 `TestResult`를 근거로 삼는 객체는 근거별 `verification_level`·`data_origin`을 **null을 포함해 그대로** 배열로 보존한다. 배열에서 null을 제외하거나 채워 넣지 않는다.
  - **필수 근거 중 하나라도 null(미실행·미검증)이면 대표값도 null**이며, "일부 근거 미검증"과 어느 근거인지를 사유에 남긴다. null인 근거를 빼고 나머지끼리 대표값을 정하지 않는다.
  - 모든 근거가 non-null이면, 검증 수준은 `STATIC < PARTIAL_PATH < ENGINE` 순으로 **가장 얕은(약한) 값**을 대표값으로 삼는다(깊이·커버리지 축이므로 서열 의미가 있음).
  - 데이터 출처는 신뢰도 서열이 아니라 **실제 실행 여부의 구분**이다: 근거 중 하나라도 `EXAMPLE`이면 대표값은 `EXAMPLE`(불변식 2 — 예시 자료가 섞인 결과를 `MEASURED`로 표시 금지), 전부 `MEASURED`일 때만 `MEASURED`.
  - 서로 다른 값이 섞였다는 이유로 더 강하거나 더 깊은 값으로 승격하지 않는다.

## 5. 판정 불변식

모든 트랙에 적용한다. 위반은 버그다.

1. `UNKNOWN`을 `PASS`로 승격하지 않는다. 확인 부족과 위반 확인을 구별한다.
2. 실행하지 않은 시험, `EXAMPLE` 자료, 기대값을 `MEASURED` 결과로 표시하지 않는다.
3. 실행 표식이 없다는 것만으로 코드 미실행을 입증하지 않는다. 경로 도달, 거부 근거, 실제 설정값이 함께 필요하다. 구체 조건은 A7이 정한다.
4. 통신 시도가 없으면 차단 성공이 아니다. 미수신만으로 `PASS`가 되지 않는다.
5. 정책 적용 범위와 변경 영향은 별개다. `EXEMPTED`여도 변경 영향은 기록한다. 면제된 위반이 `PASS`로 바뀌지 않는다.
6. `DRAFT` 정책은 공식 영향평가 기준으로 쓰지 않는다.
7. 자동 권고는 승인이 아니다. `ELIGIBLE`만으로 배포하거나 롤백하지 않는다.
8. 시험 결과·비교·권고에는 검증 수준과 데이터 출처를 붙인다. 증적 파일은 SHA-256과 수집 위치·시각으로 식별한다.
9. **비교 단위는 엔진 이미지(digest)다.** 이미지에 포함된 의존성 차이는 비교 대상에 속한다. 모델, 시험 자료, 설정, GPU·드라이버, Kubernetes, 정책, 통제 모드, 관측 조건은 같아야 한다. 이들이 다르거나 같음을 확인할 수 없으면 `INCONCLUSIVE`다. (D08) **비교 대상 이미지의 vLLM 버전·주요 의존성 버전·base image digest는 Evidence로 남긴다. 결론은 vLLM 버전만의 효과가 아니라 이미지 전체(포함된 모든 의존성 변경)의 합산 효과이며, `Comparison`·`Recommendation`의 `reasons`에 이를 명시한다. vLLM 버전만의 효과로 좁혀 해석하지 않는다.** (D08 보완, D12)
10. 위반 증거가 없는 것과 준수 증거가 있는 것은 다르다. 센서 장애·자료 누락은 `UNKNOWN` 또는 부분 확인으로 표시한다. 확인된 위반은 다른 누락 때문에 지우지 않는다.
11. 예외는 승인·유효기간·대상 범위가 모두 유효할 때만 효력이 있다. 만료·미승인 예외는 적용하지 않고 이유를 남긴다.
12. **선정되지 않은 시험은 TestResult를 만들지 않는다. 선정되었으나 실행하지 못한 시험은 TestResult를 `UNKNOWN`으로 남기고 미실행 사유를 기록한다.** 미선정과 미실행을 같은 상태로 합치지 않는다. (D12)
13. **릴리스 승인 직전에 근거로 쓴 ConfirmedPolicy·예외·EnvironmentProfile의 유효성을 재확인한다.** 시험 이후 정책 개정, 예외 만료·철회, 환경 변경이 있으면 재평가한다. **재평가는 재시험과 다르다:** 기존 Evidence·Observation으로 다시 판정할 수 있으면 그 근거로 재판정하고 재평가 사실·근거를 남긴다. 기존 증거가 바뀐 조건을 다루지 못할 때만 재시험한다. 재평가 자체를 생략하고 그대로 승인하지 않는다. (D13, D21로 보완 — 재판정과 재시험을 구분)
14. **여러 근거를 집계하는 `verification_level`·`data_origin`은 필수 근거 중 null이 하나라도 있으면 대표값도 null이다.** null을 제외하고 나머지 근거만으로 대표값을 정하면 미검증 범위가 숨겨진다. 근거 배열에는 null과 그 사유를 그대로 남긴다. (D14, 신규 — 4절 집계 규칙 보완)
15. **Approval이 잠근 대상 revision과 실제 확정에 쓴 입력 revision은 정확히 일치해야 한다.** 승인 대상 내용(Assignment·Exception 등)을 먼저 고정하고 그 revision을 승인한 뒤, 승인 내용과 일치하는 ConfirmedPolicy만 CONFIRMED로 만든다(D10). 승인 이후 입력이 바뀌면 새 승인 없이 CONFIRMED로 만들지 않는다 — 승인은 한 번 받으면 이후 변경에도 유효한 백지위임이 아니다. (D21, 신규)

16. **판단 보조 제안(AssistSuggestion)은 정책 적용·변경 영향·시험 선정·판정·비교·권고·준수 상태·승인 함수의 입력이 아니다.** 판단 보조 기능을 켠 경우와 끈 경우 같은 입력에서 위 객체들의 내용이 같아야 한다. 제안을 채택해도 교환 객체는 바뀌지 않으며, 사람이 해당 입력 절차에서 직접 확인·입력한 값만 기록된다. (D34, 신규)
