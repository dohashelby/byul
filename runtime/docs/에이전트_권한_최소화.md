# 에이전트 계정 권한 줄이기 (14회차 발견 2)

> Claude가 구현함(Codex 사용 한도). **Codex 교차 검수 전**이며 실서버 적용 전이다. 로컬 kind에서 확인했다.

## 1. 왜

14회차에 서버의 runtime-agent kubeconfig를 점검했더니 **필요 없는 권한까지 모두 허용**이었다(비밀값 읽기, Pod 삭제, 노드 조회, 권한 변경 등). 에이전트는 승인된 요청으로 서버를 바꾸는 프로그램이라, 계정이 털리면 피해 범위가 곧 이 권한이다.

## 2. 필요한 권한 (한 목록에서 관리)

`tools/agent_rbac.py`의 `REQUIRED`가 기준이다. 같은 목록으로 권한 파일을 만들고(render) 점검한다(check).

| 범위 | 대상 | 동작 | 쓰는 기능 |
| --- | --- | --- | --- |
| 서빙 namespace | TracingPolicyNamespaced, CiliumNetworkPolicy | get·list·create·update·patch·delete | 10번 규칙 적용·복원, Tetragon 모드 전환 |
| 서빙 namespace | deployments·replicasets | get·list·watch, deployments patch | 묶음 적용 뒤 Gateway 재시작·상태 확인 |
| 서빙 namespace | pods, pods/portforward, pods/log | get·list, create, get | Gateway 상태 확인, 11번 엔진 로그(선택) |
| Tetragon namespace | pods, daemonsets, pods/exec | get·list, get, create | `tetra`로 정책 모드 조회 |
| 클러스터 | TracingPolicyNamespaced | list | 전체 정책 상태 수집(`-A`) |
| 클러스터 | CRD `ciliumnetworkpolicies.cilium.io` 하나 | get | Cilium 설치 여부 |

**없어야 하는 권한(`FORBIDDEN`)**: 비밀값·ConfigMap 읽기, 서빙 Pod 안으로 exec, Pod·Deployment 삭제·생성, Tetragon Pod 삭제·daemonset 변경, 노드 조회, 권한 바인딩·namespace 생성, CRD 변경, 클러스터 전체 정책 생성. 와일드카드(`*`)는 쓰지 않는다.

## 3. 도구

```bash
# 권한 파일 만들기(검토용 예시: deploy/agent/runtime-agent-rbac.example.json)
.venv/bin/python -B -m tools.agent_rbac render --namespace serving-lab --tetragon-namespace kube-system > rbac.json
# 지금 쓰는 kubeconfig 점검
.venv/bin/python -B -m tools.agent_rbac check --context <ctx> --kubeconfig /etc/serving-runtime/kubeconfig
# 새 계정을 관리자 kubeconfig로 흉내 내 미리 점검
.venv/bin/python -B -m tools.agent_rbac check --context <ctx> --as system:serviceaccount:serving-lab:runtime-agent
```

| 결과 | 뜻 | 종료 코드 |
| --- | --- | --- |
| `ok` | 필요한 권한 모두 있음, 없어야 할 권한 없음 | 0 |
| `missing` | 필요한 권한 부족(기능 실패) | 1 |
| `unknown` | 확인 실패(연결 등). 원문은 출력하지 않음 | 1 |
| `too_broad` | 필요한 권한은 있지만 넘치는 권한이 있음 | 2 |

`kubectl auth can-i`에서 `pods/log`처럼 쓰면 "log라는 이름의 Pod"로 해석된다. 도구는 하위 자원을 `--subresource`로, 이름 제한 권한은 이름까지 넣어 묻는다(14회차 수동 점검의 `pods/log: yes`는 이 이유로 정확한 근거가 아니었다).

## 4. 로컬 kind 확인 (2026-11-09)

| 확인 | 결과 |
| --- | --- |
| 기존 관리자 kubeconfig | `too_broad`(없어야 할 14개 모두 허용) — 서버와 같은 상황 |
| 만든 권한 적용 후 계정 흉내 점검 | `ok`(필요 28개 yes, 금지 14개 no) |
| 같은 계정으로 실제 명령 | 정책 전체 목록, `tetra tp list` exec, Cilium CRD·정책 조회, server-side dry-run apply/replace, 엔진 로그, Gateway rollout status·port-forward·재시작 patch(dry-run) 모두 성공 |
| 금지 확인 | secrets(두 namespace)·nodes 조회, Pod 삭제 모두 Forbidden |

## 5. 서버에 적용하는 순서 (다음 서버 회차)

1. 관리자 kubeconfig로 `render` 결과를 검토한 뒤 `kubectl apply`.
2. `check --as system:serviceaccount:serving-lab:runtime-agent` → `ok` 확인.
3. 장기 토큰 Secret(`type: kubernetes.io/service-account-token`, annotation `kubernetes.io/service-account.name: runtime-agent`)을 만들고, 토큰과 클러스터 CA로 새 kubeconfig를 만든다. 토큰은 화면에 출력하지 않고 0600 파일로만 다룬다.
4. 기존 `/etc/serving-runtime/kubeconfig`를 0600 백업으로 보관하고, 설치 설정의 `KUBECONFIG_FILE`을 새 파일로 바꿔 설치기를 다시 실행한다(에이전트는 설치기가 켜지 않는다).
5. `check --kubeconfig /etc/serving-runtime/kubeconfig` → `ok`. 수집 서비스 상태·10번 dry-run·엔진 로그 수집이 그대로 되는지 확인한다.
6. 문제가 있으면 백업 kubeconfig로 되돌리고 설치기를 다시 실행한다.

## 6. 한계

- 사용자 서비스(`byul-tetragon-identities`, ubuntu 계정)는 범위 밖이다. 그 서비스는 서빙 Pod 조회와 Tetragon exec(`/proc` 스캔)를 쓴다.
- 묶음 적용(`bundle apply`)은 sudo로 root가 실행하지만 같은 kubeconfig를 쓰므로 위 권한 안에서 동작한다.
- Tetragon exec 권한은 Tetragon Pod 안에서 명령을 실행할 수 있는 강한 권한이다. 지금 구조(정책 모드 조회)에서는 필요하다. 줄이려면 Tetragon gRPC나 상태 API로 바꾸는 별도 설계가 필요하다.
