# 원격 적용·모드 전환 사용과 검증

현재 운영 서비스·CA·토큰 발급·LAB 표시 작업 기준은 `byul_runtime` / `57e8ad4`다(요청에 적힌 `c46b617`과 다름; 체크아웃 변경 없음). 아래 이전 인계의 커밋은 당시 기준이다. 이번 작업은 커밋·push하지 않았다. 설계 `설계_원격적용_모드전환.md` D1~D7 및 §6.1을 따른다. contracts/update는 수정하지 않는다.

## 1. 플랫폼 설정·권한

`BYUL_OPERATION_TOKENS`에는 다음 모양의 JSON 배열을 환경 변수로 주입한다. sha256 자리에는 실제 토큰의 SHA-256을 설정 관리 경로에서 넣는다. 원문 토큰은 터미널·로그·감사에 출력하지 않는다. §14의 발급 CLI는 설정에 넣을 해시 항목 JSON만 표준출력한다.

```json
[
  {"id":"operator-01","role":"runtime_operator","sha256":"<64자리 해시>"},
  {"id":"approver-01","role":"approver","sha256":"<다른 64자리 해시>"},
  {"id":"viewer-01","role":"viewer","sha256":"<다른 64자리 해시>"},
  {"id":"agent-01","role":"agent","server":"server-01","sha256":"<다른 64자리 해시>"}
]
```

토큰 ID는 개인 실명 대신 발급된 역할 식별자다. 서로 다른 사람에게 별도 ID를 발급해야 2인 확인의 의미가 있다. 같은 사람에게 다른 역할 토큰을 발급해 2인 승인을 우회해서는 안 된다. 해시는 상수 시간 비교, 중복 ID/해시 설정은 기동 실패다. 원문 토큰은 환경 변수에 두지 않고 클라이언트/에이전트의 전용 비밀 파일로 전달한다. 플랫폼 환경에는 해시만 둔다.

| 역할·요청 | 요청 | 승인 | 조회 | 임대·다운로드·결과 |
| --- | --- | --- | --- | --- |
| viewer | 거부 | 거부 | 새 운영 목록 허용 | 거부 |
| runtime_operator(관리자 토큰) | 허용 | 기본 거부, LAB 자기 요청만 | 허용 | 거부 |
| approver | 거부 | 요청자와 다른 ID | 허용 | 거부 |
| agent | 거부 | 거부 | 자기 서버만 | 자기 서버·임대 소유자만 |
| 인증 없음 | 새 API 401 | 401 | 기존 조회는 종전 동작, 새 API 401 | 401 |

| 요청 종류 | 승인 |
| --- | --- |
| bundle.apply | 별도 approver 필수 |
| tetragon.mode → enforce | 별도 approver 필수, 안전장치·Sigkill 확인 필수 |
| bundle.switch | 별도 승인 없이 approved, 에이전트는 기대 상태·묶음 재검증 |
| tetragon.mode → monitor | 별도 승인·차단 근거 없이 approved, 기대 상태·대상·허용 모드는 확인 |

`BYUL_OPERATION_LAB_SELF_APPROVAL=1`은 LAB 전용이다. 요청자의 자기 승인을 `self_approval: true`로 기록하고, 에이전트에도 `--lab-self-approval`을 명시해야 실행된다. 기본은 양쪽 모두 비허용이다. 운영에는 켜지 않는다. `BYUL_OPERATION_MONITOR_SECONDS` 기본 86400, 에이전트 최소 기간과 플랫폼 기간 중 큰 값을 사용한다. 영구 저장에는 기존 `PLATFORM_DATA_DIR`를 지정한다. 기존 조회 API·묶음 내보내기 API의 인증/행동은 변경하지 않았다. 플랫폼은 기존대로 루프백에서 기동하며 원격 접근은 별도 TLS 접근 경로가 필요하다.

## 2. API 예

Authorization 헤더는 토큰을 출력하지 않는 별도 HTTP 클라이언트의 비밀 설정으로 주입한다. 다음은 본문만의 예다.

```http
POST /api/runtime/operations
Content-Type: application/json

{"kind":"bundle.apply","server":"server-01","expected":{"bundle_id":"bundle-current","approval":"verified"},"policy_id":"policy-01","policy_revision":2,"environment_id":"env-01","environment_revision":1}
```

응답 ID에 대해 다른 승인자의 인증으로 `POST /api/runtime/operations/{id}/approve`와 `{}`를 보낸다. 에이전트는 `GET ...?server=server-01` → `POST .../{id}/claim {}` → `GET .../{id}/bundle` → `POST .../{id}/result`를 수행한다. 감사와 요청 목록은 `/runtime/operations`에서 토큰으로 조회한다.

```json
{"kind":"tetragon.mode","server":"server-01","expected":{"bundle_id":"bundle-current","approval":"verified","policy_id":"7","mode":"monitor","spec_sha256":"<정책 spec 해시>"},"policy_name":"runtime-tg-secret-01","mode":"enforce","confirmation":"ENGINE_RESTART"}
```

화면의 정책 판본 [적용 요청]은 선택한 CONFIRMED 정책/환경 판본과 서버 ID·기대 current를 전송한다. Tetragon [전환 조건 조회]는 에이전트의 최근 보고로 체크리스트를 표시한다. 차단 버튼에는 조건 전부와 `ENGINE_RESTART` 입력이 필요하다. 엔진 종료 → Gateway 503 → 재시작 경고를 표시한다. 서버의 기대 ID·모드·해시가 달라지면 다시 조회해 새 요청을 만든다.

## 3. 에이전트

```bash
cd runtime
.venv/bin/python -B -m serving_runtime agent \
  --platform-url https://platform.invalid \
  --ca-file /etc/serving-runtime/platform-ca.pem \
  --agent-token-file /etc/serving-runtime/agent.token \
  --server server-01 --bundle-root /srv/serving/bundles \
  --context lab-context --namespace serving \
  --kubeconfig /etc/serving-runtime/kubeconfig \
  --token-env-file /etc/serving-runtime/viewer.env \
  --state-file /var/lib/serving-runtime/tetragon-state.json \
  --review-file /var/lib/serving-runtime/monitor-review.json \
  --history-file /var/lib/serving-runtime/remote-transitions.jsonl \
  --lock-file /run/serving-runtime-agent/lock --once --dry-run
```

실행은 명시적으로 `--dry-run`을 `--execute`로 바꾼다. 기본도 dry-run이다. 조회 주기 기본 10초, 한 번에 한 건, 파일 잠금은 프로세스 전체에 유지한다. 원격 HTTP는 거부하며 로컬 통합용 루프백 HTTP만 허용한다. 리다이렉트로 토큰을 전달하지 않는다. agent.token은 root 또는 에이전트 계정 소유 일반 파일·0600이어야 한다. kubeconfig·Gateway 조회 토큰·플랫폼 토큰은 결과에 보고하지 않는다.

`--ca-file`은 선택이다. 미지정하면 시스템 기본 CA, 지정하면 해당 PEM의 CA만 신뢰한다(시스템 CA를 함께 더하지 않음). 인증서 체인·호스트명 검증은 항상 유지하며 검증을 끄는 옵션은 없다. 파일 누락·잘못된 PEM이면 기동 실패하며 원문 토큰·인증서 내용은 출력하지 않는다. 공인 CA 사용 시 위 인자를 생략한다.

에이전트의 `--status-url`은 생략하는 것이 기본이다. 실행 전·후 상태를 context/namespace/kubeconfig의 `deployment/serving-gateway`에 매번 새 port-forward를 열어 조회하며 연결 실패 시 재개설한다. 로컬 개발 Gateway를 의도적으로 조회할 때만 `--status-url http://127.0.0.1:PORT`를 명시한다. bundle apply 자체는 기존처럼 새 port-forward를 사용한다.

현재 묶음의 검증·Gateway 승인 verified·정책 활성, 새/기존 묶음의 해시·내부 파일·대상 참조·context/namespace, 플랫폼 승인과 기대 상태를 실행 직전에 다시 검사한다. apply는 원래 apply_bundle(새 복사/기존 폴더)과 상태 확인·되돌림을 사용한다. 모드는 로컬 tools/tetragon_mode.py의 동일 ID 전환·확인·되돌림을 사용한다. `--kubeconfig`는 모든 kubectl에 명시된다. 도구 경로는 서버 설정만 받으며 요청에서 실행 문자열을 받지 않는다.

`deploy/agent/serving-runtime-agent.service`, `sudoers.example`은 설치 예시이며 설치·활성화하지 않았다. 코드/Python 환경/설정은 root 소유로 설치하고 에이전트에는 묶음 조회용 그룹 10000을 준다. 특권 묶음 적용에는 `--sudo-bundle-apply`를 추가한다. sudoers는 고정 루트·context·namespace·설정 경로의 `bundle apply`만 허용하고 셸/다른 Python 명령/kubectl을 허용하지 않는다. set-mode는 에이전트 kubeconfig의 Kubernetes RBAC로만 수행한다. systemd 예시는 dry-run이며 실제 실행 전 sudoers 문법·정확한 경로·RBAC·파일 권한을 검수해야 한다.

## 4. intent·차단 근거

intent 1.1 선택 필드:

```json
{"tetragon_allowed_modes":{"TG-SECRET-01":["monitor","enforce"]},"tetragon_enforce_method":"override_lsm"}
```

위 값은 전체 intent의 일부다. 기존 protected_paths의 명시 파일 목록도 필요하다. 새 허용 집합에서 enforce를 쓰려면 명시 방식이 필요하고, 렌더는 차단 동작을 포함하되 초기 `policy-mode=monitor`다. monitor는 복귀를 위해 항상 허용해야 한다. 현재 enforce 지원 규칙은 TG-SECRET-01뿐이다. 기존 tetragon_rule_modes는 실제 MODE가 아닌 후보 능력 선언으로 하위 호환한다. 둘을 함께 쓰면 enforce 능력 선언이 같아야 한다. 필드가 없으면 기존 렌더 바이트는 같다. 실제 MODE는 서버 조회·전환 기록의 값이며 전환할 때 묶음을 다시 만들지 않는다.

| 체크 | 실행 직전 근거 |
| --- | --- |
| policy | enabled, monitor_only 아님, 실제 차단 방식, 현재 spec·ID·MODE |
| evidence | 실제 trial 재판정 passed, 동일 방식/spec SHA-256/노드 커널, combined 변형 |
| capability | live 커널/기능 재점검: available이면 static, unknown이면 evidence와 같은 동일 노드·커널·방식·spec의 real combined passed 근거로 live_trial. unavailable이면 근거가 있어도 거부 |
| monitor_period | 설정 기간, 연속 수집, 이벤트 수 0 또는 전부 검토·오탐 0, 최근 집계 |
| collection | 최신 정상 상태와 policies/writer/identities/events_verified 전부 true, 열린 공백 없음 |
| allowed_mode | 현재 검증된 intent의 해당 규칙 허용 집합에 enforce 포함 |

D7에 따라 시험 근거에 달력상 만료는 없고 방식/spec/커널 변경 시 재시험한다. 최신 상태·모니터 집계는 별도로 20~30초 freshness를 요구한다. 수집기는 기존 tetragon-state 생산자를 사용한다. 현재 set-mode 도구는 한 daemon에서 실행하므로 원격 enforce는 단일 노드로 제한한다. 다중 노드에 대해서는 안전하게 거부한다.

`--review-file`은 완전한 모니터 구간을 집계하고 사람이 검토한 서버 로컬 근거다. 요청 본문에서 근거·검토를 받지 않는다. 예:

```json
{"windows":[{"policy":"runtime-tg-secret-01","node":"node-01","method":"override_lsm","spec_sha256":"<64자리 해시>","kernel":"<실제 uname -r>","since":"2026-11-05T00:00:00+00:00","until":"2026-11-06T00:00:00+00:00","continuous":true,"event_count":2,"reviewed_event_count":2,"false_positive_count":0,"reviewer_token_id":"reviewer-01","events_sha256":"<구간 원본 해시>"}]}
```

모니터 구간·집계·원본 해시는 서버 운영자가 신뢰 가능한 완전한 자료로 만들어야 한다. 파일은 원자적으로 갱신하고 root/에이전트만 쓸 수 있게 설치한다. **이 변경은 구간 집계·검토 시스템 자체를 자동 생성하지 않는다.** 파일/연속성/집계가 없거나 오래됐으면 차단을 거부한다. 정적 분류는 그대로 두고, unknown인 Sigkill/fmodret 후보는 evidence와 같은 실측 근거가 있으면 차단 능력을 `live_trial`로 확인한다. `unavailable`은 실측 근거가 있어도 거부한다. 준비 상태 결과의 `capability_basis`(static/live_trial)와 `capability_reason`을 플랫폼 API가 보존하며 화면에 '확인: 실측 시험으로 확인' 또는 거부 사유를 표시한다. API·웹은 같은 6개 checks를 모두 요구한다.

## 5. 검증·Claude kind 인계

자동 시험:

```bash
cd runtime
TMPDIR=/dev/shm .venv/bin/python -B -m unittest discover -s tests
cd ../platform/web
npm run typecheck && npm test
cd ../api
uv run --frozen --with-editable ../../update --with-editable ../../runtime python -m pytest -q
```

새 API 통합 시험 `tests/test_operations.py::test_platform_agent_apply_temporary_gateway_verified`: 실제 export → 요청/다른 토큰 승인 → agent 조회/임대/다운로드 → 실제 apply_bundle 복사/링크 → 임시 Gateway 승인 verified를 검증한다. Kubernetes rollout/chown만 시험 더블이다. gateway-core는 Gateway 객체의 실제 승인 투영을 소켓 없이 확인하고, gateway-http는 실제 임시 HTTP listener를 열어 확인한다(로컬 소켓 금지 환경에서는 명시 skip). kind/GPU를 대신하는 실증은 아니다.

Claude가 소켓 허용 환경에서 위 시험 전체를 다시 실행하고, kind에서는 다음을 수행한다. 이 작업에서는 kind·실서버·GPU를 실행하지 않는다.

1. 별도 시험 namespace에 기존 LAB 배포·시험용 Pod를 준비한다. 기존 kind 설명서 `docs/상세_안내.md`의 설치/전제 조건과 `tools/k8s_lab_check.py --help`, `tools/tetragon_trial.py --help`를 확인한다. 실제 context/namespace에 맞춘 묶음 루트·current·Gateway 조회를 준비한다.
2. **kind 에이전트 준비:** root 컨테이너로 실행하면 플랫폼 토큰 파일도 **root 소유·0600**이어야 한다(`PlatformClient`는 root 또는 실행 UID 소유만 허용). 호스트 일반 사용자 소유 파일을 그대로 mount하면 root 실행에서 거부될 수 있다. 컨테이너 내부의 비밀 파일을 root 소유로 설치하고 원문을 출력하지 않는다.

   kind의 현재/복귀 후보는 `bundle build`로 생성한 **4역할**(`gateway_policy`, `policy_approvals`, `target`, `enforcement_intent`) 묶음이어야 한다. 구형 2역할 리허설 묶음은 원격 에이전트에서 거부한다. 서버 값 파일의 `target.kubernetes.context`/`namespace`가 에이전트 설정(예: `kind-runtime-lab`/`serving-rehearsal`)과 같아야 하며, target_ref와 intent의 대상도 일치해야 한다. CONFIRMED 원본 정책·정규 JSON SHA-256·서버 값·intent를 준비한 뒤:

   ```bash
   cd runtime
   remote_kind_policy_sha256=$(.venv/bin/python -B -c 'import hashlib,json,sys; print(hashlib.sha256(json.dumps(json.load(open(sys.argv[1])), ensure_ascii=False, sort_keys=True, separators=(",", ":")).encode()).hexdigest())' /tmp/remote-kind/policy.json)
   .venv/bin/python -B -m serving_runtime bundle build \
     --policy /tmp/remote-kind/policy.json \
     --policy-sha256 "$remote_kind_policy_sha256" \
     --server-values /tmp/remote-kind/server-values.json \
     --intent /tmp/remote-kind/intent.json \
     --output-parent /tmp/remote-kind/built --bundle-id rehearsal-v2
   .venv/bin/python -B -m serving_runtime bundle verify \
     --bundle-dir /tmp/remote-kind/built/rehearsal-v2
   ```

   `--policy`에는 approval 요약이 아닌 `byul-policy/0.1` CONFIRMED 원본을 준다. 위 해시는 원본 객체를 UTF-8, `ensure_ascii=False, sort_keys=True, separators=(",", ":")`로 직렬화해 계산한다. 생성된 폴더를 kind 노드의 실제 bundle-root 볼륨에 root:10000·폴더 0750/파일 0640으로 배치하고 current 상대 링크 및 Gateway의 같은 볼륨 mount를 맞춘다. 기존 초기 배치 절차로 Gateway를 재시작해 해당 묶음의 verified를 확인한다. 복귀 후보도 서로 다른 묶음 ID로 같은 절차를 따른다. 호스트 개발용 8080이나 오래된 고정 port-forward를 에이전트 기본 상태 조회로 사용하지 않는다.

## 8. kind 지적 보완: 세부 사유와 위험

기존 `Result.code`는 유지하며 선택 `reason_code`를 추가했다. 이전 결과·클라이언트도 그대로 처리할 수 있고, 자유 형식 예외·경로·주소·토큰은 전송하지 않는다.

| reason_code | 의미 | 대표 기존 code |
| --- | --- | --- |
| BUNDLE_ROLES_MISSING | 에이전트 필수 4역할 누락 | VALIDATION_FAILED |
| BUNDLE_INVALID | 묶음 구조·해시·내용·ID 또는 intent 검증 실패 | VALIDATION_FAILED |
| CURRENT_LINK_INVALID | 현재 적용 묶음 링크·대상이 안전한 폴더가 아님 | VALIDATION_FAILED |
| STATUS_UNREACHABLE | 새 port-forward/상태 조회 재시도 후 연결 불가 | VALIDATION_FAILED, 실행 후 STATUS_UNKNOWN |
| STATUS_MISMATCH | Gateway 묶음 ID·해시·verified·활성 상태 불일치 | STATE_CHANGED 또는 필드 손상 시 VALIDATION_FAILED |

실행이 시작된 뒤의 실패는 기존 unknown/STATUS_UNKNOWN 규칙을 유지한다. 에이전트 계정이 탈취되면 공격자가 계정의 kubeconfig·조회 토큰과 허용된 root 적용 경로를 악용해 임의 묶음을 적용할 위험이 있다. 4역할·해시 검증은 서명이나 독립된 발행자 인증이 아니다. root로 에이전트 전체를 실행하면 이 위험 범위가 더 크므로 격리된 kind 시험에만 사용하고, 운영에서는 전용 계정·고정 sudoers·root 소유 코드/설정·제한 RBAC를 검수해야 한다.

## 9. 운영 요청 화면 보완

- 상단에 저장된 운영 토큰의 현재 역할·역할 ID와 [토큰 지우기]를 표시한다. 최초에는 password 입력 후 [토큰 저장]을 누른다. sessionStorage는 같은 탭 세션의 화면 이동/새로고침에 유지하고, 접근 실패 시 메모리만 사용한다. 값은 저장 후 입력에서 지우며 결과·감사에 넣지 않는다. 정책 판본 적용/Tetragon 전환/운영 목록이 같은 세션 토큰을 공유한다.
- 토큰이 있으면 진입 시 목록을 자동 조회한다. 목록은 종류·대상 서버, 요청됨→승인→가져감→실행→결과, 현재 상태, 요청/승인 역할 ID, 시각, 결과 코드·세부 사유, 증거 SHA-256을 표시한다. 상태 필터와 행/요청 버튼으로 상세를 열고 전후 묶음·단계·승인 시각을 확인한다. dry-run 검증 통과는 state=checked/code=DRY_RUN으로 기록하며 화면·필터에 '실행 없이 확인 완료', 진행 단계에 실행 생략·결과 완료를 표시한다. 검증 실패는 failed와 해당 사유를 유지한다.
- 서버별 마지막 조회·상태 보고·현재 적용 묶음을 표시한다. 플랫폼에 등록됐으나 아직 조회하지 않은 에이전트도 '미확인'으로 표시한다. [운영 요청 조회]로 최신 결과를 갱신한다.
- 운영 요청자만 [이전 묶음으로 되돌리기]를 열 수 있다. `/agent-state`로 보고된 서버·현재 적용 묶음을 자동 채우고, 같은 대상의 검증된 4역할 묶음 목록에서 선택한다. 정상 화면은 최근 30초 내 보고를 요구한다. 목록이 없는 구형 에이전트는 갱신 안내를 표시하며 직접 입력은 [고급] 안에만 있다. 기대 현재 상태는 서버에서 실행 직전에 다시 검증한다.
- 승인 대기는 승인자 역할에 [승인]을 표시한다. 자기 요청은 기본 비활성이다. LAB 자기 승인 설정일 때는 표시와 함께 자기 승인을 허용하고, 운영 요청자는 자신의 요청에만 버튼이 나타난다. 최종 권한/자기 승인 판정은 API·에이전트가 유지한다.

내부 형식 추가: Result의 선택 `reason_code`, agent-state의 선택 `bundles: [{bundle_id, sha256}]`(기본 빈 목록, 최대 256), 목록의 `actor: {id, role}` 및 등록 서버 자리, 요청의 `claimed_at`/`running_at`. 기존 필드와 결과 코드는 유지한다. 공용 contracts/update는 변경하지 않았다. 묶음 목록은 마지막 보고 시점 자료이며 삭제·만료·외부 변경은 실행 전 재검증에서 거부한다. 실행 직후 current 보고는 다음 에이전트 조회 주기(기본 10초)에 갱신되므로 `--once` 실제 적용 뒤에는 조회용 에이전트를 한 번 더 실행한다. 고급 입력도 서버 검증을 우회하지 않는다.

## 11. 모니터 기록 생성·사람 검토

생성기는 기존 `tools.tetragon_status`와 Gateway가 같은 context/namespace에 대해 기록 중인 상태·실제 관측을 읽는다. status는 expected-policies·identities·feed-heartbeat·observations를 지정해 복구 4조건이 healthy여야 한다. stream 원문은 직접 입력하지 않는다. Gateway의 `--observation-feed tetragon=...`와 `--tetragon-identities ...`로 `confirmed` 귀속을 수행한 `observations.jsonl`을 사용한다.

에이전트와 같은 전용 UID 또는 root로 실행한다. 출력은 root 또는 에이전트 UID 소유, 정확히 0600이어야 한다. root로 실행하는 kind 에이전트에 일반 사용자 소유 파일을 mount하면 거부되므로 생성기도 해당 격리 환경 안에서 root로 실행하거나 실행 계정을 일치시킨다. 운영에서 에이전트 전체를 root로 실행하라는 뜻은 아니다. 입력·부모 폴더는 신뢰 가능한 계정만 수정할 수 있어야 하며 관측/상태 입력에 group/world 쓰기 권한이 있으면 생성기가 거부한다.

```bash
cd runtime
.venv/bin/python -B -m tools.tetragon_monitor_window \
  --context kind-runtime-lab --namespace serving-lab \
  --policy runtime-tg-secret-01 \
  --status /tmp/monitor-example/tetragon-state.json \
  --observations /tmp/monitor-example/observations.jsonl \
  --reviews /tmp/monitor-example/human-reviews.json \
  --output /tmp/monitor-example/monitor-windows.json --watch
```

주기 기본값은 5초(`--interval`, 1~20초). `--policy`는 여러 번 지정할 수 있다. `--watch` 없이 한 번 실행하면 현재 정상 상태부터 길이 0인 창을 만든다. 기간을 축적하려면 계속 실행한다. 프로세스를 다시 시작하면 연속성 입증이 끊겼으므로 새 창이다. 에이전트의 기존 실행 인자에 `--review-file /tmp/monitor-example/monitor-windows.json`을 추가한다. 기본 24시간 등 플랫폼·에이전트의 최소 모니터 기간은 그대로 적용되며 kind에서 짧은 기간을 쓰려면 양쪽 LAB 설정을 명시해야 한다.

출력은 `windows`와 별도의 `monitor-windows.json.events.json`(기본 catalog)이다. catalog는 사람이 이벤트 내용을 확인하는 로컬 파일이며 agent-state에 원문을 전송하지 않는다. 검토 절차:

1. catalog의 해당 정책·노드·창 시작을 확인하고, 각 `events[].event`의 실제 대상·행동·시각을 검토한다.
2. 해당 `event_sha256`을 아래 별도 파일에 복사하고 사람이 직접 verdict를 적는다. `reviewer_token_id`는 발급된 검토자 토큰의 ID이며 토큰 원문이 아니다. 도구는 검토 파일·verdict·검토자 ID를 생성하지 않는다.
3. 사람이 저장한 검토 파일을 같은 디렉터리의 임시 파일로 작성하고 0600으로 설정한 뒤 rename한다. 편집 중인 손상 파일을 읽으면 검토가 0건이 된다.
4. 다음 생성 주기와 에이전트 상태 보고 뒤 화면에서 `총건수·검토 n/전체·오탐·창 시작·마지막 확인`을 확인한다. 새 이벤트는 미검토로 남으며, 오탐 1건 이상 또는 검토 누락은 enforce 조건을 통과하지 못한다. 검토 변경은 운영 요청 승인과 별개이며 approver의 별도 승인을 대체하지 않는다.

```json
{
  "reviewer_token_id": "reviewer-01",
  "events": [
    {"event_sha256": "<catalog에서 사람이 확인한 이벤트의 64자리 해시>", "verdict": "not_false_positive"},
    {"event_sha256": "<다른 이벤트의 64자리 해시>", "verdict": "false_positive"}
  ]
}
```

이 예시의 자리값은 실제 유효 해시가 아니며 자동 승인 자료로 사용하지 않는다. 동일 해시 중복·잘못된 verdict/검토자 ID·파일 오류는 전체 검토를 무효로 처리한다. 한 파일은 한 검토자 ID를 사용하며, 다른 창·정책 ID/spec/method/kernel로 바뀌면 과거 검토 해시는 승계되지 않는다. 이벤트 0건인 정상 연속 창은 사람 검토 없이도 기간 조건만 통과할 수 있다. 나머지 5개 안전 조건은 별도다.

개발 스크립트 opt-in 예시(기존 stream·identity·baseline 설정을 함께 제공):

```bash
RUNTIME_TETRAGON_STATE=1 \
RUNTIME_TETRAGON_MONITOR_WINDOW=1 \
RUNTIME_TETRAGON_MONITOR_POLICIES=runtime-tg-secret-01 \
RUNTIME_TETRAGON_MONITOR_REVIEWS=/tmp/monitor-example/human-reviews.json \
platform/scripts/run-with-runtime.sh
```

기본 출력은 `$RUNTIME_DATA_DIR/tetragon-monitor-windows.json`이며 `RUNTIME_TETRAGON_MONITOR_OUTPUT`으로 바꿀 수 있다. 스크립트는 에이전트를 자동 실행하지 않는다. 별도 에이전트의 `--review-file`을 같은 파일로 지정하고 계정/권한을 맞춘다. 필요한 수집·복구 설정이 없으면 빈 windows를 갱신한다.

창 계산의 정확한 경계·해시·공백 처리는 설계 §6.1 표를 따른다. status 신선도는 20초, safety `until`은 30초이며 단순 파일 재읽기로 시간을 늘리지 않는다. 미검토·오탐이 해결돼도 기간이 부족하면 계속 거부한다. 관측 저장소는 최대 64 MiB 전체 읽기, 상태/검토 파일은 각 2 MiB 제한이다. 초과·손상·읽기 불가 때 창을 비우고, 저장소 보존 정리/교체/절단 시 새 창부터 시작한다. 대용량 증분 처리와 재기동 후 창 복원은 아직 제공하지 않는다. 로컬 파일 신뢰에 기반하며 사람 검토의 암호학적 서명/플랫폼 검토자 인증은 제공하지 않는다.

## 14. 운영 배치: 수집기·HTTPS·토큰

### 수집기 systemd 설치 예시

반복 설치에는 [노드 설치기](../deploy/install/README.md)를 사용할 수 있다. 설정 파일 하나로 계정·root 소유 코드·설정 권한·sudoers·세 단위·공유 폴더·최초 baseline을 준비하며, `--dry-run`은 클러스터 조회 없이 호스트 사전 점검만 수행한다. 사용자 단위 수집기는 별도 설치 안내를 따른다.

`deploy/agent/`의 세 단위를 함께 설치한다. 아래는 서버 운영자가 실행할 예시이며 이번 작업에서는 설치·시작하지 않았다. `lab-context`/`serving`, 서버 ID·모든 경로를 실제 배치에 맞춘다. 상태 수집기는 context 내 전체 정책을 읽으므로 namespace 인자가 없고 모니터 생성기·에이전트에 namespace를 지정한다.

전제: root 소유·runtime-agent 쓰기 불가인 `/opt/byul/runtime`와 Python 환경, `kubectl` 실행 경로, `/etc/serving-runtime/kubeconfig` 및 RBAC를 준비한다. kubeconfig는 홈 디렉터리 참조 없이 인증서를 포함하거나 `/etc/serving-runtime`의 읽기 가능한 파일을 참조해야 한다(`ProtectHome=true`). 상태 수집에는 Tetragon Pod/정책 조회 및 Pod exec를 통한 tetra 조회 권한이 필요하며, set-mode 권한은 에이전트의 기존 RBAC 범위를 따른다.

Gateway 데이터 그룹 10000과 관측 그룹 10010(`serving-observe`)이 존재해야 한다. `deploy/gpu-lab/README.md`의 식별 수집·sentinel·생존 기록 배치를 먼저 완료한다. 그룹 번호가 기존 다른 그룹과 충돌하면 그대로 설치하지 않고 배치 그룹을 맞춘다.

```bash
sudo usermod -aG 10000,10010 runtime-agent
sudo install -d -o runtime-agent -g runtime-agent -m 0750 /var/lib/serving-runtime
sudo install -d -o runtime-agent -g runtime-agent -m 0750 /var/lib/serving-runtime/evidence
sudo chmod 0750 /srv/serving/runtime/data
sudo chgrp 10000 /srv/serving/runtime/data
```

`/srv/serving/observation`은 기존 신뢰하는 호스트 수집기 계정 소유·GID 10010·2750, 식별 자료는 0640·10010, Gateway 관측 폴더는 UID 10000·GID 10000·0750으로 유지한다. 입력 파일에 그룹/기타 쓰기 권한을 주지 않는다. 모든 상위 폴더에도 그룹 탐색 권한이 필요하다. `id -G runtime-agent`와 실제 계정의 `test -r`로 kubeconfig·식별 자료·생존 기록·관측 JSONL 읽기를 확인한다. 단위의 `SupplementaryGroups=10000 10010`은 서비스 재시작 시 적용된다.

최초 baseline은 **정상 정책의 spec·모드를 사람이 확인한 뒤 한 번만** 캡처한다. 아직 baseline이 없으므로 이 명령에는 `--expected-policies` 등 복구 입력과 `--watch`를 넣지 않는다. 기존 수집기·수동 실행은 중지한 상태에서 실행한다.

```bash
cd /opt/byul/runtime
sudo -u runtime-agent env KUBECONFIG=/etc/serving-runtime/kubeconfig \
  .venv/bin/python -B -m tools.tetragon_status \
  --context lab-context --evidence-dir /var/lib/serving-runtime/evidence \
  --output /var/lib/serving-runtime/tetragon-state.json \
  --capture-baseline /var/lib/serving-runtime/baseline.json
```

종료 코드 0과 baseline의 context·정책 범위·mode·spec을 확인한다. baseline/상태는 0644, recovery/monitor-review/catalog는 0600이다. baseline을 부팅마다 자동 캡처하거나 실패한 정책을 새 정상값으로 덮어쓰지 않는다. 의도한 정책 변경은 별도 검토 후 서비스 중지 상태에서 재캡처하며, 모니터 창은 다시 누적한다. 실측 근거는 같은 evidence 폴더에 기존 절차로 배치한다.

설치용 사본의 자리값과 `agent.env`의 `PLATFORM_URL`, 비밀 파일·CA 경로를 맞춘 뒤:

```bash
cd /opt/byul/runtime/deploy/agent
sudo install -m 0644 serving-runtime-tetragon-status.service serving-runtime-monitor-window.service serving-runtime-agent.service /etc/systemd/system/
sudo systemd-analyze verify /etc/systemd/system/serving-runtime-tetragon-status.service /etc/systemd/system/serving-runtime-monitor-window.service /etc/systemd/system/serving-runtime-agent.service
sudo systemctl daemon-reload
sudo systemctl enable --now serving-runtime-tetragon-status.service serving-runtime-monitor-window.service serving-runtime-agent.service
```

기존 agent 서비스가 실행 중이면 위 명령만으로 변경된 시작 인자가 적용되지 않으므로 설치 작업 중 세 서비스를 중지한 뒤 다시 시작한다. sudoers는 기존 `visudo` 검증 절차를 따르며 예시의 `--dry-run`은 실제 운영 실행 검수 후에만 `--execute`로 바꾼다.

순서는 status → monitor-window → agent다(`After`/`Wants`). 이는 프로세스 시작 순서이며 정상 수집을 기다리는 준비 완료 신호가 아니다. 상태/모니터 창 누락·오래됨·잘못된 권한이면 기존 안전 조건이 차단 전환을 거부한다. 수집기 재시작 시 모니터 연속 창은 새로 시작한다. 각 단위는 runtime-agent·UMask 0022·PrivateTmp·ProtectHome·ProtectSystem strict, 쓰기는 `/var/lib/serving-runtime`만 허용하고 실패 시 재시작한다. sudo가 필요한 에이전트와 달리 수집기는 `NoNewPrivileges=true`다. UMask와 별개로 파일 생산자가 정한 0644/0600을 유지한다.

검증은 `systemctl is-active`로 세 프로세스, `stat -c '%a %U %G %n'`으로 출력 권한을 확인한다. 상태 JSON의 최신 generated_at·monitoring healthy·복구 네 조건, monitor-review의 state ok·continuous 및 증가하는 창을 확인한 뒤 에이전트 dry-run 결과를 조회한다. `journalctl -u serving-runtime-tetragon-status -u serving-runtime-monitor-window -u serving-runtime-agent`에서 시작 오류를 확인하되 토큰 파일 내용이나 환경 전체를 출력하지 않는다. sentinel 중단 등 관측 불가 때는 readiness가 거부되는지 별도 점검한다.

### 운영 토큰 발급·회전·폐기

발급은 플랫폼 API Python 환경에서 수행한다. 부모 폴더는 신뢰하는 운영자만 쓸 수 있게 미리 준비한다. 다음 명령은 원문을 stdout에 쓰지 않고, 지정한 **새 0600 파일**에만 저장한다. stdout에는 `BYUL_OPERATION_TOKENS` 배열에 추가할 해시 항목 객체 하나가 나온다.

```bash
cd platform/api
uv run --frozen python -m byul_platform.operation_tokens new \
  --id agent-01 --role agent --server server-01 \
  --token-file /secure/operation-tokens/agent-01.token
```

`--role`은 viewer/runtime_operator/approver/agent 중 하나다. `--server`는 agent에서 필수이며 다른 역할에서는 거부한다(다른 역할에 서버 제한이 적용되는 것으로 오해하지 않도록 함). ID는 실명이 아닌 역할 식별자다. 기존 파일·디렉터리·심볼릭 링크는 덮어쓰지 않는다. 쓰기 실패 시 해시 항목을 출력하지 않으며 불완전한 0600 파일이 남을 수 있으므로 운영자가 확인·폐기하고 새 경로로 다시 발급한다. 토큰 값은 `cat`, 셸 변수, 명령행 인자나 로그에 넣지 않는다. 에이전트 서버에 비밀 전달 경로로 배치한 agent.token은 root 또는 runtime-agent 소유 0600으로 유지한다. 플랫폼에는 원문을 복사하지 않고 해시만 등록한다.

회전은 새 ID·새 파일로 발급 → 새 해시 항목을 기존 JSON 배열에 추가 → 플랫폼 재시작 → 클라이언트 비밀 파일 교체·에이전트 재시작·인증 확인 → 구 해시 항목 제거·플랫폼 재시작 순서다. 중복 ID/해시는 기존 검증이 기동을 거부하므로 사용하지 않는다. 즉시 폐기는 해당 해시 항목을 제거하고 플랫폼을 재시작한다. 이미 진행 중인 요청의 중단까지 보장하지는 않으므로 실행 상태도 확인한다. 구 원문 파일·배포본도 비밀 관리 경로에서 폐기한다.

### 권장 연결: TLS 프록시 → loopback 플랫폼

플랫폼은 `127.0.0.1:8700`에 유지하고 앞단 TLS 프록시만 HTTPS로 노출한다. 프록시는 Authorization 헤더를 API로 전달하고 헤더/본문·토큰을 access/error 로그에 기록하지 않는다. 다음 nginx 조각은 설치 파일이 아닌 예시다. 인증서·개인키·DNS·접근 범위는 해당 운영 환경에서 관리한다.

```nginx
server {
    listen 443 ssl;
    server_name platform.example.invalid;
    ssl_certificate /etc/platform-tls/fullchain.pem;
    ssl_certificate_key /etc/platform-tls/private.key;
    location / {
        proxy_pass http://127.0.0.1:8700;
        proxy_set_header Host $host;
        proxy_set_header Authorization $http_authorization;
        proxy_set_header X-Forwarded-Proto https;
    }
}
```

에이전트는 `--platform-url https://platform.example.invalid --ca-file /etc/serving-runtime/platform-ca.pem`을 사용한다. systemd 예시 ExecStart에 CA 인자를 추가하고 root 소유·에이전트 읽기 전용 CA PEM을 배치한다. 공인 CA면 `--ca-file`을 생략한다. SSH 역방향 터널은 LAB 연결 이력이며 이 구성의 필수 요소가 아니다. 기존 조회 API·내보내기 API 전체에 새 인증이 추가되는 것은 아니므로 프록시 접근 범위/접근 인증도 운영 환경에 맞춰 정한다.

## 15. LAB 전용 값과 운영 기본값

| 항목 | 운영 기본/배포 예시 | LAB에서만 명시적으로 변경 |
| --- | --- | --- |
| 플랫폼 모니터 기간 | `BYUL_OPERATION_MONITOR_SECONDS` 미지정 = 86400초 | `BYUL_OPERATION_MONITOR_SECONDS=60` |
| 에이전트 최소 모니터 기간 | `--monitor-seconds` 생략 = 86400초 | `--monitor-seconds 60` (양쪽 기간 중 큰 값 적용) |
| 플랫폼 자기 승인 | `BYUL_OPERATION_LAB_SELF_APPROVAL` 미지정 = 비허용 | `BYUL_OPERATION_LAB_SELF_APPROVAL=1` |
| 에이전트 자기 승인 | `--lab-self-approval` 없음 = 비허용 | `--lab-self-approval` (양쪽 opt-in 필요) |
| 연결 경로 | HTTPS, 사설 CA라면 `--ca-file` | 로컬 통합의 loopback HTTP·SSH 역방향 터널 |

에이전트 systemd/sudoers 예시는 기간 축소·자기 승인 인자를 포함하지 않는다. 운영 요청 화면과 Tetragon 전환 카드 상단은 인증된 기존 operations 목록 응답의 monitor_seconds/lab_self_approval을 사용해, 기간이 86400초보다 짧거나 자기 승인이 켜졌을 때 `LAB 설정: 모니터 기간 60초 · 자기 승인 허용` 같은 경고 배지를 표시한다. 기본 운영값 또는 더 긴 기간·자기 승인 비허용이면 표시하지 않는다. 전환 카드는 [전환 조건 조회] 후 확인할 수 있다. 이 표시는 플랫폼 설정이며 에이전트의 현지 설정을 대신 검증하지 않는다. API 응답·contracts 변경은 필요 없다.
