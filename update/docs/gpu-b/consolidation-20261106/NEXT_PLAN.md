## 2. 환경 없이 진행할 도구 개발

- SUP-16: 실제 기록기의 LF 계약 수정 결과를 재사용한다. native 미확인8은 별도 사실·소유권/whole-run/worker/producer 근거의 공백으로 다루고, writer 성공으로 채우지 않는다. 새 구현은 이미 있는 수집·소비 경로의 실제 누락에 한정한다(세션1, 필요 공통 계약은 외부 개발26).
- SUP-05: 85초 stack의 vLLM import·torchcodec entry-point·관측 profile Path frame과 원90초 초과를 분리한다. 설치판 source와 기존 raw로 가설을 먼저 좁히고, source 또는 실행 조건의 검증 가능한 차이가 없으면 같은 모델/기한으로 재실행하지 않는다. 관측 overhead·자원 경합의 기여를 단일 stack으로 단정하지 않는다(세션5/6, 실행 배정 세션2).
- SUP-15: cold1회38.374초 성공과 기존 warm45초 alive 원인을 분리한다. stack/atexit가 없는 과거 원인 공백을 코드 해시 동일만으로 해소하지 않는다. 새 관측이 필요한 분기만 한정 배정한다(세션1/2/3).
- `byul/runtime`의 mock backend, 입력 validator, 기존 schema·enum·상태/원자료 구분을 참고한다. LAB run/policy/target ID·프롬프트·로컬 경로·예제 정책 임계값은 시험 입력으로 만들 수 있다. runtime 예제의 출력128/context2048/body65536은 운영 승인값이 아니다. `observation_origin=synthetic`와 실측 `real`을 구분하며, runtime 내부 기록을 update의 EVD/RES/RPT와 같은 객체로 간주하지 않는다.
- 실제 producer 함수가 만든 정상·미지원 출력을 기존 consumer에 넣어 계약을 확인한다. 수작업 양성 JSON이나 새 enum으로 지원을 가장하지 않는다. 공통 구현이 실제로 없는 부분만 외부 개발26 반환물로 한정한다.

## 3. 다음 실측 묶음

세션1은 기존 고정 준비본에서 같은 source·image·model·기동 조건을 공유하는 실행 가능한 분기를 추린다. 세션2는 현재 승인된 자원·비용·원 기한 안에서 실행을 배정한다. 상태 변경·재시작·정상/도전의 신원이 섞이면 별도 엔진/세션을 사용한다. 현재 고정 실행의 입력을 hot-swap하지 않는다.

GPU와 독립 CPU는 자원 충돌이 없을 때 병행한다. CPU 준비를 기다리며 GPU를 켜두지 않는다. 필수 변경 검토가 끝난 실행을 추가 요약문·중복 archive 검증·전체 suite·새 사람 승인 때문에 지연시키지 않는다. 새 입력·공통 계약·TP2·비용/기한 확대가 필요한 분기는 별도 조건으로 남긴다.
