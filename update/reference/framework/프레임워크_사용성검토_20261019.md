# 서빙엔진 보안 프레임워크 사용성·완결성 검토

작성 2026-10-19 · 대상 `serving-security-framework-20261018/` (README, 01~05, 검수기록, `select_checklist.py`, `data/*.json`) · 원본은 수정하지 않았다.

**이번 검토의 범위.** 읽기 편한지, 흐름이 맞는지, 빠진 것이 없는지, 문서끼리 어긋나지 않는지를 봤다. vLLM 코드 근거의 정확성은 기존 `프레임워크_독립검증보고서_v2`와 `검수기록.md`의 외부 검토 반영 내용을 전제로 하고 다시 대조하지 않았다. 엔진·GPU 시험은 하지 않았다.

## 한 줄 총평

뼈대는 탄탄하다. 5개 영역 → 보호 목적 28개 → 세부 점검 77행 → 시나리오 83개 → 근거 Q 28개로 추적이 이어지고, 77행이 모두 같은 틀(적용 조건·위험·확인 방법·정상 대조·시험 순서·증거·미충족·미확인·충족)로 쓰여 있어 실무에서 바로 따라 할 수 있다. 아쉬운 점은 내용이 아니라 **포장**이다. 지금 쓸 수 있는 부분, 계획 단계인 부분, 작업 이력이 한 문서 안에 섞여 있어 처음 여는 사람이 길을 잃기 쉽고, 같은 개념에 이름이 여러 개 붙어 있다. 빠진 것은 우선순위, 도식, 범위 밖 명시, 용어집, 끝에서 끝까지 걷는 예시다.

## 1. 확인해서 문제가 없었던 것

- 문서 안 내부 링크의 앵커를 전수 검사했다. 깨진 앵커는 0개다. 상단 내비게이션 줄과 "바로 찾기" 목차도 모든 문서에 있다.

- 77행 전부에 핵심 필드 11개가 있고 빠진 행이 없다. 정상 대조·증거·시험 순서는 행마다 다르게 쓰여 있어 복사 붙여넣기 흔적이 거의 없다.
- 판정 규칙(충족/미충족/미확인/해당 없음, 하위에서 상위로 집계)이 01, 03, 05에서 서로 모순 없이 반복된다.
- `select_checklist.py`가 템플릿으로 정상 실행되고, 입력이 부족한 항목은 "미확인"으로 남긴다.

## 3. 흐름이 잘 되어 있는가

README가 제시한 순서(01 개요 → 02 환경 → 03 점검 → 05 시험·판정, 04는 엔진이 다를 때)는 논리적이다. 다만 아래가 흐름을 끊는다.

- **파일 번호와 사용 순서가 다르다.** 번호는 01~05인데 쓰는 순서는 02 → 03 → 05이고 04는 선택이다. 문서 상단 내비게이션은 번호순이라 이 순서를 알려주지 않는다. 각 문서 머리에 "사용 단계 N/3"처럼 위치를 표시하고 04에 "엔진·버전이 바뀔 때 보는 참고" 표지를 달면 된다.
- **02의 중간에 정책 절이 끼어 있다.** 환경을 고르는 흐름(조건 → 앱 신원 → 선택 → 판단 → 예시) 한가운데 "채택한 팀 기준" 절이 있는데, 실제 내용은 03 링크표뿐이다. 한 줄 안내로 줄여도 된다.
- **같은 단위를 부르는 이름이 여러 개다.**

| 단위 | 지금 쓰이는 이름 |
| --- | --- |
| 28개 | 상위 질문(11회) · 보호 목적(25회) · 보호 요구(339회, 일부는 POL을 뜻함) |
| 77개 | 세부 점검(23회) · 하위 시험(84회) · 시험 초점(86회) |
| Q 28개 | 평가 질문(111회) · 평가 기록 · 기존 Q |

05 §4의 "상위 질문은 적용 하위 시험 중 미충족이 하나라도 있으면…"은 28개 보호 목적의 집계인지 Q의 집계인지 읽는 사람이 판단해야 한다. 제안은 **영역(5) → 보호 목적(28) → 세부 점검(77) → 시험(시나리오 연결)** 네 단계로 이름을 고정하고, Q는 "근거 ID"로만 부르는 것이다. 이 매핑을 용어집 한 장에 두면 된다.

- **ID 체계가 흩어져 있다.** R·AS·POL·TB·SURF·SC·Q는 01에 한 문장으로 설명되어 있지만, B-SURF·F·P0는 정의 없이 쓰인다. 용어집(README 또는 01 상단)을 권한다.
- **끝에서 끝까지 걷는 예시가 없다.** 05에 Q-R05-04 시험 예시가 하나 있을 뿐이다. 환경 JSON 작성 → selector 실행 → 77행 중 점검 선택 → 시험 → `result_template.json` 기록 → 판정·보고까지 참조 구성의 한 항목(예: 직통 route 인증 시험)으로 한 번 보여주면 처음 쓰는 사람의 이해가 크게 빨라진다.

## 4. 빠진 것

중요도 순이다. 앞의 세 가지를 우선 권한다.

1. **우선순위가 없다.** 문서에서 시나리오 83개와 점검 77행이 모두 같은 무게로 놓여 있다. `checklist.json`에는 행마다 `review_order`(기본 구성 우선 57 / 선택 시 15 / 구현 경로 우선 5)가 있지만 문서에는 나오지 않고, 이 값은 "취약점 심각도가 아닌 준비 순서"라고 정의되어 있다. 05 §2.2의 "먼저 준비할 공동 시험" 4묶음이 사실상 첫 실행 목록인데 근거 표시가 없고 "P0"는 정의되지 않았다. `review_order`를 문서의 각 행에 열로 보여주기만 해도 "이 구성에서 먼저 볼 것"이 나온다. 심각도·영향은 별도 보고서(논리·체크리스트 검토)에서 다룬다.
2. **도식이 없다.** 위협모델링 프레임워크인데 데이터 흐름·신뢰 경계(TB) 그림이 한 장도 없다. 참조 구성(사용자 → 앱 → Gateway → API 서버 → core → worker/GPU, 모델 저장소·cache·관측 수집기)에 신뢰 경계와 다섯 영역을 겹친 그림 한 장이 있으면 팀원 온보딩과 발표에 가장 효과가 크다.
3. **범위 밖이 한 곳에 모여 있지 않다.** 모델 행동 위협(프롬프트 주입·탈옥·출력 안전), 학습 단계, 하드웨어 사이드채널, 앱·Gateway 내부 보안은 어디에도 "이 프레임워크가 다루지 않는 것"으로 정리돼 있지 않다(관련 키워드 검색 0건). 심사자나 팀이 가장 먼저 물을 질문이다. 02의 "업무 앱 전체를 감사하는 대신…"처럼 흩어진 문장을 한 절로 모으면 된다.
4. **위협 도출 방법 설명이 짧다.** 24개 묶음이 자산·경계·공격자 권한에서 어떻게 나왔는지는 몇 줄뿐이다. 독립검증 v2의 E2가 지적한 대로 평가 방법 유형(examine/interview/test)과 판정문이 분리되어 있지 않고, 위협별 대응 결정(수용·완화·이전·회피) 필드도 없다.
5. **보고서 양식이 없다.** 05 §5는 보고서에 넣을 항목을 나열만 한다. 결과 JSON 양식은 있어도 사람이 읽는 1쪽 요약 양식은 없다.
6. **국내 규제·지침 대응표가 없다.** 개인정보보호법, 전자금융감독규정, ISMS-P, KISA AI 보안 안내서 관련 언급이 문서 어디에도 없다. 국내 기업 환경에 적용하는 프레임워크라면 28개 보호 목적과의 참고용 대응표(준수 주장이 아님을 명시)가 설득력을 높인다. 다만 원문을 확인해서 써야 하므로 선택 사항으로 둔다.
7. **현재 상태를 한눈에 보는 곳이 없다.** README에 날짜뿐이고 문서 판본·변경 요약이 없다. `검수기록.md`는 시간순 작업 일지라 과거 숫자(132·133·134)가 섞여 있어 "지금 상태"를 알기 어렵다. 맨 위에 "현재 상태 요약" 블록을 두고 이력은 아래로 내리면 된다.
8. **selector 테스트가 폴더에 없다.** 검수기록은 "selector 12개 단위시험"을 통과했다고 하지만 `tests/`나 테스트 파일이 폴더에 없어 재현할 수 없다.

1. **한 시간 안팎:** 폴더 밖 링크 처리, 오탈자, `validation_report.json` 숫자, `__pycache__` 정리, README 첫 문단·상태 범례·용어집.

3. **하루 이상:** 03·01 분리, 계획 절의 로드맵 분리, 신뢰 경계 도식, 보고서 양식, 국내 규제 대응표(선택).

## 7. 한계

문서·JSON의 구조와 일관성을 정적으로 검사한 결과이며, 보안 판정이나 코드 근거의 재검증이 아니다. `source_manifest.json`이 가리키는 원본 통합본·취합용은 이 환경에서 열어보지 못해 해시 일치는 확인하지 못했다.
