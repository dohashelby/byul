## 1. 목표와 범위

| 목표 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| A. 정책 묶음 적용 | 플랫폼 [정책 묶음 내보내기]로 받은 묶음을 운영자가 서버에 접속해 `bundle apply`로 직접 실행한다 | 플랫폼에서 [적용 요청]을 누르면 서버가 가져가 적용하고, 결과를 플랫폼에 보고한다 |

- 자동 모드 승격(사람 결정 없이 차단으로 바꾸는 것)

**확인한 제약:**
- 플랫폼 API에는 **사용자 인증이 없다.** 묶음 내보내기의 `requested_by_role`은 요청 본문에 스스로 적는 값이다(`bundle_export.py:31`).

## 3. 구조: 서버가 가져가는 '적용 에이전트'

```
[대시보드] 적용 요청 / 모드 전환 요청 (관리자)
      │  POST (플랫폼 인증·권한·감사)
      ▼
[플랫폼] 요청 저장: requested → (승인 단계 선택) approved
      ▲                                  │
      │ 결과 보고(POST)                    │ 서버가 주기적으로 조회(GET, 에이전트 토큰)
      │                                  ▼
[서버: runtime 적용 에이전트]  ── 요청 1건 가져옴(lease) → 재검증 → 실행 → 확인 → 보고
      │ 실행: apply_bundle / tetragon_mode (sudo 범위 제한)
      ▼
[Gateway 재시작 / Tetragon set-mode] → GET /api/status·/api/tetragon-status로 확인
```

**가져가는 방식(pull)을 권하는 이유:**
1. 서버에 들어오는 포트를 열지 않는다. 지금도 Gateway는 port-forward로만 조회한다.
2. 서버가 최종 검증권을 갖는다. 묶음 해시, 승인 목록, 대상, 차단 근거를 서버에서 다시 확인하고 맞지 않으면 거부한다.
3. 플랫폼이 서버 자격 증명(SSH 키, kubeconfig)을 갖지 않는다.

**에이전트 형태:**
- `serving_runtime agent` 명령과 systemd 서비스로 만든다. 일반 사용자로 실행한다.
- 특권이 필요한 동작(묶음 루트 쓰기, 링크 교체)만 `sudo`로 하고, **허용 명령을 고정한 sudoers 규칙**으로 제한한다. 예: `serving_runtime bundle apply`만 허용한다.
- 한 번에 요청 하나만 처리한다. 서버에 잠금 파일을 두어 동시 실행을 막는다.
- 조회 주기는 기본 10초다. 요청이 없으면 아무것도 하지 않는다.

## 4. 요청과 상태 흐름

### 4.1 요청 종류

| 종류 | 입력 | 에이전트 실행 |
| --- | --- | --- |
| `bundle.apply` | 정책 판본, 환경 판본, (선택) 서버 값 덮어쓰기 | 플랫폼이 만든 묶음(.tar.gz와 해시)을 받아 `apply_bundle`(새 복사)을 실행한다 |
| `bundle.switch` | 이미 서버에 있는 bundle_id | `apply_bundle --existing`(롤백·재적용) |
| `tetragon.mode` | 정책 이름, 목표 모드(`monitor`/`enforce`) | `tetragon_mode`(set-mode, 확인, 실패 시 되돌림) |

### 4.2 상태

`requested → (approved) → claimed(임대 시간 포함) → running → succeeded | failed | rolled_back | unknown | expired`

- **claimed:** 에이전트가 가져간 상태다. 임대 시간(예: 10분) 안에 결과가 없으면 `unknown`으로 표시하고 사람이 확인한다. **자동으로 다시 실행하지 않는다.** 이미 서버에 반영됐을 수 있기 때문이다.
- **rolled_back:** 실행은 했으나 확인이 실패해 이전 상태로 되돌린 경우다.
- **unknown:** 실행은 했을 수 있지만 확인을 하지 못한 경우다. 지금 `bundle apply`의 "새 링크 유지·수동 확인 필요"가 여기에 해당한다.
- 요청에는 **요청 시점의 기대 상태**를 붙인다. 예: 지금 current = X, 지금 모드 = monitor. 에이전트는 실행 직전 실제 상태가 기대와 다르면 `failed(STATE_CHANGED)`로 거부한다. 다른 사람이 그 사이 바꾼 것을 덮어쓰지 않기 위해서다.

### 4.3 결과 보고에 담는 것

- 요청 ID, 서버 ID(역할명), 시작·끝 시각(UTC)
- 이전/이후 상태: current bundle_id, 승인 상태, 정책 MODE
- 실행 단계별 결과(검증, 링크, 재시작, 상태 확인 / set-mode, 확인)
- 오류 코드
- 증거 파일 해시
- **비밀값, 서버 주소, kubeconfig 경로는 보고하지 않는다.**

| 감사 | 요청, 승인, 실행, 결과를 플랫폼 저장소에 추가 전용으로 기록한다. 실명 대신 역할·토큰 ID를 쓴다. |

## 6. 차단 전환 안전장치 (B 전용)

`tetragon.mode → enforce`는 아래를 **모두** 만족해야 요청 버튼이 켜진다. 에이전트도 실행 직전에 다시 검사한다.

1. 대상 정책이 monitor_only가 아니다. 차단 동작이 들어 있고 지금 상태가 enabled다.
2. **그 서버에서 그 차단 방식의 시험 근거가 있다.** AWS-20(또는 L-05b·L-05c) 통과 기록이 있어야 하고, 방식(`tetragon_enforce_method`)·정책 spec 해시·커널 판본이 지금과 같아야 한다. 근거가 없거나 오래됐으면 "시험 필요"로 막는다.
3. 차단 능력 '가능'은 정적 근거 또는 실측 근거로 판정한다. 사전 점검 `available`이면 `capability_basis=static`, `unknown`이면 2번과 같은 동일 노드·커널·방식·정책 spec 해시의 real `combined` 시험 passed 근거가 있을 때만 `live_trial`로 통과한다. `unavailable`은 실측 근거가 있어도 거부하며 사유를 결과·화면에 표시한다. 별도 evidence·모니터·수집 등 나머지 조건은 모두 충족해야 한다.
4. 모니터 기간 조건(설정값, 예: 24시간) 동안 그 규칙에 걸린 이벤트가 0건이거나, 사람이 하나씩 검토해 오탐이 아님을 표시했다.
5. 수집 상태가 정상이다(`/api/tetragon-status`의 복구 4조건 충족). 감시가 끊긴 상태에서 차단으로 바꾸면 결과를 확인할 수 없기 때문이다.

**Sigkill 계열 경고:** `sigkill_fd_install`·`override_lsm`(Sigkill 포함)은 엔진 프로세스를 종료시킬 수 있다. 확인 화면에 "엔진 종료 → Gateway 503 → 재시작" 경로를 보여 주고 확인 입력을 받는다.

**되돌리기:** 대시보드 [탐지로 전환]은 위 조건 없이 즉시 실행한다(§5 승인 없음).

### 6.1. 모니터 기록 생성기 (2026-11-06)

`tools.tetragon_monitor_window`를 기존 stream/status와 같은 독립 도구로 제공한다. Gateway의 `observations.jsonl`은 수집 당시의 identity로 정규화·귀속한 기록이므로 이를 사용한다. raw `tools.tetragon_stream` 출력에 현재 identity를 나중에 붙여 과거 이벤트를 confirmed로 추정하지 않는다. stream을 사용한다면 기존 Gateway feed·identity·heartbeat 경로로 정규화한 저장소를 입력한다. 공용 contracts 확장 없이 기존 `--review-file`의 `windows`를 생성한다.

| 입력·변화 | 창 계산 |
| --- | --- |
| 첫 정상 상태 | 이름·namespace별, 각 node의 enabled/monitor 정책부터 시작. 과거 기간 소급·프로세스 재시작 후 이어붙이기 없음 |
| 같은 정책 ID·spec·method·monitor·kernel | `since` 유지, `until`은 status의 `generated_at`만 사용. 반복해서 읽어도 현재 시각으로 연장하지 않음 |
| ID/spec/method/kernel·agent epoch 변경 | 새 정상 상태 시각부터 새 창 |
| enforce/monitor_only/disabled·정책 사라짐 | 해당 창 제거. monitor 복귀 후 새 창. 두 표본 사이의 기록된 모드 전환도 재시작 |
| open_gap·복구 4조건 미충족 | 창 제거, healthy 복구 후 새 창. 표본 사이 복구됐어도 공백 이력·verification epoch 변경으로 재시작 |
| status 20초 초과·미래 시각·역행·표본 간격 20초 초과 | 무효 또는 새 창. `until` 30초 신선도는 safety에서 추가 검사 |
| 실제 이벤트 | real/Tetragon·정책명·namespace·node·context 일치, identity confirmed, 창의 since≤observed_at≤until만 집계. health_check와 sentinel 컨테이너 제외 |
| 이벤트 해시 | 정규화 객체 전체를 UTF-8·키 정렬·공백 없는 JSON으로 직렬화한 순서로 정렬한 목록의 SHA-256. 중복 행은 건수에 포함 |
| 검토 | 별도 사람이 작성한 이벤트별 verdict+reviewer_token_id만 반영. 미검토는 reviewed<count, 오탐은 false_positive_count>0으로 차단 거부 |
| 읽기 실패·손상·관측 저장소 교체/절단/기존 내용 변경 | 실패는 빈 windows, 저장소 변경은 새 창. 검토 파일 오류는 검토 0건. 검토용 catalog 쓰기 실패도 빈 windows |

기본 5초 `--watch`이며 입력과 출력 경로는 서로 달라야 하고 출력별 단일 프로세스 잠금을 사용한다. 출력과 별도 이벤트 catalog는 같은 폴더의 고유 임시 파일(생성 순간부터 0600)에 쓰고 fsync→rename→디렉터리 fsync한다. 에이전트는 root 또는 실행 UID 소유의 일반 파일, 정확히 0600, 2 MiB 이하를 열린 fd 기준으로 확인한다. 생성기는 에이전트 계정 또는 root로 실행하고 root 소유 코드·설정 및 신뢰 가능한 부모 디렉터리를 사용한다.

사람은 `OUTPUT.events.json`의 이벤트 내용을 확인한 뒤 별도 검토 파일에 이벤트별 SHA-256과 `not_false_positive`/`false_positive`를 기록한다. 이벤트별 SHA-256은 context·정책 ID/spec/method/kernel·창 시작·이벤트 전체에 묶이므로 다른 창에 검토가 승계되지 않는다. 도구는 verdict나 검토자 ID를 자동으로 채우지 않는다. 검토자 ID는 로컬 기록의 발급 토큰 식별자이며 플랫폼 인증/2인 승인과 별개다. 로컬 계정의 파일 위조를 막는 서명은 제공하지 않는다.

agent-state의 선택 `policies[].monitor_windows`는 node·since/until·continuous·총건수/검토건수/오탐건수만 보낸다. 운영 요청과 Tetragon 정책 화면의 같은 체크리스트에서 표시하며, 원문 이벤트·로컬 경로·검토 토큰 원문은 보내지 않는다. 안전 평가는 namespace·정책 ID·monitor 모드도 현재 상태와 대조하며 구형 수동 창은 이 필드가 없으면 거부한다. 설정 기간과 기존 나머지 안전 조건은 그대로 필요하다.

현재는 관측 저장소 전체를 매 주기 검증(최대 64 MiB), 상태/사람 검토 입력은 각각 2 MiB까지 읽는다. 초과 시 무효 처리한다. 장기·대용량 기록의 증분 집계/보존 연계, 재기동 후 연속성 복원은 후속 범위이며, 보존 정리 전에 안전한 새 관측 기간을 확보해야 한다. healthy status의 복구 4조건을 관측 경로의 신선도 근거로 사용하므로 이벤트가 없는 정상 창에서 파일 mtime만으로 수집 중단을 추정하지 않는다. 수집·상태·생성기 프로세스를 함께 감시해야 한다. 사용·검토 예시는 `원격운영_사용과검증.md` §11을 따른다.

| D1 | 원격 전달 방식 | **서버가 가져가는 에이전트(pull)** |
| D2 | 플랫폼 인증 최소 수준 | 관리자 토큰 + 역할. 정식 로그인은 D-02를 따른다 |

## 8. 구현 단계

1. **계약 초안·인증 (platform):** 관리자·에이전트 토큰, 역할, 감사 저장소, 요청·결과 API(`POST /api/runtime/operations`, `GET /api/runtime/operations?server=…`(에이전트), `POST /api/runtime/operations/{id}/claim|result`, `POST …/{id}/approve`).
2. **에이전트 (runtime):** `serving_runtime agent`, 요청 조회·임대·재검증, `apply_bundle`/`tetragon_mode` 호출, 결과 보고, 잠금, systemd 단위 예시와 sudoers 예시.
3. **intent 허용 모드 집합 (runtime, D4):** 선택 필드를 추가하고 기존 `tetragon_rule_modes`와의 관계를 정리한다. 하위 호환을 유지한다.
4. **차단 전환 안전장치 (platform + runtime):** 근거 조회(시험 결과 + 능력 판별 + 수집 상태) → 버튼 활성 조건 → 에이전트 재검사.
5. **화면 (platform/web):**
   - 정책 판본에 [적용 요청]
   - 운영 요청 목록(상태, 승인, 결과, 증거)
   - Tetragon 정책 화면에 [차단으로 전환]/[탐지로 전환]과 조건 체크리스트, Sigkill 경고
6. **시험:**
   - 단위: 권한 거부, 상태 경쟁(STATE_CHANGED), 임대 만료 → unknown, 되돌림, 근거 없는 enforce 거부
   - 로컬 kind 통합: 플랫폼 요청 → 에이전트 → apply → Gateway `verified` / monitor → enforce → L-05b 차단 확인 → monitor. 감시 공백이 없어야 한다.
   - 실패 주입: 묶음 해시 불일치, set-mode 시간 초과, 플랫폼 연결 끊김
7. **5회차 서버:** 에이전트를 설치하고 실제 적용·전환을 확인한다(시험용 Pod 우선).

## 9. 위험

- **원격으로 서버를 바꾸는 경로가 생긴다.** 인증이 약하면 침해 경로가 된다. §5를 먼저 구현하기 전에는 원격 실행을 켜지 않는 기본값(`agent --dry-run`, 보고만)을 둔다.
- 플랫폼과 서버 시계가 다르면 임대·만료 판정이 어긋날 수 있다. 서버 시각을 기준으로 기록한다.
- 에이전트가 죽으면 요청이 쌓인다. 플랫폼에 '에이전트 마지막 조회 시각'을 표시한다.
- 에이전트 계정 탈취 시 계정이 쓸 수 있는 묶음과 허용된 root 적용 명령을 악용해 임의 묶음을 적용할 위험이 있다. 해시·자기 신고 승인 검증은 발행자 서명 검증이 아니다. 에이전트 전체를 root로 실행하면 영향 범위가 더 커지므로 격리된 kind 시험과 운영 설치를 구분하고, 운영의 전용 계정·root 소유 코드/설정·고정 sudoers·제한 RBAC를 검수한다.
- 차단 전환은 엔진 종료를 일으킬 수 있다(§6 경고). 운영 환경에서는 승인 단계를 끄지 않는다.
