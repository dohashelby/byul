**2026-10-25 시험 전 1차 확정:** 업데이트 위협·영향평가 인계와 결과의 분기 참조를 보완하고, 독립 재검토 후 사용자 요청으로 현행 로컬 문서·양식을 개발·평가 기준선으로 확정했다. [1차 확정 범위·검증·담당별 후속 작업](시험전_1차확정_20261025.md)을 기준으로 적용한다. 아래의 날짜별 실행 상태는 해당 시점 기록이다.

서빙엔진을 도입·운영·변경할 때 필요한 보안 점검을 고르고, 어떤 증거로 충족 여부를 판단할지 안내한다. **플랫폼·ML 운영자, 보안 검토자, 개발·시험 담당자**가 같은 기준으로 점검을 준비하고 결과를 검토하는 데 사용한다.

## 전체 프레임워크 구성

이 프레임워크는 서빙엔진의 기밀성·무결성·가용성·책임 추적성을 목표로 한다. 위협과 취약 원리에서 보호 요구를 도출하고, 조직이 실제 환경과 생명주기에 맞게 적용·평가하도록 안내한다.

| 구성요소 | 역할 |
| --- | --- |
| 보안 목표 | 보호 자산, 공격자와 경계, 엔진·주변 환경의 책임 및 보호가 성립하는 조건을 정한다. |
| 거버넌스 | 정책 소유자와 제출·검증·승인·운영 역할, 직무 분리·교육·예외 승인을 정한다. |
| 위험 관리 | 위협·취약 원리에서 요구를 도출하고 영향·우선순위·수용·보완·사고 대응을 관리한다. |
| 보안 기능과 보호 요구 | 여덟 기능의 36개 요구에 방어 위치·범위·한계와 CHK를 대응시킨다. |
| 환경 확인 | 호출·배포·공유 구조, 실제 활성 기능과 집행 주체에 따라 적용 범위를 결정한다. |
| 생명주기 | 도입부터 폐기까지 요구를 적용·확인할 시점과 담당 역할을 정한다. |
| 보호 요구의 적용과 검증 | 정상 대조·조건·증거에 따라 판정하고 보완·재시험·재평가한다. |

구성도에서 보안 관리는 거버넌스와 위험 관리를 묶는다. 보호 요구의 적용과 검증은 환경 확인, 점검 및 시험 선정, 통제 확인과 시험, 판정과 검토 보고로 이어진다. 범위와 신뢰 가정은 위험 관리의 위협 분석에서 함께 확인한다.

보안 목표가 전체 방향을 정하고, 거버넌스는 정책과 담당 책임을 정한다. 위협 분석에서 필요한 보호 요구를 도출하며, 환경별 기준에 따라 적용할 요구와 CHK를 고른다. 도입부터 폐기까지 이를 적용하고 평가 결과에 따라 보완한다.

**현재 상태:** 여덟 보안 기능·36개 보호 요구·77개 CHK로 내용을 재구성했다. 실제 계정·허용 대상·예산·기한은 조직에서 정하며 엔진·GPU 시험은 미실행 상태다. vLLM 0.31.0은 공통 요구를 설명하는 구현 참조 구성이다.

**상태 표시:** ‘팀 기준 채택’은 평가 기준을 정했다는 뜻이다. ‘구현 계획’은 기능을 만들 예정이라는 뜻이고, ‘미실행’은 시험 전, ‘미확인’은 판정할 증거가 부족한 상태다. 기능을 쓰는지 모르면 적용 상태는 ‘미정’으로 둔다.

<a id="terms"></a>

**표시 읽기:** **시나리오(SC, Scenario)**는 문제가 생길 수 있는 상황, **점검(CHK, Check)**은 실제로 확인하고 판정할 항목, **도출 근거·관련 사례(Q)**는 그 점검을 만든 정책·코드·사례·절차다. 화면에서는 이름을 먼저 읽고 ID는 같은 항목을 찾아갈 때 사용한다. Q는 별도의 추가 점검이나 판정 단위가 아니다.

## 용어와 숫자를 읽는 법

| 용어 | 뜻과 쓰임 |
| --- | --- |
| 보호 자산(AS) | 모델·요청 자료·실행 상태·자격·기록 등 보호할 대상 |
| 보호 요구(POL) | 허용한 접근·실행·공유·종결 등 지켜야 하는 조건. 기존 통합본의 POL을 참조한다. |
| 보호 요구 36개 | 여덟 보안 기능에서 유지할 조건. 기존 28개 보호 목적의 복합 요구를 나누고 각 요구에 CHK를 배치했다. |
| 세부 점검 77개 | CHK 고정 ID로 식별하는 체크리스트 항목. 적용 조건·시험 분기·정책·증거·판정 기준을 갖춘다. |
| 도출 근거(Q) 28개 | 기존 정책·판정·구현·사례·시험 연결을 보존한 기록. 세부 점검의 관련 근거와 판정을 추적한다. |
| 시나리오(SC) 83개 | 공격자·접점·적용 조건과 보호 요구 위반 또는 실패 상황. 위협 후보 73개·실패/오설정 검증 9개·공유 신뢰 범위 1개다. |
| 시험 초점 83개 | 시나리오마다 무엇을 확인할지 적은 설계 초점. 구현된 시험 수나 실행 횟수가 아니다. |
| 실행 시험 | 실제 환경·입력·절차·계측을 갖춰 실행하는 단위. 한 시나리오가 여러 시험으로 나뉠 수 있다. |
| R / TB / SURF | 동작 경로 / 신뢰가 달라지는 경계 / 구체적인 공격표면. SURF는 공격표면의 고정 ID다. |
| F / P0 | F는 기존 코드 검토 지적 번호. P0는 먼저 준비할 공동 시험을 가리키던 표기로, 취약점 심각도 등급은 아니다. |

보호 목적·세부 점검·Q·SC는 **여러 개씩 연결된다.** Q–SC 136개는 관계 수이며 실행 시험 136개를 뜻하지 않는다. 동일 실행의 증거를 재사용하더라도 각 점검·요구의 판정은 따로 남긴다.

## 자료의 역할

[최신 통합본](참고자료/통합본/통합본.md)은 정상 흐름과 소스 근거의 기준이고, 기존 취합용（출처: `서빙엔진_통합검토_초안_v0.2.1.md`）은 팀원 의견·위협 도출의 작업 이력이다. 이 폴더는 그 내용을 평가자가 사용할 수 있게 정리한 프레임워크·체크리스트다. 근거 수정 시 원본을 고친 뒤 여기의 같은 Q ID를 갱신한다. 원본 파일의 기준 해시는 `data/source_manifest.json`에 기록했다.

R01~R09·R11~R13을 다룬다. **R10은 미디어 일부 정적 검토 반영·전체 평가 대기, R14는 검토 대기**이며 관련 환경 차이는 빠뜨리지 않도록 남겨두었다. 그 기능을 쓰는 환경의 전체 보안을 이번 체크리스트만으로 평가 완료할 수 없다.

현재 엔진 구현 근거의 중심은 프로젝트 고정 vLLM v0.31.0이다. 다른 엔진은 공식 문서에서 확인한 기능 차이와 적용 방법을 제공한다. 특정 설치판의 지원·통제 효과는 선정 판본의 소스와 실제 시험으로 확인해야 한다. 모든 기업·엔진·버전의 조합을 검증한 목록은 아니다.


## 저장소 구성과 읽는 순서

핵심 문서와 실제 판정에 필요한 근거를 함께 관리한다. 문서 이름·기존 링크 경로는 유지하고, vLLM 전체 소스는 공식 저장소의 고정 commit으로 참조한다.

```text
serving-security-framework/
├── README.md                         사용 안내·현재 상태
├── 01~05 문서                        프레임워크·환경·점검·엔진 차이·평가
├── data/                             CHK 정본·환경/결과 양식·위협지도·출처
├── 노션_공유용/                      01~07 공유 문서·위협지도·사용 중인 그림
├── 엔진별_적용검토/                  선정 엔진의 고정 소스 대조·범위·미확인
├── 평가기록/                         실제 자료에 근거한 평가 사례
├── 개발전달/                         별도 업데이트 검증 폼 명세
├── 참고자료/                         통합 분석·실행 흐름·취약점 근거와 출처
├── 소스/출처확인/                    고정 commit·선정 파일 hash·확보 방법
└── select_checklist.py · verify_*     선정 보조·정합성 검증
```

- **현재 기준:** 원문 01~05와 `data/checklist.json`을 사용한다. 노션 공유용 01~07은 이를 읽기 쉽게 정리한 공유본이다.
- **필요 근거:** [통합본](참고자료/통합본/통합본.md), [실행 흐름 검토](참고자료/실행흐름검토/검토결과와_수정제안.md), [상세 코드 근거](참고자료/실행흐름검토/상세_코드근거.md), [취약점 색인](참고자료/통합본/references/vllm031-review-inputs/serving-vulnerability-r-index-20261016/취약점_사례_R별_참고색인.md)을 보존한다. 기존 CHK가 직접 참조하는 취합 자료도 필요한 근거로 유지한다.
- **코드:** [고정 commit·출처·로컬 확보 안내](소스/출처확인/README.md)를 따른다. vLLM v0.31.0은 현재 소스 근거, v0.11.0은 과거 비교 근거다. 설치 환경·실행 결과는 실제 평가 기록으로 별도 확인한다.
- **과거 작업 자료:** 이전 검토 문서와 옛 PPT는 [정리 전 고정 판본](https://github.com/mg-princess/serving-security-framework/tree/32070389f755e5974c286f92e3be86e6320bdda9)에서 확인할 수 있다. 기존 로컬 파일도 남겨두며 새 Git 배포 목록에서는 제외한다.
- **작성·복사 이력:** `data/source_manifest.json`에 필요한 참조 파일의 출처·hash와 배포 구분을 남긴다. 전체 소스 파일별 옛 목록은 정리 전 고정 판본에서 확인한다.

GitHub는 전체 소스 사본·로컬 작업 출력·편집기 임시 파일을 추적하지 않는다. 기존 소스 사본은 컴퓨터에서 계속 열 수 있으며 필요한 경우 공식 저장소에서 같은 commit을 다시 확보할 수 있다.

## 개발에 사용할 자료

프레임워크가 제공하는 범위는 점검 ID·관계·적용/제외/미정 및 분기 조건이다. 03에서 항목을 읽고 JSON의 같은 `id`로 찾는다. 조건식 언어·환경 수집 키/API·실행 시험·증거 저장·정본/생성물 운영 방식은 개발팀이 설계한다. 현재 selector를 CHK 자동 선택기로 완성했다고 해석하지 않는다.

- `data/checklist.json`: 도출 근거(Q) 28개와 상위 질문 대응, CHK ID 77개·목적/Q/SC 역참조·환경별 적용 및 시험 분기 기준과 버전 관리 계획. selector는 기존 Q만 사용하며 새 구조의 세부 선택·실행은 미구현.
- `data/environment_template.json`: 팀 참조 구성의 **계획값**. 실제 설치값·정책값은 null.
- `data/result_template.json`: 하위 시험 결과 기록 양식. 실행 결과를 꾸며 넣지 않았다.
- `select_checklist.py`: 환경값으로 큰 질문을 적용/비적용 후보/미정으로 고르는 보조 기능. 엔진에 접속하거나 시험하지 않는다.

```sh
python3 -B select_checklist.py data/environment_template.json
```

기능을 false로 지정하더라도 `feature_absence_evidence`에 비사용·비노출 근거가 없으면 미정으로 남는다. 다른 엔진·판본은 공통 질문을 유지하고 구현 매핑 필요 상태로 표시한다. 출력은 선택 결과이며 통과 판정이 아니다.

조건부 입력 키는 `request_code_revision_selection`, `dynamic_import`, `alternate_sources_or_formats_or_derived_cache`, `remote_acquisition_or_retry`, `prefix_cache_or_shared_cache`, `shared_or_remote_weights`이다. 여러 조건을 OR로 묶은 키는 관련 기능이 모두 비활성이고 비노출 근거가 있을 때만 false로 둔다. `r10_features`와 `managed_or_external_fallback`은 이번 범위 밖의 검토 필요성을 표시한다.


## 다음에 채울 내용

1. 실제 모델·이미지·GPU·의존성·실행기와 접근·송신·수집 설정을 확인한다.
2. 팀 기준을 적용할 계정·허용표·수치·기한과 승인자를 정한다.
3. 우선 점검의 시험 입력·계측·중단·복구 절차를 구현한다.
4. 시험 증거와 보안·정상 기능·성능 결과를 기록하고 보완·적용 여부를 판단한다.

원본 통합본·취합용·실행흐름 검토 자료는 위 참고자료 폴더에서 연다. 현재 문서의 링크는 폴더 안 상대 경로를 사용하며, 원본 위치·해시는 `data/source_manifest.json`에서 관리한다. 상세 수정 이력은 [검수기록](검수기록.md)에 있다.

selector의 12개 회귀 검사는 `python3 -B select_checklist.py --self-test`로 재현한다. 이 검사는 적용 분류 로직만 확인하며 엔진·보안 통제 시험을 실행하지 않는다.

## 문서·JSON 일치 확인

문서를 수정한 뒤 폴더에서 `python3 verify_framework.py`를 실행한다. CHK ID·연결 관계·적용 조건·분기 표·증거·정상 대조·시험 순서·판정·보완 방법과 관계 수를 비교한다. 엔진 동작이나 통제 효과를 시험하는 명령은 아니다.


## 위협지도 탐색

[위협지도 HTML](노션_공유용/위협지도_탐색.html)을 내려받아 브라우저에서 연다. 위협 유형·보호 영역·환경 정보로 시나리오를 찾고 **시나리오 → 관련 점검 → 도출 근거** 순서로 읽는다. 페이지 안에서 검색·필터·상세 설명을 사용할 수 있고, Markdown 원문 링크는 폴더 전체를 함께 내려받아야 열린다. GitHub 파일 화면에서는 HTML이 실행되지 않는다.

```sh
python3 -B verify_framework.py
node verify_explorer.cjs
python3 -B select_checklist.py --self-test
```

두 검증 스크립트는 문서·데이터·화면 함수의 일치를 검사한다. 브라우저 화면이나 엔진 동작을 시험하는 명령은 아니다.

지도 연결은 [threat_map.json](data/threat_map.json)에서 관리한다. [편집 가능한 지도 SVG](노션_공유용/assets/serving-flow-threat-map.drawio.svg)는 drawio에서 열어 수정할 수 있다. `verify_explorer.cjs`로 지도·통합본 출처·시나리오별 접점·HTML 연결을 함께 검사한다.

현재 전체 구성은 [01의 구성 표](01_프레임워크와_위협통제연결.md#전체-프레임워크-구성)를 따른다. [기존 PPT](https://github.com/mg-princess/serving-security-framework/blob/32070389f755e5974c286f92e3be86e6320bdda9/%EB%85%B8%EC%85%98_%EA%B3%B5%EC%9C%A0%EC%9A%A9/assets/BBLS_%EC%9D%B8%ED%8F%AC%EA%B7%B8%EB%9E%98%ED%94%BD_%EC%A0%84%EC%B2%B4.pptx)는 과거 다섯 영역·세 관점의 배치 이력으로 보존한다.

다른 엔진과 Llama 모델·llama.cpp에 적용할 범위, 공통 증거 보완 10개와 남은 범위는 [엔진별 적용 검토](04_엔진과_버전별_차이.md#다른-서빙엔진에-적용하는-범위)에서 확인한다.
