# AWS GPU dev 서버 4회차 확인순서

기준: `byul_runtime` 4432c0f와 이번 미커밋 변경. 3회차 [확인순서](서버3회차_확인순서.md)의 A(노트북)·B(서버)·C(복구·증거·Stop) 형식을 따른다. 실제 서버 적용·커널 차단·두 엔진 지표는 아직 미확인이다. 모든 시각은 UTC, 결과는 통과/실패/확인 불가로 기록한다. 토큰·키·주소·요청 본문·원시 `/metrics`·원시 Tetragon 로그는 반출하지 않는다. 서버 비용은 USD 1.2/시간 가정이다.

## A. 전원 켜기 전: 노트북 (서버 비용 0)

| 순서 | 준비와 종료 조건 | 막히면 |
| --- | --- | --- |
| 1. 승인·복귀점 | 정책 담당자가 TG-SECRET-01의 **가짜 파일 한 경로** monitor/enforce 각각의 intent·승인 정책 판본·적용 시간을 확인한다. 서버 담당자는 Tetragon 규칙 삭제 후 monitor 복원 권한과 기존 `current` 상대 링크 대상을 확인한다. | 승인 원본·정규 해시·복원 담당 또는 이전 묶음이 없으면 가동 보류. LAB 자기 신고를 승인으로 세지 않는다. |
| 2. 두 엔진 묶음 | vLLM·SGLang **각각 monitor/enforce**의 확정 정책 원본, 원본 SHA-256, 서버 값, intent, 고유 bundle ID를 준비한다. 아래 `bundle build`/`verify`를 네 번 실행하고 역할 파일 해시·크기·정책 판본과 후보 `tetragon-tg-secret-01.json`의 namespace·Pod selector·가짜 경로·read mask 4·Equal/Override(-1)를 확인한다. monitor 후보는 Post다. | 불일치·후보 규칙에 실비밀 경로 포함 시 중단. 기존 묶음 파일을 직접 덮어쓰지 않는다. |
| 3. 이미지·시험 | Gateway 이미지·호스트 수집기와 도구를 같은 코드 세대로 반입 준비하고, `TMPDIR=/dev/shm .venv/bin/python -B -m unittest discover -s tests` 결과와 skip 사유를 적는다. 노트북 platform/web은 `npm run typecheck && npm test`를 수행한다. | 실패·설명 못 한 skip이면 적용 보류. |
| 4. 화면 연결 준비 | 노트북 API의 Gateway upstream 설정·viewer 토큰 파일, 웹 주소, 로컬 포트포워드 명령을 정리한다. 실제 자료 연결을 별도 표지로 확인할 준비를 한다. | 예시/합성 자료가 켜져 있으면 실제 확인으로 기록하지 않는다. |

묶음 명령은 [정책 수동적용 절차](정책_수동적용_절차.md)의 새 CLI를 쓴다. `<engine>`은 `vllm`/`sglang`, `<mode>`는 `monitor`/`enforce`이고 각각 확정 원본이 필요하다.

```bash
cd runtime
.venv/bin/python -B -m serving_runtime bundle build --policy <확정-policy.json> --policy-sha256 <정규-해시> --server-values <engine-server-values.json> --intent <engine-mode-intent.json> --output-parent <staged-bundles> --bundle-id <engine-mode-새-ID>
.venv/bin/python -B -m serving_runtime bundle verify --bundle-dir <staged-bundles/engine-mode-새-ID>
```

## B. 서버 가동 중

먼저 [서버 실행순서표](서버_실행순서표.md) 1~3단계와 [정책 수동적용 절차](정책_수동적용_절차.md)의 적용 전 검증을 수행한다. `bundle apply`의 입력 묶음·이전 링크·Gateway 정책 상태를 대조하고 **각 적용에서 dry-run을 먼저** 실행한다. 아래 공통 명령은 네 묶음 전환마다 반복한다. 실제 적용은 승인된 작업자만 수행한다. `apply`가 rollback 성공을 보고해도 `current`·Pod·정상 200을 다시 읽고, 조회 불가로 새 링크가 유지되면 성공으로 세지 말고 이전 링크 수동 복구 절차로 간다.

```bash
sudo -E env KUBECONFIG=<서버-kubeconfig> PATH="$PATH" .venv/bin/python -B -m serving_runtime bundle apply --bundle-dir <검증된-묶음> --bundle-root /srv/serving/bundles --context byul-aws-lab --namespace serving-lab --kubeconfig <서버-kubeconfig> --status-url http://127.0.0.1:8080 --token-env-file <서버-토큰파일> --dry-run
sudo -E env KUBECONFIG=<서버-kubeconfig> PATH="$PATH" .venv/bin/python -B -m serving_runtime bundle apply --bundle-dir <검증된-묶음> --bundle-root /srv/serving/bundles --context byul-aws-lab --namespace serving-lab --kubeconfig <서버-kubeconfig> --status-url http://127.0.0.1:8080 --token-env-file <서버-토큰파일>
sudo -E env KUBECONFIG=<서버-kubeconfig> PATH="$PATH" .venv/bin/python -B -m serving_runtime bundle apply --existing <기존-묶음-ID> --bundle-root /srv/serving/bundles --context byul-aws-lab --namespace serving-lab --kubeconfig <서버-kubeconfig> --status-url http://127.0.0.1:8080 --token-env-file <서버-토큰파일> --dry-run
sudo -E env KUBECONFIG=<서버-kubeconfig> PATH="$PATH" .venv/bin/python -B -m serving_runtime bundle apply --existing <기존-묶음-ID> --bundle-root /srv/serving/bundles --context byul-aws-lab --namespace serving-lab --kubeconfig <서버-kubeconfig> --status-url http://127.0.0.1:8080 --token-env-file <서버-토큰파일>
```

| 우선 | 확인 순서·실행 | 통과 기준 | 실패·확인 불가 및 증거 |
| --- | --- | --- | --- |
| 1 | vLLM monitor 묶음 적용, `current`·Gateway bundle ID/approval verified·Pod Ready·수집기 확인. `aws_lab_preflight.py --engine vllm --override-check` 실행. | 같은 승인 판본·코드 세대·수집 정상. Override 항목은 실측 전 `unknown` 허용. | 적용/복귀 불일치면 차단 전환 중단. `01-vllm-적용.md`. |
| 2 | vLLM monitor에서 `aws_lab_acceptance.py --engine vllm --cases AWS-01,AWS-09,AWS-10,AWS-11` 실행. AWS-11은 AWS-09·10을 같은 실행에 넣어야 전후 대조한다. | 정상 200·AWS-10 read/Post 탐지·AWS-11 정상 요청/stream/캐시·잘못된 경고 0. | AWS-10은 기존 탐지 기준 그대로. 실패·unknown은 그대로 기록. `02-vllm-monitor/`. |
| 3 | [SGLang 전환 절차](SGLANG_전환절차.md)대로 한 엔진만 SGLang으로 전환하고 SGLang monitor 묶음을 적용한다. **의도된 엔진 Pod 직접 실행 전에** `aws_lab_acceptance.py --engine sglang --cases AWS-01,AWS-09,AWS-10,AWS-11`을 끝내 판정 구간 종료 UTC를 기록한다. | 두 엔진의 AWS-11 판정과 AWS-01·10 회귀가 각각 완료되고, SGLang 정상 200·read/Post 탐지·stream/캐시·잘못된 경고 0을 확인. | SGLang 준비 실패나 AWS-11 unknown은 그대로 기록하고 차단 시험을 보류. `03-sglang-monitor/`. |
| 4 | **양 엔진 AWS-11 종료 뒤**, 커널 근거를 수동 확인하고 SGLang enforce 묶음 dry-run→apply, 정확한 TG-SECRET-01 Tetragon manifest 적용·현재 spec 대조. 이미 enforce가 적용된 뒤 AWS-20을 `--allow-rule-switch --aws20-monitor-manifest <검토한-monitor-manifest>`로 단독 실행한다. 이어 SGLang monitor **묶음도** dry-run→apply로 복원하고 `aws_metrics_names.py --engine sglang --context byul-aws-lab --output <서버-evidence>/sglang-metric-names.json`을 실행한다. | 가짜 파일 EPERM, 같은 Pod UID·규칙 ID·정확 경로·read mask의 원시 Override, 같은 구간 정상 요청 HTTP 200/ALLOWED, 도구의 monitor 규칙 복원 뒤 읽기 성공, Gateway monitor 묶음 복귀. 지표는 이름 목록·F6 후보 찾음/없음만 저장. | 커널 지원 불명·정책 spec 불일치면 AWS-20 미실행/unknown. 정상 요청 실패·반대 읽기 결과·복원 실패는 failed. 복원 실패면 즉시 정책 삭제 후 승인 monitor manifest 적용. 지표 불일치는 `verified: false` 유지. `04-sglang-차단-복원/`. |
| 5 | vLLM으로 복귀해 monitor 묶음·Pod Ready를 확인한 뒤 vLLM enforce 묶음과 TG-SECRET-01 manifest를 4번과 같은 방식으로 적용·대조하고 AWS-20을 단독 실행한다. monitor 규칙·묶음을 복원한 뒤 `aws_metrics_names.py --engine vllm --context byul-aws-lab --output <서버-evidence>/vllm-metric-names.json`을 실행한다. | vLLM AWS-20의 EPERM·동일 Pod UID Override·정상 200·복원 뒤 읽기 성공, 최종 vLLM monitor 묶음·규칙, 두 엔진 지표 이름 대조표. | 실패·unknown은 4번과 같은 기준으로 처리하고 vLLM monitor 복원을 우선한다. 원시 `/metrics` 반출 금지. `05-vllm-차단-복원/`. |
| 6 | 양 엔진 AWS-11 종료 뒤 3회차 보존 빈 캐시 `/srv/serving/cache/sglang/<digest>/<revision>/dev-profile-01.run3-cold-20261104`의 **하위 상대 경로와 용량만** 서버 안에서 추출한다. `du -a --block-size=1` 출력은 서버 안에서 경로를 검사·상대화하고 파일 내용·원시 로그를 읽지 않는다. | Triton/Inductor 등 실측 폴더 구조에서 SP1 캐시 경로 후보와 근거를 명시. | 폴더 누락·권한 문제는 확인 불가. 새 캐시 이동·삭제 없이 `06-sp1-cache-paths.md`. |
| 7 | 노트북 웹·API를 실제 서버 Gateway 포워드에 연결한다. 화면에서 자료 등급/환경·기간을 먼저 확인하고 알림, 엔진 실행 단계, Tetragon 차단 표지·개요의 보조 표시를 실제 AWS-20 시간창으로 대조한다. | 실제 event ID와 Gateway 관측/원시 시각을 연결하고 monitor 창에서는 차단 보조 표시가 없는지 확인. | 플랫폼 API·인증·시간 범위가 맞지 않으면 화면 검증 unknown. 화면 캡처는 민감값 검사 뒤 `07-dashboard.md`. |

커널 수동 근거: Tetragon Pod에서 `tetra probe config`, 노드에서 `zgrep CONFIG_BPF_KPROBE_OVERRIDE /proc/config.gz` 또는 `grep CONFIG_BPF_KPROBE_OVERRIDE /boot/config-$(uname -r)`, 오류 주입 가능한 `security_file_permission`·정책 load 상태·실제 EPERM을 함께 확인한다. preflight의 `unknown`은 지원 부정을 뜻하지 않는다. `AWS-20`은 enforce 적용/승인을 하지 않으며 실제 정책이 가짜 경로 하나와 정확한 read Override인지 먼저 읽는다. 복원은 try/finally에서 실행되지만 프로세스 강제 종료나 클러스터 오류는 수동 복구가 필요하다.

### 시험 중 의도한 엔진 실행

3회차 [결과 문서](../../docs/AWS_GPU_서버3회차_결과_20261104.md)의 같은 절처럼, **vLLM과 SGLang의 AWS-11 판정 구간이 모두 끝난 뒤** 4~6번의 별도 점검을 시작한다. `aws_metrics_names.py`가 엔진 Pod에서 실행하는 Python, AWS-20의 가짜 파일 읽기와 복원 뒤 읽기, 캐시 구조 조회를 위해 Pod 안에서 직접 실행한 명령은 Tetragon 실행 이벤트를 만들 수 있다. 호스트에서 수행한 캐시 조회는 호스트 작업으로 구별한다.

각 실행의 **시작·종료 UTC 시각, 엔진·Pod UID, 목적, 실행 도구/사례 ID**를 사례 보고서 또는 해당 증거 요약에 적고, 원시 인자·파일 내용은 기록하지 않는다. AWS-11의 시작·종료 UTC와 대조해 이 구간 밖의 의도된 직접 실행을 AWS-11 오탐으로 세지 않는다. 실행이 AWS-11 구간과 겹치거나 시각·Pod 귀속을 확인할 수 없으면 제외했다고 단정하지 않고 AWS-11 판정을 재검토한다.

## C. 복구·증거·Stop

1. Tetragon TG-SECRET-01은 monitor manifest와 실제 spec·읽기 성공으로 확인한다. enforce가 남으면 [설계 문서](../../docs/Tetragon_차단_설계.md) 5절대로 해당 규칙을 삭제하고 승인 monitor를 적용한다. SGLang 캐시·Deployment·host service를 원래 상태로, vLLM monitor 묶음과 `current` 상대 링크·Gateway Pod를 원래 승인 판본으로 되돌린다. 정상 200/401, collector `ok`, 승인 `verified`를 확인한다.
2. 사례별 보고서와 묶음 ID/해시, 정책 UID/적용·복원 시각, errno 번호, 일치 필드/건수, 지표 **이름** 대조표, SP1 상대 경로·용량, 대시보드 검증 결과만 `evidence-<date>`에 정리한다. 서버에서 반출 대상만 토큰·키·IP/호스트·실명·요청 본문·원시 로그·지표 값 패턴을 검사하고 문제 파일은 서버에서 가린다. 노트북 수신 뒤 파일 수·SHA-256과 민감값 검사를 반복한다.
3. 복구·증거 반출을 확인한 뒤 Stop을 요청하고 실제 `stopped` 상태·UTC 시각을 적는다. 복구 실패면 비용보다 상태 복구를 먼저 처리하고 담당 역할에 전달한다.

## 시간·비용과 중단 순서

계획치: 가동·preflight·묶음 20~35분, vLLM monitor/차단/복원 25~40분, SGLang 전환·시험 35~55분, 커널·지표·캐시·화면 대조 20~30분, 복구·증거·Stop 25~40분 = **125~200분, 약 USD 2.50~4.00** (125/60×1.2, 200/60×1.2). 3회차 계획의 가동 20~35분·복구 25~40분, 보존된 SGLang 빈 캐시 부팅 약 4분 20초를 기준으로 했고, 새 차단·화면·지표 구간은 시험 계획 추정이다. 서버 지연·재시도·차단 복구는 추가 비용이다. 서버 비용 0인 A 준비 시간은 제외한다.

**마지막 40분은 복구·증거·Stop에 확보한다.** 시간이 부족하면 ① 대시보드 화면 대조 ② SP1 캐시 경로 분석 ③ 두 번째 엔진의 지표 이름 대조 순으로 생략한다. 시작한 AWS-20의 monitor 복원, Gateway 묶음 복귀, 엔진 전환 복구는 생략하지 않는다. 커널 근거가 불명확하거나 monitor 기준선이 실패하면 enforce 적용을 시작하지 않는다.
