# 기업·runtime 입력 요청 목록 (개발 담당, 2026-11-06)

이 목록의 값이 없으면 해당 점검은 lab 실측을 마쳐도 보안 판정이 UNKNOWN으로 남는다. 우리 쪽에서 예시 값으로 채우지 않는다(EXAMPLE 값은 공식 결과가 아니다).

- 각 점검의 정책 키 가운데 `*_environment_sha256`·`*_target_sha256`·`*_prepared_sha256`·`*_session`·`*_validity_*`처럼 실행에 묶이는 값은 실행 도구가 채운다. 여기서는 묻지 않는다.
- "받을 곳"은 값을 정하거나 기록을 만들어 줄 주체다. **기업**은 보안·운영·자격 관리 담당, **runtime**은 BYUL runtime(Gateway·observation feed) 담당이다.
- 근거: 현행 팩 `PACK-BASELINE@33`의 점검 정의(`policy_prose.enterprise_decisions`, `unknown_criteria`), 2026-11-05 GPU 기록([gpu-20261105.md](gpu-20261105.md)).

| 요청 | 이유 | 받을 곳 |
|---|---|---|
| 정책 확정자와 팩 검토자 지정 | 지금 정책·팩이 모두 DRAFT라 결과가 `official=false`다 | 기업 |
| 점검별 영향도(`impact`: HIGH/MEDIUM/LOW) | 77개 모두 비어 있어 우선순위·보고 집계에 쓰지 못한다 | 기업 |

## 1. 개발 담당 점검 (12개 + LIF-13 1개)

### 접근·권한

**REQ-02 — 경로가 바뀌어도 최종 API에 인증·권한 검사가 적용되는가**
- 지금: GPU에서 기록·native 수집은 모두 COMPLETED. 기록 생산자와 인가 결정의 인증이 없어 UNKNOWN.
- 요청:
  - 허용 경로 목록과 Gateway 경로 재작성 규칙(어떤 외부 경로가 어떤 내부 API로 가는지)
  - Gateway가 전달하는 신원 형식과 직통 접근 허용 주체·목적
  - 경로 기록 생산자(Gateway)의 기록 봉인·생산자 인증 방식
- 받을 곳: 기업(경로·신원 규칙), runtime(기록 봉인·인증)

**REQ-03 — 일반 사용자가 허용받지 않은 관리·진단 작업을 할 수 없는가**
- 지금: runtime Gateway의 관리 경로(관리자 `/metrics` 포함)가 404라 security UNKNOWN, functional FAIL.
- 요청:
  - `general_allowed_kinds`: 일반 사용자에게 허용하는 작업 종류 목록
  - 관리 역할 정의와 관리·진단 경로 목록(어떤 역할이 어느 경로를 쓰는지)
- 받을 곳: 기업(역할·허용표), runtime(관리 경로 노출 방식)

### 응답·정보 노출

**REQ-13 — 응답 옵션과 오류 메시지가 허용된 정보만 반환하는가**
- 지금: 엔진 직통은 금지 반환 옵션을 받아들여 FAIL, Gateway는 3개 옵션 모두 400 거부.
- 요청:
  - `allowed_response_fields`: 수신자에게 허용하는 응답 필드
  - `allowed_error_fields`: 허용하는 오류 응답 필드
  - `forbidden_return_options`: 금지할 반환 옵션(예: 입력 사본·logprobs 계열을 쓰는지)
  - `required_targets`: 판정 대상(엔진 직통·Gateway 중 어디까지)
- 받을 곳: 기업

**REQ-17 — 캐시 적중 시간 차이로 비공개 정보가 드러나지 않는가**
- 지금: 통계 설계와 11-03 GPU 표본·오버헤드 대조는 끝. 판정 기준이 없다.
- 요청:
  - `cache_timing_max_auc_percent`: 허용하는 최대 AUC(%)
  - `cache_timing_min_samples`: 최소 표본 수
  - 캐시 공유 단위(사용자/서비스 계정/tenant)와 공개 prefix 공유 여부
- 받을 곳: 기업

### 네트워크·자격

**PLT-07 — 엔진의 외부 송신이 허용된 목적지·작업에 한정되는가**
- 지금: 금지 수신기 연결 FAIL, 차단 뒤에는 집행 증거가 없어 UNKNOWN.
- 요청:
  - 허용 목적지·포트·프로토콜·작업 목록
  - 정책이 끊겼을 때의 동작(마지막 정책 유지/만료/초기 부재)
  - 차단 집행 감사 기록(어느 장치가 차단했는지 남기는 기록)과 그 생산자
- 받을 곳: 기업(허용표·동작), runtime 또는 네트워크 정책 담당(집행 감사)

**PLT-10 — 자격 철회 뒤 새 접근을 기한 안에 거부하는가**
- 지금: 대조 키·퇴역 키가 handler 전에 거부되는 것은 수집. 발급자 사건이 없어 UNKNOWN.
- 요청:
  - 철회 대상 자격과 발급자(`revocation_issuer_id`)
  - 전파 기한 `revocation_propagation_limit_ms`, 허용 시계 오차 `revocation_max_clock_skew_ms`, 기한 기준 `revocation_deadline_basis`
  - 발급자의 철회 사건 기록(사건 ID·시각)과 그 생산자
- 받을 곳: 기업(자격 관리)

**PLT-11 — 이미 열린 연결도 철회 정책대로 제한되는가**
- 지금: 실행 불가. lab에는 살아 있는 연결 중에 철회할 수 있는 발급자가 없다(vLLM 고정 키).
- 요청:
  - 열린 연결 중에 자격을 철회할 수 있는 IdP 또는 runtime 자격 철회 기능과 그 사건 기록
  - 진행 중 연결 처리 정책 `session_residual_policy`, 최대 대기 `session_max_wait_seconds`, 전파 기한·시계 오차
- 받을 곳: 기업(IdP), runtime(자격 철회)

**PLT-12 — 폐기 자격의 남은 사본에 교체·회수·삭제 기준이 적용되는가**
- 지금: 사본 목록과 그 기록 생산자는 기업 자격 관리의 사실이라 lab에서 만들지 않는다.
- 요청:
  - 폐기 대상 자격의 사본 목록(비밀 저장소·환경변수·파일·백업 위치와 수신자)
  - 사본별 처리 방법·기한·보존 예외
  - 처리 결과 기록과 그 생산자, 최대 기록 지연 `copy_max_record_delay_ms`
- 받을 곳: 기업(자격 관리)

### 기록·관측

**OBS-01 — 필수 접근·관리·승인 기록으로 누가 무엇을 했는지 확인할 수 있는가**
- 지금: Gateway 파일 소유·bytes와 허용/거부/후속 기록을 수집. 봉인·생산자 인증·독립 사건 증명이 없어 UNKNOWN.
- 요청:
  - `observation_required_events`: 필수 사건 목록
  - `observation_required_fields`: 사건별 필수 필드
  - `observation_max_delay_ms`: 기록 지연 한도
  - 사건별 책임자와 증거 전달 방식
  - Gateway 기록의 봉인·생산자 인증 방식(현재 끝 표식 없는 추가 전용 파일)
- 받을 곳: 기업(사건·필드·기한), runtime(봉인·인증)

**OBS-05 — 허용한 사용 통계 보고가 정한 항목·목적지를 지키는가** (측정 남음)
- 지금: 허용 구성 추론 PASS. 실제 보고 전송은 관측하지 못해 UNKNOWN.
- 요청:
  - `usage_allowed`: 사용 통계 보고를 허용하는지
  - `allowed_usage_fields`·`allowed_usage_sinks`·`usage_report_paths`: 허용 필드·목적지·경로
  - 허용한다면 양성 대조를 위해 시험용 수신 목적지를 쓸 수 있는지
- 받을 곳: 기업

**OBS-06 — 기록·진단 사본의 조회·반출을 허용 주체로 제한하고 저장 암호화를 적용하는가**
- 지금: RBAC 허용 읽기와 무권한 오류를 수집. 로그 사본 목록과 거부 감사 증거가 없어 UNKNOWN.
- 요청:
  - 자료별 허용 독자·반출 목적·승인자
  - 로그·진단 사본 목록(위치·보존 기간)
  - 저장 암호화 요구, 복호화 역할, 키 관리 책임
  - 거부된 조회의 감사 기록과 그 생산자
- 받을 곳: 기업

**OBS-09 — 요청 값으로 로그의 사용자·대상·상태를 위조할 수 없는가** (열린 질문)
- 지금: 참조 수집기 경계 복원을 구현했고 GPU 재측정이 남았다. CRI 로그를 줄 단위로 읽는 수집기는 입력 줄바꿈을 별도 사건으로 볼 수 있다(k3d에서 확인).
- 요청:
  - 실제 기업 로그 수집기 종류와 읽는 위치(노드 로그 파일 tail인지 등)
  - 기업 수집 경로를 OBS-09 판정 대상에 넣을지 여부
- 받을 곳: 기업

**OBS-11 — 기록 수집 중단·누락·시각 오류를 표시하고 증거 부족 시험을 미확인으로 처리하는가**
- 지금: Kubernetes 읽기 경로는 구현. 수집 상태 기록을 만드는 생산자가 없다.
- 요청:
  - `required_records`: 필수 기록 종류
  - 기록별 `collection_deadline_ms`·`max_clock_uncertainty_ms`·`detection_deadline_ms`·`alert_deadline_ms`
  - 수집 상태 기록의 생산자(기업 수집 파이프라인 또는 runtime observation feed의 heartbeat·공백 표식)
  - 수집기 중단·복구 절차와 중단 시 운영 유지/제한/중단 방침
- 받을 곳: 기업(기한·절차), runtime(observation feed)

### 수명

**LIF-13 — 공유 가중치 해제 후 재취득·대체 공급이 승인·수명 기준을 지키는가** (GPU 재측정 뒤에도 남음)
- 지금: 세대 결합과 정본 실행 안의 소비자 동작을 구현. GPU 재측정이 남았고, release 주체의 인가 정책이 없어 그 부분은 UNKNOWN으로 남는다.
- 요청:
  - 공유 가중치 release를 허용하는 주체와 조건
  - release 뒤 기존 참조·후속 소비자 처리(재취득 허용, 디스크 fallback 허용 여부, 강제 종료 여부)
- 받을 곳: 기업

## 2. GPU 담당 점검 중 기업 입력 대기 (참고)

**PLT-08 — 각 통신 구간에서 상대 인증과 기밀성·무결성 기준을 지키는가**
- 지금: 평문 독립 FAIL을 보존. 실제 호출 앱·Gateway/TLS 구성이 필요하다.
- 요청: 구간별 암호화 요구, TLS 종료 위치, 신뢰할 인증기관, 상대 인증 방식, 예외와 유효기간, 평문 금지 여부(`plaintext_forbidden`)
- 받을 곳: 기업

## 3. 요청 순서 제안

1. 공통 0절(확정자·검토자·운영 구성): 모든 결과의 공식 여부를 정한다.
2. 값만 정하면 바로 판정이 가능한 것: REQ-13, REQ-17, OBS-05, REQ-03의 허용 작업 목록.
3. 기록 생산자가 필요한 것: runtime과 함께 OBS-01·REQ-02(봉인·인증), OBS-11(feed), PLT-07(집행 감사).
4. 자격 관리 시스템이 필요한 것: PLT-10·11·12.
5. 운영 구조 확인이 필요한 것: OBS-06, OBS-09 수집기, LIF-13 release 정책, PLT-08.
