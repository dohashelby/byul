프레임워크는 **보안 목표·신뢰 가정, 거버넌스, 위험 관리, 보안 기능과 보호 요구, 환경별 적용, 생명주기, 평가·개선**으로 구성한다. 기술적 요구는 여덟 보안 기능으로 정리하고, 각 요구의 담당자·적용 조건·확인 시점을 관리 절차에서 정한다.

| 구성요소 | 맡는 역할 | 이 자료에서 확인할 내용 |
| --- | --- | --- |
| 보안 목표 | 보호 자산, 공격자와 경계, 엔진·주변 환경의 책임 및 보호가 성립하는 조건을 정한다. | 보호 자산·공격자·경계·환경 책임 |
| 거버넌스 | 정책 소유자와 제출·검증·승인·운영 역할, 직무 분리·교육·예외 승인을 정한다. | 정책 소유자·담당 역할·권한 분리·예외 |
| 위험 관리 | 위협·취약 원리에서 요구를 도출하고 영향·우선순위·수용·보완·사고 대응을 관리한다. | 17개 취약 원리·83개 시나리오·위험 처리 |
| 보안 기능과 보호 요구 | 여덟 기능의 36개 요구에 방어 위치·범위·한계와 CHK를 대응시킨다. | 여덟 기능·36개 보호 요구·77개 CHK |
| 환경 확인 | 호출·배포·공유 구조, 실제 활성 기능과 집행 주체에 따라 적용 범위를 결정한다. | 실제 호출·공유·배포 구조와 선택 기능 |
| 생명주기 | 도입부터 폐기까지 요구를 적용·확인할 시점과 담당 역할을 정한다. | 도입·반입·배포·운영·변경·복구·폐기 |
| 보호 요구의 적용과 검증 | 정상 대조·조건·증거에 따라 판정하고 보완·재시험·재평가한다. | 증거·판정·보완·재평가 |

구성도의 보안 관리에는 거버넌스와 위험 관리가 포함된다. 보호 요구를 적용할 때는 환경을 확인하고 점검·시험을 고른 뒤, 통제 동작과 증거를 확인해 판정·보고한다. 위협을 분석할 때 보호 범위와 신뢰 가정도 함께 검토한다.

목표와 거버넌스가 보호 수준과 책임을 정한다. 위협 분석 결과에서 요구를 도출하고, 실제 환경에 적용할 대책과 점검을 고른다. 생명주기의 각 단계에서 요구를 적용·평가하며, 발견한 문제와 변경 사항을 위험 관리에 반영한다.

## 1. 목표와 범위

보안 목표는 **기밀성·무결성·가용성·책임 추적성**이다. 요청·모델·실행 상태와 기록을 보호하고, 허용된 작업을 안정적으로 처리하며 행위와 변경을 추적한다. 기술적 범위는 서빙엔진과 직접 맞닿은 Gateway·호스트·저장소·네트워크·배포·관측 접점이다.

| 확인할 경계 | 정할 내용 |
| --- | --- |
| 엔진과 주변 구성요소 | 인증·인가·망 제한·암호화·파일 권한을 실제로 맡는 구성요소 |
| 계정·프로세스·cluster | 같은 UID·Ray cluster 등에서 공유하는 권한과 침해 시 영향 범위 |
| 요청·사용자·캐시 | 공유를 허용한 집단, 요청 상태의 소유자, 재사용 가능한 조건 |
| 공통 요구와 참조 구현 | 공통 요구는 엔진·버전별로 적용하고, vLLM 0.31.0은 코드·시험의 참조 구성으로 사용 |

서버·저장장치·관리망의 보호는 필요한 운영환경 조건과 담당 책임으로 기록한다. 모델 학습 전체와 업무 앱 전체 감사의 범위는 프로젝트 소개에서 구분했다.

### 보안 목표

보안 목표는 보호할 자산이 유지해야 할 성질이다. 기밀성·무결성·가용성·책임 추적성을 다음과 같이 정의한다.

| 보안목표 | 보호할 성질 |
| --- | --- |
| 기밀성 | 비공개 입력·결과·상태·공급물·자격·관측 자료가 허용된 독자·공유 집단·목적지 밖에 공개되거나 추정되지 않도록 한다. |
| 무결성 | 신원·입력·공급물·결과·실행 및 승인 상태가 허용된 대상·변환·문맥과 일치하고, 비허용 변경·혼입·허위 상태 수용을 제한한다. |
| 가용성 | 채택한 자원·시간·서비스 조건에서 정상 처리 기회를 유지하고, 실패·종결·재기동을 관리한다. |
| 책임 추적성 | 필수 사건을 주체·대상·실행과 연결하고, 기록의 정확성·보존·수집 상태를 확인해 행위와 결정을 추적할 수 있도록 한다. |

기술적 보호 기준은 [4절](#framework-requirements)에서 보안 기능 8개와 그 아래의 보호 요구·점검 순서로 설명한다.

## 2. 거버넌스

조직은 정책과 담당자를 정하고, 기술적 통제가 실제로 적용되는지 검토한다. 제출·검증·승인·배포·운영 역할의 분담과 겸임 조건을 기록하고, 담당자가 필요한 지식과 권한을 갖추도록 교육한다.

| 관리할 내용 | 남길 결정·기록 |
| --- | --- |
| 정책·보호 수준 | 허용 대상·금지 행위·예산·기한·보존 기준과 정책 버전 |
| 역할·직무 분리 | 정책 소유자, 제출자·구현자·검증자·승인자·운영자, 겸임 시 검토 방식 |
| 예외·위험 수용 | 사유·영향·보완 통제·승인자·유효기간·재검토 조건 |
| 교육·대응 역량 | 권한 사용, 코드·공급물 취급, 증거 수집, 사고 보고·복구 담당 교육 |

역할 분담은 조직이 결정하고, 1.3 승인 권한 분리에서는 실제 계정과 집행점이 정한 역할을 따르는지 확인한다. 예외를 승인한 경우에도 원래의 미충족·미확인 결과와 남은 위험을 보존한다.

### 조직별 정책 채택과 변경 검토

정책 소유자는 03의 참조 정책에서 그대로 채택할 기준과 조직이 채울 허용 대상·수치·기한을 구분한다. 보안 검토자는 다음 내용을 확인하고 정책 승인자가 적용 판본과 시점을 확정한다.

| 검토 단계 | 확인하고 남길 내용 |
| --- | --- |
| 적용값의 근거 | 관련 보호 요구·CHK·환경, 허용 대상·공유 범위, 수치의 단위·측정 구간·조건을 연결한다. 예산은 정상 서비스에 필요한 자원과 허용 손실, 기한은 보호할 사건과 대응 필요 시간을 근거로 정한다. 현재 설정값과 근거 없이 같게 두지 않는다. |
| 보호 요구와의 일치 | 채택값이 기존의 승인 일치·비허용 접근 거부·격리·필수 기록 등 확정된 조건을 유지하는지 확인한다. 시험에서 그 기준의 충족·위반을 구별할 수 있는지도 [증거 채택 검토](06_평가와_솔루션_런타임.md#증거-충분성과-채택-검토)로 확인한다. 충돌하거나 근거가 부족한 정책은 보완 대상으로 남기고 그 값에 의존하는 충족 판정을 보류한다. |
| 변경 영향과 승인 | 변경 이유·전후 값·영향 CHK와 분기·집행 위치를 대조하고 승인자·적용 시점·정책 판본을 남긴다. 분기 재선정과 재시험 대상, 재사용할 증거와 유효한 이유를 함께 검토한다. |

정책값을 바꿔 재평가할 때는 이전 정책의 결과를 보존하고 새 판본의 결과를 따로 남긴다. 확정된 보호 요구·CHK 판정 기준 자체에 결함이 발견되면 프레임워크 담당자가 근거와 영향 항목을 검토해 개정안을 작성하고, 기준 승인 후 관련 항목을 재평가한다. 조직의 적용값 조정과 기준 개정을 구분하며 CHK 고정 ID와 과거 결과를 유지한다. 예외의 승인·기한·남은 위험은 위 관리체계의 기록을 재사용한다.

플랫폼·개발·시험 담당자는 집행 가능 범위·정상 서비스 요구·측정 방법과 실제 값을 제공한다. 프레임워크 담당자는 검토 절차와 보호 요구의 일관성을 관리하고, 조직의 정책 소유자·승인자가 실제 적용값을 정한다.

### 거버넌스 결정과 후속 처리

정책 소유자·검토자·승인자와 보완 담당자는 조직이 배정한다. 아래 상황은 기존 정책·예외·후속 기록에서 처리하며, 해당 대상·CHK·판본과 결정·후속 근거를 연결한다.

| 상황 | 검토·결정할 사람과 일 | 후속 담당과 확인할 결과 |
| --- | --- | --- |
| 정책값 미정 | 보안 검토자는 미정값과 영향 CHK를 정리하고, 정책 소유자는 필요한 근거를 모아 안을 작성한다. 정책 승인자가 기준값·판본·적용 시점을 확정한다. 소유자·승인자가 미지정이면 조직의 역할 지정 권한자에게 배정을 요청한다. | 플랫폼·시험 담당자는 집행 가능 범위·측정 근거를 제공하고, 정책 소유자는 결정 담당·후속 시점을 기존 기록에 남긴다. 값에 의존하는 판정은 미확인을 유지하고, 값이 확정되면 영향 시험·증거의 재평가와 실제 적용 상태를 확인한다. |
| 역할 겸임 | 정책 승인자가 실제 담당·계정, 허용할 겸임 범위와 보완·독립 검토 조건을 정한다. 보안 검토자는 해당 조건의 충족을 확인한다. 정한 검토 조건을 확보하지 못하면 조직의 역할 지정 권한자에게 검토·승인 역할 재배정을 요청한다. | 역할 지정 담당은 배정·겸임 조건을 남기고 운영·개발 담당은 실제 계정 권한 반영 근거를 제공한다. CHK-SUP-001의 승인 권한 분리는 실제 승인 기록 변경 결과로 별도 확인한다. 겸임 결정과 검토·승인 결과는 같은 대상 기록에 연결한다. |
| 필수 검사 미확인 | 시험 담당자는 부족한 증거와 보완·재시험안을 제시하고, 보안 검토자는 증거 충분성과 대체 검사 동등성을 검토한다. 승인자는 CHK-SUP-014의 채택한 보류 조건 안에서 보완·재검사 또는 허용된 대체 검사 사용을 결정한다. | 보완 담당·기한·확인할 증거를 기존 후속 기록에 남기고 검사 원결과·관리 결정·실제 사용 전이를 대조한다. 팀 참조의 필수 증거 부족은 보류를 유지하며, 이미 확인된 위반과 원결과는 보존한다. 처리 해소는 요구 증거와 후속 판정으로 확인한다. |
| 예외 만료 | 운영의 예외 관리 담당은 만료·대상 범위·보완 이행·남은 위험을 확인해 원 승인권자 또는 현재 지정된 승인권자에게 재검토를 요청한다. 승인권자는 예외 종료 또는 새 유효기간·조건의 재승인을 결정한다. | 만료된 허용은 유효한 예외로 사용하지 않는다. 운영 담당은 승인 공백이 있는 영향 대상을 원래 정책의 보류·접근 제한 등 해당 절차로 처리하고 실제 적용을 확인한다. 예외 관리 담당은 이전·후속 결정과 처리 근거를 연결하고, 보안 검토자는 영향 CHK의 재확인 결과를 검토한다. |

결정권자는 보완 담당과 확인 시점도 정한다. 보안 검토자는 필요한 증거·재시험·정책 적용 결과가 확보됐는지 검토하고 미결 항목을 다음 담당에게 인계한다. 예외·겸임·위험 수용 결정과 CHK 판정은 기존 기준에 따라 각각 유지한다.

프레임워크 담당자는 결정 주체·후속 담당·해소 근거의 누락과 기존 기준의 일관성을 검토한다. 조직의 정책 소유자·승인자는 실제 값·겸임·예외를 결정한다. 개발·시험 담당자는 권한·보류·만료 처리의 구현·계측·실행 근거를 제공하고 자동 알림·저장·연동 방식은 개발팀이 설계한다.

## 3. 위험 관리

**자산·공격자·정상 및 실패 흐름 → 위협·취약 원리 → 보호 요구 → 대책·집행 위치 → CHK·증거·판정** 순서로 도출 근거를 확인한다. 위협뿐 아니라 조직 정책과 운영환경의 보호 조건도 요구의 근거로 기록한다.

공격·실패는 17개 원리로 설명한다. 시나리오 83개는 위협 후보 73개, 실패·오설정 9개, 공유 실행 권한의 침해 범위 1개다. 기존 24개 묶음은 동작·공격 접점을 찾는 분석 색인이다. 각 시나리오의 영향과 대책 효과는 실제 조건과 실행 증거로 확인한다.

위험의 영향·가능성·노출·공격자 권한·기존 통제를 검토해 우선순위를 정하고 보완·회피·수용을 결정한다. 이상을 발견하면 담당자에게 보고하고, 정한 권한에 따라 격리·자격 철회·증거 보존·복구·재평가를 수행한다. 새로운 위협이나 구성 변경도 같은 검토에 반영한다.

## 5. 환경별 적용

업데이트에서는 변경 근거를 실제 경로·자산·신뢰 경계·보호 조건에 대조하고 관련 요구·CHK·분기와 선정 이유를 남긴다. 시험·증거 재사용 범위와 남은 확인·담당을 함께 인계한다. [05의 공통 인계 규칙](../05_평가와_증거관리.md#update-impact-handoff)과 [06 평가 흐름](06_평가와_솔루션_런타임.md#62-평가-흐름)을 따른다.

1. 실제 호출·공유·배포 구조, 엔진·버전·활성 기능과 권한을 확인한다.
2. 각 CHK의 적용 조건과 추가 시험 조건을 확인해 점검을 고른다.
3. 허용표·정책값·수치를 정하고 어느 구성요소에서 보호를 집행할지 정한다.
4. 사용·노출 여부를 모르는 기능은 적용 판단을 미정으로 남긴다. 적용은 분명하고 판정값이 부족하면 미확인으로 남긴다.
5. 해당 없음에는 기능의 비사용·비노출과 근거가 유효한 범위를 기록한다.

[03 체크리스트](04_환경별_적용과_체크리스트.md#환경정책-확인)에서 호출 경로·사용자 신원·캐시 공유·실행 모드 등 환경별 확인 내용을 읽는다.

## 6. 생명주기

일곱 시점의 수행·검토·승인 책임과 증거를 아래에 정리했다. 실제 담당자와 정책값을 배정하고 실행 결과를 남길 때 사용한다.

- 일곱 시점에서 필요한 활동을 수행한다. 변경과 업데이트, 복구는 해당 사건이 발생할 때 수행하고, 재개 조건을 확인한 뒤 운영으로 돌아간다.
- 각 시점의 점검은 검토 후보다. 02의 환경 확인과 CHK별 시험 분기로 실행 대상을 정하고, 선정·비적용·미정의 이유를 기록한다. 변경·복구의 영향 범위가 후보보다 넓으면 다른 점검도 검토한다.
- 아래 역할은 조직이 배정할 책임이다. 실제 담당자·검토자·승인자와 권한, 겸임 시 보완 절차는 조직이 지정한다. Gateway·엔진·OS·망·저장소는 통제 집행 위치로 기록한다.
- 기존 증거를 재사용할 때는 대상·구성·정책·시험 절차 버전과 수집 상태가 여전히 유효한지 확인한다. 원 실행 ID·증거 출처·시각·적용 한계와 재사용 이유를 남기고 달라진 조건은 다시 확인한다.
- CHK 판정과 사용·위험 수용 결정을 각각 기록한다. 미충족·미확인은 해당 상태로 유지하고, 예외에는 사유·허용 범위·잔여 위험·승인자·유효기간·재검토 계기를 적는다.

| 도입과 설계 | 서비스 설계 담당자, 서빙엔진 운영 담당자, 보안정책 담당자 | 정책·설계 기준 승인 |

#### 단계 사이에 넘길 결과

정상 도입은 도입과 설계, 반입과 검증, 배포와 기동을 거쳐 운영으로 이어진다. 운영 중 변경과 장애·사고가 생기면 영향받는 확인으로 돌아가고, 변경·복구 뒤 실제 상태를 운영에 다시 넘긴다. 폐기 시점에는 서비스 종료 결과와 남은 보존 관리를 인계한다. 각 경로는 발생한 사건과 적용 조건에 따라 사용한다.

기존 선정·평가·승인·배포 기록을 서로 참조해 사용한다. 받는 담당자는 인계된 대상·구성·정책 판본이 자신이 처리할 대상과 일치하는지 확인한다. 증거·판정·예외·미결 항목은 원 기록을 참조한다.

| 단계 | 받아 확인할 것·최초 확인 | 넘길 결과·받는 곳 |
| --- | --- | --- |
| 도입과 설계 | 서비스 목적·보호 자산·실제 환경을 바탕으로 범위·신뢰 경계·역할·정책과 시험 계획을 처음 정한다. 변경으로 이 전제가 달라지면 해당 설계 판단을 다시 확인한다. | 승인한 범위·정책·역할과 선정 기록을 반입·배포 담당에게 넘긴다. 변경·복구에서 다시 검토한 판단은 그 담당에게도 돌려준다. 미정 정책값과 뒤에서 처음 실행할 시험은 담당자·확인 시점을 기존 후속 확인란에 연결한다. |
| 반입과 검증 | 설계·현재 정책과 공급물 식별정보를 받아 실제 사용할 파일·의존성·reader·코드의 승인 범위와 필수 검사 원결과를 확인한다. | 사용 승인 대상의 식별정보·검사/예외 근거·보류 항목을 배포 담당에게 넘긴다. 변경·복구에서 새 공급물이 필요할 때도 같은 결과를 해당 담당에게 연결한다. 실제 적재 일치는 배포의 CHK-SUP-006에서 이어 확인한다. |
| 배포와 기동 | 승인 대상·정책·선정 시험을 받아 실제 배포·적재 대상과 대조한다. 실제 집행·worker 준비·정상 요청을 선정 범위에서 처음 확인하고, 이전 증거를 쓰는 범위는 기존 재사용 원칙으로 검토한다. | 확인한 실제 실행 구성·정책 판본, 시험/증거 참조, 개방 결과와 미결 항목을 운영 담당에게 넘긴다. 변경·복구에서 수행한 확인 결과는 해당 결정 담당에게 연결한다. 운영에서는 이 실제 구성과 관측 대상을 기준으로 삼는다. |

- **변경·복구에서 다시 여는 확인:** 신뢰 경계·공유·책임·보호 수준의 변화는 도입과 설계의 해당 판단으로, 공급물·reader·공급원 변화는 반입과 검증으로, 실제 배치·적재·준비·라우팅 변화는 배포와 기동의 해당 확인으로 연결한다. 복구에서는 현재 승인·철회와 복원 후 잔존 상태를 함께 대조한다. 영향 시험과 재사용 증거는 02의 선정 목록 검토와 위 증거 재사용 원칙을 적용한다.

## 7. 평가와 보완

판정 단위는 CHK다. 문서·설정·코드 확인과 정상 대조·실행 시험으로 필요한 증거를 확보하고 충족·미충족·미확인·해당 없음을 기록한다. 요구가 여러 CHK에 걸치면 각 요구에 해당하는 세부 결과를 확인한다.

필수 사건의 기록이 누락되면 해당 기록 요구를 판정하고, 그 기록이 필요한 다른 시험은 확보한 증거 수준으로 판단한다. 수집 경로의 건전성은 시스템 요구이고, 증거 부족을 미확인으로 남기는 것은 평가 절차다. 보완 후 관련 CHK를 재시험하고, 정책·구성·기능이 바뀌면 적용 범위와 시험을 다시 검토한다.

구체적인 시험·판정·보고 흐름은 [05 평가·증거·솔루션](06_평가와_솔루션_런타임.md)에서 설명한다. 업데이트 검증과 런타임 도구는 이 체계의 일부 점검·집행·관측을 지원한다. 실제 지원 범위와 미구현·미실행 상태는 별도로 기록한다.
