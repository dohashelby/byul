## 1. 평가 대상과 기록 단위

평가 결과마다 **CHK 고정 ID + 관련 Q/SC + 선정 시험 분기 + 실행 시험 + 절차 판본 + 환경·정책 버전**을 함께 기록한다. 하나의 세부 점검이나 Q에 여러 구현 분기가 있으면 분기별 결과를 남긴다. 같은 실행의 증거는 재사용하되 각 보호 요구의 판정은 따로 한다.

환경에는 server/backend/engine과 commit·이미지 digest·설치 의존성, 모델/config/tokenizer/code·형식·revision·GPU/driver·executor·활성 기능·실제 설정을 기록한다. 정책에는 승인자·판본, 허용 집합과 수치·단위·측정 조건·예외 기한을 기록한다. 값의 출처와 확인 시각도 남긴다.

<a id="시나리오와-하위-시험의-기록-단위"></a>
## 1.1 시나리오·Q·세부 점검의 관계

CHK는 점검 항목, Q는 도출 근거, SC는 위협·실패 상황을 식별한다. 보호 요구는 현행 36개 요구를 뜻하며, 기존 목적 앵커는 참조 정책 원문으로 이동할 때 사용한다. 03·JSON에서 목적→CHK→Q/SC와 역참조를 확인할 수 있다. 같은 Q/SC를 참조해도 CHK별 보호 요구·집행점·판정은 유지한다. CHK 안의 필수 세부 결과도 각각 기록한다. 확인된 위반은 미충족, 필수 증거 부족은 미확인으로 남긴다. 기존 `subtest_ids`는 시나리오별 공유 시험 초점의 참조이며 고유 실행 ID를 대신하지 않는다. 실행·증거를 재사용하는 범위와 실행기·저장 schema는 개발팀이 설계한다.

현재 83개 시나리오에 주 평가 질문을 하나씩 연결해 시나리오별 시험 초점 83개를 두었다. 동일 시험이 여러 점검의 근거로 쓰이면 실행 ID와 증거를 공유하고 CHK별 기준으로 판정한다. 질문 관계 수와 실제 시험 수는 따로 집계한다. 실제 환경에서는 하나의 설계도 엔진·backend·상태 조합에 따라 여러 시험으로 나뉠 수 있다.

03의 하위 시험 표와 data/checklist.json에 적용 조건·공격자·접점·확인 방법을 기록했다. 실제 실행 전에는 대상 판본·정책값·정상 동작을 확인할 대조 입력·실패 주입 방법·계측·중단 및 복구 절차를 채운다. 83개 시험 초점을 실행 가능한 자동 시험으로 구현하는 작업은 남아 있다.

### 공통 확인·분기·필수 결과의 기록

공통 확인, 112개 조건별 분기, 네 CHK의 필수 결과 9개는 여러 방식으로 연결된다. 한 실행이 여러 범위의 증거를 제공하고 한 결과에 여러 실행·검토가 필요할 수 있다. PLT-008은 내부 IPC·TP 분기와 함께 실제 API 전송 보호를 각각 남긴다. REQ-005의 모델 권한/사용 종료, LIF-013의 release/재취득·대체 공급/기존 참조 수명, OBS-006의 조회·반출/암호화·복호화도 각각 기록한다.

적용 판단, 도구 지원, 시험 선정, 수행, 수집과 판정을 구분한다. 적용 범위의 확인된 위반은 미충족으로 보존하고, 필요한 공통 확인·세부 결과·증거가 부족하면 전체 충족을 보류한다. 조건부 결과의 비적용은 해당 범위 근거와 함께 남긴다. 주·보조 보호 요구에는 실제 확인한 범위의 증거만 연결한다.

선정 목록 완결성은 특정 환경·정책·내용 판본·시점의 기대 범위를 빠짐없이 적용 판단했는지다. 수행 범위 완결성은 선정한 적용 범위의 정상 대조·절차·필수 관측과 결과가 충분한지다. case의 `subtest_inventory_complete` 하나로 전체 선정 목록을 확정하지 않는다. 상세 정보·채운 형식과 개발팀 선택은 [결과 기록 최소 명세](개발전달/결과기록_최소명세_초안.md)를 따른다.

## 1.2 환경·버전이 달라질 때 남길 기록

03의 77개 항목은 보호 요구를 판정하는 세부 점검 기준이다. 각 항목에는 기존 Q 28개·SC 83개가 여러 개씩 연결된다. 실행 가능한 자동 시험은 별도로 구현한다. 동일 Q/SC에 여러 세부 확인이 연결될 수 있으므로 결과에는 주 보호 요구·세부 점검·문서/절차 판본·기존 Q/SC·선정 분기·실행 ID를 함께 기록한다. 기존 ID와 결과 이력은 보존한다.

처음 보는 버전의 지원 상태와 시험 결과는 분리한다. 구현 매핑 검토 필요, 시험 연결 코드(adapter) 미지원, 분기 미도달은 자동 통과로 처리하지 않는다. 결과 비교에는 현재/후보 환경의 수집 출처·시각·자료 hash·정책·시험 버전을 포함한다. 이전 버전의 통과 결과를 새 환경에 적용하려면 증거의 유효 범위를 다시 확인한다. 담당자는 미확인 항목까지 검토해 적용 여부를 판단한다. 기록·자동 수집·adapter 선정의 연동은 구현·실행 전이다.

### 기능·실패·복원별 기록 주의사항

기능·실패 유형·rank·backend별 결과를 나눠 기록한다. 기존 한 행의 verdict만으로 모든 분기 충족을 표시하지 않는다. 접근 허용/거부·권한/정책 변경·관리 작업 중 필수 사건을 정책으로 정하며 본문 전체 로깅을 강제하지 않는다. 복원은 배포 template·외부 설정·volume·Gateway/IAM별 실제 대상과 책임·재개 증거를 남긴다. 관측 외 모델·입력·임시/cache/backup 사본도 Q-C12에 연결해 수명·접근·삭제를 확인한다. 정책 결정과 실제 시험은 남아 있다.

selector의 비적용 후보는 평가자의 최종 비적용 판정과 다르다. 환경·근거 검수 후에만 제외를 확정하며, 시험하지 않은 항목은 충족으로 바뀌지 않는다.

## 1.3 요구별 평가와 관리 결정

77개 CHK는 주 보호 요구에 배치하며, 복합 항목은 다른 요구에서도 참조한다. 결과에는 36개 요구의 현재 번호와 CHK 고정 ID를 함께 적는다. 기존 SUP·REQ·PLT·LIF·OBS 접두어와 Q·SC는 과거 근거와 시험 이력을 찾는 데 사용한다.

예를 들어 OBS-006의 조회·반출 권한과 저장 보호, OBS-008의 자료 무결성과 해석·실행 권한은 확인 내용을 구분해 기록한다. OBS-011에서는 시스템의 수집 장애 표시를 점검하고, 증거가 부족한 시험을 미확인으로 처리하는 평가 규칙도 적용한다. LIF-008은 실패 감지·상위 통지를 확인하며 공유 엔진 전체의 장애 영향은 실제 시험으로 별도 확인한다.

시험 담당자가 판정과 증거를 제공하고, 정책·위험 승인자가 보완·예외·배포·재개를 결정한다. 미충족·미확인 결과와 승인 결정은 각각 남긴다. 도입·배포·변경·복구·폐기의 평가 시점은 01의 생명주기 표를 따른다.

## 1.4 생명주기별 평가 기록

[시점별 담당·점검·증거·결정 조건](01_프레임워크와_위협통제연결.md#생명주기별-보안-활동)을 기준으로 평가를 준비한다.

생명주기별 기록은 시점과 발생 사건을 먼저 적고, 해당 환경에서 선택한 CHK·시험 분기와 근거를 남긴다. 도입과 설계에서는 계획과 정책 결정 근거를 기록하고, 실행한 시험에는 실행 ID와 결과를 남긴다.

| 기록 | 작성할 내용 |
| --- | --- |
| 대상과 계기 | 일곱 시점 중 해당 시점, 발생 사건, 엔진·모델·설정·정책 버전 |
| 책임 | 실제 수행자·검토자, 승인이 필요한 경우 승인자와 권한 |
| 이전·다음 기록 | 직전 선정·평가·승인·배포 기록 참조, 인계한 대상·구성·정책 판본, 인계받을 역할과 남은 확인 항목 |
| 선정 | 적용 CHK·시험 분기, 비적용 근거·미정 조건, 변경·복구의 영향 범위 |
| 증거와 판정 | 출처·수집 시각·실행 ID·수집 상태, CHK별 결과·한계 |
| 처리 결정 | 적용·보류·예외·재개 등의 결정과 이유, 승인 시각·조건 |
| 후속 확인 | 보완 담당자·기한, 재시험 대상, 예외 만료·재검토 계기 |

기존 증거를 쓰는 경우 대상·구성·정책·시험 절차와 수집 상태가 여전히 유효한지 확인하고 재사용 이유를 적는다. 수치 기준이나 증거가 부족한 점검은 미정·미확인 상태를 유지한다. 담당자의 예외·사용 승인은 CHK의 충족 여부와 함께 각각 남긴다.

단계 간 대조와 인계는 [01의 단계 사이에 넘길 결과](01_프레임워크와_위협통제연결.md#생명주기-단계-사이의-인계)를 따른다. 기존 기록의 참조를 사용하고 같은 실행의 증거를 이어 쓴다.

## 2. 실행 전 준비

1. 정상 동작과 보호 요구를 R·POL·근거에 연결하고 적용 이유를 적는다.
2. 정상 동작을 확인할 대조 입력, 금지/경계 입력, 실패 주입을 각각 준비한다. 모델·의존성에 맞는 시험 입력·대상 자료(fixture)인지 확인한다.
3. 격리된 시험 대상·실행 권한·관측 위치·중단 기준·복구 절차를 정한다. 실제 사용자 본문·비밀값 대신 합성 표식과 자격 참조를 쓴다.
4. 정책값이 미정이면 측정은 가능하지만 그 값에 의존하는 통과 판정은 보류한다. 기존 명시 요구 위반을 관측했다면 별도로 미충족을 기록한다.
5. 허용 동작도 정상 동작해야 한다. 전부 막는 방식으로 보안 충족을 만들지 않는다.

시험 준비와 결과에는 다음 자원 정보를 함께 기록한다. 대상 구성과 중단·복구·정리 절차는 기존 기록을 참조한다.

- **시험 자원:** 필요한 CPU·메모리와 GPU 사용 시 GPU 수·GPU 메모리·TP 구성, 전용·공유 여부.
- **시간:** 예상 자원 점유 시간과 산정 근거, 실행 후 실제 점유 시간과 측정 근거. 전체 실행 시간은 기존 시작·종료 시각을 재사용하고 자원 점유 시간과 구분한다.
- **운영 영향:** 운영 서비스와 자원을 공유하면 영향받는 서비스, 허용 영향·시험 시간대와 기존 중단 기준의 적용 범위.
- **자원 반환:** 시험 종료 후 임시 실행 환경과 할당·예약이 정리되고 시험용 자원이 반환됐는지 확인할 기록·시각·관측 근거.

개발·시험 담당자가 추정·측정값과 근거를 제공한다. 확인 전 값은 미정·미확인으로 남긴다.

<a id="시험-명세를-개발에-넘기는-기준"></a>
## 2.1 개발 담당에게 넘길 시험 명세

각 하위 시험에 실행 adapter, 실제 시험 입력 자료, 준비·실행·정리 명령, 정상 대조, 증거 수집 위치, 판정식, 중단/복구 절차가 모두 있어야 자동 시험으로 등록한다. 현재 체크리스트의 절차는 이를 작성할 기준이며 실제 엔진용 명령·fixture·adapter 구현은 남아 있다.

자동화 후보는 구성/manifest 대조, HTTP 허용/거부, 증거 연결, 부하·오류 측정이다. 위험 수용·역할 허용·자료 공유·보존 예외·증거 충분성은 사람이 판단한다. low-level kernel·native 참조 회수는 선정한 구현과 전문 계측이 필요한 별도 시험이다.

<a id="먼저-준비할-공동-시험-묶음"></a>
## 2.2 먼저 준비할 공동 시험

아래는 참조 구성에서 먼저 준비할 공동 시험이다. 접근 경로·공급물·공유 상태·종결은 뒤의 결과를 신뢰하기 위한 전제이고, 관측은 모든 시험에 필요하므로 우선한다. 기존 P0 표기는 이 준비 순서를 뜻했으며 취약점 심각도 등급으로 사용하지 않는다. 같은 실행에서 여러 Q의 증거를 모으되 결과는 점검·요구별로 남긴다.

| 순서 | 먼저 준비하는 이유 | 03에서 시작할 보호 요구 |
| --- | --- | --- |
| 1. 진입·통신과 기본 증거 | 비허용 주체가 우회할 수 있으면 다른 정책의 전제가 무너진다. 시험 초기부터 허용/거부와 handler 실행 증거를 남긴다. | 1.2 작업·대상 인가, 1.6 통신 접근·송신 제한, 5.5 통신 상대·전송 보호, 8.1 필수 사건 기록 |
| 2. 승인 공급물·정상 기동 | 시험한 모델·코드가 승인한 대상인지 확인해야 이후 결과를 해석할 수 있다. | 2.1 승인 대상·출처 식별, 2.2 실제 사용의 무결성, 7.2 기동 준비 확인 |
| 3. 요청·결과·공유 상태 | 기본 텍스트·stream·prefix cache가 활성화되는 참조 구성에서 사용자 간 귀속과 공유 제한을 확인한다. | 3.1 최종 입력 검증, 4.1 요청·결과 귀속, 4.2 공유 권한·범위, 4.3 재사용 문맥의 호환성 |
| 4. 자원·종결·장애·복원 | 기본 요청과 증거 수집을 준비한 뒤 경계 부하와 실패를 제한적으로 주입한다. | 6.1 자원 예산·공정성, 6.3 실패 감지·상위 통지, 6.4 종결·자원 회수, 7.4 복구 정책·상태 검증 |

선택 기능은 위 순서를 기다렸다가 무조건 나중에 확인하는 것이 아니라, 도입할 때 해당 보호 요구를 함께 검토한다. 우선순위는 기능·노출·영향과 준비 상황이 바뀌면 다시 정한다.

| 공동 실행 | 준비할 것 | 실행 순서 | 질문별로 남길 판정 |
| --- | --- | --- | --- |
| 진입과 통신 | 실제 route·Gateway/직통·역할 허용표·내부/송신 구간·시험 계정 | 정상 허용 요청 → 비허용 역할/키/직통 → 경로 변환 → 내부/송신 허용·거부 → 정상 TP/요청 재확인 | Q-C01 작업 인가, Q-C07 각 구간 보호. 연결 실패와 handler 거부를 별도 관찰 |
| 승인 실물과 변경 | 합성 표식이 있는 승인 모델 묶음·manifest·실제 소비 관측·교체 권한·중단/복귀 계획 | 정상 로딩 → 허용된 시험 writer로 사본/alias 교체 → 불일치 처리 → 정상 묶음 복귀 → worker/canary 확인 | Q-R05-02 실물 연결, 04 교체 방지, 14 실제 서비스, 15 증거, Q-C09 재개. 하나가 통과해도 다른 항목 자동 통과 금지 |
| 요청과 cache | 두 시험 주체·공유 집단 정책·신뢰된 salt 집행·실제 cache 관측 | 정상 같은 집단 재사용 → 다른 집단·상이 문맥 → 직접 전달 필드/재사용 token 경로 → 동시 요청·자리 재사용 | Q-C03 공유, Q-C04 입력 소비, Q-C02 귀속. timing과 실제 재사용 증거를 분리 |
| 자원과 종결·관측 | 작은 시험 예산·정상 workload·취소 기한·rank 장애 복구·수집기 | 정상 부하 → 느린 수신/경계 부하 → 대기·계산·출력 중 취소 → rank 장애 → 정상 요청 → 수집 장애 | Q-C05 자원·정상 성능, Q-C08 종결, Q-C11 수집. debug/profiler는 활성한 별도 하위 시험 |

### 승인 실물 시험을 작성하는 예

- 대상: Q-R05-04의 `승인 후 파일 교체` 하위 시험. 설치판·모델·manifest·loader·의존성을 먼저 고정한다.
- 정상 대조: 승인한 무해한 시험 묶음을 로딩하고 실제 읽기·worker 준비·정상 요청을 확인한다.
- 변경 시도: 시험 writer가 실제 가진 권한으로만 승인된 시험 사본을 교체한다. 소비 중 운영 파일은 사용하지 않는다.
- 관찰: 쓰기 자체가 거부되는지, 교체가 됐다면 consumer가 사용 전에 거부하는지, 요청 수용과 실패 상태가 어떻게 남는지 확인한다.
- 판정: 교체가 예방되거나 교체물 소비가 거부되고 정상 대조가 성공하면 해당 통제의 충족 근거가 된다. 교체물이 승인 없이 실제 소비되면 미충족이다. 단지 API가 오류를 반환했거나 일부 파일 hash만 확보했다면 실제 소비 여부는 미확인일 수 있다.
- 정리: 원래 승인 묶음을 복구하고 임시 파일·시험 자격을 회수한다. 복구와 후속 정상 요청을 기록한다.

시험 입력 자료·실행 명령·관측 adapter가 아직 없으므로 이 예시는 자동 시험 등록 전 작성 지침이다.

<a id="업데이트와-다른-엔진에-적용"></a>
## 2.3 업데이트·엔진 변경 시험

현재/후보 환경 각각의 실제 구성과 정책 버전을 고정한다. 변경 영향 시험, 알려진 패치의 회귀 시험, 기존 보호 유지 시험을 구별한다. 버전 문자열만으로 시험을 자동 생략하지 않는다. 엔진 변경은 API 이름뿐 아니라 loader·cache·관리·종결·증거 의미를 다시 매핑해야 한다.

동일 정책·모델·workload·측정 조건을 맞추고 차이를 기록한다. 의도한 변경으로 조건을 같게 할 수 없다면 비교 불가 이유와 별도 수용 기준을 남긴다. v0.11.0 분석 이력이 실제 업데이트 비교의 현재판을 의미하지 않는다.

<a id="update-impact-handoff"></a>
### 업데이트 건별 위협·영향평가와 시험 선정 인계

평가자는 [01의 위협 검토 방법](01_프레임워크와_위협통제연결.md#위협에서-점검으로-연결하는-방법)과 [02의 선정 목록 완결성 검토](02_환경별_적용기준.md#선정-목록의-완결성-검토)를 이번 변경에 적용한다. 기존 변경 티켓·위험 검토·선정 기록에 다음 관계를 남기고 시험 담당자에게 넘긴다. 같은 영향을 갖는 변경은 근거를 묶어 기록할 수 있다.

| 인계 내용 | 기록할 최소 내용 |
| --- | --- |
| 변경 근거 | 현재·후보 대상의 고정 참조, 소스·설정·의존성 등의 변경 위치와 출처, 확인 범위와 미확인. 기존 환경 기록을 참조한다. |
| 위협·영향 판단 | 실제 사용 경로·자산·신뢰 경계와 보호 조건 중 무엇이 달라지는지, 어떤 주체의 접근·조작·관찰 또는 실패로 요구가 깨질 수 있는지, 기존 통제와 남는 영향. 영향 없음도 해당 환경의 근거를 남긴다. |
| 시험 선정 | 관련 보호 요구·CHK·적용 분기와 선정 이유. 변경 영향 시험·알려진 수정의 회귀 시험·기존 보호 유지 시험 및 기존 증거 재사용 범위를 구분한다. |
| 남은 확인과 인계 | 부족한 근거·대응되지 않는 경로, 다음 행동·담당 역할, 해소 후 다시 볼 선정·증거·판정 범위. 검토자·시점은 기존 선정 기록에 남긴다. |

변경 근거 제공자는 대상 일치와 변경 사실을 확인하고, 평가자는 위협·영향 판단과 선정 범위를 검토한다. 시험 담당자는 선정한 조건을 실행·관측할 수 있는지 확인해 준비 부족을 돌려준다. 조직별 정책값과 위험 수용은 기존 정책 소유자·승인권자가 결정한다.

기존 요구에 대응되지 않는 변경은 보호 범위·요구의 공백 검토로 넘긴다. 변경 의미나 적용 여부를 확인할 근거가 부족하면 추가 확인 대상으로 남기고, 필요한 시험 목록을 바꾸는 미결 사항이 있는 동안 `subtest_inventory_complete`는 거짓으로 유지한다. 확인된 범위의 시험은 기존 권한·안전·준비 조건에 따라 진행할 수 있다. 코드 차이가 없다는 이유만으로 기존 보호 유지 시험을 생략하지 않는다.

시험에 넘길 때 검토한 선정 근거·시험 범위와 남은 확인·담당이 함께 있어야 한다. 실패 보완이나 재확인에서 변경·정책·환경이 달라지면 영향받는 선정과 재사용 범위를 다시 검토하고 원결과를 보존한다. 새 승인 단계를 추가하지 않고 기존 선정 검토와 변경 절차를 사용한다. 자동 변경 추출·추천·저장·실행 연동은 개발팀 작업이다.

<a id="평가-자료-자체의-보호--구현시험-계획"></a>
## 3. 실행·증거 수집과 자료 보호

시험 실행 ID에 대상 판본·설정·정책·입력·원본 증거와 보고서 판본을 함께 연결한다. 수집자는 증거를 추가하고, 검토자는 판정을 기록하며, 승인자는 예외·채택을 결정하도록 기업별 역할을 정한다. 기존 원본을 덮어쓰지 않고 정정본과 변경 이유를 남긴다.

- 정상 대조: 허용 수집·조회·승인과 원본 재검증, 재수집 이력 확인.
- 미충족: 비허용 수정·삭제·증거 교체가 허용되거나 필수 변경 이력이 누락됨.
- 미확인: 저장소 권한·원본 기준·검증 기록을 확보하지 못함. 해시만으로 작성자 신원이나 최초 증거의 진실성을 입증하지 않음.

보존 기한·접근 역할·승인 책임은 기업별 결정값이다. 저장소 보호·이력·변조 탐지 기능의 실제 구현과 시험은 남아 있다. Q-C11·Q-R05-15와 함께 평가한다.

<a id="기존-자료로-점검을-준비하는-순서"></a>
### 기존 자료로 점검을 준비하는 순서

기존 정책·배포 자료·평가 기록을 먼저 모아, 선택한 CHK의 적용 조건·필요한 증거·정상 대조와 맞춘다. 보호 요구의 ‘환경에 맞춰 채울 값’은 관련 점검을 묶은 안내이므로, 이번 CHK·분기에 필요한 값만 확인한다. 여러 항목에 쓰는 같은 허용표·설정·실행 증거는 한 번 확보하고 해당 기록을 참조한다.

| 가져온 자료 | 재사용 여부를 확인할 내용 | 부족할 때 다음 행동 |
| --- | --- | --- |
| 승인 정책·허용표·서비스 기준 | 이번 서비스·대상·작업에 적용되는 승인 판본과 유효기간을 확인한다. 유효한 기준은 참조하고 변경·미정인 값만 결정한다. | 정책 소유자가 필요한 기준을 마련하고 권한자가 확정한다. 현재 설정값과 승인 기준은 구분한다. |
| 배포 기록·설정·환경 자료 | 이번 실제 대상과 유효 상태를 뒷받침하는지 확인한다. 기존 자료에 변경 내역·현재 상태 확인 근거를 더할 수 있다. | 환경·운영 자료 제공 역할이 빠진 경로·구성·설정을 확인한다. 계획값이나 오래된 자료만 있으면 실제 상태 확인을 요청한다. |
| 과거 시험 결과·원본 증거 | 기존 재사용 조건에 따라 이번 결론을 뒷받침하는 범위를 정한다. 변경된 집행 경로·입력 처리·공유·의존성·측정 조건이 결과에 영향을 주는지 검토한다. | 평가자가 재사용할 범위와 다시 확인할 범위를 구분하고, 시험 담당자가 필요한 경로·분기의 증거를 확보한다. |

문서·설정 검토로 판정하는 내용과 실행 결과가 필요한 내용은 각 CHK의 기존 기준을 따른다. 자료 확보는 연결 조회·내보낸 파일·기존 문서나 시험 보고서 등 기업이 제공 가능한 방법을 사용하되, 대상·출처·시점·확인 범위가 해당 결론을 뒷받침해야 한다. 담당자 설명은 운영 의도나 증거 위치를 확인할 때 활용한다.

부족한 내용은 기존 평가 기록에 **CHK·분기 → 확보한 근거 → 남은 확인 → 다음 행동·담당 역할** 순서로 정리한다. 일반 응답만 시험했으면 남은 필수 옵션·오류 경로를, 취소 응답만 있으면 해당 CHK가 요구하는 내부 종결 증거를 추가 대상으로 적는다. 계측·시험기가 필요한 경우 개발·시험 담당자의 준비 과제로, 허용값이 필요한 경우 정책 결정 과제로 나눈다. 실제 역할은 기업의 업무·권한에 맞춰 지정한다.

재사용 여부는 자료별·확인 범위별로 기록한다. 예를 들어 응답 허용 정책이 그대로여도 반환·오류 처리 경로가 바뀌면 정책은 참조하고 관련 실행 결과는 다시 확보한다. 판정·집계와 증거 충분성은 아래 기존 규칙을 적용하고, 확인된 위반·미확인 범위와 관리자의 처리 결정은 각각 유지한다. 기존 보고서·티켓·평가 기록을 참조하며 같은 내용을 항목마다 새 문서로 작성할 필요는 없다.

<a id="증거-충분성과-채택-검토"></a>
### 증거 충분성과 채택 검토

검토자는 03의 필요한 증거와 충족·미충족·미확인 기준을 적용할 때 다음 내용을 확인한다. 시험 담당자는 실행 전에 증거와 판정 조건의 대응을 제시하고, 검토자는 수집 방법이 해당 결론을 뒷받침하는지 검토한다. 실행 후에는 실제 확보한 증거로 다시 확인한다. 항목의 성격에 맞춰 기존 문서·설정·실행 기록과 검토 결과를 재사용한다. 문서·설정 검토는 기준과 유효 상태를 대조하고, 실행·메모리·시간·통계 증거는 해당 CHK의 기존 판정에 필요한 범위에서 확인한다.

- **판정 대상까지의 연결:** 문서·설정 검토는 승인 대상과 유효 설정을, 실행 시험은 실제 집행·소비·거부 지점에 도달한 결과를 뒷받침해야 한다. 관측 지점의 신뢰 근거·관측 범위와 누락 구간을 적는다. 설정값과 자기 보고만 확보했다면 실제 집행에 대한 결론의 범위를 제한한다.
- **위반을 구별하는 방법:** 실행 시험은 해당 CHK에서 정한 정상·비허용 대조가 보호 조건의 충족과 위반을 구별하는지 확인한다. 통계적 추론을 사용하는 시험은 표본·오차·대조 설계의 근거를 검토한다. 결과를 보고 판정 방법을 조정한 경우 변경 이유와 판본을 남기고 조정한 방법의 결론을 별도 자료·실행에서 확인한다. 이미 확인한 요구 위반은 유지한다.
- **충돌과 적용 한계:** 서로 다른 증거가 같은 대상·시각·조건을 가리키는지 대조하고 불일치 원인을 확인한다. 관측하지 못한 경로·rank·조건과 증거 재사용 범위를 남긴다. 필수 증거 부족은 미확인, 확인된 요구 위반은 미충족으로 유지하며 항목별 판정과 집계는 아래 4절을 따른다.

다음 두 항목은 기존 증거 목록에 더해 **증거 사이의 대응과 방법의 한계**를 검토한다.

| 점검 | 증거를 채택할 때 추가로 확인할 내용 |
| --- | --- |
| [CHK-SUP-006](03_체크리스트와_보완가이드.md#CHK-SUP-006) — 승인 모델의 실제 적재 | 승인 파일·rank별 배정·필수 tensor에서 mapper·양자화·후처리를 거쳐 실제 적재 내용으로 이어지는 대응을 확인한다. 기대값은 승인 원본과 승인된 변환 절차에서 정하고, 의도된 생성값과 누락을 구분한다. 바이트가 달라지는 변환은 비교할 표현을 정하고, 수치 오차가 있는 비교를 사용할 때 그 허용 근거를 남긴다. 각 필수 rank·부분의 실제 소비를 뒷받침하는 계측·비교 범위를 명시하고, 누락·교체 자료를 구별하는지 확인한다. 직접 계측과 검토된 대체 증거를 조합해 필수 대응을 확인한다. 파일 hash·header·경로명·canary 결과만으로 남는 적재 증거의 공백을 해소하지 못하면 해당 범위는 미확인으로 남긴다. |
| [CHK-REQ-017](03_체크리스트와_보완가이드.md#CHK-REQ-017) — 캐시 신호에 의한 추론 | 공격자가 읽을 수 있는 시간·응답 필드·지표별로 prefix 존재·부재의 실제 상태와 추론 결과를 대조한다. 지연 등으로 통계적 추론을 하는 분기에서는 표본·오차, cache 상태·요청 순서·동시부하 등 주요 조건의 통제와 정상 대조를 확인한다. 존재·부재 구성비와 우연 수준을 고려해 추론 성능의 불확실성 범위가 채택 기준에 대한 결론을 지지하는지 본다. 추론 방법을 자료에 맞춰 조정하면 조정 자료와 최종 판정 자료를 구분한다. 직접 반환된 hit 정보는 그 독자·집단·보호 정책과 대조한다. 기준을 넘는 추론과 관측 능력 부족을 구별할 근거가 부족하면 미확인으로 남긴다. |

개발·시험 담당자가 fixture·계측·변환 비교·통계 계산을 구현하고 측정값과 원자료를 제공한다. 보안·플랫폼 검토자는 관측 범위와 방법의 충분성을 검토하고 정책 승인자는 조직별 허용값을 확정한다. 표본 수·오차·기한·예산 등 실제 수치는 대상과 방법의 근거가 확보된 뒤 기록한다.

<a id="기한-판정의-증거"></a>
### 기한 판정의 증거

기한을 판정하는 시험에서는 채택한 시작·완료 사건의 의미와 각 시각을 같은 실행에 연결한다. 같은 시계의 기록을 사용하거나 서로 다른 시계의 차이·오차를 확인할 근거를 남긴다. 오차 때문에 기한 준수 여부를 가를 수 없으면 해당 결과는 미확인으로, 기한 초과가 확인되면 미충족으로 기록한다. 기존 시각·동기화·수집 기록을 재사용하고 기한값과 실제 측정값은 담당 조직·시험 담당자가 제공한다.

<a id="결과-기록과-집계"></a>
## 4. 항목별 판정과 결과 집계

| 구분 | 값 |
| --- | --- |
| 적용 상태 | 적용 / 비적용 / 미정 / 충돌. 비적용에는 근거와 다시 볼 조건 필요 |
| 실행 상태 | 미실행 / 대기 / 진행중 / 완료 / 중단 |
| 수집 상태 | 미수집 / 부분수집 / 수집완료 |
| 보안 판정 | 충족 / 미충족 / 미확인 / 비적용(화면의 해당 없음) |
| 정상 기능·성능 | 각 기준의 충족 / 미충족 / 미확인 / 해당 없음과 측정값 |

위 표는 기존 45필드의 값을 채우기 위해 [필드사전](개발전달/결과기록_필드사전_초안.json)이 제안한 `framework_projection`(프레임워크 표시값) 이름이다. BYUL update 도구 guard의 기존 영문 상태값은 유지한다. 오류·수집 실패의 실제 사실과 원인·시각·영향 범위는 수행/수집 상세와 증거에 남긴다. 오류로 끝난 수행은 중단 여부와 실제 수행 범위를, 수집 실패는 미수집/부분수집 중 확보한 상태를 함께 기록한다. 새 ERROR/FAILED enum의 채택이나 오류 사실의 생략을 요구하지 않는다. 수집 상태는 제품에 추가 구현된 enum이 아닌 설계 표시값이다.

**충족:** 적용 경로의 필수 증거와 채택 기준이 있고 보호 요구·정상 대조를 만족한다. **미충족:** 해당 요구 위반을 관측했다. **미확인:** 미실행·미정·미관측·분기 미도달 등으로 결론이 없다. **해당 없음:** 기능·경로가 적용되지 않는 증거가 있다.

발생이 확인된 필수 사건의 기록이 채택한 수집·보존 조건이나 기한을 위반하면 기록 확보 요구는 미충족이다. 기록 확보 여부를 판단할 필수 증거가 부족하면 미확인으로 남긴다. 누락된 기록을 대신할 다른 필수 증거로도 판단할 수 없는 의존 시험은 미확인으로 두고, 이미 확인한 요구 위반은 미충족으로 유지한다.

**판정 단위와 기준**

현재 평가 결과는 **CHK별 적용 분기와 채택한 정책·환경값**을 기준으로 기록한다. 도출 근거(Q)은 기존 정책·절차·사례와 구현 근거를 제공한다. Q의 기준과 CHK의 기준이 어긋나면 충돌 내용을 확인해 기준을 맞추기 전까지 충족으로 처리하지 않는다. 이미 확인한 요구 위반은 미충족으로 남긴다.

필수 시험 목록의 완결성은 [02의 선정 목록 검토](02_환경별_적용기준.md#선정-목록의-완결성-검토)로 확인한다.

**집계하는 대상**

1. 먼저 같은 환경·정책·절차 판본에서 각 CHK에 필요한 적용 시험·분기의 결과를 모은다. 연결된 모든 SC를 무조건 실행하거나 같은 증거를 중복 집계하지 않는다.
2. 필요한 적용 시험에 미충족이 하나라도 있으면 해당 CHK는 미충족이다. 미충족 없이 미확인이 있으면 미확인이다. 선정 목록이 완성되고 필요한 공통 확인·적용 분기·필수 세부 결과가 모두 충족이면 충족이다. 전부 비적용이고 근거가 있을 때만 해당 없음이다.
3. 보호 요구의 결과는 그 요구에 실제 기여하는 공통·세부 범위 결과와 증거를 같은 규칙으로 모은다. CHK 전체 판정을 보조 요구에 복사하지 않는다. Q와의 관련 링크만으로 보호 요구를 자동 충족 처리하지 않는다. 필요한 세부 점검·분기 목록이 미완성이면 알려진 시험을 모두 통과해도 미확인이다.

확인된 위반은 다른 증거가 부족하더라도 미충족으로 남긴다. 보안·정상 기능·성능은 각각 집계한다. 현재 selector와 결과 템플릿이 이 집계를 자동 수행하는 것은 아니며 평가자가 연결·증거를 확인해야 한다.

충족은 각 점검의 적용 분기·정상 대조·필수 증거·정책 조건을 기준으로 판정한다. 문서·설정 검토 항목은 해당 단계의 검토 증거를, 실행 시험 항목은 해당 집행 위치의 결과를 확인한다.

### 기록 확보와 수집 장애 탐지의 판정 예시

사건별 수집·보존 조건과 기한을 먼저 확인한다. 일시 중단 뒤 기록이 정한 기한 안에 복구되고 필수 필드를 대조할 수 있으면 기록 확보의 충족 근거가 된다.

| 확인한 상황 | 기록 확보 — CHK-OBS-001 | 장애 탐지 — CHK-OBS-011 | 해당 기록이 필요한 시험 |
| --- | --- | --- | --- |
| 필수 기록이 수집 기한을 넘겨 누락됐고 장애를 정한 범위·기한에 정확히 탐지·처리함 | 미충족 | 해당 장애 시험 분기의 충족 근거 | 다른 필수 증거로 판단할 수 없으면 미확인 |
| 필수 기록 누락과 필수 탐지의 기한 초과를 각각 확인함 | 미충족 | 미충족 | 다른 필수 증거로 판단할 수 없으면 미확인 |

각 CHK의 전체 판정은 필요한 다른 적용 분기까지 모아 정한다. 탐지 성공과 기록 확보 실패는 각각 남긴다. 이미 확인한 요구 위반은 미충족으로 유지한다.

필수 검사 원결과가 미확인이어도 보류가 요구되는 경로에서 운영 사용을 정확히 막았다면 SUP-014의 해당 보류 분기는 충족 근거가 된다. CHK 전체 판정에는 정상 성공 시 허용되는지 등 필요한 적용 분기를 함께 확인한다.

<a id="평가-방법의-적용-사례"></a>
## 4.1 평가 방법의 적용 사례

보호 조건을 확인하는 시험은 실제 처리 경로를 거치고, 위반을 드러낼 입력과 정상 대조를 갖춰야 한다. 팀의 「vLLM 보안 수정에서 보안 함수 호출 누락에 대한 회귀 시험의 검출 한계 연구」는 이 평가 방법을 검토할 사례를 제공한다.

| 구분 | 시험 범위와 확인 내용 |
| --- | --- |
| 시험 대상 | 2026년 상반기 vLLM 보안 수정 17건에서 만든 변이 78개 중 보안 위반이 확인된 22개를 비교했다. |
| 관찰 결과 | 선정 CPU 시험은 호출형 18개 중 14개를 검출하지 못했다. 미검출 14개 중 13개는 계측한 시험 프로세스에서 호출 실행이 관찰되지 않았고, 1개는 차이를 드러낼 입력이 부족했다. |
| 보완 시험 | 미검출을 확인한 뒤 작성한 사용 지점 시험은 수정본에서 통과하고 해당 변이 14개를 검출했다. |

**평가 방법에 반영할 내용:** 보안 함수의 동작 확인과 함께 실제 처리 코드의 호출·설정 전달을 확인한다. 위반을 구별할 입력으로 최종 보안 결과를 검사하고, 허용한 정상 동작도 유지되는지 대조한다. 실행 관찰은 해당 경로를 거쳤는지 판단하는 보조 증거로 사용한다.

**현재 확인 범위와 후속 검증:** 위 결과는 선정한 수정·변이와 시험·계측 범위의 결과다. 사용 지점 시험은 미검출 확인 뒤 작성됐으며, 별도 서버·자식 프로세스는 원 CPU 계측 범위 밖이었다. 현재 CHK에 활용할 때는 논문의 사례·환경·시험을 해당 점검과 분기에 대응시켜 다시 실행하고, 보안·정상 동작의 증거와 판정을 기록한다.

**관련 점검:** [오류 응답 정보 제한](03_체크리스트와_보완가이드.md#CHK-REQ-013), [외부 송신 제한](03_체크리스트와_보완가이드.md#CHK-PLT-007), [추가 코드 실행 허용](03_체크리스트와_보완가이드.md#CHK-SUP-009), [실행 방식별 외부 모듈 제한](03_체크리스트와_보완가이드.md#CHK-SUP-011).

**연구 원문:** [팀 보관 PDF](노션_공유용/assets/ACK2026_paper.pdf), 본문 2–3쪽의 방법·결과·한계.

<a id="보고와-운영-연결"></a>
## 5. 검토 보고·승인·운영 연결

환경별 보완 순서는 노출 경로, 필요한 공격 권한, 영향받는 자산·서비스, 실제 통제와 남은 위험을 보고 정한다. 위협 후보의 적용 여부와 미확인을 함께 적고 검토자가 우선순위와 이유를 기록한다. 기업이 쓰는 위험평가 방식이 있으면 그 기준을 따른다.

보안 위반을 발견하면 영향 모델·요청·계정을 확인하고 기업의 사고 대응 담당에게 보고한다. 사건의 영향과 정한 권한에 따라 필요한 요청·통신·자격을 제한하고 원본 증거를 보존한다. 보완 후 관련 항목을 다시 시험하며 재개 승인자가 서비스 재개를 결정한다. 보고 담당·채널·기한, 초기 제한 권한, 보존 대상과 재개 승인자는 기업이 정한다. 실제 통제 연동과 대응 시험은 남아 있다.

보고서는 환경·변경점, 항목 선정 이유, 보안·기능·성능 결과, 증거·한계, 미충족/미확인, 보완·재시험, 승인/보류·예외 기록을 포함한다. 위험 수용은 담당자가 하며 도구가 자동 승인하지 않는다.

정책값 미정·역할 겸임·필수 검사 미확인·예외 만료의 결정과 후속 처리는 [01 거버넌스 결정과 후속 처리](01_프레임워크와_위협통제연결.md#거버넌스-결정과-후속-처리)를 따른다. 기존 결정·후속 기록에 대상·담당·기한과 해소 근거를 연결한다.

운영에는 승인된 설정·정책과 그 적용 상태를 등록한다. Gateway 접근, 송신 정책, 모델/설정 변경, 엔진/자원 상태, 수집 중단을 관련 Q ID에 연결한다. 변경·위반·관측 장애가 발생하면 영향 항목을 재선정한다. 경보만 발생했다고 차단 성공으로 기록하지 않는다. 중앙 연결이 끊겼을 때 기존 정책 유지·변경 처리·증거 보존은 실제 구현으로 시험해야 한다.

## 6. 처음부터 끝까지 따라가는 예시 — 직통 접근 제한

사용자 요청은 Gateway를 거쳐야 하고 일반 사용자의 엔진 직통 접근을 제한하는 팀 참조 기준을 예로 든다. **아래는 사용 절차 예시이며 실제 엔진을 시험한 결과가 아니다.** 현재 도구가 하는 일과 사람이 하는 일을 각 단계에 표시했다.

### 6.1 환경 확인과 입력 — 담당자

`data/environment_template.json`을 읽고 실제 대상의 엔진·commit·이미지 digest·모델·Gateway·노드·TP 구성과 근거를 확인한다. 실제 확인 전에는 `profile_status: "계획값"`, 알 수 없는 값은 `null`을 유지한다. 팀 참조 정책의 직통 허용 주체는 Gateway와 지정 운영·점검 주체이고 일반 사용자는 제외한다. 실제 주소·허용 출발점·route 목록·인증·인가 위치와 승인된 정책 버전은 담당자가 채운다.

환경의 실제 구성과 정책을 확인했다면 출처·시각을 `runtime_evidence`에 연결하고 `policy_revision`과 `policy_values`에 승인 기준을 기록한다. 이 필드를 채웠다는 사실만으로 도구가 설정을 검증하거나 정책을 집행하지는 않는다. 실제 TP 크기 등 전용 키가 없는 값은 관련 근거에 명시한다.

### 6.2 Q 적용 분류 — 현재 selector

폴더에서 다음을 실행하면 엔진 접속 없이 계획 템플릿의 Q 적용 분류를 확인할 수 있다.

```sh
python3 -B select_checklist.py data/environment_template.json
```

현재 제공한 템플릿으로 확인한 출력은 Q 28개 중 적용 24개·미정 4개이며, 모든 보안 판정은 미확인·실행은 미실행이다. Q-C01은 공통 요구이므로 적용으로 분류된다. **이 출력은 환경 확인·77개 점검 자동 선택·시험 결과가 아니다.** 입력이나 규칙이 달라지면 분류 수를 다시 확인한다.

### 6.3 구체 점검 선택 — 평가자

03의 ‘1.2 작업·대상 인가’에서 **‘Gateway를 거치지 않은 요청으로 허용받지 않은 작업을 할 수 없는가?’**를 고른다. 이 점검은 Q-C01·Q-C07, SC-01-01과 연결된다. Q-C01이 적용된다고 그 아래 모든 경로나 다른 선택 기능의 시험이 자동 선정되는 것은 아니다.

### 6.4 시험 준비와 실행 — 개발·시험 담당자

- 준비: 실제 등록 route·listener·망 규칙, Gateway/직통 경로, 일반·운영 시험 계정, handler 실행·거부를 관찰할 기록, 중단·복구 절차를 확보한다.
- 정상 대조: 허용된 신원·출발점에서 Gateway를 거쳐 승인 모델에 무해한 요청을 보내 정상 처리되는지 확인한다.
- 제한 확인: 비허용 사용자 출발점의 직통 호출과 무키·오류키·허용키 조합을 실제 route별로 비교한다. `/v1`뿐 아니라 등록된 `/invocations` 등 인증 prefix 밖 추론 경로도 포함한다. 미등록 경로는 등록 여부를 기록한다.
- 증거: 출발점·경로·route, 적용 인증 범위, 네트워크 거부 또는 실제 handler 수행 여부를 연결한다. 연결 실패·404·OPTIONS 응답만으로 전체 경로가 보호됐다고 판단하지 않는다.
- 정상 기능: 제한 적용 뒤에도 허용한 Gateway 경유 일반·스트리밍 요청이 정상 처리되는지 확인한다.

이 단계의 엔진별 입력·계측·실행 코드는 작성·확인해야 한다. selector는 위 시험을 실행하지 않는다. 실행 권한이나 관측 자료가 없으면 임의 결과를 만들지 않고 미실행·미확인으로 남긴다.

### 6.5 결과 기록 — `result_template.json` 사용

기존 템플릿을 복사해 대상 CHK·시험 분기·Q/SC·환경으로 바꾼다. 한 기록은 한 CHK의 공통 확인·선정 분기·필수 결과에 대응하는 구체적인 케이스와 수행·판정을 담는다. 아래는 **구판 checklist SHA256 7f857208…에 고정된 시험 전 기록 예시**다. 원 판본과 문구를 보존한다. 현재 기본 양식 `data/result_template.json`은 현행 `data/checklist.json`의 SHA256을 참조하므로 새 기록은 복사한 양식의 실제 기준·원문을 확인한다. 표시한 필드 외 출처·시각·중단/복구 참조·정상 대조 등 기존 템플릿 필드도 유지한다.

| 추가 필드 | 기록 규칙 |
| --- | --- |
| `record_id` | 결과 기록 자체의 고유 식별자. 기록 생성 도구가 발급하며 빈 양식에서는 `null`로 둔다. |

| `checklist_revision` | 기준으로 사용한 `data/checklist.json`의 판본. 예시는 원본 bytes의 SHA-256을 기록하며 해당 원본을 함께 보존한다. 새 판본으로 시험할 때 실제 기준 판본으로 갱신한다. |
| `test_branch_ref` | 해당 CHK의 `test_branch_conditions`에서 `name`, `scenario_ids`, `apply_when`을 원문 그대로 복사한다. CHK·체크리스트 판본과 세 값을 함께 대조해 정확히 한 분기를 참조한다. CHK ID와 기존 112개 분기의 이름·조건은 유지한다. |
| `test_case_id` | 해당 분기를 실제 경로·대상·조건으로 구체화한 시험 케이스의 식별자. 시험 담당자가 케이스 명세에 부여하고 개정된 내용은 `procedure_version`으로 구분한다. 준비 전에는 `null`이다. |
| `test_case_parameters` | 이번 케이스의 경로·작업·신원 역할·rank·상태 등 판정 범위를 구분하는 조건. 필요한 값만 기록하며 비밀값은 참조로 남긴다. |

`subtest_id`는 기존 Q/SC의 공유 시험 초점이고 `test_case_id`·`execution_id`는 각각 구체적인 케이스와 실제 실행이다. 같은 실행·증거가 여러 CHK에 쓰이면 `execution_id`와 증거 참조를 공유하되 결과 기록은 CHK별로 나눈다. 같은 분기에서도 실제 경로·조건에 따라 케이스를 나누고, 현재/후보 환경 및 재시험 실행의 결과는 각각 남긴다. 기록 고유 ID나 시험 케이스 ID를 새 CHK·분기 ID로 사용하지 않는다.


`test_branch_ref.apply_when`은 기준 판본의 분기 적용 조건이고, `test_case_parameters`는 실제 시험 조건이다. 적용 조건을 복사하는 작업은 기준 선택으로 자동 채울 수 있다. 참조가 0개 또는 여러 분기에 대응하면 연결을 확정하지 않고 검토 대상으로 남긴다. 과거 기록은 원본과 판정을 보존하며, 당시 판본·실제 시험 조건·증거로 분기를 유일하게 확인한 경우에만 정정·연결 기록을 추가한다. 모호한 연결을 CHK 충족 집계에 자동 반영하지 않는다.

공통 확인·필수 결과에 대응하는 분기가 없으면 분기/Q/focus를 억지로 붙이지 않고 해당 참조를 비우고 이유를 남긴다. `subtest_id`는 canonical focus, `question_id`는 그 주 Q, `shared_question_ids`는 같은 focus의 나머지 Q를 사용한다. case의 실제 SC와 분기 정의의 전체 SC는 각 역할에 맞게 보존한다.

양식은 미실행·미확인 상태를 유지한다. 실행 결과를 등록할 때 CHK·분기·Q/SC·주 보호 요구가 기준 판본과 일치하는지 확인하며, 근거를 확보하지 못한 값은 미정으로 남긴다. `subtest_inventory_complete`와 CHK 집계는 02의 선정 목록 완결성 및 이 문서의 기존 집계 규칙을 따른다.

기존 Q 중심 기록은 원본·판정·식별자를 보존한다. Q/SC만으로 CHK를 자동 확정하지 않고, 실제 시험 범위와 증거를 검토한 연결만 추가한다. 미해결 연결은 검토 대상으로 남기고 CHK 충족 집계에 자동 반영하지 않는다. `facts`에 남긴 과거 설명도 보존한다. 새 필드의 저장·가져오기·검증·기존 기록 연결은 개발팀 구현 과제다.

문서·설정 검토에는 실제 검토자·시각·절차 판본과 자료 Ref를 남긴다. 기존 EVD와 operator/procedure가 수행 신원이며 엔진 request ID를 생성하지 않는다. 수동 출처는 DECLARED, 합성 예시는 EXAMPLE의 상한을 유지한다. 엔진 정상 대조·위반 시도가 필수인 범위에서 문서 검토만 끝났으면 그 검토 수행은 완료로, 엔진 시험과 보안 판정은 미실행·미확인으로 기록한다.

증거를 다시 쓸 때 원 EVD/RES·PLAN·환경·정책·팩·시각을 보존하고 새 대상에서 채택한 범위·검토자·시각·유효성 근거를 별도로 남긴다. 이월은 새 실행 수에 포함하지 않는다. 구판 읽기·복원, 당시 판정 재현, 현행 새 평가와 실제 승인은 각각 기록한다.

### 6.6 판정과 보고 — 검토자·승인 담당자

| 관측 결과 | 이 점검의 처리 |
| --- | --- |
| 정한 모든 필수 경로에서 금지 작업이 차단되고 정상 대조·요구 증거가 충족됨 | 해당 시험 범위의 충족 근거로 기록. 다른 경로·Q 전체로 확대하지 않음 |
| 비허용 주체가 직통으로 금지 handler 작업을 실제 수행함 | 미충족. 관련 노출·인가를 보완하고 같은 조건에서 재시험 |
| `/v1`만 봤거나 경로·집행 위치·실제 수행 여부를 확인하지 못함 | 미확인. 추가 경로 조사·증거 확보 후 판정 |

결과와 미확인을 아래 보고 양식에 옮기고 적용·보완 후 재시험·보류를 담당자가 결정한다. 현재 예시의 결론은 실제 시험 미실행·미확인이며 적용 승인은 없다.
