# 플랫폼 없이 시작하는 LAB 첫 설치

기존 클러스터·엔진에 런타임을 새로 설치하는 운영자용 절차다. 작업 위치는 검수한 저장소의 `runtime/`이다. 아래 명령은 서버에서 승인된 작업 시간에 실행한다. 인증 입력과 조회 원본은 서버 안에만 둔다. LAB 승인에는 운영자가 검토한 대상·기간·근거를 사용한다.

## 1. 서버용 Python과 인수 도구

호스트 설치기는 의존성이 없는 runtime만 `/opt/byul/runtime`에 설치한다. `labtools`에서 사용하는 `guard`는 같은 판본의 `update` 패키지가 제공한다. 별도 인수용 venv에 두 패키지를 설치한다. `update`는 Python 3.12만 지원한다. 서버에서 패키지를 받을 수 없다면 같은 Python·플랫폼용 의존성 wheel을 사전에 반입해 `pip --no-index --find-links`로 설치한다.

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -e . -e ../update
.venv/bin/python -c 'from guard.adapters.vllm_engine_callback_sensor import TAG; from serving_runtime.gateway.backend import upstream_request_id; assert upstream_request_id("vllm", "a"*32) == TAG+"a"*32'
```

인수 시험·preflight는 이 `.venv/bin/python`으로 실행한다. 호스트 설치기의 `/opt/byul/runtime/.venv`와 구분한다.

## 2. 새 인증 입력 생성

아래 블록은 새 비공개 폴더만 만들며 기존 입력을 덮어쓰지 않는다. 실행 뒤 생긴 `private-install/`을 저장소 밖의 접근 제한 위치로 옮긴다. 토큰을 출력하거나 셸 명령 인자로 넘기지 않는다. `auth.json`에는 SHA-256만, `runtime-acceptance.env`에는 실제 추론·조회 토큰만 들어간다. `viewer.env`는 설치기의 `VIEWER_ENV_FILE`, `agent.token`은 `AGENT_TOKEN_FILE`에 연결한다. 에이전트는 disabled/inactive로 유지한다. 향후 플랫폼에 연결할 때는 별도 등록한 에이전트 자격증명을 사용한다.

```python
# TOKEN_SETUP: .venv/bin/python으로 실행
import hashlib, json, secrets
from pathlib import Path
root = Path("private-install")
root.mkdir(mode=0o700)
def write(name, text):
    path = root / name
    with path.open("x") as stream:
        path.chmod(0o600)
        stream.write(text)
viewer, inference, agent = [secrets.token_urlsafe(32) for _ in range(3)]
write("runtime-acceptance.env", f"RUNTIME_VIEWER_TOKEN={viewer}\nRUNTIME_INFERENCE_TOKEN={inference}\n")
write("viewer.env", f"RUNTIME_VIEWER_TOKEN={viewer}\n")
write("agent.token", agent + "\n")
principals = [{"principal_id": name, "roles": [role],
               "token_sha256": hashlib.sha256(token.encode("ascii")).hexdigest(),
               **({"allowed_models": ["test-model"]} if role == "inference" else {})}
              for name, role, token in [("lab-viewer", "viewer", viewer), ("lab-inference", "inference", inference)]]
write("auth.json", json.dumps({"schema_version": "runtime-auth/1.0", "auth_ref": "LAB-LOCAL-AUTH",
     "principals": principals, "route_roles": {"POST /v1/chat/completions": ["inference"],
     "POST /v1/completions": ["inference"], "GET /api/*": ["viewer"]}}, indent=2)+"\n")
```

권한이 짧은 순간에도 넓어지지 않도록 실행 전 `umask 077`을 설정한다. 생성 후에는 `load_auth`의 `state == "ok"`와 파일 mode 0600을 확인하고 값은 기록하지 않는다. [GPU LAB README의 인증 Secret 등록](../gpu-lab/README.md)은 그대로 따른다. Secret 생성에 쓸 파일은 이 `auth.json`이다.

## 3. 엔진 실측값과 첫 LAB 정책 묶음

실제 엔진 Pod의 `engine` 컨테이너에 대해 다음을 대조한다. 조회 JSON 전체는 서버의 0600 파일로만 보관한다.

| 입력 | 확인 방법 | 연결 위치 |
| --- | --- | --- |
| 이미지 digest | 승인된 엔진 Pod의 `status.containerStatuses[].imageID`와 배포 이미지의 registry digest 대조 | `target.engine.image_digest`, intent `assets.cache_generation.image_id`, preflight `--expect-engine-digest` |
| 모델 snapshot 호스트 경로 | engine의 `/models` volumeMount가 가리키는 `volumes[].hostPath.path` | Gateway `model` hostPath, `render_gateway_assets --model-root` |
| 모델 revision | 모델 snapshot 출처·다운로드 기록과 실제 디렉터리 대조 | intent `assets.cache_generation.model_revision` |
| compile profile | 현재 엔진 설정을 검토해 부여한 판본 ID | intent `assets.cache_generation.compile_profile` |

노드·Pod 이름·주소·전체 imageID 원본을 반출하지 않는다. 공개 엔진 이미지의 `sha256:` digest만 구성에 넣는다. 이미지의 플랫폼 manifest digest와 index digest가 다르면 각각 근거를 구분하고 **실행 Pod에서 확인한 값**을 사용한다. `/models`는 컨테이너 경로이고 호스트 snapshot 경로와 역할이 다르다. Gateway YAML의 예시 snapshot을 그대로 사용하지 말고 운영자 사본에서 엔진과 같은 snapshot으로 바꾼다. 모델·cache 파일 자체는 변경하지 않는다.

`deploy/gpu-lab/intent.aws-lab.json`과 `target.aws-lab.json`을 서버의 비공개 준비 폴더로 복사해 실제 값으로 채운다. `REPLACE`가 없어야 한다. namespace/context/selector/컨테이너명, 모델 ID, 엔진 판본도 실제 배포와 대조한다. 아래 입력 JSON은 운영자가 검토해 작성한다. `intent_file`과 `target_file`은 준비한 절대 경로, `approved_by`는 검토 역할, `approval_ref`는 실제 LAB 승인 기록, `valid_until`은 승인 만료 시각이다. `bundle_id`는 새 ID다.

```json
{
  "intent_file": "/secure/intent-resolved.json",
  "target_file": "/secure/target-resolved.json",
  "bundle_id": "lab-first-reviewed-1",
  "approved_by": "lab-operator",
  "approval_ref": "LAB-REVIEW-REFERENCE",
  "valid_until": "2026-11-15T22:00:00+09:00"
}
```

위 값은 형식 예시다. 실제 승인과 일치하도록 새 `lab-input.json`(0600)에 적은 뒤 아래 블록을 실행한다. 플랫폼 서비스나 이전 `current`가 없어도 새 폴더 `lab-first-bundles/<bundle_id>`를 생성한다. 정책·승인 목록·intent·target의 해시와 크기를 실제 바이트로 계산하고 실제 로더로 검증한다. 플랫폼용 `bundle build --policy`는 CONFIRMED 원본을 요구하므로 이 LAB 경로와 구분한다.

```python
# LAB_BUNDLE_SETUP: .venv/bin/python으로 실행; 입력은 runtime/lab-input.json
from datetime import datetime, timezone
import hashlib, json, re
from pathlib import Path
from serving_runtime.policy.policy_bundle import verify_policy_bundle
from serving_runtime.policy.policy import load_policy
from serving_runtime.target.target import load_target
from serving_runtime.enforcement.intent import parse_intent
cfg = json.loads(Path("lab-input.json").read_text())
now = datetime.now(timezone.utc)
assert datetime.fromisoformat(cfg["valid_until"].replace("Z", "+00:00")) > now
assert re.fullmatch(r"[A-Za-z0-9][A-Za-z0-9._:-]{0,127}", cfg["bundle_id"])
assert cfg["approved_by"].strip() and cfg["approval_ref"].strip()
intent = json.loads(Path(cfg["intent_file"]).read_text())
target = json.loads(Path(cfg["target_file"]).read_text())
assert "REPLACE" not in json.dumps([intent, target])
parse_intent(intent)
assert load_target(cfg["target_file"]).state == "ok"
policy = json.loads(Path("deploy/gpu-lab/policy.aws-lab.json").read_text())
policy.update(target_id=target["target_id"], allowed_models=[target["model"]["id"]],
              valid_from=now.isoformat(), valid_until=cfg["valid_until"], approval_ref=cfg["approval_ref"])
parent = Path("lab-first-bundles")
parent.mkdir(mode=0o700, exist_ok=True)
out = parent / cfg["bundle_id"]
out.mkdir(mode=0o700)
def write(name, doc):
    path = out / name
    path.write_text(json.dumps(doc, ensure_ascii=False, indent=2)+"\n")
    path.chmod(0o600)
    return path
policy_path = write("policy.json", policy)
assert load_policy(policy_path).ok
policy_sha = hashlib.sha256(policy_path.read_bytes()).hexdigest()
write("approvals.json", {"schema_version": "runtime-policy-approvals/1.0", "entries": [{
    "policy_id": policy["policy_id"], "policy_version": policy["policy_version"], "sha256": policy_sha,
    "approval_ref": cfg["approval_ref"], "approved_at": now.isoformat(), "valid_until": cfg["valid_until"]}]})
write("intent.json", intent)
write("target.json", target)
files = []
for role, name, schema in [("gateway_policy", "policy.json", "runtime-mvp/1.1"),
                         ("policy_approvals", "approvals.json", "runtime-policy-approvals/1.0"),
                         ("enforcement_intent", "intent.json", intent["schema"]),
                         ("target", "target.json", target["schema_version"])]:
    raw = (out/name).read_bytes()
    files.append(dict(role=role, path=name, schema_version=schema, sha256=hashlib.sha256(raw).hexdigest(), bytes=len(raw)))
write("bundle.json", {"schema_version": "byul-policy-bundle/0.1", "bundle_id": cfg["bundle_id"],
    "created_at": now.isoformat(), "target_ref": target["target_id"],
    "policy_ref": {"policy_id": policy["policy_id"], "policy_version": policy["policy_version"], "sha256": policy_sha},
    "approval": {"approved_by": cfg["approved_by"], "approved_at": now.isoformat(), "approval_ref": cfg["approval_ref"]},
    "validity": {"valid_from": now.isoformat(), "valid_until": cfg["valid_until"]}, "files": files})
verify_policy_bundle(out)
```

이 LAB `policy_ref.sha256`은 생성한 Gateway 정책 바이트 해시이며 LAB 검토 기록에 명시한다. 플랫폼 승인 원본의 정규 해시는 플랫폼을 통한 실제 승인 판본을 받을 때 별도로 대조한다. 생성 실패 때 남은 폴더는 진단용으로 보존하고 새 ID로 다시 준비한다. 서버 배치는 [수동 적용 절차 5~10단계](../gpu-lab/정책_수동적용_절차.md)를 따른다. 최초 설치에서는 기존 `current`가 없는 상태를 기록하고 완성·검증한 폴더로 새 **상대 링크**를 만든다. 승인 기준선·폐기 목록의 생성·검토·게시도 [업데이트 검증 후보와 승인](../../docs/업데이트검증_후보와승인.md)을 따른다. 빈 폐기 목록 역시 검토 후 게시한다.

## 4. GID 충돌과 설치 후 빠진 전제 확인

`getent group 10000`과 `getent group 10010`을 서버에서 확인한다. 설치기는 파일 쓰기·계정 생성 전에 충돌을 거부한다. 예를 들어 사용하지 않는 12000을 검토했다면 비공개 `install.env`의 `GATEWAY_DATA_GID=12000`을 지정한다. Gateway의 `runAsGroup`, policy/data hostPath의 소유 그룹, 관련 서비스의 데이터 읽기 그룹을 12000으로 맞춘다. `supplementalGroups`의 관측 GID는 `OBSERVE_GID`와 맞추고, Gateway UID 및 trusted-owner UID 10000은 유지한다. 기존 `serving-bundles` 그룹이 있으면 그 GID를 사용한다. 설치기의 `--dry-run`으로 먼저 검사한다.

GPU LAB README의 Secret 등록·엔진 로그 옵션 추가 절차를 완료한 뒤 아래처럼 **값을 출력하지 않는 검사**를 추가한다. context·namespace는 운영자가 검토한 실제 값으로 맞춘다.

```sh
# Secret 메타데이터 존재 확인: 없으면 AUTH_SECRET_MISSING으로 설치 완료 처리를 중단
kubectl --context byul-aws-lab -n serving-lab get secret serving-gateway-auth -o name >/dev/null || { echo AUTH_SECRET_MISSING; exit 1; }
# 공개 로그 옵션 이름만 비교하며 env·Secret·전체 args는 출력하지 않는다.
kubectl --context byul-aws-lab -n serving-lab get deployment serving-engine -o json |
  .venv/bin/python -c 'import json,sys; d=json.load(sys.stdin); c=next(c for c in d["spec"]["template"]["spec"]["containers"] if c["name"]=="engine"); a=c.get("args",[]); missing={"--enable-log-requests","--enable-request-id-headers"}-set(a); print("ENGINE_LOG_OPTIONS_MISSING" if missing else "ENGINE_LOG_OPTIONS_OK"); sys.exit(bool(missing))'
.venv/bin/python -c 'from guard.adapters.vllm_engine_callback_sensor import TAG; assert TAG == "byul-cb-"; print("LABTOOLS_UPDATE_OK")'
```

これは配置前提の点検だ。Secret のキー名・auth 設定の読み込み、実ログの callback ID・応答の receipt は、既存 preflight と R-04/R-13 の実行結果で確認する。`serving-runtime-agent` が disabled/inactive であることも確認する。
