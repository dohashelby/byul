# AWS GPU dev 서버 3회차 확인순서

기준: `byul_runtime`의 `b3fc80e`. 이 문서는 **한 번의 서버 가동에서 남은 확인을 끝내기 위한 순서와 판정표**다. 기존 배포·인수 명령은 [서버 실행순서표](서버_실행순서표.md) 1~17단계, [SGLang 전환 절차](SGLANG_전환절차.md) 1~4절, [ACCEPTANCE](ACCEPTANCE.md)의 「추가 확인 AWS-12~17」·「사례와 증거」, [정책 수동적용 절차](정책_수동적용_절차.md) 1~10단계를 따른다. 여기에는 2회차 뒤 남은 확인만 적는다. 2회차의 통과는 [2회차 결과](../../docs/AWS_GPU_서버2회차_결과_20261104.md)의 당시 코드·캐시 상태에 한정된다. 서버 뒤 교차 검수 보완판은 실제 환경에서 미확인이다.

가동 요금은 약 **USD 1.2/시간**으로 잡는다. 모든 시각은 UTC로 기록하고 발표용 화면에는 시간대도 표시한다. 증거 부모 폴더는 서버에 `evidence-<date>`를 새로 만든다. 파일 이름은 아래 표의 상대 이름을 사용한다. 결과는 `통과 / 실패 / 확인 불가`로 분리하고, 확인 불가를 통과로 바꾸지 않는다. 주소·호스트명·인스턴스 ID·토큰·키 값·실명·요청 본문·원시 로그 전문은 문서나 반출 증거에 쓰지 않는다.

## B. 서버 가동 중 공통 순서

[서버 실행순서표](서버_실행순서표.md) 1~3단계로 가동, 첫 preflight, 이미지·묶음·규칙 적용을 끝낸다. 수집기 상태는 **수집기 서비스를 소유한 일반 사용자**로 확인한다. `sudo` preflight는 사용자 systemd 서비스를 보지 못해 거짓 `fail`을 낼 수 있다. 새 Gateway 태그와 같은 커밋 수집기를 확인하고, vLLM 새 묶음의 `current` 링크 대상·검증·Gateway의 실제 묶음 ID를 서로 대조한 다음 preflight를 재실행한다. SGLang으로 바꿀 때도 같은 검증을 반복한다. 각 확인은 시작/끝 시각, 엔진, Pod UID의 비식별 축약값, 묶음 ID, 결과, 판정 근거의 필드 이름만 남긴다.

### 3. gap 실증: 실제 코드에서 가능한 순서와 한계

[수집기 코드](../../tools/k8s_observation_feed.py)의 Tetragon 자식은 `kubectl logs --follow`이고, 자식 종료를 1초 tick에서 발견하면 `tetragon.gaps.jsonl`에 `gap_opened`를 추가한다. 바로 자동 재연결을 시도하므로 수동으로 `kill` 후 천천히 서비스 상태를 보면 이미 `gap_closed`가 될 수 있다. **확인 불가 가능성이 있는 경합 시험**이다. 서비스의 PID 전체를 `pkill` 패턴으로 찾지 않는다. 원격 셸까지 종료된 2회차 이력이 있다.

1. 일반 사용자 서비스의 main PID를 `systemctl --user show`로 얻고 그 **직계 자식 중 명령 인자가 Tetragon `logs --follow`인 한 PID만** `/proc/<pid>/cmdline`으로 식별한다. 명령 전문을 출력하지 않고 PID·기존 gap 파일 끝 위치·Tetragon 행 수만 기록한다. 엔진 Pod UID와 현재 수집 상태도 고정한다.
2. 같은 사용자로 짧은 감시 스크립트를 서버 임시 위치에서 실행한다. 해당 자식 PID에 `SIGTERM`을 한 번 보내고 새 `gap_opened` 행이 같은 gap 파일에 **fsync된 것을 확인하자마자** `systemctl --user stop byul-observation-feed`를 호출한다. 감시는 0.1초 안팎으로 폴링하고 새 행의 `kind=tetragon`·gap ID·`backfill_since`만 읽는다. `gap_opened` 전에 서비스를 멈추면 정상 종료라 gap이 안 생기므로 그 시도는 무효다. 중간에 이미 `gap_closed`가 생겼으면 자동 복구 경로만 본 것이므로 이 시험을 통과로 쓰지 않는다.
3. 서비스가 실제 stopped이고 Tetragon feed 행 수가 더 늘지 않음을 확인한 뒤, 엔진 Pod 안에서 **고정된 무해한 실행 한 건**을 한다. 예: 기존 AWS-09의 셸 실행과 구분되는 `/usr/bin/true` 1회. 실행 전후 UTC 시각과 Pod UID를 남기며 출력·환경값은 보지 않는다. 이 경로가 이미지에 없으면 존재하는 무해한 실행 파일을 먼저 확인하고 이름을 기록한다. 서버에서 직접 실행하면 엔진 Pod 기록이 되지 않는다.
4. `systemctl --user start byul-observation-feed`로 재개한다. 새 수집기 시작 때 `_prior_backfill_since`가 열린 gap의 가장 이른 `backfill_since`를 사용하고 Tetragon에는 `--since-time`을 넘긴다. 첫 정상 tick 뒤 `_close_prior_gaps`가 같은 ID를 `collector_restart`/`requested_unverified`로 닫는지 확인한다. 엔진 Pod UID·실행 시각·실행 경로가 재조회된 `tetragon.jsonl`과 Gateway 관측에 실제로 있는지도 대조한다. 중복 행은 있을 수 있으므로 행 수 증가만으로 성공으로 치지 않는다.

이 실증은 양 엔진 AWS-09·10·11 판정 구간이 끝난 뒤에만 진행하고 발표 시연 장면과도 시각을 분리한다. 무해한 실행은 허용 목록 밖이라 의도한 `outside_allowlist` 경고가 생긴다. 이를 시험 실행으로 표시하고 전후 정상 요청 ID·실행 UTC 시각을 함께 기록해 AWS-11 오탐으로 세지 않는다(직접 Pod 실행 자체에는 Gateway 요청 ID가 없다).

이 방법은 코드 경로상 실행 가능하지만 자동 재연결과 서비스 stop 사이의 **1초 내 경합은 서버에서 미검증**이다. 로그 보존·회전, Tetragon 출력 지연, 조기 재연결 때문에 실제 실행이 안 돌아올 수 있다. gap 닫힘 상태는 backfill **요청** 증거이고, 실행 1건 대조가 이 시험 범위의 전달 증거다. 실패해도 수집기를 정상으로 복구하고 `gap_id`·시각·상태만 남긴다.

### 4~6. 빈 캐시 첫 부팅에서 함께 볼 것

- [SGLang 전환 절차](SGLANG_전환절차.md) 1절의 기존 캐시 경로를 기록하고 **삭제 대신 다른 이름으로 이동**해 복구 가능하게 둔다. 원래 mount가 가리키는 경로를 빈 디렉터리로 다시 만들고 `tmp`, `home`, `config`, `xdg`, `hf`, `inductor`, `triton`, `cuda`, `pycache`를 UID 2000/GID 0·0700으로 준비한다. 부팅 전부터 로그 표지·EndpointSlice·시간표를 동시에 읽는 관찰 터미널을 연다. 기존 캐시를 건드리기 전에 새 디렉터리가 실제 엔진 mount에 반영될지 확인한다.
- `kubectl get endpointslice -l kubernetes.io/service-name=serving-engine`의 ready 주소 **개수만** 주기적으로 기록한다. 캡처 종료, `compiling` 시간표, Ready 시각을 같은 UTC 축에 놓는다. Ready 전에 고정 요청 ID를 가진 Gateway 정상 요청 1건을 보내 HTTP 상태·Gateway 결정만 적고, 같은 ID의 엔진 `request.received`가 없는지 제한된 로그 조회로 확인한다. Ready 후 정상 양성 요청으로 로그 경로를 검증한다. 로그 원문이나 Service 주소를 저장하지 않는다.
- Ready 뒤 **첫 요청**을 보내고 Tetragon 실행 경로와 부모, 시간표 `phase_basis`·`phase_trusted`, `exec_verdict`를 대조한다. SGLang intent의 추론 Triton 경로·Python 부모와 정확히 일치해야 한다. 셸은 부모 설명이 맞아도 `suspect_binary`여야 한다. 준비 표지가 누락되면 [전환 절차](SGLANG_전환절차.md) 2절의 시간 상한을 따르며 임의로 compiling을 늘리지 않는다.
- 엔진 컨테이너는 `readOnlyRootFilesystem`이 설정되지 않았으므로 `/models` 읽기 전용만으로 `ptxas` 보호를 주장할 수 없다. 정확한 `ptxas` 파일과 부모 디렉터리에 대해 UID 2000의 `stat` 모드·소유권과 `test -w`의 **참/거짓만** 기록한다. `kubectl exec`의 사용자 ID를 먼저 확인한다. `touch`, 편집, 덮어쓰기 시험은 하지 않는다. 다른 상위 디렉터리 교체 가능성까지 이 확인으로 증명하지 않는다.
- 시험 뒤 새 캐시를 별도 이름으로 보존할지 폐기할지 기록하고, 원래 캐시 경로·owner·mode·하위 폴더·Deployment mount를 복원한다. 이후 [전환 절차](SGLANG_전환절차.md) 4절의 vLLM 복귀를 수행한다.

### 7. vLLM 과거 기록: 원본 전체를 내보내지 않는 추출

범위는 **11/3 15:31:56~15:31:57 UTC**의 엔진 Pod `process_exec` 두 건이다. Gateway 저장소 `/srv/serving/runtime/data/observations.jsonl`에서 `source=tetragon`, `kind=process_exec`, 해당 시간, 당시 vLLM 엔진 Pod UID·namespace·label을 함께 대조한다. 이 저장소에는 `binary`, `phase`, `phase_basis`, `phase_trusted`, `phase_source_error`, `parent_check`, `parent_attribution`가 있으나 **실제 부모 경로 필드는 저장되지 않는다**. 따라서 Gateway 저장소만으로 요구한 세 값 중 부모 경로를 추출할 수 없다. Tetragon 호스트 feed의 같은 시간·UID·binary 행에 `process_exec.parent.binary`가 남아 있을 때만 서버 안에서 결합한다. 결합 키가 모호하면 부모를 추측하지 않는다.

서버의 비공개 작업 스크립트가 두 JSONL을 **서버 안에서** 읽어 시간·Pod UID·binary로 한정한 후 `binary`(실제 경로), `parent.binary`(실제 부모 경로 또는 `null`), `phase_basis`·`phase_trusted`(단계 출처), `parent_check`만 새 JSON에 쓴다. 원시 행, args, Pod 이름, UID, Secret, 주소는 출력 파일에 넣지 않는다. 출력 파일만 노트북으로 옮겨 비밀·주소 패턴을 검사한다. 부모 경로가 없거나 다중 일치면 `확인 불가`와 누락 필드만 남긴다. 두 행의 문자열·부모 조건이 현 vLLM intent와 같아도 시간표 출처 오류가 있었는지는 별도 대조해야 하며, 원인은 관측 전 확정하지 않는다.

### 8. 사람이 확인할 플랫폼 화면

[runtime README](../../README.md)의 연결 안내와 [platform README](../../../platform/README.md)의 환경변수 절대로, 노트북에서 서버 Gateway로 **로컬 포워드/터널**을 연 뒤 노트북 platform을 `RUNTIME_BASE_URL`로 그 로컬 Gateway 조회 주소에 연결한다. 조회 보호가 켜져 있으면 `RUNTIME_VIEWER_TOKEN`은 비공개 환경 파일에서만 주입하고 명령행·로그에 값을 출력하지 않는다. platform이 실제 연결을 표시하고 예시 자료 띠가 없는지 먼저 사람이 본다. Gateway 재시작·엔진 전환 후 포워드 연결을 다시 확인한다. 화면 갱신 간격(3초)을 고려해 시각과 건수만 적는다.

| 화면 | 사람의 확인 지점 |
| --- | --- |
| `/runtime/requests` 요청 이력 | 정상 허용, 인증/한도/필드 거부의 요청 ID·결정·엔진 도달 여부. |
| `/runtime/events` 사건 로그 | 셸 실행 탐지, 규칙·출처·시각. 탐지는 차단으로 표기하지 않는다. |
| `/runtime/observe/collectors`, `/runtime/observe/hubble`, `/runtime/observe/tetragon` 수집원 | 각 수집원 상태·gap/손실·Hubble dropped·Tetragon 실행. 수집기를 멈추면 `unobservable`/관측 불가 상태가 나타나는지 보고, 재개 후 복구를 본다. |
| `/runtime/enforce/cilium`, `/runtime/enforce/lab` 통제 적용 | Cilium 적용/차단과 lab 시험 상태를 실제 규칙·Hubble 근거와 맞춘다. |
| `/runtime/target`, `/runtime/settings` 대상·구성 | 엔진 종류·Pod/설정 대조·조회 인증 상태가 현재 전환 상태와 맞는지 본다. |
| `/runtime/policy` 정책·기준 | 묶음 ID, 정책 판본, 활성 상태, 승인 `verified`, 판정 기준이 실제 Gateway API와 맞는지 본다. |

### 9. 발표 장면 리허설

고정된 비밀 없는 시험 요청과 기존 [ACCEPTANCE](ACCEPTANCE.md) 사례·허용 플래그를 이용한다. 요청 ID와 화면에서 확인한 시각만 기록한다. vLLM에서 먼저 전 장면을 보고, SGLang 전환 뒤 **같은 화면 경로**로 반복한다. 화면에 값 노출이 생기면 캡처하지 말고 필드 이름만 기록한다.

| 장면 | 명령 개요 | 사람의 화면 위치·기대 |
| --- | --- | --- |
| 정상 허용 | AWS-01의 일반 정상 요청 1건 | `/runtime/requests`: 허용과 엔진 로그의 같은 요청 ID. |

### 10. 선택 성능: 이 서버에서 실행 가능한가

[성능 도구](../../tools/perf_compare.py)는 모드를 바꾸지 않고 [AWS 계획](perf-plan.aws-lab.json)의 B0·B1·B2 **이미 준비된 세 Gateway URL**로 요청한다. B0는 같은 Gateway/CNI/모델을 두고 추가 센서·판정·통신 규칙을 끈 구성, B1은 관측·Tetragon monitor, B2는 요청 옵션·통신·선정 거부를 더한 구성이다. 단일 GPU dev 서버에서 현재 문서가 제공하는 것은 vLLM↔SGLang 순차 전환과 현재 정책 묶음이며, 독립된 B0/B1/B2 준비·전환·복원 절차나 세 Gateway의 실재 여부는 확인되지 않았다. **현 상태에서는 정식 성능 비교 실행 불가**로 계획한다. 세 구성을 사전 준비·승인하고 같은 엔진/모델·부하·캐시 조건과 Gateway URL을 각각 검증한 경우에만 실행 판단을 다시 한다. B0를 엔진 직통으로 대체하지 않는다.

도구 기본 예산은 각 모드마다 예열 20 + 일반 100 + stream 100건을 3블록에서 반복해 **총 1,980요청**이며 동시성 2, 요청당 timeout 300초다. 실행 시간은 서버 실측값이 없어 **예측 불가**다. 실패가 없고 평균 요청 시간이 대략 1~3초라고 가정해도 직렬 부하 환산만 16.5~49.5분이며, 준비·모드 복귀와 긴 stream/timeout을 제외한 거친 가정치다. 따라서 이번 단일 가동의 고정 시간표에는 넣지 않는다. 생략하면 AWS 기능·화면 확인은 가능하지만 B0 대비 10% LAB 성능 예산, 3블록 순서 효과와 성능 합격은 **미측정**이다. 선택 판단을 `10-perf-decision.md`에 남긴다.

## C. 종료 전 복구·증거·Stop

1. `evidence-<date>`에 위 10개 요약과 인수 `report.json`·`report.md`, 적용 전후 묶음 ID·링크 대상·규칙 이름/복원 결과, 시작/끝 시각, `통과/실패/확인 불가`를 모은다. 요청 내용·원시 Secret·원시 로그 전문은 넣지 않는다. 과거 서버에 남아 있던 보고서가 필요하면 존재·무결성만 확인하고 별도 승인된 반출 범위로 다룬다.
2. 서버에서 반출 **대상 파일만** 토큰/관리 키의 실제 값, 주소·호스트명·인스턴스 ID 패턴, 비밀 이름/값, 프롬프트로 검사한다. 검색 명령은 일치 값이 아니라 파일명·건수만 출력하게 한다. 문제가 있으면 서버에서 해당 값만 가리고 재검사한다. 노트북 수신 뒤 파일 수·SHA-256을 맞추고 같은 검사를 반복한다.
3. 임시 NetworkPolicy와 Cilium/Tetragon 변경은 [서버 실행순서표](서버_실행순서표.md) 6·15단계 및 [SGLang 전환 절차](SGLANG_전환절차.md) 4절대로 원본 spec·labels와 대조한다. 원래 SGLang 캐시와 mount, host service vLLM 설정, **원래 정책 묶음 `current` 상대 링크**, vLLM Deployment·imageID를 복원하고 Gateway를 재시작한다. 수집기 `ok`, 정상 200/거부 401, 정책 승인 `verified`를 재확인한다.
4. 증거 반출과 복구가 확인된 뒤 [서버 실행순서표](서버_실행순서표.md) 16~17단계대로 Stop을 요청하고 stopped 상태·시각을 기록한다. 복구 실패·증거 미반출이면 비용을 감수하고 상태와 담당 역할을 즉시 전달한다. Stop 시도 자체와 실제 stopped를 구별한다.

## D. 시간·비용 및 중단 우선순위

서버 시간은 계획치다. 전원 켜기 전 승인·빌드·묶음·전체 시험 시간은 제외한다. 첫 부팅 약 4분 20초는 4~6번 창 안에 포함한다. 중복 실행을 줄이기 위해 vLLM 적용/재판정/기록 추출/화면·시연 → SGLang 빈 캐시 첫 부팅/Ready 창/재판정/같은 화면·시연 → 두 엔진 AWS-11 종료 뒤 gap 실증 → vLLM 복귀 순서로 묶는다.

| 구간 | 서버 가동 예상 | 누적 | 약 USD 1.2/시간 환산 |
| --- | --- | --- | --- |
| 가동·preflight·같은 커밋 적용·묶음 확인 | 20~35분 | 20~35분 | 0.40~0.70 |
| vLLM AWS-09·10·11(함께 선택)·13, 과거 기록, 1차 화면/시연 | 30~50분 | 50~85분 | 1.00~1.70 |
| SGLang 전환·빈 캐시 첫 부팅·Ready/권한 | 30~45분 | 80~130분 | 1.60~2.60 |
| SGLang AWS-09·10·11(함께 선택)·13·16·17, 화면/시연, gap | 40~65분 | 120~195분 | 2.40~3.90 |
| vLLM 복구·증거 검사/반출·Stop | 25~40분 | **145~235분** | **약 2.90~4.70** |

실패 복구와 네트워크 지연은 추가 비용이다. **복구·증거·Stop 시간 40분을 항상 남겨 둔다.** 시간이 모자라면 ① 선택 성능(기본 생략), ② 시연의 중복 화면 설명과 부가 장면, ③ 과거 vLLM 기록 원인 분석, ④ gap 실증 순으로 포기한다. ⑤ 화면 전체 확인은 남은 필수 경로부터 진행하고 미확인 화면을 명시한다. [서버 실행순서표](서버_실행순서표.md)의 「시간이 부족할 때」는 1회차 전체 인수용으로 AWS-13을 뒤로 미루지만, 이번 3회차는 AWS-13 보완판 실증이 목적이므로 위 순서를 쓴다. 시작한 AWS-13·16·17, 수집 중단, NetworkPolicy 회수, 캐시 이동은 **복구 없이 중단하지 않는다**. 새 Gateway·수집기/묶음 검증과 SGLang Ready 전 창, 빈 캐시 첫 JIT, 최종 vLLM 복귀·반출·Stop을 우선 완료한다.
