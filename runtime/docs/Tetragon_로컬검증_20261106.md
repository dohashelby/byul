# Tetragon 차단 판정·로컬 실측·대시보드 연결

기준: `byul_runtime`의 PR #224 머지 `1a03e6c` 이후 변경. 2026-11-06 KST에 수행했다. 사용자 요청으로 로컬 커밋만 남기며 PR·푸시·머지는 하지 않는다. 실제 AWS 서버와 GPU 엔진은 실행하지 않았다.

## 구현 내용

1. `enforcement/verification.py`에서 **파일 읽기 거부**, **프로세스 종료**, **시험 서비스 재시작·복구**를 각각 판정한다. 이벤트 이름만으로 확인 처리하지 않는다.
2. `tools/tetragon_trial.py`는 로컬 `kind-runtime-lab`에 매번 새 namespace와 시험용 HTTP Pod를 만든다. 파일을 읽는 주체는 그 Pod의 PID 1이다. 가짜 파일은 일반 파일로 만들고 내용은 출력하지 않는다. 감시 모드의 성공 읽기 → 차단 모드 시험 → 감시 복귀를 대조한다. 기존 엔진·Gateway 정책은 삭제하지 않는다.
3. `tools/tetragon_status.py`가 노드별 실제 정책 ID·STATE·MODE와 기능 점검을 읽고 원자적으로 상태 파일을 쓴다. Gateway는 이 파일을 읽기 전용 `/api/tetragon-status`로 제공하며, platform의 `/api/runtime/tetragon-status`와 `/runtime/enforce/tetragon` 화면으로 이어진다. Gateway나 platform에 정책 수정 권한을 추가하지 않았다.

## 판정 근거

- 대상: 같은 정책·Pod UID·파일·프로세스 ID·차단 모드 시간 구간이어야 한다. 기존 자료는 1.7.1의 `process.pod.container.pid`로 확인한다. 새 시험은 아래 커널 task·CRI 대조로 주 프로세스 PID 1을 독립 확인하고 감시 이벤트의 커널 PID를 차단 이벤트와 연결한다. Pod UID는 Kubernetes/CRI에서 확인한 값이며 `identity_source=kernel_task`로 Tetragon 캐시 귀속과 구분한다.
- 읽기 거부: 감시 모드의 읽기는 성공해야 한다. 차단 중 사용자 공간 EPERM과 동일 프로세스의 Override 이벤트, 또는 실제 Override(-1) 설정과 `security_file_permission`의 read mask 4·반환값 -1을 요구한다. 다른 경로·PID·시간·mask의 이벤트, 단순 Sigkill 이벤트는 거부 증거로 쓰지 않는다.
- 커널 반환값 해석: Linux 6.18의 `vfs_read`는 `rw_verify_area`가 오류를 반환하면 실제 파일 읽기로 진행하지 않는다. `rw_verify_area`는 `security_file_permission`의 거부 결과를 반환한다. 이 소스와 로컬 가짜 파일의 같은 읽기·프로세스·반환값을 대조해 **해당 시험 읽기의 권한 검사 거부**로 판정한다. 보호 경로 전체·다른 API·모든 우회의 방지를 주장하지 않는다. [Linux 6.18 read 경로](https://github.com/torvalds/linux/blob/v6.18/fs/read_write.c).
- 프로세스 종료: 같은 프로세스의 Sigkill 이벤트와 같은 Pod·컨테이너의 종료 코드 137, OOMKilled가 아님, 해당 시간의 종료 기록을 대조한다. Pod UID 변경만으로 재시작을 추정하지 않는다.
- 복구: HTTP 접근 실패 → 컨테이너 restartCount 증가 → HTTP 정상 복구, 같은 정책 ID의 monitor 복귀와 다시 읽기 성공을 요구한다. 이는 시험용 HTTP 서비스의 증거이며 실제 Gateway 503·vLLM·SGLang 복구 실증은 아니다.
- 저장된 결과의 `confirmed` 표지만 신뢰하지 않는다. Gateway가 근거와 전환 시간을 다시 대조해 판정을 재계산한다. 수집 불완전·에이전트 교체·근거 불일치는 미확인이다.

## 실제 kind 결과

환경은 Tetragon CLI **v1.7.1**, WSL2 커널 **6.18.33.2-microsoft-standard-WSL2**, 단일 kind 노드다.

| 시험 | 읽기 거부 | 주 프로세스 종료 | 시험 서비스 재시작·복구 | 감시 복귀 |
| --- | --- | --- | --- | --- |
| `sigkill_fd_install` | 미확인 | 확인: 동일 PID의 Sigkill·종료 137 | 확인 | 동일 ID 복귀·읽기 성공 |
| `override_lsm` Override+Sigkill | 확인: read 권한 검사 반환 -EPERM | 확인: 동일 PID의 Sigkill·종료 137 | 확인 | 동일 ID 복귀·읽기 성공 |
| `override_lsm` **Override 단독 진단** | 확인: 사용자 공간 EPERM·동일 PID Override | 종료하지 않는 진단 | 종료·재시작을 목표로 하지 않음 | 동일 ID 복귀·읽기 성공 |
| `override_syscall` | 규칙 load_error로 미검증 | 미검증 | 미검증 | 미로드 시험 정책·namespace 정리 |

Override 단독은 **시험 전용**이다. 실제 사용 후보의 Sigkill을 제거하거나 기본 방식을 바꾸지 않았다. syscall 후보의 실제 오류는 `override action not supported on syscalls, bpf_override_return helper not available`이었다. 로드 실패를 성공으로 바꾸지 않는다.

정상 수집된 앞선 실측 원본·적용 manifest·원시 이벤트를 보존하고 강화한 판정기로 재평가했다. **재평가는 새 실행이 아니다.** 보고서의 원래 시작·종료 시각, `reassessed_at`, 원본/manifest/이벤트 해시를 구분한다.

- 정상 실측·정규화 보고서: `~/.local/state/serving-runtime/tetragon-evidence/*.verification.json`
- 보존 원본: 같은 폴더 `artifacts/<시험 ID>/`의 `original.verification.json`, `policy.json`, `probe-events.jsonl`
- 모드 전환: 같은 폴더 `transitions.jsonl`
- 화면의 **시험 근거 다운로드**는 원문 내용·명령 인자 없이 식별자·시각·반환값·종료 기록·전환·해시를 내려준다.
- 초기 구현 확인 중 실패·미확인 기록은 `/tmp/byul-tetragon-proof*`에 남아 있으며 최종 정상 실측과 구분한다.

보완 전 재실행(`/tmp/byul-tetragon-validated-final`)에서는 fd_install·LSM 결합·LSM 단독 모두 감시 단계의 읽기와 주 프로세스 이벤트를 연결하지 못해 차단 단계로 진행하지 않았다. syscall은 같은 로드 오류로 미지원이었다. 에이전트 restartCount는 이 재실행 전후 4로 같았다. 이 네 결과도 영구 근거 폴더와 화면에 보존했다. 아래 보완 후 새 실행으로 반복 재현을 확인했으며 과거 실패를 성공으로 덮어쓰지 않았다.

## 귀속 누락 조사·보완 후 반복 실측

고유 정책의 gRPC 이벤트를 namespace 필터 없이 수집하자 `process.flags=unknown`, Pod·binary·exec_id가 없는 kprobe 이벤트를 확인했다. 기존 namespace 필터는 이 이벤트를 제외해 빈 파일을 만들었다. 노드 procfs의 PID namespace 불일치 경고와 캐시 누락·퇴출도 관측했다. WSL·kind의 귀속 제약과 일치하지만 에이전트 내부 원인을 하나로 단정하지 않는다. 호스트 procfs 경로 보정 실험도 해결하지 못했으며 임시 mount와 DaemonSet 변경을 원복했다. 두 번의 계획된 에이전트 교체가 있었고 그 구간의 감시 무공백을 주장하지 않는다.

시험 도구를 다음처럼 보완했다.

- 시험마다 정책 이름을 고유하게 만들고 그 정책만 수집한다. namespace 필터로 불완전한 이벤트를 숨기지 않는다. 귀속 재시도 15×2초를 고려해 감시 대조를 최대 40회 기다린다.
- **시험 정책에만** `data.source=current_task`를 추가해 커널의 tgid·start_boottime·PID namespace inode를 직접 읽는다. 후보의 훅·파일 조건·접근 mask·집행 action은 유지한다. [Tetragon v1.7.1 current_task 공식 시험](https://github.com/cilium/tetragon/blob/v1.7.1/pkg/sensors/tracing/kprobe_test.go).
- Kubernetes의 정확한 Pod UID·컨테이너 ID → 해당 노드 CRI init PID → `/proc`의 PID 1 여부·namespace inode·시작 tick을 읽는다. 이벤트의 커널 namespace와 시작 시각이 그 init과 일치해야 한다. tick 단위 절삭은 `[tick/HZ, (tick+1)/HZ)`의 정수 구간으로 비교한다. child·다른 컨테이너·PID 재사용·충돌하는 Pod 정보는 거부한다.
- 차단 직전에 CRI identity를 다시 확인하고 감시/차단 이벤트의 같은 커널 PID를 요구한다. Gateway도 저장된 task 근거·실제 적용 data 선언·모드 시간 구간을 재대조한다. 단순한 PID 일치나 성공 표지로 통과시키지 않는다.

보완 후 **새 독립 namespace에서 각각 3회 연속** 다음 결과를 확인했다. 각 실행 전후 같은 에이전트 Pod UID·restartCount 0을 확인했다.

| 방식 | 반복 결과 | 확인 범위 |
| --- | --- | --- |
| fd_install Sigkill | 3/3 통과 | 같은 주 프로세스의 Sigkill·종료137·재시작·HTTP 복구·동일 정책 ID 감시 복귀·읽기 성공. 파일 읽기 거부는 미확인 |
| security_file_permission Override+Sigkill | 3/3 통과 | read mask4의 -EPERM·주 프로세스 종료137·재시작·HTTP 복구·동일 ID 감시 복귀·읽기 성공 |

새 실행 근거는 `/tmp/byul-tetragon-repaired-round2`, `/tmp/byul-tetragon-repaired-repeat`와 영구 근거 폴더에 보존한다. 별도 Override 단독 진단도 새 커널 task 대조로 사용자 공간 EPERM·Override·감시 복귀를 확인했다(`/tmp/byul-tetragon-repaired-diagnostic`). 이 진단은 프로세스 종료를 목표로 하지 않는다.

이 보완은 **시험의 정확한 대상 확인**을 해결한다. 일반 운영 이벤트의 Tetragon process-cache/Pod 귀속 문제나 에이전트 자체 버그가 수정된 것은 아니다. 운영 배포의 수집·재시작 안정성 및 실제 GPU 엔진 검증은 별도로 남는다.

## 실측 중 발견한 제한과 보완

- 1.7.1의 표 출력은 메모리가 `2.00 MB`처럼 두 토큰이라 MODE 열이 밀렸다. 파서를 실제 출력에 맞춰 수정하고 회귀시험을 추가했다. `monitor_only`는 차단 동작 없는 정책에서 실제 관측된 상태다. set-mode의 전환 입력은 monitor/enforce이며 감시 전용 정책을 임의로 enforce로 취급하지 않는다.
- CRD가 `args`·`returnArg`에 `maxData=false`, `returnCopy=false`, `resolve=""`, probe에 `return=false`를 보완한다. 이 확인된 기본값만 정규화해 비교한다. true나 실제 selector/action 차이는 무시하지 않는다.
- 기존 export allowlist가 시험용 이름·namespace를 포함하지 않았다. 기존 설정을 수정하지 않고 시험 정책의 별도 gRPC 이벤트 스트림을 수집했다. 스트림은 시간 제한과 시험 소유 프로세스 정리로 제한한다.
- 재시험 중 **2026-11-05 18:03:06 UTC** Tetragon 컨테이너가 exit 2로 종료됐다. 종료 메시지의 `TotalMemlock`/`ListTracingPolicies` 및 Go map 경로에서 내부 오류를 확인했다. 자동 재시작 뒤 기준 정책들이 enabled로 다시 조회됐다. 이 구간을 감시 무공백 통과로 기록하지 않으며 완전한 공백 길이는 측정하지 못했다.
- 정책 추가/제거 직후 즉시 조회를 피하도록 안정화 대기를 넣었다. 상태 수집도 CRD 변경 시 현재 모드를 미확인으로 두고 다음 안정된 조회를 기다린다. 시험 중 에이전트 restartCount/Pod UID가 바뀌면 수집 근거를 불완전 처리하고 추가 시험을 중단한다. **에이전트 자체 버그를 고쳤다는 뜻은 아니다.** 이후 실서버 시험 전 동일 버전의 이 경로를 재검토해야 한다.
- `tetra probe`의 `override_return=false`만으로 security 훅 방식이 불가능하다고 단정하지 않는다. fmodret 경로가 있으면 로드 시험이 필요한 후보로 남긴다. 로컬의 결과를 AWS에 그대로 적용하지 않는다.

## 실행·화면

```bash
cd runtime
.venv/bin/python -B -m tools.tetragon_trial \
  --output '<시험-폴더>' --methods sigkill_fd_install override_lsm override_syscall \
  --allow-isolated-kind-trials
.venv/bin/python -B -m tools.tetragon_trial \
  --output '<시험-폴더>' --methods override_lsm \
  --override-only-diagnostic --allow-isolated-kind-trials
.venv/bin/python -B -m tools.tetragon_status \
  --context kind-runtime-lab --output '<Gateway-data-dir>/tetragon-state.json' \
  --evidence-dir '<시험-폴더>' --watch
```

시험 CLI는 목표 미확인/실패/미지원이 하나라도 있으면 종료 코드 2를 반환한다. 각 결과 JSON을 함께 확인한다. 상태 수집 도구는 kubectl 읽기 조회와 Tetragon의 조회 명령만 사용한다. mode helper를 쓰는 기존 AWS/kind 시험도 전환 기록을 남기며 수집기는 지정한 근거 폴더 아래 기록을 읽는다.

개발 스크립트는 `RUNTIME_TETRAGON_STATE=1`일 때 수집기를 함께 시작한다. `RUNTIME_KUBE_CONTEXT`는 명시한 context(기본 kind-runtime-lab), `TETRAGON_EVIDENCE_DIR`은 시험 근거 폴더다. Gateway는 기본 data dir의 `tetragon-state.json`, 또는 `--tetragon-state` 경로를 읽는다. 20초 넘게 갱신되지 않거나 다른 context·잘못된 자료면 현재 상태로 표시하지 않는다.

화면: **Runtime → 통제 적용 → 파일·프로세스 정책 (Tetragon)**. 조회만 가능하다. 화면에서 서버 정책 모드를 변경하거나 묶음을 원격 적용하는 기능은 다음 단계다.
