## 적용 범위와 현재 준비 상태

이 작업본은 vLLM v0.31.0을 현재 구현 근거로 삼는다. 보호 요구·평가 질문은 재사용하고, loader·API·key·종결 함수 등 구체 경로와 시험 절차는 엔진·판본별로 대조한다. 현재 83개 시나리오는 보편적인 필수 항목 83개가 아니라 기본·선택 구성을 함께 담은 검토 목록이다. 참조 환경에 필요한 시나리오부터 실행하며, 다른 엔진에서는 의미가 같은 요구에 새 구현 근거를 연결하고 없는 기능은 조건에 따라 제외한다.

R05·R08·R09 추가 검토는 기존 10개 시나리오의 조건·시험 초점을 보완했다. 24개 묶음·83개 시나리오와 28개 Q 기록을 유지한다. 선택 live 변경은 여러 구현의 시험 변형을 포함하므로 83개가 최종 실행 횟수를 뜻하지 않는다. 재배포 기본·live 선택, 로컬/원격 공급의 조건부 범위는 유지한다.

[**문서에서 쓰는 표시:** R은 업무·동작 경로, AS는 보호 자산, POL은 보호 요구, TB는 신뢰가 달라지는 경계, SURF는 영향을 줄 수 있는 접점이다. Q는 평가 근거 기록, SC는 구체 시나리오를 찾는 ID다. 세부 동작과 소스 근거는 통합본](참고자료/통합본/통합본.md)을 사용한다.

## 분석 범위와 다루지 않는 내용

**다루는 범위:** 추론 서빙엔진의 요청·실행·공유 상태, 모델·코드 취득과 로딩, 직접 사용하는 자격·호스트·장치·통신, 배포·변경·종결·복구, 관측 자료를 다룬다. Gateway·업무 앱·Kubernetes·저장소는 엔진 접근·신원 전달·실제 소비·통제에 연결되는 접점에서 확인한다.

**전체 평가를 제공하지 않는 범위:** 업무 앱·RAG·에이전트의 전체 보안, 학습·데이터 준비 전 과정, 기업망 전체 감사, 모델의 일반 품질·유해성·탈옥/프롬프트 주입 방어, 하드웨어·드라이버 전체의 보안 검증, 법규 준수 인증은 포함하지 않는다. 다만 입력 처리·template·코드 실행·공유 메모리 등 서빙 경로의 보호 요구에 영향을 주는 접점은 점검한다. cache 재사용의 시간 관측처럼 이미 포함한 시나리오는 이 범위 설명으로 제외하지 않는다.

R10의 미디어 일부 정적 근거와 R14 평가 대기 상태를 유지한다. 기본 구성의 성공으로 선택 기능이나 다른 엔진의 전체 보호를 판정하지 않는다. 기존 DFD의 R·TB·공격표면을 읽을 때 이 범위를 적용한다.

## 위협에서 점검으로 연결하는 방법

1. 통합본의 정상·실패 흐름에서 입력자와 실제 소비 대상, 자산·보호 요구, 경계를 찾는다.
2. 주체가 실제 가진 권한으로 어느 접점을 조작·관찰할 수 있는지 확인한다.
3. 해당 환경에서 보호 요구가 깨지는 경로를 시나리오로 적고 기존 통제와 한계를 연결한다.
4. R×POL과 공격표면을 대조해 빠진 경로를 확인한다. 빈칸은 검토 대기·비적용 근거·후보 미도출을 구분해 남긴다.
5. 겹치는 보호 요구는 세부 점검·Q에 모으고, 적용 조건·정상 대조·증거·판정을 작성한다. 취약점·패치는 조건과 시험 기준을 보완하는 근거로 사용한다.

설정·문서·코드 확인, 담당자 확인, 실행 시험을 필요에 따라 함께 사용한다. 수용·보완·적용 보류 등 처리 결정은 시험 결과와 분리해 보고서에 기록한다. 용어와 개수의 의미는 [README 용어표](README.md#terms)를 따른다.

## 프레임워크 구성과 활용

| 구성 | 담는 내용 | 실제로 하는 일 |
| --- | --- | --- |
| 공통 서빙 분석 | R 정상·실패 흐름, AS 자산, POL 요구, SURF 접점, TB 경계, 공격자 시작 권한 | 대상 기능에서 누가 어떤 자료를 어디까지 바꿀 수 있는지 설명 |
| 보안 내용 체계 | 아래 다섯 영역과 세 관점 | 공급물부터 실행·관측·폐기까지 빠뜨리지 않고 검토 |

| 보호와 평가 기준 | 위협 후보, 기존/추가 통제, 체크리스트·보완 방법·시험·증거·판정 | 무엇을 왜 확인할지와 부족한 부분을 해결할 방법 제시 |

공통 분석은 환경별 적용 이후 사라지는 자료가 아니다. 실제 환경에서 선택한 각 질문은 원래 R·보호 요구·근거를 참조한다. 시험에서 예상과 다른 동작이 나오면 정상 흐름과 위협 후보를 함께 수정한다.

### 공통 적용·판정 규칙

- 같은 정책과 실행 증거를 여러 영역에서 재사용한다. 업무상 허용 관계와 기반 권한을 서로 다른 정책으로 만들지 않는다.
- 검토·시험의 최소 단위에는 적용 조건, 정할 정책값, 확인 방법, 요구 증거, 충족 기준, 보완 방법을 둔다. 서로 독립적으로 실패할 수 있는 확인은 결과를 나눠 기록한다.
- 필수 적용 항목이 미확인이면 상위 목적 전체를 충족으로 표시하지 않는다. 확인한 위반은 다른 증거가 부족하더라도 미충족으로 유지한다. 예외 승인은 미충족을 충족으로 바꾸지 않는다.
- 검사·인증 의존 서비스·정책 적용·수집기가 실패했을 때 허용·거부·보류·기존 정책 유지 중 어떤 동작이 필요한지 해당 항목에서 정한다. 모든 환경에 일률적인 서비스 중단을 요구하지 않는다.
- 공급물의 내용·승인과 실행 중 메모리 안전을 연결하되 각각 판정한다. 권한 철회와 실제 작업 종결, 공급물 적재와 최종 서비스 준비도 각각 확인한다.
- 대체 공급원·fallback은 해당 보호 요구를 다시 적용하는 조건이다. 공유 공급물은 내용·접근·수명에 관한 여러 요구를 함께 선택하는 기능별 묶음이다.
- R10의 미디어 정적 검토 일부 반영·전체 평가 대기, R14 검토 대기와 생성 코드·컴파일 캐시·native 완료의 근거 부족은 유지한다. 이 표가 모든 구현의 검토 완료를 뜻하지 않는다.

### 작성 방식에 참고한 공식 자료

[CSA CCM·CAIQ](https://cloudsecurityalliance.org/artifacts/introductory-guidance-to-ccm)의 통제와 질문 연결, [OWASP ASVS](https://owasp.org/projects/asvs)의 검증 요구, [NIST SP 800-53A](https://csrc.nist.gov/pubs/sp/800/53/a/r5/final)의 평가 방법, [CIS Benchmarks](https://www.cisecurity.org/cis-benchmarks-overview)의 제품별 점검·보완 방식을 참고했다. 이 문서가 해당 표준 준수나 인증을 획득했다는 의미는 아니다.

| 담당 역할 | 결정하거나 제공할 것 |

동일인이 여러 역할을 맡을 수 있다. 중요한 것은 누가 어떤 판단에 책임지는지 남기는 것이다. 예외에는 대상·사유·보완 통제·승인자·기한·재검토 조건을 적는다. 예외 승인은 시험의 미충족을 충족으로 바꾸지 않는다.

운영 통제는 Gateway의 일반/관리 API, host/container의 송신·권한, 배포의 모델/설정, 엔진·자원의 서비스 상태, 수집기의 장애를 본다. 기록은 판단 근거다. 지표 하나로 모델 실물·요청별 GPU 회수·모든 통신 보호를 입증하지 않는다. 정책 적용 실패와 중앙 연결 단절 시 실제 정책 상태도 별도로 확인한다.

## 위협 유형과 외부 분류를 쓰는 방법

기존 사례 분류는 A 접근·대리 권한, B 공급물·코드 신뢰, C 공유·귀속, D 입력 조건, E 자원, F 종결·전환, G 정보 노출, H 메모리 안전, U 상세 보류다. 다섯 보호 영역은 적용 대상을, 이 유형은 보호 요구가 깨지는 방식을 나타낸다. 유형과 영역은 일대일이 아니다.

기존 GHSA/CVE·패치와 유형은 체크리스트의 사례 근거에 보존했다. 동일 사례를 여러 Q에서 참조해도 독립 취약점으로 중복 집계하지 않는다. ATT&CK·ATLAS는 공격자의 구체적인 활동과 조건을 정한 뒤 참조로 매핑한다. 이번에 기법 번호를 확인하지 않은 후보에 임의 번호를 붙이지 않는다. 외부 기법 매핑이 없다는 이유로 내부 상태 혼입·종결·자원 위협을 제외하지 않는다.

**평가 질문·시험 초점**

[Q-C02](03_체크리스트와_보완가이드.md#Q-C02)
**시험:** 두 주체의 같은 ID·동시/늦은 결과와 내부 ID·child·반환 대조 동일 외부 ID 동시 요청, randomization on/off, 등록된 abort 경로의 타 사용자/빈 ID 요청을 확인한다. 외부 ID 하나에 여러 내부 실행이 연결된 경우, 외부 ID로 하는 abort는 연결된 실행들을 대상으로 삼을 수 있다. 내부 ID는 해당 실행 또는 parent에 속한 child를 찾는다. ID 구분은 소유자 인가를 대신하지 않으며 공개 Chat 취소 API를 가정하지 않는다. `generate`가 collector를 아직 받지 못했어도 로컬 등록 상태가 없다고 단정하지 않는다. 단일 등록은 로컬 등록 뒤 Core 전송을 기다리고, 병렬 child 등록에는 실패 시 parent 내부 ID로 abort하는 처리가 있다. 각각 등록 전·전송 도중·등록 완료의 실패/취소를 시험한다.

B만 새 엔진/새 상태에서 수행한 정상 대조와 토큰 제약 적용·request→slot→idx mapping·count/flag 갱신을 비교한다. allowed_token_ids 지원 endpoint/내부 sampling 전달 경로가 확인되지 않으면 그 분기는 미확인으로 둔다. 다중 요청 순서 변경·종료·선점 후 재추가를 추가 분기로 수행한다. 완료/취소 도달과 slot 재사용 증거를 남기며 HTTP 완료만으로 slot 해제를 추정하지 않는다.

[Q-C08](03_체크리스트와_보완가이드.md#Q-C08)
**시험:** 상태별 취소·abort·scheduler·native참조·후속 정상요청 시각 연결 `CancelledError`/`GeneratorExit`는 collector가 있을 때 그 내부 ID로 abort한다. `EngineDeadError`는 개별 abort 없이 오류를 전달하고 실행 그룹의 실패·종료를 확인한다. `VLLMClientError`/`GracefulHTTPError`도 이 분기에서 abort하지 않는다. `InputStreamError`와 기타 예외는 collector가 있으면 내부 ID abort 후 오류를 전달한다. 등록·전처리 단계에서 생긴 상태의 정리는 별도 경로로 확인한다. scheduler는 종료 요청 ID를 `finished_req_ids`에 넣고 후속 `SchedulerOutput`으로 전달한다. V1은 `GPUModelRunner._update_states()`에서 요청 상태·InputBatch 항목을 제거한다. V2는 `finish_requests()`→`_remove_request()`에서 request slot과 관련 상태를 정리한다. 실제 runner를 확인해 해당 분기를 적용하며, 후속 실행 정보가 전달되었다는 증거 없이 scheduler 종료만으로 worker 정리 완료를 판정하지 않는다. GPU 즉시 중단·메모리 물리 소거를 뜻하지 않는다. stop 문자열 종료도 별도 시험한다: 문자열 복원·stop 감지→응답 종료 판단→Core 미종결 시 abort ID 전달→scheduler/선정 worker 정리의 시각을 연결한다. 정상 길이 종료와 비교하고 응답 종료만으로 계산·참조 회수 완료를 판정하지 않는다.

**R·POL 검토 범위:** 각 묶음의 관련 R·POL은 위협 후보의 출발점이다. 각 시나리오에는 해당되는 권한·접점·위반 결과만 적용한다. 같은 묶음에 있다는 이유로 모든 R×POL 조합에 위협이 있다고 기록하지 않는다. R01~R09·R11~R13을 다루며, 관리형 서비스에 의존하는 POL-10은 R14와 함께 대기한다. 평가 도구 자체의 보호 요구인 POL-12는 평가·증거 관리 규칙으로 확인하며 서빙엔진 공격 시나리오 수에 넣지 않았다.

**남은 검토:** 조건부 backend·플러그인·공유 가중치·snapshot의 실제 도달 경로, 기업별 역할·공유·보존 정책, 버전별 패치 효과는 해당 시나리오와 Q의 미확인 상태를 유지한다. 사례 원장의 영향 판본만으로 현재 설치판의 취약 여부를 결정하지 않는다.


### 공격표면 대응표의 검토 범위

시나리오 범위 연결 26개, 부분 검토 7개, backend 미선정 1개, 대기 3개다. 26개는 연결된 시나리오 범위만 뜻하며 공격표면 전체 검토나 통제 검증 완료가 아니다. 033의 미디어 취득 검토를 020의 영속 job·client shared memory로 확대하지 않는다.
