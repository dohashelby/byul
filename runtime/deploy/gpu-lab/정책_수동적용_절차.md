# 플랫폼 승인 정책의 Gateway 수동 적용 절차 (첫 버전)

이 문서는 플랫폼의 `byul-policy/0.1` **CONFIRMED 판본**을 사람이 Gateway용 파일로 바꾸고 AWS GPU lab의 묶음 디렉터리에 놓는 절차다. 권장 적용 기준은 **“승인 목록의 해시와 일치하는 정책만 적용”**이다. 플랫폼의 승인 기록과 `bundle.json.approval`은 자기 신고이며, 이 절차가 승인 행위 자체를 검증하지는 않는다. 근거: `contracts/README.md`, `policy_bundle.py`, `approval.py`.

**실행 범위:** AWS 실제 환경에서 아직 수행 안 함, 로컬에서 로더 검증까지만 함. 아래 서버 복사·재시작·요청 확인은 AWS에서 미확인이다. 저장소의 `deploy/gpu-lab/*.aws-lab.json`은 LAB 시험값이며 플랫폼의 정식 승인 판본이 아니다. 근거: `README.md`.

## 첫 버전을 수동으로 하는 이유

| 확인한 상태 | 근거 |
| --- | --- |
| 계약에는 `byul-policy/0.1` → Gateway 내부 정책 변환이 예정되어 있으나, 플랫폼 API에는 해당 변환·묶음 생성 기능이 없다. 저장소에도 묶음 생성 도구가 없다. `bundle verify`는 생성이 아니라 검증이다. | `contracts/README.md`, `policy.schema.json`, `platform 문서 경로`, `cli.py` |
| 원격 전달 경로와 관리 디렉터리 작성 주체가 미결이다. 플랫폼에서 Gateway로 묶음을 전달하는 인증 절차도 정의되어 있지 않다. | `결정기록_정책묶음_수신.md`, `gateway.yaml` |
| Gateway는 시작 시 묶음을 한 번 읽어 스냅샷으로 고정한다. 재로드가 없어 새 묶음 적용에는 재시작이 필요하다. | `policy_bundle.py`, `cli.py`, `결정기록_정책묶음_수신.md` |
| 서명, 원격 전달 실패 처리, 자동 되돌리기가 없다. 현재 승인 대조는 정책 파일 바이트의 SHA-256과 승인 목록 항목 비교이며 서명이 아니다. | `approval.py`, `policy_state.py`, `contracts/README.md` |
| AWS 서버의 Gateway는 호스트 디렉터리만 읽는다. 플랫폼이 그 서버에서 닿는 위치에 있다는 보장은 없다. 자동 수신을 붙이려면 서버의 묶음 쓰기 권한과 전달 인증을 새로 정해야 하므로 권한 범위도 아직 확정할 수 없다. 뒤 문장은 현재 배치와 미결 사항에서 나온 판단이다. | `gateway.yaml`, `결정기록_정책묶음_수신.md` |

수동이어도 **변환 → 전달 → 적용** 단계는 자동 방식과 같다. 현재는 각 단계를 사람이 수행한다. 변환 규칙·전달 경로와 인증·재시작/실패 처리·서명 및 되돌리기 조건이 갖춰진 뒤 자동화를 다시 판단한다. 이 문서는 자동 적용 기능을 설명하지 않는다.

## 적용 순서

적용 시간을 미리 잡는다. `gateway.yaml`의 `strategy: Recreate`는 새 Pod보다 기존 Pod를 먼저 내리므로 **정상 적용에도 재시작 동안 요청이 끊긴다**. 새 묶음이 서버에서 잘못되면 새 Gateway가 뜨지 않아 **되돌릴 때까지 요청을 처리할 수 없다**. 그래서 5번의 로컬 검증과 6번의 서버 재검증은 링크 교체·재시작 전에 반드시 끝내야 한다. 이전 묶음과 되돌리기 명령도 미리 준비한다.

1. **승인 판본 확보**
   - 할 일: 플랫폼의 `byul-policy/0.1` `CONFIRMED` JSON 판본, `policy_id`, `policy_version`, `target_ref`, `validity`, `approval`, 정규 JSON SHA-256을 확보한다. 정규 JSON은 키 정렬·공백 없는 UTF-8이다. `policy_ref.sha256`은 이 원본의 정규 해시이고 승인 목록 및 `files[].sha256`은 각 Gateway 파일의 바이트 해시다.
   - 명령: 플랫폼의 승인 판본 조회 절차로 정확한 JSON과 정규 해시를 내보내고, 표시된 `status`·판본 번호를 대조한다.
   - 확인할 것: 원본 파일과 정규 해시가 같은 판본을 가리킨다.
   - 멈출 조건: 승인 판본을 식별할 수 없거나 원본 정규 해시가 없다.
2. **Gateway 정책 파일 준비**
   - 할 일: 별도 작업 폴더에서 `runtime-mvp/1.1` 또는 지원되는 `1.2` JSON을 사람이 작성한다. 플랫폼의 ID·판본·`target_ref`·기간·`approval_ref`를 Gateway의 `policy_id`·`policy_version`·`target_id`·`valid_from`/`valid_until`·`approval_ref`에 맞추고 `runtime.gateway`를 내부 형식으로 옮긴다. `target`에는 실제 엔진 image digest 등 서버 값을 넣는다. `enforcement_intent`가 있으면 본문의 `schema`를 묶음 항목의 `schema_version`으로 쓴다.
   - 명령: 작업 폴더에 역할별 JSON 파일을 작성하고 `sha256sum <Gateway 정책 파일>`로 파일 해시를 확인한다.
   - 확인할 것: 역할별 문법·값과 `policy_id`·`policy_version`·`approval_ref`가 원본 승인 판본에 맞는다.
   - 멈출 조건: 서버별 대상 값이나 변환 규칙을 확인하지 못했다.
3. **승인 목록 작성**
   - 할 일: 최종 Gateway 정책 파일의 바이트 해시를 `runtime-policy-approvals/1.0` `entries[]`에 ID·판본·`approval_ref`·`approved_at`과 필요 시 `valid_until`과 함께 적는다. `policy_approvals` 역할은 필수다. 파일 수정 후에는 해시와 `policy_version`을 다시 정한다. 목록을 새로 썼다는 사실은 플랫폼 승인이 아니다.
   - 명령: `sha256sum <Gateway 정책 파일>`.
   - 확인할 것: 목록의 해시·ID·판본·승인 참조가 최종 파일과 원본 승인 판본에 맞는다.
   - 멈출 조건: 승인 근거나 최종 파일 해시가 맞지 않는다.
4. **묶음 작성**
   - 할 일: 겹치지 않는 새 `<bundle_id>` 폴더에 역할 파일을 복사하고 `bundle.json`을 사람이 작성한다. 묶음 생성 도구는 없다. 각 파일의 `sha256sum`·`wc -c` 결과를 `files[].sha256`·`files[].bytes`에 넣는다. 경로는 묶음 내부 상대 경로이고 `gateway_policy`는 필수다. `created_at`·`approval.approved_at`은 시간대 포함, `validity.valid_from`/`valid_until`은 시간대 포함 시각 또는 `null`이다. 아래 LAB 예시는 형식만 참고한다.
   - 명령: `sha256sum <역할 파일>` 및 `wc -c <역할 파일>`.
   - 확인할 것: 파일 목록·크기·해시·시간 형식·상대 경로가 최종 묶음과 맞는다.
   - 멈출 조건: ID 중복, 파일 누락, 해시·크기 불일치 또는 시간대 누락.
5. **로컬 적용 전 검증**
   - 할 일: 완성된 묶음을 검증하고 사람이 원본 플랫폼 정책과 별도로 대조한다. 로더는 `policy_ref` ID·판본과 Gateway 파일의 ID·판본 일치를 검사한다. 원본 플랫폼 정책은 입력받지 않으므로 `policy_ref.sha256` 출처와 플랫폼 승인 자체는 사람이 대조한다. Gateway 정책·target/intent의 모든 의미와 실제 Kubernetes 대상도 별도 확인한다.
   - 명령: `cd runtime && .venv/bin/python -B -m serving_runtime bundle verify --bundle-dir <묶음 폴더>`.
   - 확인할 것: 원본 정책 ↔ `policy_ref`의 ID·판본·정규 해시, Gateway 정책의 ID·판본·대상, 승인 목록의 ID·판본·`approval_ref`·Gateway 파일 해시, 서버별 `REPLACE…` 값과 파일 권한이 모두 맞는다.
   - 멈출 조건: 명령 실패 또는 대조 항목 하나라도 불일치. 기존 서버 `current`는 그대로 둔다.
6. **서버 복사와 재검증**
   - 할 일: 검증된 묶음을 서버 임시 위치로 전달하고 `/srv/serving/bundles/<bundle_id>/`에 완성된 새 폴더로 배치한다. 전송 중인 폴더를 `current`가 가리키게 하지 않는다. 서버 CLI 설치·복사 경로·권한은 실제 환경에서 확인한다.
   - 명령: 승인된 전달 수단으로 복사한 뒤 서버에서 `serving-runtime bundle verify --bundle-dir /srv/serving/bundles/<bundle_id>`와 `sha256sum <역할 파일>`을 실행한다.
   - 확인할 것: 로컬과 서버의 파일 바이트 해시가 같고, Gateway UID 10000이 폴더·파일을 읽는다(예: 그룹 10000, 폴더 0750, 파일 0640).
   - 멈출 조건: 서버 검증 실패, 해시·권한 불일치 또는 배치 미완료. 링크는 교체하지 않는다.
7. **`current` 상대 링크 교체**
   - 할 일: 기존 링크 대상과 새 묶음 ID를 기록하고 기존 묶음은 되돌리기용으로 보존한다. 호스트 `/srv/serving/bundles`는 컨테이너 `/etc/serving/bundles`이므로 절대 링크를 쓰지 않는다. 링크 교체만으로 실행 중 Gateway 정책은 바뀌지 않는다.
   - 명령: `/srv/serving/bundles`에서 새 ID를 `BUNDLE_ID`에 넣고 `ln -s "$BUNDLE_ID" current.next` 다음 `mv -Tf current.next current`.
   - 확인할 것: `current`가 완성된 새 폴더를 가리키고 이전 ID가 기록됐다.
   - 멈출 조건: `current.next`가 이미 있으면 원인을 확인하고 치우기 전까지 멈춘다. 링크 대상이 예상과 달라도 멈춘다.
8. **Gateway 재시작**
   - 할 일: 작업 시간에 새 묶음을 읽도록 재시작한다. `Recreate`로 기존 Pod가 먼저 내려가 요청이 끊긴다. 새 묶음이 잘못되면 되돌리기 전까지 서비스가 멈춘다.
   - 명령: `kubectl --context byul-aws-lab -n serving-lab rollout restart deployment/serving-gateway` 다음 `kubectl --context byul-aws-lab -n serving-lab rollout status deployment/serving-gateway`.
   - 확인할 것: 새 Pod 준비와 시작 옵션 `--policy-bundle /etc/serving/bundles/current`. 준비 완료 뒤에도 시작 전에 쓰인 대상 Pod 스냅샷은 인정하지 않으므로 최대 약 10초(수집기 쓰기 5초 + Gateway 읽기 5초, 조회 시간 추가 가능) 동안 `TARGET_UNAVAILABLE` 503일 수 있다. 이 구간이 지난 뒤 정상 요청을 확인한다. 명령 형식은 로컬 `kubectl rollout ... --help`로 확인했으나 AWS 실행은 아직 없다.
   - 멈출 조건: rollout 실패 또는 새 Pod가 준비되지 않으면 아래 되돌리기로 간다.
9. **적용 결과 확인**
   - 할 일: 플랫폼 대시보드 또는 Gateway에서 묶음·정책·승인 상태를 조회하고 정상 요청 1건과 정책상 거부 요청 1건의 Gateway 결정·엔진 전달 여부를 기록한다. 요청 본문·토큰은 기록하지 않는다. 묶음 SHA-256은 `bundle.json` 바이트, `current.sha256`은 Gateway 정책 파일 바이트다. AWS 결과는 아직 미확인이다.
   - 명령: Gateway `GET /api/policy`, `GET /api/status`와 승인된 정상·거부 시험 요청을 실행한다.
   - 확인할 것: `policy_bundle.bundle_id`·`sha256`, `current.policy_id`·`policy_version`·`sha256`, `gateway_active`, `approval.state`가 승인 판본·목록과 맞는다. 목록을 정상 읽어 `verified`가 되어야 성공이다(`last_verified`는 조건부 상태일 뿐 이 절차의 성공 아님).
   - 멈출 조건: 불일치·`verified` 미달·위 스냅샷 대기 구간이 지난 뒤에도 계속되는 정상 요청 실패(`TARGET_UNAVAILABLE` 503 포함)·거부 요청의 예상 외 전달이면 아래 되돌리기로 간다.
10. **결과 기록**
   - 할 일: 적용 시각, 플랫폼 승인 판본·정규 해시, Gateway 정책 ID·판본·파일 해시, `bundle_id`·`bundle.json` 해시, 이전/새 `current`, 검증·재시작·정상/거부 요청 결과와 담당 역할만 남긴다. 사람 실명·토큰·키·서버 IP·요청 본문은 남기지 않는다.
   - 명령: 승인된 변경 기록에 위 필드와 검증 결과를 기록한다.
   - 확인할 것: 성공/실패와 되돌리기 결과가 실제 관측과 맞는다.
   - 멈출 조건: 검증·요청 결과가 없으면 적용 성공으로 닫지 않는다.

### `bundle.json` 로컬 LAB 형식 예시

아래 값은 당시 `deploy/gpu-lab/*.aws-lab.json` 원본으로 만든 **로더 시험용** 묶음이 실제 통과한 예시다. 11/3 intent 허용 목록 변경 뒤 `enforcement_intent` 해시·크기는 더 이상 현재 파일과 일치하지 않으므로 새 묶음의 값으로 다시 계산한다. 플랫폼 승인 판본과 연결된 운영 값이 아니다. 특히 예시의 `policy_ref.sha256`은 LAB 테스트 편의상 Gateway 파일 해시를 넣은 값이며, 실제 적용에는 **승인된 원본 `byul-policy/0.1`의 정규 해시로 교체**해야 한다. `approval`도 승인 증거가 아니다. 파일을 수정했다면 모든 해시와 바이트 수를 다시 계산한다.

``json
{
  "schema_version": "byul-policy-bundle/0.1",
  "bundle_id": "manual-policy-bundle-check",
  "created_at": "2026-11-02T00:00:00+09:00",
  "policy_ref": {
    "policy_id": "aws-lab-policy-001",
    "policy_version": "1",
    "sha256": "c61b058f17c606edc4376219796d0b6f16856b28f54151da804f37287ccac25f"
  },
  "target_ref": "serving-engine-aws-lab",
  "approval": {
    "approved_by": "runtime-lab",
    "approved_at": "2026-11-02T00:00:00+09:00",
    "approval_ref": "LAB-RUNTIME-SELF-001"
  },
  "validity": {"valid_from": null, "valid_until": null},
  "files": [
    {"role": "gateway_policy", "path": "policy.aws-lab.json", "schema_version": "runtime-mvp/1.1", "sha256": "c61b058f17c606edc4376219796d0b6f16856b28f54151da804f37287ccac25f", "bytes": 439},
    {"role": "policy_approvals", "path": "policy-approvals.aws-lab.json", "schema_version": "runtime-policy-approvals/1.0", "sha256": "fa6fdde1282148dc00e537d4e47b3c7e1dd1d0afc294ab247cea1f82542e6a9f", "bytes": 386},
    {"role": "enforcement_intent", "path": "intent.aws-lab.json", "schema_version": "runtime-enforcement-intent/1.1", "sha256": "961014a6368eb1acd92f27351878eb82f106c54e7d7285db97640d0d27228765", "bytes": 1730},
    {"role": "target", "path": "target.aws-lab.json", "schema_version": "runtime-target/1.0", "sha256": "0e3ac03d57f4c415c2acfadce345af86c6cb5fd915fd9ff40d82dcc0ddb4c720", "bytes": 412}
  ]
}
``

로컬에서 확인한 명령 형식(작업 위치: `runtime/`):

``bash
sha256sum deploy/gpu-lab/policy.aws-lab.json
wc -c deploy/gpu-lab/policy.aws-lab.json
.venv/bin/python -B -m serving_runtime bundle verify --bundle-dir /path/to/completed-bundle
``

마지막 경로는 운영자가 완성한 묶음 폴더로 바꾼다. 로컬 재현에서는 정상 파일 4개가 통과했고, `policy.aws-lab.json`에서 길이가 같은 글자 1개를 바꾸자 `SHA-256이 bundle.json과 다릅니다`로 거부됐다. 로더는 바이트 수를 먼저 검사하므로 길이가 바뀐 수정은 `bytes가 다릅니다`로 거부된다. 근거: `policy_bundle.py`.

## 실패와 되돌리기

- **적용 전 검증 실패:** `current`를 교체하지 않고 기존 묶음과 Gateway를 유지한다. `bundle verify`는 구조·경로·파일 크기·SHA-256·내부 schema·기간·정책 `target_id`를 검사한다. 실패한 묶음은 배치하지 않는다. 근거: `policy_bundle.py`.
- **묶음 파일 해시 불일치:** Gateway 시작 경로의 `verify_policy_bundle`이 오류를 내고 `mvp` CLI는 종료 코드 1로 끝난다. 새 Pod가 준비되지 않을 수 있다. 로컬 CLI에서 한 글자 변경의 종료 코드 1을 확인했다. 링크나 원본 파일 변경만으로 실행 중 Gateway의 정책은 바뀌지 않는다. 재시작하면 `Recreate`로 기존 Pod가 먼저 내려가며, 새 묶음이 잘못됐으면 되돌릴 때까지 요청을 처리할 수 없다. 승인 목록 해시와 Gateway 정책이 불일치할 때는 묶음 로더가 아니라 승인 대조가 `rejected`가 되고 새 요청은 정책 상태 503으로 막힌다. 근거: `cli.py`, `approval.py`, `policy_state.py`, `결정기록_정책묶음_수신.md`.
- **교체 뒤 실패:** 기록해 둔 이전 묶음 ID가 남아 있고 그 묶음이 현재도 유효한지 먼저 확인한다. `/srv/serving/bundles`에서 이전 ID를 `PREVIOUS_BUNDLE_ID`에 넣고 `ln -s "$PREVIOUS_BUNDLE_ID" current.rollback` 다음 `mv -Tf current.rollback current`로 상대 링크를 되돌린다. `current.rollback`이 이미 있으면 그 원인을 확인하고 치운 뒤 실행한다. 이어서 Gateway를 다시 시작한다. `/api/policy`·`/api/status`와 정상/거부 요청을 다시 대조하고 결과를 남긴다. 이전 정책도 만료·철회·승인 목록 불일치 상태라면 복구 성공으로 기록하지 않는다. 자동 되돌리기는 없다. 근거: `gateway.yaml`, `policy_bundle.py`, `policy_state.py`.

## 이 절차가 보장하지 않는 것

- SHA-256 목록 대조는 **변조 방지 서명**이 아니다. 목록과 파일을 함께 바꿀 수 있는 주체를 암호학적으로 구별하지 못한다. 플랫폼의 승인 행위 자체도 검증하지 않는다. 근거: `contracts/README.md`, `approval.py`.
- Gateway 묶음의 `enforcement_intent` 역할은 관측/후보 입력이다. Cilium·Tetragon 규칙 집행은 별도 `serving-runtime enforce render --intent ... --out ...` 뒤 사람이 후보를 검토하고 `kubectl apply`해야 한다. 묶음 검증이나 Gateway 정책 활성 상태만으로 외부 집행을 단정하지 않는다. 근거: `README.md`, `policy_bundle.py`, `policy_state.py`.

가짜 보호 파일 경로를 intent에 추가한 뒤에는 정책 묶음을 재작성하고 `enforce render`의 TG-SECRET-01 후보를 검토·재적용한다. ConfigMap·엔진 patch 적용 후 엔진 재시작까지 확인해야 AWS-10을 실행할 수 있다. 기존 규칙의 적용 상태를 새 묶음만으로 추정하지 않는다.
