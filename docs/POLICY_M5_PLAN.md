# M5 구현 범위와 OBS-11 후속 계획

## 기준과 결과의 의미

시작점은 M4 `codex/gua-policy-evidence-m4`의 `2632c245bafd3628965e22c4d6dc86f0d1d3c046`이며,
M5는 `codex/gua-policy-m5`에서 작업한다. PR #6이 미병합이므로 초안 PR의 base는 M4다.
M1~M4 문서는 당시 계약·검증 기록이며 현재 동작은 이 문서와 [SPEC](../SPEC.md)을 따른다.
실제 기업 정책값·계정·권한·승인·SLA는 결정하지 않는다.

## LIF-07 수정

**확인한 원인:** [policy_items](../src/guard/judges/policy_items.py)가 같은 trial/대상/case의
request_outcome·inference_outcome·order_basis 충돌을 모두 같은 보류 조건으로 처리했다.
그 결과 두 필수 항목에서 준비 전 수락과 순서가 확인돼도 추론 실패/성공의 차이가 있으면
보안 FAIL보다 먼저 반환해 UNKNOWN으로 가렸다.

**채택한 최소 변경:** 준비 전 수락의 보안 위반은 항목 상태·수락·순서 근거·현재 첨부 연결로 판단한다.
같은 사건의 수락/차단 모순은 이 위반을 확정할 수 없게 한다. 추론 결과의 모순이나
서로 다른 유효 순서 확인 방법은 독립적으로 확인된 보안 FAIL을 지우지 않는다.
모순은 계속 이유와 누락 정보에 기록하고 PASS는 보류한다. 서로 다른 필수 항목의
ready/not_ready 차이 자체는 사건 모순이 아니다. 순서 미확인·첨부 미연결은 FAIL을 새로 만들지 않는다.
독립 사건의 확인된 FAIL·신고 FAIL·UNKNOWN 비승격·성능 UNKNOWN을 보존한다.
SUP-14의 전이 충돌 처리와 LIF-07의 정상 묶음 기능 실패 조건은 바꾸지 않는다.

## OBS-11: 후속 구현 전 결정표

M5에서는 OBS-11 정책 선언·관측·판정을 추가하지 않는다. `P-DRAFT-AUDIT-REQUIRED-RECORDS`
목록만 등록해서 발생 확인·기한 내 수집·누락 구별까지 지원한다고 주장할 수 없다.

| 쟁점 | 팀이 결정할 내용 | 바로 준비 가능한 기술 산출물 |
|---|---|---|
| OBS-01 관계 | 같은 사건/레코드 요구, 일부 공유, 별도 요구 중 무엇인가 | 두 CheckDef 원문·원문 ID·필수 관측/실패 조건 대응표 |
| 필수 case | 정상 발생·누락·수집 지연·수집기 장애·경로 미적용 등의 채택 범위/ID | 기업 결정을 비운 case 표·호환성 규칙 |
| 사건 발생 증거 | 로그 수집 경로와 독립인 발생 근거 및 대상 식별자 | 발생 근거·수집 기록을 별도로 연결하는 최소 관측 설계 |
| 기한·시간 불확실성 | 단위·기산점·마감·시계 출처·오차 처리 | 기한 경계 전/동일/후, 시계 미확인·오차 겹침 테스트 설계 |
| 누락과 미확인 | 발생 확정+완전한 관측 창이 확인된 누락 vs 발생/창 미확인 | 확정 누락은 관측 미충족·종속 시험 UNKNOWN, 이를 정상 처리/필요 경보 누락 시 OBS-11 FAIL로 구별한 판정표 초안 |
| 장애·알림·대응 | 수집기 장애와 사건 미발생 구별; 알림·운영 대응의 별도 요구 | 관측 누락·알림·사람 대응 결과를 분리한 증거 예시 |
| 예외·보존 | 예외 승인·보존 범위·추적 조건 | 기존 예외 표시/append-only 계약과 충돌 점검 |

기한·SLA·시계 오차·실제 담당자·권한·승인자는 추정하지 않는다. OBS-01과의 관계 및
발생/시간 증거 계약을 합의한 다음 필요한 정책만 등록한다. 서로 다른 단계의 관측을
필수 문자열 목록으로 숨기거나 범용 규칙 설정으로 억지로 표현하지 않는다.

후속 최소 변경 후보는 OBS-11 override·카탈로그/설명 JSON·전용 수동 관측 보조 함수·순수 판정·
기존 보고 한계 연결이다. 새 모델/저장소/실행기 도입은 증거 계약으로 필요성을 먼저 입증한다.
완료 확인은 발생 확정/미확인, 기한 경계/불확실, 수집기 장애, 누락 정상 처리/경보 누락, 종속 판정 UNKNOWN, 부분 증거, 신고 FAIL 보존,
UNKNOWN 비승격, 과거 팩 재판정, JSON/HTML 이유·출처 연결에 대한 계약 테스트다.
실제 수집 체계나 엔진의 정상/누락 시험은 별도 승인된 격리 환경에서 수행한다.

## M5 검증 방법

모든 구현·테스트 작성을 끝낸 뒤 기본 pytest, frozen lock, wheel 빌드, 저장소 밖 설치본의
정책 양식→선정→수동 입력→판정→JSON/HTML 경로를 검사한다. 실제 M4 wheel과 보존된
revision 11 팩으로 만든 객체를 M5에서 재판정해 과거 객체 보존과 수정된 FAIL을 확인한다.
신규 팩 재생성의 멱등성, 다른 75점검·원문·증거 바이트 보존, 카탈로그 계수·메타데이터·
manifest 무결성도 확인한다. 실행 결과와 환경 제약은 [PROGRESS](../PROGRESS.md)에 기록한다.
모든 입력/첨부 예시는 EXAMPLE이며 실제 승인 체계·엔진·두 이미지 실증은 수행하지 않는다.

## M6 후속 설계 (구현 전 제안)

OBS-01/OBS-11 의미 대응, 12개 정책 후보 분해, 사건별 수치 표의 타입 한계, 독립 발생/조회 창·시계 구간·누락/경보/종속 처리 계약, 열린 결정과 다음 구현 프롬프트는 [M6 설계](POLICY_M6_PLAN.md)에 정리했다. 새 정책·양식/판정·기업 수치의 구현/승인은 아니며 M5의 팩12·현재 계약은 유지한다.
