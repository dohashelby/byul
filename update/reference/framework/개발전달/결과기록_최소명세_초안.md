# 결과 기록 최소 명세와 구현 제안

**공통 기록 의미 확정: 2026-10-27 · 제품 저장/API/스키마 제안: 미구현.** I-001·S03·S04를 개발팀에 인계한다. 03·05의 기존 적용·판정·증거 보존 원칙을 아래 공통 기준으로 확정하고, 그 정보를 담을 추가 필드·열거값·객체 확장은 개발팀이 선택한다. 기존 파일명 `_초안`은 저장 구조와 채움 형식의 제안 상태 및 기존 링크를 유지한다. 이번에 채택해 구현한 Q 보조기의 입력 snapshot 계약은 별도 명세를 따른다. 이 문서의 예시는 EXAMPLE이며 실제 엔진 실행 결과가 아니다.

## 기존 구조와 변경 경계

BYUL의 ENV·POL·CHG·PLAN·EVD·RES·RPT, 팩 보존본과 CAS를 그대로 사용한다. 별도 결과 DB나 병렬 저장 형식을 먼저 만들지 않는다. 아래 정보의 보존 여부를 검토하고 기존 객체의 판본 있는 확장 등으로 구현 방식을 정한다. 새로운 객체·범위 ID나 고정 단위 수를 공통 규칙으로 요구하지 않는다. 예시 JSON은 그 확장에 필요한 정보를 보여 주는 설계 자료이며 현행 guard importer의 입력 형식으로 채택된 것은 아니다.

현행 EVD는 한 CHK·side의 증거를 담는다. 여러 세부 결과를 독립 EVD revision으로 덮어쓰는 방식은 마지막 revision만 소비하는 현재 경로에서 정보가 사라질 수 있다. 후속 확장은 한 EVD 안의 범위별 관측/사례와 그 RES의 범위별 판정을 유지하는 방향으로 정한다. 큰 증거는 기존 artifacts/CAS를 참조한다.

## 판본과 정확한 참조

- 내용 근거는 저장소·정확 commit 또는 미게시 로컬 commit, checklist 파일 bytes SHA256, CHK ID로 식별한다. 형식 schema_version은 파서 구조, date/record_date는 원 작성/기록일, 개별 revision은 해당 객체 내용 판본이다. 서로 대신하지 않는다.
- commit·파일 bytes hash·JSON canonical hash는 이름과 범위를 명시한다. 과거 날짜/해시를 최신값으로 일괄 바꾸지 않는다. 내용 판본을 알 수 없으면 null과 미확인 사유를 남긴다.
- 기존 내부 check_id와 framework CHK ID는 id_map의 고정 대응을 사용한다. 이름·정렬·문장 수정으로 재번호하지 않는다.
- 기존 full branch ref는 `{assessment_id, checklist_ref, name, scenario_ids, apply_when}`다. checklist_ref에는 내용 판본과 SHA를 포함한다. `apply_when` 원문은 공백·구두점을 포함해 보존한다. 배열 index는 해당 판본 안의 조회 보조이고 영구 ID를 대신하지 않는다.
- 분기 이름과 SC만으로 병합하지 않는다. 같은 이름/SC를 쓰는 SUP-008·REQ-018·REQ-020·PLT-008의 서로 다른 apply_when을 별개 참조로 저장한다. 새 내부 범위 ID는 선택 설계이며 기존 full ref와 명시적 대응 없이 대체하지 않는다.
- 문구 수정은 구/신 full ref의 관계를 기록한다. 원문이 바뀌었는데 새 ref의 apply_when만 옛 결과에 삽입하지 않는다.

## 공통 확인과 분기와 필수 결과

공통 확인은 CHK가 기본적으로 요구하는 보호·정상 대조다. 116개 분기는 조건별 시험 초점이며 모든 실행 목록을 열거한 것이 아니다. 필수 세부 결과9개는 각각 판정할 보호 범위다. 하나의 실행이 여러 분기·세부 결과에 증거를 제공할 수 있고, 하나의 세부 결과가 여러 실행·문서 검토를 필요로 할 수 있다. 이 관계는 일대일이 아니다.

선정 snapshot에는 기대하는 공통 확인·분기·필수 결과, 각각의 적용 근거와 지원·선정 상태를 남긴다. 실행을 위해 자연어 apply_when을 임의 조건식으로 바꾸지 않는다. 검토된 fact/정책 매핑 또는 사람의 적용 검토를 별도로 기록한다. API 보호처럼 기존 SC 분기만으로 충분히 표현되지 않는 기본 결과를 누락하지 않는다.

|REQ-005|모델별 사용 권한 / 사용 종료 모델의 실행 중단|모델 선택 기본 / 사용 종료·alias 변경 시|

## 적용부터 판정까지의 필드 의미

선정 목록 완결성은 **특정 팩/정책/환경/시점의 기대 범위를 빠짐없이 적용 판단했는지**다. 현재 `inventory_complete`의 의미와 REVIEWED 팩 조건을 유지한다. 새 수행 범위 완결성은 **선정된 적용 범위의 필수 절차·정상 대조·관측·필수 결과가 충분한지**다. `coverage_complete`는 제안 필드이며 inventory_complete를 덮어쓰지 않는다. 기존 case 안의 subtest_inventory_complete는 구판 입력값으로 보존하고 새 PLAN snapshot과 상충하면 충돌로 표시한다. case boolean 하나를 전체 목록 권위로 삼지 않는다.

CHK 집계는 적용 범위의 FAIL 우선, 필요한 공통/필수 결과가 UNKNOWN이면 전체 UNKNOWN, 모든 적용 필수 범위가 PASS이고 해당 완결성 관문을 만족할 때 PASS다. CHK 전체의 비적용은 대상에 연결된 근거가 필요하다. 조건부 결과의 NOT_APPLICABLE은 근거를 보존하며 나머지 적용 결과를 가리지 않는다. 세 축의 정상 기능·성능 미확인은 보안 근거와 각각 기록한다.

## 보호 요구별 판정과 증거 기여

주 요구는 purpose_ref, 보조 요구는 security_requirement_contributions에 있는 관계만 사용한다. 각 요구 기여는 `{requirement_id, source_unit_refs, evidence_refs, verdict, reasons, missing_evidence}`로 제안한다. CHK 전체 판정을 보조 요구에 그대로 복사하지 않는다. 해당 요구가 필요한 단위와 증거의 범위를 검토해 기여한다.

- OBS-006에서 조회·반출 권한 PASS와 암호화 UNKNOWN을 함께 보존한다. 저장 자료 보호(requirement-5-4)는 UNKNOWN, 작업·대상 인가(requirement-1-2)의 확인한 조회권한 기여는 PASS로 남길 수 있다. 후자는 해당 요구 전체의 다른 CHK까지 통과했다는 뜻이 아니다.
- PLT-008에서 내부 통신 PASS와 API 증거 부족 UNKNOWN을 보존한다. 통신 상대·전송 보호(requirement-5-5)는 UNKNOWN이다. 내부 peer 근거가 인증/인가 요구에 기여할 범위만 별도로 가리키며 API 인증/인가 전체에 확대하지 않는다.
- LIF-013의 release 권한 PASS, 후속 취득의 비승인 공급 FAIL, 참조 수명 UNKNOWN은 각각 보존하고 CHK는 FAIL이다. 실제 사용 무결성 등 해당 보조 요구의 위반도 근거별로 기록한다.

## 채운 자료형과 null과 빈 값

전체 필드 사전은 `결과기록_필드사전_초안.json`에 있다. 현행 result_template의 모든 최상위 필드를 기존 객체와 대응하고 추가 계약을 구분한다.

- `evidence`는 설명 문자열 나열이 아니라 case별 descriptor 배열을 제안한다. 각 항목은 대상/관측, 기존 EVD·artifact 또는 문서 bytes Ref, 출처·수집/검토 시각·자료 등급·필수 여부·채택 근거를 담는다. 본문/Secret을 공통 계약에 추가하지 않는다.
- `/`·`·`로 이어 쓴 required_observations 문구는 설명이다. OR 또는 전역 AND로 자동 파싱하지 않는다. 각 판정에 필요한 실제 증거와 대체 증거 동등성의 승인 근거를 따로 정한다. 근거 부족을 이름이 비슷한 다른 관측으로 채우지 않는다.
- `normal_control_result`는 기존 `{attempted:boolean,succeeded:boolean|null,detail:string}`와 관련 증거 Ref를 사용한다. null은 미제공/미확인, false는 실제 실패, `attempted:false`에서 succeeded=true는 허용하지 않는다.
- `approval`은 기존 RPT의 ACCEPT/REJECT 자기신고 관리 결정과 가능한 근거 Ref로 대응한다. `null`은 결정 미제공, 빈 객체는 채운 승인으로 허용하지 않는다. CHK 판정과 승인/예외·보류를 분리한다. 미정 정책의 보류 사유를 PASS로 바꾸지 않는다.
- `environment_evidence_source`, adapter/procedure/fixture 참조는 이름·판본·내용 hash와 EVD/입력/문서의 명시 Ref로 대응한다. 외부 링크 문자열만으로 자료 진위나 지금 유효성을 확인했다고 하지 않는다.
- 빈 배열은 기록된 항목0개, null은 미제공/미확인이다. 비적용은 별도 applicability/verdict와 근거로 표현한다. `policy_values:{}`는 필요한 정책이 없는 범위에만 완결될 수 있고 필수값 누락을 대체하지 않는다.

## 수동 문서와 설정 검토

수행 방식은 ENGINE_TEST / CONFIG_REVIEW / DOCUMENT_REVIEW를 제안한다. 엔진 수행과 문서 검토의 완료 의미를 구분한다. 수동 자료의 원 출처는 DECLARED 상한이고 합성 예시는 EXAMPLE이다. 기존 `EVD.execution.operator {by,at}`와 manual-entry executor·절차 판본/증거 Ref를 재사용한다.

문서 검토가 완료되면 그 절차의 execution_status=COMPLETED와 실제 검토 시각·검토자·procedure Ref를 남길 수 있다. EVD ID와 operator/procedure 조합이 수행 신원이며 엔진 request ID를 만들어 넣지 않는다. 실제 엔진의 정상 대조/위반 시도가 필수인 CHK에서 문서 검토만 끝났다면 normal_control.attempted=false, 실제 challenge 미시도, 판정 UNKNOWN을 유지한다. 수동 판정기의 기존 허용 관측/상한을 확대하지 않는다. 새 typed 수행 방식 필드는 후속 객체 판본 확장 전까지 제안이다.

## Q와 공유 시험 초점과 SC의 허용 관계

- canonical focus는 `items[].subtests[].id`의 고유 ID이며 primary_question과 scenario_id를 원문에서 확인한다. 동일 focus가 여러 Q 아래에 나타나는 것은 같은 실행의 별도 보호 요구 연결이다.
- `subtest_id`가 있을 때 question_id는 canonical primary Q, shared_question_ids는 같은 focus를 참조하는 다른 Q 목록이다. 임의 Q/SC 문자열을 이어 새 focus를 만들지 않는다. canonical 목록·CHK.subtest_ids·Q membership의 관계를 검증한다.
- case의 scenario_ids는 실제 확인한 focus/CHK의 허용 SC이고, branch_ref.scenario_ids는 원 분기의 전체 정의를 정확히 보존한다. 두 배열을 무조건 동일하게 만들지 않는다. 단일 focus case의 실제 SC는 canonical focus의 SC와 일치한다.
- 공통 확인이나 필수 결과가 기존 focus 하나로 표현되지 않으면 subtest_id/question_id=null, shared_question_ids=[]와 이유를 남긴다. 예를 들어 PLT-008의 API 보호 기본 결과에 내부 IPC SC를 억지로 붙이지 않는다. 연결 가능한 실제 branch/focus만 선택적으로 참조한다.

## 원 실행과 새 재사용 판단

원 EVD/RES Ref, 원 PLAN·환경·정책·팩/프로파일·실행/수집 시각은 바꾸지 않는다. 새 판단은 새 PLAN/대상 환경·정책·범위, 재사용 검토자/시각/유효성 근거, 채택/보류와 이유를 따로 기록한다. 원 자료의 data_origin은 재사용 때문에 승격하지 않는다. 이월은 새 실측으로 세지 않는다.

CHK·관측/절차/판정기·정책·모델/실행 조건·범위가 동등한 부분만 재사용한다. 새 필수 결과가 생기면 그 부분은 UNKNOWN/재시험이다. 원환경/정확Ref가 미해소면 재사용을 보류한다. 허용되는 재사용과 비교 가능성은 다른 판단이며 `FAIL→UNKNOWN`은 FIXED가 아닌 UNKNOWN이라는 기존 compare 규칙을 유지한다.

## 과거 형식의 읽기와 반출과 재판정

`record_kind:framework_assessment_review`는 과거 CPU 실행 자료의 검토 dossier이며 현행 result_template case·guard RPT와 별도로 라우팅한다. 원 JSON bytes/해시·원 case/RES Ref·당시 환경/팩을 보존한다. dossier의 execution_id=null을 새 엔진 실행으로 채우지 않는다. 명시된 실행/관측/주장만 새 구조의 대응 후보로 연결하고 독립 원 객체를 확인하지 못한 상태도 보존한다.

현행 guard importer는 이 dossier를 자동 RPT/EVD로 받아들이는 기능이 없다. 읽기·복원 성공, 새 기준에 따른 재판정, 실제 운영 적용 승인은 각각의 수행·결정 기록으로 남긴다. 원판정의 보안 충족이 새 배포의 승인 권한을 대신하지 않는다. 후속 reader를 구현하기 전에는 검토용 자료로 읽고 변환 완료로 표시하지 않는다. 과거 팩의 실측은 그 원팩의 실행 근거로 보존하고, 현재 팩의 실행 여부는 별도 기록한다.

구판 읽기·복원은 원문 우선으로 유지한다. 새 필드를 기본값으로 채워 과거 객체를 다시 봉인하지 않는다. 새 범위 해석은 새 PLAN/EVD 참조/RES/RPT 이력으로 남긴다. 현재 pack snapshot은 정의를 보존하므로 당시 재판정 재현에는 당시 judge/parser/canonicalizer 코드·wheel/lock·Python 또는 검증된 구판 호환 회귀가 더 필요하다. 확보하지 못하면 원판정 읽기·복원과 현행 새 평가를 구분한다.

반출은 기존 bundle의 DB·CAS·팩/범위 정의·참조 폐쇄를 검증한다. 새 품질/재사용 판단 artifact도 참조에 포함한다. 단위 결과·full branch 원문·관측·관리 결정을 저장/내보내기/복원해 동일한 의미를 유지해야 한다. 예시 validator의 JSON roundtrip은 이 설계 관계의 검사이며 제품 store 전체 구현 완료를 뜻하지 않는다.

## 구조 필드와 합성 표시문

편집 원천은 base_method_and_evidence의 일반 방법/엔진별 고유 메모와 normal_control·challenge_steps·required_observations·fail_criteria·unknown_criteria·remaining_setup 등 구조 필드로 정한다. method_and_evidence는 그 순서/강조/줄바꿈을 적용한 표시문으로 생성 또는 동등성을 검사한다. 앞부분32개 문장 차이를 모두 오류로 단정하지 않는다. HTML escape·고유 F 조건·인용·엔진 활성 조건을 보존한다.

현재 표현에서 분리할 수 없는 고유 설명은 원문 메모와 근거에 남기고 사람이 검토한 대응을 기록한다. 한쪽만 변경한 반례를 검출하는 도구를 후속 생성기의 인수 기준으로 삼는다. 이 명세는 자동 prose parser를 새로 만드는 요구가 아니다.

## 합성 예시와 후속 구현의 인수 조건

`examples/결과기록_합성예시_초안.json`은 네 CHK의9필수 결과, 수동 검토, 원 실행/새 판단, 같은 이름의 full branch 참조와 과거 dossier 대응을 채운 EXAMPLE 자료다. 실제 지원 판본의 사용법으로 게시하기 전에 기존 객체 확장/reader/validator/생성팩·정책/계약/API/OpenAPI·TS/화면 변경을 함께 검토한다.

인수 조건은 전체 PASS 관문·독립 FAIL·요구별 기여, 잘못된 Q/SC/Ref/모호한 분기·만료/상충 inventory, 구판 dossier 라우팅·원본 해시, 재사용 원환경 보존·비교·반출복원이다. 명세·합성 사례 검증은 자료 관계와 반례를 확인한다. 개발팀 구현의 입력·출력·기존 모듈 대응·완료 조건은 [개발팀 인계 명세](개발팀_인계명세.md)를 따른다. 제품 저장·반출복원·실제 엔진 시험의 완료 근거는 개발팀이 별도로 제공한다.

## 명세와 양식의 검사

|실행|확인 범위|
|---|---|
|`python3 verify_framework.py`|현재 정본의 4CHK/9필수 결과 이름·적용 조건·충족 기준·주/보조 요구 귀속, 03 결과표, 현재 빈양식 45필드·내용 SHA·full branch·Q/focus/SC 및 필드사전|
|`python3 -m unittest discover -s tests -v`|정상 입력과 누락·중복·다른 CHK/요구 귀속·일부 충족 확대 등 독립 변형의 회귀 검사|
|`python3 개발전달/verify_assessment_record_examples.py`|EXAMPLE 4CHK/9결과와 참조·집계·수동검토·재사용·구판 연결, JSON roundtrip 및 25개 합성 반례|

정본 검사의 기대 계약은 검사 대상 catalog에서 다시 생성하지 않고 검토한 c67 기준을 독립 보존한다. 기준을 의도적으로 바꾸면 원문·명세와 검사 계약을 함께 검토한다. 이 검사는 프레임워크 자료와 합성 예시를 다룬다. 개발팀은 제품 EVD/RES·저장/API·반출복원과 실제 실행 결과를 별도로 검증한다. 구판 CPU 자료는 원 bytes·원 판본으로 읽으며 현재 빈양식의 갱신 대상에 포함하지 않는다.

OBS-012는 관측 사본의 5.7 결과와 Q-C12 로그·진단 외 자산별 사본 결과를 각각 보존하고 필요한 적용 범위로 CHK를 요약한다. 관측 결과를 비관측 자산이나 CHK 전체에 복사하지 않고, CHK 요약도 5.7에 복사하지 않는다. 사본별 정책이 미정이면 그 부분은 미확인으로 남긴다. 기존 별도 결과 기록과 범위별 집계 규칙을 사용한다.
