### 3. 이전 gap backfill

- 11:44:04.014Z 수집기의 Tetragon 자식(`kubectl logs --follow`) 하나에 SIGTERM을 보냈다. 0.15초 뒤 `gap_opened`(`backfill_since` 11:44:02Z)를 확인하고 바로 서비스를 정지했다. 정지 전에 gap이 닫히지 않았다.
- 정지 중 Tetragon 기록 줄 수는 늘지 않았다. 이 사이 11:44:06.66Z~06.78Z에 엔진 Pod에서 `/usr/bin/true`를 1회 실행했다(종료 코드 0).
- 11:44:10.02Z에 재시작했다. 같은 gap ID가 11:44:10.35Z에 `closed_by=collector_restart`, `backfill=requested_unverified`로 닫혔다.
- **전달 확인**: 재시작 뒤 Tetragon 기록에 정지 중 실행한 `/usr/bin/true` 1건(11:44:06.772Z, 같은 Pod UID, `serving-lab`, `engine`)이 나타났다. 2회차까지 미확인이던 backfill 실제 전달을 이 시험 범위에서 확인했다.
- 한계: 1회 실행이다. 로그 회전·긴 중단·Tetragon 출력 지연에서의 완전성은 확인하지 않았다. gap 기록의 `requested_unverified`는 설계대로 요청 증거이고, 전달 증거는 실행 1건 대조다.

### 4. SGLang 빈 캐시 첫 기동

- 2회차 캐시는 `dev-profile-01.run2-warm`으로 옮겨 두었다. 원래 경로를 UID 2000/GID 0/0700 빈 폴더와 하위 폴더 9개로 다시 만든 뒤 기동했다(11:31:46Z 적용, 11:36:06Z rollout 완료).
- 엔진 로그 표지: prefill 캡처 시작 11:35:10, prefill 캡처 끝 11:35:48, decode 캡처 끝 11:35:49, "fired up and ready" 11:35:59.
- 단계 시간표: loading 11:35:08.9~09.2, **compiling 11:35:10.6~11:35:59.987(준비 표지까지)**, 이후 inferring. PR #216의 "준비 완료까지 compiling 유지"가 실제 기동에서 동작했다.
- 셸 `/bin/sh` 36건은 모두 `compiling`, `suspect_binary`, `suspect_context=compile_toolchain_parent`이다. 이 가운데 **캡처 끝~준비 사이 9건**이 2회차 관찰 건수와 같다. 부모 설명이 붙어도 의심 경고는 유지됐다.
- 준비 뒤 첫 요청의 Triton `ptxas`(`/opt/sglang/lib/python3.12/site-packages/triton/backends/nvidia/bin/ptxas`) 4건은 `inferring`, `allowed_in_phase`, `parent_check=matched`이다.
- 남은 관찰:
  - compiling 중 `nvcc`·`gcc`·`ninja` 등은 `phase_signal_unverified`다. 로그 표지(`engine_signal`)는 신뢰 근거가 아니므로 설계대로다.
  - loading 표지 이전(11:33:47~11:34:35)의 `ptxas`·`gcc`·`ld` 등 7건은 `phase_unknown`이다. 단계 표지가 나오기 전의 실행이며, 2회차 시간표 한계에 적힌 "첫 Load weight 전 단계 없음"과 같은 성격이다. `outside_allowlist` 경고는 아니다.

### 5. Ready 전 엔진 미도달

- Gateway 준비(11:32:17Z) 뒤 15초 간격으로 정상 chat 요청을 보냈다.
- 엔진 준비 전 15건은 모두 Gateway 503이었다. 사유는 6건이 `TARGET_UNAVAILABLE`(대상 Pod 스냅샷 `container_missing`), 9건이 `TARGET_UNVERIFIED`(`model.id` 확인 불가)다.
- 같은 요청 ID 15건은 엔진 로그에 **0건**이었다.
- `serving-engine` Service의 ready endpoint는 vLLM 삭제 뒤 0개였고, 11:36:07Z에 1개가 됐다.
- 준비 뒤 2건(11:36:18Z, 11:36:36Z)은 200 `ALLOWED`이고, 같은 요청 ID가 엔진 로그에 있다.
- 해석: 이번에는 준비 전 요청을 **Gateway 대상 확인이 먼저 막았다**. Service endpoint 제외는 그 뒤의 두 번째 보호로 0개 상태임을 확인했다. Gateway 대상 확인을 통과한 상태에서 endpoint 반영이 늦는 경우는 이번에 재현하지 않았다.

### 6. `ptxas` 파일 보호

- 엔진 컨테이너 실행 계정은 UID 2000, GID 0이다.
- `ptxas` 파일과 상위 폴더 4단계(`bin`, `nvidia`, `triton`, `site-packages`)는 모두 `root:root 755`이고, UID 2000에서 `test -w`가 거짓이다.
- 루트 파일시스템은 읽기·쓰기(`rw`) mount이므로, 보호 근거는 읽기 전용 mount가 아니라 **파일 소유권·권한**이다. 내용 읽기·쓰기 시험은 하지 않았다.

### 7. vLLM loading 오경고 2건

- 대상: 11/3 15:31:56.985Z `/usr/local/cuda/bin/ptxas`, 15:31:57.985Z `/usr/local/cuda/bin/nvcc`. 둘 다 실제 부모는 `/usr/bin/python3`이다(Tetragon 호스트 기록과 시각·경로로 1:1 결합). 단계는 `loading`/`engine_signal`, `phase_source_error` 없음, 판정 `outside_allowlist`, `parent_check=not_constrained`이다.
- 현재 vLLM intent(2회차 묶음 `…-8d515ec`, 3회차 `…-b3fc80e`와 내용 같음)에는 두 경로가 loading·compiling 허용과 `/usr/bin/python3` 부모 조건으로 들어 있다. 이 intent였다면 `not_constrained`가 아니라 `matched`가 됐어야 한다. 이전 묶음 `…-e7fc0f1` intent에는 두 경로도 부모 조건도 없다.
- Gateway 정책 적재 기록은 15:29:35Z와 15:33:05Z다. 2회차 결과 문서에 "`current` 링크 교체가 권한 문제로 실패한 채 Gateway를 재시작해 이전 묶음을 읽었고 sudo로 교체 뒤 다시 시작했다"고 적혀 있다.
- **유력 원인**: 15:29:35Z 적재본이 이전 묶음이었고, 경고 2건은 15:33:05Z 재적재 전 약 3분 사이에 났다. 판정 값이 이 원인과 맞는다.
- 한계: 정책 이력에는 묶음 ID가 남지 않는다(정책 파일 해시는 두 묶음이 같다). 그래서 15:29:35Z에 어느 묶음을 읽었는지는 **직접 확인 불가**다. 현재 코드·intent를 바꿀 근거는 없다. 이번 3회차 vLLM AWS-11은 통과했다.

## 적용·복구 상태

- 정책 묶음: `bundle-aws-lab-dev-vllm-b3fc80e`, `bundle-aws-lab-dev-sglang-b3fc80e`를 새로 배치했다(root:10000, 폴더 0750, 파일 0640, 노트북·서버 `bundle verify` 통과). 2회차 묶음과 비교하면 vLLM은 `bundle.json` 말고 같고, SGLang은 intent의 `ptxas` 한 줄만 다르다. 시작 시 `current`는 `…-vllm-8d515ec`였다. 종료 시 `current`는 내용이 같은 새 검증본 `…-vllm-b3fc80e`다.
- Cilium·Tetragon 규칙: SGLang intent 후보와 적용 중 규칙 7개가 `kubectl diff`에서 같아 변경하지 않았다. NetworkPolicy도 건드리지 않았다.
- SGLang 캐시: 원래 경로에 2회차 캐시를 되돌렸다(소유·권한 원래와 같은 `2000:0 700`). 이번 빈 캐시 기동으로 생긴 캐시는 `dev-profile-01.run3-cold-20261104`로 보존했다.
- 종료 시 상태: 엔진은 vLLM(원래 digest), Gateway는 `rt-b3fc80e`, 수집기는 vLLM 설정으로 `active`, 최종 preflight fail 0. 시험용 port-forward는 정지했다.
- 서버 배포 사본: `~/runtime-integration/deploy-b3fc80e`(서버 값 채움, 서버 밖으로 반출하지 않음).

- 1회 관찰이다. 다른 image·재기동·긴 수집 중단에서 SGLang 단계 표지와 backfill 완전성을 다시 확인해야 한다.

- 정식(reference) 환경 평가가 아니다.
