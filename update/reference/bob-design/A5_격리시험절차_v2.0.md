# A5 격리시험 절차·판정 기준 v2.0

> v2.0 기준선 · 2026-10-02 · A14 D37~D39. 문서 검토 반영본이며 팀 소유자 승인·코드 시험·실측 완료를 뜻하지 않는다.

- **이 문서가 정하는 것:** 격리 실행 절차(S5), 증거 수집·완전성, 환경 동일성 검사, 시험별 판정 적용, 방향별 비교·권고(S6), RunManifest·Observation·Evidence·TestResult·Comparison·Recommendation 상세
- **다른 문서에서 가져오는 것:** 공통 객체·enum·불변식(A1 v2.0), 시험 정의·판정 규칙(A7 v2.0), 확정 정책(A11 v2.0), 영향평가·시험 계획(A4 v2.0), 환경·자료(A15 v2.0), 도구 보안(A13 v2.0)

**소유:** T2 · **상태:** v2.0 문서 기준선(2026-10-02; 구현·실측 완료 아님) · **기준:** A1 v2.0

**사례 ID ↔ 정식 시험 ID:** `MODEL-NORMAL-LOAD` → TEST-FUNC-003, `MODEL-AUTO-MAP-BLOCK` → TEST-MODEL-007, `MODEL-AUTO-MAP-REPEAT` → 같은 선정 TEST-MODEL-007의 추가 RUN(반복성 점검 자체는 별도 TEST/RES가 아님). TEST-NET-004는 런타임(A6)에서 확인한다.

## 1. 문서 목적

이 문서는 A4가 선정한 시험을 A15의 환경과 시험자료로 실행하는 절차를 정의한다.

개발자는 이 문서를 보고 다음 기능을 구현할 수 있어야 한다.

- 시험 입력과 환경값의 유효성 확인
- 기준 버전과 후보 버전의 순차 실행
- 실행 사이 캐시·Pod·표식 파일 정리
- 버전별 필수 증거 수집
- 두 실행 조건의 동일성 확인
- 시험별 PASS·FAIL·UNKNOWN 판정
- 구버전·신버전 비교에 따른 업데이트 권고·차단·보류

이 문서는 “어떤 환경과 자료를 사용할지”를 새로 정하지 않는다. 환경·모델·fixture·증거 종류는 A15를 입력으로 사용한다.

S7 런타임 통제는 1차 범위이며 A6/T3가 구현한다. A5는 격리 실행과 공통 Evidence·TestResult 계약을 소유하고 §3.4에서 NET-004 연결안을 정의한다. 커널 사전 차단은 비목표다. 프로세스·파일 탐지와 SYS/PERF 격리 관측은 현재 범위이며 §8.5·§8.6을 따른다.

### 2.2 이 문서에서 정하는 값

다음 항목은 외부 제품의 기본 동작이 아니라 본 프로젝트의 격리시험 설계 결정이다.

- 기준 버전을 먼저 실행하고 완전히 정리한 후 후보 버전을 실행
- 인프라 오류만 제한적으로 재시도
- 필수 증거가 없으면 PASS로 추정하지 않고 UNKNOWN 처리. **단 유효한 위반 증거가 있으면 다른 증거가 빠져도 FAIL 유지** (A1 불변식 10)
- 기준·후보 조건이 다르거나 확인할 수 없으면 비교(Comparison)는 INCONCLUSIVE, 개별 TestResult는 보존 (A1 불변식 9)
- 표식 존재 여부를 코드 실행의 핵심 증거로 사용
- 정상 모델 시험을 통해 보안 수정 이후 기능 정상성을 함께 확인

타임아웃 숫자는 PoC 초기값이며 사전 동작 확인 시험 후 조정할 수 있다. 조정한 값은 기준·후보에 동일하게 적용한다.

## 3. 입력과 출력

### 3.1 A4에서 받는 입력

정식 묶음은 A4 §11의 `change_fact:ChangeFact`, `impact_assessments:ImpactAssessment[]≥1`, `test_plan:TestPlan`이다. 객체 필드·참조·배열 위치를 그대로 사용한다. 과거 `analysis_id`, `enterprise_impact`, `isolated_test_requirement`, `test_selection` 형식은 새 계약이 아니며 검증 오류로 돌려준다.

| 입력 필드 | 실행기에 필요한 검증/매핑 |
| --- | --- |
| `change_fact.versions` | A15 대상 버전·이미지 내부 버전·소스 근거와 대조 |
| `impact_assessments[].policy_ref`, `.environment_ref`, `.change_refs` | 고정 참조 해석, CONFIRMED 및 승인 revision 유효성 확인 |
| `test_plan.impact_refs` | 받은 IA 집합의 exact Ref와 일치 |
| `test_plan.selected_tests` | TEST 원문 조회; ISOLATED만 A5 실행, RUNTIME은 §3.4로 |
| `test_plan.selection_reasons` | TEST·정책·behavior·phase·requirement_ref를 IA 요구에 연결 |
| `RequirementRef가 가리키는 IA.validation_requirements[i].conditions` | A15 실제 환경 값과 병합하여 RUN.resolved_conditions 잠금 |
| 같은 요구의 `expected`, `required_evidence`, `unknown_when` | 정책 기대와 필수 수집·판정 불가 사유. A7보다 약한 PASS 규칙 금지 |
| `impact_assessments[].runtime_requirements` | A6/T3로 전달; 격리 비교·권고 근거에 포함하지 않음 |
| `test_plan.not_selected_tests` / `.selection_reasons` | 미선정과 선정 사유 보존; 미선정 RES 생성 금지 |

실행 게이트: CONFIRMED 정책·scope APPLICABLE·해당 요구 APPLICABLE, TEST 선정 및 카탈로그 등록, 구현 상태 ready/verified, 필수 관측 구현, A15 preflight 성공. MODEL은 IA.applicability=APPLICABLE일 때만 실행한다. FUNC는 보안 영향과 독립된 적용 요구의 기본 시험이다. NET는 A6에서 실행한다. ready/verified는 내부 구현 준비 상태이며 **A1 교환 enum 아님**이다.

conditions의 동일 키 요청·실측이 다르면 실행 전 차단한다. 누락은 실측으로 채울 수 있지만 값의 출처를 남긴다. 확인 불가 값을 false·0·빈 문자열로 채우지 않는다. 선정 후 차단은 TEST·대상별 NOT_STARTED RUN과 UNKNOWN RES로 남긴다. 미선정 시험은 RUN/RES를 만들지 않는다.

### 3.2 A15에서 받는 입력

A15 §10의 정적 환경 설정을 동일한 키로 받는다. 이 설정은 선언값이며 A11 EnvironmentProfile 또는 실측 RunManifest를 대신하지 않는다. 아래 YAML은 설정 예시이고 시험 실행·결과 객체가 아니다. 실제 잠금은 A15 §8.1 및 A5 §3.3 Conditions 계약을 사용한다.

~~~yaml
targets:
  baseline:
    version: "0.13.0"
    image: vllm/vllm-openai:v0.13.0
  candidate:
    version: "0.14.0"
    image: vllm/vllm-openai:v0.14.0
environment:
  namespace: vllm-guard-test-cve-2026-22807
  gpu_count: 1
  isolation: node
  evidence_root: artifacts/cve-2026-22807
test_materials:
  normal_model:
    id: facebook/opt-125m
    commit_sha: 27dcfa74d334bc871f3234de431e71c6eeba5dd6
    mount: /models/normal
  normal_request: tests/fixtures/cve-2026-22807/normal-request.json
  attack_fixture:
    path: tests/fixtures/cve-2026-22807/auto-map-model
    mount: /models/attack
test_cases:
  - MODEL-NORMAL-LOAD
  - MODEL-AUTO-MAP-BLOCK
  - MODEL-AUTO-MAP-REPEAT
required_evidence:
  - image_metadata
  - model_metadata
  - environment_metadata
  - actual_settings
  - pod_spec
  - network_policy
  - execution_logs
  - process_exit
  - loading_and_response
  - error_scope
  - path_reached
  - policy_rejection
  - marker_observation
  - observation_window_and_status
~~~

| 설정 키 | 타입·필수 여부 | null/검증 |
| --- | --- | --- |
| `targets` | `{baseline:{version:string,image:string},candidate:{version:string,image:string}}`, 필수 | 모든 값 non-null; allowlist 버전·문자열 검사, digest는 preflight 확인 |
| `environment` | `{namespace:string,gpu_count:integer≥1,isolation:string,evidence_root:string}`, 필수 | non-null; MODEL은 node; Namespace는 A13 허용 접두사 |
| `test_materials` | 등록 executor가 요구한 자료 역할별 object, 필수 | 추가 역할은 A17 §4.4 registry로 검증. 기존 normal_model/normal_request/attack_fixture는 해당 실행기에서만 요구하는 별칭 |
| `test_cases` | string[], 필수 | ≥1; A17 §4.4 바인딩의 등록 동작에 연결된 내부 사례만 허용. 선언 목록은 선정 목록이 아니며 PLAN이 최종 제어 |
| `required_evidence` | 위 예시의 증거 역할 string[], 필수 | ≥1; 시험별 적용 역할과 실제 수집 구현 검증. 다른 시험의 미사용 역할을 수집 누락으로 집계하지 않음 |

추가 키는 거부하고 A15 §3·§4·A5 §6의 자원·보안·옵션·타임아웃 규칙으로 Conditions를 구성한다. test_materials에서 모델 자료·시험 입력 원문을 확인해 files_sha256/test_input_sha256을 계산한다. 미확인 node/GPU/이미지 내부값은 preflight에서 확보하며 선언 예시에 지어 넣지 않는다.

### 3.3 완전한 교환 스키마

구조 버전은 RUN/OBS=2.1, EVD/RES/CMP/REC=2.0(A1 §2.4)을 사용한다. 이전 생략형 예시는 유효 객체가 아니며 입력에서 지원하지 않는 버전은 오류다. T3의 런타임 Evidence도 아래 계약으로 직렬화한다. §3.3 표에 없는 필드는 거부한다. 객체 내 `resolved_conditions`, 관측 subject별 observed_value, 버전 식별 구조도 아래 계약을 따른다.

#### 3.3.1 모든 객체의 공통 필드·타입

| 필드/타입 | 타입 | 필수 | null/빈값 |
| --- | --- | --- | --- |
| `id` | nonempty string, 객체별 A1 접두어 | 필수 | 불가 |
| `schema_version` | string, 객체별 A1 §2.4 값 | 필수 | 불가 |
| `revision` | integer ≥1 | 필수 | 불가 |
| `created_at` | RFC3339 string, 시간대 필수 | 필수 | 불가 |
| Ref | `{id:nonempty string,revision:integer≥1}`; 추가 키 불가 | 참조 타입 | 불가 |
| SHA | 소문자 16진수 64자리 string | 해시 타입 | 필드별로 결정 |
| Digest | `sha256:` + SHA string | 이미지 타입 | 필드별로 결정 |
| Window | `{start:RFC3339 string,end:RFC3339 string}`; start≤end | 구간 타입 | 불가 |

동일 ID·revision은 불변이다. RUN 상태 변경은 같은 ID의 새 revision으로 기록하고 이전 것을 보존한다. OBS/EVD/RES/CMP/REC는 새로운 사실·재수집·재판정이면 새 ID로 기록한다. 상태 전이에 따라 RUN을 참조할 때는 수집/생성 시점의 고정 revision을 유지하며 판정기는 revision의 완전 일치만 강제하지 않고 동일 RUN ID 및 시간/상태 이력을 대조한다. RES.run_ref는 최종 판정 대상 RUN revision이다. 다른 RUN ID의 증거를 단일 RES에 섞지 않는다. 참조 대상 접두어·revision·RUN 귀속을 검사하며 해결 불가 참조는 오류다. null/누락/빈 배열/UNKNOWN은 서로 다르다.

#### 3.3.2 RunManifest (RUN)

| 필드 | 타입 | 필수 | null/빈값 |
| --- | --- | --- | --- |
| `test_ref` | Ref (TEST) | 필수 | 불가 |
| `target_version` | `{role:string,vllm:string,image_ref:string,image_digest:Digest\|null,platform:string\|null}` | 필수 | 전체 null 불가; digest/platform은 NOT_STARTED 또는 시작 전 ABORTED의 preflight 미확인 때만 null |
| `resolved_conditions` | Conditions (아래 정의) | 필수 | 전체 null 불가; 미확인 하위 값은 명시한 곳만 null |
| `execution_status` | NOT_STARTED/RUNNING/COMPLETED/ABORTED | 필수 | 불가 |
| `phase` | ISOLATED/RUNTIME | 필수 | 불가 |
| `qualification` | `OFFICIAL`\|`EARLY_SMOKE` (A5 상세값, A1 §4 enum 아님, D42) | 필수 | 불가. 예약 시 고정, 이후 revision에서 바꿀 수 없음. A8 I8a 조기 스모크 실측은 `EARLY_SMOKE`. RELEASE 승인 근거로는 `OFFICIAL` RUN의 RES만 쓴다(A12 §5.4) |
| `plan_ref`, `environment_ref` | Ref 각각 | 필수 | 불가 |
| `requirement_refs` | A4 RequirementRef[] | 필수 | ≥1·중복 금지; 예약 후 불변 |
| `policy_refs` | Ref[] (POL) | 필수 | ≥1 |
| `started_at`, `ended_at` | RFC3339 string 각각 | 필수 | NOT_STARTED이면 모두 null; RUNNING이면 ended_at null; COMPLETED와 RUNNING을 거친 ABORTED는 모두 non-null; **시작 전 ABORTED(NOT_STARTED→ABORTED)는 started_at null·ended_at=포기 시각(transition_run의 `at`)** — 실제 시작이 없으므로 started_at을 만들어 넣지 않는다 |
| `stop_reason` | string | 필수 | RUNNING 및 정상 COMPLETED는 null; NOT_STARTED/ABORTED이면 nonempty |
| `condition_evidence_refs` | Ref[] (EVD) | 필수 | NOT_STARTED와 시작 전 ABORTED일 때 `[]` 허용; 실행한 RUN(RUNNING을 거친 RUN)은 ≥1 |

role은 출처 역할 이름(baseline/candidate 등)이며 판정 enum이 아니다. 비교 방향을 바꿔도 원본 role을 수정하지 않는다. image_ref는 실행 요청 식별자이고 digest는 확인된 실제 대상이다. NOT_STARTED의 image_ref에 요청 태그가 있어도 이를 실측 digest로 취급하지 않는다.

Conditions의 **모든 키는 필수**, null 여부는 아래 표대로다. source 입력 불충분으로 NOT_STARTED라면 null을 허용하는 필드에 미확인을 남기고 stop_reason에 위치를 적는다. RUNNING 전에 해당 phase 실행 필수값을 모두 확정한다. runtime_options는 **잠근 요청 조건**이며 실제 최종 설정의 증명은 model.actual_settings/기동 원본 EVD다. 이름이 resolved라는 이유로 실행 적용을 입증했다고 간주하지 않는다.

| Conditions 키 | 타입 | null 허용·조건 |
| --- | --- | --- |
| `isolation` | string (`namespace` 또는 `node`, 내부 등급, **A1 교환 enum 아님**) | 불가; MODEL은 node |
| `environment_snapshot` | EnvSnapshot object 아래 필드 모두 포함 | 불가; NOT_STARTED 또는 시작 전 ABORTED에서 미확인 하위 값 null 허용 |
| `model` | `{id:string,commit_sha:string\|null,files_sha256:SHA,mount:string}` | MODEL/FUNC/SYS/PERF 실행 시 필수; NET 또는 NOT_STARTED/시작 전 ABORTED의 자료 미확인은 null. fixture는 commit_sha=null이고 files_sha256으로 고정; 정상 모델 commit_sha는 40자리 lowercase hex |
| `test_input_sha256` | SHA | NOT_STARTED/시작 전 ABORTED 미확인만 null |
| `runtime_options` | `{trust_remote_code:boolean\|null,dtype:string\|null,tensor_parallel_size:integer≥1\|null,served_model_name:string\|null,host:string\|null,port:integer(1..65535)\|null}` | object는 non-null; 실행 설정 미확인·phase 미사용 필드는 null. FUNC/SYS/PERF 실행에 필요한 옵션은 non-null |
| `security_context` | `{pod:PodSC,container:ContainerSC}` object | NOT_STARTED/시작 전 ABORTED 미확인만 null; 아래 PodSC/ContainerSC 타입 및 A15 §3.2 사용 |
| `mounts` | `{path:string,read_only:boolean,purpose:string}[]` | NOT_STARTED/시작 전 ABORTED 미확인만 null; 실행 시 ≥1 |
| `environment_variables` | `{name:string,value:string}[]` | `[]` 허용; 비밀 원문 저장 금지, 필요 비밀은 식별 참조를 시험 자료에 기록 |
| `network_policy_sha256` | SHA | NOT_STARTED/시작 전 ABORTED 미확인만 null |
| `control_mode` | OBSERVE/BLOCK | 정책 입력 없으면 null; NET 실행은 non-null |

Conditions에 정의되지 않은 SC 키를 임의로 추가하지 않는다.

EnvSnapshot의 각 키: `namespace:string`, `node_uid:string`, `node_name:string`, `gpu_model:string`, `gpu_count:integer≥1`, `gpu_allocation:string`, `cpu_request:string`, `cpu_limit:string`, `memory_request:string`, `memory_limit:string`, `kubernetes_version:string`, `driver_version:string`, `host_cuda_version:string`, `cni_name:string`, `cni_version:string`. 각 키는 필수이며 NOT_STARTED/시작 전 ABORTED에서 확인하지 못한 값만 null; 실행 시 non-null이다. host CUDA 조건은 nvidia-smi의 드라이버 지원 상한과 호스트 설치 toolkit을 구분한 기록값이며 컨테이너 CUDA runtime과 혼동하지 않는다. 호스트 toolkit 미설치가 확인되면 확인 사실을 문자열로 기록한다. 이미지 안 CUDA는 이미지 메타데이터로 따로 보존하며 동등성에서 허용 차이다.

OBS에는 `provenance:{data_origin:MEASURED|EXAMPLE,verification_level:ENGINE|PARTIAL_PATH|STATIC,producer_version:string}` 필드를 필수로 추가한다. 수집 서비스가 RUN·원본 EVD와 대조해 부여하며 센서/사용자 주장만 복사하지 않는다. observed_value=null이고 판정 근거가 없으면 provenance 전체는 null이다. 합성 사건은 EXAMPLE·STATIC, 실제 엔진 경로를 확인한 실측은 MEASURED·ENGINE이다. 판정 래퍼의 내부 검증 타입은 A17 §4.1을 따른다.

COMPLETE의 observed_value 전체 null은 금지한다. COMPLETE는 수집 범위가 완결됐다는 뜻이며 값의 진위를 보장하지 않는다. FAIL은 유효 관측·증적의 귀속·무결성·내용을 검증한 뒤 내린다. PARTIAL이라도 확보한 유효 위반을 사용할 수 있다.

| `direction` | UPDATE/ROLLBACK | 필수 | 불가 |

BEHAVIOR_CHANGED는 두 PASS의 정책 충족 외 의미 있는 변화가 사전 정의된 동작 비교 기준으로 확인될 때만 가능하다. 응답 텍스트가 다르다는 이유로 자동 생성하지 않는다. 1차 두 시험에는 별도 동작 동등성 기준이 없으므로 현재 판정기는 이 값을 자동 발행하지 않지만 §9 권고 입력에는 처리 규칙을 둔다.

#### 3.3.8 검증·집계 순서

1. 타입·필수·null·enum·ID 접두어·시간·Ref 해결을 검증한다. 실패는 위치·이유 오류이며 조용히 보정하지 않는다.
2. TEST·RUN·OBS·EVD의 귀속 및 원본 파일 무결성을 검사한다. 무효한 EVD만 판정에서 제외한다.
3. A7 우선순위로 RES를 판정한다. 확인된 FAIL은 다른 누락·중단보다 우선한다.
4. A1 불변식 9로 CMP를 판정하고 개별 RES를 보존한다.
5. §9로 REC를 판정한다. basis_metadata는 null 포함 원본 RES별 값이다. 대표 검증 수준은 모든 값이 non-null일 때 STATIC < PARTIAL_PATH < ENGINE의 최약값, 하나라도 null이면 null이다. 데이터 출처도 null 전파, 전부 MEASURED일 때만 MEASURED, 하나라도 EXAMPLE이면 EXAMPLE이다. EXAMPLE/null 근거로 ELIGIBLE을 내지 않는다.

### 3.4 RUNTIME 시험 RUN·RES 발행 계약 (D25 채택, D27 확정, D40로 RUNTIME 시험 일반화)

**책임:** T2가 RUN·OBS·EVD·RES 스키마, 저장 API, A7 §6 판정기를 소유한다. T3 `runtime verify`는 아래 API로 전용 RUN을 예약·전이하고, 같은 통제 경계의 시도·차단·수신 관측을 OBS·EVD로 넘긴다. RES는 T2 판정기만 발행한다. RuntimeEvent·EnforcementStatus는 T3가 발행한다(A6 §2.7). NET RES는 S6 Comparison·Recommendation 근거에 넣지 않고 A12에 S7 결과로 따로 전달한다. **D40:** 같은 계약을 `phase=RUNTIME`인 모든 TEST에 쓴다(1차: TEST-NET-004, TEST-APIGW-001). 시험별 차이는 `resolved_conditions.runtime_context`의 내용과 관측 subject(§8.4, §8.8)뿐이며 API 이름·멱등·CAS·미실행 규칙은 같다. RUNTIME RES는 모두 S6 근거에 넣지 않는다.

#### 3.4.1 API 계약

내부 함수 계약이다(HTTP endpoint 아님). 모든 호출은 §3.3 validator를 통과한 객체만 저장한다. 입력 검증 실패는 저장하지 않는다. DB commit 이후 감사·파일·외부 자원 실패는 §3.4.4의 미완료 복구 경계를 따르며 아무 기록도 없다는 뜻이 아니다.

| 호출 | 입력 | 출력 | 멱등·경합·오류 |

| `transition_run` | `run_ref`, `expected_revision`, `target_status`(RUNNING/COMPLETED/ABORTED), `at`, `reason`, `request_key`, `start_payload`(§3.4.4) | 같은 ID의 새 RUN revision | `expected_revision`이 최신과 다르면 `STALE_REVISION`(CAS). 허용 전이: NOT_STARTED→RUNNING, NOT_STARTED→ABORTED(시작 전 포기), RUNNING→COMPLETED, RUNNING→ABORTED. 그 밖 `INVALID_TRANSITION`. RUNNING 전이는 정책 적용·센서 준비 확인 EVD가 있어야 허용 |
| `append_observations` | `run_ref`(관측 당시 revision), OBS 목록, EVD 목록 | 저장된 OBS·EVD Ref 목록 | 같은 ID·revision에 다른 내용 → `IMMUTABLE_VIOLATION`. 다른 RUN ID의 OBS·EVD 섞임 → `RUN_MISMATCH`. COMPLETED·ABORTED 뒤 추가는 거부(새 관측은 새 RUN) |
| `finalize_and_judge` | 최종 `run_ref`, 판정에 쓸 OBS Ref 목록, `judge_version`, `request_key` | RES Ref 1개 | RUN이 COMPLETED·ABORTED가 아니면 `RUN_NOT_FINAL`. 같은 `request_key` 재요청 → 기존 RES 반환(응답 유실 대비). 한 RUN의 최초 RES는 1개. **재판정**은 새 `request_key`로 새 RES를 만들고 `reason`에 원본 RES Ref를 적는다(§3.3.5) |
| `read_runtime_result` | `run_ref` | 그 RUN의 RES Ref 목록(시간순) | 없으면 빈 목록. T3는 결과를 읽어 RTE·ENS와 연결할 뿐 판정을 다시 구현하지 않는다 |

**미실행:** 선정 후 정책·센서·경계가 준비되지 않으면 RUN을 NOT_STARTED→ABORTED로 닫고 `finalize_and_judge`로 UNKNOWN RES를 발행한다(`verification_level`·`data_origin` null, 사유 필수, A1 불변식 12). **재시도**(실제 probe를 다시 보냄)는 새 RUN이다. 전달 오류는 진단으로 남기며 성공 RES를 만들지 않는다.

#### 3.4.2 목적지·관측 구간·원시 자료

- **목적지 표기:** `runtime_context.destination`은 구체 IP 리터럴 문자열(IPv4/IPv6, 접두 길이 없음), `protocol`은 TCP/UDP, `port`는 정수다. A11 `allowed_destinations`의 CIDR 문법(`PROTOCOL|CIDR|PORT`)과 다른 필드다. `network.context.forbidden`은 판정기가 계산한다 — 이 목적지·프로토콜·포트가 어느 허용 항목에도 포함되지 않으면 true. 제출값을 그대로 믿지 않는다.
- **관측 구간:** 계획 구간은 `reserve_runtime_run` 시 `runtime_context.window`로 고정한다(이후 바꾸지 않음). 실제 관측 구간은 각 EVD·OBS의 `window`다. 판정기는 시도 시각이 계획 구간 안에 있고, `network.sensor_health` EVD의 window가 시도 시각부터 수신 판정 대기 시간 끝까지를 덮을 때만 미수신을 PASS 근거로 쓴다. 덮지 못하면 UNKNOWN이다.
- **원시 자료 검증:** 판정기는 OBS의 `observed_value`만 판정에 쓰고, 원시 artifact(A6 §3.3 `raw/`)는 해석하지 않는다. 원시 자료를 OBS로 만드는 파서는 T3 수집기 소유이며, 파서 이름·버전을 `EVD.source.method`에, 원시 위치를 `EVD.source.source_location`에 남긴다. 판정기는 OBS의 `evidence_refs`가 같은 RUN의 COMPLETE·PARTIAL EVD를 가리키는지만 검사한다. 원시 artifact 포맷은 A6가 정한다.
- **마스킹 출처:** 비밀을 제거한 bytes를 저장한 EVD는 `source.method`에 `sanitized:<마스킹 프로필 버전>`을 적는다. 비밀이 든 원본은 저장하지 않으며 그 해시도 남기지 않는다(A11 `source_file.content_kind`, A13 §8).

#### 3.4.3 시험 밖 운영 증적

정책 번들 등록·운영 적용처럼 시험 RUN이 없는 증적은 **1차에서 A5 EVD로 발행하지 않는다.** A6 감사 로그와 런타임 artifact로만 보관하고, EnforcementStatus의 `evidence_refs`에는 NET-004 RUN에서 만든 EVD만 넣는다. RuntimeEvent의 `evidence_refs`에는 그 사건이 속한 등록 RUNTIME 시험 RUN의 EVD만 넣는다(NET 사건→NET-004, 게이트웨이 사건→APIGW-001, D42). 다른 RUN의 EVD를 섞으면 거부한다. 이를 위해 미선정 시험의 RUN을 만들지 않는다. 운영 증적용 별도 RUN 의미는 이후 범위다.

#### 3.4.4 준비·시작·복구 계약 (D43)

reserve가 PLAN의 선정 RequirementRef를 검증하고 policy_refs를 연결 IA의 POL 집합에서 도출한다. 호출자가 임의 policy_refs를 덮어쓰지 않는다. runtime_context의 종류·RTP·UID·계획 window는 기존처럼 예약 전에 준비하여 고정한다. 아직 신원·구간을 확정할 수 없으면 runtime_context=null인 미실행 RUN만 남기고 ABORTED로 닫는다. RUNTIME RUNNING 전이에 UID·계획 window를 새로 넣거나 바꾸는 경로는 없다.

`start_payload={preflight_updates:object,condition_evidence_refs:Ref[]≥1}|null`이다. RUNNING 전이만 non-null이며 다른 전이는 null이다. preflight_updates는 `{image_digest:Digest?,platform:string?,environment_snapshot:EnvSnapshot?,model:Model?,test_input_sha256:SHA?,security_context:SecurityContext?,mounts:Mount[]?,network_policy_sha256:SHA?}`의 닫힌 키 집합이다. Model=Conditions.model의 non-null 타입, SecurityContext=Conditions.security_context의 non-null 타입, Mount=Conditions.mounts의 원소 타입이며 EnvSnapshot도 §3.3.2의 정의 그대로다. 이들은 별도 교환 객체가 아니다. 이미 확인된 non-null 값은 유지하고, 예약에서 명시적으로 null인 허용 값만 확인된 준비 사실로 채운다. 객체형 업데이트는 §3.3.2 소유 타입의 전체 하위 키를 갖춘 완전한 값을 받는다. 부모 객체가 non-null이어도 null인 하위 값은 보완할 수 있으며 기존 non-null 하위 값은 타입과 값이 동일해야 한다. 필수 키 누락·키 추가·기존 값 변경/삭제는 거부한다. 배열은 기존 non-null이면 원소·순서를 그대로 유지하고, 필드 전체가 null인 경우에만 소유 타입의 완전한 배열로 채운다. runtime_options/pack_locks/binding/요구/runtime_context의 UID·계획 window는 업데이트 허용 대상이 아니며 새 값을 주입하지 않는다. 미사용 null은 그대로 둘 수 있고, 갱신 후 전체 Conditions를 phase별 시작 validator로 다시 검사한다.

흐름: 예약 RUN r1 → 준비 EVD 저장(append_observations에 OBS=[] 허용) → 동일 RUN ID·이력·준비 사실·hash를 검증한 start_payload와 CAS → RUNNING r2 → 실제 관측 → 최종 RUN → 판정. 준비 EVD는 시작 전 r1 귀속을 유지할 수 있지만 실행 관측·MEASURED 시험 성공을 주장하지 않는다. RUN의 condition_evidence_refs는 시작 전이에 함께 고정하고 이후 제거하지 않는다.

started_at은 공식 RUNNING으로 확정된 시작 전이의 at이며 하네스/검증 작업의 논리 시작을 뜻한다. 엔진 로딩 완료나 첫 요청 도달 시각은 OBS/EVD로 별도 입증한다. 공식 RUNNING 확정 전 취소는 시작 전 취소, 확정 뒤 취소는 시작 후 중단이다. 감사 완료만으로 후보가 공식 기록이 되지는 않는다. 후보의 시각은 공식 확정 전에는 실행 시작 이력으로 사용하지 않는다. ended_at은 실제 종료/포기 시각이다. runtime_context.window는 예약한 계획 구간이며 OBS/EVD.window는 실제 관측 구간이다. 구간 밖 관측으로 전체 PASS를 만들지 않는다. 공식 RUNNING을 거친 COMPLETED/ABORTED는 started_at을 보존하며 시작 전 null 예외를 사용할 수 없다. 시작 전 ABORTED는 started_at=null·ended_at=포기 시각·UNKNOWN·출처 null이고 미확인 준비 값은 null을 유지한다.

reserve/transition/finalize의 멱등 범위는 주체+유스케이스+request_key(예약의 기존 idempotency_key는 내부 별칭)다. 인증·권한을 먼저 재확인하고 동일 완료 요청은 CAS보다 먼저 기존 결과를 반환한다. 같은 키의 다른 요청은 CONFLICT, 새 키의 낡은 revision은 STALE_REVISION이다. 미완료 동일 키는 복구하고 실제 probe를 중복 실행하지 않는다. DB의 전이 후보·내부 명령 결과·audit outbox는 같은 transaction에 저장하되 후보와 공식 RUN revision을 구별한다. 내부 명령은 run_id·expected_revision·candidate payload/hash·request_key·lease epoch·audit 완료·확정/취소 결과를 보호 저장하며 교환 Ref를 발행하지 않는다. durable audit/앵커 확인 후에도 현재 RUN revision·취소 상태·lease epoch를 다시 검사하고, 공식 RUN revision 등록과 명령 결과 확정을 한 DB transaction에서 처리한다. 외부 파일·audit append·클러스터 효과까지 원자 DB 작업으로 주장하지 않는다. 미완료 후보는 기존 공식 RUN만 조회 가능하게 한 채 복구하고 부작용·승인 사용·성공 응답을 금지한다. 공식 확정 후 readback한 결과만 성공 반환한다.

**D44 확정/취소 경합:** 시작 후보와 취소는 동일 RUN의 공용 명령/CAS 경계에서 직렬화한다. 확정 전 취소가 이기면 미공개 RUNNING 후보를 취소로 종결하고 r1에서 시작 전 ABORTED r2 후보를 만든다. 그 ABORTED의 감사/확정을 마친 뒤 공개하며 start 키의 결과는 취소로 고정한다. 취소된 RUNNING 후보는 공식 revision을 차지하지 않고 실행 성공으로 재반환하지 않는다. 시작 확정이 이기면 RUNNING r2를 보존하고 이후 취소는 최신 r2에 대한 ABORTED r3다. 새 요청의 낡은 expected_revision은 STALE_REVISION이며 암묵 승격하지 않는다. 감사 완료 뒤/공식 확정 전 취소도 앞 경로다. 완료 키 재요청·응답 유실은 확정된 원래 결과를 반환하며 probe를 중복 실행하지 않는다. 공식 확정 후 장애가 나면 실행 여부/소유를 대조해 보존·종결하고 같은 RUN으로 재실행하지 않는다.

**D45 후보 감사의 귀속:** 미공개 전이 후보의 감사 object Ref는 현재 공식 RUN(예: r1)에 고정하고, payload hash는 내부 전이 명령의 고정 bytes를 식별한다. 명령은 후보 내용/hash와 request_key를 담고 operation에서 후보 검증임을 구분한다. 후보 r2를 공식 교환 Ref로 발행하지 않는다. 공식 확정 transaction은 감사 완료 명령의 후보 hash와 등록 RUN bytes/hash의 일치를 확인하고 연결을 내부 metadata에 보존한다. 취소된 후보의 감사는 삭제하지 않으며 취소/확정 결과에 연결한다. 같은 r2 후보 번호였다는 이유로 미공개 RUNNING 후보의 감사가 공식 ABORTED의 감사로 재사용되지는 않는다(A13 §12).

시작 후 장애는 보존 가능한 근거를 먼저 봉인하고 ABORTED로 닫는다. 유효 위반은 FAIL로 유지하고 근거가 없으면 UNKNOWN이다. 종료 뒤 관측을 추가하지 않으며 실제 재실행은 새 RUN이다. 이전 lease epoch의 늦은 쓰기를 거부하고 정리 실패는 pool을 차단한다. 감사/보존 실패는 객체가 전혀 없다는 뜻이 아니라 완료·효력 공개가 불가능한 상태다.

### 5.2 실행 잠금값 생성

실행 직전 다음 값을 확인하여 run-lock.yaml에 기록한다.

- 기준·후보 이미지 digest
- 컨테이너 내부 vLLM 버전
- 정상 모델 commit SHA
- 정상 모델 파일 SHA-256
- 공격용 fixture 파일 SHA-256
- 시험 입력 파일 SHA-256
- Kubernetes 버전
- GPU 모델과 개수
- NVIDIA 드라이버
- CUDA runtime
- CPU·메모리 request와 limit
- NetworkPolicy SHA-256

완료 조건:

~~~text
모든 필수값 수집 성공
AND 이미지 내부 버전이 A15 기대 버전과 일치
AND 모델·fixture가 기준·후보에서 동일
→ run-lock 확정

필수값 수집 실패 또는 버전 불일치
→ 실행 중단
→ 내부 PRECONDITION_FAILED 사유 기록
→ 선정 시험별 NOT_STARTED RUN + UNKNOWN RES(검증 수준·출처 null) 생성
~~~

PRECONDITION_FAILED는 내부 실패 코드(**A1 교환 enum 아님**)이며 RunManifest/RES 경계에서 NOT_STARTED·UNKNOWN으로 변환한다. run-lock은 완성될 때만 잠금 완료로 표시하고 미확인 값이 남은 초안을 확정본으로 사용하지 않는다.

### 5.3 Kubernetes 환경 생성

**범용 실행 계약:** namespace·증거 루트·표식 계약·내부 사례 ID는 A17 §4.4 실행 바인딩에서 읽는다. 아래 22807 전용 문자열·경로는 첫 팩의 예시이며 필수 상수가 아니다. 코어는 팩 ID 또는 CVE로 분기하지 않는다.

1. 승인된 `vllm-guard-test-cve-2026-22807` Namespace를 생성한다(A13 §4.5 허용 접두사).
2. ResourceQuota·ServiceAccount·NetworkPolicy를 적용한다.
3. 정상 모델 snapshot과 공격용 fixture를 read-only로 준비한다.
4. /evidence는 실행 시도별 새 emptyDir로 생성한다.
5. 기준·후보 Deployment는 replicas=0으로 생성한다.
6. GPU 자원 1개·전용 노드 할당·운영 워크로드 부재를 확인한다. MODEL은 node 등급만 허용한다. NetworkPolicy를 지원하는 CNI와 통제 준비 근거도 실행 전에 확인한다(A15 §8a).

완료 조건:

- Namespace가 Active
- 정책 자원이 모두 적용됨
- 외부 model download egress가 차단됨
- 실행 대상 외 Pod가 없음
- GPU 할당 가능
- 증거 저장공간 쓰기 가능

#### 5.3a 실행 바인딩 검증

A17 §4.4 registry에서 TEST 실행기·subject·자료 역할·전제 평가기를 해석한다. 팩의 미지원 선언은 코드로 실행하지 않고 `UNSUPPORTED_BINDING`으로 거부한다. 선택된 시험 실행 준비 실패는 NOT_STARTED/시작 전 ABORTED 및 UNKNOWN으로 남긴다. A15 §10의 기존 자료 키는 첫 팩의 바인딩 별칭이며 다른 팩에 모든 키를 강제하지 않는다.

### 5.4 사전 동작 확인 시험(Smoke Test)

공식 실행 전 A17 §5 SmokeRecord를 검증한다. 버전 문자열만이 아니라 A17 §5.2 qualification profile의 이미지 digest·플랫폼·정상 준비 모델·엔진 인자·환경 지문·파서 버전·증거 해시가 일치해야 한다. 실제 시험자료는 Binding의 허용 차이와 별도 preflight로 검사한다. 다르면 새 준비 smoke가 필요하다. smoke는 별도 준비 실행이며 순환적으로 공식 시험의 기존 smoke 자격을 요구하지 않는다. 준비 실행도 C2~C5와 필요한 자원 격리 조건을 충족해야 한다.

취약점 시험 전에 환경 자체가 작동하는지 확인한다.

~~~text
정상 모델 snapshot mount
→ 대상 Deployment replicas=1
→ Pod Scheduled 확인
→ GPU 인식 확인
→ vLLM 프로세스 시작 확인
→ readiness 확인
→ 최소 정상 요청 1회
→ 응답과 로그 저장
~~~

사전 동작 확인 시험의 목적은 취약점 판정이 아니다. 이미지, GPU, 모델 mount, 포트, 자원값이 시험 가능한 상태인지 확인하는 것이다.

실패 처리:

| 상황 | 처리 |
|---|---|
| ImagePullBackOff | 인프라 오류, 한 번 재시도 |
| GPU 스케줄 실패 | 환경 오류, 시험 중단 |
| OOMKilled | 자원 가정값 조정 후 전체 run을 처음부터 다시 시작 |
| 모델 파일 누락 | 입력 오류, 시험 중단 |
| readiness timeout | 로그 수집 후 원인 분류 |
| 최소 정상 요청 실패 | 환경 준비 실패는 UNKNOWN, 정상 모델 명시적 로딩/요청 오류는 A7에 따라 FAIL; 취약점 시험은 준비 상태 검토까지 보류 |

자원값을 변경하면 기존 RUN·증거·FAIL을 보존한 채 새 batch-key·RUN·run-lock으로 처음부터 시작한다. 사전 smoke는 별도 실행 기록이며 FUNC의 공식 RUN과 혼용하지 않는다.

### 5.5 기준 버전 정상 모델 시험

목적:

- 기준 버전이 정상 모델을 로딩하고 최소 요청을 처리할 수 있는지 확인
- 이후 공격용 fixture 결과와 환경 장애를 구분

절차:

~~~text
새 cache·tmp·evidence 볼륨 생성
→ vLLM 0.13.0 실행
→ trust_remote_code=false 확인
→ 정상 모델 로딩 대기
→ readiness 확인
→ 고정된 최소 요청 실행
→ 응답·로그·Pod 상태 수집
→ 증거 해시 생성
~~~

정상 모델 판정은 §8.1을 그대로 사용한다. /health 성공만으로 로딩/응답 PASS를 만들지 않는다. 해당 공식 RUN의 로딩 성공·전체 오류 0·유효 응답 ≥1이 확인돼야 한다. 실행 요청 1회만 보내며 timeout·retry·validator 버전을 실행 전에 잠근다.

### 5.6 실행 사이 완전 정리

다음 실행 전에 이전 실행의 영향을 제거한다.

1. 로그·Pod spec·events·관측 자료를 Pod 삭제 전에 외부 증거 경로에 복사한다. 종료 컨테이너에 pods/exec가 가능하다고 가정하지 않는다. 실행별 /evidence 볼륨에 접근하는 비특권 수집 sidecar 등 보존 경로를 사전에 검증하고, 수집기는 엔진 종료 후에도 관측 종료·외부 복사까지 유지한다. 엔진 워크로드에 Kubernetes API token을 제공하지 않는다.
2. evidence-manifest에 파일 SHA-256을 기록한다.
3. 대상 Deployment를 replicas=0으로 내린다.
4. 대상 Pod가 완전히 종료될 때까지 확인한다.
5. 실행 시도에 사용한 **쓰기용** cache·tmp·evidence 볼륨을 삭제한다. A15가 준비한 고정 모델 snapshot은 읽기 전용 볼륨으로 따로 두고 삭제하지 않는다 (A15 §4).
6. 같은 label을 가진 잔여 Pod·Job·PVC가 없는지 확인한다.
7. GPU 프로세스가 남아 있지 않은지 확인한다.
8. 다음 실행용 새 볼륨과 새 시도 ID를 생성한다.

정리 완료 조건:

~~~text
대상 Pod 0개
AND 잔여 GPU 프로세스 없음
AND 이전 cache 볼륨 없음
AND 다음 evidence 경로에 이전 marker 없음
→ 다음 시험 허용

하나라도 확인 불가
→ 다음 시험 금지
→ 아직 시작하지 않은 다음 선정 시험은 NOT_STARTED+UNKNOWN
→ 현재 RUN은 확보한 증거로 판정하며 유효한 PASS/FAIL을 사후 정리 실패만으로 지우지 않음
~~~

### 5.7 기준 버전 공격용 fixture 시험

절차:

~~~text
공격용 fixture를 /models/attack에 read-only mount
→ 비어 있는 /evidence mount
→ vLLM 0.13.0 실행
→ 실제 명령에서 trust_remote_code=false 확인
~~~

핵심 판정 증거는 표식 파일이다. 모델 로딩 실패나 로그 문자열만으로 코드 실행 여부를 추정하지 않는다.

### 5.8 기준 버전 반복성 시험

공격용 fixture 시험을 완전히 정리한 뒤 동일한 입력으로 한 번 더 수행한다.

~~~text
새 Pod
+ 새 cache
+ 새 tmp
+ 새 evidence
+ 동일 이미지 digest
+ 동일 fixture SHA-256
+ 동일 실행 명령
→ 두 번째 결과 수집
~~~

반복 실행도 선정된 TEST-MODEL-007의 추가 RUN이며 RUN·OBS·EVD·RES를 별도로 남긴다. 반복성 일치 여부를 위한 별도 TEST나 RES는 만들지 않는다. 불일치는 내부 repeatability 값과 검토 사유로 남긴다. 어느 시도라도 유효 위반이면 그 RUN의 RES FAIL을 보존하고 권고의 도착 FAIL 게이트에 포함한다. 반복 결과를 기존 RES에 덮어쓰지 않는다.

### 5.10 환경 동일성 검사

기준과 후보의 실제 Pod spec과 run-lock을 비교한다.

동일해야 하는 항목(A15 §4.2와 같은 목록):

- Namespace·GPU 노드 식별·GPU 모델·개수·할당 방식
- CPU·메모리 request/limit
- 정상 모델 ID·commit SHA·파일 목록 해시, 시험 fixture 파일 목록 해시
- 시험 요청·시험 입력 파일 SHA-256
- 엔진 실행 옵션·환경 변수(대상 역할·RUN 식별값만 허용 차이)
- 볼륨 mount 경로·읽기/쓰기 속성, SecurityContext
- 적용 NetworkPolicy 정규화 내용·해시, CNI 종류·버전·통제 준비 근거
- timeout·retry·시험 순서
- Kubernetes·호스트 NVIDIA 드라이버·호스트 CUDA 조건
- ConfirmedPolicy·EnvironmentProfile의 고정 revision, 통제 모드
- 관측 수집기·판정 규칙 버전, 필수 관측 대상·오류 집계 범위·관측 구간 정의
- 표식 계약·경로(실제 RUN·대상 식별값은 허용 차이)

허용 차이: 대상 역할·RUN/시도 식별값·실행 시각·Pod UID/IP·자동 생성 metadata, 이미지 tag/digest·vLLM 버전·이미지 내부 의존성 및 CUDA runtime. 표식 계약은 같고 표식의 RUN/대상 식별값만 달라야 한다. 실제 동작에 영향을 주는 환경 변수를 RUN 식별값이라는 이유로 제외하지 않는다.

동등성 검사에서는 API가 자동 생성한 필드만 사전 목록으로 정규화하여 제외한다. 실행 옵션·환경 변수·NetworkPolicy의 의미가 같다고 사람이 추측하지 않고 정규화 내용·hash와 원본을 함께 저장한다. 관측 구간의 절대 시각은 다르지만 구간 정의·수집 범위·시간 제한은 같아야 한다.

허용 차이 외 차이가 있으면 내부 environment_equivalence=fail, 확인 부족이면 unknown(**A1 교환 enum 아님**)이고 둘 다 CMP=INCONCLUSIVE다. 개별 RES는 바꾸지 않는다. 이미지 내 CUDA와 의존성 차이는 비교 대상이며 host 드라이버/조건과 구분한다. image-metadata에 vLLM·Python·torch·transformers·CUDA runtime·base image digest를 보존한다. base digest는 registry 최종 digest만으로 알 수 없으며 빌드 provenance 등 근거가 필요하다. 확인 못한 필수 이미지 메타데이터는 사유를 남겨 CMP INCONCLUSIVE·REC MANUAL_REVIEW로 둔다(도착 FAIL이면 BLOCKED).

## 6. 타임아웃과 재시도

### 6.1 PoC 초기 타임아웃

| 단계 | 초기값 | 시작·종료 기준 |
|---|---:|---|
| Pod scheduling | 300초 | Pod 생성부터 Scheduled |
| Image pull | 900초 | pull 시작부터 컨테이너 생성 |
| 정상 모델 startup | 1200초 | 컨테이너 시작부터 readiness |
| 정상 요청 | 60초 | 요청 전송부터 응답 완료 |
| 공격용 fixture 관찰 | 300초 | 프로세스 시작부터 종료·표식·timeout |
| 자원 정리 | 300초 | scale down부터 잔여 자원 0 |

이 숫자는 PoC 시험 설계값이다. 사전 동작 확인 시험 후 변경할 수 있지만 한 run 안에서는 변경할 수 없다.

### 6.2 재시도 가능한 경우

- 일시적인 image pull 실패
- Kubernetes API 일시 오류
- 증거 복사 중 일시적인 I/O 오류

최대 재시도 횟수는 1회다. 재시도할 때는 새 Pod·새 볼륨·새 시도 ID를 사용한다.

### 6.3 재시도하지 않는 경우

- 유효한 실행 표식이 생성됨
- 모델 로딩이 명확하게 거부됨
- vLLM 프로세스가 재현 가능한 애플리케이션 오류로 종료됨
- 정책 위반 동작이 관찰됨
- 필수 입력의 hash가 다름

보안 결과를 원하는 결과가 나올 때까지 반복해서는 안 된다.

### 6.4 결과가 서로 다른 경우

최초 시도와 재시도의 보안 결과가 다르면 더 유리한 결과를 선택하지 않는다.

~~~text
동일 조건에서 결과 불일치
→ INCONSISTENT
→ 시험 결과 UNKNOWN (단 한 시도에서라도 유효한 위반 증거가 있으면 FAIL)
→ 두 시도의 증거 모두 보존
~~~

## 7. 증거 수집과 완전성

### 7.1 수집 시점

| 시점 | 수집 증거 |
|---|---|
| 실행 전 | run-lock, 입력 hash, 적용 manifest |
| Pod 생성 직후 | Pod spec, imageID, node, events |
| 모델 로딩 중 | stdout, stderr, vLLM log |
| 시험 종료 직전 | marker 존재 여부와 내용, 프로세스 종료 코드, readiness 결과 |
| Pod 삭제 전 | 최종 logs, describe 결과, events |
| 정리 후 | 잔여 자원 검사 결과 |

수집 sidecar가 실행별 볼륨에 접근하는 구성은 **[가정]** smoke에서 검증할 대상이다. read-only 모델 mount·엔진의 API token 미주입·수집기의 최소 권한을 지킨다. 종료한 Pod 안 emptyDir만 증거의 유일한 사본으로 두지 않는다. 파일 수집 시각·inode/mtime은 보조 정보이며 RUN별 볼륨 생성·연속 관측·원본 수집 귀속을 함께 검증한다. 로그/표식이 평가 대상 프로세스에서 만들어질 수 있다는 출처 한계도 남긴다.

### 7.2 표식 판독

**범용 실행 계약:** namespace·증거 루트·표식 계약·내부 사례 ID는 A17 §4.4 실행 바인딩에서 읽는다. 아래 22807 전용 문자열·경로는 첫 팩의 예시이며 필수 상수가 아니다. 코어는 팩 ID 또는 CVE로 분기하지 않는다.

표식은 다음 조건을 모두 만족할 때만 유효하다.

- 정확한 경로에 존재
- marker_id가 CVE-2026-22807-AUTO-MAP-EXECUTED
- target이 현재 실행 대상과 일치
- trust_remote_code가 false
- 파일 생성 시각이 현재 시도 시간 범위 안에 있음
- 파일 SHA-256이 evidence-manifest에 기록됨

오래된 표식, 다른 시도의 표식, 손상된 JSON은 코드 실행 증거로 사용하지 않는다.

### 7.3 증거 완전성

필수 증거 중 하나라도 누락되면 evidence_completeness는 incomplete다.

특히 다음 해당 RUN의 필수 판정 증거 누락은 PASS 확정을 막는다. 확보한 위반이 없으면 UNKNOWN이다. **단 유효한 위반 증거(실행 표식 등)가 이미 있으면 누락이 있어도 FAIL을 유지한다** (A1 불변식 10).

- 실제 vLLM 버전 또는 image digest
- 실제 실행 명령
- trust_remote_code 값
- fixture SHA-256
- marker 존재 여부 검사 결과
- vLLM 로그
- 해당 RUN 관측 구간·수집 상태

기준·후보 동일성 검사 누락은 개별 보안 판정을 변경하지 않고 CMP를 INCONCLUSIVE로 만든다.

#### 8.1.1 FUNC 응답 검증 요약 (D43)

**D44 최소 보존:** 응답 본문은 메모리에서 고정 validator로 검사하고 보존하지 않는다. 현재 판정에 응답 본문·본문 해시의 보존 필요성이 없으므로 합성 응답을 포함해 둘 다 계산/저장하지 않는다. 검사에 필요한 응답 bytes만 일시 처리하며 로그·오류·진단·보고서·감사에도 본문/본문 해시를 복사하지 않는다(A13 §8). 신규 EVD 파일 `response-validation.json`은 `{format:"guard-func-response-summary/1",run_ref:Ref,request_fixture:{pack_id:string,pack_revision:int≥1,path:string,sha256:SHA},validator_version:string,received:boolean,content_length:int≥0|null,format_valid:boolean|null,valid_response_count:int≥0,error_count:int≥0,validation_reason:string}`이다. 모든 키 필수·추가 키 금지이며 body_sha256·response_body는 허용하지 않는다. format은 내부 요약 파일 식별자이고 교환 EVD schema_version·승인 domain 변경이 아니다. request_fixture는 A17 Binding.materials의 팩 revision·상대 path·bytes SHA 잠금이며 별도 교환 객체 Ref가 아니다. 동일 role/path의 검증된 자료만 사용한다. 무응답은 received=false·length/format_valid=null·valid_count=0·사유 필수다. 요약의 사유는 오류 분류/사실만 쓰고 실제 응답 조각을 인용하지 않는다. 요약 파일 자체의 EVD SHA는 저장된 안전한 요약 bytes의 해시로 유지한다. 향후 원문이 꼭 필요한 검증은 필요성·범위·보존 계약을 별도 설계하기 전까지 허용하지 않는다. 기존 요약·EVD·서명 bytes는 덮어쓰거나 현행 형식으로 자동 변환하지 않는다. 과거 형식은 잠긴 parser의 읽기 지원 여부를 확인하고 미지원이면 근거 부족으로 처리한다.

functional.responses는 이 요약에서 count·validator·사유를 추출한다. 오류 수의 기존 집계 범위는 바꾸지 않는다. 해시는 응답 의미의 증명이 아니다. 같은 보존 사실을 이용하는 정책 재판정은 새 RES로 가능하지만 새 응답 validator로 원문을 재검사하려면 새 RUN이 필요하다. 요약에 보존되지 않은 의미를 추정하지 않는다.

엔진과 다른 전용 부하 노드의 Pod에서 합성 입력만 보낸다. 클라이언트·토크나이저·자원·응답 검증기 버전을 RUN에 고정한다. 지표는 **ICL(inter-chunk latency, 내용 청크 간 지연)**을 사용한다. 토큰 간 지연(ITL)으로 표시하거나 기존 ITL 기준을 자동 변환하지 않는다. 기존 정책은 새 ICL 기준을 사람이 명시한 새 revision으로 입력한다.

**응답 검증 계약 `openai_response/2`:** 프로필에 `stream:boolean`을 필수로 둔다. endpoint와 stream의 네 조합을 별도 validator로 등록한다. HTTP 2xx만 성공 후보이며 오류 envelope·연결 오류·timeout·형식 오류를 분리한다. completions 비스트림은 choices[0].text, chat 비스트림은 choices[0].message.content 문자열을 확인한다. 1차는 n=1·텍스트 출력만 지원하며 도구 호출·복수 choice는 프로필 단계에서 거부한다. stream=true는 UTF-8 SSE frame을 먼저 조립하고 TCP 수신 조각을 청크로 세지 않는다. completions의 choices[0].text, chat의 choices[0].delta.content가 비어 있지 않을 때만 내용 청크다. role-only·빈 delta·usage-only frame은 지연 표본에서 제외하되 정상 메타데이터로 허용한다. 해당 choice의 finish_reason과 정상 종료 `[DONE]`을 모두 확인한다. 종료 누락·중간 오류는 실패다. usage-only의 choices=[]는 허용한다. 비스트림에서 TTFT/ICL은 null이고 해당 기준이 있으면 입력 계약 오류다. 정상 종료됐으나 내용 청크가 없는 응답은 형식 오류다.

**측정:** 단조 시계 nanoseconds로 송신 직전 t0, 각 내용 청크 ti, 정상 종료 te를 기록한다. TTFT=(t1−t0)/1e6 ms, ICL 표본=(ti−t(i−1))/1e6 ms(i≥2), e2e=(te−t0)/1e6 ms. 첫 내용은 첫 토큰으로 단정하지 않는다. 하나의 청크뿐이면 ICL 표본은 없으며 필요한 ICL은 null이다. 생성 토큰 수는 프로필에 `token_count_source: usage|tokenizer`를 필수로 고정한다. usage는 정상 종료 usage.completion_tokens 정수≥0를 사용하고 누락이면 null, tokenizer는 전체 생성 텍스트를 메모리에서 고정 토크나이저로 인코딩한 개수다. 청크별 토큰 수를 합산하지 않는다. 한 RUN 안에서 출처를 바꾸지 않는다. 본문은 저장하지 않는다.

**원시 JSONL:** 파일 첫 행은 `{kind:"header",schema_version:"2.0",profile_ref,profile_sha256,client_version,validator_version,tokenizer_sha256,token_count_source,concurrency,rep,measure_start_ns,issue_end_ns,measure_end_ns}`다. 요청 행은 `{kind:"request",request_id,issued_ns,content_chunk_ns:int[],end_ns:int|null,http_status:int|null,status:OK|HTTP_ERROR|API_ERROR|TIMEOUT|FORMAT_ERROR|TRANSPORT_ERROR,error_code:string|null,output_tokens:int|null}`로 고정한다. 요청 ID는 반복 안에서 유일하다. 발행 마감 전에 송신한 요청은 timeout까지 drain하고 모두 최종 상태를 기록한다. measure_end_ns는 마지막 요청 종료/drain 시각이며 예열 요청은 포함하지 않는다. HTTP body·입력 원문·헤더는 기록하지 않는다. 파일 해시·행 수·파서 버전을 EVD 및 RUN 관측 계약으로 잠근다.

#### 8.6.3 관측 subject·집계

| OBS.subject | observed_value 타입 |
| --- | --- |
| `perf.profile` | `{profile_ref:Ref,profile_sha256:SHA,client_version:string,validator_version:string,tokenizer_sha256:SHA,token_count_source:usage\|tokenizer,stream:boolean,load_pod_resources:{cpu:string,memory:string}}` |
| `perf.metrics` | `{levels:[{concurrency:int≥1,reps:[{request_count:int≥0,error_count:int≥0,ttft_p50_ms:number\|null,ttft_p95_ms:number\|null,icl_p50_ms:number\|null,icl_p95_ms:number\|null,e2e_p95_ms:number\|null,output_tokens_per_s:number\|null}],median:{ttft_p95_ms:number\|null,icl_p95_ms:number\|null,output_tokens_per_s:number\|null,error_rate:number\|null}}]}` |
| `perf.stability` | `{levels:[{concurrency:int≥1,cv_ttft_p95:number\|null,cv_icl_p95:number\|null,cv_throughput:number\|null}],max_cv:number}` |

집계 규칙:
- 지연 표본은 정상 종료한 요청만 사용한다. ICL은 모든 성공 요청의 내용 청크 간격을 모은다. 분위수는 오름차순 x의 nearest-rank, p분위=x[ceil(p*n)-1]이다. 빈 표본은 null, 짝수 개의 중앙값은 가운데 두 값의 산술평균이다.
- 각 단계 대표 지연은 반복별 p95의 중앙값이다. 처리량은 반복별 성공 요청 output_tokens 합 / ((measure_end_ns−measure_start_ns)/1e9)이며 대표값은 반복 중앙값이다. 필요한 토큰 수 누락·시간 구간 오류는 null이다.
- error_rate는 전체 반복 error_count 합/request_count 합이다. 분모 0은 null, error_count≤request_count다. CV는 반복값의 모집단 표준편차/산술평균이다. 평균 0이고 모든 값이 0이면 CV=0, 그 밖의 계산 불가는 null이다. 지연·처리량·CV는 유한한 비음수, error_rate는 0..1이다. 필수 반복의 null을 제거해 합격시키지 않는다.
- 저장은 IEEE-754 binary64, 표시는 별도 반올림이며 판정은 반올림 전 값으로 한다. PF10 재계산 허용오차는 max(1e-9, abs(expected)*1e-9), 개수·타임스탬프·해시는 정확히 일치한다.
- 원시 파일·관측 구간이 완전하지 않으면 오류율의 분모도 불확실하므로 그 오류율을 유효 FAIL로 쓰지 않는다. 완전한 오류율의 기준 초과는 다른 지연 지표 누락·불안정보다 우선한다.

**최소 집계 예:** 정상 내용 청크 시각이 t0+10ms, t0+30ms, t0+50ms이면 TTFT=10ms, ICL 표본=[20,20]ms다. 한 청크에 여러 토큰이 포함돼도 ICL=20ms를 토큰 지연으로 나누지 않는다. 반복 p95가 [10,20,30]ms이면 대표값=20ms, 모집단 CV=√(200/3)/20이다. 이 예시는 EXAMPLE 산식 확인용이며 엔진 실측이 아니다.

#### 8.6.4 실행 위치와 순서

- 격리 실행(S5)에서 정상 모델 smoke 통과 후(선정된 FUNC RUN이 있으면 그 다음), 같은 노드·같은 정상 모델로 PERF RUN을 따로 만든다. MODEL-007 fixture와 섞지 않는다.

등록 subject `apigw.health`의 observed_value는 `{gateway_workload_uid:string,runtime_policy_ref:Ref,bundle_sha256:SHA,covered_window:Window,intervals:[{window:Window,status:GatewayHealth}]≥1,producer_version:string}`이다. GatewayHealth는 A6 §6.4의 값만 사용한다. 추가 키 금지. T3 gateway 수집기가 같은 RUN/UID/RTP/bundle의 상태 변화·heartbeat·수집 연결을 EVD에 봉인하고 OBS를 생산한다. ## 9. 방향별 비교·권고와 단위 테스트 표

### 9.1 Comparison 기본 결정표(9개 판정 조합)

아래 baseline/candidate는 **비교 방향의 출발/도착**이다. 먼저 환경 동일성·필수 메타데이터를 검증한다. 다르거나 미확인이라면 모든 조합에서 INCONCLUSIVE, 개별 RES는 보존한다.

| 출발 RES | 도착 PASS | 도착 FAIL | 도착 UNKNOWN |
| --- | --- | --- | --- |
| PASS | NO_CHANGE | REGRESSION | INCONCLUSIVE |
| FAIL | FIXED | EXISTING_FAILURE | INCONCLUSIVE |
| UNKNOWN | INCONCLUSIVE | INCONCLUSIVE | INCONCLUSIVE |

PASS→PASS에서 별도 승인된 동작 동등성 기준의 유효 변화 근거가 있을 때만 BEHAVIOR_CHANGED를 쓸 수 있다(§3.3.6). 1차는 응답 품질의 별도 동등성 기준이 없고 성능 변화율만으로 BEHAVIOR_CHANGED를 만들지 않으므로 자동 발행하지 않는다. UNKNOWN이 하나라도 있으면 INCONCLUSIVE다. 이 결정표는 보안과 기능에 같은 방식으로 적용한다. FUNC FIXED면 기준 실패 원인·환경 근거를 이유에 기록한다.

### 9.2 권고 우선순위와 범위 게이트

검증 오류(잘못된 enum·참조·방향·이미지 혼합·TEST/조건 대응 오류)는 권고로 보정하지 않고 오류로 반환한다. 유효 입력을 받은 뒤 다음 순서다.

1. **도착 버전의 유효 FAIL이 하나라도 있으면 BLOCKED.** 선정 시험의 어떤 조건·시도에서든 확인한 위반은 비교가 INCONCLUSIVE여도 유지한다. 무결성이 깨진 그 근거만 제외한다. 이 게이트는 아래 36칸보다 우선한다.
2. 필수 격리 비교를 모은다. 여러 조건이면 각 조건의 CMP·RES를 보존한다. MODEL/FUNC 축의 대표 비교는 REGRESSION > EXISTING_FAILURE > INCONCLUSIVE > BEHAVIOR_CHANGED > FIXED > NO_CHANGE 순서로 정한다(내부 집계 우선순위, **A1 교환 enum을 새로 만들지 않음**). 하나의 FIXED로 다른 조건의 불명·실패를 숨기지 않는다.
3. 아래 36칸으로 기본 권고를 정한다.
4. BLOCKED가 아니라면 미검증(모든 필수 SYS/PERF CMP의 INCONCLUSIVE 포함)/null·EXAMPLE·필수 격리 비교 누락·변경 영향 UNKNOWN·등록 근거/필수 이미지 메타데이터 미확정·필수 모델 시험 미선정에 따른 CVE 수정 효과 범위 부재는 MANUAL_REVIEW다. 1차 ELIGIBLE은 해당 범위의 ENGINE/MEASURED 근거, 모든 필수 격리 시험의 도착 버전 완결된 PASS 조건과 수정 효과를 확인한 경우만 가능하다. 보안 영향 NOT_APPLICABLE이면 FUNC만 실행할 수 있지만 CVE 수정 효과 권고는 MANUAL_REVIEW로 남긴다.
5. REC에는 선정된 격리 범위·미선정 사유·DEFERRED·이미지 전체 효과·잔존 CVE의 기록 전용 한계를 적는다. S7은 별도 릴리스 검토 항목이다. ELIGIBLE로 자동 배포·롤백하지 않는다.

추가 범위 게이트: 적용·비면제 요구가 기능 비활성/미구현으로 미선정되어도 필수 검증 gap은 남는다. 해당 요구의 누락·UNKNOWN·INCONCLUSIVE는 MANUAL_REVIEW 및 A12 RELEASE PENDING이다. SYS/PERF가 모두 PASS여도 MODEL/FUNC 기본 권고의 BLOCKED·MANUAL_REVIEW를 승격하지 않는다. `REC-SYS-GAP`, `REC-PERF-GAP`, `REC-DISABLED-GAP`은 독립 단위 사례 ID로 등록하며 MODEL/FUNC 기본 ELIGIBLE 입력에 각 gap을 추가했을 때 MANUAL_REVIEW를 기대한다. 도착 유효 FAIL을 함께 주면 BLOCKED가 우선한다.

### 9.3 전체 비교값 조합 36개

각 칸은 **앞선 도착 FAIL·범위 게이트가 없고, 방향·버전·근거가 유효한 경우의 기본 기대값**이다. 단위 테스트는 `direction∈{UPDATE,ROLLBACK}` 두 값으로 각 36개를 실행한다. 비교 enum은 이미 방향을 반영하므로 같은 칸은 두 방향에서 같은 REC verdict다. BEHAVIOR_CHANGED는 정책 통과 외 동작 변화의 수동 검토다.

| MODEL 비교 \ FUNC 비교 | NO_CHANGE | REGRESSION | FIXED | EXISTING_FAILURE | BEHAVIOR_CHANGED | INCONCLUSIVE |
| --- | --- | --- | --- | --- | --- | --- |
| NO_CHANGE | MANUAL_REVIEW | BLOCKED | MANUAL_REVIEW | BLOCKED | MANUAL_REVIEW | MANUAL_REVIEW |
| REGRESSION | BLOCKED | BLOCKED | BLOCKED | BLOCKED | BLOCKED | BLOCKED |
| FIXED | ELIGIBLE | BLOCKED | ELIGIBLE | BLOCKED | MANUAL_REVIEW | MANUAL_REVIEW |
| EXISTING_FAILURE | BLOCKED | BLOCKED | BLOCKED | BLOCKED | BLOCKED | BLOCKED |
| BEHAVIOR_CHANGED | MANUAL_REVIEW | BLOCKED | MANUAL_REVIEW | BLOCKED | MANUAL_REVIEW | MANUAL_REVIEW |
| INCONCLUSIVE | MANUAL_REVIEW | BLOCKED | MANUAL_REVIEW | BLOCKED | MANUAL_REVIEW | MANUAL_REVIEW |

### 9.4 게이트 단위 테스트 입력

아래는 규칙 검토용 EXAMPLE 입력이며 MEASURED 객체를 만들지 않는다.

| ID | 입력·추가 조건 | 기대 |
| --- | --- | --- |
| G1 | MODEL INCONCLUSIVE, FUNC NO_CHANGE, 도착 MODEL 유효 FAIL | BLOCKED, CMP는 INCONCLUSIVE·RES FAIL 보존 |
| G2 | MODEL FIXED, FUNC NO_CHANGE, 필수 RES 출처 중 하나 null | MANUAL_REVIEW, 대표 verification_level/data_origin null, 근거 배열 null 보존 |
| G3 | MODEL FIXED, FUNC FIXED, 근거 하나 EXAMPLE | MANUAL_REVIEW, 대표 data_origin EXAMPLE |
| G4 | MODEL NO_CHANGE, FUNC NO_CHANGE, 모든 ENGINE/MEASURED | MANUAL_REVIEW; 수정 효과 미재현 |
| G5 | MODEL FIXED, FUNC BEHAVIOR_CHANGED, 도착 FAIL 없음 | MANUAL_REVIEW |
| G6 | MODEL FIXED, FUNC NO_CHANGE, 이미지 외 조건 다름 | 두 해당 CMP INCONCLUSIVE, 도착 FAIL 없으면 MANUAL_REVIEW |
| G7 | PLAN MODEL 미선정/FUNC 선정, FUNC PASS→PASS | MODEL RES/CMP 없음; FUNC 근거 REC MANUAL_REVIEW, 범위 제한 이유 |
| G8 | MODEL 선정 후 미실행 | NOT_STARTED RUN, UNKNOWN RES, 출처 두 값 null, CMP INCONCLUSIVE |
| G9 | 면제 근거로 사용한 예외의 승인/기간 무효 또는 확정 입력/승인 revision 불일치 | 무효 면제 적용 금지·재평가; 불일치 입력은 새 승인 없이 CONFIRMED로 승격 금지. 이미 유효 선정된 미실행은 NOT_STARTED+UNKNOWN |
| G10 | CMP.direction 또는 대상 digest 혼합 | 위치를 담은 검증 오류, REC 미생성 |
| G11 | 유효 위반 EVD와 손상된 다른 EVD 공존 | 손상 EVD만 제외, RES FAIL·도착이면 REC BLOCKED |
| G12 | NODE 격리 미확보 | MODEL NOT_STARTED+UNKNOWN, namespace로 대체 실행 금지 |

### 9.5 UPDATE·ROLLBACK 기대 사례

**[가정] 실측 전 목표:** 0.13.0 MODEL FAIL·FUNC PASS, 0.14.0 MODEL PASS·FUNC PASS, 동일 조건, 필수 근거 모두 ENGINE/MEASURED·유효.

| direction | baseline_result_ref가 가리키는 출발 | candidate_result_ref가 가리키는 도착 | MODEL/FUNC CMP | REC |
| --- | --- | --- | --- | --- |
| UPDATE | 0.13.0 원본 RES | 0.14.0 원본 RES | FIXED / NO_CHANGE | ELIGIBLE |
| ROLLBACK | 0.14.0 원본 RES | 0.13.0 원본 RES | REGRESSION / NO_CHANGE | BLOCKED |

원본 RES·RUN.role을 변경하지 않고 새 CMP·REC를 생성한다. 위 목표와 다른 실제 결과도 그대로 보고한다. 조건 불일치 시 양쪽 CMP는 INCONCLUSIVE이고 UPDATE는 도착 유효 FAIL이 없으면 MANUAL_REVIEW, ROLLBACK은 도착(0.13.0) 유효 FAIL 때문에 BLOCKED다.

## 10. UNKNOWN과 실행 실패의 구분

### 10.1 시험 시작 전 실패

다음은 실행 자체를 시작하지 않은 상태다. 실패 코드(내부 축)와 함께 `RunManifest.execution_status=NOT_STARTED`를 남기고, **선정된 시험이면 TestResult를 UNKNOWN + 사유로 만든다**(A1 불변식 12). 미선정 시험은 결과를 만들지 않는다.

- INPUT_INVALID
- TEST_NOT_IMPLEMENTED (A4 선정 단계에서 걸러져야 하며, `TestPlan.not_selected_tests`에 "시험 미구현"으로 기록)
- PRECONDITION_FAILED
- ENVIRONMENT_UNAVAILABLE

### 10.2 실행 후 처리 범위

아래는 처리 사유 목록이며 모든 사유가 현재 RUN을 UNKNOWN으로 바꾸는 것은 아니다. 해당 RUN 판정 부족·다음 실행 미시작·CMP 불명확을 구분한다.

- 필수 증거 누락
- 해당 RUN의 필수 조건 미확인(비교 조건 불일치는 CMP INCONCLUSIVE)
- 표식 판독 실패
- 인프라 오류와 애플리케이션 오류 구분 불가
- 재시도 결과 불일치
- 정리 완료 여부 확인 불가로 다음 시험 미시작(현재 유효 판정 보존)
- 정상 모델 동작 확인 실패로 공격용 결과 해석 불가

실행 실패와 보안 FAIL을 하나의 상태로 합치지 않는다. 위 사유가 있어도 이미 확보한 유효한 위반 증거는 FAIL로 유지한다.

## 12. 개발 기능 분리

고정된 클래스명이나 모듈명을 강제하지는 않지만 다음 기능은 분리해 구현한다.

1. 입력 검증
   - A4·A15 스키마와 시험 등록 상태 확인
2. 실행 잠금
   - digest·revision·hash 수집 및 run-lock 생성
3. 환경 관리
   - Namespace·Pod·볼륨·NetworkPolicy 생성과 정리
4. 시험 실행
   - 정상 모델·공격용 fixture·반복 시험 수행
5. 증거 수집
   - 로그·표식·Pod 정보·hash 저장
6. 조건 비교
   - 기준·후보 환경의 허용 차이와 비허용 차이 판별
7. 판정
   - 시험별 결과, 버전 비교, 업데이트 결정 생성

Agent가 PASS·FAIL을 자유롭게 판단하지 않는다. 판정은 이 문서의 결정표를 일반 코드로 구현한다. Agent는 로그 요약이나 UNKNOWN 원인 설명을 보조할 수 있지만 원본 증거와 결정표를 변경할 수 없다.

## 13. 구현 의사코드

```python
def execute_isolated_comparison(bundle, environment_spec):
    selected = validate_schema_refs_and_resolve_isolated_tests(bundle)  # A4 §11
    manifests = allocate_not_started_runs(selected, each_version=True)
    try:
        validate_policy_approval_exception_and_execution_gates(bundle)
        lock = collect_and_validate_preflight(environment_spec)
        enforce_node_isolation_for_model(lock)
        for target in ("baseline", "candidate"):
            for requirement in selected:
                run = start_new_run(manifests, target, requirement, lock)
                collect_observations_and_evidence(run)
                result = decide_by_a7_valid_evidence_first(run)  # 유효 FAIL 최우선
                persist_immutable_result(result)
                export_evidence_before_deleting_pod(run)
                if not cleanup_verified(run):
                    stop_remaining_runs("cleanup incomplete")
                    break
            if remaining_runs_stopped():
                break
    except PreflightOrInfrastructureError as exc:
        record_failure_reason(exc)  # 코드로 PASS/FAIL 자동 치환 금지
    finally:
        finalize_started_runs_preserving_valid_verdicts()
        emit_unknown_for_selected_not_started_runs(manifests)
        export_available_evidence_then_cleanup_exact_owned_resources()
    comparisons = compare_each_required_condition_and_direction()
    return recommend_with_destination_fail_priority(comparisons)
```

초기 입력 구문·스키마·참조 검증 오류는 유효 PLAN을 해석할 수 없으므로 공식 객체를 만들지 않고 오류 응답한다. 반면 해석 가능한 기존 PLAN의 정책·예외 상태가 바뀌어 실행 게이트에서 막히면 선정 목록을 지우지 않고 NOT_STARTED+UNKNOWN과 재평가 사유를 남긴다. 유효 선정 목록 확보 후 preflight 실패부터는 미실행 결과를 보존한다. finally는 수집 실패를 기록하고, 보존 시도 없이 볼륨을 지우지 않는다. 삭제 권한·허용 Namespace·RUN 소유 label을 확인한다. 재판정은 새 RES이며 기존 결과를 덮어쓰지 않는다.

## 14. 개발 완료 기준

다음 조건을 모두 만족하면 A5 구현이 완료된 것으로 본다.

- A4·A15 입력을 검증하고 누락 시 실행을 차단한다.
- 기준과 후보를 동시에 실행하지 않는다.
- 각 시험이 새 Pod·새 cache·새 evidence 경로에서 실행된다.
- 정상 모델·공격용 fixture·반복성 시험이 모두 구현돼 있다.
- 필수 증거를 Pod 삭제 전에 보존한다.
- 기준·후보 환경 동일성을 자동 비교한다.
- 인프라 실패와 보안 FAIL을 구분한다.
- PASS·FAIL·UNKNOWN 결정표가 일반 코드로 구현돼 있다.
- 기준 FAIL·후보 PASS·정상 기능 유지 시 UPDATE는 ELIGIBLE, ROLLBACK은 BLOCKED가 나온다.
- 기준 PASS·후보 FAIL이면 BLOCKED가 나온다.
- 증거 누락이나 환경 차이가 있으면 MANUAL_REVIEW가 나온다. 단 후보의 확인된 FAIL이 있으면 BLOCKED다.
- 분석→정책→요구사항→시험→증거→판정 추적 관계가 report에 남는다.
- 정리 단계가 정확한 run ID의 자원만 대상으로 한다.
- 격리 실행의 필수 관측과 통제 준비를 검증한다. S7 런타임은 별도 인수하며 §3.4 합의 전 완료로 표시하지 않는다.

## 15. 승인 전 유효성 재확인과 인수 보류

T2는 판정 근거 POL·ENV·TEST·PLAN 및 승인 대상 revision 목록을 A12에 넘긴다. 릴리스 승인 직전 정책 revision 변경·예외 만료/철회·환경 변경이 있으면 재평가한다. 기존 증거로 새 조건을 다루면 새 RES/CMP/REC로 재판정하고 이전 고정 참조를 보존한다. 증거가 부족하면 새 RUN으로 재시험한다. Approval이 잠근 입력 revision과 확정 입력 revision이 다르면 재승인 없이는 확정·릴리스 진행하지 않는다. A12/A13 승인 검증 자체는 T3 소유다.

NET 발행 계약은 §3.4로 확정했다(D27). **[결정 필요]** 실제 전용 GPU 노드 할당, 경로·거부 parser 근거, 이미지 내부 및 base image provenance 확보가 남아 있다. 문서 구체화 완료와 실측 준비 완료·정책/릴리스 승인은 다른 상태다.
