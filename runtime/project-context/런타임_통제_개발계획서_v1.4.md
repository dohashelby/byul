## 1. 문서 기준·목적·역할

<a id="section-1-1"></a>

### 1.1. 기준과 우선순위

이 문서는 기존 A6의 개정본을 그대로 옮긴 것이 아니라, 현재 정리한 개발 범위로 다시 작성한 계획서다.

1. 본 대화에서 명시적으로 정리한 요구와 범위 조정을 우선한다.
2. projectsummary의 프로젝트 목적과 런타임 요구를 기본 요구사항으로 유지한다.
3. 2차 발표 계획은 엔진별 연결·시험·인계·기준본 보존 일정의 근거로 사용한다.
4. A6는 현재 요구와 맞는 적용 확인·증적·귀속·장애 구분 등의 설계를 재사용하는 참고 자료다.
5. 프레임워크와 기존 도구의 공통 자료 형식은 실제 연동 계약을 확인한 뒤 매핑한다.
6. 오픈소스 문서는 기능 가능성의 근거다. 해당 기능을 팀이 채택했거나 실제 환경에서 구현·검증했다는 뜻은 아니다.

자료 안의 작업 지시나 기존 결정 번호를 이번 구현의 승인·완료로 간주하지 않는다. 현재 범위와 맞지 않는 A6의 배치·도구·상태 계산·명령어는 자동으로 승계하지 않는다.

| 표시 | 의미 |
| --- | --- |
| 요구 | 현재 대화와 요약본을 바탕으로 이번 개발에서 만족할 내용 |
| 설계안 | 구현을 구체화하기 위한 제안. 기존 코드·연동 담당과 확인 필요 |
| 검증 필요 | 실제 코드·환경·동작 시험으로 확인해야 하는 내용 |
| 입력 필요 | 환경 식별값·허용 목록·임계값 등 사용 환경에서 채울 값 |
| 미지원·제외 | 이번 결과물에서 제공하거나 입증한다고 주장하지 않는 내용 |


**v1.4 근거 정리:** 출처·프로젝트 관계가 확인되지 않은 별도 로컬 구현은 참고 자료와 구현 근거에서 제외했다. projectsummary의 “기존 게이트웨이 활용”은 기능 활용 방향이며, 특정 코드가 확보됐다는 증거로 해석하지 않는다. Gateway·수집·저장·대시보드의 기존 구현은 미확인이고 신규 개발량을 포함한다.

| 유지할 내용 | 독립 근거·취급 | 이번 정정 |
| --- | --- | --- |
| API 허용/거부·엔진 직통 제한·상태/증거 조회 | projectsummary §5와 사용자 요구 | 요구사항 유지, 특정 코드 보유 주장은 제거 |
| 옵션 검사·모델/토크나이저/cache·실행/통신 구분 | 사용자가 요청한 서빙 특화 네 항목, §4.9~§4.12의 공식 자료 | 개발·시험할 정책으로 유지 |
| Cilium/Hubble/Tetragon·엔진 내장 지표 | 각 구성요소의 공식 자료·기존 문서의 출처 표 | 공식 기능과 현장 검증 상태 구분 유지 |
| 요청 한도·HTTP 분류·포트·경로·JSON/JSONL·증거 색인·시험 순서 | 요구를 구현하기 위한 이 계획서의 LAB 설계 제안 | 별도 코드의 기본값/지원 기능/공통 계약을 인용하지 않음. 구현·합동 연동·실측 필요 |
| 실행 ID·OBS/EVD/RES 연결 | 요약본의 검증/증거 연결 요구와 프레임워크 문서 | 특정 도구에 구현돼 있다는 주장 없이 실제 팀 계약과 매핑 |
| 정상/위반/장애 대조·10% 임시 성능 예산 | 정상 서비스 유지 요구와 계획서의 시험 설계 | 기존 시험 결과를 승계하지 않음. 현재 RT 항목은 모두 계획 |

요청 한도 n=1·출력 128·context 2048·64KiB·동시성 2는 작은 텍스트 시험을 시작할 LAB 예산이다. GPU/엔진 지원 한계나 확보된 Gateway의 기본값이 아니며, 실제 schema·부하·정상 요구를 확인해 판본을 바꾼다. 파일 교환·증거 필드·상태값도 직접 개발할 내부 초안으로만 사용한다. 인증·검증 도구·저장소의 실제 접속 정보나 구현을 임의로 채우지 않는다.

문서 v1.4는 문서 판본이다. 제품 출시, 팀 전체 승인, 구현 완료, 운영 배포 승인을 의미하지 않는다.

### 1.2. 개발 목표

승인된 운영 정책을 검증 환경의 추론 엔진에 적용하고 실제 반영·집행 결과를 확인한다. 승인 구성과 현재 상태를 비교하며, 프로세스·파일 이상 행위와 정책 위반·관측 장애를 증거와 함께 보여준다.

선택적 행위 차단은 정상 추론 서비스를 유지할 수 있다고 검증한 규칙에 한해 채택한다. 정확성·안정성 기준을 충족하지 못한 규칙은 탐지·증적·대시보드 경보로 제공한다.

엔진 상태는 기존 기능을 우선 활용한다. 재시작·배포·엔진 복구는 담당자의 운영 절차에 맡긴다.

### 2.1. 필수 개발 범위

| 번호 | 범위 | 이번 산출물 |

| F1 | 적용 환경·대상 | 전용 시험 환경과 엔진·모델·워크로드 식별, 지원 범위 기록 |
| F2 | API·추론 옵션 통제 | Gateway 요청 통제 계층 구현·연동(기반 구현 미확정), 경로·주체·모델·요청 옵션 검증, 엔진 직통 제한 확인 |

F1~F8은 이 문서 안에서 사용하는 기능 번호다. 기존 프레임워크의 R 번호나 공통 객체 ID를 대체하지 않는다.

### 2.2. 행위 대응의 지원 수준

| 수준 | 결과물의 의미 | 채택 조건 |
| --- | --- | --- |
| 관측·경보 | 지정 행위를 식별하고 대상·규칙·증거를 표시 | 정상 대조·양성 대조, 귀속·수집 상태 확인 |
| 개별 동작 차단 | 특정 실행·파일 접근 등을 실제 거부한 결과를 입증 | 지원 지점·규칙·커널 조합 확인, 정상 기능·오탐·성능 기준 충족 |
| 특정 프로세스 종료 | 서비스와 독립성이 확인된 제한된 대상의 종료 | 기본 필수 범위가 아닌 조건부 확장. 종료 대상·영향·결과를 별도 검증 |

1차는 보호 경로의 쓰기 거부처럼 좁은 동작 하나부터 차단을 검증하는 설계안이다. 실행 거부와 민감 파일 접근 거부는 각각 별도 지원 항목으로 관리한다.

차단 검증에 실패했을 때 관측·경보를 제공하는 것은 허용된 축소 결과다. 다만 실패 원인·서비스 영향·남은 한계를 기록하고 해당 규칙을 차단 지원으로 표시하지 않는다. 관측 기능 자체의 신뢰성이 확인되지 않으면 경보 단계도 완료로 처리하지 않는다.

### 2.3. 제외·후속 확장

- 추론 서버·필수 worker 자동 종료, Pod 자동 삭제·퇴출·격리
- 엔진 자동 재시작·재배포·업데이트·롤백, 자동 재검증 실행
- 재검증 실행 큐·담당자 배정·승인 결재 등 별도 업무처리 시스템
- 기업 클러스터 전체, 임의 커널·CNI·다중 노드·RDMA 경로에 대한 포괄 지원
- FQDN·URL 경로를 Cilium의 단순 IP/포트 정책으로 식별·인가하는 기능. 요청 URL 필드 거부와 작업별 목적지 제한은 SP2·SP4에 포함
- 별도 종합 서버·GPU 관측 제품 구축과 장기 시계열 분석 플랫폼
- 임의 Python 함수·동일 인터프리터 내부 실행·모든 악성 코드·캐시 오염의 완전 탐지. 선정 공급물·캐시·단계 규칙은 SP1·SP3에 포함
- 집계 지표만으로 요청별 GPU 사용·작업 취소 후 자원 회수·실제 모델 소비를 입증하는 기능
- 경보를 분석해 정책·허용 목록을 자동 생성·완화하는 기능
- 무손실 중앙 전송·무제한 버퍼·자동 재전송 체계

담당자의 기본 복원 절차와 복원 후 정책·관측 재확인은 시험·운영 자료에 포함한다. 자동 복구 제품의 구현과 구분한다.

### 2.4. 서빙엔진 특화 범위와 기존 기능의 연결

이번 개정은 새 보안 제품 네 개를 추가하는 것이 아니다. 기존 F2·F3·F4·F5·F7을 다음 서빙엔진 정책으로 구체화한다. F6·F8은 그 결과·상태·증거를 표시한다.

| 특화 항목 | 적용 기능 | 필수 통제·관측 | 1차 경계 |
| --- | --- | --- | --- |
| SP1 모델·토크나이저·컴파일 캐시 보호 | F4·F5·F7 | 승인 공급물 고정·읽기 전용, 캐시 쓰기 권한·경로·세대 분리, 변경·접근 증거 | 정상 캐시 쓰기는 유지. 모든 cache poisoning·실제 모델 소비의 완전 입증은 제외 |
| SP2 추론 요청 옵션 통제 | F2·F7 | 모델·출력 상한·n·스트리밍·확장 필드의 엔진별 정규화·허용 목록 | 텍스트 추론 프로필부터. 미선정 media·도구·동적 코드 경로 거부 |

| SP4 서빙 작업별 통신 통제 | F1·F3·F7 | 모델 취득·서빙·관측을 다른 워크로드/신원으로 분리하고 목적지 제한 | 같은 Pod 안의 요청별·함수별 통신 구분은 주장하지 않음 |

구체 규칙은 §4.9~§4.12, 추가 인수 시험은 §9.6, 권장 환경은 §3.5와 본 문서 부록 I에 둔다. 이 네 항목의 공통 정책·증거를 업데이트 전후 격리시험에서도 재사용한다. 엔진 자체 수정 효과와 앞단 통제 효과는 별도 실행 경로로 평가한다.

## 3. 대상 환경·배치 구조

### 3.1. 환경 기준

- Linux Kubernetes 전용 시험 노드의 등록된 엔진 워크로드를 대상으로 한다.
- 운영 워크로드와 섞인 노드에 특권 센서를 임의 설치하지 않는다.
- vLLM부터 구현·검증하고 SGLang에 공통 계약을 적용한다.
- vLLM 소스 검토 버전과 실제 설치 이미지·의존성 조합을 구분한다. 참조 문서의 v0.31.0은 실제 설치 완료의 근거가 아니다.
- 도구·커널·CNI 버전은 실제 준비 후 고정한다. 최신 문서의 버전을 설치 버전으로 복사하지 않는다.

<a id="section-3-2"></a>

### 3.2. 도입 도구를 최소화하는 구성안

추론 엔진의 내장 기능을 활용한다. Gateway는 요구되는 요청 통제 역할이며 확보된 구현으로 간주하지 않는다. 기반 구현·라이브러리는 미확정이고 요청 검증·중계·기록을 개발 범위에 포함한다. 전용 LAB의 보안 구성은 Cilium·Tetragon, 통신 증거 수집은 Cilium의 Hubble 최소 기능으로 선정한다. Hubble은 관측원이며 차단 집행기는 아니다. Relay/UI 추가는 실제 수집 경로가 요구할 때만 검토하며 별도 종합 관측 플랫폼은 도입하지 않는다.

| 구성요소 | 맡길 역할 | 실제 채택·동작 확인 |
| --- | --- | --- |
| Cilium | 워크로드 ingress·egress 정책 집행 | 실제 CNI 구성·권한·기존 정책과의 관계·허용/거부 결과 |
| Tetragon | 프로세스·파일 행위 관측, 지원 지점의 선택적 집행 | 커널·버전·규칙·모드 전환·필터·손실·서비스 영향 |
| Hubble | 통신 흐름·정책 판정 증거 | 필요한 필드·정책 원인·대상 귀속·손실을 기존 출력으로 확보 가능한지 |

도구 2~3개는 추가 도입 목표이며 모든 하위 프로세스·라이브러리 수를 뜻하지 않는다. Cilium이 이미 설치돼 있다면 재사용 여부부터 확인한다. 호환되지 않는 기존 CNI를 이 문서만으로 교체하지 않는다.

Gateway 기반은 별도 선정한다. 신규 구현에 필요한 인증 연동·요청 검증·일반/stream 중계·오류 처리·증거 기록의 개발량을 P0에서 산정한다. 추후 팀이 제공한 코드가 있어도 출처·사용 조건·요구 충족 여부를 확인하기 전에는 재사용으로 계산하지 않는다. Falco·KubeArmor 등 같은 역할의 센서를 기본 구성에 중복 도입하지 않는다.

기능 근거: [Cilium 정책](https://docs.cilium.io/en/stable/security/policy/), [Hubble 관측](https://docs.cilium.io/en/stable/observability/hubble/).

### 3.4. 신뢰·권한 경계

- 정책 적용 자격과 증거 조회 자격을 분리하고 엔진 Pod에 관리 자격을 넣지 않는다.
- 승인 정책은 기존 승인 근거·판본·대상·유효성을 확인한다. 새 승인 서비스를 만들지 않는다.
- 센서·수집 경로의 발신자와 대상을 확인하고, 엔진이 자기 사건을 임의 주입·수정할 수 없게 한다.
- 센서 수신부는 관리 경로로 제한한다. 같은 namespace·ClusterIP만으로 발신자 인증을 대체하지 않는다.
- 조회 화면은 관리 경로와 조회 권한을 적용한다. 요청 주체가 보내는 본문·헤더를 신원이나 정책 승인으로 신뢰하지 않는다.
- 1차 전달은 §5.4의 인증된 관리 경로 파일 묶음으로 선정한다. 실제 관리 계정·권한과 공통 ID 매핑은 D-03에서 확인한다.

GPU 서버는 미정이며 사용자는 권장 환경의 선정·근거 검토를 요청했다. 아래는 **설계상 선택한 시험 기준**이다. 서버 확보·설치·실행 완료를 뜻하지 않는다. 2026-10-20 공식 자료를 재검토했으며 사실과 프로젝트의 판단을 구분한다.

네이티브 Linux 선정은 WSL이 vLLM을 지원하지 않는다는 뜻이 아니다. 현재 WSL은 Docker daemon·GPU·클러스터 가용성이 확인되지 않았고, 이번 인수에는 호스트 커널·CNI·GPU를 함께 통제할 환경이 필요해서 분리한다. 단일 노드는 고가용성·노드 간 통신 검증을 제공하지 않는다.

<a id="section-3-6"></a>

### 3.6. 구성요소별 책임·직접 개발·완료 조건

각 구성요소를 같은 기준으로 관리한다. 아래에서 Cilium·Hubble·Tetragon·엔진 기능은 공식 제공 기능의 활용 계획이고, Gateway·수집·저장·화면은 개발 대상이다. 이 프로젝트에 이미 구현됐다는 뜻이 아니다. 재사용 점검 결과는 **그대로 사용/보완/신규/미지원**으로 기록하고 코드·설정 경로와 판본을 남긴다.

| 구성요소 | 활용 기능 또는 필요한 역할 | 우리가 직접 개발·연결할 부분 | 완료를 확인할 결과 |
| --- | --- | --- | --- |
| Gateway — 개발 대상 | 인증 연동·API 중계·일반/stream 처리 요구(보유 구현 미확정) | 실제 route/옵션 목록·정책 검사·거부/오류 분류·직통 제한 연동·요청 결과 기록 | 정상 stream/취소 유지, 금지 입력 backend 미전달, 실제 응답·증거 |
| Cilium | Pod ingress/egress 정책 집행 | 대상 selector·필수 통신 표·정책 변환/재조회·기존 규칙 결합·시도 대조 | 허용 통신 성공·선정 금지 통신 거부·실제 대상/정책 일치 |
| Hubble | Cilium datapath의 flow/verdict·손실 관련 관측 | 관리 수집 경로·필드 정규화·Pod/정책 귀속·누락 표시·증거 조회 | 통신 시도/실제 결과와 관측 연결, 비정책 장애·관측 불가 구분 |
| Tetragon | 프로세스·파일 관측, 지원 지점의 개별 동작 거부 | 실제 서빙 규칙·정상 예외·capability·모드/실제 결과·대상 귀속 | 선정 정상/의심 행위 구분, 검증된 규칙만 차단 표시 |
| 배포·파일 권한 | RO mount·UID/GID·volume 권한 | 승인 manifest·실제 mount/경로·cache 세대·소유권 비교 | 승인 공급물 변경 거부·정상 cache 쓰기/재사용. 실제 enforcer를 mount/권한으로 기록 |
| vLLM/SGLang 내장 기능 | 상태·선정 로그·/metrics 중 실제 제공 기능 | 엔진별 활성 설정·의미/단위 매핑·수집 상태·차이 표시 | 실제 지표·오류 조회, stale/미제공 구분, 엔진별 별도 증거 |

모든 결과는 공통 정책/대상 연동부 → 수집·정규화 → 증거 저장 → 읽기 전용 화면/기존 보고서로 연결한다. 공통 완료 조건은 §6.6·§9.9, 단계별 최소 완료선은 §10.1·§10.5에 둔다. 특정 도구의 성공으로 다른 영역까지 지원 완료로 표시하지 않는다.

기능 근거: [Cilium 집행 모드·규칙 결합](https://docs.cilium.io/en/stable/security/policy/intro/), [Hubble의 노드/Relay 관측 경계](https://docs.cilium.io/en/stable/observability/hubble/). 공식 지원과 실제 채택 버전의 동작은 별도 확인한다.

## 4. 기능별 상세 설계

<a id="section-4-1"></a>

### 4.1. F1 — 대상 등록·현재 환경 확인

**입력:** 승인 환경·엔진·모델 식별값, cluster·namespace·workload selector, 기준 구성 참조.

**처리:**

1. 접근 가능한 실제 cluster·node·workload·Pod·container를 조회한다.
2. 승인 대상과 실제 대상의 일치 여부와 지원 기능을 확인한다.
3. 대상 식별값과 조회 시각을 저장한다.
4. Pod 교체·컨테이너 재시작을 새 관측 대상으로 구분한다.

**출력:** 대상 스냅샷, 지원·미지원·미확인 목록, 기준 구성 연결.

**오류:** 권한 부족·메타데이터 누락·다중 대상 충돌은 자동 추정하지 않는다. 누락 값·원인을 표시하고 해당 적용·판정을 보류한다.

**완료 기준:** 시험·적용·관측이 같은 대상을 가리키고, 이전 Pod의 증거가 새 Pod의 적용 근거로 사용되지 않는다.

<a id="section-4-2"></a>

### 4.2. F2 — API 접근 통제

**입력:** 실제 활성 API 목록, 경로·메서드·모델 허용 목록, 인증 방식·주체·역할, 일반·관리·진단 API 구분, 직통 허용 운영 주체.

**처리:**

1. Gateway 기반과 인증 연동 방식을 선정하고, 경로 정규화·인증·인가·일반/스트리밍 중계·기록을 구현한다. 기존에 완성된 코드가 있다는 전제는 두지 않는다.
2. 신뢰할 수 있는 인증 결과로 요청 주체를 확인한다.
3. 허용된 경로·메서드·모델인지 평가하고 엔진 호출 전 허용·거부한다.
4. 일반 호출자의 엔진 직통 경로를 네트워크 구성과 함께 제한한다.
5. 일반·관리·진단 API와 실제 노출 경로를 함께 시험한다. /v1 경로만으로 전체를 대표하지 않는다.

**출력:** 주체·대상·정책·허용/거부·사유·시각, 확인 가능한 요청 ID, Gateway 자체 오류와 엔진 오류 구분.

**정상 기능:** 청크 단위 스트리밍을 유지하고, 취소·타임아웃·업스트림 오류 처리를 검증한다. HTTP 연결 종료만으로 엔진 작업 정리를 입증하지 않는다.

**오류:** 인증 실패에 따른 거부, 정책 평가 오류, 엔진 연결 실패를 다른 원인으로 기록한다. 평가 오류를 정상 차단 성공으로 집계하지 않는다. 정책 부재·평가 오류 시 요청 처리 제안은 §7.3과 D-05에 둔다.

**완료 기준:** 허용 일반·스트리밍 요청 성공, 금지 주체·API·모델 거부, 직통 제한 확인, 정상 요청 오차단·추가 지연 측정.

**Gateway 구현·인수 점검표:** 인증 결과의 발급/검증 주체, route 정규화, body 제한, JSON 중복 키/타입 검사, 엔진별 옵션 정규화, stream 중계, 취소·timeout·slot 회수, 오류 로그/민감정보 제거를 항목별로 점검한다. 각 항목은 구현·시험 후에만 지원으로 기록한다.

| API/상황 | 1차 처리 설계 | 실제 완료 증거 |
| --- | --- | --- |
| POST /v1/chat/completions | vLLM·SGLang 공통 첫 진입 route. 인증·승인 모델·텍스트 옵션 확인 | 일반·stream 응답과 전달된 정규화 입력 |
| POST /v1/completions | 엔진별 실제 schema를 고정한 뒤 공통 추가 route로 시험 | 각 엔진 지원 목록·옵션 경계·정상 응답. Chat 성공으로 대체 금지 |
| 모델 조회·상태·진단·관리 API | 실제 활성 목록을 조사해 일반/관측/운영 역할을 구분. 미등록 route는 기본 거부 | 직접 노출 목록·Gateway/관리 listener의 허용·거부. 진단 경로 누락 확인 |
| 인증 정보 없음/검증 실패 | 401, backend 미전달 | 검증한 주체 근거·거부 원인. 인증 원문 제외 |
| 인증된 주체의 금지 API/메서드/모델 | 403, backend 미전달 | rule/policy·주체 역할·대상·전달 수 |
| 잘못된 JSON·타입·중복/충돌 키·금지 옵션 | 400, backend 미전달 | 필드명/위반 분류. 과대 body는 413으로 별도 분류 |
| 동시성 초과 | §4.13의 429·Retry-After 제안, 정상 두 stream의 slot 유지 | 초과 요청 거부·기존 요청 완료·취소/오류 뒤 slot 회수 |
| 정책 평가 내부 오류/유효 정책 부재 | §7.3에 따라 503, 직통 우회 없음 | 내부 오류·정책 상태·영향 요청 수. 보안 차단 성공으로 집계 금지 |
| backend 연결 실패/대기 timeout | 응답 시작 전은 502/504 설계. 시작된 stream은 실제 중단/오류로 기록 | HTTP 시작 상태와 최종 결과 분리, Gateway/엔진 원인 구분 |

실제 엔진이 반환한 입력 오류는 출처를 보존하고 Gateway의 사전 정책 거부로 바꾸지 않는다. 이미 시작된 stream은 HTTP 상태를 뒤늦게 403으로 바꿨다고 표시하지 않는다. 클라이언트 연결 종료만으로 엔진 내부 취소·GPU 자원 회수를 확정하지 않는다. 위 HTTP 분류는 프로젝트 LAB 설계이며 팀의 기존 API 계약이 다르면 D-03에 매핑·변경 이유를 남긴다.

### 4.3. F3 — 송신·내부 통신 통제

**입력:** 대상, 승인 목적지 IP/CIDR·포트·프로토콜, 필요한 DNS·관측·모델 취득·내부 통신, 기존 유효 정책 집합.

**1차 필수 범위:**

- IP/CIDR·TCP 단일 포트 조건의 허용·거부 시험부터 시작한다.
- 인터넷과 사내 서비스 목적지를 모두 정책 대상으로 취급한다.
- 필수 정상 통신은 실제 목적지·포트·프로토콜을 명시해 허용한다. TCP 결과로 DNS UDP 등 다른 경로의 통제를 입증하지 않는다.
- IPv4·IPv6, UDP, FQDN은 실제 선정·검증 범위를 별도 표시한다. 미검증 주소 계열·프로토콜은 지원이라고 표시하지 않는다.

**처리:**

1. 목적지·프로토콜·포트와 정책 결합 의미를 검증한다.
2. 실제 CNI에서 겹치는 allow/deny와 방향을 반영한 최종 허용 범위를 확인한다. 승인 입력을 임의로 합쳐 허용을 확장하지 않으며, Cilium의 실제 allow 결합 의미는 아래 표와 공식 근거에 따라 별도로 계산한다.
3. 정책을 적용하고 현재 설정·대상·집행 상태를 다시 확인한다.
4. 팀 소유 확인 목적지로 허용·금지 시도를 수행한다.
5. 시도 결과·정책 판정·수신 관측·수집 상태를 같은 구간과 대상에 연결한다.

**출력:** 원본 정책 참조, 적용 설정·대상, 시도 ID·연결 정보, 실제 결과, 정책 원인과 증거 위치.

**오류·한계:** timeout·404·수신 없음만으로 통제 성공을 추정하지 않는다. 목적지 미기동·센서 중단·정책 원인 미확인은 별도 사유로 표시한다. 네트워크 제어 밖의 로컬 IPC·RDMA를 자동 포함하지 않는다.

**완료 기준:** 금지 통신의 제한과 허용 통신·모델 로딩·추론·필수 내부 통신의 유지를 함께 확인한다.

**Cilium 대상·필수 통신 표:** LAB namespace의 관리자가 부여한 task role label·Pod UID·namespace와 선택된 ingress/egress 방향을 고정한다. 새 Pod는 실제 selector와 정책 재반영을 확인하며 임의 클라이언트 role 문자열을 사용하지 않는다.

| 출발 → 목적지 | 선정 통신 | 기본 처리·확인 |
| --- | --- | --- |
| 등록 시험 client → Gateway | 사용자 TCP 8080 예 | 정상 일반/stream 허용. 실제 Service/배치 포트는 manifest에 기록 |
| Gateway → engine | vLLM TCP 8000 / SGLang TCP 30000 예 | 엔진별 선택 포트만 허용. engine ingress는 Gateway 및 명시한 관리 경로로 제한 |
| 일반 client → engine 직통 | engine API 포트 | 금지. 건강한 엔진에 대한 시도·Cilium 판정·정상 Gateway 대조 |
| observer → Gateway 관리 listener | TCP 8081 예 | 허용. HTTP 읽기 경로/주체 제한은 Gateway 어댑터에서 별도 검사 |
| acquire → 팀 소유 artifact-fixture | fixture TCP 8088 시작안 | 준비 작업 허용. 동일 fixture의 engine 접근은 거부 |
| 필요한 workload → cluster DNS | 실제 CoreDNS selector·UDP/TCP 53 | 필요한 정상 이름 조회만 시험. L4 DNS 허용으로 도메인별 통제/유출 방지를 주장하지 않음 |
| 관리 collector → API server/관측원 | 실제 등록 API/수집 경로·port | 필요한 조회 RBAC·발신자 인증 확인. source socket/host 경로는 Pod 정책만으로 보호됐다고 설명하지 않음 |
| engine → 기타 선정 시험 외부/내부 목적지 | 등록 receiver의 IP/port/protocol | 기본 제한 결과를 실제 시험. node/host·다른 주소 계열·RDMA까지 자동 확대 금지 |

기본 제한은 전용 LAB의 선택된 endpoint·방향에 적용하고 필수 정상 경로를 명시해 연다. 전체 cluster의 enable-policy 모드를 일괄 변경하거나 운영 정책을 삭제하지 않는다. Cilium/Kubernetes의 **겹치는 allow 규칙은 일반적으로 허용 범위를 넓히며, 명시적 deny는 우선**하므로 모든 유효 정책과 방향을 조회해 최종 결과를 계산한다. 승인 의도 밖의 broad allow가 있으면 그 사실과 제한 실패를 남기며 성공을 가장하지 않는다. 이를 수정할 때도 LAB의 관리 대상 정책만 변경한다. [규칙 결합](https://docs.cilium.io/en/stable/security/policy/intro/), [deny 우선순위와 한계](https://docs.cilium.io/en/stable/security/policy/deny/)

적용 결과는 요청 정책 판본·K8s 정책 객체/세대·대상·실제 endpoint 집행 상태·허용/금지 시도를 함께 기록한다. 여러 구성요소의 변경은 원자적 트랜잭션이 아니다. 일부 적용·재조회 실패·대상 불일치는 부분/미확인으로 표시하고 §7.3에 따라 처리한다. Hubble 수신 장애만으로 Cilium 집행 성공 또는 실패를 추정하지 않는다.

### 4.4. F4 — 승인 구성 비교

**입력:** 승인 기준 스냅샷, 실제 구성 조회값, 의미 비교할 필드 목록.

| 비교 항목 | 조회·비교 수준 |
| --- | --- |
| 엔진·이미지 | 실제 엔진 버전, 이미지 digest |
| 실행 설정 | 비밀을 제외한 실행 옵션과 선정 환경 설정 |
| 모델·토크나이저 | 모델·tokenizer·chat template의 ID·고정 revision·승인 manifest·읽기 전용 경로 |
| 컴파일 캐시 | 실제 경로·소유권·권한·세대·image/모델/컴파일 설정 연결. 정상 쓰기와 승인 불일치 구분 |
| 실행 기반 | 계정·권한·마운트·모델 경로 읽기 전용 등 선정 항목 |
| 정책 | 기대 정책과 실제 적용 판본·의미 내용 |

**처리:** 동일한 대상·필드에서 승인값과 현재값을 정규화해 비교하고, 일치·불일치·조회 불가를 구분한다. Pod UID·IP 같은 자동 변동 메타데이터를 의미 구성과 구분하되 사건 귀속에는 보존한다.

**출력:** 승인값·현재값·차이·확인 시각·대상, 관련 정책·평가항목·재검증 요청 기록.

**오류·한계:** 읽기 실패를 불일치로 단정하지 않는다. 파일 metadata·해시 일치와 실제 로딩·소비 확인은 다른 수준으로 표시한다. 모델 전체 파일 검증이 필요한 시험을 metadata로 대체하지 않는다.

**완료 기준:** 통제된 구성 변경을 식별하고, 조회 실패·자동 메타데이터 변화와 구별한다.

### 4.5. F5 — 프로세스·파일 행위 관측과 선택적 차단

**입력:** 대상, 실행 단계, 행위 규칙·판본, 정상 예외, 보호·민감 경로, 센서·커널 기능, 규칙별 관측/차단 모드.

| 선정 행위 | 관측할 내용 | 정상 예외의 범위 |
| --- | --- | --- |
| 승인되지 않은 프로세스 실행 | 셸·다운로더·지정 실행 파일과 부모·대상 식별 | 기동 스크립트·승인된 컴파일 도구·유지보수 |
| 보호 경로 변경 시도 | 모델·설정 경로의 쓰기·변경 시도와 결과 | 승인된 재배포·모델 교체·캐시·로그 경로 |
| 지정 민감 파일 접근 | 워크로드에 불필요한 자격증명·호스트 파일 접근 | 실제 정상 동작에 필요한 파일 목록 |

**처리:**

1. 대상 필터·규칙 적재·센서 상태를 확인한다.
2. 정상 기동·로딩·추론·컴파일·유지보수와 무해한 양성 대조를 관측한다.
3. 예외를 조정하고 탐지 대상이 여전히 식별되는지 재시험한다.
4. 좁은 동작 하나부터 지원되는 지점의 거부를 구현·시험한다.
5. 실제 거부 결과와 정상 서비스 영향 기준을 확인한다.
6. 기준을 충족한 규칙만 차단 지원 목록에 등록한다. 나머지는 관측·경보 또는 미지원으로 기록한다.

Tetragon은 지원되는 지점에서 호출 반환값을 바꾸는 동작 거부와 프로세스 종료 신호를 제공한다. 종료 신호만으로 이미 진행된 동작을 되돌리거나 반드시 막는다고 볼 수 없다. 임의 함수에서 모든 행위를 거부할 수 있다고 가정하지 않는다. [공식 집행 설명](https://tetragon.io/docs/concepts/enforcement/)

**출력:** 규칙·판본·모드·대상·실행 파일·부모·대상 경로·단계·시각·귀속·관측/집행 결과·증거·손실 정보.

**필수 제약:**

- 추론 서버·필수 worker·그 스레드를 자동 종료하지 않는다.
- 자식 프로세스라는 사실만으로 서비스와 독립적이라고 판단하지 않는다.
- 접근 거부도 엔진 오류·중단을 일으킬 수 있으므로 정상 기능 시험을 생략하지 않는다.
- write 관련 사건을 관측했다는 사실과 실제 파일 내용 변경을 구분한다.
- 요청·사용자 귀속은 별도 신뢰 가능한 연결이 있을 때만 기록한다.
- 센서가 사건을 내보내지 않았다는 사실만으로 안전·차단 성공으로 판정하지 않는다.
- Python 내부의 모든 함수·import·악성 코드 실행을 포괄 탐지한다고 주장하지 않는다.

**완료 기준:** §7의 관측→차단 검증과 정상 서비스 기준 충족. 차단이 어려우면 탐지·증적·경보를 제공하고 제한을 명시한다.

**Tetragon의 실제 서빙 규칙 선정표:** 아래는 구현할 규칙 목록이며 아직 실제 탐지/차단 결과는 없다. 파일 경로·실행 파일·hook·예외는 선택 image에서 확인한다. 무해한 대조 입력을 사용하고 자격증명 내용은 수집하지 않는다.

| 규칙 초안 | 서빙에서 확인할 행위 | 기본 지원 목표·정상 대조 |
| --- | --- | --- |
| TG-EXEC-01 | 등록 engine Pod에서 승인 목록 밖 shell/downloader/실행 파일의 실행 | 관측·경보 필수. 정상 시작 script·worker·compiler를 좁게 구분. 무조건 종료/실행 거부로 시작하지 않음 |
| TG-ASSET-01 | 승인 model/tokenizer/config 경로에 대한 선정 쓰기·대체 시도 | 선정 접근 관측과 실제 파일 결과 연결. RO/권한에 의한 거부는 그 enforcer로 표시 |
| TG-SECRET-01 | 엔진 작업에 불필요한 지정 민감 경로의 접근 | 합성 비밀 파일 복제본으로 읽기 시도 관측, 정상 필요 파일 대조. 파일 내용은 로그 제외 |
| TG-CACHE-01 | 전용 compile cache의 선정 권한 변경·예상 밖 실행/쓰기 경로 | 정상 JIT/cache 생성·재사용 유지. cache 쓰기 자체나 compiler 이름만으로 경보하지 않음 |
| TG-DENY-01 | 미승인 시험 프로그램의 지정 cache 보호 복제 경로에 대한 쓰기 목적 open | 조건부 실제 거부. 일반 권한상 writable인 대상을 monitor에서는 쓰고 enforce에서는 거부·내용 불변 확인. 정상 엔진의 cache 쓰기 유지 |

§4.13의 blocked-probe.txt는 **커널/도구 거부 capability 확인용**이다. 그 성공만으로 TG-DENY-01의 실제 서빙 계정·cache 경로·실행 파일·정상 예외가 검증됐다고 하지 않는다. 다음 단계에서 실제 등록 engine Pod/계정의 전용 cache 아래 복제 경로와 선정 실행 파일 조건으로 다시 검증한다. 지원 지점의 정확한 함수·인자·오류 반환·필터를 규칙 판본에 저장한다. 모든 cache 오염·mmap·이미 열린 FD·Python 내부 동작을 막는 규칙으로 확대하지 않는다.

선정 실행 자체의 사전 거부는 이와 별도 capability/정상 대조가 끝난 규칙에 한해 확장한다. 행위 거부가 앱 오류·중단을 유발하면 해당 규칙의 차단 채택을 보류한다. TG-EXEC/ASSET/SECRET/CACHE의 필수 관측 실패는 관측 완료로 처리하지 않고, TG-DENY 미지원은 관측/미지원 사유와 남은 위험을 표시한다. [Tetragon 관측/집행 모드](https://tetragon.io/docs/concepts/tracing-policy/mode/)

### 4.6. F6 — 엔진 기본 상태 조회

**재사용/직접 개발 경계:** 상태·지표 생성은 vLLM/SGLang의 내장 기능을 사용한다. 우리가 만들 것은 관리 조회 어댑터·선정 필드/단위 매핑·수집 상태·화면/보고서 연결이다. 별도 GPU exporter·시계열/대시보드 제품을 기본 추가하지 않는다.

**입력:** 엔진별 실제 상태 route·/metrics·선정 로그, image/의존성 판본·활성 옵션, 수집 주기와 조회 권한. observer는 §4.12 관리 listener를 경유하며 사용자가 engine 관리 포트를 직접 조회하지 않는다.

| 공통 표시 목적 | vLLM v0.31.0 소스/후보 | SGLang v0.5.21 소스/후보 | 처리·완료 기준 |

선정 버전 소스에서 이름/정의 후보를 확인했다. **지표의 존재는 설치 image에서 실제 export됨·활성화됨을 뜻하지 않는다.** 반입 때 실제 /metrics snapshot·HELP/TYPE·label·단위·활성 옵션을 metric-map으로 저장한다. Prometheus 형식은 출처·라이선스·지원 형식을 확인한 parser 라이브러리를 선정하되 Prometheus 서버 설치를 요구하지 않는다. SGLang은 선택 버전의 metrics 활성 설정을 확인한다.

수집은 LAB 5초 점검·15초 stale 설계를 사용하되 엔진 상태 검사가 실제 요청 생성/부하를 유발하는지는 별도 확인한다. 이 조회 실패를 engine 자동 재시작 조건으로 연결하지 않는다. 원문 prompt/response·인증값이 포함된 로그는 기본 수집하지 않는다.

**출력:** engine/metric-map 판본, 원본 지표명·의미·단위·대상·구간·값/미제공 사유, 발생/수집/마지막 성공 시각·reset/stale·오류 출처. 누락을 0으로 채우지 않는다.

**완료 기준:** 두 엔진 각각 실제 선정 지표·오류·조회 장애·stale를 표시하고, API 정상 추론 증거와 지표 조회 증거를 구분한다. §9.3 성능 판정은 동일 워크로드의 클라이언트 결과를 우선 사용한다. 임계값은 해당 판본·조건과 함께 기록한다.

### 4.7. F7 — 정책 적용·변경 이력

**입력:** 승인 정책 참조·판본·대상·유효 기간·승인 근거, 기존 적용 상태, 후보 설정.

**처리:**

1. 정책 출처·대상·유효성·지원 범위를 확인한다.
2. 적용할 설정으로 변환하되 허용 목록·예외를 조용히 추가·삭제하지 않는다.
3. 기대 정책과 실제 설치된 정책을 구분해 저장한다.
4. 설정 재조회와 선정 허용·거부 시험으로 실제 상태를 확인한다.
5. 적용·변경·철회와 실패·확인 시각을 이력에 남긴다.

**출력:** 기대/적용 정책, 설정 반영·동작 확인 결과, 실패 사유, 변경 이력.

**오류:** 새 후보의 실패와 기존 정책의 실패를 구분한다. 읽기 실패로 적용 성공을 추정하지 않는다. 확인되지 않은 후보를 현재 유효 정책으로 교체하지 않는다.

**완료 기준:** 승인 입력→설정 반영→동작 확인→조회·증적 연결이 일관되고, 정책 변경 후 판본과 관측 구간이 섞이지 않는다.

### 4.8. F8 — 관측 장애·정책 유효성·증적 기록

**입력:** 각 수집부의 상태·시각·손실, 현재 정책·유효성 확인 근거, 위반·구성 차이·적용 실패 기록.

**처리:**

1. 수집 정상·중단·지연·손실·확인 불가를 구분한다.
2. 정책의 적용 여부와 승인 유효성을 별도 확인한다.
3. 중앙 연결 실패·정책 만료·철회·초기 부재·확인 실패를 기록한다.
4. 사건·현재 상태·경보·증거·최소 재검증 요청 기록을 저장·표시한다.
5. 연결 단절 중 기존 제한이 유지되는지 실제 시험하고 결과를 기록한다.

**출력:** 상태 스냅샷, 관측 구간·누락 사유, 정책 유효성 결과, 사건·증거 링크.

**제약:** 센서·중앙 연결 장애만으로 정책을 자동 해제·완화하거나 서버를 종료하지 않는다. 유효성을 확인하지 못한 정책을 유효하다고 표시하지 않는다. 자동 복구·재배포·시험 실행 큐는 만들지 않는다.

관측 경로의 장애와 실제 집행 경로의 장애는 별도로 확인한다. 사건 수신이 중단됐다는 사실만으로 설치된 커널·네트워크 규칙의 집행 중단이나 정상 집행을 추정하지 않는다.

**완료 기준:** 오래된 정상 화면과 현재 정상 상태를 구분하고, 확인된 위반이 수집 장애 때문에 지워지지 않는다. 관측 불가를 안전·준수로 바꾸지 않는다.

### 4.9. SP1 — 모델·토크나이저·컴파일 캐시 보호

**목적:** 승인하지 않은 공급물·설정·캐시가 로딩되거나, 추론 중 모델·토크나이저가 바뀌는 경로를 줄이면서 정상 컴파일을 유지한다.

**입력:** image digest, 모델·토크나이저 ID/고정 revision, 파일 manifest, 실행 계정, mount·권한, 캐시 소유자·경로·캐시 세대, loader·remote-code·plugin 설정.

| 규칙 | 보호 대상·집행 지점 | 확인할 결과 |
| --- | --- | --- |
| ASSET-01 | 가중치·모델 config·토크나이저·chat template 등 선정 파일을 승인 manifest에 고정 | 로딩 전 목록·해시·revision·실제 mount 일치. 불일치 후보는 준비 오류로 표시 |
| ASSET-02 | 서빙 Pod의 모델·토크나이저는 읽기 전용 mount와 비관리자 계정으로 제공 | 추론 중 쓰기·삭제·대체 시도가 거부되고 정상 로딩·추론 유지 |
| ASSET-03 | 승인 경로 밖의 모델·토크나이저·설정·코드 경로와 경로 이탈을 차단 또는 후보 거부 | 경로 정규화·링크 해석·선정 loader 설정과 거부 근거 |
| CACHE-01 | 컴파일·Triton·엔진 캐시는 공급물과 별도 쓰기 경로에 배치, 실행 계정 소유·다른 계정 쓰기 제한 | 정상 생성·재사용 성공, 타 계정 쓰기 거부·권한 확인 |
| CACHE-02 | 모델 revision·엔진 image·PyTorch/CUDA·컴파일 설정으로 캐시 세대를 구분 | 다른 세대의 캐시를 조용히 신뢰·혼용하지 않음. 세대 불일치·출처 미확인 표시 |
| CACHE-03 | 캐시에서 실행 파일 생성·권한 변경·예상 밖 접근을 선정 규칙으로 관측 | 허용된 컴파일 산출과 의심 행위 구분, 규칙·프로세스·경로·단계 기록 |

**경로·권한 설계:**

- 모델·토크나이저·설정은 준비 작업이 작성한 승인 경로를 서빙 컨테이너에 읽기 전용으로 mount한다.
- 컴파일 캐시는 엔진 image·모델·컴파일 조건별 전용 volume/하위 경로로 관리한다. 다른 tenant·엔진과 임의로 공유하지 않는다.
- 정상 엔진 계정의 캐시 쓰기는 허용한다. 캐시 전체 읽기 전용, 일괄 실행 금지, 서비스 준비 후 모든 컴파일 금지 같은 규칙을 기본값으로 두지 않는다.
- 심볼릭 링크·rename·truncate·mmap 등 경로·변경 방식은 선정 시험에 따라 범위를 명시한다. 파일 해시와 특정 write 사건만으로 모든 변경 방식을 보장하지 않는다.
- 사용한 캐시 경로의 환경변수와 엔진이 실제 선택한 경로를 확인한다. 설정값만 보고 다른 dependency 캐시까지 보호됐다고 판단하지 않는다.

**처리:** 공급물 manifest 등록 → 실행 옵션·mount·권한 확인 → 정상 로딩 → 콜드 캐시 컴파일·추론 → 웜 캐시 재사용 → 선정 접근·변경 관측 → 기준 차이·거부·미확인 기록.

**출력·대시보드:** asset ID·revision·manifest, 실제 확인 수준(설정/파일/접근), 경로 분류·권한·기준/현재 차이, 캐시 세대·소유자·규칙·실행 단계·행위 결과·증거.

**한계:** 해시는 실제 추론에 사용한 모델의 의미적 동일성을 입증하지 않는다. 엔진과 같은 권한의 침해 프로세스가 정상 캐시 쓰기 경로를 악용하는 상황을 Unix 권한만으로 완전히 차단할 수 없다. 동일 UID·Python 내부 실행과 미선정 변경 경로는 별도 한계로 남긴다.

SP1의 디스크 컴파일 캐시와 GPU의 KV/prefix 캐시는 보호 대상·수명이 다르다. 파일 권한으로 요청·사용자 간 KV 공유 격리까지 보장했다고 표시하지 않는다. 관련 프레임워크 항목과 요청의 cache_salt 정책은 별도로 연결한다.

**완료 기준:** 정상 모델·토크나이저 로딩과 콜드/웜 캐시 동작 유지, 읽기 전용 공급물의 선정 쓰기 거부, 타 계정 캐시 쓰기 제한, 다른 캐시 세대·미승인 공급물의 감지/준비 거부와 원본 증거.

공식 vLLM 문서는 캐시를 신뢰하는 저장 영역으로 다루며 쓰기 권한 제한을 권고한다. 이 문서의 volume·manifest·세대 분리는 그 기능을 프로젝트 요구에 맞춰 구체화한 설계다. [vLLM v0.31.0 캐시 보안](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/usage/security.md#cache-directory-security)

### 4.10. SP2 — 추론 요청 옵션 통제

**목적:** 인증된 요청이라도 승인된 모델·작업·자원·확장 기능 범위 안에서만 엔진에 전달한다.

**입력:** 엔진·버전·endpoint별 실제 요청 스키마, 허용 모델, 옵션 허용 목록·기본값·상한, 확장 기능 사용 여부, 본문 크기·동시성 정책.

| 분류 | 1차 규칙 | 집행 위치·증거 |
| --- | --- | --- |
| 모델·작업 | 등록된 모델 별칭과 텍스트 Chat/Completion 등 선정 route만 허용. 생략 모델의 해석도 고정 | Gateway + 엔진 활성 route/설정 확인, 실제 전달 대상 |
| 출력 수·길이 | n 상한, max_tokens/max_completion_tokens 등 엔진별 출력 상한·누락 기본값 적용. 충돌 별칭 거부 | Gateway 정규화 후 전달·거부, 위반한 필드명·상한·정규화 판본 |
| 입력·본문·동시성 | 본문 바이트·배열·문자열·동시 요청 수와 엔진 max context 제한 | 요청 전 검증 + 엔진 실제 토큰 한도, 정상 경계값 대조 |
| 종료·스트리밍 | 일반/streaming 허용, ignore_eos·정지 조건 등 선정 옵션 제한 | 허용 스트리밍·취소 유지, 긴 생성과 정책 거부 구분 |
| 정보 노출 | logprobs·prompt_logprobs·echo 등 선정 옵션은 필요할 때만 허용 | 실제 endpoint 지원 여부·권한·응답 메타데이터 |
| tokenizer·template 변경 | 1차 텍스트 프로필에서는 요청 chat_template·chat_template_kwargs·prompt_embeds와 미선정 processor 인자를 거부 | 승인 tokenizer/template·입력 해석을 요청이 바꾸지 않는지 실제 schema·backend 미전달 확인 |
| KV/prefix 공유 문맥 | cache_salt 등 공유 문맥을 임의 클라이언트 값으로 신뢰하지 않음. 필요 시 신뢰한 Gateway 정책으로 생성·고정 | 미구현 프로필에서 다중 사용자 KV 공유 보호를 주장하지 않음 |
| 확장 실행·외부 입력 | 미선정 tool/MCP·media URL/로컬 파일·동적 adapter·logits processor·추가 실행 인자 등 비활성·거부 | 요청 필드 검증 + 시작 설정·관리 route 제한 + 네트워크 경계 |
| 임의 필드·중복 키 | route별 허용 키·타입·중첩 구조로 검사, 알 수 없는 키·중복 키·잘못된 alias 조합 거부 | 파서와 엔진 사이 해석 차이 시험 |

**처리:**

1. 인증·모델·route를 확인한다.
2. JSON 파서에서 중복 키·비정상 타입·크기·허용 필드를 검사한다.
3. 해당 엔진의 실제 이름·기본값을 공통 의미에 매핑한다.
4. 출력 토큰 별칭이 함께 있으면 명시 규칙으로 거부하며 한쪽만 보고 통과시키지 않는다.
5. 승인한 기본값·상한을 적용한 전달 입력을 만들고, 거부 요청은 엔진에 보내지 않는다.
6. 요청 전체 내용 대신 정책 판정에 필요한 필드명·분류·수치·판정과 전달 여부를 기록한다.

문자 수·본문 크기를 토큰 수라고 표시하지 않는다. Gateway가 실제 tokenizer로 입력 토큰을 측정하지 않는 프로필에서는 byte/문자 제한과 엔진 context 한도를 따로 표시한다.

**초기 시험 프로필 제안:** n=1, 출력 기본값·최대값 128 tokens, 엔진 context 2048 tokens, 본문 최대 64KiB, Gateway 동시 요청 2개. 이는 작은 모델의 정상/경계/거부 시험을 위한 제안값이며 기업 정책·성능 실측값이 아니다. 실제 프로필 채택 시 값·엔진 의미·시험 절차를 함께 고정한다.

정수·boolean·실수·문자열의 자동 형변환에 의존하지 않는다. n과 토큰 수의 하한·상한, null·누락·0·음수·boolean·문자열 입력의 처리를 규칙과 시험에 명시한다.

**시작 옵션과 요청 옵션의 구분:** trust_remote_code·load_format·tokenizer 경로·engine plugin·컴파일 설정 등은 시작·배포 구성에서 관리한다. 같은 이름을 요청 JSON에서 거부했다고 엔진 설정이 안전하게 고정된 것으로 보지 않는다. 동적 모델·LoRA 로딩이 노출되는 경우 관리 API·활성 기능까지 확인한다.

**출력:** policy/rule ID·판본, engine/route/schema revision, 옵션 이름·정규화 결과·위반 사유·엔진 전달 여부·서버 생성 요청 ID. prompt·response·인증 원문은 기록하지 않는다.

**완료 기준:** 허용 경계값의 일반·스트리밍 성공, 상한+1·기본값·충돌 alias·중복 키·미선정 확장 필드 거부, 거부 요청이 엔진에 도달하지 않았다는 대조 증거. vLLM 스키마를 SGLang에 그대로 적용하지 않는다.

v0.31.0의 [Chat 요청 스키마](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/openai/chat_completion/protocol.py)·[Completion 요청 스키마](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/entrypoints/openai/completion/protocol.py)와 보안 문서를 직접 조회해 선정 필드를 확인했다. 실제 image의 활성 설정·전달·거부 동작과 SGLang 매핑은 별도 시험한다. 부록 D의 로컬 최신 HEAD만으로 선정 image를 검증한 것으로 간주하지 않는다.

### 4.11. SP3 — 로딩·컴파일·추론 중 실행 행위 통제

**목적:** 정상 Python·worker·컴파일 도구와 모델 공급물·캐시의 관계를 기준으로 예상하지 않은 실행·접근을 식별하고, 검증한 동작만 거부한다.

**입력:** 실행 image·계정·프로세스 역할, 모델·토크나이저·캐시 경로, 승인 실행 파일·부모 관계, 단계 근거·정상 예외·유효 기간, 커널 후킹 capability.

| 단계·상황 | 정상 허용 후보 | 탐지·통제 대상 |
| --- | --- | --- |
| loading | 승인 Python·loader·tokenizer의 읽기, 정상 worker 생성 | 미승인 공급물·코드 경로, 공급물 쓰기, 미선정 외부 취득 |
| compiling | 실제 확인한 Python·컴파일러·linker·Triton 관련 도구와 전용 캐시 쓰기 | 미승인 실행 파일·쓰기 경로·출처 불명 캐시, 캐시 권한 변화 |
| inferring/serve | 추론·스트리밍·정상 worker·필요한 지연 JIT | 예상 밖 셸·다운로더·프로그램 실행, 공급물 변경·민감 파일 접근 |
| maintenance | 승인된 대상·사유·기간에 한정한 작업 | 범위 밖 동작·기간 경과·관측 중단 |
| unknown | 필요한 관측·대상 확인과 기존 통제 유지 | 새 차단 적용 보류·경보, 단계 불명확을 임의 허용 권한으로 사용하지 않음 |

기존 init/serve/maintenance와 세부 단계 loading/compiling/inferring는 같은 축이 아니다. 세부 단계에는 선언·엔진 신호·시험 조정기 중 어떤 근거로 식별했는지 기록하며, 시각만으로 내부 함수 실행을 확정하지 않는다. 로딩·컴파일·추론은 겹칠 수 있다.

**통제 원칙:**

- serve 상태에서도 정상적인 지연 컴파일이 발생할 수 있으므로 컴파일러를 일괄 금지하지 않는다.
- Python·worker는 정상 목록에 있더라도 접근 대상·시도 결과·다른 근거로 사건을 계속 본다. Python 전체 무시 예외를 만들지 않는다.
- 컴파일러 이름만으로 정상이라고 보지 않고 경로·image·부모·출력 경로·단계 근거를 함께 본다.
- 선정 실행·파일 접근의 거부는 지원된 지점에서 수행한다. 새 도구를 추가하거나 필수 worker를 종료해 대체하지 않는다.
- uprobe로 임의 Python 내부 함수를 강제로 바꾸는 기능은 1차에서 제외한다.
- 모델의 custom code·plugin 허용 여부는 승인 시작 구성에서 제한하고 시험한다. OS 실행 이벤트가 없다고 동일 프로세스 안의 코드 실행이 없었다고 판정하지 않는다.

**출력:** phase와 세부 단계·근거, 실행 파일·image·부모·프로세스 역할, 접근 경로 분류·행위·결과, 규칙·예외·지원 capability와 정상 대조.

**완료 기준:** 콜드 로딩·컴파일·웜 재시작·일반/스트리밍 추론에서 필요한 행위 유지, 선정된 비정상 실행·접근의 관측, 차단 채택 규칙의 실제 거부·서비스 유지. 미지원 지점은 관측·경보 수준과 이유를 표시한다.

<a id="section-4-12"></a>

### 4.12. SP4 — 서빙 작업별 통신 통제

**목적:** 목적지 허용 목록에 더해 어떤 서빙 작업 주체가 그 목적지에 접근할 수 있는지 제한한다.

Kubernetes 네트워크 정책은 기본적으로 워크로드·Pod 경계를 기준으로 한다. 같은 Pod·프로세스의 HTTP 요청을 사용자·업무별로 구분하는 권한 체계로 사용하지 않는다. 작업 역할은 클라이언트 JSON 필드나 엔진이 바꿀 수 있는 label을 그대로 신뢰하지 않는다.

| 작업·주체 | 설계상 분리 | 허용 통신 | 기본 금지 |
| --- | --- | --- | --- |
| 모델 취득·준비 | artifact-acquire Job/Pod, 준비 계정 | 승인된 아티팩트 서비스·필요 DNS·승인 기록 경로 | 임의 인터넷·내부 관리·관측 제어 경로 |
| 서빙·로딩·컴파일 | serving-engine Pod, 전용 계정 | Gateway와의 응답·선정 필수 내부 통신 | 공급물의 런타임 다운로드·임의 외부 목적지·취득 자격 사용 |
| 사용자 요청 진입 | gateway Pod | 선정 engine API 포트 | 비등록 엔진·임의 외부 전달 |
| 상태·증적 수집 | runtime-observer Pod/관리 프로세스 | 선정 관리 listener·저장·허용 Kubernetes 조회 | 임의 사용자 API·아티팩트 취득·광범위 외부 송신 |
| 허용/거부 시험 목적지 | 팀 소유 receiver·probe Pod | 등록한 시험 연결·상태 확인 | 운영 대상·제3자 서비스로 시험 확장 |

**1차 배치:** 취득 Job이 승인 파일을 준비하고 종료한 뒤, engine이 같은 승인 공급물을 읽기 전용으로 사용한다. engine의 외부 취득 권한을 작업 단계에 맞춰 열었다 닫는 대신 주체·계정·네트워크를 분리한다. 취득 자격은 engine Pod에 전달하지 않는다.

**정책 표현:** 클러스터 내부는 신뢰한 namespace/Pod selector·서비스 신원과 포트, 외부는 선정 IP/CIDR·프로토콜·포트로 관리한다. 동일 Pod의 여러 컨테이너를 별도 네트워크 보안 주체로 간주하지 않는다. label 수정·정책 적용 권한은 관리 경로에 한정한다.

**관측 주의:** 같은 목적지에 대한 취득 Job 허용과 engine 거부를 각각 시험한다. TCP 연결 허용은 HTTPS 서비스 안의 URL·파일·업무 권한을 입증하지 않는다. 목적지 redirect·CDN·fallback·취득 재시도가 추가 경로를 요구하면 자동 허용하지 않고 승인 목록·시험 범위를 갱신한다.

**관측 포트:** observer의 엔진 상태 조회는 read-only 관리 listener를 경유하도록 설계한다. 같은 엔진 포트에 접근할 수 있다는 사실만으로 GET /metrics만 허용됐다고 설명하지 않는다. HTTP 경로 제한은 Gateway/관리 어댑터에서 확인한다.

**확장:** 원격 media·tool server·원격 KV/분산 통신을 켜려면 별도 작업 주체·인증·경로·정책·정상 대조를 정의한다. 1차 텍스트 프로필에서는 비활성화한다. 같은 서빙 프로세스에서 여러 업무 목적지 권한을 다르게 적용해야 한다면 애플리케이션 계측·분리 구성을 추가 설계하고 현재 지원으로 표시하지 않는다.

**출력:** task role·주체와 그 근거, namespace·Pod UID·계정, 단계, policy·출발/목적지·프로토콜·포트·정책 원인·수신/health 증거. 개별 요청 ID는 실제 연결이 있을 때만 추가한다.

**완료 기준:** 취득 주체의 허용 목적지 성공, engine의 동일 목적지 거부, 정상 오프라인 로딩·컴파일·추론 성공, observer의 지정 수집 경로 성공·다른 경로 제한을 확인한다.

### 4.13. 첫 구현 규칙·보호 경로·정상 예외

아래 정책은 전용 LAB의 첫 구현 대상으로 선정한다. 파일명·포트·계정은 이 프로젝트의 설계값이며 오픈소스의 필수 경로가 아니다. 실제 image에서 경로·권한·실행 파일을 확인한 뒤 정책에 저장한다.

| 영역 | 1차 구현값·동작 | 검증·축소 조건 |
| --- | --- | --- |
| 모델·tokenizer | /opt/serving/assets/model·tokenizer를 RO mount, 승인 목록은 /opt/serving/approved/manifest.json | 정상 로딩·추론과 선정 쓰기/삭제 거부. RO mount의 효과를 Tetragon 효과로 기록하지 않음 |
| 컴파일 캐시 | /var/cache/serving/{engine}/{image-id}/{model-revision}/{compile-profile}, engine UID 10001 전용 쓰기 | 실제 dependency 캐시 경로·다른 계정 접근·cold/warm 동작. 전체 캐시 RO/noexec 금지 |
| 작업·계정 | 준비 Job UID 10002, engine UID 10001, 무해한 타 계정 probe UID 10003; 별도 Pod·관리 자격 분리 | GPU device·읽기 그룹·volume 권한 확인. engine이 자기 label·관리 정책을 바꾸지 못함 |
| 요청 경계 | 모델 별칭 1개, n=1, 출력 기본/상한 128, context 2048, body 64KiB, 동시 engine 전달 2 | 상한 초과는 거부, 누락은 승인 기본값. 충돌 alias·중복 키·비정상 타입·미선정 확장 거부 |
| 일반·stream | 둘 다 허용. 세 번째 동시 요청은 기다림 없이 429로 거부하고 Retry-After: 1을 제안 | 두 요청의 stream 종료·취소/오류 처리 후 slot 회수 확인. 의도한 429는 정상 부하 시험 실패와 구분 |
| 통신 | Gateway→engine 지정 API, observer→읽기 전용 관리 listener, acquire→선정 fixture·필요 DNS만 허용 | 같은 fixture의 acquire 허용·engine 거부를 각각 확인. 단순 포트 허용으로 HTTP 경로 인가를 대신하지 않음 |
| 선정 실행 관측 | engine의 예상 밖 shell·downloader, 모델/설정 변경·선정 민감 파일 접근 | 실제 실행 파일·image·부모·경로로 좁혀 관측. Python·worker·compiler 전체 제외 규칙 금지 |
| 첫 Tetragon 거부 | 전용 probe 프로그램의 /opt/serving/probes/blocked-probe.txt 쓰기 목적 open을 지원된 사전 지점에서 거부 | 해당 파일은 일반 권한상 쓸 수 있는 복제 시험 경로. Tetragon OFF/관측에서는 성공, 차단에서는 실패·내용 불변, 정상 추론 유지. 이 결과만으로 모든 write/mmap/이미 열린 FD 차단을 주장하지 않음 |

Tetragon의 실제 후킹 함수·인자·필터·오류 반환은 capability 점검 후 고정한다. CONFIG_BPF_KPROBE_OVERRIDE·대상 지원 여부만으로 충분하지 않고 실제 거부 결과가 필요하다. 거부 기능이 없으면 이 규칙을 관측·경보 또는 미지원으로 명시하고 필수 worker 종료로 대체하지 않는다. [선정 버전의 Override 조건](https://github.com/cilium/tetragon/blob/v1.7.1/docs/content/en/docs/concepts/tracing-policy/selectors.md#override-action)

**정상 목록 확정 절차:** 같은 image·모델로 cold load/compile → warm cache 재기동 → 일반·stream → 지연 JIT → 승인 유지보수 순서로 관측한다. 실행 파일 경로·가능한 해시/image·부모·접근 대상·단계 근거를 기록하고 담당자가 예외를 승인한다. 관측됐다는 이유만으로 자동 허용하지 않는다. 선정 비정상 probe를 다시 실행해 예외가 탐지를 없애지 않았는지 확인한다.

예외 기록은 exception_id·rule_ref·image_digest·executable/parent·path/action·phase·reason·approved_by·approval_ref·valid_from/until을 포함한다. 임시 유지보수는 LAB 시작값 30분 후 만료, 정상 상시 예외는 해당 image·정책 판본과 결합한다. 새 image·model revision·compiler 경로·만료 때 재검증한다. 30분은 무기한 예외를 피하기 위한 프로젝트 설계값이다.

부모 관계를 Tetragon의 matchParentBinaries로 집행할 경우 parents map 활성화와 메모리 증가를 확인한다. 수집 이벤트에 부모가 있다는 사실과 커널 필터가 그 조건을 적용한다는 사실을 구분한다. [선정 버전의 부모 필터](https://github.com/cilium/tetragon/blob/v1.7.1/docs/content/en/docs/concepts/tracing-policy/selectors.md#parent-binaries-filter)

요청 정책값의 이유: n=1로 다중 생성 변수를 제외하고, 128 출력·2048 context로 정상/경계/초과를 작은 모델에서 반복한다. 64KiB는 HTTP 파싱 보호 한도이며 토큰 한도가 아니다. 동시성 2는 정상 병행 stream과 초과 요청을 재현하기 위한 값이다. 모두 기업 요구량·공식 권장 최적값·실측 한도가 아니다.

<a id="section-4-14"></a>

### 4.14. Hubble 통신 관측·손실·정책 연결

**역할:** Hubble은 Cilium이 본 flow와 판정을 수집하는 관측원이다. 차단 수행 주체는 Cilium datapath이며, Hubble 연결 성공·DROPPED 이벤트 하나로 특정 프로젝트 정책의 차단을 확정하지 않는다.

**수집 경로:** 단일 노드는 신뢰한 node collector가 관리 권한으로 로컬 Hubble API/CLI의 JSON을 읽고 정규화하는 경로를 먼저 선정한다. 인증되지 않은 socket·API를 engine에 노출하지 않는다. Relay가 실제 수집에 필요하면 인증·범위·이미지/구성을 기록하며 Hubble UI는 필수로 추가하지 않는다. 로컬 socket 접근은 Pod 네트워크 정책으로 대체할 수 없는 관리 권한이다.

| 수집 항목 | 원본·정규화 요구 | 누락/한계 처리 |
| --- | --- | --- |
| 시각·방향·프로토콜 | flow 시각·node·traffic_direction·IP/L4 port/protocol·verdict | 시계/주소 변환 구간과 collector 수집 시각 분리 |
| 대상 | source/destination endpoint·namespace/Pod·identity·Service 중 제공 필드 | collector의 실제 K8s snapshot·Pod UID와 연결. 못 찾으면 귀속 미확인 |
| 정책 근거 | drop_reason_desc·policy_match_type, 제공되는 allowed_by/denied_by 정책 정보 | 필드 존재를 모든 flow의 완전한 원인으로 가정하지 않음. 정책 미귀속이면 해당 정책의 차단 성공 보류 |
| 실제 시도 대조 | trial_id·출발/목적지·등록 receiver health·수신 결과·클라이언트 오류 | trial_id는 시험 조정기의 실제 기록. raw flow에 HTTP request_id가 있다고 꾸미지 않음 |
| 수집 신뢰성 | lost_events·해당 source/loss count, 연결 상태·재연결 구간·마지막 정상 수집 | 지원 필드 누락은 미확인, 이벤트 없음은 정상/차단 증거 아님 |

이벤트가 없는 정상 idle과 수집 장애를 구분한다. stale는 마지막 flow 시각만으로 판단하지 않고 신뢰한 API/관리 경로의 마지막 정상 상태 확인·연결 오류·재연결 구간을 기준으로 계산한다. 실제 건강 확인을 제공하지 못하면 정상으로 추정하지 않고 확인 불가로 표시한다.

선정 Cilium proto에는 위 flow/정책 및 lost_events 응답 필드가 있다. 실제 활성 이벤트 종류·필드 채움·drop 표시를 확인하고 parser 판본을 저장한다. [flow.proto v1.20.3](https://github.com/cilium/cilium/blob/v1.20.3/api/v1/flow/flow.proto), [observer.proto v1.20.3](https://github.com/cilium/cilium/blob/v1.20.3/api/v1/observer/observer.proto)

**완료 시험:** 같은 receiver에 대한 acquire 허용·engine 거부, 건강한 목적지의 금지 port, 정책과 무관한 receiver 중단, Hubble 수집 중단/누락을 각각 실행한다. 허용은 클라이언트/receiver 성공과 flow를, 거부는 Cilium 정책 원인·대상·실제 연결 결과·건강한 receiver 대조를 연결한다. timeout·DROPPED·수신 없음만으로 차단 확인하지 않는다. Hubble 미수신 시 Cilium은 실제 다른 증거가 있는 범위만 표시하고 관측 영역은 불가/부분으로 남긴다.

실제 정책 원인을 다른 Cilium 진단 출력으로 보완할 때도 출처·수집 구간·대상·정확한 정책 귀속을 보존한다. 패킷별 여러 flow를 요청 차단 여러 건으로 합산하지 않는다. L4 flow만으로 사용자 요청별·URL별 인가를 설명하지 않는다.

### 5.1. 승인 입력과 최소 연동 계약

기존 승인 체계에서 확인 가능한 정책 참조·판본·대상·기간·승인 근거를 입력받는다. 별도 승인 키·결재 서비스를 새로 만들지 않는다. 기존 검증기·서명·번들 검증이 필요한 경우 해당 인터페이스를 재사용하고 확인한 범위만 문서화한다.

| 교환 항목 | 최소 내용 | 연동 책임 |
| --- | --- | --- |
| 정책 입력 | 정책·판본·대상·공급물/캐시·요청 옵션·단계 행위·작업 통신 규칙·예외·기간·승인 근거 | 정책 담당과 런타임 담당 |
| 기준 구성 | 엔진·이미지·모델·선정 옵션·권한·마운트 | 환경·배포 담당과 런타임 담당 |
| 적용 결과 | 기대/적용 설정·대상·조회·동작·실패 사유 | 런타임 담당 |
| 관측·증적 | 사건·상태·관측 구간·수집 상태·위치·무결성 정보 | 런타임·검증 도구 담당 |
| 재검증 요청 기록 | 발생 사유·관련 항목·대상·정책·증거 | 런타임 생성, 기존 절차에서 담당자 처리 |

최소 교환은 §5.4의 관리 경로 JSON 파일 묶음으로 선정한다. 기존 API가 확인되면 같은 자료를 변환하는 어댑터로 연결하며 공통 ID·권한 매핑은 D-03에서 합동 확인한다. 가상의 공통 API·객체 ID를 이미 존재하는 것처럼 사용하지 않는다.

<a id="section-5-2"></a>

### 5.2. 정책별 독립성과 변경

- API·통신·행위 규칙의 적용 상태를 구분한다. 한 영역의 성공으로 다른 영역까지 정상이라고 표시하지 않는다.
- 변경 전후 정책·대상·규칙·모드와 시행 시각을 기록한다.
- 승인 정책이 바뀌면 관련 설정·정상 예외·지원 기능을 재확인한다.
- 철회된 정책을 신규 적용 근거로 사용하지 않는다. 현재 남아 있는 설치 규칙과 승인 상태는 별도로 기록한다.
- 적용 실패 때의 원래 규칙 보존·부분 적용 여부를 확인한다. 자동 복구를 구현했다고 주장하지 않는다.

<a id="section-5-3"></a>

### 5.3. 기준 구성의 깊이

1차는 선정한 배포·실행 구성과 조회 가능한 모델 식별 정보의 비교다. 모델 파일 전체 해시, 실제 프로세스가 읽은 파일, 실제 추론에 소비한 모델을 각각 다른 확인 수준으로 둔다.

새 기준 구성의 승인은 기존 담당자 절차를 사용한다. 런타임이 발견한 현재값을 자동으로 새 승인값으로 삼지 않는다.


<a id="section-5-4"></a>

### 5.4. 검증 도구와의 파일 교환 계약

1차는 **버전이 있는 JSON + JSONL + 증거 폴더**로 연결한다. API 서버·메시지 큐·새 승인 서비스를 추가하지 않고, 기존 검증 도구와 같은 자료를 사람이 확인·재현할 수 있게 하려는 선택이다. 아래 이름과 schema_version=runtime-lab/1.0은 런타임 내부 초안이며 팀의 공통 객체·실제 API가 아니다. 프레임워크 문서의 OBS/EVD/RES·정책 객체 후보와의 변환은 담당자 합동 확인 전까지 미완료로 표시한다.

| 방향·파일 | 필수 내용 | 검증 규칙 |
| --- | --- | --- |
| 입력 approved-policy.json | schema_version, policy_ref/version, target_ref, approval_ref, valid_from/until, API·통신·행위 규칙, 예외 | 관리 경로의 승인 근거·대상·유효성·지원 기능 확인. 사용자 본문의 approval 값을 신뢰하지 않음 |
| 입력 baseline.json | baseline_ref, image_digest, engine, model/tokenizer revision, manifest 참조, 옵션·mount·계정, cache_generation | 승인값과 현재 조회값을 분리. 필수 누락이면 준비/적용 보류·사유 기록 |
| 입력 run-context.json | 실제 run_id, evaluation_refs, environment_ref, target_ref, workload_ref, 실행 구간 | 격리시험에서 기존 검증 도구가 발급한 실행 ID 사용. 운영 사건에는 run_id를 만들지 않고 observation_session_id 사용 |
| 출력 runtime-result.json | 정책 판본·대상·적용/유효성/관측/구성 상태, 규칙별 관측·시도·실제 거부·미확인, evidence_refs | 탐지≠차단, 적용 설정≠동작 성공. 미확인을 정상/0으로 바꾸지 않음 |
| 출력 events.jsonl | 사건 ID·UTC 시각·규칙·대상·단계·실제 enforcer·결과·증거 참조 | 원본 출처·정규화 판본·귀속·누락 구간 보존. 프롬프트·응답·인증 원문 제외 |
| 출력 evidence/index.json·files/ | evidence_id, 상대 경로, bytes, sha256, collector_version, 수집 구간·출처 | 파일 실제 크기·해시 확인. 폴더 밖 경로·symlink 이탈 거부. 해시를 관리자까지 포함한 변조 방지로 설명하지 않음 |
| 출력 revalidation-request.json | reason, target_ref, policy_ref, changed_fields, evaluation_refs, evidence_refs | 기존 절차로 넘길 요청 기록. 자동 시험 실행·업데이트 승인 아님 |

파일 묶음의 입력과 출력은 엔진이 수정할 수 없는 관리 디렉터리로 분리한다. JSON 중복 키·비정상 수치·지원하지 않는 schema·필수 필드 누락은 오류로 기록한다. 완료 파일은 임시 파일 작성 후 rename하고 증거 index가 존재하는지 확인한 다음 완료 표시를 쓴다. 쓰기 실패·부분 묶음은 완료로 발행하지 않는다. 실제 전달은 같은 호스트의 관리 경로부터 시작하고 외부 전달이 필요하면 기존 인증 채널을 사용한다.

**연동 완료 시험:** 기존 도구의 실제 실행 1개에 정책·기준 구성을 입력 → 런타임 허용/거부·변경·관측 장애 결과 생성 → 같은 run_id·policy_ref·evidence_id로 기존 결과 조회/보고서에서 열기. 파일 누락·해시 불일치·잘못된 대상은 증거 부족/연동 오류로 표시한다. 이 시험을 RT-INT-01의 필수 대조로 수행한다.

**앞단 검증과의 구분:** 엔진 자체 수정 효과는 런타임의 추가 차단을 빼고 별도 시험한다. 통제를 적용한 시험은 실제 배포 프로필의 보완 효과와 정상 기능을 확인한다. 정책을 시험에서 사용했다는 이유만으로 운영 배포 승인까지 자동 부여하지 않는다.

**구성요소와 파일 교환의 연결:** Gateway 결과는 HTTP 판정/최종 stream 결과, Cilium은 적용/집행 상태, Hubble은 flow/손실, Tetragon은 process/file와 모드·실제 결과, 배포/권한은 mount/파일 결과, 엔진은 상태/metric-map으로 분리해 저장한다. 같은 target_ref·policy_ref/version·environment_ref로 묶고 시험인 경우 실제 run_id를 사용한다. 서로 다른 관측원을 한 원본으로 덮어쓰지 않는다.

| 연동 확인물 | 작성/확인 역할 | 필수 확인 |
| --- | --- | --- |
| approved-policy·baseline 입력 | 정책/환경 담당 → 런타임 담당 | 승인 출처·판본·유효성·실제 대상, 구성요소별 규칙/필수 여부 |
| 공통 객체 변환표 | 검증 도구 담당 + 런타임 담당 | 외부 필드/ID ↔ 내부 필드, 필수/선택/미확인 사유·허용 값·판본·권한 |
| 결과·사건·상태 변환 | 런타임 담당 → 검증 도구/보고서 담당 | §6.6의 출처/집행기/관측/실제 결과 분리, 원본 참조 |
| 실 연동 인수 | 같은 실제 실행을 양쪽 담당이 조회 | 정상·거부·관측 장애 및 증거 누락이 같은 의미로 표시되는지 |

공통 계약 미확정 상태에서도 내부 개발은 진행하되 외부 OBS/EVD/RES 등의 이름/enum을 임의로 확정하지 않는다. 파일이 생성됐다는 사실과 기존 검증 도구가 실제 소비했다는 사실을 다른 완료 단계로 기록한다.

**관리 권한 설계:** 정책/기준/예외 작성·적용은 신뢰한 관리 주체, 관측 원본/정규화 출력 쓰기는 수집 주체, 화면/보고서 읽기는 허가된 조회 주체, engine은 승인 assets 읽기·자기 cache 쓰기만 가진다. 수집/적용/조회 기능은 권한을 구분하되 별도 인증 제품을 만들지 않는다. 실제 계정·RBAC·파일 ACL·외부 전달 자격을 D-03/D-08에 확인한다. 화면 조회자가 정책 파일을 바꾸거나 engine이 자기 증거를 지울 수 있으면 인수 실패다.

## 6. 이벤트·상태·증적 형식

### 6.1. 자료 단위

| 단위 | 의미 |

적용되지 않는 필드는 값과 사유를 구분한다. 누락·미확인 값을 임의 ID·0·빈 문자열로 채워 근거가 있는 것처럼 만들지 않는다.

실제 시험에서는 기존 실행 ID를 연결한다. 시험 밖 사건 때문에 가짜 시험 실행을 만들지 않는다. 요청 ID는 신뢰 가능한 연동이 있을 때만 추가한다.

### 6.3. 탐지·조치·효과의 구분

| 기록 | 의미 | 추가 확인 없이 주장할 수 없는 것 |
| --- | --- | --- |
| 탐지 | 규칙에 맞는 사건을 관측함 | 공격 성공·행위 차단 |
| 집행 시도 | 거부·종료 동작이 실행됐거나 요청됨 | 해당 행위가 실제로 중단됨 |
| 거부 확인 | 오류 반환·보호 대상 결과 등으로 해당 동작 거부를 확인함 | 모든 우회 차단·정상 서비스 유지 |

| 정상 대조 확인 | 선정 정상 작업이 정한 조건에서 성공함 | 임의 워크로드·다른 환경의 무중단 보장 |

API·통신·프로세스·파일 결과를 같은 차단 건수로 합산하려면 집계 기준을 별도 정의한다. 1차 화면에서는 영역·규칙·지원 수준별로 구분한다.

<a id="section-6-4"></a>

### 6.4. 상태를 독립적으로 표현

| 상태 축 | 표시할 내용 |
| --- | --- |
| 정책 유효성 | 확인된 유효·만료·철회·없음·확인 불가, 마지막 확인 시각 |
| 적용·동작 | 미적용·반영 확인·동작 확인·실패·확인 불가 |
| 구성 비교 | 일치·불일치·일부 확인·조회 불가 |
| 관측 | 정상·지연·부분 손실·중단·확인 불가 |
| 행위 결과 | 탐지·집행 시도·거부 확인·종료 확인·결과 미확인 |

위 표현은 공통 교환 enum을 새로 확정한 것이 아니다. 내부 저장값과 공통 형식의 매핑은 D-03에서 정한다.

같은 대상·구간에서 유효한 위반 근거와 센서 장애가 함께 있으면 둘 다 보존한다. 사건의 귀속·무결성 자체가 깨진 경우는 근거 제외 사유를 남긴다. 관측 결손과 확인된 위반을 하나의 정상/비정상 색으로 덮지 않는다.

<a id="section-6-5"></a>

### 6.5. 저장·보존·민감정보

- 초기 저장 기능은 소규모 JSON/JSONL·증거 파일과 색인으로 직접 개발한다. 기존 저장 구현이 확보됐다는 전제는 두지 않는다. 별도 중앙 로그 플랫폼을 필수로 추가하지 않는다.
- 동시 기록·쓰기 실패·용량 한도·보존·삭제·재시작 때 누락 구간을 처리하고 표시한다.
- 원본과 정규화 결과의 관계를 남기고, 변경·재분석 때 기존 증거를 덮어쓰지 않는다.
- 파일 증거는 실제 bytes의 크기·해시를 계산한다. 수집 실패·파일 없음은 별도 사유로 기록한다.
- 해시는 내용 일치 확인 수단이다. 저장 관리자까지 포함한 변조 방지를 해시 하나로 보장하지 않는다.
- 엔진에는 감사 기록 수정 권한을 주지 않는다. 조회·기록·삭제 권한을 분리한다.
- 프롬프트·응답·API 키·인증 헤더·환경변수·파일 내용·프로세스 인자 원문은 기본 수집에서 제외한다.
- 비신뢰 문자열의 길이·제어문자·화면 출력을 제한·이스케이프한다.
- LAB 원본은 §11 D-08의 7일/5GiB 한도와 시험 증거 별도 보존을 적용하는 설계다. 실제 저장·삭제/조회 권한과 운영 보존은 인계 때 확정한다.

<a id="section-6-6"></a>

### 6.6. 구성요소별 판정과 공통 결과 변환

단일 정상/차단 값 대신 **정책 유효성·실제 적용·관측 신뢰성·행위 결과·정상 서비스 대조**를 독립 필드로 둔다. 아래 표시는 내부 의미이며 외부 enum 매핑은 §5.4에서 확인한다.

| 원본/영역 | 실제 집행 주체 | 결과로 남길 것 | 거부 확인에 필요한 대조 |
| --- | --- | --- | --- |
| Gateway 요청/stream | Gateway | 허용·정책 거부·내부 오류·upstream 실패·취소·stream 중단, backend 전달 여부 | 규칙과 HTTP/최종 결과·backend 미전달. 내부 503을 정상 보안 차단으로 바꾸지 않음 |
| Cilium 설정/진단 | Cilium datapath | 정책 판본·실제 endpoint·방향·적용/부분/실패/미확인 | 기대/실제 규칙·정책 원인·실제 시도와 정상 목적지 대조 |
| Hubble flow/손실 | Cilium datapath, 관측원=Hubble | raw verdict/drop/정책 정보·flow 대상·관측 상태·누락 | §4.14의 시도/수신/정책 귀속. raw DROPPED만으로 project 거부 확정 금지 |
| Tetragon 사건 | Tetragon의 선정 hook | 탐지·모드·집행 시도·실제 오류/대상 결과·미확인 | monitor/enforce 대조·보호 파일/실행 결과·정상 추론 유지 |
| 파일/mount/UID | mount 또는 파일 권한 | 접근 거부·파일 내용/metadata·승인 차이 | 쓰기/삭제 결과·내용/권한·정상 cache 쓰기. Tetragon 성공으로 전환 금지 |
| 엔진 status/metrics | 해당 없음(지표 조회) | 측정값·단위·scope·reset·fresh/stale·미제공/수집 불가 | 상태 조회는 차단 건수에 넣지 않음. 정상 추론은 별도 요청 결과로 입증 |

최소 연결 정보는 component/source·enforcer·원본 schema/parser 판본·target_ref·Pod UID(확인 가능할 때)·policy_ref/version·event/trial ID·시각/관측 구간·evidence_refs·귀속 근거다. source=Hubble이라는 이유로 enforcer=Hubble로 만들지 않는다. 정책 후보/적용 상태와 마지막 성공 상태도 분리한다.

요청 ID를 가진 Gateway 기록, 시험 조정기의 trial_id, 실제 run_id 또는 운영 observation_session_id의 용도를 구분한다. HTTP ID가 없는 flow/process 사건은 source/destination·대상·구간·관리 스냅샷으로 연결 가능한 수준과 한계를 남기고 요청별 확정 ID를 만들어 넣지 않는다. 시간 근접만으로 인과관계를 확정하지 않는다.

하나의 네트워크 시도에 여러 flow가 있으면 원본을 보존하되 시도 결과와 별도로 집계한다. 재수집/재연결 중복과 실제 반복 시도를 구분할 수 없으면 총 차단 횟수에 억지로 합산하지 않는다. 근거가 없거나 원본이 손실되면 결과 미확인·관측 결손을 표시한다. 이미 확인된 유효 위반은 동시 수집 장애 때문에 지우지 않는다.

화면과 보고서는 이 정규화 결과/근거를 함께 사용하며 서로 별도 계산으로 상태를 바꾸지 않는다. 실제·mock·예시 자료의 출처 라벨을 끝까지 유지한다.

<a id="section-7"></a>

## 7. 정상 서비스 유지·장애 처리

<a id="section-7-1"></a>

### 7.1. 정상 서비스 유지의 의미

정상 서비스 유지는 검증할 요구사항이다. 제품이 모든 상황에서 무중단이라는 보장은 아니다.

- 추론 서버·필수 worker의 자동 종료·Pod 삭제·자동 재시작을 대응 기능으로 사용하지 않는다.
- 금지 요청·행위가 거부되는 것과 정상 사용자 작업이 실패하는 것을 구분한다.
- 정상 요청·스트리밍 완료, 준비 상태, 필수 프로세스·연결 유지와 오류율·지연·처리량을 확인한다.
- 프로세스가 살아 있다는 사실만으로 서비스가 정상이라고 판단하지 않는다.
- 센서 CPU·메모리·이벤트 부하를 측정한다. 상시 종합 관측 제품을 도입하지 않더라도 시험 중 영향 측정은 수행한다.
- 기준·워크로드·반복 조건을 측정 전에 고정한다. 허용 수치는 D-04에서 측정 근거와 함께 확정한다.

<a id="section-7-2"></a>

### 7.2. 관측에서 차단으로 전환하는 조건

1. 엔진·모델·이미지·워크로드·규칙·예외·관측 구간을 고정한다.
2. 기동·로딩·일반·스트리밍·취소·컴파일·유지보수 정상 대조를 수행한다.
3. 무해한 양성 대조로 규칙·귀속·수집 경로가 작동하는지 확인한다.
4. 예외를 좁게 조정하고 양성 대조를 다시 수행한다.
5. 선정한 동작의 거부와 정상 작업을 같은 조건에서 확인한다.
6. 오탐·서비스 영향·성능·수집 손실 기준을 만족한 규칙만 집행 대상으로 기록한다.
7. 미충족 규칙은 해당 규칙의 집행을 해제·관측으로 전환한 후 적용 상태를 다시 확인한다. 다른 통제까지 일괄 해제하지 않는다.
8. 변경 전후 규칙·모드·시각·이유·확인 결과를 보존한다.

정책 모드 지원은 실제 버전에서 확인한다. [Tetragon 정책 모드](https://tetragon.io/docs/concepts/tracing-policy/mode/)

<a id="section-7-3"></a>

### 7.3. 구성요소별 오류·정책 생명주기 처리

아래 요청 처리는 **전용 LAB의 설계 기본값**이다. 운영 정책 담당의 최종 승인을 대신하지 않는다. 관측 중단과 실제 집행 실패를 구분하고, 서버/필수 worker 종료·Pod 삭제·자동 재배포/engine rollback을 대응 기능으로 사용하지 않는다.

| 상황·영역 | 신규 요청·기존 작업 처리 | 설정·증거·화면 처리 |
| --- | --- | --- |
| 초기 유효 정책/필수 기준 없음 | 해당 보호 route 준비 보류·503. 기존 별도 serving 대상 임의 종료 없음 | 정책 없음·누락·준비 실패. 아직 보호 중이라고 표시하지 않음 |
| 승인 안 된/잘못된 새 후보 | 유효하게 동작 중인 기존 정책으로 처리. 후보 적용을 보류 | 후보 실패와 기존 실제 상태 분리, 실패 사유·판본 보존 |
| Gateway 인증/역할 거부 | 해당 요청 401/403, backend 미전달 | 정상 정책 거부·주체/규칙/사유 기록 |
| Gateway 정책 평가 내부 오류 | 해당 요청 503·직통 우회 없음 | 내부 오류·영향 요청 수, 차단 성공으로 집계 금지 |
| backend 연결 실패·stream 오류 | §4.2의 502/504 또는 이미 시작한 stream의 실제 중단/최종 결과 기록 | 정책 거부·Gateway/engine 오류 구분, 취소 전파/slot 회수 확인 |
| Cilium/Gateway/필수 assets 보호의 실제 적용 실패·대상 불일치가 확인됨 | 해당 target의 보호 준비 미완료. LAB admission에서 신규 요청 503; 이미 진행 중인 작업의 결과를 추정/강제 종료하지 않음 | 적용 실패/부분·target·실패 시각·서비스 영향·운영자 복원 요청. kernel 규칙이 모두 이전 상태라고 가정하지 않음 |
| 여러 구성요소의 일부 적용 실패 | 새 판본의 종합 적용 완료를 선언하지 않음. 영향 target은 위 admission 기준 적용 | component별 실제 판본·변경 성공/실패·영향 기록. 관리자가 LAB 소유 규칙만 이전의 유효 설정으로 복원/재확인 |
| 중앙 연결 단절·새 유효성 조회 불가 | 마지막 승인·반영 정책이 로컬에서 아직 유효한 동안 적용 유지. 새 승인/변경 사용 보류 | 중앙 단절·마지막 확인 시각·현재 로컬 유효성/실제 상태 구분. 무기한 유효로 연장하지 않음 |
| 정책 만료 또는 신뢰한 경로로 철회 확인 | LAB은 해당 정책 대상의 신규 요청 503. 진행 중 stream을 일괄 kill/종료하지 않고 최종 결과 기록 | 만료/철회·영향 범위·요청 실패·담당자 확인 기록. 기존 Cilium/파일 제한은 자동 삭제하지 않으며 유효 정책으로 표시하지 않음 |
| Hubble 수집 중단·flow 누락 | 이것만으로 Gateway 요청 차단·Cilium 정책 해제 안 함 | 네트워크 관측 불가/부분·loss·구간. Cilium 실제 집행 상태는 별도 증거로 확인 |
| Tetragon 수집 경로 중단·미지원 hook | 관측 장애만으로 server 종료/규칙 완화 안 함. 해당 규칙의 보호 수준은 미확인/미지원 | 관측 장애와 실제 hook 집행을 분리. 차단 지원을 새로 선언하지 않음 |
| engine status/metrics 조회 실패 | 이것만으로 추론 요청 차단·engine 자동 재시작 안 함 | 지표 수집 불가·마지막 성공값/시각. 0/정상으로 대체 금지 |
| 저장/화면/기존 보고서 연결 실패 | 기존 집행 규칙 유지, 자동 정책 완화 없음 | 기록/내보내기 실패·누락/용량·원본 보존 범위·UI offline. 발행 완료로 표시하지 않음 |
| 정상 요청 오차단·서비스/성능 영향 기준 초과 | 영향 규칙의 차단 채택 보류. 담당자가 유효한 이전 설정/관측 모드로 변경하고 재시험 | 영향과 운영자 조치·실제 변경·정상 복원 증거. broad allow 자동 생성 금지 |
| 승인 구성 차이 | 정상/위반/조회 실패를 구분해 경보·최소 재검증 요청 | 불일치를 자동 새 승인값으로 채택하지 않음 |

초기 admission 필수 확인은 Gateway 유효 정책, 선정 통신 제한, 승인 assets/mount이다. Tetragon 개별 거부는 규칙별 채택 수준에 따르고 Hubble/지표 조회는 관측 상태로 별도 관리한다. 관측 장애가 있다는 사실을 집행 실패로 자동 바꾸지 않으며, 실제 필수 보호 실패를 확인한 경우에는 위 LAB 요청 제한을 적용한다.

정책 만료/철회 시 503은 운영 연속성과 보안의 절충을 명시한 LAB 설계이며 실제 서비스 가용성 손실을 기록한다. 정상 정책 아래의 정상 기능 오차단과 별도 장애 사례로 시험하되 그 실패를 숨기지 않는다. 운영에서 같은 동작을 채택할지는 D-05에서 정책/운영 담당이 결정해야 한다. 정책을 몰래 연장하거나 철회된 승인으로 복원하지 않는다.

정책 적용은 구성요소 간 원자적 처리가 아니다. 실제 실패/관측 불가/이전 정책 유효성을 각각 표시하고, 중앙 단절→정책 만료→복구와 부분 적용→담당자 복원의 연속 사례도 인수 시험에 포함한다. 설치된 kernel/network 제한이 남아 있다는 사실은 승인 유효성의 증거가 아니다.

<a id="section-7-4"></a>

### 7.4. 실행 단계·정상 예외

| 단계 | 구분 근거 | 예외 원칙 |
| --- | --- | --- |
| init | 컨테이너 기동·정상 준비 전 단계 | 승인된 모델 로딩·컴파일에 필요한 행위 |
| serve | 서비스 준비 후 | 좁게 선정한 정상 실행·접근 |
| maintenance | 담당자·사유·대상·시작/종료 시각이 있는 승인된 작업 | 작업에 필요한 제한된 예외, 관측 지속 |

단계·예외는 신뢰할 수 있는 관리 경로에서 입력한다. Pod 주석·사건 문자열만으로 예외 권한을 생성하지 않는다. 기한 없는 유지보수 예외를 만들지 않는다.

단계가 불명확하면 근거를 기록하고 새 차단 채택을 보류한다. 기존 API·통신 통제를 임의 완화하지 않는다. 예외 만료 후 차단을 재개할 때도 실제 규칙·단계·정상 기능을 확인한다.

엔진·모델·토크나이저·이미지·컴파일 설정·캐시 세대·요청 옵션·작업 주체·규칙·예외 변경 시 관련 시험을 다시 수행한다. serve 상태만으로 정상 JIT를 전면 금지하지 않으며, 단계 추정만으로 정책을 자동 완화하지 않는다.

<a id="section-7-5"></a>

### 7.5. 담당자 복원 절차

자동 엔진 복구를 만들지 않는다. 담당자용 절차에는 영향 규칙 식별, 이전 유효 설정 확인, 승인된 변경 경로로 관측 전환·설정 복귀, 실제 적용 재조회, 정상 요청·통신·수집 재확인, 결과 기록을 포함한다.

만료·철회된 승인으로 복원했다고 정상 처리하지 않는다. 엔진 버전 복구와 통제 규칙 복귀를 별도 절차로 기록한다.

- 팀이 소유한 전용 시험 노드·목적지·무해한 파일·규칙을 사용한다.

성능 10%는 서비스 연속성을 우선하면서 개발 단계의 회귀를 걸러낼 내부 예산으로 제안·선정한 값이다. 공식 자료는 TTFT·처리량·백분위 측정 방법의 근거이며 이 10%를 권고하지 않는다. 실제 서비스 한도를 승인할 때는 시험 전에 별도 판본으로 입력하고 LAB 기준을 운영 승인으로 재사용하지 않는다.

기준 반복의 변동 폭이 허용 예산과 같거나 크거나, cold compile·출력 길이·캐시 상태가 달라 비교가 불공정하면 성능은 판정 보류한다. 통과를 위해 결과를 본 뒤 한도를 자동 완화하지 않는다. 선정 규칙이 정상 기능 또는 성능 기준을 만족하지 못하면 원인을 남기고 차단 채택을 보류한다.

### 9.8. 반복 시험과 성능 판정 절차

1. 환경·image digest·모델/tokenizer revision·정책·워크로드 판본·resolved 옵션을 고정한다. 같은 GPU에 두 엔진을 동시에 올리지 않는다.
2. 기능 시험은 cold load/compile, warm cache 재기동, 일반·stream·정상 취소, 경계/초과 요청, 파일·통신 probe를 각각 실행한다. compilation이 실제로 없으면 캐시 동작 검증을 미실행으로 남기고 그 경로를 발생시키는 승인 프로필을 따로 선정한다.
3. warm 성능은 각 모드에서 warmup 20건 후 일반 100건·stream 100건을 측정한다. 입력 묶음·실제 입력/출력 토큰·temperature·n·context·동시성 2를 동일하게 한다. 초과 요청·취소·위반 probe는 별도 기능 시험이다.
4. B0는 같은 Gateway·CNI·모델 파일/mount를 유지한 기본 구성으로 추가 런타임 센서/판정/통신 규칙을 끈다. B1은 관측·수집을 추가하고 Tetragon 규칙을 monitor로 둔다. B2는 요청 옵션·작업 통신·선정 개별 거부를 추가한다. 공통 기본 인증·네트워크 격리·파일 권한은 유지하며 B0를 엔진 직접 호출로 대체하지 않는다.
5. B0→B1→B2, B1→B2→B0, B2→B0→B1의 세 비교 블록을 실행해 순서 영향을 줄인다. 각 실행의 cache·warmup·GPU 부하 조건이 같아야 한다. 클라이언트 측 TTFT/E2E는 같은 위치에서 측정하고 시계 차이로 계산하지 않는다.
6. 블록별 지연 증가율=(B1 또는 B2 / B0 - 1)×100, 처리량 감소율=(1 - B1 또는 B2 / B0)×100을 기록한다. 각 실행 p50/p95·평균·분모·오류·출력 토큰·센서 자원을 함께 보존한다. 세 블록의 중간값만으로 실패 블록을 숨기지 않는다.
7. 차단 규칙은 관측 대조 → 실제 거부 → 파일/수신 결과 확인 → 일반·stream 정상 대조 → 증거 조회까지 통과해야 차단 지원으로 등록한다. 실패 규칙의 관측·경보 축소는 별도로 표시하며, 파일/네트워크의 필수 격리 실패를 화면 알림만으로 통과시키지 않는다.

20/100/3회는 발표·개발 단계에서 반복성을 확보하기 위한 실행 예산이며 통계적 신뢰도나 장기 무중단 보장은 아니다. warm 결과와 cold compile 비용은 합치지 않는다. 기준 부하가 낮으므로 최대 용량·실서비스 SLO로 일반화하지 않는다.

vLLM 선정 버전의 benchmark 코드는 TTFT·완료 요청/초·실제 출력 토큰/초·백분위·warmup·최대 동시성을 제공한다. 실제 지원 CLI와 Gateway 필드 정책을 확인해 재사용하고, 불필요한 확장 필드를 주입하는 기본 옵션은 사용하지 않는다. 별도 성능 플랫폼을 추가하지 않는다. [v0.31.0 benchmark 소스](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/benchmarks/serve.py)

| 배포/파일 — RT-ASSET-01~06·RT-CFG-01~02 | 승인 로딩·엔진 cache 쓰기·warm 재사용 | 모델 쓰기/삭제·다른 UID cache 쓰기·미승인 revision/경로·세대 불일치 | 실제 mount/권한/파일 결과·정상 compile 유지. Tetragon 결과와 혼동 없음 |
| vLLM/SGLang 상태 — RT-ENV-02·RT-OBS-01·RT-UI-01·RT-PERF-01 | 각 engine의 실제 metrics/상태·정상 추론 | 미제공 지표·활성화 안 됨·조회 실패·counter reset·stale | 엔진별 metric-map·원본/단위/scope·미제공/실패 표시. 단순 200/지표로 요청별 보호 입증 금지 |
| 공통 연동/생명주기 — RT-POL-01~02·RT-OBS-02~04·RT-INT-01·RT-OPS-01 | 같은 실제 실행/정책/대상의 결과·보고서 조회 | 누락/오매핑·권한 실패·부분 적용·단절→만료→복구·수동 복원 | 구성요소별 실제 판본·독립 상태·증거 무결성/범위, 기존 도구 round-trip·인수자 재현 |

각 영역은 **구현됨/실측됨/동작 검증/미지원/미확인**과 증거를 별도로 기록한다. Hubble이나 metrics가 미수신이면 관측 영역은 미완료/부분이며, 다른 집행 영역의 실제 증거까지 지우지는 않는다. Tetragon 조건부 거부 미지원은 해당 규칙에만 표시한다. Gateway·필수 통신·RO 보호의 실제 거부 실패는 경보 화면만으로 필수 통제를 완료 처리하지 않는다.

성능·정상 대조는 개별 구성요소 재사용 점검과 전체 연결 시험을 함께 한다. B1에서 관측원별 CPU/RSS·loss를, B2에서 추가 판정/집행 영향과 정상 오류를 기록한다. 원인 확인용으로 구성요소를 한 번씩 분리 측정할 수 있으나 결과 없이 전체 overhead를 특정 도구 탓으로 돌리지 않는다. §9.3의 10%는 LAB 임시 예산이며 운영 성능 기준은 별도다.

### 10.5. 첫 시연·통합 시연 흐름과 확인 화면

**첫 실제 시연(P1):** 실제 승인 입력·등록 vLLM에 정상 텍스트 요청/stream 실행 → 출력 상한을 넘기는 무해한 요청 거부 → backend에 전달되지 않았는지 확인 → 같은 대상/정책/실행의 응답·결과·증거를 조회한다. 화면만 준비됐거나 CPU mock만 성공하면 실제 시연 통과로 표시하지 않는다.

**구성요소 통합 시연(P2/P3):** 아래 사례는 같은 환경/정책 판본 아래 순서대로 독립 실행하며, 한 사용자 HTTP 요청이 모든 probe를 자동 유발한다고 설명하지 않는다. 전체를 실제 run_id로 묶고 각 case/trial·관측원·귀속 한계를 유지한다.

| 순서 | 시연 입력·행동 | 사람이 확인할 결과 |
| --- | --- | --- |
| 1 정상 기능 | 승인 모델로 일반·stream, 정상 취소 | Gateway 최종 결과·engine 정상 응답·slot 회수·선정 상태 지표 |
| 2 요청 통제 | n/출력 경계 위반 또는 금지 옵션 | Gateway 정책 거부·사유·backend 미전달·증거. 정상 요청 재대조 |
| 3 작업 통신 | acquire와 engine이 같은 fixture에 접속, 일반 client가 engine 직통 시도 | Cilium 실제 허용/거부·Hubble 정책 귀속/관측 상태·건강한 receiver 결과 |
| 4 파일/cache | 모델 선정 쓰기/삭제 시도, engine의 정상 cache 생성/재사용 | RO/권한 거부와 정상 쓰기 구분·실제 파일/세대·enforcer 표시 |
| 5 실행 행위 | TG 규칙의 무해한 미승인 실행/합성 파일 접근, 지원 시 개별 open 거부 | Tetragon 탐지·monitor/enforce·실제 결과·정상 worker/JIT 유지. capability probe와 실제 규칙 별도 표시 |
| 6 관측 장애 | Hubble/engine 지표 등 한 수집 경로를 시험에서 중단 | 해당 관측만 stale/불가·마지막 시각/손실 표시, 기존 규칙/정상 서비스의 실제 상태 별도 확인 |
| 7 기존 도구 연결 | 결과·사건·증거·필요 재검증 기록을 같은 실행으로 내보내기 | 기존 결과/보고서에서 대상·정책·증거 조회, 누락/미지원·실제/mock 구분 |

최종 시연은 vLLM 결과와 SGLang의 대응 결과를 각각 연결한다. Tetragon 미지원 규칙은 그 상태로 설명하고, Cilium/파일 통제/요청 통제의 성공 여부를 별도로 보여준다. 자동 policy 완화·server/worker kill·Pod 삭제로 시연을 복구하지 않는다. 필요한 설정 복원은 인수자가 승인된 관리 경로로 수행하고 기록한다.

### I.1. 선정 결과와 판단 기준

이 부록은 본 계획서의 개발·시험환경 상세와 선정 근거를 기록한다. 장비·버전 선정 근거는 이전 조사 시점의 기록으로 유지하며 이번 수정에서 최신 버전·가용성·호환성을 다시 검증하거나 설치하지 않았다. 설치 전 공식 지원 상태·패치·이미지 가용성을 재확인한다. 요청 한도·경로·포트·성능 예산은 프로젝트 LAB 설계값이고, 보유한 코드의 기본값이나 시험 결과가 아니다. 요약본의 기능 요구는 유지하며 특정 구현 보유 여부와 분리한다.

**개발은 현재 WSL/Python, 실제 인수는 Ubuntu Server 24.04 전용 GPU 서버의 단일 노드 Kubernetes에서 수행한다.** 모델은 Qwen/Qwen2.5-0.5B-Instruct 한 개, GPU는 L4 한 장을 기준으로 vLLM과 SGLang을 순차 시험한다. 보안 제품은 Cilium·Tetragon 두 계열과 Cilium의 Hubble 최소 관측을 사용한다. 엔진 내장 지표를 활용한다. Gateway·수집·저장은 개발 대상이며 기존 구현이 확보됐다는 전제는 두지 않는다. Gateway 기반·인증 연동은 P0에서 선정하고 개발량을 산정한다.

판단 순서는 ① SP1~SP4를 실제 검증할 수 있는가 ② 정상 서비스 중단·운영 환경 영향 없이 분리할 수 있는가 ③ 공식 지원/호환 조건에 맞는가 ④ 적은 도구와 작은 모델로 반복 가능한가이다. 최신 버전이라는 이유만으로 바꾸거나, 참조 문서의 버전이라는 이유만으로 전체 조합을 검증 완료로 취급하지 않는다.

| --- | --- | --- |
| DEV-LOCAL | 기존 WSL Ubuntu 24.04.4·Python 3.12.3·serving-runtime .venv | 정책·파서·정규화·기록·화면·파일 교환 개발 |

이전 조회에서 현재 WSL은 kernel 6.18.33.2-microsoft-standard-WSL2, 논리 CPU 16개·RAM 약 7.5GiB·Python 3.12.3이었다. Docker CLI는 있으나 daemon 접근은 권한 오류였고 GPU/Kubernetes 가용성은 확인되지 않았다. 도구/장비가 없다는 결론이 아니라 실제 통합시험 환경으로 확인되지 않았다는 뜻이다.

| 노드 제어 | Cilium/Tetragon node agent | 설치된 정책·이벤트·고정 관리 경로 | 사용자/엔진의 정책·role label 수정 |

vLLM 내부 포트 8000, SGLang 내부 포트 30000을 시작안으로 매핑하되 실 기동 옵션과 Service를 확인한다. observer는 Gateway 관리 listener를 통해 선정 상태만 조회한다. IP/포트 허용만으로 /metrics 전용 읽기 권한을 주장하지 않는다. 실제 포트·API는 구현 전이며 설계값이다.

모델은 준비 Job/관리자가 승인 경로에 반입한 뒤 engine에 RO로 제공한다. engine에게 다운로드 권한을 주었다가 추론 때 끄는 방식 대신 별도 Pod·계정·자격으로 분리한다. 동일 Pod의 여러 컨테이너를 별도 네트워크 주체로 취급하지 않는다. 내부 목적지는 신뢰한 namespace/Pod selector와 port, 외부는 선정 CIDR/port/protocol로 표현한다. 실제 Hugging Face CDN·redirect·인증 검증은 fixture 결과와 분리한다.

단일 노드에서 control-plane workload 배치 허용은 전용 LAB에서만 수행하고 사전 기록한다. 노드 agent의 필요한 권한을 engine에 복사하지 않는다. 관리 조회·적용은 발급·권한을 확인한 인증 계정으로 수행하고 승인 ID 문자열만으로 자격을 대체하지 않는다.

VLLM_CACHE_ROOT·VLLM_ASSETS_CACHE 및 실제 Inductor/Triton/FlashInfer 경로를 각각 조회한다. SGLang도 실제 resolved 경로를 별도로 고정한다. 환경변수 하나로 모든 dependency 캐시가 이동했다고 가정하지 않는다. 선정 vLLM 보안 문서는 캐시를 신뢰 영역으로 다루며 권한 제한을 설명한다. 세대별 volume·승인 manifest는 프로젝트의 설계다. [v0.31.0 캐시 보안](https://github.com/vllm-project/vllm/blob/v0.31.0/docs/usage/security.md#cache-directory-security)

정상 예외는 cold load/compile·warm restart·일반/stream·지연 JIT·승인 유지보수를 실제 관측한 후 image·실행 경로·부모·접근 대상·단계와 결합한다. Python/worker/compiler 전체 무시 예외는 금지한다. 부모 커널 필터를 사용하면 parents map 활성화·메모리 비용을 확인한다. 유지보수 예외는 LAB 기본 30분, image·model·정책 변경과 만료 시 재검증한다. 예외는 관측에서 자동 생성하지 않는다.

probe 거부는 지원된 사전 hook에서 쓰기 목적 open을 거부하는 한 지점부터 확인한다. 열린 FD·mmap·rename 등 모든 경로를 포함하는 보호로 확대하지 않는다. 같은 UID의 캐시 악용·Python 내부 실행·실제 추론 모델 소비를 완전 입증하는 기능은 제외한다. engine/필수 worker 종료와 Pod 삭제·자동 재배포는 대응 기능으로 쓰지 않는다.

| 동시성 | engine으로 전달하는 요청 2개, 초과 429·Retry-After: 1 제안 | 병행 stream·거부·slot 회수 시험을 작게 재현. 최대 처리 용량 아님 |
| 미선정 확장 | media URL/로컬 파일·tool/MCP·동적 LoRA·request template·prompt embeds·미승인 processor/추가 실행 인자 거부 | 이번 텍스트 profile 밖 입력·실행·통신 경로를 닫음 |
| 관측 상태 | 점검 5초·15초 stale | 세 번의 점검 부재를 판별할 단기 LAB 설계. 센서의 무손실 전달 보장 아님 |
| 로컬 원본 | 7일 또는 5GiB, 먼저 도달한 한도 | 단기 교차 재현·용량 제한. 인수 증거는 별도 내보내기, 누락/보존 실패 표시 |

값들은 공식 최적값이 아니라 프로젝트가 선택한 재현 가능한 시작 정책이다. 각 엔진의 실제 schema·옵션·생략/별칭 동작을 확인하고 누락·잘못된 타입·중복 키·미등록 필드를 시험한다. 상한 초과는 몰래 값만 낮추지 않고 거부한다. 모델 다운로드/custom code/plugin 같은 시작 설정과 요청 옵션을 따로 관리한다.

#### I.6.2. 시험 입력·반복 방법

1. 모델/tokenizer/template revision·입력 파일 hash를 고정한다. 짧은/중간/긴 입력 묶음의 실제 token 수를 기록한다. context 경계는 template와 출력 여유를 포함해 실제 tokenizer/엔진으로 확인한다.
2. cold load/compile·warm cache 재기동·지연 JIT는 기능 시험으로 실행한다. --enforce-eager 등으로 compilation을 끄고 cache 보호가 완료됐다고 표시하지 않는다. GPU/model/backend 조건상 발생하지 않는 경로는 미실행으로 남긴다.
3. warm 성능은 각 모드 warmup 20건 후 일반 100건·stream 100건, 동시성 2·n=1·출력 상한 128로 세 비교 블록을 실행한다. 실제 output token·종료 사유를 기록하고 정상 취소·429·위반 probe는 분리한다.
4. B0 기본 구성·B1 관측 추가·B2 통제 추가를 B0/B1/B2, B1/B2/B0, B2/B0/B1 순서로 비교한다. Gateway·CNI·기본 파일 권한·engine/model·부하 위치는 고정한다. 새 runtime 기능의 증가분을 보되 CNI 자체 비용을 이 결과로 주장하지 않는다.
5. 기준 조건이 불안정하거나 출력 길이·cache 상태·GPU 경쟁이 달라지면 판정 보류한다. 100건·3회는 실행 예산이며 통계적 신뢰도·실서비스 용량 보장이 아니다.

이미 설치된 운영 CNI는 교체하지 않는다. 새 전용 cluster의 도구 설치·노드 변경은 환경 구축 단계에서 수행할 작업이며 이번 문서 수정 과정에서는 수행하지 않았다.
