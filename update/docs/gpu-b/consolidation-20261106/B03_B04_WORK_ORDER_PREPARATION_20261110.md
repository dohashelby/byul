실제 적용 전에는 A04의 @34로 다시 생성하고 실제 provider/recipe·ENV/target/prepared·정책·실행 설정을 결합해야 한다. `work/<plan>/<attempt>/<check>/<side>` 경로와 실제 attempt를 사용한다. 묶음은 목록 분류이며 기동 공유를 허용한 결과가 아니다. 이미지·모델·기동 설정과 상태 독립성이 확인된 사례만 같은 기동으로 묶는다.

원 생성기는 저장소 밖의 새 출력 경로만 받는다. 예를 들어 아래는 공급 묶음의 준비 명령이며 엔진 실행 명령이 아니다.

## B04 TP2 준비

기존 `tools/b12_tp2_inputs.py`와 `b12_tp2_verify.py`, [TP2 계획 B 절](../../dev-1/tp2-run-plan.md)을 재사용한다. LIF-08·11·SUP-06의 정상·실패·복구 파일 포인터는 현재 미입력이다. 파일이 들어오면 `--verify-inputs-root`로 실제 bytes SHA와 ENV·정책·target·prepared 선언 결합을 먼저 검사하며, 이 검사도 실제 runtime·자격·준비 자산 검증을 대신하지 않는다.

계획 슬롯은 기존 문서의 LIF-08 900초·LIF-11 600초·SUP-06 900초, B 합계40분을 선언값으로만 연결했다. 전체205분·EC2 $20은 과거 합동 TP2 계획이며 현재 가격·할당량·비용 적합성 조회 결과나 이번 기동 승인이 아니다. 기본 수집120초·개별 정책 창·원 보호/정리 기한은 바꾸지 않았다. 실제 하네스와 맞지 않는 시간 조건은 별도 미충족으로 반환한다.

현재 rank-fault 구현/신원, TP2 rank·shard/복구 입력, 생산자 실제 GPU 자격, @34가 준비됐다고 표시하지 않았다. `/2·/3` decoder와 `producer_qualifications` receipt0을 구분한다. 예정 `/4`는 A02의 별도 작업이다. TP2 기동은 하지 않았다.
