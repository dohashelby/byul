## 설계 보강과 이유

- **복원 시 enforce 재활성화 방지:** 현재 live 모드가 monitor여도 저장된 spec이 enforce로 재로드될 수 있으면 교체를 거부한다. 명시 monitor spec 또는 알려진 Post 전용 spec만 안전하게 복원할 수 있다고 본다.
- **여러 daemon·경합:** 변경 전 모든 예정 daemon의 enabled·동일 실제 모드를 요구한다. 객체 resourceVersion으로 변경을 제한하며, 이번 요청의 annotation과 UID를 확인해 다른 작업의 객체를 복원·삭제하지 않는다. 새 객체 제거는 raw DELETE의 UID/resourceVersion precondition을 사용한다. 확인 불가는 `unknown`이다.
- **승인:** 이번 종류는 사용자 요구대로 LAB 설정에서도 별도 approver만 승인하고 자기 승인을 금지한다. 기존 종류의 LAB 예외는 유지했다.
- **해시 일치:** 새로 적용하는 모든 Tetragon spec에 monitor를 명시하므로 Gateway expected-policy 렌더도 같은 함수를 쓴다. 예전 Post 전용 spec은 동기화 전까지 해시 불일치가 표시될 수 있고, 변경 후 기존 모니터 창·시험 근거는 재검증해야 한다.
- **Cilium 검증:** SSA server dry-run·diff와 실제 create/replace의 서버 dry-run을 모두 수행한다. 실제 변경 후 현재 Gateway 묶음·승인과 고정 추론 요청을 확인한다. 결과에는 manifest·diff·명령 출력·예외 원문·주소·인증값을 넣지 않는다.
- 정책별 동작은 dry-run에서는 실행 예정이며 component `dry_run`으로 미적용을 구분한다. `extra`는 같은 namespace의 기존 정책을 보고만 하고 삭제하지 않는다.

## 남은 제약·Claude 실서버 확인

1. 실제 kubeconfig RBAC·CRD/admission·Tetragon 정책 로드·모든 daemon의 모드와 spec, Cilium 전달 지연·트래픽 허용/차단·복원은 미확인이다. 가짜 runner 시험을 실서버 통과로 해석하지 않는다.
2. 먼저 current와 Gateway ID·해시·승인 일치 → dry-run → 새 승인 요청으로 Tetragon monitor 생성/교체 → unchanged/extra 보존을 확인한다. enforce인 다른 spec의 거부와 기존 모드 전환/readiness 회귀를 확인한다.
3. Cilium CRD 없음은 `not_installed`, CRD 있음+실제 적용 미선택은 dry-run·diff만 수행하는지 확인한다. 실제 적용 선택은 유지보수 중 시험하며 Gateway 조회·허용 모델 첫 항목의 추론 성공, 실패 시 이전 객체·Gateway 통신 복원을 확인한다. 인증 배포는 기존 env의 inference 자격과 해당 모델의 실제 서빙이 필요하다.
4. 임시 백업은 종료 시 정리된다. 장기 수동 복구 사본은 운영자가 사전에 별도 0600으로 보관한다. 프로세스 강제 종료·복원 권한 부족·동시 변경·늦은 확인·임대 만료 뒤 결과 거절은 수동 확인 대상이며 자동 replay하지 않는다.
5. 수동 CLI와 운영 에이전트는 동일 잠금을 쓰거나 에이전트를 중지한 유지보수 시간에 실행한다. CLI는 권한 있는 사람이 직접 실행하는 경로이고 플랫폼 승인 대행 경로가 아니다.

Claude의 대화형 검수와 실제 서버 확인을 기다린다. 커밋·push는 하지 않았다.
