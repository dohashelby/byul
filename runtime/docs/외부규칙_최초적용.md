# Tetragon·Cilium 규칙 처음 적용·동기화

`enforcement.apply`는 현재 Gateway가 승인 검증해 활성화한 묶음의 `enforcement_intent`만 사용한다. 서버 ID, 묶음 ID·SHA-256, target의 context·namespace를 재검증한다. 묶음 설치·Gateway 재시작은 기존 `bundle.apply`/`bundle.switch` 단계다. 이 기능은 외부 정책을 생성·교체하며 새 bundle을 설치하지 않는다.

## 처음 적용

1. 기존 묶음 적용을 끝내고 Gateway의 bundle ID·SHA-256, `approval=verified`, `gateway_active=true`를 확인한다. 에이전트 계정의 kubeconfig에는 대상 namespace의 TracingPolicyNamespaced/CiliumNetworkPolicy `get,list,create,update,patch,delete`, Cilium CRD `get`, Tetragon namespace의 daemonset/pods 조회·pods/exec, Gateway port-forward 권한이 필요하다. 별도 sudo 경로를 추가하지 않는다. CRD가 존재하지만 권한이 부족한 경우에는 미설치로 간주하지 않고 실패한다.
2. 웹 **운영 요청 → 외부 규칙 처음 적용·동기화**에서 서버와 구성요소를 선택한다. Tetragon은 필수이고 Cilium은 선택이다. 에이전트가 보고한 현재 묶음 해시가 없거나 상태가 오래되면 먼저 조회를 갱신한다. `runtime_operator`가 요청하고 다른 `approver`가 승인한다. 이 종류는 LAB 설정에서도 자기 승인을 허용하지 않는다.
3. 기본 에이전트(`execute=false`)는 렌더·비교·서버 dry-run·Cilium diff까지만 실행하고 `checked/DRY_RUN`으로 종결한다. 승인된 요청도 자동 재사용하지 않는다. 결과를 검토한 뒤 새 요청을 만들고 `--execute` 에이전트로 수행한다.
4. **Cilium 실제 적용**은 기본 꺼짐이다. 켜면 monitor 모드 없이 즉시 트래픽을 차단할 수 있다. CRD 부재는 `not_installed`로 건너뛴다. 설치돼 있으면 기본은 SSA server dry-run·diff이며, 실제 생성·교체는 `cilium_apply=true`와 `execute=true`가 모두 있어야 한다. 적용 전 create/replace 자체도 서버 dry-run으로 검사한다.

수동 경로도 같은 함수를 사용하며 기본은 dry-run이다. 실제 설치 경로·식별자로 자리표시자를 바꾼다. 운영 에이전트와 동시에 실행하지 말고 같은 lock 파일을 사용하거나 에이전트를 중지한 유지보수 시간에 실행한다.

```bash
.venv/bin/python -B -m serving_runtime enforce sync \
  --existing '<현재_묶음_ID>' --bundle-root '<묶음_루트>' \
  --context '<context>' --namespace '<namespace>' \
  --kubeconfig '<kubeconfig_파일>' --token-env-file '<Gateway_인증_env>' \
  --lock-file '<운영_잠금_파일>' --components tetragon cilium
```

`--existing` 대신 `--bundle-dir '<검증할_묶음_폴더>'`도 가능하다. 어느 입력이든 설치된 current와 ID·해시가 같아야 한다. 실제 Tetragon 적용은 `--execute`, Cilium까지 실제 적용하려면 추가로 `--cilium-apply`를 명시한다. CLI는 서버에서 실행 권한을 가진 사람이 직접 사용하는 경로이며 플랫폼 승인 요청을 만들지는 않는다.

## 확인

- 결과는 `validation, render, dry-run, apply, verify` 단계와 정책별 이름·구성요소·`created/replaced/unchanged/extra/skipped`·모드·spec SHA-256을 제공한다. dry-run 정책 동작은 **실행 예정 동작**이고, Cilium만 미적용인 혼합 실행은 component의 `dry_run`으로 구분한다. manifest·diff·명령 출력·예외 원문·인증값은 결과에 포함하지 않는다.
- Tetragon은 모든 후보에 `policy-mode=monitor`를 명시한다. 변경 전 모든 예정 daemon의 enabled·동일 실제 모드를 직접 조회한다. 현재 enforce인 정책이 달라졌거나 모드가 불명확하면 `SAFETY_REJECTED`; 같은 spec의 enforce 정책은 그대로 `unchanged`다. 차단 전환은 기존 `tetragon.mode`와 readiness 경로만 사용한다.
- 기존 spec 자체가 enforce로 다시 로드될 수 있으면, 실제 모드가 monitor라도 교체를 거부한다. rollback이 의도치 않게 enforce를 켜는 것을 막기 위함이다. Post 전용이고 모드 옵션이 없는 기존 spec은 안전한 복원 대상으로 인정한다.
- Gateway의 expected-policy 해시도 monitor 명시 렌더와 맞췄다. 예전 Post 전용 spec에 모드 옵션이 없으면 동기화 전에는 해시 불일치가 표시될 수 있다. 정책 수집기의 새 spec·모니터 창을 다시 확인하고, 기존 차단 시험 근거를 새 spec의 근거로 재사용하지 않는다.
- 적용한 객체는 다시 조회해 spec을 확인하고 Tetragon의 enabled·monitor/monitor_only 로드를 확인한다. Cilium 변경 후에는 Gateway의 현재 묶음·승인 상태와 고정 짧은 추론 요청(허용 모델 첫 항목, 입력 `ping`, 출력 1토큰)을 확인한다. 인증 배포는 기존 env에 `RUNTIME_INFERENCE_TOKEN`이 필요하다. 이 확인은 전체 네트워크 허용·차단 시험을 대체하지 않는다.
- 묶음에 없는 같은 namespace의 기존 정책은 `extra`로 보고하고 삭제하지 않는다. 정책 이름·spec 해시만 보고하며 extra의 모드는 `null`이다.

## 실패·되돌리기

적용 전에 기존 객체를 0700 임시 폴더 안의 0600 파일에 보관한다. 전체 후보의 dry-run을 통과해야 첫 변경을 시작한다. 적용 직전 current·임대·객체 UID/resourceVersion·Tetragon 모드를 다시 확인한다. 이번 변경에는 임시 식별 annotation을 붙인다. 중간 오류·timeout·확인 실패 시 역순으로 이전 객체를 복원하며, 이번에 생성한 객체는 UID/resourceVersion 조건부 DELETE로 제거한다. 다른 작업이 바꾼 객체를 덮어쓰거나 삭제하지 않는다.

복원 spec·실제 모드·Gateway 확인까지 되면 `rolled_back/ROLLED_BACK`, 확인할 수 없으면 `unknown/STATUS_UNKNOWN`이다. 지연·모호한 변경 명령은 다시 실행하지 않는다. 임시 백업은 함수 종료 시 정리되므로 수동 복구에 필요한 사본은 유지보수 전에 운영자가 별도 0600으로 보관한다. 원문을 플랫폼 결과나 공유 로그로 보내지 않는다.

`unknown`이면 자동 재요청하지 말고 Claude가 실제 객체·Tetragon 모드·Gateway와 통신을 확인한다. 수동 복구는 보관한 이전 객체와 **현재 resourceVersion**을 대조해 복원하고, 새로 생성된 정책 제거는 소유·참조를 검토한 뒤 수행한다. 묶음을 `bundle.switch`로 되돌린 것만으로 외부 정책이 복원되지는 않는다. 이전 묶음이 current로 검증된 뒤 다시 sync하고 `extra` 정책은 사람이 검토한다.

실서버의 RBAC, Tetragon 로드 지연·여러 daemon, Cilium 전달 지연·추론 및 차단 효과·복원은 로컬 가짜 runner 시험만으로 확인되지 않는다.
