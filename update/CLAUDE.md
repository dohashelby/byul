# serving-guard 작업 규칙

이 폴더는 "서빙엔진 보안 검증 솔루션"을 새로 만드는 작업 디렉토리다. 세션을 시작하면 이 파일이 자동으로 읽힌다.

## 정본과 참고
- **`SPEC.md`가 정본이다.** 객체 7종, 불변식 INV-01~19, 파이프라인, 플러그인 인터페이스, 개발 순서(§8)가 모두 여기 있다.
- `reference/framework/` : 점검 77행의 원천 데이터(`data/checklist.json`)와 환경·결과 템플릿. **필요할 때만 찾아본다.**
  - `03_체크리스트와_보완가이드.md`는 37만 자다. **통째로 읽지 않는다.** 필요한 행만 grep으로 찾는다.
  - 점검 데이터는 `data/checklist.json`을 코드로 읽는다(문서를 파싱하지 않는다).
- `reference/bob-design/` : 이전 프로젝트(BoBProject)의 설계 문서. **구조 참고용이다.** 여기 있는 서명 승인, 감사 outbox, CAS, 객체 20여 종, 웹 UI를 만들지 않는다(SPEC §9).
- SPEC과 참고 문서가 충돌하면 SPEC을 따르고 `DECISIONS.md`에 한 줄 적는다.
- 변경 유형별 시험 범위(엔진 정식 릴리스 전체 시험·소스 diff 보고, 패치 릴리스는 diff 선정·이월, 모델·환경·정책 변경은 증분 감사·이월)는 `docs/UPDATE_SELECTION.md`가 SPEC "U1" 절의 세부 정본이다(2026-10-25 사용자 결정).

## 기술 기준
- Python 3.12만 지원(`>=3.12,<3.13`), `uv` 사용, 패키지명 `guard`, `src/guard/` 레이아웃(SPEC §10). 현행 개발·제품·CI·시험 보조 Python 환경은 3.12로 맞춘다. vLLM 대상 이미지의 내부 Python은 독립된 환경이며 기존 digest·검토 프로파일은 이 전환으로 바꾸지 않는다. 과거 3.11 실험의 환경 표기·원본 증거·저장 팩은 당시 사실대로 보존하며 별도 3.11용 소스나 제품을 유지하지 않는다.
- pydantic v2, typer, pyyaml, httpx, pytest. 그 외 의존성은 추가 전에 사람에게 묻는다.
- 모든 객체는 append-only. 해시 규칙은 SPEC §2.3.

## 작업 방식
1. SPEC §8의 개발 순서를 따르되, 합의한 구현 묶음을 마친 뒤 테스트한다. 묶음 안의 각 단계마다 테스트를 실행하지 않는다.
2. **사용자 지시(2026-10-19): 구현을 한 묶음으로 마친 뒤 테스트 → 실패 수정 → 필요한 재검증 순서로 진행한다.** 불변식 회귀는 `tests/invariants/test_inv_XX.py`에 유지하고, 구현이 불변식을 어기면 구현을 고친다. 구현 중간에 같은 테스트를 반복 실행하지 않는다.
3. 코어(`core/`, `models/`, `store/`)에 엔진 이름(`vllm` 등)을 쓰지 않는다. 엔진별 코드는 `adapters/`에만.
4. 실행하지 않은 시험의 결과를 만들거나 예시 값을 `MEASURED`로 표시하지 않는다(INV-02).
5. **사용자 지시(2026-10-24): 60초를 넘겨도 중단하지 않으며 시간 초과 실패 gate를 추가하지 않는다.** 전체 suite의 pytest 시간과 부모 프로세스 벽시계를 각각 기록한다. 중복 준비 비용은 줄이되 기존 사례·assert·기대값·불변식을 완화하거나 새 skip/제외로 통과시키지 않는다. 실제 엔진이 필요한 테스트의 `@pytest.mark.engine`과 기존 기본 제외 조건은 유지한다.
6. 아래 "진행 방식"의 승인 범위·중단 조건을 따른다. 새 결정이 필요한 변경만 보류하고 질문하며, 독립적으로 가능한 작업은 계속한다. 팀 결정이 필요한 질문은 `DECISIONS.md`의 "열린 질문"에도 적는다.
7. 단계가 끝날 때마다 `PROGRESS.md`에 "한 일 / 테스트 결과 / 다음 단계 / 막힌 것"을 짧게 갱신한다.

## 하지 않는 것 (SPEC §9)
전자서명·registry, 감사 outbox, 웹 UI·로그인, 게이트웨이 구현, LLM 판단 보조, vLLM 외 엔진 어댑터 구현, 77행 전부 자동화.

## 진행 방식 (2026-10-20 추가)
- 새 실행기 종류나 `core/`·`models/`·`judges/` 변경까지 현재 요청·승인된 계획에 포함됐는지 확인한다. 해당 변경까지 승인된 범위는 다시 묻지 않고 진행한다. 포함되지 않은 변경은 보류하고 질문한다.
- 근거가 없으면 UNKNOWN. 상태를 바꾸는 요청은 보내지 않는다(검증된 안전 프로브만). 판정 규칙을 결과에 맞춰 고치지 않는다.
- 승인된 안전 요청 형식·경로와 기술 설정의 기본값은 보수적으로 정하고 지속되는 결정만 `DECISIONS.md`에 한 줄 기록한다. 기업의 허용 기준·한도·승인값은 임의로 채우지 않는다. 예시 값은 `EXAMPLE`로 구분하며 미입력·명시적인 빈 값의 기존 의미를 바꾸지 않는다.
- 승인 범위를 확대해야 하거나, 승인된 범위에 포함되지 않은 SPEC 제품 계약·불변식·판정 의미·수락 기준·의존성·비용·운영 대상·기존 사용자 자원의 변경이 필요할 때 해당 변경을 보류하고 질문한다.
- 실제 `FAIL`·`UNKNOWN`·`NOT_COMPARABLE`은 원본과 원인을 기록하고 승인된 검증을 계속한다. 결과가 예상과 다르다는 이유만으로 모든 작업을 중단하거나 정책·시험 조건·판정 기준을 바꾸지 않는다.

## 개발 효율 원칙 (2026-10-25 추가)
- **실행기는 점검마다 만들지 않는다.** 정책·점검을 추가할 때 기존 관측과 실행기의 재사용을 먼저 검토한다. 정책값이나 판정 조건만 달라지면 새 실행기를 만들지 않고 기존 관측과 정책값으로 판정한다(예: capability·mount를 이미 수집하면 허용 목록이 다른 정책은 판정 데이터만 추가). 기존 실행기로 수집할 수 없는 관측이나 새로운 시험 절차가 필요할 때만 실행기를 확장하거나 새로 만든다. 기존 수집으로 확인할 수 없는 사실을 주장하지 않는다(예: 마운트 목록만으로 실제 파일 접근 가능성을 확인했다고 하지 않는다). 여러 점검이 같은 수집 기반을 공유해도 점검별 정책·증거·판정·검증 범위는 구분한다.
- **소스를 확정한 뒤 검증한다.** 구현·테스트 코드·문서 초안·정적 검토를 마치고 모든 담당자의 파일 수정을 종료한 뒤 검증할 소스 snapshot과 파일 해시를 확정한다. 검증을 위해 먼저 커밋할 필요는 없다. 확정 뒤 수정은 영향 범위를 기록하고 직접 테스트·같은 계약 테스트·불변식 회귀부터 재검증한 뒤 최종 기본 suite와 필요한 통합 검증을 수행한다. 공통 계약·불변식에 영향이 있거나 영향 범위가 불명확하면 전체 검증을 다시 수행하며, 전체 검증을 무조건 한 번으로 제한하지 않는다.
- **문서·주석만 바뀌면 전체 시험을 반복하지 않는다.** 시작 시점 대비 `git diff --stat`과 실제 diff로 `src/`·`packs/`·`tools/`·`tests/`뿐 아니라 `pyproject.toml`·`uv.lock`·CI·실행/빌드 설정의 변경도 확인한다. 제품 동작에 영향이 없는 문서·주석 변경이면 관련 정합성을 검증하고 기본 suite·wheel·실제 엔진 시험을 반복하지 않는다. 주석 변경은 파일 바이트가 달라졌음을 기록하고 AST 등으로 실행 로직의 동일성을 정적으로 확인한다.
- **실제 엔진 시험은 묶어서 한다.** 같은 이미지 digest·모델·기동 설정의 시험은 상태 독립성과 사례별 정책·계획·증거·출력 분리를 확인한 뒤 한 번의 기동으로 묶는다. 정상 대조와 전후 상태 확인을 하고, 재시작·OOM·모델 변경·상태 독립성 불확실이 생기면 새로 기동한다. 서로 다른 두 이미지의 업데이트 비교를 같은 엔진 재사용으로 대신하지 않는다.
- **작업 크기를 유형별로 잡는다.** 정책값 설정 / 기존 관측을 쓰는 판정 추가 / 새 관측 추가 / 새 실행기 / 엔진 내부 원인 증명은 필요한 검증이 다르다. "정책 하나 → 실행기 하나 → 전체 테스트 → 두 이미지 실증"을 기본 단위로 삼지 않는다. 새 관측·시험 절차뿐 아니라 실제 엔진 동작·요청 실행 경로·기동 설정·프로파일·비교 조건에 영향을 주는 변경과 사용자의 명시적인 실증 요청도 고려해 필요한 실제 시험 범위를 작업 계획에서 정한다. 모든 정책 변경에 두 이미지 전체 실증을 요구하거나 단순 문서·판정 데이터 변경만으로 엔진을 자동 재기동하지 않는다.
- 시간은 구현·테스트·엔진 준비·수집으로 나눠 기록한다. 테스트 삭제·새 skip·기대값 완화로 시간을 줄이지 않는다.
- **사용자 지시(2026-10-26, AWS 전략 갱신):** 독립적인 CPU 구현·회귀는 계속하고 Kubernetes 전체 이식이나 GPU 준비를 선행 조건으로 삼지 않는다. 가까운 대표 제품 경로에 필요한 대상/세대·전송·수집 경계만 기존 실행기에서 분리해 조기 확인한다. GPU는 준비된 시험 묶음과 비용 계획에 한해 사용하며 CPU·대역 결과를 Kubernetes/GPU 실증으로 승격하지 않는다. sources/와 AWS 인계 원본은 읽기 전용이다.

## BYUL UPDATE 경계 (2026-10-26)

- `../contracts/README.md`와 실제 스키마는 외부 교환 형식의 기준이다. guard 내부 모델은 유지하고 경계에서 변환한다. 공용 스키마·enum·생산자·표시 소유권을 임의 변경하지 않는다.
- RPT JSON이 원본이고 verification-result 변환과 화면은 platform 담당이다. `report/html.py`·`--html`을 복구하지 않는다. OBS 증거 HTML은 별개다.
- 공용 계약의 null·UNKNOWN·정확한 Ref·정규 문서 해시와 파일 bytes 해시·자료 출처를 보존한다. 계약 문서에 본문·토큰·Secret을 추가하지 않는다.
- 초기 v1과 77개 구현·실험 확대 로드맵을 구분한다. 현황은 `tools/checklist_status.py`로 재생성하며 미검증 분기·과거 팩·실증 대기를 명시한다.
- 재검증 요청 수신은 엔진 기동 승인이 아니다. 현재 플랫폼의 읽기 전용 조회 경계를 유지한다.
