## 1.1 무엇을 해결하려는가

기업이 모델을 직접 운영하면 엔진·모델·실행 설정과 접근 권한을 업무에 맞게 구성할 수 있다. 그만큼 모델 반입, API 노출, 내부 통신, 자원 사용, 로그 보관과 업데이트도 직접 관리해야 한다.

우리 프로젝트는 담당자가 다음 세 질문에 답하도록 돕는다.

1. **어떤 위험을 확인해야 하는가?** 서빙 동작과 보호 요구를 분석해 환경에 맞는 점검을 고른다.
2. **무엇이 부족하고 어떻게 보완해야 하는가?** 기존 통제의 범위와 빈틈을 확인하고 설정·권한·운영 절차를 보완한다.
3. **도입하거나 업데이트해도 되는가?** 보안·정상 기능·성능 결과와 확인하지 못한 내용을 검토하고, 담당자가 적용·재시험·보류를 결정한다.

![ServeGuard 프로젝트 전체 흐름 — 업데이트 검증·격리 시험·런타임 통제](assets/project-overview.png)

*공통 보안 기준으로 변경 영향을 분석하고, 현재·후보 환경을 격리 시험한 뒤 담당자가 적용 여부를 결정한다. 운영에서는 승인한 정책과 구성을 확인한다. 그림의 배지는 현재 코드와 목표 연동을 표시하며, 현재 제공 범위는 1.6에 정리했다.*

**숫자와 용어부터 읽기**

| 용어 | 뜻 |
| --- | --- |
| TP·rank | TP는 Tensor Parallelism으로 하나의 모델 계산을 여러 GPU가 나눠 수행하는 병렬 실행. rank는 그 실행에 참여하는 구성원이다. |
| KV cache·prefix cache | KV cache는 이전 토큰 계산의 중간 결과를 보관한다. prefix cache는 같은 앞부분의 계산 결과를 재사용한다. |
| 보호 요구·CHK | 보호 요구는 유지해야 할 보안 조건이다. CHK는 적용 조건·시험·판정 기준을 갖춘 세부 점검의 번호다. |
| SC·Q | SC는 구체적인 위협·실패 시나리오, Q는 점검을 도출할 때 참고한 정책·코드·사례·절차를 모은 기록이다. |


여덟 보안 기능 아래에 보호 요구 36개와 점검 77개를 배치했다. 예를 들어 **1 인증·접근 통제 → 1.3 승인 권한 분리 → 1.3.1 권한 분리(CHK-SUP-001)** 순서로 읽는다. CHK ID의 접점 코드는 유지했다. 환경과 활성 기능에 따라 각 점검에서 확인할 내용을 고른다. 시나리오 83개는 점검이 필요한 상황을, Q 28개는 점검의 정책·코드·사례 근거를 담는다.

## 1.2 서빙엔진의 동작과 위협

서빙엔진은 준비한 모델을 읽어 GPU에 올리고, 들어온 요청을 변환·배치해 실행한 뒤 결과를 반환한다. 이 과정에서 여러 요청이 계산 자원·캐시·버퍼를 함께 사용하고, 운영자는 모델·설정 변경과 장애 복구를 수행한다.

| 동작 | 문제가 생길 수 있는 상황 | 필요한 보호 |
| --- | --- | --- |
| 모델·코드 준비 | 승인 후 파일이 바뀌거나 함께 읽는 추가 코드가 승인에서 빠짐 | 승인 범위 확인과 실제 사용 파일 대조 |
| 요청·결과 처리 | Gateway 우회, 다른 모델·결과 사용, 입력 변환 뒤 검사 누락 | 최종 API·모델·입력·결과의 권한과 처리 확인 |
| 공유·GPU 실행 | 다른 요청의 상태·자료가 남거나 캐시 공유 범위를 벗어남 | 공유 집단·상태 갱신·버퍼 수명 확인 |
| 변경·종료·관측 | 취소 뒤 작업 잔존, 불완전한 복구, 민감한 로그 공개·증거 누락 | 종료·재개 조건과 기록 보호·수집 상태 확인 |

이 위험은 엔진 버전뿐 아니라 실제 배포·활성 기능·권한에 따라 달라진다. 그래서 공통 보호 기준을 먼저 정하고, 기업의 환경에 맞는 점검과 시험을 선택한다. 02에서 목표·관리 체계와 여덟 보안 기능의 요구를 설명하고, 03에서는 실제 동작과 위협 경로를 자세히 살펴본다.

## 1.3 일반 소프트웨어 업데이트와 무엇이 다른가

이미지·의존성·API 권한·네트워크를 확인하는 기본 원칙은 다른 소프트웨어에도 적용된다. 서빙엔진에서는 다음 동작 때문에 시험 조건과 증거가 더 필요하다.

| 서빙 동작 | 업데이트 때 확인할 내용 |
| --- | --- |
| 모델·tokenizer·template·추가 코드의 조합 | 승인한 묶음과 실제로 선택해 읽는 파일·코드가 같은가? 로더나 기본값 변경으로 다른 코드·형식을 읽지 않는가? |
| 여러 요청의 배치 처리와 KV·prefix cache 재사용 | 각 자료가 어느 사용자·모델·요청에 속하는지 구분하고, 허용한 범위에서만 공유하는가? |
| GPU 실행·컴파일·CUDA Graph·TP 통신 | 선택한 실행기(runner)와 실행 모드에서 입력을 제때 갱신하고, 버퍼와 참조를 사용하는 동안 유효하게 유지하는가? |
| 스트리밍·취소·worker 장애 | 응답이 끝난 뒤 실제 작업·전송·참조가 정리되는가? |
| 모델·이미지·설정의 변경과 복구 | 필요한 모든 worker가 준비됐는가? 현재 승인에 맞는 상태로 복원됐는가? |

사용하는 기능과 바뀐 처리 경로를 확인해 필요한 시험을 선택한다.

### Gateway가 있어도 왜 확인해야 하는가

Gateway는 인증·인가·요청 제한을 맡을 수 있다. 모델 파일을 읽는 과정, 내부 IPC·TP 통신, GPU 상태 재사용, 서버의 외부 송신과 실패 후 정리는 각 경로에서 적용하는 통제도 확인해야 한다. Gateway를 거치지 않는 직접 접근이 가능한지도 별도 시험한다.

따라서 시험 결과에는 **엔진 자체 동작**과 **Gateway 등 통제를 적용한 결과**를 각각 남긴다. Gateway의 차단 결과와 엔진의 수정 동작은 각각의 실행 증거로 확인한다.

### 프레임워크의 특화 범위

서빙엔진의 취약 원리를 보호 요구·방어 위치·적용 조건·CHK에 대응시켰다. 요청·공유 자원의 재사용과 실패·취소·복구 과정도 분석한다. 거버넌스와 환경·생명주기·평가 절차는 이 요구를 누가 언제 적용하고 확인할지 설명한다. 선행 자료와 비교한 추가 기여와 실제 대책 효과는 항목별 대조·실행 시험으로 확인할 과제다.

## 1.4 누가 어디에 사용하는가

| 사용자 | 제공하거나 판단할 내용 |
| --- | --- |
| 플랫폼 운영자·ML 엔지니어 | 실제 엔진·모델·설정·배포 환경과 정상 요청 예시, 서비스 요구사항, 시험 자원 |
| 보안 담당자·검토자 | 보호 요구, 허용·금지 대상과 예외, 시험·증거의 충분성, 보완 사항 |
| 승인 담당자 | 결과·남은 위험·운영 조건을 검토해 적용·재시험·보류 결정 |

주요 대상은 서빙엔진과 실행 환경을 직접 관리하는 조직이다. 내부 직원용·고객용 모두 실제 호출 경로와 책임 범위를 확인한다. 관리형 서비스는 고객이 설정·관측할 수 있는 접점을 먼저 확인하며, 고객이 직접 확인한 설정·증거와 사업자에게 확인받을 내부 동작을 나눠 기록한다.

**분석 범위:** 추론 요청·실행, 모델·코드 공급과 로딩, 직접 연결된 호스트·자격·통신, 배포·변경·복구, 관측 자료다. 업무 앱·Gateway·Kubernetes·저장소는 이 흐름과 연결된 접점을 본다.

학습 전체, RAG·에이전트·업무 앱 전체 감사, 모델의 일반적인 품질 순위, 모든 프롬프트 주입·유해 응답 방어는 현재 평가 범위에 포함하지 않는다. 기업 정책·법규 전체의 자동 해석이나 준수 인증도 제공 목표에 포함하지 않는다.

## 1.5 최종 산출물 여섯 가지

| 산출물 | 제공할 내용 | 사용자가 얻는 결과 |

| ③ 업데이트 검증 자동화 도구 | 현재·후보 환경 비교, 등록한 시험의 선택·실행, 증거 수집·비교·보고 지원 | 반복 가능한 검증 실행과 결과 |

| ⑤ 런타임 통제·관측 기능 | 송신 제한, 지원하는 API 통제 연동, 승인 구성 변경·수집 장애 확인 | 적용 상태·허용/거부·경보·재평가 요청 |
| ⑥ 재현·운영 자료 | 설치·시험·연동·결과 해석·장애 대응·지원 범위 | 다른 담당자의 재현과 운영 |

①은 전체 체계이며 ②는 이를 실제 점검에 쓰는 자료다. ③이 시험을 지원하고 ④가 결과를 정리한다. ⑤는 승인 조건을 운영에서 확인하고 ⑥은 설치·재현·운영을 돕는다. 세 묶음으로 보면 **프레임워크와 점검 기준 / 업데이트 검증과 보고 / 운영 통제와 관측**이다.

## 1.6 현재 어디까지 준비됐는가

**현재 제공 범위**

| 구분 | 현재 상태 |
| --- | --- |
| 정리된 기준 | 일곱 구성요소, 여덟 보안 기능과 보호 요구 36개·점검 77개, 공격·실패 원리 17개·서빙 접점별 분석 묶음 24개·시나리오 83개, 환경별 확인 항목 12개와 점검·증거·판정 기준. API 전송 보호, 기록의 저장 암호화, 사용 종료 모델의 실행 차단을 기존 점검에 반영 |
| 개발 중인 기능 | 환경 정보 수집, 적용 점검·시험 선택, 업데이트 비교·보고, 런타임 통제·관측 연동. 전체 기능을 실제 환경에서 함께 실행해 확인하는 작업이 남아 있다. |
| 검증이 남은 범위 | 기업별 허용 대상·정책값·수치를 정한 뒤 실제 엔진과 GPU를 사용해 평가해야 한다. 외부 자료·파일 작업(R10)은 미디어 일부를 코드로 검토했고 전체 평가는 남아 있다. 관리형 서비스·외부 대체 실행(R14)은 검토 대기다. 다른 엔진·버전의 상세 적용도 추가 확인이 필요하다. |

기존 접점별 팀 참조 정책에는 허용·금지 원칙을 정리했다. 실제 적용에는 자료 등급별 저장 암호화 요구, 구간별 통신 보호 방식·예외와 기업별 허용 대상을 정해야 한다. 자원 한도·종료 기한·시간 오차 등 시험 수치도 남아 있다. 실제 기업에서는 자신의 모델·계정·공유 관계·통신 목적지·자원·보존 기준을 확인해 적용한다. 실제 시험과 항목별 판정은 앞으로 수행해 기록한다.

## 1.7 이 자료를 읽는 순서

전체 설명은 [보안 프레임워크](02_보안_프레임워크.md)의 큰 목차를 따른다. 전체 설명은 **목표와 범위 → 거버넌스 → 위험 관리 → 보안 기능과 보호 요구 → 환경별 적용 → 생명주기 → 평가와 보완** 순서로 읽는다.

실제 평가는 **환경 확인 → 점검·시험 분기 선정 → 시험·증거 수집 → 판정·보고·후속 결정** 순서로 진행한다. 환경·점검은 [04](04_환경별_적용과_체크리스트.md), 시험·판정은 [06](06_평가와_솔루션_런타임.md), 엔진·버전은 [07](07_엔진별_적용가이드.md)에서 확인한다.

- **멘토링·프로젝트 소개:** 01 → 02 → 06. 필요할 때 위협 지도·체크리스트·매트릭스를 연다.
- **실제 평가 준비:** 04의 요약표와 같은 번호의 해설에서 조건·기준을 확인하고, 05에서 위협·근거를 살펴본 뒤 06의 시험·판정 절차를 따른다.
- **필요한 기준 찾기:** 04에서 점검을 찾고, 05에서 관련 위협과 통제를 확인한다. 세부 조건은 각 CHK·SC 링크에서 읽는다.

이 일곱 페이지는 소개와 활용을 위한 **공유 페이지 01–07**이다. 별도로 유지하는 **상세 원문 01–05**와 번호가 다르다.

| 찾는 내용 | 상세 원문 | 찾는 방법 |
| --- | --- | --- |
| 정상 흐름·R별 코드 근거 | [통합본](../참고자료/통합본/통합본.md) | 담당 R과 관련 근거 위치 검색 |
| 구체 위협·실패 조건 | [원문 01 — 위협별 보호 대책](../01_프레임워크와_위협통제연결.md) | SC ID 검색 또는 공유 페이지 05의 SC 링크 |
| 실제 점검·정책·시험·판정 | [원문 03 — 체크리스트](../03_체크리스트와_보완가이드.md) | CHK ID 검색 또는 공유 페이지 04의 CHK 링크 |
| 엔진·버전별 근거 | [원문 04 — 엔진·버전 차이](../04_엔진과_버전별_차이.md) | 버전·기능·처음 보는 버전 항목 |
| 결과 집계·보고·재현 예시 | [원문 05 — 평가·증거 관리](../05_평가와_증거관리.md) | 평가 단계와 기록 예시 |

상세 원문은 GitHub의 같은 이름 문서에서 확인할 수 있다. 실제 평가에는 각 CHK의 적용 조건·필수 분기·증거·판정 기준을 함께 확인한다.
