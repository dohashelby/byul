## 3.1 분석 대상과 그림 읽는 법

[위협지도 탐색 열기](위협지도_탐색.html) — 공유 폴더의 HTML 파일을 브라우저에서 열고 **흐름의 위치 → 시나리오 → 관련 점검 → 도출 근거** 순서로 살펴본다.

현재 분석의 참조 구성은 **사용자 → Gateway → vLLM v0.31.0 → 단일 노드 다중 GPU·TP 그룹 1개 → 응답**이다. 텍스트 모델 하나, 일반·스트리밍 요청, KV·prefix cache를 사용한다. 이미지·모델·설정 변경은 중단 후 재시작·재배포로 처리한다.

앱이 사용자를 대신해 호출하면 `사용자 → 업무 앱/백엔드 → Gateway → vLLM`처럼 실제 순서를 적는다. 최종 사용자와 엔진에 연결한 서비스 계정은 다를 수 있다.

![정상 서빙의 세 가지 큰 흐름](assets/dfd-overview.png)

그림의 상자는 처리 주체·자료·기능을, 큰 묶음은 관련 기능을 나타낸다. 자료가 이동하면서 소유자·권한·자료에 대한 신뢰가 달라지는 지점에는 신뢰 경계를 표시한다. 서버·네트워크 위치는 실제 접근에 영향을 주는 곳에 함께 적는다. 상세 그림에서는 주요 호출과 실패 흐름을 따라간다.

### 동작 흐름에서 보안 요구를 찾는 방법

그림은 자료·요청·권한이 이동하는 경로를 보여준다. 각 경로에서 깨질 수 있는 조건을 아래 여덟 보안 기능으로 분류하고, 04의 보호 요구와 CHK에서 확인한다. R 번호와 기존 다섯 접점 코드는 동작·정책 근거를 찾는 색인으로 사용한다.

| 경로에서 확인할 내용 | 해당 보안 기능 |
| --- | --- |
| 호출자·관리자·프로세스의 권한과 자격 | 1 인증·접근 통제 |
| 승인한 모델·코드·생성물과 실제 소비 대상 | 2 공급물 무결성 |
| 입력 변환·자료 해석·코드 실행·GPU 메모리 경계 | 3 입력 처리·코드 실행 안전성 |
| 요청 소유자·공유 범위·재사용 문맥·버퍼 수명 | 4 상태 격리·재사용 안전성 |
| 응답·로그·통계·저장·전송에서의 자료 보호 | 5 정보·통신 보호 |
| 예산·재시도·장애 영향·작업 종결 | 6 자원 관리·서비스 가용성 |
| 검사 결과·기동 준비·변경·복구 | 7 구성·변경 관리 |
| 필수 사건·기록 무결성·관측 상태 | 8 감사 기록·관측 신뢰성 |

## 3.2 모델 준비·승인·로딩

아래 표는 **조직의 승인·배포 통제와 vLLM이 파일·코드를 선택해 사용하는 경로를 함께** 보여준다. 조직은 검사·승인 절차와 신규 요청 제한을 구성한다. 어떤 구성요소가 검사·차단을 맡는지, loader·rank가 어떤 자료를 실제로 사용하는지 확인한다.

![모델 취득·승인·로딩 과정](assets/dfd-models.png)

| 순서 | 정상 동작 | 확인할 보호 조건 |
| --- | --- | --- |
| 1. 제출·취득 | 지정 공급원에서 모델·설정·tokenizer·필요 코드를 받거나 로컬 반입 | 제출자 권한과 서버가 사용하는 저장소 자격 |
| 2. 검사·승인 | 필수 검사 결과를 확인하고 실제 사용할 이미지·파일·설정을 승인 묶음에 포함 | 승인 권한, 대상 식별, 검사 오류·생략 처리 |
| 3. 로더·파일 선택과 해석 | 실행 설정에 따라 실제로 사용할 로더·파일 해석기·모델 구현과 파일 목록 선택 | 별칭·redirect·추가 공급원·기본값이 승인 범위를 바꾸는지 |
| 4. 파일 읽기·메모리 적재 | loader가 파일을 읽고 필요한 worker·TP rank가 담당 모델 부분을 적재 | 승인한 파일이 실제로 열렸는지, 어떤 변환을 거쳐 각 rank에 적재됐는지 |
| 5. 컴파일 결과·캐시 준비 | 선택한 실행 모드에서 필요한 컴파일 결과·cache 등 준비·재사용 | 생성 도구·입력·권한이 현재 실행 조건에 맞는지 |
| 6. 서비스 준비 | 필요한 rank·실행 모드 준비와 정상 요청을 확인한 뒤 접수 | 모델 로딩 뒤 서비스 전체의 준비 여부 |

**일치 확인:** 승인한 묶음과 각 rank가 실제로 읽은 파일, 담당 shard, 변환·적재 기록을 대조한다. 파일 해시는 읽은 파일을 식별하는 증거로 사용하고, rank별 적재 결과는 각자 맡은 모델 부분을 기준으로 확인한다.

R은 정상 동작 경로를 구분한 번호다. 이 과정의 관련 경로는 주로 R05·06·07·09다. R08은 별도의 공유 가중치 daemon·원격 공급을 선택한 환경에 적용한다.

## 3.3 요청 수신·추론 실행·결과 반환

![요청 입력부터 실행·반환까지의 상세 흐름](assets/dfd-requests.png)

| 순서 | 정상 동작 | 확인할 보호 조건 |
| --- | --- | --- |
| 1. 진입·권한 확인 | 앱/Gateway가 신원을 검증하고 허용 작업·모델을 선택 | 실제 API 경로, 경로 재작성, 직접 접근 가능 여부, 서비스 계정을 통해 요청한 사용자 |
| 2. 입력 준비 | 요청을 파싱하고 template·토큰화·선택 전처리를 적용 | 앞단이 검사한 입력과 엔진이 실제로 처리하는 입력의 일치 |
| 3. 실행 등록 | 외부 요청별 내부 실행·collector·선택 모델 기록 | 외부 요청 ID·실행 시도·child request의 사용자와 모델 일치 |
| 4. 배정·공유 상태 사용 | scheduler가 요청을 배치하고 KV·prefix cache 및 자원을 관리 | 공유를 허용한 집단, 캐시 키에 포함한 정보, batch slot 이동에 따른 상태 갱신 |
| 5. worker·TP 실행 | 선택한 runner·kernel·실행 모드에서 연산하고 필요한 rank 간 통신 | 입력·버퍼·handle의 사용·해제 시점과 로컬 IPC·TP 통신 상대의 접근 권한 |
| 6. 출력 처리 | 생성 결과를 원래 요청에 맞춰 일반·스트리밍 응답 반환 | 결과를 받을 사용자, 프롬프트·토큰 사본과 오류 필드의 공개 범위 |

선택 기능에서는 `kv_transfer_params.prompt_token_ids` 같은 필드가 일반 template·토큰화 경로와 다른 입력을 선택하게 할 수 있다. 어떤 입력을 허용·전달하는지, template·토큰화 중 어떤 처리를 생략하는지, 이후 어떤 검사를 거치는지 확인한다.

기본 CUDA 구성의 runner 선택과 V1·V2 경로를 확인한다. 실제 사용하는 runner에서 mask 초기화와 과거 패치의 적용 여부를 확인한다. CUDA Graph는 입력 갱신 → 연산 → 출력 사용 → 버퍼 재사용 순서를 따라가며, 잘못된 입력이나 이전 상태가 사용되는지 확인한다.

## 3.4 종료·장애·변경·복원

![운영 변경·관측·종결 과정](assets/dfd-operations.png)

| 상황 | 따라갈 정상 처리 | 별도로 확인할 결과 |
| --- | --- | --- |
| 정상 완료·stop 문자열 | 출력 종료 판단 → Core 미종결 시 중단 전달 → 실행·참조 정리 | 응답 종료와 계산·전송·참조 종료 시각 |
| 취소·연결 종료·timeout | 취소 대상 해석 → 엔진이 살아 있으면 abort → scheduler·worker 상태 갱신 | 외부/내부 ID·시도·collector 범위, 늦은 출력, 실제 회수 |
| 엔진·rank 장애 | 장애를 전달하고 완료되지 않은 실행을 성공으로 처리하지 않음 | 신규 접수 제한, 영향 요청 오류, 그룹·잔존 자원·후속 기동 |
| 재배포 | 신규 접수 중단 → 진행 요청 처리·기존 그룹 종료 → 새 묶음 기동·준비 → 접수 재개 | 이전 요청과 새 모델·상태 혼입, 모든 필수 rank의 준비 |
| 복원 | 현재 승인에 맞는 이전 묶음과 필요한 외부 상태 복원 | 이미지 밖 설정·자격·volume·Gateway, 준비 완료와 요청 재개 |
| 모델 사용 종료·폐기 | 퇴역 모델의 신규 실행 중단 → 진행 요청 처리·자원 정리 → 자료·자격의 보존·삭제 기준 적용 | 이전 모델명·alias·직통 경로의 실제 선택 모델, 현재 승인된 활성 모델의 정상 처리, 남은 사본·접근 |

엔진이 살아 있으면 요청별 abort와 상태 정리를 확인한다. `EngineDeadError`가 발생하면 오류 전달과 실행 그룹·잔존 자원을 확인한다. scheduler와 worker의 상태 제거, GPU 작업 완료, 자료 소거는 각각 관측한다.

기본 다중 GPU·TP 구성에서는 재배포 절차를 확인한다. 특수 snapshot·실행 중 변경·공유 daemon을 선택하면 해당 기능의 변경·복원 절차를 추가로 확인한다.

## 3.5 동작 경로별 적용 범위

PP는 Pipeline Parallelism(파이프라인 병렬 실행), EP는 Expert Parallelism(전문가 병렬 실행), PD는 Prefill–Decode 분리다. 이 구성은 실제로 선택했을 때 해당 동작과 시험을 추가한다.

| 경로 ID | 동작 흐름 | 참조 구성과 선택 기능 |
| --- | --- | --- |
| R01·02·03 | 접수·실행·반환 | 요청·모델 선택, TP 실행·cache, 일반·스트리밍 반환 |
| R04 | 분산 전달·내부 통신 | 노드 내부 IPC·TP는 기본. 다중 노드·복수 replica·PP/EP·PD는 추가 |
| R05·06·07 | 공급·실행 준비 | 모델 취득·승인·실제 로딩, 코드·이미지·파생물, 실행 자격 |
| R08 | 공유·원격 가중치 | 별도 daemon·원격 공급 선택 시 추가. TP 실행과 구분 |
| R09 | 관리·변경 | 관리 접점·재배포는 기본. 실행 중 weights 교체 등은 추가 |
| R10 | 외부 자료·파일 작업 | 미디어 일부 정적 검토 반영. URL·파일·batch·공유 메모리 전체 평가는 대기 |
| R11 | 실패·종결 | 연결 종료·timeout·worker 장애·종결은 기본. 자동 재시도는 추가 |
| R12·13 | 관측·복원·정리 | 로그·진단, 재배포 복원·자원·사본 정리. 특수 snapshot 등은 추가 |
| R14 | 관리형·외부 대체 실행 | 현재 검토 대기. 관리형·다른 endpoint fallback을 선택하면 별도 검토 |

## 3.6 공격·실패 원리와 방어

**분류를 읽는 기준**

공격·실패 원리 **17개**로 같은 위험을 모았다. 기존 **24개는 서빙 접점별 분석 묶음**으로 남겨 코드·R 근거를 찾는 데 사용한다. 시나리오는 **83개**로 유지하며, 원리를 부여한 82개(위협 후보 73개·실패 및 오설정 9개)와 공유 실행 권한의 침해 범위 1개로 나눈다. 77개 CHK와 SC 식별자는 그대로 사용한다.

주 분류는 각 시나리오에서 직접 확인하는 핵심 실패 원리다. 한 SC가 다른 원리도 포함하면 성립 조건을 붙여 함께 표시한다. STRIDE는 침해되는 보안 속성을 확인하는 별도 분류로 유지한다.

| 공격·실패 원리 | 주 분류 시나리오 | 점검 초점 |
| --- | --- | --- |
| [1. 인증·인가 우회](#attack-type-01) | 12개 | 최종 집행점의 주체·대상·행위 인가와 진입 제한 |
| [2. 입력 변환을 이용한 검사 우회](#attack-type-02) | 2개 | 최종 소비 입력의 제한과 변환 선택값 검증 |
| [3. 입력 오류의 서비스 장애 전파](#attack-type-03) | 2개 | 소비자 제약 검증과 요청별 오류 처리 |
| [4. 요청·공유 상태 혼동](#attack-type-04) | 6개 | 상태 식별·호환성·수명 관리 |
| [5. GPU 메모리 안전성 위반](#attack-type-05) | 1개 | 선택 kernel의 경계·정수 폭·초기화 검증 |
| [6. Side-channel 정보 추정](#attack-type-06) | 1개 | 공유 범위 제한과 관측 신호·추정 가능성 평가 |
| [7. 자원 고갈·처리 기회 독점](#attack-type-07) | 6개 | 단계별·누적 예산, 동시성·공정성·대기 한도 |
| [8. 공급물 변조·누락과 승인 대상 불일치](#attack-type-08) | 9개 | 불변 식별, 변경 권한 제한, 실제 소비 대상 대조 |
| [9. 비승인 코드 실행](#attack-type-09) | 10개 | 소비 전 승인·허용 검사, 안전한 reader·sandbox, 쓰기권 제한 |

#### 3.6.1.1 엔진 직접 호출을 통한 무단 추론·관리 작업 · SC-01-01

**주체·처음 가진 권한:** 엔진 주소에 접속할 수 있지만 해당 작업은 허용받지 않은 호출자

**성립 조건:** 호출자가 엔진 주소에 직접 접근할 수 있을 때.

**공격·실패 상황**

호출자는 Gateway 대신 엔진 주소로 요청을 보낸다. 엔진에서 실제 등록된 API가 앞단의 권한 제한 없이 실행되면, Gateway에서 금지했던 추론·관리 작업을 수행할 수 있다.

**발생 과정:** 엔진 주소 발견 → Gateway를 거치지 않고 실제 API 호출 → 금지 작업 실행

**방어 위치:** 배포망·listener·Gateway 및 최종 API

**예방·대응:** Gateway·승인 관리 주체만 엔진 listener에 접근하도록 망·socket 권한을 제한하고, 공개 API를 허용 목록으로 정한다. 최종 API에서 호출 주체·작업 인가를 집행한다.

**대책의 적용 범위·남은 조건:** 망 제한은 그 망 안의 허용 주체가 가진 작업 권한까지 구분하지 못한다. API key의 보호 prefix와 실제 등록 route를 각각 확인한다.

**확인할 정상 동작:** 허용 신원이 실제 진입 경로에서 정상 추론한다. Gateway 사용 시 경유 요청을, 비사용 시 직접 진입점의 허용 요청을 정상 대조로 삼는다.

**점검·판정 기준:** [1.2.1 CHK-REQ-001](04_환경별_적용과_체크리스트.md#CHK-REQ-001)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 Gateway를 거치지 않고 실제 API 호출 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** v0.31.0 인증 middleware는 /v1·/v2·/inference·/cohere prefix를 검사하고 root_path를 제외한 scope path를 사용한다. 사용자별 모델·작업 허용표와 실제 배포망 통제는 조직에서 집행할 부분이다.

#### 3.6.1.2 경로 재작성 차이를 이용한 인증 우회 · SC-01-02

**주체·처음 가진 권한:** 요청 경로와 header를 바꿀 수 있는 호출자

**성립 조건:** 프록시가 요청 경로를 재작성하거나 root_path를 사용할 때.

**공격·실패 상황**

호출자는 요청 경로와 header를 바꿔 보낸다. 인증 계층이 검사한 경로와 router가 실행한 경로가 다르면 보호가 필요한 API가 검사에서 빠질 수 있다.

**발생 과정:** 요청 경로·header 조작 → 인증 대상과 최종 route 불일치 → 보호 API 실행

**방어 위치:** Gateway 경로 재작성과 서버 인증 middleware·router

**예방·대응:** 인증과 라우팅이 같은 최종 경로를 판단하도록 정규화·root_path 처리와 프록시 전달 규칙을 맞추고, 보호 route의 무자격·오자격 요청을 거부한다.

**대책의 적용 범위·남은 조건:** 한 가지 URL의 거부만으로 모든 rewrite·prefix·별칭 경로가 보호됐다고 판단할 수 없으므로 등록 route별로 대조한다.

**확인할 정상 동작:** 기본 경로와 승인된 prefix 설정에서 같은 작업에 같은 권한이 적용된다.

**점검·판정 기준:** [1.2.2 CHK-REQ-002](04_환경별_적용과_체크리스트.md#CHK-REQ-002)

**공개 사례·패치에서 확인할 점:** [GHSA-94f4-hr76-p5j6](https://github.com/vllm-project/vllm/security/advisories/GHSA-94f4-hr76-p5j6) — 인증과 router가 해석하는 경로의 차이를 이용한 사례다. 현재 scope path 처리와 실제 프록시 경로를 대조하고 다른 인증 제외 경로와 구분한다.

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 인증 대상과 최종 route 불일치 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** v0.31.0 인증 middleware는 /v1·/v2·/inference·/cohere prefix를 검사하고 root_path를 제외한 scope path를 사용한다. 사용자별 모델·작업 허용표와 실제 배포망 통제는 조직에서 집행할 부분이다.

#### 3.6.1.3 추론용 자격을 이용한 관리 API 실행 · SC-01-03

**주체·처음 가진 권한:** 일반 추론 권한만 가진 사용자

**성립 조건:** 관리·진단 API가 활성화되고 사용자에게 노출될 때.

**공격·실패 상황**

추론 권한만 가진 사용자가 모델 변경·unload·진단 API를 호출한다. 일반 추론용 자격이 관리 작업까지 허용하면 서비스 상태나 진단 자료에 영향을 줄 수 있다.

**발생 과정:** 일반 사용자 자격 확보 → 관리·진단 route 호출 → 변경·unload·진단 수행

**방어 위치:** 관리 API의 인가 계층과 별도 관리 접근 경로

**예방·대응:** 추론과 관리 역할을 나누고, 관리·진단 작업마다 역할·대상 권한을 검사한다. 필요 없는 route를 비활성화하거나 노출을 제한한다.

**대책의 적용 범위·남은 조건:** 공통 API key만으로 기업의 역할별 권한이 구현됐는지는 별도 확인한다. 같은 listener의 관리 경로도 조사한다.

**확인할 정상 동작:** 관리 역할은 허용 작업을 수행하고 일반 호출자는 추론만 수행한다.

**점검·판정 기준:** [1.2.3 CHK-REQ-003](04_환경별_적용과_체크리스트.md#CHK-REQ-003)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 관리·진단 route 호출 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** v0.31.0 인증 middleware는 /v1·/v2·/inference·/cohere prefix를 검사하고 root_path를 제외한 scope path를 사용한다. 사용자별 모델·작업 허용표와 실제 배포망 통제는 조직에서 집행할 부분이다.

#### 3.6.1.4 전달 신원 위조를 통한 다른 사용자 권한 사용 · SC-01-04

**주체·처음 가진 권한:** 외부 요청의 신원·역할 header를 바꿀 수 있는 사용자

**성립 조건:** 앱·Gateway가 전달한 신원을 후속 권한 검사에 사용할 때.

**공격·실패 상황**

사용자가 tenant·사용자·역할을 나타내는 전달값을 바꾼다. 후속 구성요소가 검증된 신원과 사용자 입력을 구분하지 않으면 다른 사용자의 권한으로 모델이나 작업을 사용할 수 있다.

**발생 과정:** 사용자 header 조작 → 검증되지 않은 전달 신원 수용 → 다른 주체의 모델·작업 사용

**방어 위치:** 신원을 확인하는 앱·Gateway와 전달 신원을 받는 서비스

**예방·대응:** 외부가 보낸 신원·역할 header를 제거하고 검증한 신원으로 다시 생성한다. 수신 측은 승인한 송신자와 전달 경로를 검증하고 그 신원에 맞는 인가를 적용한다.

**대책의 적용 범위·남은 조건:** vLLM의 request ID·priority·rank 값은 신원 증명과 구분한다. 실제 인가에 사용하는 필드와 외부 decorator 동작은 환경별로 확인한다.

**확인할 정상 동작:** 업무 앱이 전달한 검증된 사용자 또는 앱 신원이 정책에 맞게 사용된다.

**점검·판정 기준:** [1.1.1 CHK-REQ-004](04_환경별_적용과_체크리스트.md#CHK-REQ-004)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 검증되지 않은 전달 신원 수용 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** v0.31.0 인증 middleware는 /v1·/v2·/inference·/cohere prefix를 검사하고 root_path를 제외한 scope path를 사용한다. 사용자별 모델·작업 허용표와 실제 배포망 통제는 조직에서 집행할 부분이다.

#### 3.6.1.5 모델 선택값 변경을 통한 비허용 모델 실행 · SC-02-01

**주체·처음 가진 권한:** 자기 요청의 모델·adapter 선택값을 바꿀 수 있는 사용자

**성립 조건:** 모델별 사용 권한이 다르거나 adapter 기능을 사용할 때.

**공격·실패 상황**

사용자가 요청의 model·adapter 선택값을 바꾼다. 최종 대상에 대한 권한 검사 없이 이름만 전달하면 자신에게 허용되지 않은 모델로 요청이 실행될 수 있다.

**발생 과정:** model·adapter 선택값 변경 → 최종 대상의 사용자 권한 검사 누락 → 제한 모델 실행

**방어 위치:** Gateway·모델 router·adapter 등록·선택 계층

**예방·대응:** 검증한 신원에 모델·adapter 허용표를 적용하고 alias·resolver를 거친 최종 대상도 대조한다. 사용 종료한 모델의 신규 실행을 차단한다.

**대책의 적용 범위·남은 조건:** 모델 존재 여부 검사와 사용자 인가는 따로 확인한다. LoRA·resolver·SageMaker 분기는 실제 설치·등록·권한 경로를 확인한다.

**확인할 정상 동작:** 호출자가 허용된 활성 모델을 정상 사용한다. 사용 종료 시험에서는 다른 활성 모델과 현재 승인된 alias 매핑도 정상 동작한다.

**점검·판정 기준:** [1.2.4 CHK-REQ-005](04_환경별_적용과_체크리스트.md#CHK-REQ-005)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 최종 대상의 사용자 권한 검사 누락 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 모델 존재·adapter 선택 검사와 내부 요청 ID 처리는 확인됐다. 확인한 코드의 객체 조회·취소에는 사용자별 소유자 인가 입력이 없어 Gateway·저장소의 실제 인가를 확인해야 한다.

#### 3.6.1.6 다른 사용자의 저장 응답 조회·변경 · SC-02-03

**주체·처음 가진 권한:** 다른 사용자의 response ID를 알 수 있는 호출자

**성립 조건:** Responses 저장 기능이 켜지고 해당 요청이 결과 저장을 요구할 때.

**공격·실패 상황**

사용자가 다른 사람의 response ID로 조회·취소·변경하거나 이전 대화를 이어간다. 저장소의 객체 소유자 검사가 빠진 경로에서는 읽기·변경 권한을 벗어난 처리가 가능할 수 있다.

**발생 과정:** 다른 response ID 확보 → 객체 소유자 검사 누락 → 조회·취소·대화 이어쓰기

**방어 위치:** Responses 저장·조회·변경 API와 객체 저장소

**예방·대응:** 객체 생성 때 검증한 소유자를 기록하고 조회·취소·수정·이전 대화 사용마다 소유자·행위 권한을 검사한다.

**대책의 적용 범위·남은 조건:** ID를 추측하기 어렵게 만드는 것만으로 객체 인가가 충족되지는 않는다. 저장 옵션과 route가 실제 활성일 때 적용한다.

**확인할 정상 동작:** A는 자신의 저장 결과를 조회·취소하고 B는 자신의 객체를 사용한다.

**점검·판정 기준:** [1.2.5 CHK-REQ-006](04_환경별_적용과_체크리스트.md#CHK-REQ-006)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 객체 소유자 검사 누락 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 모델 존재·adapter 선택 검사와 내부 요청 ID 처리는 확인됐다. 확인한 코드의 객체 조회·취소에는 사용자별 소유자 인가 입력이 없어 Gateway·저장소의 실제 인가를 확인해야 한다.

<a id="guide-SC-05-01"></a>
#### 3.6.1.7 cache salt 사칭을 통한 금지된 KV 공유 · SC-05-01

**주체·처음 가진 권한:** 자기 요청에 cache salt를 제출할 수 있는 사용자

**성립 조건:** 서로 분리해야 할 사용자 집단이 같은 cache backend를 사용할 때.

**공격·실패 상황**

사용자가 다른 집단의 salt를 자기 요청에 넣는다. Gateway나 엔진이 신뢰할 수 있는 신원에서 공유 집단을 정하지 않으면 금지된 집단 사이에서 KV를 재사용할 수 있다.

**발생 과정:** 다른 집단의 salt 제출 → 같은 공유 key 사용 → 집단 간 KV 재사용

**방어 위치:** 검증한 신원을 가진 Gateway와 모든 cache 사용 진입점

**예방·대응:** 신뢰된 신원에서 공유 집단을 결정하고 서버가 관리하는 집단별 구분값을 적용한다. 클라이언트 salt의 무시·거부·재작성 규칙을 일관되게 적용한다.

**대책의 적용 범위·남은 조건:** salt는 특정 캐시 공유를 제한한다. 프로세스·메모리 전체 격리가 필요한 집단은 별도의 실행·배포 경계를 선택한다.

**확인할 정상 동작:** 같은 허용 집단은 캐시를 재사용하고 다른 집단은 공유하지 않는다.

**점검·판정 기준:** [4.2.1 CHK-REQ-015](04_환경별_적용과_체크리스트.md#CHK-REQ-015)

**분류 이유:** 핵심 공백은 호출자가 다른 공유 집단의 salt를 사용할 권한이 있는지 검사하는 지점이다. 키 계산 오류와 구분해 인가 우회로 분류했다.

**함께 확인할 원리:** [요청·공유 상태 혼동](#attack-type-04) — 시나리오의 성립 조건에서 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**기존 구현·남은 확인:** salt는 첫 block의 tagged key에 들어가고 뒤 block hash로 이어진다. 확인한 전달 경로에서 인증 주체와 salt의 사용 권한을 대조하는 코드는 확인되지 않았다.

#### 3.6.1.8 로컬 socket 접근을 통한 내부 제어 침입 · SC-08-01

**주체·처음 가진 권한:** 해당 namespace·socket·공유 메모리에 접근할 수 있는 로컬 프로그램

**성립 조건:** 같은 호스트·namespace에서 socket·공유 메모리에 접근할 수 있을 때.

**공격·실패 상황**

별도 로컬 프로그램이 API↔Core·Core↔worker의 내부 접점에 접근한다. 권한이 과도하면 내부 제어나 자료 처리 경로에 들어갈 수 있다.

**발생 과정:** 로컬 프로세스가 내부 접점에 접근 → 제어 메시지 제출 → Core·worker 소비

**방어 위치:** OS 계정·mount namespace·IPC socket·공유 메모리 권한

**예방·대응:** 내부 접점을 전용 권한으로 제한하고 비허용 UID·namespace·mount에서 접근을 막는다. 실제 연결과 명령 수용 여부를 각각 확인한다.

**대책의 적용 범위·남은 조건:** 같은 호스트에 있다는 사실보다 실제 계정·socket·SHM 권한을 기준으로 판단한다.

**확인할 정상 동작:** 승인 core·worker가 IPC를 통해 정상 요청을 수행한다. / 허용한 호출 주체가 각 API 구간에서 정상 요청·스트리밍 응답을 주고받고, 승인한 rank 사이 TP 처리도 정상 완료된다.

**점검·판정 기준:** [1.4.2 CHK-PLT-002](04_환경별_적용과_체크리스트.md#CHK-PLT-002) · [5.5.1 CHK-PLT-008](04_환경별_적용과_체크리스트.md#CHK-PLT-008)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 제어 메시지 제출 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** API↔Core와 Core↔worker는 서로 다른 메시지 경로를 사용한다. worker queue의 pickle 복원과 같은 UID 등 공유 신뢰 전제가 있어 실제 socket·SHM·namespace 접근권이 중요하다.

#### 3.6.1.9 제출 권한으로 자기 모델의 승인 기록 위조 · SC-09-01

**주체·처음 가진 권한:** 공급물을 제출하거나 저장소에 쓸 수 있지만 승인 권한은 없는 주체

**성립 조건:** 공급물 제출·저장 권한과 승인 저장소가 존재할 때.

**공격·실패 상황**

제출자가 자신의 파일을 올린 뒤 승인 상태나 대상 digest를 바꾸려 한다. 제출 권한만으로 유효 승인 기록을 수정할 수 있으면 검토하지 않은 모델이 배포될 수 있다.

**발생 과정:** 공급물 제출 → 승인 저장소 수정 → 비승인 모델을 승인 상태로 사용

**방어 위치:** 승인 저장소 ACL·승인 서비스·배포 승인 검증

**예방·대응:** 제출·수정 권한과 승인 기록 변경 권한을 분리하고 승인 대상 식별정보와 별도 변경 이력을 보호한다. 배포 때 유효한 승인을 확인한다.

**대책의 적용 범위·남은 조건:** 승인 기록을 남기는 것과 승인 변경을 제한하는 것은 별도 통제다. 실제 승인 도구·계정·겸임 예외를 정해야 한다.

**확인할 정상 동작:** 승인 역할은 시험 공급물을 승인하고 제출자는 업로드한다.

**점검·판정 기준:** [1.3.1 CHK-SUP-001](04_환경별_적용과_체크리스트.md#CHK-SUP-001)

**분류 이유:** 승인 기록을 수정할 권한의 분리가 먼저 깨진다. 기록 변조는 그 권한으로 수행하는 후속 행위다.

**함께 확인할 원리:** [공급물 변조·누락과 승인 대상 불일치](#attack-type-08) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**기존 구현·남은 확인:** 통합본에는 승인·배포 역할의 분리 요구가 있다. 조직의 실제 승인 도구·계정별 권한과 배포 게이트가 집행됐다는 환경 증거는 아직 없다.

#### 3.6.1.10 제한된 배포 계정의 운영 환경·모델 변경 · SC-09-02

**주체·처음 가진 권한:** 일부 모델·환경에만 배포 권한을 가진 운영자

**발생 과정:** 일부 배포 권한 보유 → 허용 밖 대상 선택 → 승인 없는 배포

**방어 위치:** 배포 API·CI/CD 권한·환경별 승인 게이트

**예방·대응:** 모델×환경×작업별 권한을 배포 집행점에서 검사하고 승격·긴급 예외의 승인·기한·이력을 적용한다.

**대책의 적용 범위·남은 조건:** 승인된 모델이어도 해당 계정의 배포 환경·작업 권한은 따로 확인한다.

**확인할 정상 동작:** 승인한 모델을 허용된 시험 환경에 배포한다.

**점검·판정 기준:** [1.2.6 CHK-SUP-002](04_환경별_적용과_체크리스트.md#CHK-SUP-002)

#### 3.6.1.11 daemon 접속으로 권한 밖 가중치 읽기 · SC-16-01

**주체·처음 가진 권한:** daemon socket에 접근할 수 있는 로컬 프로그램

**성립 조건:** 별도 weights daemon을 사용하고 해당 socket에 접근할 수 있을 때.

**공격·실패 상황**

같은 OS 계정의 다른 프로그램이 daemon에 접속해 모델 가중치를 읽거나 attach한다.

**방어 위치:** 별도 weights daemon의 socket 권한·모델 인가

**대책의 적용 범위·남은 조건:** 같은 OS 계정과 같은 모델 사용 권한은 별도 판단한다. 기본 TP 실행과 구분한 선택 기능이다.

**기존 구현·남은 확인:** 선택 weights daemon은 socket·peer UID·구성 key 검사를 일부 제공한다. 메시지에 pickle을 사용하고 checkpoint 식별은 payload 전체 승인을 확인하지 않으며 release는 전역 cache에 영향을 준다.

#### 3.6.1.12 진단 자료 조회권을 이용한 고권한 replay · SC-21-03

**주체·처음 가진 권한:** 진단 자료 조회만 허용된 주체

**성립 조건:** 외부 replay 도구와 읽기·실행 권한이 실제로 배치될 때.

**공격·실패 상황**

조회만 허용된 사람이 진단 자료를 도구에 넣어 작업을 재실행한다. 팀 참조 구성에서는 이 도구를 사용하지 않는다.

**발생 과정:** 파일 조회권 보유 → replay 도구 호출 → 권한 밖 작업 재실행

**방어 위치:** 외부 replay 도구의 실행 인가·계정·입력 정책

**예방·대응:** 조회와 replay 실행 권한을 나누고 승인한 실행 역할만 제한된 계정으로 재실행하게 한다.

**대책의 적용 범위·남은 조건:** 실제 도구가 배치된 선택 환경에서 적용한다. 진단 파일 보관만으로 replay 기능을 가정하지 않는다.

**확인할 정상 동작:** 외부 replay를 쓰는 환경에서 승인 실행 역할만 합성 자료를 재실행한다.

**점검·판정 기준:** [1.2.7 CHK-OBS-007](04_환경별_적용과_체크리스트.md#CHK-OBS-007)

**분류 이유:** 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다. 이 SC에서는 replay 도구 호출 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** chat 응답의 prompt 문자열·token ID 반환과 오류·기본 예외 기록 경로가 있다. 반환 필드 제한·로그 독자·암호화·replay 권한은 실제 Gateway·저장소·도구에서 확인한다.

<a id="attack-type-02"></a>
### 3.6.2 입력 변환을 이용한 검사 우회

**개념:** 앞단이 검사한 입력과 엔진이 실제 처리하는 입력이 달라 필요한 제한을 피한다.

**방어 초점:** 최종 소비 입력의 제한과 변환 선택값 검증

**이렇게 묶은 이유:** 잘못된 값의 오류 처리와 구분해, 변환 경로가 검사를 우회하는 원리를 다룬다.

**예시:** Gateway는 messages를 검사했는데 엔진은 요청에 함께 들어온 재사용 token ID를 사용한다. 실제 입력에도 같은 제한을 적용하지 않으면 앞단의 검사를 피할 수 있다.

<a id="guide-SC-03-01"></a>
#### 3.6.2.1 chat template 변경을 통한 입력 검사 우회 · SC-03-01

**주체·처음 가진 권한:** 요청 template이나 관련 인자를 제출할 수 있는 호출자

**성립 조건:** 요청 API가 template·관련 옵션을 받고 앞단이 messages를 검사할 때.

**공격·실패 상황**

Gateway는 messages를 검사했지만, 엔진은 요청에서 지정한 template으로 다른 입력을 만든다. 최종 입력에 필요한 제한이 적용되지 않으면 검사한 내용과 다른 자료가 모델에 전달된다.

**발생 과정:** messages 검사 → 요청 template·인자에 따라 실제 입력 변경 → 최종 입력 제한 누락

**방어 위치:** Gateway의 요청 필드 정책과 renderer 전후 검사

**예방·대응:** 요청 template 지정과 관련 kwargs의 허용 범위를 따로 정하고 실제 소비 입력에 필요한 제한을 적용한다. 승인된 template 선택과 최종 토큰을 기록한다.

**대책의 적용 범위·남은 조건:** template 지정 허용 플래그가 모든 template 인자를 제한하는지는 별도 확인한다. 모델의 기본 template 해석 안전성은 공급물 점검에서 함께 다룬다.

**확인할 정상 동작:** 정상 메시지는 승인 template 적용 후 허용 길이·내용 제한을 만족한다.

**점검·판정 기준:** [3.1.1 CHK-REQ-007](04_환경별_적용과_체크리스트.md#CHK-REQ-007)

**분류 이유:** 앞단이 검사한 입력과 엔진이 실제 처리하는 입력이 달라 필요한 제한을 피한다. 이 SC에서는 요청 template·인자에 따라 실제 입력 변경 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 요청 template 허용 설정과 renderer의 재사용 토큰 분기가 있다. 재사용 토큰은 일반 변환과 다른 경로를 선택하므로 실제 endpoint와 후속 검사를 대조해야 한다.

<a id="guide-SC-03-02"></a>
#### 3.6.2.2 재사용 토큰 경로를 이용한 입력 검사 우회 · SC-03-02

**주체·처음 가진 권한:** kv_transfer_params를 API에 제출할 수 있는 호출자

**성립 조건:** kv_transfer_params 안의 prompt_token_ids가 renderer에 도달할 때.

**공격·실패 상황**

호출자가 미리 만든 토큰 ID를 요청에 넣어 일반 chat template 적용·토큰화를 건너뛰는 분기를 선택한다. 이후 필요한 검사가 빠지면 앞단 정책과 다른 입력을 처리할 수 있다.

**발생 과정:** prompt_token_ids 전달 → 일반 렌더링·토큰화 생략 → 필요한 입력 검사 누락

**방어 위치:** 해당 API schema·Gateway 필드 처리·renderer 이후 입력 검사

**예방·대응:** 재사용 토큰 필드를 사용하지 않으면 거부·제거하고, 허용할 때는 출처·모델·길이·토큰 범위를 확인한다. 일반 입력과 같은 보호 요구를 최종 소비 단계에 적용한다.

**대책의 적용 범위·남은 조건:** renderer의 해당 분기와 후속 검사를 구분한다. PD 비활성만으로 해당 필드가 도달하지 않는다고 처리하지 않는다.

**확인할 정상 동작:** 일반 메시지와 신뢰된 재사용 ID 요청이 각 경로의 필수 검사를 거친다.

**점검·판정 기준:** [3.1.2 CHK-REQ-008](04_환경별_적용과_체크리스트.md#CHK-REQ-008)

**분류 이유:** 앞단이 검사한 입력과 엔진이 실제 처리하는 입력이 달라 필요한 제한을 피한다. 이 SC에서는 일반 렌더링·토큰화 생략 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 요청 template 허용 설정과 renderer의 재사용 토큰 분기가 있다. 재사용 토큰은 일반 변환과 다른 경로를 선택하므로 실제 endpoint와 후속 검사를 대조해야 한다.

<a id="attack-type-03"></a>
### 3.6.3 입력 오류의 서비스 장애 전파

**개념:** 허용 범위 밖 값·개수·조합이 실행기에 도달해 예외가 발생하고 다른 요청에 영향을 줄 수 있다.

**방어 초점:** 소비자 제약 검증과 요청별 오류 처리

**이렇게 묶은 이유:** 정상 값의 과도한 사용으로 자원을 소진하는 경우와 구분한다. 공유 엔진 종료 등 실제 영향은 해당 시험의 확인 상태를 유지한다.

**다른 원리와 함께 나타나는 상황:** [SC-23-04 health 정상 표시로 실제 추론 장애 은폐](#guide-SC-23-04) — 입력 오류가 실행 장애를 유발한 기존 공개 사례와 같은 경로일 때. 현재 실행기의 장애 확대는 시험 대기다.

**예시:** 한 사용자가 모델 어휘 범위 밖 token ID를 보낸다. 실행기 예외를 요청 안에서 처리하지 못하면 같은 엔진의 다른 요청도 영향을 받을 수 있다.

<a id="guide-SC-04-01"></a>
#### 3.6.3.1 잘못된 토큰 입력으로 공유 추론 서비스 방해 · SC-04-01

**주체·처음 가진 권한:** 입력 토큰과 길이를 정할 수 있는 호출자

**성립 조건:** 호출자가 token ID·길이를 정하고 해당 모델·runner가 입력을 처리할 때.

**공격·실패 상황**

호출자가 모델 어휘 범위를 벗어난 토큰이나 처리 가능한 길이를 넘는 입력을 보낸다. API와 실제 실행 단계의 제약이 맞지 않으면 오류가 계산 단계까지 도달할 수 있다.

**발생 과정:** 범위 밖 토큰·길이 제출 → 실행 단계까지 전달 → 요청 오류의 서비스 영향

**방어 위치:** API·InputProcessor·실제 runner의 입력 검증과 예외 처리

**예방·대응:** 모델 어휘·길이 제한을 실제 소비자 기준으로 검사하고, 오류를 해당 요청에 한정해 반환한다. 다른 정상 요청과 후속 canary의 성공을 확인한다.

**대책의 적용 범위·남은 조건:** 입구 검사만으로 후속 실행의 모든 제약을 확인할 수 없다. 모델·runner·선택 endpoint마다 도달 조건을 확인한다.

**확인할 정상 동작:** 선정 tokenizer·모델의 유효 ID와 길이 경계 안 요청이 정상 처리된다.

**점검·판정 기준:** [3.1.3 CHK-REQ-009](04_환경별_적용과_체크리스트.md#CHK-REQ-009)

**공개 사례·패치에서 확인할 점:** [GHSA-4xqp-c3mv-qff7](https://github.com/vllm-project/vllm/security/advisories/GHSA-4xqp-c3mv-qff7) — 과도한 min_tokens의 오류 뒤 health가 정상으로 남는 사례다. 입력 검증과 요청별 오류 처리, 실제 후속 추론을 함께 시험한다. 새 V2 옵션 예외의 종료 영향과는 별도 근거다.

**공개 사례·패치에서 확인할 점:** [GHSA-85xf-c7hm-whqw](https://github.com/vllm-project/vllm/security/advisories/GHSA-85xf-c7hm-whqw) — 구조화 출력의 요청 오류가 공유 EngineCore에 영향을 준 사례다. 현재 선택한 기능·오류 경계에서 회귀한다.

**분류 이유:** 허용 범위 밖 값·개수·조합이 실행기에 도달해 예외가 발생하고 다른 요청에 영향을 줄 수 있다. 이 SC에서는 실행 단계까지 전달 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 모델 어휘·sampling 값 검사는 존재한다. 실행기의 개수·조합 제약과 오류 전파는 별도로 확인해야 하며, 기존 V2 예외 후보의 공유 엔진 종료 영향은 미확인이다.

<a id="guide-SC-04-02"></a>
#### 3.6.3.2 생성 옵션 조합으로 실행기 예외 유발 · SC-04-02

**주체·처음 가진 권한:** sampling 옵션의 값·개수·조합을 정할 수 있는 호출자

**성립 조건:** 해당 API와 실행기가 sampling 옵션을 처리할 때.

**공격·실패 상황**

값 하나하나는 허용 범위 안이어도 옵션 항목의 수나 조합은 실행기 한도를 넘을 수 있다. V2의 해당 processor에는 1024·1024·128개 상한에서 발생하는 ValueError가 정적으로 확인돼 있다.

**발생 과정:** 옵션 값·개수·조합 제출 → API와 processor 제약 불일치 → 예외 발생

**방어 위치:** API 옵션 validator와 실행기 processor·예외 경계

**예방·대응:** 옵션의 값뿐 아니라 개수·조합 비용을 실행기 제한과 맞추고 오류를 요청별로 처리한다. 정상 입력과 경계 입력의 응답·공유 엔진 상태를 비교한다.

**대책의 적용 범위·남은 조건:** V2의 정적 ValueError 근거와 공유 엔진 종료 가능성을 구분한다. 실제 종료·영향 범위는 시험 대기다.

**확인할 정상 동작:** 허용 sampling 조합으로 정상 요청이 완료된다.

**점검·판정 기준:** [3.1.4 CHK-REQ-010](04_환경별_적용과_체크리스트.md#CHK-REQ-010)

**분류 이유:** 허용 범위 밖 값·개수·조합이 실행기에 도달해 예외가 발생하고 다른 요청에 영향을 줄 수 있다. 이 SC에서는 API와 processor 제약 불일치 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 모델 어휘·sampling 값 검사는 존재한다. 실행기의 개수·조합 제약과 오류 전파는 별도로 확인해야 하며, 기존 V2 예외 후보의 공유 엔진 종료 영향은 미확인이다.

<a id="attack-type-04"></a>
### 3.6.4 요청·공유 상태 혼동

**개념:** 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**방어 초점:** 상태 식별·호환성·수명 관리

**이렇게 묶은 이유:** 요청 ID, KV key, 배치 자리, 컴파일 호환성, 모델 전환에서 같은 상태 대응 문제를 모았다. salt의 사용자 권한은 인증·인가에서 다룬다.

**다른 원리와 함께 나타나는 상황:** [SC-05-01 cache salt 사칭을 통한 금지된 KV 공유](#guide-SC-05-01) — 시나리오의 성립 조건에서 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**다른 원리와 함께 나타나는 상황:** [SC-16-03 가중치 payload 교체로 모델·세대 혼입](#guide-SC-16-03) — 시나리오의 성립 조건에서 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**다른 원리와 함께 나타나는 상황:** [SC-18-03 자동 재시도로 중복 실행·결과 혼입](#guide-SC-18-03) — 시나리오의 성립 조건에서 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**예시:** 요청 A가 끝난 배치 자리를 요청 B에 배정한다. A의 토큰 제한 mask가 남아 있으면 B가 자기 요청에 없는 제한을 적용받을 수 있다.

<a id="guide-SC-02-02"></a>
#### 3.6.4.1 요청 ID 충돌을 이용한 결과·취소 대상 혼동 · SC-02-02

**주체·처음 가진 권한:** 외부 요청 ID와 동시 요청 시점을 정할 수 있는 호출자

**성립 조건:** 외부 ID를 사용하고 요청이 동시에 실행되거나 child request가 생길 때.

**공격·실패 상황**

사용자가 같은 외부 ID로 요청을 겹쳐 보내거나 취소한다. 외부 ID와 내부 실행·시도·collector의 관계를 잘못 처리하면 다른 실행을 취소하거나 결과를 잘못 전달할 수 있다.

**발생 과정:** 같은 외부 ID로 요청 겹침 → 내부 실행·시도 대응 혼동 → 다른 실행 취소·결과 전달

**방어 위치:** 요청 등록부·collector·취소·결과 반환 계층

**예방·대응:** 내부 실행 ID와 외부 ID·사용자·시도를 함께 관리하고, 취소·조회 때 대상 집합과 소유 권한을 검사한다. 늦은 결과를 완료된 이전 시도로 구분한다.

**대책의 적용 범위·남은 조건:** 무작위 ID는 충돌을 줄이지만 객체 인가를 대신하지 않는다. 외부 ID 전체 취소와 내부 실행 하나의 취소를 따로 시험한다.

**확인할 정상 동작:** 고유 표식이 있는 A·B 일반·스트리밍 요청이 각각 올바른 연결로 반환된다.

**점검·판정 기준:** [4.1.1 CHK-REQ-011](04_환경별_적용과_체크리스트.md#CHK-REQ-011)

**분류 이유:** 외부 ID와 내부 실행·시도의 대응 오류가 출발점이라 상태 혼동을 주 분류로 삼았다. 조회·취소의 소유자 인가는 함께 확인한다.

**기존 구현·남은 확인:** 모델 존재·adapter 선택 검사와 내부 요청 ID 처리는 확인됐다. 확인한 코드의 객체 조회·취소에는 사용자별 소유자 인가 입력이 없어 Gateway·저장소의 실제 인가를 확인해야 한다.

<a id="guide-SC-05-02"></a>
#### 3.6.4.2 캐시 키 충돌·누락을 이용한 다른 입력 재사용 · SC-05-02

**주체·처음 가진 권한:** 입력이나 허용된 adapter를 선택할 수 있는 사용자

**성립 조건:** 실제 cache key 구성과 해당 모델·입력 기능을 사용할 때.

**공격·실패 상황**

모델·adapter·입력 자료가 달라졌는데도 캐시 식별값이 필요한 차이를 구분하지 못하면 다른 문맥의 KV가 재사용될 수 있다.

**발생 과정:** 입력·모델 조건 변경 → 필요한 구분값 누락·충돌 → 다른 문맥의 KV 사용

**방어 위치:** cache key 생성·hash·모델 변경 시 무효화

**예방·대응:** 모델·adapter·입력 자료·설정의 필요한 차이를 키에 포함하고 형식·태그를 구분한다. 수정된 key·hash 구현을 적용하고 모델 변경 때 재사용 적합성을 확인한다.

**대책의 적용 범위·남은 조건:** 강한 hash만으로 입력 구성요소의 누락은 해결되지 않는다. LoRA·미디어 등은 실제 기능과 해당 key 경로에서 시험한다.

**확인할 정상 동작:** 기본 모델·입력과 실제 활성 재사용 문맥이 같으면 기대한 캐시를 재사용한다. adapter·media는 해당 기능을 사용할 때만 정상 대조에 포함한다.

**점검·판정 기준:** [4.3.2 CHK-REQ-016](04_환경별_적용과_체크리스트.md#CHK-REQ-016)

**공개 사례·패치에서 확인할 점:** [GHSA-rm76-4mrf-v9r8](https://github.com/vllm-project/vllm/security/advisories/GHSA-rm76-4mrf-v9r8) — 예측 가능한 hash 충돌을 이용한 캐시 혼동 사례다. 키 계산의 수정과 입력 의미·태그 구성을 각각 확인한다.

**공개 사례·패치에서 확인할 점:** [GHSA-rh6f-3x46-j33q](https://github.com/vllm-project/vllm/security/advisories/GHSA-rh6f-3x46-j33q) — 서로 다른 입력·타입이 같은 캐시 항목으로 취급되는 사례다. prefix key와 선택 멀티모달 경로를 구분해 회귀 조건을 정한다.

**분류 이유:** 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다. 이 SC에서는 필요한 구분값 누락·충돌 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** salt는 첫 block의 tagged key에 들어가고 뒤 block hash로 이어진다. 확인한 전달 경로에서 인증 주체와 salt의 사용 권한을 대조하는 코드는 확인되지 않았다.

#### 3.6.4.3 재사용 배치 자리의 토큰 제한 상태 혼입 · SC-06-01

**주체·처음 가진 권한:** 토큰 허용 목록과 요청 시점을 조절할 수 있는 호출자

**성립 조건:** 실제로 선택한 runner에서 batch slot 이동·재사용이 발생할 때.

**공격·실패 상황**

요청 A가 사용한 토큰 허용 마스크가 자리 이동이나 완료 뒤 지워지지 않으면 같은 자리를 받은 요청 B의 생성도 제한될 수 있다.

**발생 과정:** 제약 요청 이동·종료 → 원래 자리의 mask 잔존 → 다음 요청에 제한 상속

**방어 위치:** 선택 runner의 batch slot 이동·교환·해제 코드

**예방·대응:** 이동·완료·취소·재사용 시 요청별 mask를 올바른 자리로 옮기고 원래 상태를 초기화하는 수정을 적용한다. 제약 없는 정상 요청과 자리 재사용 요청을 비교한다.

**대책의 적용 범위·남은 조건:** V1 condense의 수정 근거는 V2 전체의 상태 관리를 대신하지 않는다. 실제 runner와 CPU mask 할당·도달 조건을 확인한다.

**확인할 정상 동작:** 서로 다른 sampling 제한의 A·B 요청을 새 slot에서 처리한다. 실제 V1이면 condense mask 분기, V2이면 slot/count 갱신 분기를 적용한다.

**점검·판정 기준:** [4.4.1 CHK-REQ-018](04_환경별_적용과_체크리스트.md#CHK-REQ-018)

**공개 사례·패치에서 확인할 점:** [GHSA-6cxc-2vcg-w5qc](https://github.com/vllm-project/vllm/security/advisories/GHSA-6cxc-2vcg-w5qc) — V1 batch 자리 이동 뒤 이전 mask가 남는 사례다. 현재 원래 자리 초기화 코드와 할당·이동 조건을 확인하고 V2에는 그 실행기의 별도 근거를 적용한다.

**분류 이유:** 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다. 이 SC에서는 원래 자리의 mask 잔존 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** V1 InputBatch에는 이동 뒤 원래 mask 자리를 비우는 코드가 있다. 실제 선택 runner·mask 할당·backend 조건에서 상태 재사용과 메모리 동작을 확인해야 한다.

#### 3.6.4.4 PD 전송 참조 조작으로 KV·완료 상태 오연결 · SC-08-04

**주체·처음 가진 권한:** PD API의 전송 메타데이터나 connector peer 메시지를 조절할 수 있는 주체

**성립 조건:** PD·NIXL 등 분리 실행과 해당 connector를 선택했을 때.

**공격·실패 상황**

요청자가 전송 메타데이터를 조절하거나 peer가 잘못된 참조·완료 상태를 보낸다. 요청·모델 세대·버퍼의 대응을 잘못 처리하면 다른 실행의 KV나 상태가 사용될 수 있다.

**발생 과정:** 요청·peer 메타데이터 조작 → 모델·세대·요청 검증 누락 → 잘못된 KV·완료 참조

**방어 위치:** PD connector의 peer 인증·전송 메타데이터·버퍼 수명 관리

**예방·대응:** 전송 상대와 요청·모델·세대·rank 대응을 검증하고 buffer 등록·사용·완료·해제를 일치시킨다. 불필요한 전송 필드는 진입점에서 제한한다.

**대책의 적용 범위·남은 조건:** PD·NIXL을 사용하는 구현에 적용한다. 기본 TP 실행과 별도로 실제 connector 소비·전송·완료를 확인한다.

**확인할 정상 동작:** TP 처리에서 각 rank의 담당 계산·중간 상태와 선정 출력 rank·집계 경로의 최종 반환을 요청·모델·buffer에 연결한다.

**점검·판정 기준:** [4.1.3 CHK-REQ-014](04_환경별_적용과_체크리스트.md#CHK-REQ-014)

**분류 이유:** 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다. 이 SC에서는 모델·세대·요청 검증 누락 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 시나리오의 성립 조건에서 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다.

**기존 구현·남은 확인:** API↔Core와 Core↔worker는 서로 다른 메시지 경로를 사용한다. worker queue의 pickle 복원과 같은 UID 등 공유 신뢰 전제가 있어 실제 socket·SHM·namespace 접근권이 중요하다.

#### 3.6.4.5 구버전 생성물 재사용으로 실행 불일치 · SC-12-02

**주체·처음 가진 권한:** 원본 모델이나 컴파일 옵션을 바꿀 수 있는 주체

**성립 조건:** 컴파일·파생 파일·npcache를 재사용할 때.

**공격·실패 상황**

모델이나 도구·옵션을 바꾼 뒤 이전 생성물이 계속 유효한 것으로 선택된다.

**발생 과정:** 모델·도구·옵션 변경 → 구 캐시를 유효로 판단 → 다른 조건의 생성물 실행

**방어 위치:** cache key·호환성 검사·배포 재생성 절차

**예방·대응:** 원본·도구·의존성·설정·장치 조건의 호환 기준을 정하고 불일치한 생성물을 무효화·재생성한다.

**대책의 적용 범위·남은 조건:** 생성물 삭제를 일괄 요구하기보다 호환 근거가 있는 재사용과 근거 없는 재사용을 구분한다.

**확인할 정상 동작:** 보호·호환 조건이 같은 승인 묶음에서 기존 파생 결과를 정상 재사용한다. 결과에 영향이 없는 설정 차이는 동일성을 깨는 조건으로 취급하지 않는다.

**점검·판정 기준:** [4.3.1 CHK-SUP-015](04_환경별_적용과_체크리스트.md#CHK-SUP-015)

**분류 이유:** 원본·도구·옵션과 재사용 결과의 호환성 대응이 틀린 경우다. 악성 코드 삽입 여부와 따로 평가한다.

**기존 구현·남은 확인:** compile cache의 키·디렉터리·해석·compiler load 경로가 있다. 캐시 키는 재사용 대상을 선택하는 정보이며 작성자의 승인과 자료의 진위는 별도 통제가 필요하다.

#### 3.6.4.6 실행 중 교체에서 weights·KV 세대 혼합 · SC-17-03

**주체·처음 가진 권한:** live·rolling 변경을 수행할 수 있는 운영자

**성립 조건:** live update·rolling·다중 replica 구성을 선택했을 때.

**공격·실패 상황**

변경 중인 실행 그룹에서 이전 요청과 새 모델·KV·정책이 섞인다.

**발생 과정:** live·rolling 변경 → 기존 요청과 새 상태 동시 사용 → 혼합 결과·정책 적용

**방어 위치:** 변경 coordinator·세대 관리·routing·KV 무효화

**예방·대응:** 진행 요청의 처리·배수·중단 기준과 신규 요청 전환 시점을 정하고 모델·KV·정책 세대의 대응을 유지한다.

**대책의 적용 범위·남은 조건:** live·다중 replica·rolling의 실제 지원 구성을 선택했을 때 적용한다. 기본 재시작 절차와 구분한다.

**확인할 정상 동작:** live/rolling 미사용 기준에서는 재시작·재배포로 일관성을 유지한다.

**점검·판정 기준:** [7.3.2 CHK-LIF-006](04_환경별_적용과_체크리스트.md#CHK-LIF-006)

**분류 이유:** 진행 요청·weights·KV·정책의 세대 대응이 어긋나는 경우라 상태 혼동으로 옮겼다.

**함께 확인할 원리:** [공급물 변조·누락과 승인 대상 불일치](#attack-type-08) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**기존 구현·남은 확인:** mp backend의 rank별 준비·초기화 실패·종료 경로를 확인했다. Gateway·배포 도구의 현재 승인 대조와 서비스 재개 게이트는 조직의 실제 구현이 필요하다.

<a id="attack-type-05"></a>
### 3.6.5 GPU 메모리 안전성 위반

**개념:** 주소 계산·경계·초기화 오류로 의도하지 않은 GPU 메모리를 읽거나 쓴다.

**방어 초점:** 선택 kernel의 경계·정수 폭·초기화 검증

**이렇게 묶은 이유:** 논리적인 요청·캐시 대응과 메모리 주소의 안전성은 검사 위치와 수정 방법이 달라 구분한다.

**예시:** 특정 kernel이 큰 offset을 좁은 정수로 계산한다. 값이 잘려 잘못된 주소를 읽으면 같은 GPU에 있는 다른 요청의 자료가 노출될 수 있다.

<a id="guide-SC-06-02"></a>
#### 3.6.5.1 GPU 메모리 경계 오류로 다른 요청 자료 노출 · SC-06-02

**주체·처음 가진 권한:** 해당 실행 경로에 도달하는 입력 크기·배치를 조절할 수 있는 호출자

**성립 조건:** 특정 backend·dtype·shape·배치가 실제 GPU 코드에 도달할 때.

**공격·실패 상황**

호출자가 도달 가능한 입력 크기나 배치를 바꾼다. 해당 kernel이나 버퍼 관리에 결함이 있으면 범위 밖 읽기·쓰기 또는 이전 자료의 혼입이 생길 수 있다.

**발생 과정:** 특정 shape·dtype·배치 도달 → offset·초기화·버퍼 수명 오류 → 잘못된 자료 읽기·쓰기

**방어 위치:** 선택 kernel·연산 라이브러리·CUDA Graph 버퍼 관리

**예방·대응:** 해당 kernel·의존성의 수정본을 적용하고 정수 폭·경계·초기화·입력 갱신·출력 수명을 확인한다. 검증 전 임시 입력 제한에는 대상·기한을 둔다.

**대책의 적용 범위·남은 조건:** 요청 제한은 구현 수정 전의 보완 수단이다. 실제 backend·의존성·Graph 모드에서의 도달·영향 시험이 필요하다.

**확인할 정상 동작:** 선택한 kernel이 유효 shape·length 입력으로 대조 구현과 맞는 결과를 낸다. / capture 후 동일 shape의 새 입력을 넣으면 새 입력에 해당하는 결과가 나온다. / 정상 TP graph 등록·실행·종료 후 새 기동이 성공한다.

**점검·판정 기준:** [3.4.1 CHK-REQ-019](04_환경별_적용과_체크리스트.md#CHK-REQ-019) · [4.4.2 CHK-REQ-020](04_환경별_적용과_체크리스트.md#CHK-REQ-020) · [4.4.3 CHK-REQ-021](04_환경별_적용과_체크리스트.md#CHK-REQ-021)

**분류 이유:** 주소 계산·경계·초기화 오류로 의도하지 않은 GPU 메모리를 읽거나 쓴다. 이 SC에서는 offset·초기화·버퍼 수명 오류 지점과 기존 정상 대조를 확인한다.

### 3.6.6 Side-channel 정보 추정

**개념:** 응답 시간이나 cache 적중 신호를 반복 관측해 비공개 입력을 추정한다.

**방어 초점:** 공유 범위 제한과 관측 신호·추정 가능성 평가

**이렇게 묶은 이유:** 직접 자료를 읽는 정보 노출과 구분한다. 반복 관측·통계 대조가 필요한 공격 원리다.

**예시:** 공격자가 후보 문장들을 반복해서 보내고 응답 시간을 비교한다. 비공개 입력과 prefix가 겹칠 때 더 빨라진다면 그 입력이 사용됐는지 추정할 수 있다.

<a id="guide-SC-05-03"></a>
#### 3.6.6.1 캐시 적중 시간으로 비공개 프롬프트 추정 · SC-05-03

**주체·처음 가진 권한:** 캐시를 공유하며 응답 시간·적중 신호를 관측할 수 있는 호출자

**성립 조건:** 캐시를 공유하고 시간·응답 필드·지표를 충분히 관측할 수 있을 때.

**공격·실패 상황**

호출자는 비공개 문장의 후보를 반복해서 요청하고 시간이나 cache hit 신호를 비교한다. 관측 차이가 입력의 존재를 드러내면 읽기 권한이 없는 정보를 추정할 수 있다. 지연 변동과 지표의 집계 범위도 함께 분석한다.

**발생 과정:** 후보 prefix 반복 요청 → 시간·적중 신호 관측 → 비공개 입력 존재 추정

**방어 위치:** prefix cache 공유 정책·적중 정보 노출·배포 분리

**예방·대응:** 비공개 집단 간 공유를 제한하고 검증된 집단별 salt를 적용한다. 불필요한 요청별 적중 정보를 줄이며 엄격한 격리 요구에는 실행 자원 분리를 검토한다.

**대책의 적용 범위·남은 조건:** 같은 집단 안의 허용 공유와 공격자 관측 범위를 정책으로 정한다. 집계 지표·지연 차이의 실제 추정 가능성은 통계적 시험이 필요하다.

**확인할 정상 동작:** 허용 공개 문맥에서 지연·hit 신호가 정상 범위로 관측된다.

**점검·판정 기준:** [5.6.1 CHK-REQ-017](04_환경별_적용과_체크리스트.md#CHK-REQ-017)

**공개 사례·패치에서 확인할 점:** [GHSA-4qjh-9fv9-r85r](https://github.com/vllm-project/vllm/security/advisories/GHSA-4qjh-9fv9-r85r) — prefix 적중에 따른 시간 차이로 비공개 입력을 추정하는 사례다. 공유 정책과 관측 신호·통계 대조가 필요하다.

**분류 이유:** 응답 시간이나 cache 적중 신호를 반복 관측해 비공개 입력을 추정한다. 이 SC에서는 시간·적중 신호 관측 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** salt는 첫 block의 tagged key에 들어가고 뒤 block hash로 이어진다. 확인한 전달 경로에서 인증 주체와 salt의 사용 권한을 대조하는 코드는 확인되지 않았다.

<a id="attack-type-07"></a>
### 3.6.7 자원 고갈·처리 기회 독점

**개념:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다.

**방어 초점:** 단계별·누적 예산, 동시성·공정성·대기 한도

**이렇게 묶은 이유:** 추론과 모델 준비의 비용 공격을 통합했다. CPU·GPU·메모리·디스크·연결 및 공정성 시험은 실제 소비 위치별로 유지한다.

**다른 원리와 함께 나타나는 상황:** [SC-11-07 모델 template의 위험 동작·비용 유발](#guide-SC-11-07) — template의 처리 시간·메모리 비용이 문제인 분기. 금지 함수·객체 접근은 09 유형의 별도 분기다.

**다른 원리와 함께 나타나는 상황:** [SC-18-01 취소 뒤 GPU 작업·출력·참조 잔존](#guide-SC-18-01) — 시나리오의 성립 조건에서 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다.

**다른 원리와 함께 나타나는 상황:** [SC-18-03 자동 재시도로 중복 실행·결과 혼입](#guide-SC-18-03) — 시나리오의 성립 조건에서 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다.

**예시:** 한 사용자가 긴 입력과 큰 생성 개수를 조합한 요청을 반복한다. 요청당·전체 비용을 제한하지 않으면 대기열과 메모리를 점유해 다른 사용자의 응답을 지연시킬 수 있다.

<a id="guide-SC-07-01"></a>
#### 3.6.7.1 입력·생성 개수 조합으로 자원 고갈 · SC-07-01

**주체·처음 가진 권한:** body·header·요청 ID·생성 개수 등을 정할 수 있는 호출자

**성립 조건:** API가 해당 입력·생성 개수·동시 요청을 허용할 때.

**공격·실패 상황**

사용자는 긴 입력과 많은 생성 결과를 조합해 보낸다. 각각의 한도 안에서도 전체 CPU·메모리·IPC 비용이 예산을 넘을 수 있다.

**발생 과정:** 긴 body·ID·큰 n 조합 → 복제·해싱·대기 비용 증폭 → 자원 예산 초과

**방어 위치:** Gateway 요청 한도와 API·scheduler의 비용 발생 지점

**예방·대응:** body·header·ID·salt·n과 동시성의 개별·조합·누적 예산을 제한한다. 비싼 복제·해싱 전에 거부하고 전체 queue·메모리 사용도 관리한다.

**대책의 적용 범위·남은 조건:** 제품의 형식상 최대값을 기업의 안전 예산으로 사용하지 않는다. 입구 한도와 실제 비용 제한을 함께 확인한다.

**확인할 정상 동작:** 정상 소량 요청이 정한 지연·처리율을 만족한다.

**점검·판정 기준:** [6.1.2 CHK-LIF-003](04_환경별_적용과_체크리스트.md#CHK-LIF-003)

**공개 사례·패치에서 확인할 점:** [GHSA-3mwp-wvh9-7528](https://github.com/vllm-project/vllm/security/advisories/GHSA-3mwp-wvh9-7528) — n 값이 요청 객체·비용을 증폭하는 사례다. 현재 상한 존재와 기업의 조합·누적 안전 예산을 각각 확인한다.

**공개 사례·패치에서 확인할 점:** [GHSA-wpww-v874-ph2p](https://github.com/vllm-project/vllm/security/advisories/GHSA-wpww-v874-ph2p) — 긴 cache salt의 직렬화·해싱 비용이 scheduler를 점유한 사례다. 실제 비용 발생 전 길이·전체 비용을 제한하는지 시험한다.

**분류 이유:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다. 이 SC에서는 복제·해싱·대기 비용 증폭 지점과 기존 정상 대조를 확인한다.

#### 3.6.7.2 요청·우선순위 독점으로 다른 사용자 서비스 방해 · SC-07-02

**주체·처음 가진 권한:** 허용된 장문·동시 요청을 반복하거나 우선순위를 지정할 수 있는 사용자

**성립 조건:** 여러 사용자가 같은 실행 자원을 공유할 때.

**공격·실패 상황**

한 사용자가 장문·동시 요청을 반복하거나 높은 우선순위를 사용한다. 다른 사용자의 대기·선점·재계산 비용이 늘어 서비스 기준을 넘을 수 있다. 허용된 정상 요청을 함께 실행해 영향을 비교한다.

**발생 과정:** 반복·장문·고우선순위 요청 → 실행 기회 독점 → 정상 사용자 지연·재계산 증가

**방어 위치:** 신원별 quota·우선순위 정책·scheduler·대기열

**예방·대응:** 사용자별 동시성·토큰·시간 예산과 우선순위 지정 권한을 제한한다. 정상 사용자 요청이 정한 시간·처리량을 유지하는지 함께 시험한다.

**대책의 적용 범위·남은 조건:** 전체 요청 수 제한만으로 사용자 간 공정성이 보장되지는 않는다. 실제 header 우선순위와 유효 queue 설정을 확인한다.

**확인할 정상 동작:** 정상 소량 요청이 정한 지연·처리율을 만족한다.

**점검·판정 기준:** [6.1.2 CHK-LIF-003](04_환경별_적용과_체크리스트.md#CHK-LIF-003)

**분류 이유:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다. 이 SC에서는 실행 기회 독점 지점과 기존 정상 대조를 확인한다.

#### 3.6.7.3 느린 수신자로 출력 버퍼·연결 점유 · SC-07-03

**주체·처음 가진 권한:** 자기 응답을 읽는 속도를 조절할 수 있는 호출자

**성립 조건:** 스트리밍과 실제 Gateway·HTTP 역압력 경로를 사용할 때.

**공격·실패 상황**

호출자가 연결을 유지한 채 응답을 매우 천천히 읽는다. 출력 대기와 전송 버퍼에 한도가 부족하면 연결·메모리를 오래 점유할 수 있다.

**발생 과정:** 연결을 유지하며 천천히 읽기 → 출력·전송 대기 누적 → 메모리·연결 장기 점유

**방어 위치:** Gateway·HTTP 전송·출력 queue·취소 전파

**예방·대응:** 출력 queue·buffer·보존 시간·전송 timeout을 제한하고 초과 시 실제 실행 취소·전송 종료·자원 회수를 수행한다.

**대책의 적용 범위·남은 조건:** 열린 느린 연결과 완전히 끊긴 연결은 각각 시험한다. Python collector의 결과 병합만으로 Gateway·HTTP 전송 한도를 입증할 수 없다.

**확인할 정상 동작:** 정상 수신 속도와 허용 진단 설정에서 메모리가 안정적이다.

**점검·판정 기준:** [6.1.3 CHK-LIF-004](04_환경별_적용과_체크리스트.md#CHK-LIF-004)

**분류 이유:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다. 이 SC에서는 출력·전송 대기 누적 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 일부 입력값 상한과 scheduler 예산은 존재한다. queue의 유효 한도·조합 비용·신원별 공정성·HTTP 출력 대기의 실제 제한은 배포 설정과 시험이 필요하다.

<a id="guide-SC-07-04"></a>
#### 3.6.7.4 디버그 응답 보관으로 메모리 고갈 · SC-07-04

**주체·처음 가진 권한:** 디버그 응답을 수집하는 route에 긴 출력을 요청할 수 있는 호출자

**성립 조건:** 해당 route의 response debug 기능을 켰을 때.

**공격·실패 상황**

긴 응답을 요청하면 디버그 기능이 전체 응답을 추가로 모아둘 수 있다.

**발생 과정:** 긴 출력 요청 → debug 전체 응답 수집 → 추가 메모리·지연 증가

**방어 위치:** 실제 route의 debug 설정·응답 수집기

**예방·대응:** 운영에서 불필요한 debug 응답 보관을 끄고, 필요한 경우 수집 크기·기간·동시성을 제한한다. 수집 종료·실패 시 메모리 회수를 확인한다.

**대책의 적용 범위·남은 조건:** 일반 스트리밍과 debug 경로의 자원 사용을 비교한다. 적용 route와 실제 활성 설정을 확인해야 한다.

**확인할 정상 동작:** 정상 수신 속도와 허용 진단 설정에서 메모리가 안정적이다.

**점검·판정 기준:** [6.1.3 CHK-LIF-004](04_환경별_적용과_체크리스트.md#CHK-LIF-004)

**분류 이유:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다. 이 SC에서는 debug 전체 응답 수집 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 일부 입력값 상한과 scheduler 예산은 존재한다. queue의 유효 한도·조합 비용·신원별 공정성·HTTP 출력 대기의 실제 제한은 배포 설정과 시험이 필요하다.

<a id="guide-SC-15-01"></a>
#### 3.6.7.5 대형·오류 공급물로 모델 준비 자원 고갈 · SC-15-01

**주체·처음 가진 권한:** 큰 파일·오류 파일을 제출할 수 있는 공급자

**성립 조건:** 파일 취득·해석·변환·컴파일·적재 단계에 도달할 때.

**공격·실패 상황**

공급자가 매우 크거나 해석 오류가 있는 파일을 제출한다. 준비 과정이 시간·메모리·디스크 예산을 넘으면 서비스 기동이나 다른 작업이 지연될 수 있다. 단계별·누적 비용을 정상 파일과 비교한다.

**발생 과정:** 파일 제출 → 취득·해석·변환 비용 증가 → 기동·다른 작업 예산 초과

**방어 위치:** 모델 준비 작업·reader·compile·적재 자원 제한

**예방·대응:** 사전 크기·형식 검사와 단계별·전체 시간·메모리·디스크 예산을 적용한다. 동시 준비를 제한하고 실패한 작업·자료를 정리한다.

**대책의 적용 범위·남은 조건:** 사전 크기만으로 압축·변환·compile 비용을 예측할 수 없으므로 실제 누적 비용도 관측한다.

**확인할 정상 동작:** 선정 모델이 합의한 시간·메모리·저장 예산 안에 기동한다.

**점검·판정 기준:** [6.1.1 CHK-LIF-001](04_환경별_적용과_체크리스트.md#CHK-LIF-001)

**분류 이유:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다. 이 SC에서는 취득·해석·변환 비용 증가 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 파일 취득·해석·변환·compile·적재 경로가 있다. 조직의 단계별·누적 예산과 취득 SDK의 재시도·부분 파일 정리 효과는 실제 환경에서 확인해야 한다.

<a id="guide-SC-15-02"></a>
#### 3.6.7.6 재시도·부분 파일 누적으로 준비 비용 초과 · SC-15-02

**구분:** 실패·오설정

**실패 계기:** 원격 공급원의 중단·재시도; 공급자 제어 능력은 조건부 확인

**성립 조건:** 원격 취득과 재시도를 사용할 때.

**공격·실패 상황**

공급원이 반복해서 끊기면 엔진이 다운로드를 재시도하고 부분 파일을 남길 수 있다.

**발생 과정:** 공급원 중단 → 반복 재시도·부분 파일 누적 → 시간·디스크 예산 초과

**방어 위치:** 취득 SDK·retry 정책·임시 저장소·정리 작업

**예방·대응:** 재시도 횟수·총 시간·부분 파일 보존량을 제한하고 중단 시 정리·재개 규칙을 적용한다.

**대책의 적용 범위·남은 조건:** 기본은 실패·오설정 검토다. 공격자 공급원 제어는 조건이 확인될 때 구분해 기록한다.

**확인할 정상 동작:** 일시 실패 뒤 허용 횟수 안의 정상 재시도로 취득한다.

**점검·판정 기준:** [6.2.1 CHK-LIF-002](04_환경별_적용과_체크리스트.md#CHK-LIF-002)

**분류 이유:** 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다. 이 SC에서는 반복 재시도·부분 파일 누적 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 파일 취득·해석·변환·compile·적재 경로가 있다. 조직의 단계별·누적 예산과 취득 SDK의 재시도·부분 파일 정리 효과는 실제 환경에서 확인해야 한다.

### 3.6.8 공급물 변조·누락과 승인 대상 불일치

**다른 원리와 함께 나타나는 상황:** [SC-11-01 요청의 코드 버전 변경으로 비승인 모듈 로딩](#guide-SC-11-01) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**다른 원리와 함께 나타나는 상황:** [SC-12-01 공유 컴파일 캐시 변조를 통한 코드 실행](#guide-SC-12-01) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**예시:** 검토자가 승인한 모델 경로를 배포 직전에 다른 파일로 바꾼다. loader가 실제로 연 파일을 승인 내용과 대조하지 않으면 다른 모델이 서비스될 수 있다.

<a id="guide-SC-02-04"></a>
#### 3.6.8.1 모델 별칭 변경을 통한 승인 대상 바꿔치기 · SC-02-04

**주체·처음 가진 권한:** 모델 alias나 배포 전환을 변경할 수 있는 운영자

**성립 조건:** 운영자가 alias나 worker의 모델 대응을 바꿀 수 있을 때.

**공격·실패 상황**

승인된 이름으로 요청했지만 alias·배포 연결이 바뀌어 다른 모델이나 세대가 처리한다.

**발생 과정:** alias·promotion 변경 → 승인 이름과 실제 모델 대응 변경 → 다른 세대 서비스

**방어 위치:** 모델 registry·배포·routing 전환 계층

**예방·대응:** alias 변경 권한을 제한하고 현재 승인된 실제 모델·세대·worker와의 대응을 검토·기록한다. 전환 후 canary와 실제 모델 증거를 확인한다.

**대책의 적용 범위·남은 조건:** 현재 승인된 활성 모델로 alias를 재사용하는 정상 절차는 허용한다. 표시 이름만으로 실제 모델 일치를 증명하지 않는다.

**확인할 정상 동작:** 호출자가 허용된 활성 모델을 정상 사용한다. 사용 종료 시험에서는 다른 활성 모델과 현재 승인된 alias 매핑도 정상 동작한다.

**점검·판정 기준:** [1.2.4 CHK-REQ-005](04_환경별_적용과_체크리스트.md#CHK-REQ-005)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 승인 이름과 실제 모델 대응 변경 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 모델 존재·adapter 선택 검사와 내부 요청 ID 처리는 확인됐다. 확인한 코드의 객체 조회·취소에는 사용자별 소유자 인가 입력이 없어 Gateway·저장소의 실제 인가를 확인해야 한다.

<a id="guide-SC-10-01"></a>
#### 3.6.8.2 승인 뒤 파일·경로 교체로 다른 모델 로딩 · SC-10-01

**주체·처음 가진 권한:** 승인 뒤 실제 로딩 전에 파일이나 경로를 바꿀 수 있는 주체

**성립 조건:** 승인 이후 엔진이 읽기 전까지 파일·symlink·mount를 바꿀 수 있을 때.

**공격·실패 상황**

파일 쓰기 권한자가 승인된 파일이나 그 경로를 다른 내용으로 바꾼다. loader가 실제 읽은 대상을 승인 기록과 대조하지 않으면 승인되지 않은 파일로 모델이 로딩될 수 있다.

**발생 과정:** 승인 완료 → 파일·symlink·mount·redirect 교체 → loader가 다른 자료 읽기

**방어 위치:** 공급물 저장소·mount 권한·소비 전 검증

**예방·대응:** 승인된 객체를 불변 식별자로 고정하고 쓰기·경로 변경을 제한한다. 실제 열린 대상과 승인 digest·경로를 대조해 불일치 시 사용을 막는다.

**대책의 적용 범위·남은 조건:** 승인 시점의 hash만으로 이후 읽기까지의 불변성이 보장되지는 않는다. 소비 전 대조와 실제 파일 고정 방식을 함께 확인한다.

**확인할 정상 동작:** 승인한 불변 파일 경로로 일반·스트리밍 요청을 처리한다.

**점검·판정 기준:** [2.2.1 CHK-SUP-005](04_환경별_적용과_체크리스트.md#CHK-SUP-005)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 파일·symlink·mount·redirect 교체 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** config·tokenizer·primary/secondary weights의 선택·소비 경로가 있다. 확인한 loader 함수에서 조직 승인 manifest·서명자를 실제 파일과 대조하는 처리는 확인되지 않았다.

<a id="guide-SC-10-02"></a>
#### 3.6.8.3 승인에서 빠진 하위 자료로 모델 동작 변경 · SC-10-02

**주체·처음 가진 권한:** 하위 모델·설정·tokenizer나 그 참조를 바꿀 수 있는 주체

**성립 조건:** 독립 경로·revision·추가 공급원이 실제 로딩에 사용될 때.

**공격·실패 상황**

주 가중치는 승인됐지만 함께 읽는 tokenizer·설정·하위 모델은 다른 경로에서 가져온다. 변경 가능한 하위 자료가 승인 밖 동작을 만들 수 있다.

**발생 과정:** 주 모델 승인 → 별도 config·tokenizer·secondary source 선택 → 비승인 하위 자료 사용

**방어 위치:** 승인 목록·하위 from_pretrained 호출·loader source 선택

**예방·대응:** 실제 사용하는 모든 하위 자료와 revision을 승인 묶음에 포함하고 각 소비 호출에 고정값이 전달되는지 확인한다.

**대책의 적용 범위·남은 조건:** 최상위 revision 고정만으로 모든 하위 호출의 판본이 고정되지는 않는다. 실제 모델·resolver·요청 옵션별 분기를 확인한다.

**확인할 정상 동작:** 승인 목록에 포함된 config·tokenizer·template와 필요한 하위 모델로 정상 로딩한다.

**점검·판정 기준:** [2.1.1 CHK-SUP-003](04_환경별_적용과_체크리스트.md#CHK-SUP-003)

**공개 사례·패치에서 확인할 점:** [GHSA-3ww4-5jv9-j5gm](https://github.com/vllm-project/vllm/security/advisories/GHSA-3ww4-5jv9-j5gm) — 최상위 revision 고정이 하위 공급물에 전달되지 않는 사례다. 실제 하위 호출의 revision·code_revision을 조사한다.

**공개 사례·패치에서 확인할 점:** [GHSA-hhv2-872h-628q](https://github.com/vllm-project/vllm/security/advisories/GHSA-hhv2-872h-628q) — 일부 모델의 하위 processor·tokenizer·config에 고정값 전달이 빠진 사례다. 모델별 추가 경로와 기존 수정의 범위를 대조한다.

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 별도 config·tokenizer·secondary source 선택 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** config·tokenizer·primary/secondary weights의 선택·소비 경로가 있다. 확인한 loader 함수에서 조직 승인 manifest·서명자를 실제 파일과 대조하는 처리는 확인되지 않았다.

#### 3.6.8.4 이미지 tag·시작 명령 변경으로 코드 바꿔치기 · SC-10-03

**주체·처음 가진 권한:** 이미지 tag·registry 또는 배포 설정을 바꿀 수 있는 주체

**성립 조건:** 이미지 tag·registry·배포 설정을 변경할 수 있을 때.

**공격·실패 상황**

승인 후 tag가 다른 이미지를 가리키거나 시작 명령이 바뀐다. 실제 pull한 digest·패키지·entrypoint를 대조하지 않으면 다른 코드 환경이 운영에 사용될 수 있다.

**발생 과정:** 이미지·명령 승인 → tag·배포 설정 변경 → 다른 패키지·코드 기동

**방어 위치:** registry 권한·이미지 digest·배포 admission·기동 설정

**예방·대응:** 승인한 이미지 digest·패키지·entrypoint·유효 설정을 고정하고 실제 pull·기동 결과를 대조한다. 변경권과 승인을 분리한다.

**대책의 적용 범위·남은 조건:** 표시 tag·이미지 이름만 대조하지 않고 실제 digest와 실행 명령을 확인한다.

**확인할 정상 동작:** 승인 digest 이미지와 고정 패키지로 기동한다.

**점검·판정 기준:** [2.1.2 CHK-SUP-004](04_환경별_적용과_체크리스트.md#CHK-SUP-004)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 tag·배포 설정 변경 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [비승인 코드 실행](#attack-type-09) — 시나리오의 성립 조건에서 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다.

**기존 구현·남은 확인:** config·tokenizer·primary/secondary weights의 선택·소비 경로가 있다. 확인한 loader 함수에서 조직 승인 manifest·서명자를 실제 파일과 대조하는 처리는 확인되지 않았다.

#### 3.6.8.5 가중치 누락·변환 변경으로 승인과 다른 모델 제공 · SC-10-04

**주체·처음 가진 권한:** 모델 설정·가중치 변환 옵션을 바꿀 수 있는 주체

**성립 조건:** 모델별 mapper·양자화·후처리·weights 추적 조건이 있을 때.

**공격·실패 상황**

입력 파일 이름이 같아도 변환 옵션이나 실제 적재 결과가 다르면 다른 모델 동작을 만들 수 있다.

**발생 과정:** 파일 선택·변환 → 필수 tensor 누락·다른 옵션 적재 → 불완전·다른 모델 서비스

**방어 위치:** 모델 loader·rank별 적재 기록·배포 readiness

**예방·대응:** 모델별 필수 tensor·shard·변환 옵션을 정하고 실제 적재 기록과 정상 canary를 서비스 재개 조건으로 사용한다.

**대책의 적용 범위·남은 조건:** 의도된 양자화 후처리와 필수 누락을 구분한다. loaded_weights 반환·추적 옵션·경고의 의미는 모델별로 확인한다.

**확인할 정상 동작:** 완전한 checkpoint로 필요한 모든 TP rank가 자신에게 배정된 부분을 로딩한다.

**점검·판정 기준:** [2.2.2 CHK-SUP-006](04_환경별_적용과_체크리스트.md#CHK-SUP-006)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 필수 tensor 누락·다른 옵션 적재 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** config·tokenizer·primary/secondary weights의 선택·소비 경로가 있다. 확인한 loader 함수에서 조직 승인 manifest·서명자를 실제 파일과 대조하는 처리는 확인되지 않았다.

#### 3.6.8.6 중단된 컴파일 결과를 정상 생성물로 사용 · SC-12-03

**구분:** 실패·오설정

**실패 계기:** 컴파일·변환 작업의 중단·실패와 산출물 잔존

**성립 조건:** 생성 작업을 중단한 뒤 산출물이 남을 때.

**공격·실패 상황**

컴파일·변환 작업이 실패했지만 파일 일부가 남는다. 다음 실행이 완료 상태를 확인하지 않고 이를 읽으면 기동 실패나 잘못된 동작으로 이어질 수 있다.

**발생 과정:** 준비 중단 → 부분 생성물 잔존 → 다음 기동에서 완료본으로 선택

**방어 위치:** 생성 완료 표시·원자적 교체·실패 정리

**예방·대응:** 임시 위치에서 생성하고 완료 검증 뒤 게시한다. 실패·중단 자료를 격리·제거하고 다음 실행이 이를 거부·재생성하도록 한다.

**대책의 적용 범위·남은 조건:** 비악의 실패 시나리오다. 공격자 유발 능력은 별도 근거가 있을 때만 추가한다.

**확인할 정상 동작:** 완료 표시와 필요한 파일이 모두 갖춰진 생성물만 사용한다.

**점검·판정 기준:** [2.3.1 CHK-SUP-016](04_환경별_적용과_체크리스트.md#CHK-SUP-016)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 부분 생성물 잔존 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** compile cache의 키·디렉터리·해석·compiler load 경로가 있다. 캐시 키는 재사용 대상을 선택하는 정보이며 작성자의 승인과 자료의 진위는 별도 통제가 필요하다.

#### 3.6.8.7 부분 다운로드를 완성본으로 사용 · SC-15-03

**주체·처음 가진 권한:** 부분 파일을 바꿀 수 있는 주체 또는 다운로드 중단 상태

**성립 조건:** 부분 파일과 완료 cache를 같은 로딩 경로가 읽을 때.

**공격·실패 상황**

다운로드가 중단된 뒤 남은 파일을 다음 기동이 완성본으로 선택한다.

**발생 과정:** 다운로드 중단·파일 변경 → 완료 상태 오판 → 불완전 모델 로딩

**방어 위치:** 다운로드 완료 표시·cache 게시·loader 소비

**예방·대응:** 완료 검증 뒤 원자적으로 게시하고 부분 파일을 완료 cache와 분리한다. 불일치 시 거부·재취득하며 남은 자료의 쓰기권을 제한한다.

**대책의 적용 범위·남은 조건:** 실패 상태 자체와 공격자의 부분 파일 변경 가능성을 구분해 시험한다.

**확인할 정상 동작:** 완료 표시와 필요한 파일이 모두 갖춰진 생성물만 사용한다.

**점검·판정 기준:** [2.3.1 CHK-SUP-016](04_환경별_적용과_체크리스트.md#CHK-SUP-016)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 완료 상태 오판 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [검증 미완료 상태의 사용·서비스 재개](#attack-type-10) — 시나리오의 성립 조건에서 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다.

**기존 구현·남은 확인:** 파일 취득·해석·변환·compile·적재 경로가 있다. 조직의 단계별·누적 예산과 취득 SDK의 재시도·부분 파일 정리 효과는 실제 환경에서 확인해야 한다.

#### 3.6.8.8 가중치 payload 교체로 모델·세대 혼입 · SC-16-03

**주체·처음 가진 권한:** 허가된 가중치 공급 주체 또는 원본 자료 쓰기권자

**성립 조건:** publisher와 consumer가 별도 가중치 공급을 사용할 때.

**공격·실패 상황**

publisher나 원본 작성자가 payload를 바꾼다. consumer가 모델·세대·담당 rank를 제대로 대조하지 않으면 승인 밖 가중치나 다른 실행의 자료를 사용할 수 있다.

**발생 과정:** publisher·원본 변경 → 모델·rank·세대 대조 누락 → 잘못된 weights 사용

**방어 위치:** publisher 승인·payload 식별·consumer 적재 검사

**예방·대응:** 승인한 publisher·모델·내용·layout·rank·세대와 실제 수신을 대조한다. 불일치 자료는 수용하지 않고 준비 실패로 처리한다.

**대책의 적용 범위·남은 조건:** 각 consumer가 맡은 shard·layout 기준을 사용한다. 전체 파일·메모리가 모두 동일해야 한다는 기준으로 확대하지 않는다.

**확인할 정상 동작:** 완전한 checkpoint로 필요한 모든 TP rank가 자신에게 배정된 부분을 로딩한다.

**점검·판정 기준:** [2.2.2 CHK-SUP-006](04_환경별_적용과_체크리스트.md#CHK-SUP-006)

**분류 이유:** 실제 수신한 payload가 승인한 모델·내용·rank·세대와 맞는지 대조하는 무결성 문제를 주 분류로 삼았다.

**함께 확인할 원리:** [요청·공유 상태 혼동](#attack-type-04) — 시나리오의 성립 조건에서 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**기존 구현·남은 확인:** 선택 weights daemon은 socket·peer UID·구성 key 검사를 일부 제공한다. 메시지에 pickle을 사용하고 checkpoint 식별은 payload 전체 승인을 확인하지 않으며 release는 전역 cache에 영향을 준다.

#### 3.6.8.9 변조된 백업의 실행·서비스 사용 · SC-20-02

**주체·처음 가진 권한:** 복원할 백업·cache를 바꿀 수 있는 주체

**성립 조건:** 복원할 백업·cache를 바꿀 수 있는 주체가 있을 때.

**공격·실패 상황**

자료 쓰기 권한자가 백업을 수정하고 복구 작업이 이를 읽는다.

**발생 과정:** 백업 쓰기권 사용 → 복원 자료 교체 → 복구 consumer가 사용

**방어 위치:** 백업 저장소 권한·무결성 검증·복원 reader

**예방·대응:** 백업 작성·검토·복원 권한을 제한하고 식별·무결성·현재 승인을 사용 전에 확인한다. 안전한 복원 reader와 실행 권한을 적용한다.

**대책의 적용 범위·남은 조건:** 백업 이름·완료 표시만으로 내용과 실행 안전성을 증명하지 않는다.

**확인할 정상 동작:** 기본 재배포: 승인된 백업·설정·자격 참조·volume·Gateway 상태를 실제 배포 구성에 맞게 복원하고 정상 요청을 처리한다. 선택 snapshot: 생성 제한을 만족한 승인 자료로 재로딩·oracle·외부 gate 시험을 수행한다.

**점검·판정 기준:** [7.4.2 CHK-LIF-016](04_환경별_적용과_체크리스트.md#CHK-LIF-016)

**분류 이유:** 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다. 이 SC에서는 복원 자료 교체 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [비승인 코드 실행](#attack-type-09) — 변조된 복원 자료가 코드·객체 해석 경로에 도달할 때.

**기존 구현·남은 확인:** 일반 재배포·shutdown과 지원 조건이 제한된 snapshot 복원 경로를 구분했다. snapshot 호환 검사·oracle의 범위와 현재 조직 승인·자격 철회·외부 사본 검증은 따로 확인한다.

**예시:** 다른 계정이 쓸 수 있는 컴파일 cache에 악성 생성물을 넣는다. worker가 이를 pickle 등으로 해석해 실행하는 경로에 도달하면 서버 권한으로 코드가 실행될 수 있다.

#### 3.6.9.1 요청의 코드 버전 변경으로 비승인 모듈 로딩 · SC-11-01

**주체·처음 가진 권한:** 요청의 코드 버전 관련 필드를 바꿀 수 있는 호출자

**성립 조건:** 멀티모달 processor 경로에서 요청 mm kwargs를 허용할 때.

**공격·실패 상황**

호출자가 code_revision 같은 값을 요청에 넣어 다른 코드 버전을 선택하려 한다. v0.31.0은 기본 설정에서 비어 있지 않은 요청 mm kwargs를 거부한다.

**발생 과정:** code_revision 제출 → 허용된 요청 kwargs가 processor로 전달 → 다른 코드 버전 import

**방어 위치:** 요청 필드 정책·processor 인자·의존성의 코드 선택

**예방·대응:** 일반 요청의 코드 선택 필드를 거부·제거하고 승인 판본을 운영 설정에 고정한다. 허용해야 할 경우 최종 processor 소비 인자를 승인 목록과 검사한다.

**대책의 적용 범위·남은 조건:** 기본 mm kwargs 거부와 opt-in 허용 상태를 나눈다. 최종 실행은 auto_map·trust 설정·Transformers와 모델별 경로를 확인한다.

**확인할 정상 동작:** request override 없이 승인 processor·코드 판본으로 요청을 처리한다.

**점검·판정 기준:** [3.2.1 CHK-SUP-008](04_환경별_적용과_체크리스트.md#CHK-SUP-008)

**공개 사례·패치에서 확인할 점:** [GHSA-h3rc-6mm3-gc2m](https://github.com/vllm-project/vllm/security/advisories/GHSA-h3rc-6mm3-gc2m) — 요청의 code_revision이 동적 processor 코드 선택에 도달한 사례다. 기본 거부와 opt-in, auto_map·trust·의존성 조건을 구분한다.

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 허용된 요청 kwargs가 processor로 전달 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [공급물 변조·누락과 승인 대상 불일치](#attack-type-08) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**기존 구현·남은 확인:** 요청 mm kwargs는 기본 거부되며 opt-in 때 processor로 전달된다. plugin 그룹·endpoint factory·동적 import·실제 reader는 각각의 허용 조건과 실행 시점이 다르다.

#### 3.6.9.2 모델에 포함된 비승인 Python 코드 실행 · SC-11-02

**주체·처음 가진 권한:** 모델 코드·metadata를 제출하거나 바꿀 수 있는 주체

**성립 조건:** 선택한 모델의 custom code 소비 경로에 도달할 때.

**공격·실패 상황**

모델 제출자가 설정이나 추가 Python 파일을 바꾼다. loader가 그 코드를 실행할 때 승인·실행 제한이 부족하면 엔진 계정의 권한으로 허용 밖 동작이 생길 수 있다.

**발생 과정:** 모델 코드·metadata 변경 → custom code 소비 → 엔진 권한으로 실행

**방어 위치:** 모델 구현·추가 코드 승인·import 전 허용 검사

**예방·대응:** 선택 모델의 실제 trust 설정과 하위 호출을 대조하고 승인한 코드만 읽기 전용으로 제공한다. 코드 소비 프로세스의 권한을 제한한다.

**대책의 적용 범위·남은 조건:** 최상위 trust 플래그가 모든 하위 구현에 전달되는지는 모델별 확인이 필요하다.

**확인할 정상 동작:** 추가 코드 없이 승인한 모델이 정상 로딩된다.

**점검·판정 기준:** [3.2.2 CHK-SUP-009](04_환경별_적용과_체크리스트.md#CHK-SUP-009)

**공개 사례·패치에서 확인할 점:** [GHSA-7972-pg2x-xr59](https://github.com/vllm-project/vllm/security/advisories/GHSA-7972-pg2x-xr59) — 하위 모델 구현의 고정 trust 값이 상위 금지 설정을 무시한 사례다. 현재 해당 구현의 인자 전달을 확인하고 다른 모델까지 일반화하지 않는다.

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 custom code 소비 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 요청 mm kwargs는 기본 거부되며 opt-in 때 processor로 전달된다. plugin 그룹·endpoint factory·동적 import·실제 reader는 각각의 허용 조건과 실행 시점이 다르다.

#### 3.6.9.3 플러그인 발견·허용 검사 차이로 비승인 실행 · SC-11-03

**주체·처음 가진 권한:** 발견되는 plugin 패키지·entry point 등록을 바꿀 수 있는 주체

**성립 조건:** 설치된 entry point와 해당 runner·loader의 plugin 그룹이 사용될 때.

**공격·실패 상황**

패키지나 plugin 등록을 바꿀 수 있는 주체가 비승인 모듈을 발견 대상에 넣는다. 그룹·runner별 허용 검사가 다르면 일부 경로에서 import·실행될 수 있다.

**발생 과정:** 패키지·entry point 변경 → 그룹별 발견·필터 차이 → import·factory 실행

**방어 위치:** 설치 이미지·entry point·각 plugin loader

**예방·대응:** 운영 이미지의 plugin 패키지와 등록을 승인하고 그룹·runner별 허용 목록을 실제 loader에 적용한다. 불필요한 발견 대상과 설치 권한을 제한한다.

**대책의 적용 범위·남은 조건:** 한 plugin 그룹의 허용 목록이 모든 그룹·runner를 제한하는지 별도로 조사한다.

**확인할 정상 동작:** 승인된 plugin만 등록된 환경에서 필요한 기능이 정상 동작한다.

**점검·판정 기준:** [3.2.3 CHK-SUP-010](04_환경별_적용과_체크리스트.md#CHK-SUP-010)

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 그룹별 발견·필터 차이 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 시나리오의 성립 조건에서 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다.

**기존 구현·남은 확인:** 요청 mm kwargs는 기본 거부되며 opt-in 때 processor로 전달된다. plugin 그룹·endpoint factory·동적 import·실제 reader는 각각의 허용 조건과 실행 시점이 다르다.

#### 3.6.9.4 작업 거부 전에 플러그인 초기화 코드 실행 · SC-11-04

**주체·처음 가진 권한:** 사용할 endpoint plugin 이름이나 패키지를 바꿀 수 있는 주체

**성립 조건:** 해당 endpoint의 plugin factory를 사용할 때.

**공격·실패 상황**

운영자는 요청한 작업이 금지돼 플러그인이 실행되지 않을 것으로 기대한다. 하지만 factory 호출이 작업 검사보다 먼저라면 초기화 코드가 먼저 동작할 수 있다.

**발생 과정:** plugin 선택 → factory 실행 → 뒤늦은 작업 적합성 검사

**방어 위치:** endpoint plugin 선택·factory 호출 전 승인 검사

**예방·대응:** plugin 이름·패키지를 factory 호출 전에 승인하고 권한·설치 범위를 제한한다. 작업 적합성 검사 시점과 초기화 부작용을 확인한다.

**대책의 적용 범위·남은 조건:** 후속 task 거부가 초기화 코드 실행을 되돌려주지는 않는다. import·factory·task 검사를 순서대로 확인한다.

**확인할 정상 동작:** 승인된 plugin만 등록된 환경에서 필요한 기능이 정상 동작한다.

**점검·판정 기준:** [3.2.3 CHK-SUP-010](04_환경별_적용과_체크리스트.md#CHK-SUP-010)

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 factory 실행 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [검증 미완료 상태의 사용·서비스 재개](#attack-type-10) — 시나리오의 성립 조건에서 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다.

**기존 구현·남은 확인:** 요청 mm kwargs는 기본 거부되며 opt-in 때 processor로 전달된다. plugin 그룹·endpoint factory·동적 import·실제 reader는 각각의 허용 조건과 실행 시점이 다르다.

#### 3.6.9.5 실행 모드 변경으로 코드 허용 검사 생략 · SC-11-05

**주체·처음 가진 권한:** 동적 import 설정·지원 실행 모드에 영향을 줄 수 있는 주체

**방어 위치:** 보안 검증 코드·동적 import 설정·지원 실행 모드

**예방·대응:** 보안 판단을 명시적 조건·예외 처리로 집행하고 제거 가능한 assertion에만 의존하지 않게 한다. 지원 모드별로 같은 거부 결과를 시험한다.

**대책의 적용 범위·남은 조건:** 정확한 사례 함수와 현재 선택 경로가 만나는지 확인한 뒤 적용한다.

**확인할 정상 동작:** 지원한다고 선언한 각 실행 모드가 승인 import 목록으로 기동한다.

**점검·판정 기준:** [3.2.4 CHK-SUP-011](04_환경별_적용과_체크리스트.md#CHK-SUP-011)

**기존 구현·남은 확인:** 요청 mm kwargs는 기본 거부되며 opt-in 때 processor로 전달된다. plugin 그룹·endpoint factory·동적 import·실제 reader는 각각의 허용 조건과 실행 시점이 다르다.

#### 3.6.9.6 모델 파일 역직렬화로 비승인 코드 실행 · SC-11-06

**주체·처음 가진 권한:** 실제 reader가 읽을 파일을 만들거나 바꿀 수 있는 주체

**공격·실패 상황**

파일 작성자가 허용 밖 객체나 동작을 유발하는 자료를 넣는다.

**예방·대응:** 필요한 형식과 reader만 허용하고 수정된 의존성을 사용한다. 안전한 로딩 옵션을 확인하며 자료 쓰기권과 실행 권한을 제한한다.

**대책의 적용 범위·남은 조건:** safetensors 정책은 다른 컴파일 cache·메시지 reader까지 보호하지 않는다. 현행 weights_only 경로와 과거 취약 경로를 구분한다.

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 reader가 객체 역직렬화 지점과 기존 정상 대조를 확인한다.

#### 3.6.9.7 모델 template의 위험 동작·비용 유발 · SC-11-07

**주체·처음 가진 권한:** 모델의 tokenizer·chat template 파일을 바꿀 수 있는 주체

**성립 조건:** 모델이 제공한 template을 실제 renderer가 해석할 때.

**공격·실패 상황**

tokenizer의 template 파일을 바꿀 수 있는 주체가 허용 밖 동작이나 과도한 처리 비용을 요구하는 내용을 넣는다.

**발생 과정:** template 파일 변경 → renderer가 해석 → 허용 밖 동작·과도한 비용

**방어 위치:** 모델 template 승인·실제 renderer sandbox·자원 한도

**예방·대응:** template과 renderer 버전을 승인하고 허용 기능·sandbox·처리 비용 제한을 확인한다. 무해 경계 입력으로 정상·금지 동작을 비교한다.

**대책의 적용 범위·남은 조건:** 다른 제품의 template 취약점은 참고 사례로 사용하고 현재 vLLM renderer의 결함 여부는 별도로 확인한다.

**확인할 정상 동작:** 승인한 template가 정상 메시지를 기대 형식으로 렌더링한다. / 정상 메시지는 승인 template 적용 후 허용 길이·내용 제한을 만족한다.

**점검·판정 기준:** [3.3.2 CHK-SUP-013](04_환경별_적용과_체크리스트.md#CHK-SUP-013) · [3.1.1 CHK-REQ-007](04_환경별_적용과_체크리스트.md#CHK-REQ-007)

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 renderer가 해석 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [자원 고갈·처리 기회 독점](#attack-type-07) — template의 처리 시간·메모리 비용이 문제인 분기. 금지 함수·객체 접근은 09 유형의 별도 분기다.

**세부 상황 — template의 허용 밖 동작:** 선택 renderer의 template 해석이 허용 밖 함수·객체·동작에 도달하는 분기. 해당 동작의 실제 도달·영향은 시험 대기.

**세부 상황 — template 해석 비용 고갈:** 위험 함수 사용과 별개로 허용된 해석만으로도 시간·메모리 예산을 초과하는 분기. 비용 한도·정상 대조가 필요.

**기존 구현·남은 확인:** 요청 mm kwargs는 기본 거부되며 opt-in 때 processor로 전달된다. plugin 그룹·endpoint factory·동적 import·실제 reader는 각각의 허용 조건과 실행 시점이 다르다.

#### 3.6.9.8 공유 컴파일 캐시 변조를 통한 코드 실행 · SC-12-01

**주체·처음 가진 권한:** 다른 worker가 읽을 cache 디렉터리에 쓰기 권한이 있는 주체

**성립 조건:** 컴파일·AOT cache가 실제 생성되고 다시 읽힐 때.

**공격·실패 상황**

캐시 디렉터리에 쓰기 권한이 있는 주체가 다른 worker가 읽을 생성물을 바꾼다.

**발생 과정:** cache 쓰기권 확보 → 생성물 교체 → 다른 worker가 해석·실행

**방어 위치:** compile·AOT·Triton 등 실제 캐시 저장소와 consumer

**예방·대응:** 신뢰할 수 없는 주체와 cache를 공유하지 않고 writer·mount 권한을 제한한다. 원본·도구·설정별 식별과 검증·재생성 경로를 적용한다.

**대책의 적용 범위·남은 조건:** 기본 cache 사용 여부부터 확인한다. 형식이 pickle인 경로는 가중치 형식 제한과 별개로 평가한다.

**확인할 정상 동작:** 새 묶음의 빈 cache에서 생성하고 동일 묶음으로 정상 재기동한다.

**점검·판정 기준:** [2.2.3 CHK-SUP-007](04_환경별_적용과_체크리스트.md#CHK-SUP-007)

**분류 이유:** 변경한 cache를 다른 worker가 해석·실행하는 경로가 핵심이다. cache 쓰기권과 내용 변조는 이 경로의 선행 조건이다.

**함께 확인할 원리:** [공급물 변조·누락과 승인 대상 불일치](#attack-type-08) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**기존 구현·남은 확인:** compile cache의 키·디렉터리·해석·compiler load 경로가 있다. 캐시 키는 재사용 대상을 선택하는 정보이며 작성자의 승인과 자료의 진위는 별도 통제가 필요하다.

#### 3.6.9.9 허용 client 메시지로 비허용 객체·명령 처리 · SC-16-02

**주체·처음 가진 권한:** 허가된 client로 메시지를 만들 수 있는 주체

**성립 조건:** 선택한 daemon의 serializer·역직렬화 경로를 사용할 때.

**공격·실패 상황**

접속이 허용된 client가 메시지를 조절한다.

**발생 과정:** client 메시지 조작 → daemon의 역직렬화·dispatch → 허용 범위 초과

**방어 위치:** daemon protocol·serializer·명령 집행

**예방·대응:** 실제 메시지 형식·명령 범위를 제한하고 허용 주체·객체만 처리한다. 안전한 형식을 선택하고 동일 계정의 신뢰 범위를 명시한다.

**대책의 적용 범위·남은 조건:** pickle·동일 UID 신뢰를 쓰는 구현에서는 접속 통제와 공유 권한의 한계를 함께 평가한다.

**확인할 정상 동작:** 고정한 safetensors reader로 정상 checkpoint를 읽는다.

**점검·판정 기준:** [3.3.1 CHK-SUP-012](04_환경별_적용과_체크리스트.md#CHK-SUP-012)

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 daemon의 역직렬화·dispatch 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 시나리오의 성립 조건에서 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다.

**세부 상황 — 객체 역직렬화:** 실제 serializer가 공격자가 바꾼 객체를 해석·실행하는 분기.

**세부 상황 — 허용 밖 명령 사용:** 안전한 메시지 형식이어도 client가 권한 밖 명령·대상을 선택하는 분기.

**기존 구현·남은 확인:** 선택 weights daemon은 socket·peer UID·구성 key 검사를 일부 제공한다. 메시지에 pickle을 사용하고 checkpoint 식별은 payload 전체 승인을 확인하지 않으며 release는 전역 cache에 영향을 준다.

#### 3.6.9.10 변조한 진단 파일로 고권한 도구 동작 유도 · SC-21-04

**주체·처음 가진 권한:** 진단 파일을 바꿀 수 있지만 replay 실행 권한은 없는 주체

**성립 조건:** 진단 파일 변경권자와 이를 읽는 고권한 replay 도구가 있을 때.

**공격·실패 상황**

실행 권한이 없는 사람이 진단 파일을 바꿔 둔다.

**발생 과정:** 진단 파일 변경 → replay·역직렬화 도구 소비 → 허용 밖 실행·접근

**방어 위치:** 진단 파일 저장 권한·reader·재실행 승인

**예방·대응:** 진단 파일의 출처·무결성을 확인하고 안전한 reader·최소 권한 consumer를 사용한다. 파일 쓰기권과 실행 승인을 분리한다.

**대책의 적용 범위·남은 조건:** 외부 도구의 실제 형식·의존성·해석 경로를 확인해야 한다.

**확인할 정상 동작:** 승인 출처의 합성 진단 자료가 허용 reader로 처리된다.

**점검·판정 기준:** [3.3.3 CHK-OBS-008](04_환경별_적용과_체크리스트.md#CHK-OBS-008)

**분류 이유:** 승인 밖 모듈·플러그인·객체·template을 해석하거나 실행해 허용 밖 동작이 발생한다. 이 SC에서는 replay·역직렬화 도구 소비 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 코드 실행 없이도 도구가 허용 밖 대상·작업을 수행하는 분기.

**세부 상황 — 진단 자료의 코드·객체 해석:** replay·분석 도구의 실제 reader가 비허용 코드·객체를 해석하는 분기.

**세부 상황 — 도구의 권한 밖 대상 접근:** 진단 자료의 경로·옵션을 사용해 도구가 허용 밖 대상·작업에 접근하는 분기.

**기존 구현·남은 확인:** chat 응답의 prompt 문자열·token ID 반환과 오류·기본 예외 기록 경로가 있다. 반환 필드 제한·로그 독자·암호화·replay 권한은 실제 Gateway·저장소·도구에서 확인한다.

#### 3.6.10.1 필수 검사 오류를 성공으로 처리해 비승인 사용 · SC-13-01

**주체·처음 가진 권한:** 검사 오류·미지원·생략을 유도하거나 이용할 수 있는 공급물 제출자

**성립 조건:** 필수 검사 결과를 승인·배포 판단에 사용할 때.

**공격·실패 상황**

제출한 파일의 검사에 오류가 나거나 형식을 지원하지 않아 검사가 끝나지 않는다. 이 상태를 성공으로 바꾸면 검사하지 않은 자료가 승인·사용될 수 있다.

**발생 과정:** 검사 실패·미지원·생략 → 성공 상태로 승격 → 승인·배포 진행

**방어 위치:** 검사 상태 모델·승인 서비스·배포 게이트

**예방·대응:** 검사 원결과를 보존하고 채택한 필수 검사 보류 조건을 집행한다. 대체 검사는 동등성 검토·승인과 요구 증거를 갖춰 적용한다. 팀 참조의 핵심 위반·증거 부족은 위험 수용만으로 운영 사용하지 않는다.

**대책의 적용 범위·남은 조건:** 검사 원결과와 관리 결정을 각각 보존한다. 팀 참조에서 확인된 위반은 보완 또는 허용된 정책·묶음 재승인 뒤 재시험으로 해소 여부를 확인하며 실제 도구와 보류 집행을 대조한다.

**확인할 정상 동작:** 필수 검사와 승인 대상 일치가 확인된 정상 묶음은 다음 승인·운영 사용 단계로 진행한다.

**점검·판정 기준:** [7.1.1 CHK-SUP-014](04_환경별_적용과_체크리스트.md#CHK-SUP-014)

**분류 이유:** 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다. 이 SC에서는 성공 상태로 승격 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 기본 auto loader는 후보 패턴과 처음 일치하는 형식을 선택한다. 검사 상태와 조직의 배포 차단 연동, 선택 weights 공급의 fallback은 별도 구현·환경 확인이 필요하다.

#### 3.6.10.2 자동 파일 선택으로 승인 밖 형식 로딩 · SC-13-02

**주체·처음 가진 권한:** 자동 선택되는 대체 파일·형식 후보를 만들거나 바꿀 수 있는 주체

**성립 조건:** load_format auto 등 후보 파일 선택·대체 경로를 사용할 때.

**공격·실패 상황**

loader가 우선 파일 대신 다른 형식이나 경로의 후보를 선택한다. 주 파일만 승인한 절차에서는 이 대체 파일이 검사 밖에 남을 수 있다.

**발생 과정:** 우선 후보 선택 실패·다른 패턴 선택 → 대체 파일 선택 → 승인 밖 reader 소비

**방어 위치:** load_format·후보 파일 목록·loader 선택 검사

**예방·대응:** 형식·후보·실제 선택 파일을 승인 대상으로 관리하고 승인 밖 대체를 거부한다. 필요 없는 자동 형식·fallback 후보를 제한한다.

**대책의 적용 범위·남은 조건:** 파일 후보 선택과 손상 파일을 읽은 뒤 재시도는 다른 경로다. auto 기본 경로의 실제 동작을 확인한다.

**확인할 정상 동작:** 고정한 safetensors reader로 정상 checkpoint를 읽는다.

**점검·판정 기준:** [3.3.1 CHK-SUP-012](04_환경별_적용과_체크리스트.md#CHK-SUP-012)

**분류 이유:** 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다. 이 SC에서는 대체 파일 선택 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [비승인 코드 실행](#attack-type-09) — 선택된 대체 형식의 실제 reader가 비승인 객체·코드를 실행하는 경로에 도달할 때.

**기존 구현·남은 확인:** 기본 auto loader는 후보 패턴과 처음 일치하는 형식을 선택한다. 검사 상태와 조직의 배포 차단 연동, 선택 weights 공급의 fallback은 별도 구현·환경 확인이 필요하다.

#### 3.6.10.3 공유 공급 실패 뒤 승인 밖 파일로 전환 · SC-13-03

**주체·처음 가진 권한:** fallback 파일·공급원에 자료를 쓸 수 있는 주체

**성립 조건:** 공유·원격 가중치 공급과 fallback을 사용할 때.

**공격·실패 상황**

주 공급원이 실패하면 엔진이 로컬이나 다른 공급원으로 전환한다. 대체 자료를 승인·검사하지 않으면 다른 파일로 서비스가 계속될 수 있다.

**발생 과정:** 주 가중치 공급 실패 → fallback 선택 → 비승인 파일 사용

**방어 위치:** weights 공급·fallback 선택·소비 전 검증

**예방·대응:** 대체 공급원·자료에도 동일한 승인·무결성·실행 제한을 적용하고 허용 대체가 없으면 준비 실패로 처리한다.

**대책의 적용 범위·남은 조건:** 공유·원격 공급을 선택한 구현에서만 적용하며 기본 로컬 모델에 일괄 가정하지 않는다.

**확인할 정상 동작:** 고정한 safetensors reader로 정상 checkpoint를 읽는다.

**점검·판정 기준:** [3.3.1 CHK-SUP-012](04_환경별_적용과_체크리스트.md#CHK-SUP-012)

**분류 이유:** 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다. 이 SC에서는 fallback 선택 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 기본 auto loader는 후보 패턴과 처음 일치하는 형식을 선택한다. 검사 상태와 조직의 배포 차단 연동, 선택 weights 공급의 fallback은 별도 구현·환경 확인이 필요하다.

#### 3.6.10.4 rank 준비 실패를 놓친 채 요청 수용 · SC-17-01

**구분:** 실패·오설정

**성립 조건:** 기본 TP 실행 그룹을 기동·재배포할 때.

**공격·실패 상황**

**대책의 적용 범위·남은 조건:** 프로세스 생존·포트 개방과 실제 준비 완료를 구분한다. 기본 TP 재배포에서 직접 확인한다.

**점검·판정 기준:** [7.3.1 CHK-LIF-005](04_환경별_적용과_체크리스트.md#CHK-LIF-005) · [7.2.1 CHK-LIF-007](04_환경별_적용과_체크리스트.md#CHK-LIF-007) · [7.2.2 CHK-LIF-009](04_환경별_적용과_체크리스트.md#CHK-LIF-009) · [6.4.2 CHK-LIF-011](04_환경별_적용과_체크리스트.md#CHK-LIF-011)

#### 3.6.10.5 승인·준비 검증을 건너뛴 서비스 재개 · SC-17-02

**공격·실패 상황**

제한된 배포·관리 권한자가 현재 승인 대조를 건너뛰고 요청 수용을 재개한다.

**발생 과정:** 배포·관리 권한 사용 → 현재 승인·준비 대조 생략 → 요청 재개

**방어 위치:** 배포 승인 게이트·routing·재개 권한

**예방·대응:** 현재 승인 모델·설정·필수 준비 증거가 갖춰져야 재개되도록 집행하고 재개 권한·예외·이력을 관리한다.

**대책의 적용 범위·남은 조건:** 배포 명령의 성공만으로 서비스 준비를 대신하지 않는다. 기업별 승인·집행 도구를 확인한다.

**분류 이유:** 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다. 이 SC에서는 현재 승인·준비 대조 생략 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 시나리오의 성립 조건에서 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다.

#### 3.6.10.6 snapshot 복원 검증 전에 추론 요청 접수 · SC-20-04

**구분:** 실패·오설정

**실패 계기:** 운영자의 snapshot 복원·재기동과 동시에 들어오는 요청

**성립 조건:** Linux x86_64 동일 호스트·단일 병렬 크기의 지원 snapshot 구성을 선택했을 때.

**공격·실패 상황**

복원 과정에서 검증 절차가 끝나기 전에 listener가 열리면 동시에 들어온 요청을 먼저 받을 수 있다. 기본 다중 GPU TP 구성에서는 적용하지 않는다.

**발생 과정:** snapshot 복원 → 검증 전 listener 개방 → 동시 요청 도달

**방어 위치:** 외부 진입 차단·복원 검증·routing 재개

**예방·대응:** 복원 중에는 외부 요청 수용을 차단하고 현재 승인·검증·정상 추론을 확인한 뒤 routing을 연다.

**대책의 적용 범위·남은 조건:** 단일 병렬 크기 등 snapshot 지원 조건에서만 시험한다. 기본 다중 GPU TP 구성에는 적용하지 않는다.

**확인할 정상 동작:** 기본 재배포: 승인된 백업·설정·자격 참조·volume·Gateway 상태를 실제 배포 구성에 맞게 복원하고 정상 요청을 처리한다. 선택 snapshot: 생성 제한을 만족한 승인 자료로 재로딩·oracle·외부 gate 시험을 수행한다.

**점검·판정 기준:** [7.4.2 CHK-LIF-016](04_환경별_적용과_체크리스트.md#CHK-LIF-016)

**분류 이유:** 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다. 이 SC에서는 검증 전 listener 개방 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 일반 재배포·shutdown과 지원 조건이 제한된 snapshot 복원 경로를 구분했다. snapshot 호환 검사·oracle의 범위와 현재 조직 승인·자격 철회·외부 사본 검증은 따로 확인한다.

<a id="attack-type-11"></a>
### 3.6.11 과도한 실행 권한·서버 자격 사용

**개념:** 프로세스에 부여되거나 대신 사용하는 자격의 범위가 작업에 필요한 권한을 넘는다.

**방어 초점:** 최소 권한 계정·Secret·mount·목적지와 자격 선택

**이렇게 묶은 이유:** 요청자의 작업 인가와 실행 프로세스가 가진 권한을 구분했다. 이미 침해된 worker의 권한을 일반 API 호출자의 권한과 합산하지 않는다.

**예시:** 모델 취득용 저장소 자격이 추론 worker에도 그대로 전달된다. worker가 침해되면 추론에 필요 없는 저장소 자료까지 읽을 수 있다.

<a id="guide-SC-14-01"></a>
#### 3.6.11.1 서버 자격을 이용한 다른 저장소 자료 접근 · SC-14-01

**주체·처음 가진 권한:** 서버가 취득할 저장소·객체의 참조를 바꿀 수 있는 주체

**성립 조건:** 서버가 보유한 자격으로 지정 저장소·객체에 접근할 때.

**공격·실패 상황**

참조값을 바꿀 수 있는 주체가 자신의 권한 밖 저장소·객체를 지정한다. 서버 자격의 범위가 넓고 대상 제한이 부족하면 요청자에게 허용되지 않은 자료를 서버가 가져올 수 있다.

**발생 과정:** 참조 대상 변경 → 서버의 넓은 취득 자격 사용 → 요청자 허용 밖 자료 읽기

**방어 위치:** 모델 취득 API·SDK 자격 선택·저장소 객체 ACL

**예방·대응:** 취득 대상 저장소·객체를 허용 목록으로 제한하고 전용 최소 권한 계정을 사용한다. 실제 자격·목적지·객체 접근을 기록한다.

**대책의 적용 범위·남은 조건:** 요청자의 권한과 서버가 대신 사용하는 자격을 구분한다. 일반적인 임의 URL 입력 전체 평가는 R10의 대기 범위를 유지한다.

**확인할 정상 동작:** 선정한 공급 경로에서 실제 취득·반입·마운트 주체가 허용된 저장소 객체 또는 로컬 파일에만 접근해 모델을 준비한다. / 필요한 저장소·관측 목적지에 승인된 연결만 발생한다.

**점검·판정 기준:** [1.5.1 CHK-PLT-003](04_환경별_적용과_체크리스트.md#CHK-PLT-003) · [1.6.1 CHK-PLT-007](04_환경별_적용과_체크리스트.md#CHK-PLT-007)

**분류 이유:** 프로세스에 부여되거나 대신 사용하는 자격의 범위가 작업에 필요한 권한을 넘는다. 이 SC에서는 서버의 넓은 취득 자격 사용 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 시나리오의 성립 조건에서 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다.

**기존 구현·남은 확인:** worker의 환경 준비와 SDK 자격 선택 경로가 있다. 확인한 환경 전달 함수에는 필요한 Secret만 허용하는 목록이 없고 실제 계정·mount·자격 범위는 환경값이다.

<a id="guide-SC-14-02"></a>
#### 3.6.11.2 자격 만료 뒤 승인하지 않은 대체 접근 · SC-14-02

**구분:** 실패·오설정

**실패 계기:** 취득 자격의 만료·설정 누락

**성립 조건:** 선택한 SDK의 자격 선택·fallback 경로가 있을 때.

**공격·실패 상황**

저장소 자격이 만료되거나 빠졌을 때 SDK가 다른 계정·익명 접근을 시도할 수 있다. 그 동작이 기업 정책에 맞는지 조사하고, 허용한 자격의 정상 취득과 비교한다. 실제 대체 동작은 SDK별 확인이 남아 있다.

**발생 과정:** 자격 만료·누락 → SDK가 다른 자격·익명 경로 시도 → 정책 밖 취득

**방어 위치:** SDK 자격 chain·설정·취득 실패 처리

**예방·대응:** 승인 자격을 명시하고 대체·익명 접근 허용 여부를 정책으로 정한다. 만료·누락 시 실제 선택 주체를 관측하고 비허용 대체는 거부한다.

**대책의 적용 범위·남은 조건:** SDK별 대체 동작의 존재와 순서는 아직 환경·의존성 조사 대상이다.

**확인할 정상 동작:** 유효 자격으로 승인 객체를 정상 취득한다.

**점검·판정 기준:** [1.5.3 CHK-PLT-005](04_환경별_적용과_체크리스트.md#CHK-PLT-005)

**분류 이유:** 프로세스에 부여되거나 대신 사용하는 자격의 범위가 작업에 필요한 권한을 넘는다. 이 SC에서는 SDK가 다른 자격·익명 경로 시도 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [검증 미완료 상태의 사용·서비스 재개](#attack-type-10) — 시나리오의 성립 조건에서 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다.

**기존 구현·남은 확인:** worker의 환경 준비와 SDK 자격 선택 경로가 있다. 확인한 환경 전달 함수에는 필요한 Secret만 허용하는 목록이 없고 실제 계정·mount·자격 범위는 환경값이다.

<a id="guide-SC-14-03"></a>
#### 3.6.11.3 worker에 전달된 불필요한 비밀정보 탈취 · SC-14-03

**주체·처음 가진 권한:** 제한된 worker·프로세스의 실행 권한을 확보한 주체

**성립 조건:** worker가 환경변수·Secret mount·장치 권한을 물려받을 때.

**공격·실패 상황**

제한된 worker가 침해되면 전달받은 저장소 키나 파일·장치 권한도 사용될 수 있다. 실제 상속·mount와 필요한 작업을 비교해 불필요한 권한을 찾는다.

**발생 과정:** worker 침해 → 상속 환경·Secret·mount 읽기 → 역할 밖 자료·장치 사용

**방어 위치:** 프로세스 생성 환경·Secret mount·호스트 권한

**예방·대응:** worker에 필요한 환경변수·Secret·파일·장치만 전달한다. 취득·서빙·관측 자격을 분리하고 잔존·철회 절차를 적용한다.

**대책의 적용 범위·남은 조건:** worker 침해 권한을 일반 API 호출자의 권한으로 합산하지 않는다.

**확인할 정상 동작:** worker가 필요한 최소 자격으로 정상 실행한다.

**점검·판정 기준:** [1.5.2 CHK-PLT-004](04_환경별_적용과_체크리스트.md#CHK-PLT-004)

**분류 이유:** 프로세스에 부여되거나 대신 사용하는 자격의 범위가 작업에 필요한 권한을 넘는다. 이 SC에서는 상속 환경·Secret·mount 읽기 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** worker의 환경 준비와 SDK 자격 선택 경로가 있다. 확인한 환경 전달 함수에는 필요한 Secret만 허용하는 목록이 없고 실제 계정·mount·자격 범위는 환경값이다.

<a id="guide-SC-14-04"></a>
#### 3.6.11.4 승인 코드의 과도한 권한을 이용한 피해 확대 · SC-14-04

**주체·처음 가진 권한:** 승인된 확장 코드를 실행하되 추가 자산 접근은 제한돼야 하는 주체

**성립 조건:** 확장 코드 실행은 허용했지만 접근 범위를 제한해야 할 때.

**공격·실패 상황**

승인한 코드가 엔진 계정의 넓은 mount·자격·장치 권한으로 실행된다. 코드의 사용 승인과 별도로 실제 접근 가능 범위를 확인해 다른 보호 자산에 미치는 영향을 평가한다.

**발생 과정:** 허용 코드 실행 → 넓은 계정·mount·장치 권한 사용 → 추가 자산 접근

**방어 위치:** 컨테이너·OS 실행 계정·파일·device·송신 정책

**예방·대응:** 승인 코드에도 작업별 최소 권한과 필요한 파일·장치·통신만 제공한다. 신뢰 집단이 다르면 적절한 프로세스·배포 분리를 적용한다.

**대책의 적용 범위·남은 조건:** 코드 승인과 실행 환경의 격리는 각각 확인한다. 분리 수준과 예외는 기업의 위협·성능 요구에 맞춰 결정한다.

**확인할 정상 동작:** 승인 실행 계정이 필요한 모델·장치에 접근해 추론한다. / 필요한 저장소·관측 목적지에 승인된 연결만 발생한다.

**점검·판정 기준:** [1.4.1 CHK-PLT-001](04_환경별_적용과_체크리스트.md#CHK-PLT-001) · [1.6.1 CHK-PLT-007](04_환경별_적용과_체크리스트.md#CHK-PLT-007)

**분류 이유:** 프로세스에 부여되거나 대신 사용하는 자격의 범위가 작업에 필요한 권한을 넘는다. 이 SC에서는 넓은 계정·mount·장치 권한 사용 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** worker의 환경 준비와 SDK 자격 선택 경로가 있다. 확인한 환경 전달 함수에는 필요한 Secret만 허용하는 목록이 없고 실제 계정·mount·자격 범위는 환경값이다.

<a id="attack-type-12"></a>
### 3.6.12 철회·폐기 정책의 미반영

**개념:** 철회한 권한·모델·자격이 새 요청, 기존 세션 또는 복원 경로에서 다시 유효하게 사용된다.

**방어 초점:** 신규·기존 참조의 철회 반영과 복원 전 현재 승인 대조

**이렇게 묶은 이유:** 권한 철회와 과거 상태 복원에서 같은 현재 정책 미반영 문제를 모았다. 파일 삭제와 자격 효력 정지는 각각 확인한다.

**예시:** 운영자가 API key를 철회했는데 과거 snapshot을 복원하면서 옛 key도 되살린다. 현재 승인을 다시 확인하지 않으면 금지했던 접근이 재개될 수 있다.

<a id="guide-SC-19-01"></a>
#### 3.6.12.1 권한 철회 뒤 새 요청 계속 실행 · SC-19-01

**주체·처음 가진 권한:** 철회 전 발급받은 token·자격을 보유한 주체

**성립 조건:** 사용 중인 발급자·인증 cache·철회 절차에 반영 기한이 있을 때.

**공격·실패 상황**

이전 자격 보유자가 권한 철회 뒤 새 요청이나 자격 갱신을 시도한다. 정한 기한 뒤에도 허용되면 신규 접근 차단 요구를 충족하지 못한다.

**발생 과정:** 자격 철회 → cache·발급자 반영 지연 → 기한 뒤 신규 접근

**방어 위치:** issuer·Gateway·엔진 인증 cache·토큰 갱신

**예방·대응:** 철회 반영 기한을 정하고 발급·검증·갱신 지점에서 신규 요청을 차단한다. 캐시 무효화와 키 교체를 시험한다.

**대책의 적용 범위·남은 조건:** 제품·외부 인증 체계의 실제 철회 계약과 기한을 확인한다.

**확인할 정상 동작:** 철회 전 허용 자격으로 신규 접근이 가능하다.

**점검·판정 기준:** [1.7.1 CHK-PLT-010](04_환경별_적용과_체크리스트.md#CHK-PLT-010)

**분류 이유:** 철회한 권한·모델·자격이 새 요청, 기존 세션 또는 복원 경로에서 다시 유효하게 사용된다. 이 SC에서는 cache·발급자 반영 지연 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 자격·권한의 전달과 잔존 접점이 통합본에 정리돼 있다. issuer·Gateway cache·장기 세션의 철회 계약과 기한은 선정 환경의 정책·구현 확인이 필요하다.

<a id="guide-SC-19-02"></a>
#### 3.6.12.2 철회 전 세션·handle로 접근 유지 · SC-19-02

**주체·처음 가진 권한:** 권한 철회 전에 열린 session·연결·handle을 보유한 주체

**성립 조건:** 철회 전부터 열린 session·연결·handle이 있을 때.

**공격·실패 상황**

새 인증은 거부되지만 기존 연결이나 참조로 작업이 이어진다.

**발생 과정:** 철회 전 연결 확보 → 신규 인증만 차단 → 기존 세션·참조 계속 사용

**방어 위치:** 장기 연결·세션·공유 handle의 수명 관리

**예방·대응:** 철회 시 기존 연결의 재인증·제한·종료 규칙과 기한을 적용한다. 실제 스트림·세션·handle 접근을 시험한다.

**대책의 적용 범위·남은 조건:** 신규 요청 차단과 기존 참조 회수는 각각의 정책·결과로 기록한다.

**확인할 정상 동작:** 철회 전 기존 session·handle이 정상 동작한다.

**점검·판정 기준:** [1.7.2 CHK-PLT-011](04_환경별_적용과_체크리스트.md#CHK-PLT-011)

**분류 이유:** 철회한 권한·모델·자격이 새 요청, 기존 세션 또는 복원 경로에서 다시 유효하게 사용된다. 이 SC에서는 신규 인증만 차단 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 자격·권한의 전달과 잔존 접점이 통합본에 정리돼 있다. issuer·Gateway cache·장기 세션의 철회 계약과 기한은 선정 환경의 정책·구현 확인이 필요하다.

<a id="guide-SC-19-03"></a>
#### 3.6.12.3 폐기한 자격 사본으로 금지 접근 재개 · SC-19-03

**주체·처음 가진 권한:** 파일·로그 등에 남은 자격 사본을 읽을 수 있는 주체

**성립 조건:** 자격이 파일·로그·백업에 남고 읽기·재사용 경로가 있을 때.

**공격·실패 상황**

잔존 사본을 읽을 수 있는 주체가 폐기된 키를 꺼내 접근한다.

**발생 과정:** 잔존 파일·로그에서 키 읽기 → 폐기 후 재사용 → 접근 허용

**방어 위치:** 자격 발급자·사본 저장소·폐기·권한 회수

**예방·대응:** 자격을 발급자에서 철회하고 파일·로그·백업의 사본을 보존·삭제 정책으로 관리한다. 실제 재사용을 시험한다.

**대책의 적용 범위·남은 조건:** 파일 삭제와 자격 효력 정지는 별도 통제다. 읽기권과 실제 사용할 수 있는 경로를 확인한다.

**확인할 정상 동작:** 활성 자격 사본만 허용 위치에서 사용된다.

**점검·판정 기준:** [1.7.3 CHK-PLT-012](04_환경별_적용과_체크리스트.md#CHK-PLT-012)

**분류 이유:** 철회한 권한·모델·자격이 새 요청, 기존 세션 또는 복원 경로에서 다시 유효하게 사용된다. 이 SC에서는 폐기 후 재사용 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [민감정보 공개·사본 잔존](#attack-type-14) — 시나리오의 성립 조건에서 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다.

**기존 구현·남은 확인:** 자격·권한의 전달과 잔존 접점이 통합본에 정리돼 있다. issuer·Gateway cache·장기 세션의 철회 계약과 기한은 선정 환경의 정책·구현 확인이 필요하다.

<a id="guide-SC-20-01"></a>
#### 3.6.12.4 과거 백업으로 철회된 모델·자격 복원 · SC-20-01

**주체·처음 가진 권한:** 이전 배포 묶음을 복원할 수 있는 운영자

**성립 조건:** 이전 배포 묶음·설정·자격을 복원할 때.

**공격·실패 상황**

운영자가 예전 승인본을 복원한다. 현재 승인을 다시 대조하지 않으면 이미 철회한 모델·코드·키가 서비스에 돌아올 수 있다.

**발생 과정:** 이전 묶음 복원 → 현재 승인 대조 누락 → 철회한 모델·키 재사용

**방어 위치:** 복원 승인·구성 대조·자격 재발급·재개 게이트

**예방·대응:** 복원할 모델·코드·설정·자격을 현재 승인과 대조하고 필요한 키를 재발급한다. 외부 volume·Gateway 상태도 복원 검증에 포함한다.

**대책의 적용 범위·남은 조건:** 과거 승인 이력과 현재 유효 승인은 구분한다. snapshot 지원 제약은 해당 기능에서 별도 확인한다.

**확인할 정상 동작:** 현재 승인에 포함된 이전 묶음으로 rollback 후 정상 서비스한다.

**점검·판정 기준:** [7.4.1 CHK-LIF-015](04_환경별_적용과_체크리스트.md#CHK-LIF-015)

**분류 이유:** 과거 승인 상태를 복원한 뒤 현재 철회·승인이 적용되는지가 핵심이다. 현재 정책 미반영으로 분류했다.

**함께 확인할 원리:** [검증 미완료 상태의 사용·서비스 재개](#attack-type-10) — 시나리오의 성립 조건에서 필수 검사·승인·준비가 끝나지 않았거나 대체 경로가 같은 검사를 거치지 않았는데 사용을 허용한다.

**기존 구현·남은 확인:** 일반 재배포·shutdown과 지원 조건이 제한된 snapshot 복원 경로를 구분했다. snapshot 호환 검사·oracle의 범위와 현재 조직 승인·자격 철회·외부 사본 검증은 따로 확인한다.

<a id="attack-type-13"></a>
### 3.6.13 작업 종결 실패·중복 실행

**개념:** 취소·실패·해제·재시도 뒤 필요한 작업과 참조가 정리되지 않거나 사용 중 참조가 먼저 해제된다.

**방어 초점:** 종결 전파, 참조 수명, 시도별 정리·완료 확인

**이렇게 묶은 이유:** 공유 가중치의 전역 해제와 요청·worker·profiler 종결을 자원 수명 관점에서 통합했다. 정상 해제와 장애·중복 실행은 별도 시험한다.

**예시:** Gateway가 timeout 응답을 보낸 뒤 이전 GPU 작업이 남아 있다. 자동 재시도를 사용하면 같은 논리 요청이 두 번 실행되고 늦은 결과가 새 시도와 섞일 수 있다.

<a id="guide-SC-16-04"></a>
#### 3.6.13.1 전역 cache 해제로 다른 소비자의 참조 손상 · SC-16-04

**주체·처음 가진 권한:** daemon socket으로 release를 보낼 수 있는 소비 프로그램

**성립 조건:** ipc_cache·preload daemon에서 release를 보낼 수 있을 때.

**공격·실패 상황**

consumer 하나가 release를 보내면 daemon의 cache 전체가 해제된다.

**발생 과정:** consumer가 release 전송 → daemon 전체 cache 해제 → 다른 consumer·fallback 영향

**방어 위치:** daemon release 권한·공유 참조 수명·재취득 경로

**예방·대응:** 전역 해제 권한과 실행 시점을 제한하고 사용 중 consumer의 copy·zero-copy 수명을 보호한다. 재취득·fallback에도 현재 승인을 적용한다.

**대책의 적용 범위·남은 조건:** 실제 release는 handle 하나보다 넓은 범위에 영향을 준다. consumer 하나의 정상 종료만으로 전체 안전성을 판정하지 않는다.

**확인할 정상 동작:** daemon을 사용하지 않는 기본 TP와 별개로 선택 환경의 정상 취득·release를 확인한다.

**점검·판정 기준:** [4.4.4 CHK-LIF-013](04_환경별_적용과_체크리스트.md#CHK-LIF-013)

**분류 이유:** daemon 전체 해제와 다른 consumer의 참조 수명이 맞지 않는 것이 핵심이다. 전역 해제 명령의 인가도 관련 원리로 남겼다.

**함께 확인할 원리:** [인증·인가 우회](#attack-type-01) — 시나리오의 성립 조건에서 호출자의 신원이나 모델·객체·작업 권한을 검사하지 않아 허용 밖 기능을 사용한다.

**기존 구현·남은 확인:** 선택 weights daemon은 socket·peer UID·구성 key 검사를 일부 제공한다. 메시지에 pickle을 사용하고 checkpoint 식별은 payload 전체 승인을 확인하지 않으며 release는 전역 cache에 영향을 준다.

<a id="guide-SC-18-01"></a>
#### 3.6.13.2 취소 뒤 GPU 작업·출력·참조 잔존 · SC-18-01

**주체·처음 가진 권한:** 자기 요청을 취소하거나 연결을 끊을 수 있는 호출자

**성립 조건:** 요청이 대기·계산·출력 중 취소되거나 연결이 끊길 때.

**공격·실패 상황**

사용자에게 응답 종료를 알린 뒤에도 GPU 계산이나 출력·메모리 참조가 남을 수 있다.

**발생 과정:** 취소·연결 종료 → 응답 종료 → 계산·전송·참조 정리 누락

**방어 위치:** Gateway·ASGI·AsyncLLM·scheduler·worker 종결

**예방·대응:** 외부·내부 ID·시도별 취소를 전파하고 계산·출력·참조를 정한 기한 내 정리한다. stop 문자열의 종료 판단도 Core abort와 대조한다.

**대책의 적용 범위·남은 조건:** 응답 종료·scheduler 상태 제거·GPU 연산 완료·자료 소거는 별도 사건으로 관측한다.

**확인할 정상 동작:** 정상 완료 요청과 취소 없는 재요청이 서로 독립 처리된다. / 정상 완료 요청은 실행·전송·참조를 정한 기한에 정리한다.

**점검·판정 기준:** [4.1.2 CHK-REQ-012](04_환경별_적용과_체크리스트.md#CHK-REQ-012) · [6.4.1 CHK-LIF-010](04_환경별_적용과_체크리스트.md#CHK-LIF-010)

**분류 이유:** 취소·실패·해제·재시도 뒤 필요한 작업과 참조가 정리되지 않거나 사용 중 참조가 먼저 해제된다. 이 SC에서는 응답 종료 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [자원 고갈·처리 기회 독점](#attack-type-07) — 시나리오의 성립 조건에서 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다.

**기존 구현·남은 확인:** disconnect·generate 취소·AsyncLLM abort·Core dispatch·scheduler finish 경로가 있다. 진행 GPU 작업·전송·connector 참조의 실제 종료 시점은 상태 제거와 따로 관측해야 한다.

<a id="guide-SC-18-02"></a>
#### 3.6.13.3 worker 장애 뒤 그룹 자원 정리 실패 · SC-18-02

**구분:** 실패·오설정

**실패 계기:** rank 손실·worker 장애; 공격자의 worker 제어는 별도 조건

**성립 조건:** 사용하는 executor·collective에서 worker 장애가 발생할 때.

**공격·실패 상황**

rank 하나가 사라진 뒤 나머지 작업이나 IPC·GPU 참조가 남는다.

**발생 과정:** rank 손실 → 장애 전파·그룹 정리 미완료 → 작업·IPC·GPU 참조 잔존

**방어 위치:** executor 감시·엔진 장애 처리·그룹 재기동

**예방·대응:** worker 장애를 상위에 전달하고 영향 요청·신규 수용을 처리한다. EngineDeadError 경로에서는 실행 그룹·잔존 자원을 확인하고 준비 검증 뒤 재개한다.

**대책의 적용 범위·남은 조건:** 살아 있는 엔진의 요청별 abort와 엔진 장애를 같은 처리로 묶지 않는다.

**확인할 정상 동작:** 필수 rank가 맡은 계산·통신을 완료하고, 선정 executor의 출력 rank 또는 집계 경로가 최종 결과를 반환해 정상 TP 요청이 완료된다. 모든 rank가 같은 최종 출력을 반환한다고 가정하지 않는다. / 정상 종료 후 TP process·통신 자원을 정리하고 다시 기동한다.

**점검·판정 기준:** [6.3.1 CHK-LIF-008](04_환경별_적용과_체크리스트.md#CHK-LIF-008) · [6.4.2 CHK-LIF-011](04_환경별_적용과_체크리스트.md#CHK-LIF-011)

**분류 이유:** 취소·실패·해제·재시도 뒤 필요한 작업과 참조가 정리되지 않거나 사용 중 참조가 먼저 해제된다. 이 SC에서는 장애 전파·그룹 정리 미완료 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** disconnect·generate 취소·AsyncLLM abort·Core dispatch·scheduler finish 경로가 있다. 진행 GPU 작업·전송·connector 참조의 실제 종료 시점은 상태 제거와 따로 관측해야 한다.

<a id="guide-SC-18-03"></a>
#### 3.6.13.4 자동 재시도로 중복 실행·결과 혼입 · SC-18-03

**주체·처음 가진 권한:** 자기 요청을 재시도하는 호출자 또는 자동 retry 계층

**성립 조건:** 이전 실행이 끝나기 전에 클라이언트·Gateway 등의 retry가 시작될 때.

**공격·실패 상황**

같은 논리 요청의 새 시도가 시작됐는데 원래 실행이 계속된다. 중복 계산·비용과 늦은 결과의 잘못된 반환을 확인하고 각 시도별 정리·결과 수신자를 추적한다.

**발생 과정:** 원시도 미종결 → 새 시도 시작 → 중복 계산·늦은 결과 반환

**방어 위치:** 클라이언트·Gateway retry·요청·시도 registry

**예방·대응:** 자동 retry 사용·한도·중단 조건을 정하고 시도 ID를 구분한다. 이전 시도를 정리하고 늦은 결과를 새 시도와 분리하며 비용을 기록한다.

**대책의 적용 범위·남은 조건:** retry는 선택 기능이다. 논리 요청 ID가 같아도 실행 시도별 종료와 비용을 확인한다.

**확인할 정상 동작:** 정상 완료 요청과 취소 없는 재요청이 서로 독립 처리된다. / 선정한 retry 정책의 정상 호출을 추적한다. 비사용 구성은 한 호출·한 attempt를, 허용 구성은 정상 응답에서 불필요한 추가 attempt 없이 완료됨을 확인한다.

**점검·판정 기준:** [4.1.2 CHK-REQ-012](04_환경별_적용과_체크리스트.md#CHK-REQ-012) · [6.2.2 CHK-LIF-012](04_환경별_적용과_체크리스트.md#CHK-LIF-012)

**분류 이유:** 취소·실패·해제·재시도 뒤 필요한 작업과 참조가 정리되지 않거나 사용 중 참조가 먼저 해제된다. 이 SC에서는 새 시도 시작 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [요청·공유 상태 혼동](#attack-type-04) — 시나리오의 성립 조건에서 요청·입력·모델·세대의 대응이 틀리거나 이전 상태가 남아 다른 실행의 상태를 사용한다.

**함께 확인할 원리:** [자원 고갈·처리 기회 독점](#attack-type-07) — 시나리오의 성립 조건에서 입력·준비·대기·출력 비용을 누적시키거나 실행 순서를 독점해 다른 요청의 처리를 방해한다.

**기존 구현·남은 확인:** disconnect·generate 취소·AsyncLLM abort·Core dispatch·scheduler finish 경로가 있다. 진행 GPU 작업·전송·connector 참조의 실제 종료 시점은 상태 제거와 따로 관측해야 한다.

#### 3.6.13.5 profiler 정지 응답을 수집 종료로 오판 · SC-23-05

**구분:** 실패·오설정

**실패 계기:** 활성 profiler backend의 정지 오류

**성립 조건:** profiler 설정으로 route가 등록되고 해당 backend를 사용할 때.

**공격·실패 상황**

운영자가 정지 API의 응답이나 내부 상태값만 보고 수집 종료를 판단한다.

**발생 과정:** stop 호출·backend 오류 → 내부 상태만 종료 표시 → 수집·자원 잔존

**방어 위치:** profiler backend·API·파일·자원 회수 관측

**예방·대응:** 정지 응답과 실제 backend 수집 종료·파일 닫힘·자원 회수를 대조하고 실패·시간 초과를 표시한다.

**대책의 적용 범위·남은 조건:** profiler route 등록·권한과 실제 backend를 확인한다. 고장 주입은 격리 환경에서 수행한다.

**확인할 정상 동작:** 허용 profiler 시작·종료로 수집 파일이 정상 마무리된다. / 정상 준비·완료 기록이 실제 실행 상태와 일치한다.

**점검·판정 기준:** [6.4.3 CHK-LIF-014](04_환경별_적용과_체크리스트.md#CHK-LIF-014) · [8.3.1 CHK-OBS-002](04_환경별_적용과_체크리스트.md#CHK-OBS-002)

**분류 이유:** profiler가 실제로 멈췄는지와 자원이 회수됐는지가 핵심이라 작업 종결에 포함했다. 종료 상태 오판은 관련 원리로 남겼다.

**함께 확인할 원리:** [감사기록 오염·실행 상태 오판](#attack-type-17) — 시나리오의 성립 조건에서 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다.

**기존 구현·남은 확인:** 로그 formatter·RequestLogger·metrics·health·선택 profiler 경로가 있다. 필수 사건·저장·수집 장애·원본과 실행 대응·실제 backend 종료는 독립 증거가 필요하다.

### 3.6.14 민감정보 공개·사본 잔존

**개념:** 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다.

**방어 초점:** 공개 필드·독자·보존·삭제·저장 보호

**이렇게 묶은 이유:** 원본과 파생 사본의 비허용 열람을 통합했다. 사본 생성·읽기 권한·보존 위치와 실제 삭제 증거는 각각 유지한다.

**다른 원리와 함께 나타나는 상황:** [SC-19-03 폐기한 자격 사본으로 금지 접근 재개](#guide-SC-19-03) — 시나리오의 성립 조건에서 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다.

**다른 원리와 함께 나타나는 상황:** [SC-22-01 설정 조작으로 금지한 사용통계 보고 재개](#guide-SC-22-01) — 시나리오의 성립 조건에서 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다.

**다른 원리와 함께 나타나는 상황:** [SC-22-02 허용하지 않은 사용통계 항목·목적지 전송](#guide-SC-22-02) — 시나리오의 성립 조건에서 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다.

**예시:** 예외 기록에 전체 입력이 저장된다. 로그 담당자가 원래 대화의 읽기 권한을 갖고 있지 않아도 기록 사본에서 비공개 문맥을 볼 수 있다.

<a id="guide-SC-20-03"></a>
#### 3.6.14.1 삭제에서 빠진 사본을 통한 자료 열람 · SC-20-03

**주체·처음 가진 권한:** 보존 기한이 지난 사본에 접근할 수 있는 주체

**성립 조건:** 별도 사본과 보존 기한 뒤 읽을 수 있는 주체가 있을 때.

**공격·실패 상황**

원본을 지웠지만 로그·cache·백업에는 자료가 남아 있다.

**발생 과정:** 원본 삭제 → 로그·cache·backup 잔존 → 기간·권한 밖 조회

**방어 위치:** 자료 목록·저장소별 보존·삭제·읽기 권한

**예방·대응:** 원본·로그·캐시·백업·진단 사본별 소유자·보존 기간·삭제 방식을 정하고 실제 접근·삭제 결과를 확인한다.

**대책의 적용 범위·남은 조건:** GPU block 반환과 물리 소거 요구를 구분한다. 실제 금지 접근·보존 정책을 기준으로 판정한다.

**확인할 정상 동작:** 허용 보존 기간 동안 승인 위치의 시험 자료를 읽을 수 있다.

**점검·판정 기준:** [5.7.1 CHK-OBS-012](04_환경별_적용과_체크리스트.md#CHK-OBS-012)

**분류 이유:** 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다. 이 SC에서는 로그·cache·backup 잔존 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 일반 재배포·shutdown과 지원 조건이 제한된 snapshot 복원 경로를 구분했다. snapshot 호환 검사·oracle의 범위와 현재 조직 승인·자격 철회·외부 사본 검증은 따로 확인한다.

#### 3.6.14.2 반환 옵션·오류를 이용한 입력·내부 정보 노출 · SC-21-01

**주체·처음 가진 권한:** 반환 옵션이나 오류를 일으키는 입력을 조절할 수 있는 호출자

**성립 조건:** 해당 chat·stream API가 반환 옵션이나 오류 응답을 제공할 때.

**공격·실패 상황**

호출자가 return_prompt_text·return_token_ids 등의 옵션이나 오류 입력을 사용한다.

**발생 과정:** 반환 옵션·오류 입력 제출 → 입력 사본·진단 필드 생성 → 비허용 수신자에게 반환

**방어 위치:** Gateway·API 응답 필드 정책·오류 생성 위치

**예방·대응:** 허용된 옵션·반환 필드만 전달하고 비공개 입력 사본·내부 경로·주소를 정제한다. 실제 옵션을 끄는 엔진 설정의 유무와 Gateway 집행을 확인한다.

**대책의 적용 범위·남은 조건:** 해당 반환 옵션은 Gateway에서 제한해야 하는 경로가 있다. 직통 접근·다른 router·stream 오류도 같은 정책으로 시험한다.

**확인할 정상 동작:** 일반 응답과 안전한 오류가 허용된 필드만 반환한다. / 허용 로그 수준에서 고유 무해 표식 요청이 승인한 필드만 남긴다.

**점검·판정 기준:** [5.1.1 CHK-REQ-013](04_환경별_적용과_체크리스트.md#CHK-REQ-013) · [5.2.1 CHK-OBS-003](04_환경별_적용과_체크리스트.md#CHK-OBS-003)

**공개 사례·패치에서 확인할 점:** [GHSA-hgg8-fqqc-vfmw](https://github.com/vllm-project/vllm/security/advisories/GHSA-hgg8-fqqc-vfmw) — 특정 router의 오류 정제 누락 사례다. 같은 정제 정책이 실제 반환 위치마다 적용되는지 확인한다.

**공개 사례·패치에서 확인할 점:** [GHSA-hwrm-c4cx-rf4j](https://github.com/vllm-project/vllm/security/advisories/GHSA-hwrm-c4cx-rf4j) — 오류 응답의 내부 경로·사용자명 노출 사례다. 실제 오류·응답 필드와 수신자의 허용 정보 범위를 대조한다.

**분류 이유:** 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다. 이 SC에서는 입력 사본·진단 필드 생성 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** chat 응답의 prompt 문자열·token ID 반환과 오류·기본 예외 기록 경로가 있다. 반환 필드 제한·로그 독자·암호화·replay 권한은 실제 Gateway·저장소·도구에서 확인한다.

#### 3.6.14.3 로그 읽기 권한으로 비공개 입력 사본 열람 · SC-21-02

**주체·처음 가진 권한:** 원자료 접근 권한은 없지만 로그를 읽을 수 있는 주체

**성립 조건:** 엔진 예외 기록이나 활성화한 debug·진단 사본이 저장될 때.

**공격·실패 상황**

입력을 읽을 권한이 없는 사람이 로그 열람 권한으로 그 사본을 본다. 실제 필드를 합성 표식과 대조해 어떤 자료가 남는지 확인하고 저장·조회·복호화 권한을 평가한다.

**발생 과정:** 예외·debug에 원자료 기록 → 로그 열람자 접근 → 원자료 권한 초과

**방어 위치:** 로그 필드 선택·저장소 권한·암호화·키 관리

**예방·대응:** 필요한 필드만 기록하고 사본 조회·반출·복호화 권한을 자료 등급에 맞춘다. 기본 예외 dump와 선택 debug를 조사한다.

**대책의 적용 범위·남은 조건:** 어떤 자료가 실제 남는지는 합성 표식으로 확인한다. 저장 암호화는 키를 가진 독자의 접근 정책을 대신하지 않는다.

**확인할 정상 동작:** 허용 로그 수준에서 고유 무해 표식 요청이 승인한 필드만 남긴다. / 허용된 독자는 필요한 로그·진단 사본을 읽고, 저장 암호화가 필요한 자료는 승인된 저장·키 관리 설정으로 정상 기록·조회한다.

**점검·판정 기준:** [5.2.1 CHK-OBS-003](04_환경별_적용과_체크리스트.md#CHK-OBS-003) · [5.4.1 CHK-OBS-006](04_환경별_적용과_체크리스트.md#CHK-OBS-006)

**분류 이유:** 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다. 이 SC에서는 로그 열람자 접근 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** chat 응답의 prompt 문자열·token ID 반환과 오류·기본 예외 기록 경로가 있다. 반환 필드 제한·로그 독자·암호화·replay 권한은 실제 Gateway·저장소·도구에서 확인한다.

#### 3.6.14.4 보존 기한 뒤 남은 사용통계 사본 노출 · SC-22-03

**주체·처음 가진 권한:** usage 파일·수신 저장소의 자료를 읽을 수 있는 주체

**성립 조건:** 통계 파일과 수신·저장 위치에 보존 정책이 있을 때.

**공격·실패 상황**

운영자가 보고를 멈추거나 파일을 삭제했지만 다른 저장 위치에 사본이 남는다.

**발생 과정:** 보고·파일 생성 → 일부 위치만 삭제 → 잔존 사본 조회

**방어 위치:** 로컬 usage 파일·수신 저장소·백업 보존 정책

**예방·대응:** 통계 파일과 수신·저장·백업 사본의 독자·기간·삭제를 관리하고 실제 접근 결과를 확인한다.

**대책의 적용 범위·남은 조건:** 새 보고 중단과 기존 사본 삭제는 따로 확인한다.

**확인할 정상 동작:** 허용된 독자는 필요한 로그·진단 사본을 읽고, 저장 암호화가 필요한 자료는 승인된 저장·키 관리 설정으로 정상 기록·조회한다. / 허용 보존 기간 동안 승인 위치의 시험 자료를 읽을 수 있다.

**점검·판정 기준:** [5.4.1 CHK-OBS-006](04_환경별_적용과_체크리스트.md#CHK-OBS-006) · [5.7.1 CHK-OBS-012](04_환경별_적용과_체크리스트.md#CHK-OBS-012)

**분류 이유:** 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다. 이 SC에서는 일부 위치만 삭제 지점과 기존 정상 대조를 확인한다.

<a id="attack-type-15"></a>
### 3.6.15 수집·외부 송신 정책 위반

**개념:** 사용통계를 금지했거나 허용 항목·목적지를 제한했는데 생성·전송 정책을 벗어난다.

**방어 초점:** 유효 수집 설정과 payload·목적지·egress 제한

**이렇게 묶은 이유:** 허용된 전송을 공격자가 엿보는 경우와 구분했다. 생성 금지, 전송 금지, 제한적 허용의 정책값을 나눠 확인한다.

**예시:** 기업이 사용통계의 일부 항목과 목적지만 허용했다. 업데이트 뒤 보고 필드나 목적지가 바뀌었는데 승인 기준을 재적용하지 않으면 허용 밖 정보가 송신될 수 있다.

<a id="guide-SC-22-01"></a>
#### 3.6.15.1 설정 조작으로 금지한 사용통계 보고 재개 · SC-22-01

**주체·처음 가진 권한:** 실행 설정을 바꿀 수 있지만 외부 보고 승인 권한은 없는 주체

**성립 조건:** 내장 usage 보고 경로와 실제 rank0 환경·설정을 사용할 때.

**공격·실패 상황**

보고를 승인할 권한이 없는 설정 변경자가 opt-out에 영향을 준다.

**발생 과정:** 환경·설정 변경 → rank0 opt-out 판단 변경 → 초기·주기 보고 생성·송신

**방어 위치:** 기동 환경·usage 최초 판단·파일 생성·송신 정책

**예방·대응:** 보고 담당 프로세스의 유효 opt-out을 고정·검증하고 금지 시 새 보고 생성과 송신을 각각 차단·관측한다.

**대책의 적용 범위·남은 조건:** VLLM_DO_NOT_TRACK가 DO_NOT_TRACK보다 우선하며 정확히 1인 값을 확인한다. 송신 차단만으로 로컬 통계 생성 금지를 충족했다고 판단하지 않는다.

**확인할 정상 동작:** 필요한 저장소·관측 목적지에 승인된 연결만 발생한다. / usage 비사용 설정의 새 프로세스에서 정상 추론은 유지된다.

**점검·판정 기준:** [1.6.1 CHK-PLT-007](04_환경별_적용과_체크리스트.md#CHK-PLT-007) · [5.3.1 CHK-OBS-004](04_환경별_적용과_체크리스트.md#CHK-OBS-004)

**분류 이유:** 사용통계를 금지했거나 허용 항목·목적지를 제한했는데 생성·전송 정책을 벗어난다. 이 SC에서는 rank0 opt-out 판단 변경 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [민감정보 공개·사본 잔존](#attack-type-14) — 시나리오의 성립 조건에서 응답·오류·로그·사용통계·백업 사본에서 허용하지 않은 독자가 자료를 읽는다.

**기존 구현·남은 확인:** usage의 opt-out과 최초 활성 판단 cache를 확인했다. VLLM_DO_NOT_TRACK 값이 우선하며 정확히 1인지 비교하고, 로컬 파일과 초기·주기 송신을 별도로 확인해야 한다.

#### 3.6.15.2 허용하지 않은 사용통계 항목·목적지 전송 · SC-22-02

**주체·처음 가진 권한:** 보고 설정·입력에 영향을 줄 수 있는 주체

**성립 조건:** 일부 usage 보고를 허용하는 정책을 사용할 때.

**공격·실패 상황**

**예방·대응:** 허용 필드·목적지를 정책으로 정하고 실제 payload·주소·proxy를 대조한다. 허용 범위 밖 전송을 제한한다.

**대책의 적용 범위·남은 조건:** 도메인 허용만으로 payload 필드 제한이 충족되지는 않는다.

**확인할 정상 동작:** 필요한 저장소·관측 목적지에 승인된 연결만 발생한다. / usage를 별도 승인한 환경에서 허용 필드만 지정 목적지로 보낸다.

**점검·판정 기준:** [1.6.1 CHK-PLT-007](04_환경별_적용과_체크리스트.md#CHK-PLT-007) · [5.3.2 CHK-OBS-005](04_환경별_적용과_체크리스트.md#CHK-OBS-005)

<a id="attack-type-16"></a>
### 3.6.16 전송 자료 도청·변조

**개념:** 엔진 내부 또는 관측 전송 구간에서 제3자가 자료를 읽거나 바꾼다.

**방어 초점:** 구간별 상대 검증·기밀성·무결성 보호

**이렇게 묶은 이유:** GPU 통신과 관측 전송에 공통 원리를 적용했다. 실제 protocol·peer·hop·SDK와 보호 기능은 각각 확인한다.

**예시:** 엔진에서 수집기로 보내는 기록 구간이 평문으로 열려 있다. 해당 전송 구간에 접근한 주체는 비공개 기록을 읽거나 내용을 바꿀 수 있다.

<a id="guide-SC-08-03"></a>
#### 3.6.16.1 GPU 프로세스 통신의 도청·변조 · SC-08-03

**주체·처음 가진 권한:** 특정 내부 전송 구간을 관찰하거나 바꿀 수 있는 주체

**성립 조건:** 선택한 local collective나 다중 노드 transport 구간에 접근할 수 있을 때.

**공격·실패 상황**

해당 구간을 관찰하거나 수정할 수 있는 주체가 tensor·제어 자료를 읽거나 바꾸려 한다.

**발생 과정:** 전송 구간 접근 → tensor·제어 메시지 관찰·수정 → 기밀성·무결성 훼손

**방어 위치:** 선택 transport·신뢰 peer 목록·호스트·망 접근 제어

**예방·대응:** 허용 peer만 접속시키고 구간 정책에 맞는 상대 확인·기밀성·무결성 보호를 적용한다. 해당 transport가 제공하는 보호와 외부 계층의 통제를 구분한다.

**대책의 적용 범위·남은 조건:** 같은 노드 IPC와 다중 노드 네트워크에 같은 보호 방식을 일괄 적용하지 않는다. 실제 읽기·변조 권한과 배치를 확인한다.

**확인할 정상 동작:** TP 처리에서 각 rank의 담당 계산·중간 상태와 선정 출력 rank·집계 경로의 최종 반환을 요청·모델·buffer에 연결한다. / 정상 TP graph 등록·실행·종료 후 새 기동이 성공한다. / 허용한 호출 주체가 각 API 구간에서 정상 요청·스트리밍 응답을 주고받고, 승인한 rank 사이 TP 처리도 정상 완료된다.

**점검·판정 기준:** [4.1.3 CHK-REQ-014](04_환경별_적용과_체크리스트.md#CHK-REQ-014) · [4.4.3 CHK-REQ-021](04_환경별_적용과_체크리스트.md#CHK-REQ-021) · [5.5.1 CHK-PLT-008](04_환경별_적용과_체크리스트.md#CHK-PLT-008)

**분류 이유:** 엔진 내부 또는 관측 전송 구간에서 제3자가 자료를 읽거나 바꾼다. 이 SC에서는 tensor·제어 메시지 관찰·수정 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** API↔Core와 Core↔worker는 서로 다른 메시지 경로를 사용한다. worker queue의 pickle 복원과 같은 UID 등 공유 신뢰 전제가 있어 실제 socket·SHM·namespace 접근권이 중요하다.

<a id="guide-SC-24-01"></a>
#### 3.6.16.2 엔진→수집기 구간에서 기록 도청·변조 · SC-24-01

**주체·처음 가진 권한:** 엔진과 수집기 사이 전송을 관찰하거나 바꿀 수 있는 주체

**성립 조건:** OTLP 등 선택한 전송 구간을 관찰·변조할 수 있을 때.

**공격·실패 상황**

해당 구간의 주체가 기록을 읽거나 바꾸려 한다.

**발생 과정:** 해당 hop 접근 → 기록 관찰·수정 → 기밀성·증거 무결성 훼손

**방어 위치:** 엔진 exporter·전송 SDK·proxy·수집기 인증

**예방·대응:** 실제 protocol·endpoint·인증서·proxy에 구간 정책을 적용하고 상대 확인·TLS handshake·송신을 검증한다.

**대책의 적용 범위·남은 조건:** https 문자열만으로 SDK의 실제 TLS 동작과 상대 검증을 확인할 수 없다.

**확인할 정상 동작:** 필요한 저장소·관측 목적지에 승인된 연결만 발생한다. / 엔진→collector→sink의 승인 기록이 지정 종단으로 전달된다.

**점검·판정 기준:** [1.6.1 CHK-PLT-007](04_환경별_적용과_체크리스트.md#CHK-PLT-007) · [5.5.2 CHK-PLT-009](04_환경별_적용과_체크리스트.md#CHK-PLT-009)

**분류 이유:** 엔진 내부 또는 관측 전송 구간에서 제3자가 자료를 읽거나 바꾼다. 이 SC에서는 기록 관찰·수정 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 엔진 exporter와 외부 수집·저장 구간의 보호 요구를 분리했다. 설치 SDK·protocol·인증서·proxy에 따른 실제 상대 검증·전송 보호는 환경과 시험으로 확인해야 한다.

<a id="guide-SC-24-02"></a>
#### 3.6.16.3 수집기→저장소 구간에서 기록 도청·변조 · SC-24-02

**주체·처음 가진 권한:** 수집기와 저장소 사이 전송을 관찰하거나 바꿀 수 있는 주체

**성립 조건:** 외부 수집기에서 저장소로 보내는 다음 구간이 있을 때.

**공격·실패 상황**

엔진 송신 뒤에도 기록은 수집기에서 저장소로 이동한다. 이 구간의 보호가 부족하면 자료가 노출되거나 변조될 수 있다. 다음 구간의 상대·인증·전송 증거를 따로 확보한다.

**발생 과정:** 다음 hop 접근 → 전송 기록 관찰·수정 → 저장 자료 노출·변조

**방어 위치:** 수집기 exporter·저장소 수신·구간 접근 제어

**예방·대응:** 수집기 이후의 각 저장 구간에도 상대 인증·기밀성·무결성 요구를 적용하고 실제 송수신과 실패 표시를 확인한다.

**대책의 적용 범위·남은 조건:** 엔진→수집기 구간의 보호를 후속 구간의 증거로 재사용하지 않는다.

**확인할 정상 동작:** 엔진→collector→sink의 승인 기록이 지정 종단으로 전달된다.

**점검·판정 기준:** [5.5.2 CHK-PLT-009](04_환경별_적용과_체크리스트.md#CHK-PLT-009)

**분류 이유:** 엔진 내부 또는 관측 전송 구간에서 제3자가 자료를 읽거나 바꾼다. 이 SC에서는 전송 기록 관찰·수정 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 엔진 exporter와 외부 수집·저장 구간의 보호 요구를 분리했다. 설치 SDK·protocol·인증서·proxy에 따른 실제 상대 검증·전송 보호는 환경과 시험으로 확인해야 한다.

<a id="attack-type-17"></a>
### 3.6.17 감사기록 오염·실행 상태 오판

**개념:** 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다.

**방어 초점:** 신뢰 필드·감사 무결성·독립 증거·수집 장애 표시

**이렇게 묶은 이유:** 공격자의 기록 오염과 비악의적 수집·대응 오류를 같은 검증 원리로 모으되 상황 종류를 따로 표시한다. profiler 실제 종결은 자원 수명에서 다룬다.

**다른 원리와 함께 나타나는 상황:** [SC-23-05 profiler 정지 응답을 수집 종료로 오판](#guide-SC-23-05) — 시나리오의 성립 조건에서 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다.

**예시:** 입력 오류 뒤 추론이 실패하는데 health API는 계속 정상 응답을 보낸다. 운영 도구가 이 응답만 근거로 정상 처리하면 실제 서비스 장애를 놓칠 수 있다.

<a id="guide-SC-23-01"></a>
#### 3.6.17.1 요청 필드를 이용한 로그 신원·결과 오인 · SC-23-01

**주체·처음 가진 권한:** 자기 요청에서 기록되는 문자열·ID를 조절할 수 있는 호출자

**성립 조건:** 요청 필드가 로그의 주체·대상·상태 표현에 사용될 때.

**공격·실패 상황**

호출자가 기록되는 요청 ID나 문자열을 바꾼다.

**발생 과정:** 기록 입력 조작 → 신뢰 필드·표현에 반영 → 검토자의 사건 해석 오류

**방어 위치:** 로그 formatter·구조화 필드·조회 화면

**예방·대응:** 신뢰할 주체·대상·결과는 서버에서 생성하고 사용자 입력은 별도 필드로 인코딩한다. 로그·조회 결과를 독립 사건 증거와 대조한다.

**대책의 적용 범위·남은 조건:** HTTP 입력 수용·formatter 처리·최종 화면의 위조 효과를 각각 확인한다.

**확인할 정상 동작:** 정상 ID와 복수행 콘텐츠가 하나의 올바른 사건으로 기록된다.

**점검·판정 기준:** [8.2.1 CHK-OBS-009](04_환경별_적용과_체크리스트.md#CHK-OBS-009)

**분류 이유:** 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다. 이 SC에서는 신뢰 필드·표현에 반영 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 로그 formatter·RequestLogger·metrics·health·선택 profiler 경로가 있다. 필수 사건·저장·수집 장애·원본과 실행 대응·실제 backend 종료는 독립 증거가 필요하다.

<a id="guide-SC-23-02"></a>
#### 3.6.17.2 수집 장애를 숨긴 채 시험 통과 보고 · SC-23-02

**구분:** 실패·오설정

**실패 계기:** 수집기·권한·저장소의 장애

**성립 조건:** 필수로 기록해야 할 사건이 발생할 때.

**공격·실패 상황**

수집기·권한·저장소 문제로 필요한 증거가 사라진다. 관측 요구의 누락 결과와 그 증거에 의존한 다른 시험의 미확인을 구분한다.

**발생 과정:** 필수 사건 발생 → 수집 실패 → 증거 없는 성공 판정

**방어 위치:** 수집기 상태·타임아웃·평가 결과 집계

**예방·대응:** 수집 상태·마지막 확인 시각·누락을 표시하고 필수 증거 없는 통과를 막는다. 관측 요구의 미충족과 종속 시험의 미확인을 분리한다.

**대책의 적용 범위·남은 조건:** 경보가 없는 상태와 정상 수집 상태를 구분한다. 장애 표시와 실제 저장 결과를 확인한다.

**확인할 정상 동작:** 정상 접근·관리·승인 기록이 정한 수집 기한 안에 확보되고 시험 ID로 같은 사건을 대조할 수 있다. / 필수 시험 사건이 정한 수집 기한 안에 도착한다.

**점검·판정 기준:** [8.1.1 CHK-OBS-001](04_환경별_적용과_체크리스트.md#CHK-OBS-001) · [8.3.2 CHK-OBS-011](04_환경별_적용과_체크리스트.md#CHK-OBS-011)

**분류 이유:** 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다. 이 SC에서는 수집 실패 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 로그 formatter·RequestLogger·metrics·health·선택 profiler 경로가 있다. 필수 사건·저장·수집 장애·원본과 실행 대응·실제 backend 종료는 독립 증거가 필요하다.

<a id="guide-SC-23-03"></a>
#### 3.6.17.3 대상 식별 오류로 비승인 사용을 정상 판단 · SC-23-03

**구분:** 실패·오설정

**실패 계기:** 승인·소비 기록의 생성·수집·대조 누락

**성립 조건:** 승인·검사 기록과 실제 소비 기록을 대조할 때.

**공격·실패 상황**

서로 다른 파일·실행의 기록이 이름이나 느슨한 식별자 때문에 같은 것으로 묶인다. 실제 사용 파일·worker·실행 시점을 추적하지 못하면 비승인 사용을 놓칠 수 있다.

**발생 과정:** 승인·소비 기록 수집 → 다른 파일·실행을 같은 것으로 대응 → 불일치 누락

**방어 위치:** 승인 식별·실제 열린 파일·worker·실행 이력 대조

**예방·대응:** 승인 묶음 ID·파일 digest·실제 경로·worker·실행 시각을 추적하고 불명확한 대응은 미확인으로 남긴다.

**대책의 적용 범위·남은 조건:** 표시 이름·시각만 비슷하다는 이유로 같은 파일·실행으로 판단하지 않는다.

**확인할 정상 동작:** 정상 접근·관리·승인 기록이 정한 수집 기한 안에 확보되고 시험 ID로 같은 사건을 대조할 수 있다. / 정상 준비·완료 기록이 실제 실행 상태와 일치한다.

**점검·판정 기준:** [8.1.1 CHK-OBS-001](04_환경별_적용과_체크리스트.md#CHK-OBS-001) · [8.3.1 CHK-OBS-002](04_환경별_적용과_체크리스트.md#CHK-OBS-002)

**분류 이유:** 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다. 이 SC에서는 다른 파일·실행을 같은 것으로 대응 지점과 기존 정상 대조를 확인한다.

**함께 확인할 원리:** [공급물 변조·누락과 승인 대상 불일치](#attack-type-08) — 시나리오의 성립 조건에서 승인한 이름·파일·내용·실행 구성과 실제로 사용하는 대상이 달라진다.

**기존 구현·남은 확인:** 로그 formatter·RequestLogger·metrics·health·선택 profiler 경로가 있다. 필수 사건·저장·수집 장애·원본과 실행 대응·실제 backend 종료는 독립 증거가 필요하다.

<a id="guide-SC-23-04"></a>
#### 3.6.17.4 health 정상 표시로 실제 추론 장애 은폐 · SC-23-04

**주체·처음 가진 권한:** 오류 입력을 제출할 수 있는 호출자; 공유 엔진 장애 유발 능력은 미확인

**성립 조건:** 상태 API와 추론 경로가 서로 다른 상태를 측정할 때.

**공격·실패 상황**

상태 API는 정상 응답을 주지만 실제 모델 요청은 실패할 수 있다. 오류 요청의 공유 엔진 종료 영향은 시험이 남아 있다.

**발생 과정:** 입력 오류·실행 장애 → health는 생존 응답 → 서비스 정상 오판

**방어 위치:** readiness·실제 추론 canary·배포·운영 판단

**예방·대응:** 생존 신호와 모델 준비·정상 추론을 함께 확인하고 추론 실패를 별도 표시한다. 오류 뒤 정상 요청과 복구를 시험한다.

**대책의 적용 범위·남은 조건:** /health 200만으로 추론 가능을 판정하지 않는다. 새 V2 예외의 엔진 종료 가능성은 미확인으로 유지한다.

**확인할 정상 동작:** 정상 준비·완료 기록이 실제 실행 상태와 일치한다.

**점검·판정 기준:** [8.3.1 CHK-OBS-002](04_환경별_적용과_체크리스트.md#CHK-OBS-002)

**공개 사례·패치에서 확인할 점:** [GHSA-4xqp-c3mv-qff7](https://github.com/vllm-project/vllm/security/advisories/GHSA-4xqp-c3mv-qff7) — 과도한 min_tokens의 오류 뒤 health가 정상으로 남는 사례다. 입력 검증과 요청별 오류 처리, 실제 후속 추론을 함께 시험한다. 새 V2 옵션 예외의 종료 영향과는 별도 근거다.

**분류 이유:** health를 실제 추론 정상의 증거로 해석하는 판단 오류가 이 SC의 초점이다. 장애를 유발하는 입력 경로는 관련 분기로 남겼다.

**함께 확인할 원리:** [입력 오류의 서비스 장애 전파](#attack-type-03) — 입력 오류가 실행 장애를 유발한 기존 공개 사례와 같은 경로일 때. 현재 실행기의 장애 확대는 시험 대기다.

**기존 구현·남은 확인:** 로그 formatter·RequestLogger·metrics·health·선택 profiler 경로가 있다. 필수 사건·저장·수집 장애·원본과 실행 대응·실제 backend 종료는 독립 증거가 필요하다.

#### 3.6.17.5 기록 삭제·변조로 사고 흔적 은폐 · SC-23-06

**주체·처음 가진 권한:** 기록 저장소에 쓰기·삭제 권한을 가진 주체

**성립 조건:** 검토자와 별개로 기록 저장소 쓰기·삭제 권한을 가진 주체가 있을 때.

**공격·실패 상황**

기록 권한자가 필수 사건을 지우거나 바꾼다.

**발생 과정:** 저장소 쓰기·삭제권 사용 → 필수 기록 변경 → 실행 결과 오인

**방어 위치:** 기록 저장소 ACL·별도 감사·보존·무결성 관리

**예방·대응:** 기록·감사 관리 권한을 분리하고 채택한 변경·삭제의 필수 예방·탐지 요구를 각각 집행한다. 팀 참조의 비허용 삭제 거부를 유지하고 독립 감사·탐지 시각·보존 결과를 확인한다.

**대책의 적용 범위·남은 조건:** 기업의 저장소와 정책에 맞춰 보호 수단을 정하되, 필수 예방·탐지 결과를 각각 확인한다. 예방 필수 범위의 변경·삭제 성공과 탐지 성공은 각각 기록한다.

**확인할 정상 동작:** 정상 writer가 기록을 추가하고 검토자는 읽기만 한다.

**점검·판정 기준:** [8.2.2 CHK-OBS-010](04_환경별_적용과_체크리스트.md#CHK-OBS-010)

**분류 이유:** 기록이 누락·변조되거나 실제 사건과 다르게 해석돼 위반·장애를 정상으로 판단한다. 이 SC에서는 필수 기록 변경 지점과 기존 정상 대조를 확인한다.

**기존 구현·남은 확인:** 로그 formatter·RequestLogger·metrics·health·선택 profiler 경로가 있다. 필수 사건·저장·수집 장애·원본과 실행 대응·실제 backend 종료는 독립 증거가 필요하다.

### 공유 실행 권한과 침해 범위

SC-08-02는 하나의 worker가 이미 침해된 뒤 같은 OS 계정·내부 실행 권한을 공유하는 그룹의 영향 범위를 설명한다. 배포 분리·최소 권한을 판단할 때 함께 확인한다.

<a id="guide-SC-08-02"></a>
#### 공유 권한을 가진 worker 침해의 영향 확대 · SC-08-02

**구분:** 공유 신뢰·침해 범위

**주체·처음 가진 권한:** 허가된 worker 하나의 실행·송신 권한을 확보한 주체

**성립 조건:** 같은 UID와 pickle·callable RPC를 공유하는 실행 그룹일 때.

**공격·실패 상황**

worker 하나가 침해되면 공유한 계정·내부 제어 권한이 엔진의 다른 프로세스에도 영향을 줄 수 있다. 이 시나리오에서는 실제 공유 권한과 피해 범위를 확인하고 외부 접근 제한·최소 권한을 평가한다.

**발생 과정:** worker 하나 침해 → 같은 UID·내부 callable 제어 사용 → 실행 그룹 권한에 영향

**방어 위치:** 실행 그룹의 OS 권한·외부 접점·배포 격리

**예방·대응:** 공유 신뢰 그룹 전체를 침해 영향 범위에 포함하고 최소 권한·외부 접근 제한·필요한 배포 분리를 적용한다.

**대책의 적용 범위·남은 조건:** 같은 권한 그룹 내부를 별도 인가 경계로 가정한 역할 일탈 시험은 피한다. 추가 격리가 필요하면 별도 경계를 설계·검증한다.

**확인할 정상 동작:** TP 처리에서 각 rank의 담당 계산·중간 상태와 선정 출력 rank·집계 경로의 최종 반환을 요청·모델·buffer에 연결한다. / 같은 신뢰 범위의 core·worker가 요구된 IPC를 정상 사용한다.

**점검·판정 기준:** [4.1.3 CHK-REQ-014](04_환경별_적용과_체크리스트.md#CHK-REQ-014) · [1.4.3 CHK-PLT-006](04_환경별_적용과_체크리스트.md#CHK-PLT-006)

### 시나리오·점검·근거를 읽는 순서

## 3.8 근거를 해석할 때 알아둘 점

loader는 모델 자료를 골라 적재하는 구성요소, reader는 파일을 해석하는 구성요소다. runner는 선택한 실행 모드에서 모델 실행과 상태 갱신을 맡는다. rank는 병렬 실행에 참여하는 구성원이다. 출력 수집기(collector)는 요청의 생성 결과를 모으고, 관측 수집기는 로그·추적·지표를 모은다. 두 수집기는 모으는 자료와 종료 조건을 각각 확인한다.


| 표시 | 의미 |
| --- | --- |

| 환경 확인 필요 | 활성 기능·API 경로·권한·실제 공급원·runner 등을 확인해야 함 |

| 실제 시험 필요 | 도달·허용/거부·정리·성능 등을 실행 증거로 확인해야 함 |

| Model Theft | 가중치·저장소·daemon의 비허용 접근과 사본·전송 노출을 평가한다. | 반복 API 질의로 모델을 복제하는 전용 추출 시험은 현재 포함하지 않았다. |

**대조 후 보완한 점:** 원리별 예시를 사용자·운영자·공격자의 구체 행동과 결과로 다시 썼다. 주 분류는 SC의 직접 시험 초점과 방어 위치를 기준으로 정하고, 같은 SC의 다른 원리는 성립 조건으로 표시했다.

**남은 범위·검증:** R10의 URL·파일·일괄 입력 관련 상세 검토와 R14의 관리형 서비스·대체 실행 검토는 기존 대기 범위를 유지한다. 17개 분류의 구성 검토와 실제 엔진·GPU 시험을 구분한다.

참고 과정에서 인쇄 151쪽 Model Denial of Service의 예시 상자에 학습 데이터 오염 설명이 함께 있는 점도 확인했다. 우리 분류는 해당 SC에서 실제로 확인하는 원리와 경로를 기준으로 판단했다.

**원래 보호 대책:** 필수 rank의 준비 상태·실제 모델·정상 요청을 확인하고 Gateway·LB의 요청 수용과 연동한다. 실행 중 변경이나 replica 순차 교체를 사용하면 진행 요청과 weights·KV·정책 세대의 일관성도 확인한다.

**기존 구현:** mp backend의 rank별 준비·초기화 실패·종료 경로를 확인했다. Gateway·배포 도구의 현재 승인 대조와 서비스 재개 게이트는 조직의 실제 구현이 필요하다.

**정책 결정·실제 시험:** Gateway·LB의 재개 조건과 필수 rank 준비 증거를 정해야 한다. live·rolling은 실제 지원·사용 구성에서 추가 확인한다.

</details>
