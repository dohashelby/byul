# A17 범용 코어·확장 지점 v2.0

> v2.0 기준선 · 2026-10-02 · A14 D37~D39. 문서 검토 반영본이며 팀 소유자 승인·코드 시험·실측 완료를 뜻하지 않는다.

- **이 문서가 정하는 것:** vLLM 대상 위협평가·격리시험 솔루션을 특정 CVE에 묶지 않는 구조. 콘텐츠 팩, 확장 지점 7개의 인터페이스, 판정 플러그인, 지원 버전 설정, 하드코딩 금지 목록, 기능 켜기·끄기 설정
- **다른 문서에서 가져오는 것:** 단계·교환 객체·enum·불변식(A1 v2.0), 모듈 경계(A3 v2.0), 범위(A0 v2.0), 시험 정의 계약(A7), 확장 기능 상세(A18·A23)

**소유:** T1(초안, 소유 확정 필요) · **상태:** v2.0 문서 기준선(2026-10-02; 구현·실측 완료 아님) · **기준:** A1 v2.0

## 1. 원칙

1. **엔진은 vLLM 하나이며, 등록 실행기·관측·전제 평가기로 표현 가능하고 smoke 자격이 확인된 버전 쌍과 권고를 지원한다.** 1차 시연(CVE-2026-22807, 0.13.0→0.14.0)은 첫 번째 콘텐츠 팩일 뿐이며 코드 경로가 아니다.
2. **CVE·버전·시험에 따라 달라지는 것은 데이터(콘텐츠 팩·설정)로 둔다.** 코드는 파이프라인·계약·판정 플러그인·어댑터만 가진다.
3. **확장 지점마다 인터페이스를 먼저 고정하고 구현체를 등록한다.** 같은 확장 지점의 구현체끼리는 출력 계약(A1 교환 객체 또는 이 문서의 내부 계약)이 같다. 구현체를 바꿔도 판정 규칙은 바뀌지 않는다.
4. **판단은 규칙 기반 코드와 사람이 한다.** 보조 에이전트(A23)는 꺼져 있어도 모든 기능이 동작하고, 켜져 있어도 판정·선정·승인을 바꾸지 않는다(A1 불변식 16).
5. **선택 기능을 꺼도 필수 흐름은 깨지지 않는다.** 꺼진 기능이 담당하던 근거는 보고서에 미검증 범위로 나온다. 꺼졌다는 이유로 PASS·APPLICABLE을 만들지 않는다.

## 2. 콘텐츠 팩

### 2.1 구조

콘텐츠 팩은 한 보안 권고(또는 권고 묶음) 평가에 필요한 데이터 묶음이다. 저장소의 `packs/<pack_id>/`에 둔다.

```
packs/<pack_id>/
├─ pack.yaml              # 매니페스트(아래 표)
├─ tests/                 # TEST 정의 YAML (A7 §2 계약). 기존 공통 TEST를 쓰면 생략
├─ analysis_rules/        # 변경 분석 규칙 (A4 §5a)
├─ fixtures/              # 시험 자료 명세·해시 (A15 §5). 바이너리·모델 원본은 넣지 않고 위치·해시만
├─ advisories/            # 권고 등록 입력 (A4 §4.3). 공식 원문 URL·해시
└─ README.md              # 사람이 읽는 설명. 계약 아님
```

| `pack.yaml` 필드 | 타입 | 필수 | 의미 |
| --- | --- | --- | --- |
| `pack_id` | string, `PACK-` 접두어 | 필수 | 예: `PACK-CVE-2026-22807` |
| `revision` | integer ≥1 | 필수 | 팩 내용 개정 |
| `engine` | `"vllm"` | 필수 | 1차는 vLLM만 |
| `advisory_ids` | string[] ≥1 | 필수 | CVE·GHSA 외부 식별자 |
| `version_pairs` | `{baseline:string, candidate:string}[]` ≥1 | 필수 | 이 팩이 다루는 버전 쌍. 지원 버전 설정(§5)에 있어야 실행 가능 |
| `tests` | Ref[] (TEST) | 필수 | 팩이 쓰는 TEST. 공통 TEST 참조 가능 |
| `analysis_rule_files` | string[] | 필수 | `[]` 허용 |
| `fixtures` | string[] | 필수 | `[]` 허용 |
| `files_sha256` | `{path:string, sha256:SHA}[]` | 필수 | pack.yaml을 제외한 모든 일반 파일의 정확한 bytes 해시. 경로 오름차순·중복 금지 |
| `review` | `{status: DRAFT\|REVIEWED, reviewer:string\|null, reviewed_at:RFC3339\|null}` | 필수 | REVIEWED만 공식 평가에 사용(A13 §11 카탈로그 검토) |

`PACK`은 A1 §2.1에 등록한다(A1 v2.0). 팩은 A1 교환 객체가 아니라 카탈로그 입력이다. 보고서 `identity`에 사용한 팩 ID·revision·manifest_sha256를 남긴다.

`manifest_sha256=SHA256(pack.yaml의 정확한 UTF-8 bytes)`이며 manifest 안에는 자기 해시를 넣지 않는다. manifest는 A13 안전 YAML 파서로 읽으며 중복 키를 거부한다. files_sha256의 path는 POSIX 상대 경로로, 절대 경로·역슬래시·빈 세그먼트·`.`·`..`·심볼릭 링크·정규화 후 중복을 거부한다. manifest 외 파일 목록과 실제 파일 집합이 정확히 같아야 한다. 목록 밖 README도 거부한다. 빈 디렉터리는 해시 대상이 아니다.

팩에는 `bindings: Binding[]`(§4.4), `profile_files:string[]`, `policy_data_files:string[]`를 필수로 등록한다(`[]` 허용). 공통 팩은 advisory_ids=[]·version_pairs=[]를 허용하며 `pack_id="PACK-COMMON"`, 폴더는 `_common`이다. 사례 팩은 각 배열 ≥1이며 공통 TEST를 exact Ref로 참조한다. 실제 내용 수정은 새 revision·DRAFT이며 이전 bytes·검토 상태를 보존한다. reviewer가 새 manifest 해시를 검토한 뒤 REVIEWED로 새 revision을 발행한다. 검토 메타데이터만 바뀌어도 manifest 해시가 달라지므로 REVIEWED revision의 최종 bytes를 다시 고정한다.

B1은 DRAFT 골격·합성 자료의 로더 인수까지만 완료한다. B2 분석 규칙·B3 센서/성능 데이터를 넣을 때마다 새 revision·해시·DRAFT 전환 및 참조 갱신을 거친다. B5는 최종 팩 잠금과 전체 회귀 인수, I8은 REVIEWED 팩 자격까지 확인한다. 자동 구현자가 실제 reviewer의 확인을 만들어 넣지 않는다.

### 2.2 로드 규칙

- `catalog/`가 기동 시 팩을 읽고 스키마·해시·참조(TEST·규칙 파일)를 검증한다. 하나라도 틀리면 그 팩 전체를 거부한다(A13 경계 F). 부분 로드하지 않는다.
- `review.status=DRAFT` 팩은 EXAMPLE 실행에만 쓴다. 공식 평가(MEASURED)는 REVIEWED 팩만 쓴다.
- 팩끼리 TEST ID·규칙 ID의 정의가 겹치면 충돌한 팩들과 그 의존 팩을 거부하고 목록을 반환한다. 독립된 정상 팩은 유지한다. 같은 공통 TEST를 참조하는 것은 중복 정의가 아니다. 공통 TEST는 `packs/_common/`에 둔다.
- 1차 팩: `_common`(TEST-MODEL-007·FUNC-003·NET-004·SYS-001·SYS-002·PERF-001 정의, 공통 판정 플러그인 연결), `PACK-CVE-2026-22807`(권고·분석 규칙·fixture 명세·버전 쌍).

### 2.3 게이트웨이 route profile 파일 (D43)

PACK-COMMON의 기존 profile_files에 `gateway_route_profiles.yaml`(팩 루트 상대 경로, 전체 위치 packs/_common/gateway_route_profiles.yaml)을 포함한다. P0에서 합성 형식을 만들고 P1f 로더가 검증한다. 파일은 `{format:"guard-route-profiles/1",profiles:RouteProfile[]≥1}`이며 RouteProfile=`{profile_id:string,method:string,path:string,body_profile:NONE 또는 INFERENCE_JSON,input_schema:object|null}`이다. 모든 키 필수·추가 키 금지. profile_id 및 정규화 method/path 중복 금지, wildcard route는 미지원이다. NONE은 schema=null, INFERENCE_JSON은 non-null이다.

input_schema는 type/properties/required/additionalProperties/items/enum/minimum/maximum/minLength/maxLength/minItems/maxItems만 지원한다. type은 object/array/string/integer/number/boolean/null, 각 키는 해당 타입에 맞게 검증한다. properties에는 이 제한 스키마를 재귀 사용한다. required는 정의된 property 목록·중복 금지, additionalProperties는 boolean이다. enum은 해당 scalar 타입 값, 경계는 일관된 유한 수/비음수 정수다. 외부 참조·코드·일반 정규식·미지원 키는 거부한다. 크기·깊이 상한은 A13 입력 경계를 적용한다. 기존 제한형 validator를 재사용하며 범용 정책 언어는 추가하지 않는다. 파일 실제 bytes·팩 revision·manifest SHA·profile_id를 잠그고 A6 §15.1 compiler에 전달한다. 역할·승인 모델은 POL에서만 온다.

## 4. 판정 플러그인 (X4)

### 4.1 연결

A7 §2 TEST 정의에 필드 `judge: {plugin: string, version: string, params: object}`를 추가한다(A7 v2.0). `verdict/judges/` 아래 플러그인을 등록 테이블로 찾는다. 정의에 적힌 플러그인·버전이 등록 테이블에 없으면 그 TEST는 실행 전 거부된다(선정은 됐다면 NOT_STARTED + UNKNOWN, 사유 `JUDGE_UNAVAILABLE`).

```python
# verdict/judges/base.py — 시그니처 고정
class JudgeOutput(BaseModel):
    verdict: Literal["PASS", "FAIL", "UNKNOWN"]
    reason: str
    used_observation_refs: list[Ref]
    used_evidence_refs: list[Ref]
    verification_level: Literal["ENGINE", "PARTIAL_PATH", "STATIC"] | None
    data_origin: Literal["MEASURED", "EXAMPLE"] | None

def judge(test_def: TestDefinition, run: RunManifest,
          observations: list[VerifiedObservation], params: Mapping[str, object],
          expected: Mapping[str, object]) -> JudgeOutput: ...
# params = TEST 정의 judge.params, expected = RUN.requirement_refs를 phase별 IA 배열로 해석한 동일 expected(A4 §11.6)
```

- 순수 함수다. 파일·네트워크·시각 조회 금지(A3 §3 verdict/).
- `VerifiedObservation`은 교환 객체가 아닌 검증기 전용 내부 타입이다: `{observation:OBS,evidence:EVD[],provenance:OBS.provenance,checks:{refs:true,hashes:true,run_attribution:true,window:true,subject_schema:true}}`. Ref·파일 SHA·size·RUN ID/상태 이력·대상 UID·구간·subject 타입·출처를 검증한 서비스만 생성한다. 외부 JSON을 이 타입으로 직접 받지 않는다. 무효 증거는 제외하고 서비스 진단 기록에 사유를 보존한다. judge는 TEST.required_evidence/required_subjects와 전달된 유효 observations를 대조해 누락을 판단한다(새 미정의 컨텍스트 인자 없음). COMPLETE가 내용 진위를 자동 보증하지 않는다.
- 플러그인 등록 항목은 `evaluate_fail(test_def,run,observations,params,expected)->ViolationEvidence[]`와 위 judge를 함께 제공한다. ViolationEvidence는 `{rule_id:string,observation_refs:Ref[],evidence_refs:Ref[],reason:string}`이며 귀속·무결성이 검증된 Ref만 담는다. 시험 의미를 아는 evaluate_fail이 유효 위반을 판별하고, 공통 래퍼가 이를 먼저 평가한다. 등록되지 않은 플러그인에는 추정 FAIL 탐지기를 만들지 않는다.
- 실제 시작한 RUN의 유효 위반이 있으면 중단·누락보다 FAIL 우선이다. started_at=null인 RUN에 실행 관측이 붙으면 무결성 오류로 배제하고 미실행 UNKNOWN·출처 null을 반환한다. PASS/FAIL에 근거가 없으면 출력 계약 오류다. 사용한 근거 중 EXAMPLE이 하나라도 있으면 EXAMPLE, 검증 수준은 최약값이며 미실행/미검증은 null이다. 플러그인과 래퍼가 충돌하면 래퍼의 보수적 결과·사유를 기록한다.

### 4.3 선언형 판정 `rule_table/1`

`params={required_subjects:string[]≥1,rules:Rule[]≥1}`이다. Rule은 `{priority:int≥0,verdict:PASS|FAIL|UNKNOWN,all:Cond[],any:Cond[]}`이며 priority 중복을 거부한다. Cond는 `{subject:string,path:string(JSON pointer),op:eq|ne|ge|le|is_true|is_false|is_null|not_null,value:scalar|null}`이다. 추가 키·등록 밖 subject·타입 불일치 비교는 정의 오류다. is_*·not_null은 value=null, 수치 비교는 유한 수치만 허용한다. 코드/eval·문자열 함수 실행은 금지한다.

- 마지막 하나는 기본 UNKNOWN(all=[]·any=[])이며 다른 규칙의 빈 조건을 거부한다. 기본값을 제외한 UNKNOWN 규칙도 조건이 있어야 한다.
- all만 있으면 모든 조건, any만 있으면 하나 이상, 둘 다 있으면 `(all 전부) AND (any 하나 이상)`이다. 빠진 값은 미확인이다. is_null은 존재하는 명시적 null만 검사하며 누락 경로는 미확인이다. all의 미확인이 any의 참 하나로 무시되지 않는다.
- **모든 FAIL 규칙을 먼저 평가**하고 성립한 규칙 중 최소 priority를 고른다. 그 뒤 나머지 규칙을 priority 순으로 평가한다. PASS는 required_subjects의 모든 유효·COMPLETE·non-null 관측과 등록된 완전성 검사를 요구한다. null 검사만으로 PASS를 만들 수 없다. 성립 규칙이 없거나 필수 관측 부족이면 UNKNOWN이다.
- A5에 등록된 subject/내부 테스트 adapter만 사용할 수 있다. 새로운 타입을 팩이 단독으로 선언해 임의 센서·코드를 로드할 수 없다.

### 4.4 팩의 실행 바인딩과 범용성 경계

내부 정책 데이터는 `PDAT={id:string,revision:int≥1,kind:PROCESS_ALLOWLIST|PROTECTED_PATHS|MARKER_CONTRACT,entries:object[]}`로 팩 안에 저장한다. PROCESS_ALLOWLIST entries는 `{phase:init|serve|maintenance,exe_path:string}`이고 PROTECTED_PATHS는 `{path:string}`이다. MARKER_CONTRACT는 기존 A15 표식 자료 계약의 필드만 사용하며 실행 코드가 아니다. 종류별 추가 키와 해석되지 않는 경로 표현은 거부한다. PROFILE Ref의 id는 A5 profile_id이고 PDAT Ref의 id는 이 id다. 어떤 자료도 같은 ID/revision으로 수정하지 않는다.

`Binding={test_ref:Ref,executor:{name:string,version:string},subjects:string[],materials:{role:string,path:string,sha256:SHA}[],preconditions:{field:string,op:"eq",value:scalar}[],case_ids:string[],marker_contract_ref:Ref|null}`. 모든 키 필수, 추가 키 거부. materials는 자료 원본 또는 안전한 자료 명세의 팩 내부 위치·해시이며 외부 자원은 그 명세가 고정한다. namespace·증거 루트는 사용자 실행 설정에서 받고 manifest의 임의 경로로 덮어쓰지 않는다.

registry는 코드가 지원하는 실행기(name/version)별 subject·자료 역할·전제 field의 타입·필수 집합을 등록한다. 1차는 A5 기존 MODEL/FUNC/NET 실행 바인딩, SYS(A5 §8.5), PERF(http_load/2), AUTH(auth_surface/1)·APIGW(apigw_probe/1), 합성 전용 `synthetic/1`이다. 팩은 이 집합의 검증된 조합만 선택한다. preconditions는 A11 등록 ENV field 또는 A5 Conditions field의 동형 eq만 사용하며 미확인은 UNKNOWN, 거짓은 해당 전제 불충족이다. 실행 중인 코드를 불러오는 경로는 팩에 두지 않는다.

기존 test_materials.normal_model/normal_request/attack_fixture는 첫 실행기들의 자료 역할 별칭이다. 필요한 역할은 선정된 executor가 결정한다. case_ids도 팩 바인딩과 registry의 지원 동작으로 검증한다. 신규 subject·새 자료 해석·새 전제 연산자가 필요하면 소유 스키마·registry·adapter 코드와 시험을 먼저 확장해야 한다. **팩 교체만으로 가능한 범위는 기존 실행기가 표현하는 시험까지**다.

합성 팩은 기존 sys.* 또는 network.* 합성 관측을 사용해 피어 허용/비허용이라는 정책 모양을 검증할 수 있다. 실제 ingress 피어 관측 subject를 지원한다고 표시하지 않는다. 모의 결과는 EXAMPLE·STATIC이며 권고는 그 한계를 유지한다.

### 4.5 expected·AUTH/APIGW 실행기 인계 (D43)

서비스는 RUN.requirement_refs의 IA revision·phase·index·POL·TEST와 PLAN 선정 이유를 해석한다. 여러 요구이면 expected와 실행/증거 조건의 동일성을 확인한 뒤 기존 judge 인자 하나로 전달한다. RUNTIME도 runtime_requirements[].expected에서 읽는다. 순수 judge는 최신 정책·파일·시각을 조회하지 않는다.

AUTH expected는 승인 공개 경로 목록과 해시다(A4 §11.6). OBS.public_allowed·목록 해시를 서비스가 대조하고 불일치 근거를 배제·진단한다. 수집기의 공개 허용 주장은 정책을 바꾸지 못한다. APIGW expected는 고정 route/role/model이며 health는 A5 §8.8.1의 apigw.health 유효 OBS로 전달한다.

registry의 `auth_surface/1` 실행기는 정상 모델·라우트 inventory·공개 경로 요청 템플릿, `apigw_probe/1`은 고정 route profile·요청 계획·gateway/engine 신원·직접 접근 source 명세를 요구한다. 둘 다 A5 등록 subject만 생성하며 새 subject를 팩이 임의 선언할 수 없다. 요청 본문/키는 메모리에서만 사용하고 A13 허용 요약만 보존한다. 실제 프로필·대조 가능성은 I8/T6의 사람 실측 관문이다.

## 5. 지원 버전 설정

A15 §10a.2의 고정 allowlist를 설정으로 바꾼다(A15 v2.0).

```toml
[engine.vllm]
supported_versions = ["0.13.0", "0.14.0"]   # 정확한 버전만. 범위 표기 금지
images = { "0.13.0" = "vllm/vllm-openai@sha256:<digest>", "0.14.0" = "vllm/vllm-openai@sha256:<digest>" }
```

- 목록 밖 버전은 입력 단계에서 거부한다(지금과 같음). 버전 추가는 설정 변경 + 이미지 digest 고정 + smoke(A5 §5.4) 통과 기록이 있어야 공식 실행에 쓴다. smoke 기록이 없는 버전은 EXAMPLE 실행만 허용한다.
- 이미지 digest는 설정에서 읽고 RUN에 고정한다. 태그만 있는 설정은 거부한다.
- 코드에 버전 문자열을 넣지 않는다(테스트 픽스처 제외).

### 5.1 SmokeRecord와 자격 확인

내부 준비 기록 `SmokeRecord={record_id:string,schema_version:"2.0",engine_version:string,image_digest:Digest,platform:string,model_sha256:SHA,engine_args_sha256:SHA,environment_fingerprint:SHA,parser_version:string,checked_at:RFC3339,status:PASS|FAIL,evidence:{location:string,sha256:SHA,size_bytes:int≥0}[],data_origin:MEASURED|EXAMPLE}`를 별도 불변 저장한다. 실행 설정은 `engine.vllm.smoke_records`의 record_id 목록으로 참조한다. 공식 RUN preflight는 아래 §5.2 qualification profile의 이미지·플랫폼·정상 모델·엔진 인자·환경 지문·파서가 일치한 MEASURED/PASS 기록과 원본 해시를 요구한다. 환경 drift·이미지 변경 시 재사용하지 않는다. EXAMPLE 기록은 공식 자격이 아니다. 버전 문자열만 맞는 smoke를 재사용하지 않는다. A5 §5.4 준비 smoke는 자격 확보를 위한 별도 경로다.

### 5.2 자격 profile와 시험자료 preflight (D43)

§5.1 SmokeRecord는 필드 구조 2.0을 유지한다. model_sha256은 대상 정상 준비 모델, engine_args_sha256은 qualification profile의 잠근 인자다. 내부 QualificationProfile=`{profile_id:string,model_sha256:SHA,engine_args_sha256:SHA,environment_fingerprint:SHA,parser_version:string}`을 P0 준비 명세에서 고정하고 record_id와 연결한다. 이미지·플랫폼은 SmokeRecord의 기존 필드다. 실행 UID·관측 시각은 자격 지문에 넣지 않으며 매 RUN에서 별도 귀속한다.

MODEL 표식 자료나 개별 요청자료가 정상 smoke 모델과 다르다는 이유로 정상 자격을 무조건 재사용하거나 무조건 새 자격을 요구하지 않는다. A17 Binding preconditions/materials에 시험 목적상 허용되는 차이를 명시하고, 그 차이가 엔진 인자·자원·dtype·병렬화 등 자격 조건을 바꾸면 해당 profile의 새 smoke를 요구한다. 미등록 차이는 실행 차단이다. PERF는 실제 부하 모델·토크나이저·stream·인자가 맞는 profile을 요구한다. SYS의 양성 대조·센서 건강은 실제 RUN마다 확인하며 정상 smoke가 대신하지 않는다.

preflight는 (1) 유효 MEASURED/PASS qualification 기록과 현재 엔진/환경 일치, (2) 실제 시험자료·옵션과 해당 Binding의 고정 계약 일치를 모두 검사한다. 이 계약은 자격 재사용을 위한 검사 범위이며 실제 자료·엔진·센서 준비가 완료됐다는 선언이 아니다.

## 8. 1차 완료 기준과의 관계

- 22807 팩을 빼고 다른 팩(합성 EXAMPLE 팩 `PACK-EXAMPLE-SYNTH`)을 넣어도 파이프라인이 코드 수정 없이 끝까지 도는지를 통합 시험으로 확인한다(A8 §7.5 G-X1).
- 모든 선택 기능을 끈 설정과 모두 켠 설정 두 가지로 A8 §4 절차를 돌린다(A8 §7.5 G-X2·G-X3).

### 8.1 두 번째 콘텐츠 팩 후보: CVE-2025-29783

공식 vLLM 권고 GHSA-x3m8-f7g5-qhm7(확인 2026-10-02)은 Mooncake 분산 KV 연동 배포에서 영향 버전 ≥0.6.5,<0.8.0, 수정 0.8.0을 명시한다. [공식 권고](https://github.com/vllm-project/vllm/security/advisories/GHSA-x3m8-f7g5-qhm7).

후보만 기록하며 1차 필수 실측·지원 버전 allowlist에는 추가하지 않는다. 취약점 재현·악용 입력·RCE 시험을 만들지 않는다. 방어적 팩의 후보 항목은 (1) Mooncake 사용 여부를 검증된 설정으로 판단(꺼짐 확인=비적용, 미확인=UNKNOWN), (2) 공식 수정 이력과 배포 이미지의 연결 확인, (3) 승인된 시험 환경의 내부 통신이 허용 피어로 한정되는지 확인하는 것이다.

NET-004의 outbound 목적지 계약과 내부 ingress 피어 경계는 같지 않다. 새 관측·신원·방향 계약이 필요하며 단순 포트 연결 결과를 취약점 제거 증거로 해석하지 않는다. 허용 피어의 정상 경로 확인 없이 비허용 연결 실패만으로 차단 PASS를 만들지 않는다. 실제 분산 배치·자원·버전 pair·이미지 digest는 첫 시연 뒤 별도 검토한다. G-X1의 합성 팩은 이 정책 모양을 기존 합성 adapter로 표현하는 데 한정하며 Mooncake 실측 지원을 입증하지 않는다.
