## 공격・실패 원리별 찾아보기

**분류를 읽는 기준**

공격·실패 원리 **17개**로 같은 위험을 모았다. 기존 **24개는 서빙 접점별 분석 묶음**으로 남겨 코드·R 근거를 찾는 데 사용한다. 시나리오는 **83개**로 유지하며, 원리를 부여한 82개(위협 후보 73개·실패 및 오설정 9개)와 공유 실행 권한의 침해 범위 1개로 나눈다. 77개 CHK와 SC 식별자는 그대로 사용한다.

주 분류는 각 시나리오에서 직접 확인하는 핵심 실패 원리다. 한 SC가 다른 원리도 포함하면 성립 조건을 붙여 함께 표시한다. STRIDE는 침해되는 보안 속성을 확인하는 별도 분류로 유지한다.

## 5.1 표를 읽는 방법

대표 CHK 앞의 1.1.1 같은 번호는 02·04와 같은 점검 번호다. 번호로 보안 기능과 보호 요구를 찾고, CHK ID로 원문·코드·시나리오 근거를 확인한다.

**위협 시나리오 → 보호 요구 → 통제·집행점 → CHK·시험 분기 → 증거·판정**

공격·실패 원리 17개를 기준으로 시나리오 83개를 읽는다. 시나리오는 위협 후보 73개, 실패·오설정 검증 9개, 공유 신뢰 범위 1개로 구분한다. 기존 24개 묶음은 서빙 접점별 분석 색인으로 유지한다. 각 시나리오의 실제 영향과 통제 효과는 실행 시험이 남아 있다.

| 표시 | 뜻 |
| --- | --- |
| R | 모델 취득·로딩, 요청 실행·반환, 실패·운영 변경 등 동작 경로 |
| AS·POL | Asset(보호 자산)·Policy(보호 정책). 보호할 대상과 유지해야 할 조건 |
| TB·SURF | Trust Boundary(신뢰 경계)·Surface(공격표면). 권한·신뢰가 달라지는 경계와 조작 가능한 접점 |
| 시나리오(SC, Scenario) | 어떤 주체·접점·환경에서 보호 요구가 깨지거나 실패하는지 설명 |
| 점검(CHK, Check) | 실제 확인 방법·증거·판정 기준이 있는 항목 |
| 도출 근거·관련 사례(Q, 기존 Question ID) | 점검을 만든 정책·코드·사례·절차를 모은 기록 |

각 행에 대표 시나리오와 필요한 점검을 적었다. 한 SC가 여러 CHK를 필요로 하고 같은 CHK가 여러 SC에 쓰일 수 있다. 같은 실행 증거를 재사용하더라도 보호 요구가 다르면 각각 판정한다.

## 5.3 위협부터 판정까지 살펴보는 사례

### 사례 A. 승인 후 모델 파일 교체

- **주체·접점:** 승인 이후 파일·symlink·mount를 바꿀 수 있는 주체. R05·06·09의 승인→선택→읽기→적재 경로를 본다.
- **보호 요구:** 승인한 묶음에 포함된 파일·코드만 실제로 사용한다. POL-02·05·11의 관련 보호 요구를 확인한다.
- **통제:** 승인본을 변경할 권한을 제한하거나 읽기 전에 변경 여부를 확인해 거부한다. 어느 구성요소에서 이 제한을 적용할지 정한다.
- **평가:** [SC-10-01](../01_프레임워크와_위협통제연결.md#SC-10-01) → [2.2.1 · CHK-SUP-005](../03_체크리스트와_보완가이드.md#CHK-SUP-005). 각 worker 적재의 대응은 [2.2.2 · CHK-SUP-006](../03_체크리스트와_보완가이드.md#CHK-SUP-006)도 확인한다.
- **시험:** 승인 사본 정상 로딩과 읽기 전 무해 교체를 대조한다. 승인 당시 해시, 변경한 주체·시각, 실제 열린 파일과 사용·거부 결과를 수집한다.
- **판정:** 승인하지 않은 파일을 실제로 읽어 사용하면 미충족이다. 실제 사용 파일을 확인할 수 없으면 미확인이다. 쓰기 거부 또는 소비 전 거부와 허용 정상 동작을 확인해야 충족이다.

### 사례 B. Gateway 우회와 인증 제외 경로

- **주체·접점:** 엔진의 수신 주소(listener)에 연결할 수 있는 외부·내부 호출자다. 실제로 등록된 API 경로, Gateway의 경로 재작성과 직통 경로를 확인해야 한다.
- **보호 요구:** 허용한 호출자만 해당 작업을 수행한다. 키 존재와 사용자별 모델 인가를 각각 확인한다.
- **통제:** 승인된 진입 경로와 API별 인증·인가를 적용하고 직접 접근을 제한한다.
- **평가:** [SC-01-01](../01_프레임워크와_위협통제연결.md#SC-01-01) → [1.2.1 · CHK-REQ-001](../03_체크리스트와_보완가이드.md#CHK-REQ-001). 경로 해석은 [1.2.2 · CHK-REQ-002](../03_체크리스트와_보완가이드.md#CHK-REQ-002), 내부 통신 접근 범위는 [1.4.3 · CHK-PLT-006](../03_체크리스트와_보완가이드.md#CHK-PLT-006)도 관련 조건에서 확인한다.
- **시험:** /v1만 보지 않고 실제 추론·관리 route와 보호 prefix 밖 등록 경로를 포함한다. 키가 없는 요청·틀린 키 요청·허용된 키 요청을 Gateway 경유와 직통 경로에서 대조하고, 실제 처리 함수(handler)가 실행됐는지 확인한다.
- **판정:** 금지 호출자가 실제 작업을 수행하면 미충족. route·도달·집행점을 확인하지 못하면 미확인. 404·연결 실패 하나로 전체 API를 충족 처리하지 않는다.

### 사례 C. 취소 응답 이후 작업 잔존

- **주체·접점:** 요청 취소·연결 종료와 실행 그룹의 장애 경로. 악의적 반복 취소와 정상 장애를 각각 고려한다.
- **보호 요구:** 정한 기한에 계산·전송·참조가 끝나고 다음 정상 요청을 처리할 수 있어야 한다.
- **통제:** 외부·내부 ID 범위에 맞게 취소를 전달하고 scheduler·worker·전송 자원을 정리한다. 엔진이 종료된 경우에는 별도 장애 절차로 처리한다.
- **평가:** [SC-18-01](../01_프레임워크와_위협통제연결.md#SC-18-01) → [6.4.1 · CHK-LIF-010](../03_체크리스트와_보완가이드.md#CHK-LIF-010). 늦은 출력 혼입은 [4.1.2 · CHK-REQ-012](../03_체크리스트와_보완가이드.md#CHK-REQ-012), 실패 그룹 정리는 [6.4.2 · CHK-LIF-011](../03_체크리스트와_보완가이드.md#CHK-LIF-011)로 각각 판정한다.
- **증거·판정:** abort 접수, 실제 내부 실행 종료, 참조·전송 회수와 후속 요청을 본다. 취소 HTTP 응답이나 집계 GPU 지표만 있으면 필요한 회수 판단은 미확인이다.

S Spoofing · T Tampering · R Repudiation · I Information Disclosure · D Denial of Service · E Elevation of Privilege. **각 유형은 위협 후보가 어떤 보안 속성을 깨뜨릴 수 있는지 나타낸다.** 복수 유형은 조건별로 성립할 수 있으므로 SC 상세의 분류 이유·조건을 함께 확인한다.

## 5.5 기존 취약점·패치를 쓰는 방법

기존 사례에서 확인한 내용을 점검 이유와 함께 **도달 조건·입력·정상 대조·증거·판정 기준**에 반영한다.

| 사례에서 확인한 내용 | 평가에 반영할 내용 |
| --- | --- |
| 인증이 보호하는 경로와 실제 router 경로의 불일치 | 경로 재작성·root_path·등록 handler를 포함한 [1.2.1 · CHK-REQ-001](../03_체크리스트와_보완가이드.md#CHK-REQ-001)·002 시험 |
| batch 자리 이동 뒤 이전 mask가 남는 문제 | 선택한 runner·mask 생성 조건을 확인한 뒤 [4.4.1 · CHK-REQ-018](../03_체크리스트와_보완가이드.md#CHK-REQ-018)에서 이동·완료·재사용 대조 |
| parser·template·직렬화에서의 비허용 실행·입력 우회 | 실제 reader·import·입력 선택 분기에 도달하는 CHK-SUP·REQ 시험 |
| 오류·취소·느린 수신자의 서비스·자원 영향 | 오류 뒤 정상 요청, 열린 느린 연결과 끊긴 연결, 실제 회수 증거 |

현재 버전이 과거 취약점의 영향 범위를 벗어났더라도 실제 수정 여부를 확인해야 한다. 설치 이미지·backport·의존성·활성 경로를 대조하고 회귀 시험을 설계한다. 공지의 판본 표기가 모순되거나 경계가 불명확하면 자동 판정 근거로 쓰지 않고 수정 PR·commit과 원문을 확인한다.

**비교 결과:** 공급·자격·서비스 거부 같은 공격 행동은 외부 분류와 대조할 수 있다. 반면 batch slot별 요청 구분, CUDA Graph의 입력·버퍼 사용 기간, TP 참조 종료, 복원 전 준비 확인은 현재 분류 번호만으로 충분히 설명되지 않는다. 이 동작은 자체 SC·CHK로 유지한다. 모델 행동을 겨냥한 프롬프트 주입·학습 오염·모델 추출은 별도 범위 검토 없이 현재 평가 완료 항목으로 넣지 않는다.

## 5.7 분석 범위와 남은 확인

위협의 누락 여부는 다음 관계를 대조해 확인한다.

1. 정상 동작 경로(R)와 보호 요구(POL)를 대조한다.
2. 실제 SURF와 공격자 능력으로 조작·조회·우회 가능한 접점을 대조한다.
3. 기존 통제와 취약점·패치를 반영해 구체적인 SC를 만들고 관련 CHK에 반영한다.
4. 같은 요구는 합치되, 자료를 사용하는 프로그램, 검사·차단 위치, 실패 조건이 다르면 각각 시험할 분기를 남긴다.

시나리오가 없는 구간도 검토 여부와 이유를 확인한다. 아직 검토하지 않은 구간, 조건부 기능, 다른 항목에서 다룬 구간, 검토했으나 후보를 도출하지 않은 구간, 적용되지 않는 구간을 나눠 표시한다. 각 구간에 검토 결과와 남은 확인을 기록한다.

현재 공격표면에는 부분 검토·근거 보완·대기 항목이 남아 있다. R10 전체·R14를 검토하고, 계측 방법과 선택한 구현의 동작을 추가로 확인해야 한다.
