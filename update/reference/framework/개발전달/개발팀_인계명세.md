# 개발팀 인계 명세

**공통 기준 정리: 2026-10-27.** 이 문서는 프레임워크가 전달하는 기준·입력·결과와 개발팀이 구현·시험할 경계를 연결한다. 보안 기능 8개·보호 요구 36개·CHK 77개·시험 분기 116개와 네 CHK의 필수 세부 결과 9개를 유지한다. 공통 기록 의미는 확정했고, 추가 필드·객체·저장 구조·API 형식은 개발팀의 설계 제안 단계다.

## 판정·호환성 인수 확인

- 적용·지원·선정·수행·수집·판정을 각각 보존한다. 미사용 근거가 없는 false는 자동 비적용으로 처리하지 않는다. Q 출력은 추천이며 보안 통과 판정으로 사용하지 않는다.
- 문서/설정 검토에는 EVD와 실제 검토자·시각·절차 Ref를 남긴다. 수동 원자료의 DECLARED와 합성 EXAMPLE 등급을 유지하며 실제 엔진 시험이 필요한 범위의 증거 부족을 보존한다.
- canonical focus와 primary Q·shared Q·SC를 정본 관계에 맞춘다. full branch는 CHK·분기명·전체 SC·apply_when 원문·내용 판본으로 구별하고 실제 case의 SC와 역할을 나눈다.
- 새 재사용 판단은 원 EVD/RES·원환경/정책/팩·실행 시각을 바꾸지 않고 별도 기록한다. 미해소 Ref는 보류하고 이월을 새 실측으로 세지 않는다. `FAIL→UNKNOWN` 비교는 UNKNOWN을 유지한다.
- CPU `framework_assessment_review` dossier는 원 bytes/hash와 별도 읽기 경로를 보존한다. 구판을 새 기본값으로 채워 재봉인하지 않는다. 당시 judge/parser/lock 또는 검증된 호환경로가 있어야 재판정 재현 범위를 주장한다.
- OBS-007의 replay 금지 정책에서 거부를 확인하는 기준과 기존 제품의 PASS 지원 조건 차이를 개발팀이 검토한다. 지원 확대 전에는 실제 지원 상한을 표시한다.

```sh
python3 -B verify_framework.py

python3 -m unittest discover -s tests -v
python3 -B select_checklist.py --self-test

```

합성 예시의 보조 요구별 범위 배정은 그 EXAMPLE에 대한 검사이며 제품 전체에 고정 배정을 요구하지 않는다.

정본 검사는 네 CHK의9필수 결과·45필드 빈 양식·문서/분기/canonical 관계와 사전 hash를 확인한다. 합성 예시 검사는 지정한 설계 예시와 독립 반례를 확인한다. 정본의 필수 결과 계약은 검증 대상에서 자동 생성하지 않으며 정의 변경 시 원문·문서·계약을 함께 검토한다. SGLang 목록 검사는 정적 목록을 확인하고, 고정 소스를 확보한 대조는 `--source-root <SGLang 고정 소스> --check`를 사용한다. 각 검사는 검사한 문서·데이터·정적 범위의 근거로 남긴다.

개발팀은 채택한 제품 판본에서 생산→저장→내보내기→다시 읽기→API/화면의 동일 정보 보존, 구판 호환, 정상/위반/누락·중복·잘못된 귀속·미해소 Ref 반례를 별도로 통과시킨다. 기존 phase1의 제품 단위/API/web 시험 수는 그때의 실행 기록이며 이번 프레임워크 검사 수에 합산하지 않는다.

## 인계 완료와 다음 결정

프레임워크 담당자는 공통 의미·정본/문서·입력/결과 계약·검사 경계·기존 구현 대응·완료 조건을 제공한다. 개발팀은 객체/필드/스키마 선택, 생산자·소비자 변경 영향, 지원 판본·구판 읽기·시험 환경을 검토해 구현안을 정한다. 승인한 제품 설계와 실제 시험 기록을 새 판본으로 연결하면 해당 구현 묶음을 닫는다. 저장/API 제안을 합의 전의 확정 제품 명세로 사용하지 않는다.

## 항목 경계와 기존 소비 경로

같은 시험·원자료를 연결하는 조건과 항목별 판정 예는 [03 판정 경계](../03_체크리스트와_보완가이드.md#항목간-판정경계)를 따른다. EVD의 `check_id`와 원환경·정책·대상·시점은 유지하고, 같은 원자료를 활용한 각 CHK의 관측과 RES를 구분한다. OBS-012는 관측 사본의 5.7 결과와 Q-C12 로그·진단 외 자산별 결과를 보존하며, 필요한 적용 범위의 집계는 [최소명세](결과기록_최소명세_초안.md)의 기존 규칙을 따른다.

기존 BYUL importer는 `base_method_and_evidence`를 점검 정의의 방법으로 가져온다. 이 문자열에 각 항목의 필수 방법·조건과 짧은 F번호·고정 원문 링크를 남겼다. 추가 `implementation_note_refs`를 읽지 않아도 원근거를 찾을 수 있다. 문서·HTML은 같은 원천 필드와 기존 finding을 표시하며, 공통 메모 전문은 03의 부록에서 읽는다. 제품 객체·실행기·판정·API의 신규 구현은 별도 개발 범위로 유지한다.

REQ-021·PLT-007의 네 분기 조건은 [판본 대응표](../03_체크리스트와_보완가이드.md#분기-판본대응-20261027)에서 구판과 현행을 비교한다. 기존 결과의 분기 원문과 판본은 보존하고 새 평가 계획에 현행 조건을 사용한다.

## 내용판본과 선택 입력의 추가 분기

`schema_version`은 JSON 구조, `date`는 원작성일, `scenario_revision`은 기존 시나리오 판본이다. 이번 내용판본은 `assessment_registry.revision=2026-10-27-input-hardening`이며 전체 파일은 SHA256과 Git commit으로 식별한다. 개별 CHK에 새 revision 필드를 만들지 않는다. 과거 입력·결과는 당시 내용판본과 hash를 유지한다.

기존112개 분기를 보존하고 REQ-009 입력 정합성1개, REQ-010 구조화 출력의 복잡도/도구 조합2개, LIF-003 미디어 예산1개를 추가해 현행은116개다. 새 네 분기의 `scenario_ids=[]`는 직접 연결한 기존 SC가 없는 CHK 고유 시험이며 고정 공식 파일·행을 근거로 CHK의 고유 시험을 준비한다. 기존 token/sampling/요청 개수·공정성 SC를 새 시험의 실행 근거로 확장하지 않는다. 전체 분기 참조는 기존 CHK·내용판본과 `name`·`scenario_ids`·`apply_when` 원문으로 유지한다.

공식 시험은 vLLM `5d35ce3934a7804b298559d2d99eec33792e1eb9`의 소스 검토 근거다. 선정 설치판의 지원·실제 옵션 전달·관측·거부 시점·후속 정상 동작을 확인하고 실행·판정을 남긴다. 현재 공식 pytest와 실제 엔진/GPU/AWS 실행, 참조 v0.31.0과의 판본 호환은 미확인이다. [공식시험 대조표](공식시험_대조표.md)에서 기존 구현 유지·실제 지원 기능의 미구현 분기 보강·미병합 PR34 관측 재사용을 구분한다.

BYUL의 기존 importer는 원문과 override를 합쳐 정의를 만든다. REQ-09의 현행 실행 단계2개는 token-array 제한 프로파일로 유지된다. 추가 입력·schema/tool·미디어 분기는 정본·공식 대조표·방법/관측 설명으로 인계하며 실행 계획·typed 관측·judge·범위별 결과 연결은 개발팀 후속이다. 현행 제한 프로파일 PASS와 새 분기의 미실행/UNKNOWN을 구분하고, 새 범위의 선정·관측·판정 연결을 확인해야 그 범위를 완료로 처리한다. CheckDef revision은 기존 생성 내용 변경 시에만 증가하고 팩 revision은 manifest 변경을 따른다.
