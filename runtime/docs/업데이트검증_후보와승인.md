# GPU Lab 업데이트 검증 자료: 후보와 승인

이번 구현은 수집·검토·게시 경로만 제공한다. 승인 기준과 승인자는 다음 AWS 회차에서 Claude/사용자가 정한다. 현재 서버값, 해시가 같은 두 후보, 설치 성공을 승인 근거로 취급하지 않는다. 아래 명령은 다음 유지보수 회차용이며 이번 작업에서는 실행하지 않았다.

## 경로와 권한

| 호스트 경로 | Gateway 경로 | 용도 |
| --- | --- | --- |
| `/srv/serving/verification/candidates` | 마운트 없음 | 관측 후보. OBSERVATION_USER 소유, 관측 GID, 2750 |
| `/srv/serving/verification/approved` | `/etc/serving/verification` (readOnly) | 관리자가 검토해 게시한 문서. root 소유, Gateway data GID, 2750 |
| `/srv/serving/models/7ae557604adf67be50417f59c2c2f167def9a775` | `/models` (readOnly) | 저장소 SGLang의 snapshot 경로. 실제 vLLM 경로는 미확인; 12회차 조회 후 서버 사본을 일치시킬 것 |

Gateway UID 10000·readOnlyRootFilesystem을 유지한다. `approved`의 네 파일은 `asset-manifest.json`, `baseline.json`, `manifest.json`, `revocations.json`이다. 상위 verification은 root 소유·관측 GID·2750으로 두어 관측 사용자와 Gateway(보조 그룹 10010)가 통과할 수 있게 한다. 설치기는 관측 사용자의 관측 그룹 가입과 디렉터리를 멱등 준비하고 승인 파일을 만들거나 덮어쓰지 않는다. 사용자 서비스의 기존 그룹 목록은 재시작 뒤 확인한다. 문서와 승인 기록은 게시 도구가 setgid 그룹을 상속해 명시 0640으로 원자 저장한다. 후보도 원자 저장하고 기존 파일 덮어쓰기를 거부한다. 설치기의 Tetragon `/var/lib/serving-runtime/baseline.json`은 별도 자료이며 여기의 모델/구성 baseline과 혼용하지 않는다.

엔진은 `/models`를 모델 경로로, `/cache`를 HF_HOME·컴파일 등 가변 캐시로 사용한다. 현재 배포에는 별도의 tokenizer 경로 인자가 없다. 승인 자산 목록은 `/models`의 전체 파일을 해시한다. `/cache`의 변하는 내용은 승인 모델 기준에 섞지 않는다. 엔진 모델/토크나이저 경로나 세대가 바뀌면 실제 Pod의 hostPath·mountPath·subPath·인자를 먼저 검수하고 Gateway mount 및 후보의 root를 함께 변경한다. 다른 경로에서 tokenizer를 읽는 구성은 추가 설계·mount·승인 대상이다.

설치 후 UID 10000에서 모델 폴더 순회·파일 읽기가 가능한지 확인한다. 기존 모델 소유권·엔진 캐시 0700을 무작정 바꾸지 않는다. 권한이 부족하면 관리자가 해당 모델 snapshot에만 UID 10000의 읽기·디렉터리 탐색 ACL을 부여하고 쓰기 불가를 확인한다. Gateway에 root 그룹이나 캐시 쓰기 권한을 주지 않는다. 모델을 갱신하는 동안 해시하지 말고 변경이 멈춘 snapshot과 외부의 신뢰 가능한 배포/취득 근거를 검토한다. 파일 대조는 엔진이 메모리에 적재한 바이트의 증명이 아니다.

## Gateway 적용 전 필수 점검

**폴더 준비 → 실제 vLLM 모델 hostPath 조회·일치 → 폐기 목록 승인본 게시 → 사전 점검 → Gateway 적용/재시작** 순서다. [GPU Lab README](../deploy/gpu-lab/README.md#다음-회차-업데이트-전후-검증-자료-연결)의 kubectl 조회·조건부 적용 명령을 사용한다. vLLM 엔진의 실제 모델 hostPath는 12회차에서 kubectl로 확인 후 일치시킬 것. SGLang 파일의 경로가 같다는 이유로 vLLM까지 검증됐다고 간주하지 않는다. 자산 후보 생성 명령의 `--root`도 확인한 경로로 바꾼다.

호스트의 `tools.gpu_lab_gateway_preflight --approved-dir <최종 verification hostPath> --model-root <최종 model hostPath>`는 AWS/Kubernetes에 접속하지 않는 읽기 전용 점검이다. 두 디렉터리 누락/형식/조회 오류와 폐기 목록의 파일 없음·읽기 오류·JSON/스키마 오류를 구분해 종료 1로 중단한다. 주요 이유 코드는 `VERIFICATION_DIRECTORY_NOT_FOUND`, `MODEL_DIRECTORY_NOT_FOUND`, `REVOCATIONS_NOT_FOUND`, `REVOCATIONS_READ_ERROR`, `MALFORMED_REVOCATIONS`, `INVALID_REVOCATIONS`다. 후보 봉투·링크·특수 파일도 거부한다. 빈 목록을 만들거나 승인하지 않으며, 이미 게시된 유효한 빈 목록은 통과한다. 유효한 목록이 현재 정책을 명시 폐기한 경우의 503은 의도된 동작이다.

점검 인자는 **Gateway가 배치될 노드의 최종 매니페스트 hostPath 값**이어야 한다. 도구는 매니페스트/실엔진과의 일치나 root가 아닌 Pod의 읽기 권한을 자동 입증하지 않는다. 다중 노드면 모든 배치 가능 노드에서 준비하거나 준비한 노드로 배치를 제한해야 한다. 점검 후 적용 전 자료/경로가 바뀌면 재점검한다. 후속 제안은 확인한 경로 하나로 Kustomize patch·점검 인자를 같이 생성하는 방식이며 이번에는 자동 적용 코드를 추가하지 않았다.

| 자료/경로 누락 | 표시/시작 영향 | 이 누락 자체의 추론 차단 |
| --- | --- | --- |
| `asset-manifest.json` | collector 오류·미설정/미승인 | 없음 |
| `baseline.json` | `not_configured`·승인본 없음 | 없음 |
| `manifest.json` | `not_configured`·승인본 없음 | 없음 |
| `revocations.json` | 폐기 상태 unknown | 있음: 기존 규칙대로 503 |
| verification/model hostPath 디렉터리 | `type: Directory` 볼륨 준비 실패, Pod 시작 불가 | Gateway가 새로 시작하지 못함 |

다른 정책·인증·대상 확인 조건에 따른 차단은 별개다. 선택 자료 누락이 차단하지 않는다는 점은 유효한 폐기 목록과 함께 Gateway 객체의 실제 요청 허용 게이트를 사용하는 회귀 시험으로 확인한다.

## 후보 생성 (runtime 디렉터리에서)

설치된 runtime Python 또는 로컬 `.venv/bin/python`을 사용한다. 호스트에서 실행하며 Gateway에 kubectl·Kubernetes 자격·쓰기 권한을 추가하지 않는다. 출력 파일명은 회차별로 새로 정한다. 아래 `env-run.json`은 사람이 정한 환경 ID/판본에 대한 **후보**다.

```bash
.venv/bin/python -B -m tools.aws_environment_candidate \
  --target-registration /srv/serving/bundles/current/target.json \
  --gateway-policy /srv/serving/bundles/current/runtime-policy.json \
  --environment-id gpu-lab-env --revision 1 \
  --out /srv/serving/verification/candidates/env-run.json

.venv/bin/python -B -m tools.verification_material assets \
  --root /srv/serving/models/7ae557604adf67be50417f59c2c2f167def9a775 \
  --gateway-root /models \
  --out /srv/serving/verification/candidates/assets-run.json

.venv/bin/python -B -m tools.verification_material declaration --kind baseline \
  --environment-candidate /srv/serving/verification/candidates/env-run.json \
  --out /srv/serving/verification/candidates/baseline-run.json
.venv/bin/python -B -m tools.verification_material declaration --kind manifest \
  --environment-candidate /srv/serving/verification/candidates/env-run.json \
  --out /srv/serving/verification/candidates/manifest-run.json

.venv/bin/python -B -m tools.verification_material revocations \
  --out /srv/serving/verification/candidates/revocations-run.json
```

묶음 안의 실제 파일명은 `bundle.json`의 역할별 path를 먼저 확인한다. 위의 target/runtime-policy 파일명은 예다. `revocations --source <기존 폐기 목록 파일>`은 기존 내용의 검토 후보를 만든다. `--source` 생략은 빈 **후보**만 만든다. 기존 폐기를 지우는 의미가 될 수 있으므로 빈 목록 게시도 승인 대상이다.

`assets snapshot` 기존 명령도 관측 초안을 만들지만, 새 도구는 Gateway 로더가 받지 않는 `runtime-verification-candidate/1.0` 봉투로 후보를 구분한다. 심볼릭 링크·불완전 순회는 새 자산 후보에서 거부한다. 선언 후보는 확인한 필드만 포함하고 미확인 사유를 함께 남긴다. 같은 관측에서 baseline과 manifest를 생성해도 적합한 기준선이라는 뜻은 아니다. baseline은 승인할 기대 기준, manifest는 검토한 현재 구성 선언이다. 업데이트 후에는 baseline을 보존하고 새 manifest·실제 관측을 비교한다. 선언 값끼리 일치해도 미수집 engine API 행은 미수집으로 유지한다.

## 사람이 검토한 뒤 게시

검토자는 외부 취득/배포 근거·파일별 해시·모델 revision·기준에 포함할 필드·미확인 항목을 확인한다. 후보 수정 후에는 다시 문서를 검토하고 새 SHA-256을 기록한다. 후보의 `unconfirmed`는 승인으로 해소되지 않으며, 필드 누락을 통과로 해석하면 안 된다. 승인 명령은 판단을 대신하지 않고 검토자의 명시적인 게시 행위를 기록한다.

```bash
sudo /opt/byul/runtime/.venv/bin/python -B -m tools.verification_material approve \
  --candidate /srv/serving/verification/candidates/assets-run.json \
  --expect-sha256 REVIEWED_CANDIDATE_SHA256 \
  --reviewer REVIEWER_ID --reason REVIEW_REASON
```

baseline·manifest·revocations 후보에도 **각각** 실행한다. 검토 시 기록한 SHA-256과 현재 후보 바이트가 다르면 거부한다. 기존 승인 파일 교체는 새 후보를 검토한 뒤 `--replace`를 명시해야 한다. 후보 파일명으로 종류를 추정하지 않고 봉투의 kind와 기존 Gateway 검증기를 사용한다.

문서 SHA-256·후보 SHA-256·검토자·사유·시각을 `<kind>-<candidate hash>.approval.json`에 남기고 문서를 마지막에 원자 게시한다. 중단 시 기록만 남을 수 있으므로 **현재 문서의 SHA-256과 일치하는 기록**만 현재 게시 근거로 취급한다. 이 기록은 전자 서명이나 플랫폼의 정책 묶음 승인 계약이 아니다. 승인 경로를 쓸 수 있는 root 관리자를 신뢰하는 수동 운영 절차다. 기준/선언/폐기 목록은 시작 시 읽으므로 게시 후 Gateway를 재시작한다. 자산 목록은 주기적으로 다시 읽는다.

승인본이 없으면 자산 collector는 `ASSET_MANIFEST_NOT_APPROVED`와 ‘미설정/미승인’, baseline/manifest는 `not_configured`와 승인본 없음 사유를 표시한다. 읽기/JSON 오류는 오류다. 폐기 목록은 파일 없음 `REVOCATIONS_NOT_FOUND`, 읽기 오류 `REVOCATIONS_READ_ERROR`, 유효한 빈 목록은 `ok/not_revoked`로 구분한다. **폐기 목록 파일 없음/오류는 기존 fail-closed 규칙대로 Gateway 추론을 503으로 만든다.** 다음 배포 전에 폐기 목록을 검토·게시하고, 유지보수 동안 이 동작을 확인한다.

## 환경 후보의 계약 경계

수집기는 대상 등록의 context/namespace/selector/container로 실행 중인 단일 Ready 엔진을 확인한다. 선언된 이미지 대신 `containerStatuses.imageID`에서 digest만 남긴다. 엔진 패키지 판본·`/v1/models`·가시 GPU/드라이버는 엔진 안의 읽기 명령, 커널은 해당 노드의 nodeInfo, Tetragon/Cilium 판본은 **같은 노드**의 단일 Ready 에이전트 실행 파일에서 읽는다. kubectl은 get/exec만 사용하며 각 조회는 8초 이내로 제한한다. 권한/실패/다중 대상/누락은 미확인이고 선언 digest나 다른 노드값으로 대체하지 않는다. 모델 inventory는 실제 `/models` hostPath를 호스트에서 해시해 update의 all-scope 파일 목록(`path/bytes/sha256`)과 같은 정규 해시를 계산한다. 자산 manifest 자체의 해시와 혼용하지 않는다.

출력은 `runtime-environment-candidate/1.0`이며 `environment`에는 기존 `byul-environment/0.1`의 경로·자료형으로 확인한 값만 넣는다. `observations`/`unconfirmed`에는 미확인 표시·이유·출처가 있고 kernel/Tetragon/Cilium처럼 기존 환경 계약에 자리가 없는 값도 둔다. 원본 Pod/node 식별자·이미지 저장소 주소·환경변수·Secret·명령 출력/오류 원문은 저장하지 않는다. 결과와 CLI에 토큰·키·서버 주소·클라우드 식별 정보를 넣지 않는다.

**계약 제약:** 변경 금지인 환경 스키마는 source_commit·model revision 등의 필드를 필수로 요구하며 미확인 표현은 null만 허용한다. 이번 요구의 ‘null 없이 미확인 사유’를 지키기 위해 그런 필드는 생략하고 `import_ready: false`, `candidate_incomplete`로 명시한다. 즉 이 봉투나 미완성 `environment`를 플랫폼에 그대로 등록할 수 없다. 서버 폴더명을 모델 출처 revision으로 가장하지 않는다. 다음 회차에 검토자가 source commit·모델/토크나이저 revision·사용 사실·승인 intent를 근거로 완성하고 **기존 환경 계약 검증 → 새 환경 판본 등록 → 그 판본을 참조하는 정책 판본 → 묶음 내보내기** 순서로 진행한다. 모르는 필드를 계약상 null로 허용할지는 Claude/사용자가 정할 사항이며 이 도구는 자동 변환하지 않는다. 환경 문서에 임의 필드나 ‘미확인’ 문자열을 digest 대신 넣어 내보내기를 통과시키지 않는다.

완성본을 만드는 구체적인 경로는 다음과 같다. 계약 변경은 필요하지 않다.

1. 후보의 `environment` 객체만 검토 작업 사본 `environment-reviewed.json`으로 복사한다. 봉투·`observations`·`unconfirmed`는 동반 증거로 보존하며 환경 문서 안에 넣지 않는다.
2. 검토자가 미확인 필수 필드를 출처 근거로 채우고 기존 승인 intent·facts를 검토해 넣는다. 계약이 허용하는 null을 쓸지는 검토자가 명시 결정한다. 내보내기에 필수인 engine digest·runtime_kind·model ID·Gateway 설정·배치 정보는 확인값이 필요하다. unknown 문자열이나 임의값으로 채우지 않는다.
3. `platform/api`의 기존 검증기로 완성본을 검사한다(아래 예는 저장소 platform/api에서 실행, 값·오류 원문은 출력하지 않음). 오류 0이어도 사용 사실/승인·비교 적합성까지 입증된 것은 아니다.

```bash
.venv/bin/python -B - <<'PY'
import json
from pathlib import Path
from byul_platform.contracts import Contracts
document = json.loads(Path('/srv/serving/verification/candidates/environment-reviewed.json').read_text())
errors = Contracts(Path('../../contracts')).errors('environment', document)
print(f'ENVIRONMENT_SCHEMA_ERRORS={len(errors)}')
raise SystemExit(1 if errors else 0)
PY
```

4. 검증된 문서를 플랫폼 환경 편집/등록 경로로 새 판본에 저장한다. 정책의 environment_ref·target_ref를 해당 판본에 맞춘 뒤 기존 묶음 내보내기를 수행한다. 원본 후보의 `import_ready:false`를 true로 고쳐서 등록하는 절차가 아니다. 필수 출처 근거를 확보하지 못하면 미완성 후보를 유지한다.
