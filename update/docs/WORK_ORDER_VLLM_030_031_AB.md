# BYUL UPDATE vLLM 0.30.0 → 0.31.0 A/B 개발지시서

2026-11-18 · 출발 기준은 #292 병합 직후의 `main` `86d2e957`와 `PACK-BASELINE@39`다. [병합 커밋](https://github.com/dohashelby/byul/commit/86d2e957ae93dbb81b84c12d3ee163f85fd5adb2) · [팩과 제품 소스 고정 목록](../release/reviewed-source.json)

**목표는 vLLM 두 판본을 격리 Kubernetes GPU 환경에서 실제로 비교하고, UPDATE 대상 69개 중 보안 판정 `UNKNOWN`이 남는 점검을 6개 이하로 줄이는 것이다.** A는 AWS가 필요한 모든 시험과 공용 파일 통합을 맡는다. B는 두 판본의 관측·판정 연결, 입력 준비, Linux CI, 반출 증거 검토를 맡는다.

| 역할 | 엔진 | GPU 이미지의 출발 핀 |
| --- | --- | --- |
| 기준 `baseline` | vLLM 0.30.0, V1 | `docker.io/vllm/vllm-openai@sha256:5f5e535216848d0c52159c8c13a0af04be5f6fe1a84e79914300610796f76d40` |
| 후보 `candidate` | vLLM 0.31.0, V1 | `docker.io/vllm/vllm-openai@sha256:a4a4c0437bf7240089da5f08aa370c4aee17ae5290f7a3b468825ee26c4c3a6b` |

A는 실제 노드의 이미지 ID, 이미지 인덱스·manifest·config digest의 관계, 설치 파일, Python ABI를 확인해 핀을 확정한다. A-1에서 도구가 읽는 정본 표를 위 쌍으로 전환한다. 파일에 남은 기존 0.7.0 준비물은 해당 산출물이 작성된 당시의 판본으로 추적한다. ## 1. 완료 기준

분모는 정본 팩의 활성 점검 69개다. 팩에서 제외한 8개는 SUP-01·02·14, LIF-15, OBS-07·08·10·12다.

| 확인 항목 | 인수 기준 |
| --- | --- |
| 범위 | 정본 69개를 모두 선정 검토하고 점검별 기준·후보 138쪽의 처리 근거를 남긴다. 적용 점검은 양쪽에서 실제 실행하고 정확한 EVD·RES Ref를 비교 RPT에 연결한다. 비적용은 양쪽 환경의 선정 근거로 입증한다. REQ-04·06도 현재 설정으로 재확인한다. |
| UNKNOWN | 전체 69개에서 기준 또는 후보의 **보안 판정**이 `UNKNOWN`인 점검 ID의 합집합이 **6개 이하**다. 같은 ID가 양쪽에서 UNKNOWN이면 한 번 센다. RPT의 후보 기준 요약값 대신 각 행의 양쪽 보안 판정을 읽어 계산한다. |
| 비교 성립 | 적용 점검의 `NOT_RUN`, `ABORTED`, 누락 Ref와 비교 조건 불일치로 발생한 `NOT_COMPARABLE`은 전부 해소한다. 공백을 비적용으로 처리하려면 정책·실제 환경·선정 근거가 일치해야 한다. 기능·성능은 해당 점검에 정의된 기준과 관측 범위에 따라 보고한다. |
| 판정 | 동일하게 결합한 정책과 비교 조건에서 나온 `REGRESSED`, `FIXED`, `STILL_FAILING`, `NO_CHANGE`와 실제 `FAIL`의 이유를 보존한다. 과거 0.7.0→0.30.0의 SUP-08 회귀는 이력으로 연결하고 이번 쌍의 SUP-08은 실제 판정으로 기록한다. |
| 보고서 | 적용 범위의 원본 비교 RPT, 69행 인수표, 정책·팩·환경 Ref, 증거 반출 묶음과 SHA-256, 복원·재판정 결과를 인수한다. `official=true`는 정책 `CONFIRMED`, 팩 검토, `EXAMPLE` 근거 0건 등 제품 발행 조건을 충족한 원본에서 확인한다. |

비교 입력에서 모델·토크나이저 판본과 스냅샷, 시험 자료, GPU·드라이버·병렬 구성, 정책, 의미 있는 실행 설정을 쌍으로 고정한다. 판본별 차이는 어댑터와 지원 데이터에 둔다. 실제 GPU에서 얻은 관측을 `MEASURED`로 추적하고 CI와 사전 점검은 각각 구현 검증 및 실행 준비의 근거로 기록한다. 정식 릴리스 비교의 전체 선정과 변경 영향 기록은 U1을 따른다. ## 2. A 작업

**AWS 계정·크레딧·EC2·SSM·Kubernetes에 접근하는 작업과 실제 GPU 시험은 모두 A가 실행한다.** 현장 사전 점검, 이미지·준비물 설치, 시험 실행, 실제 관측기 자격 확인, 증거 반출과 자원 정리에도 같은 배정을 적용한다.

| 작업 | 수행 내용 | 인수 기준 |
| --- | --- | --- |
| **A-1 판본·정책과 공용 파일** | 이미 작성된 판본 표 및 설정 조립 변경을 대조하고, `tools/mvp_versions.py`가 읽는 정본 표와 입력 계획을 이번 쌍으로 맞춘다. V2 정책 기록의 승인 범위는 0.30.0 소유 lab이다. 후보에도 적용할 정책 범위를 확정받고 두 판본에 하나의 POL Ref를 사용한다. | `mvp_live_readiness`의 138쪽에 올바른 이미지·팩이 표시된다. 같은 정책 Ref에서 읽는 확정값과 실제 실행에서 결합할 값의 출처가 확인된다. |
| **A-2 AWS 세션과 실서버 사전 점검** | 승인된 세션별 비용·기한·할당량을 확정하고 최신 크레딧·예비금, 전용 실행 역할, EventBridge 감시 대상과 IAM lease를 확인한다. 현재 ENV·target·Pod/컨테이너·노드·세대·준비물 해시를 결합하고 `guard prepare-update` 결과를 보존한다. | 세션 승인, 최신 감시 상태, 양쪽 입력, 실행 묶음과 종료·삭제 검증 방법을 한 세션 기록에서 확인할 수 있다. |

| **A-4 J02 나머지 점검과 재시험** | 나머지 63개를 `guard update`로 비교하며 §4의 우선 유예 항목을 포함한다. 동일 모델·토폴로지·기동 조건에서 독립적인 사례를 묶고, 조건이 바뀌면 새로운 ENV와 비교 계획을 사용한다. B가 재현한 영향 범위를 정확한 소스로 재시험한다. | 69개가 비교 또는 근거 있는 선정 기록으로 연결된다. 적용 점검마다 실제 양쪽 실행, 판정, 세션 종료와 소유 자원 정리 결과가 있다. |
| **A-5 J03 공식 인수** | B의 독립 검토를 반영해 보안 UNKNOWN 집합과 비교 불가 원인을 확인한다. 조건을 충족한 제품 RPT와 69행 인수표를 제출하고 플랫폼에서 같은 RPT Ref로 조회되는지 확인한다. | §1의 모든 조건, 잔여 UNKNOWN의 원인·담당·다음 확인 조건, 원본을 복원할 수 있는 증거 묶음이 확인된다. |

## 5. 실행 순서와 인계

1. **착수.** A-1과 B-1을 병행한다. A는 판본 표와 양쪽 정책의 승인 범위를 확정한다. B는 138쪽의 지원·입력 공백과 첫 회귀 묶음을 낸다. AWS 승인 대기 동안에도 B-2·B-3의 독립 개발과 CI를 진행한다.
2. **소스 동결과 시험 승인.** B는 점검 ID, 양쪽 지원 이미지, 정책·fixture·설정 Ref 및 SHA, 정상 대조, 필수 관측, 예상 공백을 A에게 넘긴다. A는 최종 코드·소스 목록과 CI를 확인하고 AWS 세션을 승인 범위에 맞춰 준비한다.
3. **실측.** A는 준비 검사를 통과한 묶음부터 실행한다. TP2 할당량이 대기 중이면 가능한 J02 묶음을 먼저 수행한다. 같은 점검의 기준·후보는 동일한 비교 조건의 한 PLAN에서 대응한다. J01과 J02의 모델·토폴로지가 다르면 각각의 제품 RPT를 보존하고 69행 인수표에서 점검별 원본 Ref를 연결한다.
4. **결함 수정과 확인.** A는 구체적인 진단 코드와 해당 EVD·RES·RPT Ref, 권한 범위가 확인된 반출 파일과 해시를 B에게 준다. B는 반출 자료와 CI에서 결함을 재현하고 수정 범위를 제시한다. A는 결합값과 원본을 보존하며 승인된 영향 범위만 다시 실행한다.
5. **인수.** B의 복원·재판정 결과와 A의 실제 비교 보고서를 대조한다. 인수표에는 점검 ID, 양쪽 ENV·RES·EVD Ref 또는 선정 근거, RPT Ref, 비교 결과, 공백과 그 조치를 둔다. UNKNOWN이 6개를 넘거나 비교·증거가 누락되면 다음 해결 항목과 필요한 실측을 지정하고 작업을 이어간다.

원본 파일과 판정은 정확한 Ref와 해시로 보존한다. 반출 시 프롬프트·토큰·비밀 원문을 보호하고 필요한 메타데이터와 지문을 사용한다. 보안·기능 판정과 실측 출처는 제품의 원본 RPT를 기준으로 수락한다. [정본 설계](../SPEC.md) · [플랫폼 인수 경계](BYUL_INTEGRATION.md) · [공용 계약](../../contracts/README.md)
